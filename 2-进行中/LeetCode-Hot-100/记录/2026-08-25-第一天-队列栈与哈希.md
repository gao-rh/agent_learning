## Codex 反馈

### 直观区别：重新绑定不是修改原对象

“不可变”描述的是**对象本身**，不是保存这个对象的变量名。

```python
s = "ab"
t = s
s += "c"
```

执行后 `s == "abc"`，`t == "ab"`。这里没有把原来的字符串对象 `"ab"` 改成 `"abc"`，而是创建了一个新字符串，再让变量 `s` 指向新对象；`t` 仍然指向原来的 `"ab"`。

可变列表则不同：

```python
values = [1, 2]
alias = values
values.append(3)
```

`values` 和 `alias` 始终指向同一个列表对象，而这个对象内部从 `[1, 2]` 原地变成了 `[1, 2, 3]`。

Java 中也一样：

```java
String a = "ab";
String b = a;
a = a + "c";
```

变量 `a` 改为引用新的 `"abc"` 对象，`b` 仍引用原来的 `"ab"`。`Integer` 的重新赋值、算术运算和自增也会产生或引用另一个包装对象，并不会修改原 `Integer` 对象内部的值。

### 哈希表真正要求的是 hash 和相等关系稳定

哈希表插入和查询 key 时都要计算哈希值：

1. 插入时通过 `hash(key)` 决定把 key 放到哪个桶。
2. 查询时再次通过 `hash(key)` 决定去哪个桶寻找。
3. 如果 key 在插入后被原地修改，导致哈希值或相等关系改变，查询可能跑到另一个桶，无法找到原来的条目。

因此，更严格的说法不是“世界上只有不可变对象才能当 key”，而是：**作为 key 使用期间，它的哈希值以及参与相等比较的状态必须保持稳定。**

### Python 与 Java 的具体边界

- Python 使用“可哈希（hashable）”作为 `dict` key 的直接条件。`int`、`str`、`frozenset` 通常可哈希；`list`、`dict`、`set` 不可哈希。
- `tuple` 虽然本身不可变，但只有内部所有元素都可哈希时才能作为 key。`(1, "a")` 可以；`(1, [2])` 不可以。
- Python 官方定义要求可哈希对象的哈希值在生命周期内不变，并要求相等对象拥有相同哈希值：[Python Glossary：hashable](https://docs.python.org/3/glossary.html#term-hashable)。
- Java 的 `HashMap` 技术上允许把 `ArrayList` 放进 key；原文说“不能”是面向初学者的安全简化。问题在于 Java `List.hashCode()` 基于列表元素计算，列表内容改变后哈希值可能改变：[Java List.hashCode](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/List.html#hashCode())。因此可变列表不适合作为长期 key，除非能保证放入后绝不修改。

- Python 已验证：字符串重新赋值会得到新对象；列表 `append` 会原地修改同一对象；`hash([1, 2])` 和 `hash((1, [2]))` 都抛出 `TypeError`。

## 发散联想

- “不可变”和“常量”不同：常量限制变量能否重新赋值；不可变限制对象内部状态能否改变。
- Java 赋值对象变量和 Python 变量赋值通常都只是在复制或改变引用，不会自动深拷贝对象。
- 自定义类能否作为 key，不能只看它表面上是否允许修改字段，还要检查 `hashCode/equals`（Java）或 `__hash__/__eq__`（Python）的契约。
