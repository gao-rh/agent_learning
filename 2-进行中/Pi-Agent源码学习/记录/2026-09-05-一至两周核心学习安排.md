# 一至两周的 Pi 核心学习安排

日期：2026-09-05。用户已确认：主要使用 Python，JavaScript 只需按需看懂；只有 1–2 周且非全职投入，聚焦核心，暂用 Kimi。以下课时与取舍为 AI 建议。

本次调整依据：用户“我现在主要用Python，接下来进入下一步吧。”原先以 JavaScript 语法示例起步的安排改为 Python；随后用户进一步要求先知道 Pi 的定位、优势、整体架构和一般机制，再做最小复现。当前入口是 [整体框架导读](../资料/05-Pi整体框架与最小复现边界.md)，[Python 第一课](../实验/python-core/README.md)暂不作为立即作业；不更改历史扩展路线或上游源码。

## 你这次要达到什么程度

亲手完成并解释这一条链：

用户问题 → Kimi 返回工具调用 → 程序检查参数并读取练习文件 → 工具结果加入消息历史 → 再次请求 Kimi → 回答或继续调用工具 → 停止。

完成一个最小命令行 Agent，使用一个 read 工具、非流式模型响应、内存消息列表和顺序执行。代码只覆盖这条执行链；你能关掉参考答案，重写循环的关键逻辑，解释每次消息变化。

本次做到这里即可结束。它是 Pi 核心工具循环的学习复现；完整 Pi 的界面、并发、压缩和持久化机制继续保留为后续内容。

## 第一次学习的具体任务

打开 [Python 第一课](../实验/python-core/README.md)：

1. 先预测：把模拟工具请求追加到消息列表，是否会自动读取文件？
2. 运行观察模式，检查角色、工具名、JSON 参数和调用 ID。
3. 补完 `execute_tool_call`：解析参数、按名称找本地函数、执行、形成结果消息。
4. 运行执行模式，再修改练习文件验证真实读取；解释三条消息各自来自谁。

实际模型调用在后续学习。本课固定模拟模型响应，没有网络与费用，也不提前交付完整循环。TypeScript 注解在对照 Pi 源码时按行解释。

## 核心验收，只看这些

- 正常回答：没有 tool_calls 时结束，不发起多余请求。
- 读取练习文件：程序真的读到文件，工具结果与调用 ID 对齐；能指出第二次模型请求为什么需要前一条 assistant 消息和工具结果。
- 一次响应有多个工具请求：顺序处理，结果不遗漏。
- 故意失败：未知工具、参数不对或文件不存在时，不执行错误操作，返回可解释结果；模型再处理或正常停止。
- 无法完成：循环达到设定上限时停止；输出被长度限制截断的工具请求不执行。
- 独立解释：关掉完整参考，写出简化循环；在纸上列出每次发给模型的消息，解释停止条件。

错误、重复调用与截断用固定模拟响应验证。真实 Kimi 做少量代表案例，调用前说明请求数与 Token/费用范围；本次只是规划，不运行模型。

先理解为何每一步必要，再看 Pi 怎样组织它。不要求背文件名、抄数百行代码或背完整事件类型。

## 对照 Pi，只查这几处

首要原件：[agent-loop.ts](../资料/本地资料/pi/packages/agent/src/agent-loop.ts)。

1. runLoop：何时请求模型、执行工具、继续与结束。
2. prepareToolCall：按名称寻找工具并检查参数。
3. executePreparedToolCall：实际调用工具，接收结果或异常。
4. createToolResultMessage：把结果形成消息。

按需再查 [types.ts](../资料/本地资料/pi/packages/agent/src/types.ts) 和 [read.ts](../资料/本地资料/pi/packages/coding-agent/src/core/tools/read.ts)。streamAssistantResponse 只追踪消息变换与最终结果，流内部细节暂缓。

固定源码使用自己的 AgentMessage/toolResult 类型；Kimi 接口有其 wire 消息格式，接入层需要映射。学习版顺序、非流式行为是简化，不宣称全部复刻上游默认并行与流式实现。
