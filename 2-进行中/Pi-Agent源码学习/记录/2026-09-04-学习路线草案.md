# Pi Agent 学习路线草案

日期：2026-09-04。状态：**AI 草案 / 待确认**。基线：Pi v0.85.0。

> 2026-09-05 更新：用户已确认 JavaScript 零基础、当前只复现核心、暂用 Kimi。当前主线请读[零基础核心复现学习路线](2026-09-05-零基础核心复现学习路线.md)。本文件保留为历史草案与完整范围选学参考；下文“完整范围不可省略”等要求不再作为当前学习目标，待确认的项目身份也已由新记录解决。

## 用户原始目标

> 我计划学习派Agent的，我不太懂JavaScript，我希望你帮我做一个初步的调研，例如把它的源码都下载下来，把相关的文档都梳理一下，然后给我梳理一个学习路线。我想了解这个Agent它是怎么去，就底层执行的所有原理，就不希望只停留在表面，我到最后我希望是能够完整的去复现到这个项目的一个程度。

已知：JavaScript 基础较少；希望从执行原理一直达到完整复现，而不止会用。

未知：项目名称最终确认、语言的具体基础、每周时间、模型预算、最终覆盖范围。没有继承旧 30 天计划或其他求职排期。

## 最影响路线的选择：怎么跨过语言门槛

| 方案 | 优点 | 代价 / 适用条件 |
| --- | --- | --- |
| A. 先系统学完整 JavaScript/TypeScript，再读 Pi | 语言上下文更完整 | 反馈较晚，容易学习大量暂用不到的浏览器知识；适合语言几乎零基础且愿意长线铺垫 |
| B. 按源码需要补语言，同时做逐层复现 | 每个语法点立即对应机制，复现不脱离原仓库 | 需要每课控制难度并回补基础；本次建议 |
| C. 先用熟悉语言重写最小 Agent，再回到 TS | 能较快理解工具循环 | 容易跳过 JS 异步与真实工程细节；只能是桥梁，不能作为完整 Pi 复现终点 |

建议 B，但尚未记录为用户决定。不要求先学前端，也不把“我用 SDK 写出了十行”算作核心复现。

## 分层目标，不降低终点

- **读源码能力**：能够解释一条执行轨迹、找到对应函数与状态。
- **核心机制复现**：自己的事件流、provider 接口、Agent Loop、工具执行和失败处理；不能只包一层 Pi SDK。
- **普通 Coding Agent 功能复现**：再补历史/分支/压缩、扩展、CLI、TUI、RPC/SDK。
- **固定版本完整范围对齐**：再覆盖已实现的新 Harness、存储后端、协议与 client/server、包级功能和回归矩阵。

前三级只是里程碑。若用户最后选择全部 monorepo 已实现功能，则第四级不能省略；上游明确未实现的设计另列，不当作已完成功能要求。

可以复用通用库（HTTP/供应商 SDK、TypeBox、SQLite 驱动、测试框架），但核心 Loop、状态转换、工具分发和会话构造应能自己实现与解释。是否逐个 provider、平台和 TUI 细节做行为等价，在最终功能清单中逐项列明，不能口头宣称“全复现”。

## 阶段路线

### M0 — 基线、边界和第一次执行轨迹

阅读：[源码快照说明](../资料/00-源码快照与获取说明.md)、[执行地图](../资料/01-项目初步调研与执行地图.md)、上游 agent README 的事件示例。

任务：

- 确认项目身份，选定不自动升级的源码基线。
- 画/手写一条“读取文件后回答”的消息和事件序列。
- 分清用户输入、模型返回、Node 执行、磁盘写入、UI 渲染。
- 做补课清单中的五个摸底题。

产物：一页自己的执行轨迹与未知点。通过标准：能解释模型输出工具名为何不会自动让操作系统执行它。

本轮只完成资料准备与静态追踪，用户尚未完成此阶段。

### M1 — 够用的 JS/TS 与异步运行基础

阅读：[补课清单](../资料/03-JavaScript与TypeScript补课清单.md)、EventStream、AgentEvent 类型。

动手产物：

- 消息数组变换器、工具注册表。
- 自己的异步事件队列，支持 push、for await、end、result。
- 三个小测试：提前缓存事件、消费者等待唤醒、完成后不再接受事件。

通过标准：先预测再运行日志顺序；讲清闭包、浅拷贝、Promise、泛型与取消信号。不能只复制原 EventStream。

### M2 — 模型不是魔法：消息协议与流式适配

阅读：pi-ai README 的 Quick Start、Tools、Event Reference、Stop Reasons、Faux Provider；types.ts、models.ts、一个 API 适配器、json-parse.ts。

动手产物：

- 自己定义精简 Message/ToolCall/Usage/Event。
- 用假 provider 返回文字分片、工具调用和失败，不接真实模型。
- 实现至少一种真实 provider 协议的适配（在后续费用说明后小样本验证）。

通过标准：区分 API/provider/model；解释流式参数半成品、最终结果、错误与中止；抓到分片不足时不会过早执行工具。

真实模型成功不是这一阶段唯一证据：相同假响应必须产生可预测的完整事件轨迹。

### M3 — 自己实现 Agent Loop 与真实工具边界

阅读：agent-loop.ts → agent.ts → validation.ts → read/write/edit/bash → file-mutation-queue。

先在合成目录实现只读工具，再添加写/编辑与受控 shell。能力逐项添加：

1. 用户消息 → 模型 toolCall → 工具结果 → 再次模型请求 → 正常退出。
2. 未知工具、参数非法、工具异常和输出截断。
3. 串行/并行工具执行，完成事件顺序与历史顺序分离。
4. steering/follow-up 两类队列，取消与超时。
5. before/after hook、terminate 与 shouldStopAfterTurn。

产物：不依赖 Pi agent-core 的小型运行内核，以及无模型回归测试。

通过标准：可以自己加一个工具；能通过故障注入说明为什么不会把被长度截断的写文件请求执行出去；能说明取消后哪些副作用不可撤回。

### M4 — 会话、上下文与长任务

阅读：sessions.md、session-format.md、compaction.md；session-manager.ts、messages.ts、compaction/。

动手产物：

- JSONL 追加日志、消息 ID/父节点、当前分支。
- 重启后恢复对话上下文；分叉且保留旧历史。
- 上下文预算与摘要策略；先用固定摘要 mock，再验证真实摘要。
- 压缩失败、中止、上下文超限后的处理。

通过标准：拿同一份历史手工算出当前分支和下一次模型输入；toolCall/result 不被错误切散；能证明“历史仍在”与“模型已经看不到旧全文”同时成立。

注意：普通会话恢复并不自动等于工具中途崩溃的持久化恢复，那是 M7。

### M5 — 可扩展但有明确权限边界

阅读：extensions.md、skills.md、prompt-templates.md、settings.md、security.md、containerization.md；resource-loader、extensions/。

动手产物：

- 项目/全局资源加载与来源标注。
- 一个 skill、一个模板、一个注册自定义工具并订阅事件的 extension。
- 实验目录内的工具执行策略与隔离说明。

通过标准：解释“文字指令”和“宿主进程代码”的区别；能用日志证明加载顺序和扩展 hook 生效；知道 project trust 不限制启动后的文件/进程权限。

权限限制可作为复现版本的附加安全功能，但与上游默认行为分开记录。

### M6 — 交互和协议也是系统的一部分

阅读：pi-tui README、terminal.ts、两种 TUI 屏幕实现；json.md、rpc.md、sdk.md；对应 modes/。

动手产物：

- 同一个内核被普通 CLI、JSON/RPC 和 SDK 调用。
- 流式 TUI：输入、状态、工具进度、取消、滚动/尺寸变化的核心行为。
- 控制协议输出与调试日志分离。

通过标准：用相同假 provider，从不同入口得到等价消息历史；RPC 断开/取消不污染协议；终端正常退出时恢复输入状态。完整终端按键、图片协议和平台细节列入最终差异清单，不能省略后直接叫完全兼容。

达到 M6 可称“普通 Coding Agent 主链路复现”，但还不是新版全仓完成。

### M7 — 深入新版持久化 Harness 与跨进程运行

先读 agent/docs/harness.md 的 §0.9 实现状态，再读 Orientation、operation 状态机、执行/恢复/取消与不变量；对照 src/harness 和测试，不先通读全部设计草稿。

建议拆成四个可独立验收的小段：

1. Session、Branch、AgentLane 与事务/变更序列；用内存后端对照 JSONL/SQLite。
2. accept 与 drive 分离，工具 intent、结果 staging、检查点与恢复。
3. 取消请求、进程 close、RPC 断连三种事件的不同语义。
4. Chord 服务与状态复制，protocol 分帧、client/server 路由与 attachment 身份。

产物：可故障注入的持久运行内核，最小跨进程客户/服务端，以及事务边界测试。

通过标准：在工具前、执行后但提交前、结果提交后分别杀进程；能解释每次恢复是否可能重复外部效果；完成请求 ID/附着身份隔离测试。

不把文档未来项自动实现为新产品需求；watchSession 等当前明确未实现的接口写入差异清单。此阶段复杂度已超出小实验，须在独立仓库和独立开发任务进行；本主题只留学习记录与链接。

### M8 — 固定版本功能对齐与独立复现验收

阅读各包公开 exports、README、CHANGELOG、测试，并将已实现功能拆为可验收清单。补齐尚未覆盖的 provider、图像输入/生成、认证与模型目录、工具、终端、扩展、打包/平台等范围。

产物：

- 自己实现的项目、架构说明、运行说明、版本与依赖锁定。
- [复现验收矩阵](../资料/04-复现验收矩阵.md) 中每项的本地日志、测试和差异。
- 上游功能 → 自己的模块 → 验证方法 → 未实现/不适用原因的对照表。
- 与上游在固定 fake/model 输入下的差分结果；允许不同输出表示，但事先约定语义相等的标准。

通过标准：

1. 能不看源码讲清主链路，并现场实现/修复一个局部机制。
2. 不依赖 Pi 核心包“代做”声称已独立复现的核心功能。
3. 正常、失败、并发、取消、重启/恢复都有证据。
4. 所有声称完整覆盖的功能有测试或明确人工验收；其余全部公开列为差异。
5. 不声称复现了上游尚未实现的功能或外部模型内部原理。

“读完”“跑通”“自己写出”“行为对齐”是四个不同成果，分别记录。

## 每次学习怎么进行

每次只取一个机制：

1. 先由用户说出预测或当前理解。
2. 阅读一个关键函数/一小组相互依赖函数，解释设计问题与反例。
3. 用户写或改一个最小实验、运行、描述现象。
4. 对照原项目和测试，注入一个失败条件。
5. 用户复述结论；按 已理解 / 待继续 / 待验证 记录，不由 Codex 自动转正。

环境诊断和资料整理可由 Codex 完成；完整实现不提前替用户写完，以免遮住其真正需要掌握的机制。

## 排期与成本边界

当前不给承诺式周数：每周投入、语言摸底和最终范围尚未确认。先用 M0–M1 的实际耗时校准，再制定节奏。M7–M8 是系统工程，不应包装成几天速成。

早期用假 provider 和合成文件，新增真实模型调用为 0。后续真模型默认约 10 个代表案例，执行前给出新增案例数、预计调用次数、Token/费用范围；全量 provider/模型矩阵需另行确认，不自动运行。
