## 1. 这部分在整个项目中的位置

理赔客服风险质检项目的核心目标，是从已有 ASR 文本中筛查疑似辱骂、明显冲突等可能导致客诉的高风险通话。脱敏不是项目的核心识别能力，而是文本进入后续模型处理前的一道隐私保护边界。

完整链路可以概括为：

```text
已有 ASR 文本
  ↓
关键词预筛
  ↓
内部模型初审
  ↓
规则 + AI 混合脱敏
  ↓
外部模型复审
  ↓
人工审核
```

脱敏子链路解决的问题是：

> 在文本离开受控环境、进入后续外部模型之前，尽可能识别并替换敏感信息，同时尽量保留风险复审仍然需要的语义和业务上下文。

它不直接负责判断客服是否存在辱骂或冲突，也不能把脱敏指标与风险识别准确率混为一谈。

- 用户已确认：脱敏方法与《深入理解 AI Agent》第 3 章实验 3-3 的方法一致，可以用该实验作为公开、去标识化的等价实现进行讲解。
- 后期项目形态按 Python 多阶段 Workflow 及用户确认效果记录；不能从早期材料推导整个项目尚未上线，也不能把公开实验当成公司部署证明。

## 3. 脱敏子链路的核心设计

### 3.1 为什么不能只用 Regex

Regex 适合结构明确、可枚举的敏感信息，例如：

- 手机号等固定长度数字模式；
- 身份证等带校验规则的编号；
- 银行卡等可结合 Luhn 算法验证的数字；
- `password=...`、`token=...` 等显式字段；
- API Key、Bearer Token、连接串密码等固定格式凭据。

优点：

- 延迟低；
- 结果确定；
- 不需要模型；
- 方便测试和审计；
- 对强格式信息通常比小模型更稳定。

局限：

- 只理解字符形状，不理解业务语义；
- 无法仅凭 `13912345679` 判断它是手机号还是订单号；
- 容易漏掉“我的网银登录口令是……”之类自然语言表达；
- 规则数量不断增加后，维护成本和冲突概率上升；
- 中英文标点、字段别名、日志格式变化都可能造成边界错误。

### 3.2 为什么不能只用 LLM

受控环境内的模型适合识别依赖语义的敏感内容，例如：

- 自然语言描述的密码；
- 口语化地址；
- 医疗诊断、治疗信息和病历编号；
- 同样格式但语义不同的手机号、订单号、SKU、指标值；
- 需要结合上下文判断的账号、证件或身份信息。

优点：

- 能利用上下文；
- 不需要为每种自然语言表达手写规则；
- 可以输出类型、位置和置信度等结构化结果。

局限：

- 延迟和资源成本明显高于 Regex；
- JSON Schema 只能约束返回形状，不能保证判断内容正确；
- 模型可能发明类型、返回错误位置或过宽文本；
- 小模型可能重复生成、输出截断 JSON 或直接失败；
- 同一模型在不同上下文中可能出现不一致结果；
- 不能把模型自报的 confidence 直接当作经过校准的真实概率。

### 3.3 为什么采用 Hybrid

Hybrid 的职责分工是：

```text
Regex
  → 处理低成本、高确定性的强格式信息

受控模型
  → 补充需要上下文理解的语义型敏感信息
```

它想解决的不是“让模型更聪明”，而是：

- 减少强格式信息对模型能力的依赖；
- 让模型把能力集中在语义型长尾；
- 在模型失败时仍保留一部分确定性的规则保护；
- 用不同机制覆盖不同的失败模式。

需要明确的限制是：如果 Regex 已经把订单号误删，后面的模型看不到原始订单号，不能自动恢复。因此 Hybrid 通常有助于提高覆盖率，但不天然提高 Precision，也不天然更快。

## 4. 公开等价实现的完整处理流程

下面描述的是可在面试中公开讲解的等价实现，不是公司内部代码。

### 4.1 第一步：接收输入

输入是需要进入后续风险复审的文本：

```python
text = "Support transcript: call me at 13912345678 ..."
```

生产实现中，应该明确输入契约：

- 输入是否只有 ASR 正文；
- 是否包含说话人、时间戳、通话 ID 等结构化字段；
- 哪些字段允许进入外部模型；
- 哪些字段必须在更早阶段直接删除。

本文只确认 ASR 文本链路，不补造公司内部元数据结构。

### 4.2 第二步：Regex 检测强格式信息

规则表中的每条规则包含：

```python
RegexRule(
    category="cn_phone",
    placeholder="[REDACTED_PHONE]",
    pattern=re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"),
    validator=None,
)
```

运行后不应该只返回“命中了”，而应保存可审计候选：

```python
Finding(
    pii_type="cn_phone",
    value="13912345678",
    start=32,
    end=43,
    confidence=1.0,
)
```

对于身份证和银行卡等类型，还可以增加确定性校验函数：

```text
Regex 形状匹配
  ↓
身份证校验码 / Luhn 校验
  ↓
通过后才形成 Finding
```

校验算法可以降低一部分数字误报，但仍不能代替业务上下文判断。

### 4.3 第三步：模型检测语义型敏感信息

模型的职责不是直接重写全文，而是返回结构化 findings：

```json
{
  "findings": [
    {
      "type": "password",
      "value": "Blue moon over river 77",
      "start": 14,
      "end": 37,
      "confidence": 0.98
    }
  ]
}
```

Prompt 中至少需要明确：

- 允许识别的敏感类型；
- `value` 必须逐字来自原文；
- `start/end` 使用什么下标约定；
- 需要区分真实敏感值、字段名、说明文字、订单号、产品编号和显式诱饵；
- 不要在 value 中返回解释、标签或占位符；
- 返回结果必须符合指定 Schema。

推荐的模型职责边界是：

```text
模型负责判断和定位
确定性代码负责校验和替换
```

不让模型直接返回“改写后的整篇文本”，是为了避免它修改非敏感内容，也便于后续计算精确率、召回率和误删范围。

### 4.4 第四步：校验模型结果

任何模型 Finding 都不能不经检查直接执行。至少验证：

```python
text[start:end] == value
```

如果位置不正确，可以尝试在原文中查找精确 value：

```python
start = text.find(value)
end = start + len(value)
```

仍然找不到时必须丢弃该 Finding，不能根据模型描述猜测替换范围。

还需要：

- 统一类型别名；
- 去除 value 外层多余引号；
- 限制 confidence 在 0～1；
- 对重复 Finding 去重；
- 处理相互重叠的区间；
- 拒绝模型返回的原文外内容。

`text.find(value)` 也有局限：同一个值出现多次时会默认选择第一次，因此更严谨的实现需要保留并验证模型返回的位置或逐个匹配上下文。

### 4.5 第五步：合并 Regex 与 LLM Findings

公开实验采用 Regex-first / LLM-second：

```text
原始文本
  ↓
Regex findings
  ↓
先把 Regex 命中替换为占位符
  ↓
模型检测剩余文本
  ↓
把模型发现映射回原文位置
  ↓
合并并去重
```

伪代码：

```python
regex_hits = regex_findings(original_text)
regex_redacted = redact(original_text, regex_hits)

remaining_hits = llm_findings(regex_redacted)
mapped_hits = map_back_to_original(remaining_hits)

final_hits = normalize(regex_hits + mapped_hits)
```

该方式的优势是模型不用重复处理规则已识别的敏感值；缺陷是 Regex 的误删不可逆。

一种可作为面试改进思路、但不能冒充真实项目已实现事实的变体是：

```text
Regex 只生成候选，不立即替换
  ↓
高确定性候选直接接受
  ↓
语义模糊候选交给模型复核
  ↓
统一形成 final findings
  ↓
只执行一次替换
```

这种候选优先模式更有机会保护订单号等业务字段，但需要额外设计置信度、字段策略和冲突决策。

### 4.6 第六步：执行确定性替换

替换时按照 `start` 从右向左处理：

```python
for finding in sorted(findings, key=lambda x: x.start, reverse=True):
    text = (
        text[:finding.start]
        + f"[REDACTED_{finding.pii_type.upper()}]"
        + text[finding.end:]
    )
```

为什么从右向左：

- 先改右边不会影响左侧字符下标；
- 如果从左向右替换，占位符长度变化会使后续 start/end 失效。

保留带类型占位符而不是直接删除，可以让后续风险模型知道“这里原本有一个手机号/地址/密码”，同时看不到真实值。

### 4.7 第七步：只把脱敏文本交给外部模型

边界应该是：

```text
受控环境内部：原始 ASR + findings + 替换逻辑
受控环境外部：只传 sanitized_text
```

需要注意，模型调用回执、调试日志和评测文件如果保存了原始输入，本身也会重新形成敏感信息副本。因此“主文本已脱敏”不等于整条工程链路已经安全。

## 5. 一个与项目问题直接对应的案例

输入：

```text
客户说：请打我的电话 13912345678。
工单 13912345679 明天继续处理。
登录密码是 Blue moon over river 77。
```

正确目标：

```text
客户说：请打我的电话 [REDACTED_CN_PHONE]。
工单 13912345679 明天继续处理。
登录密码是 [REDACTED_PASSWORD]。
```

这个案例同时验证三种能力：

1. 找到真实手机号；
2. 通过上下文保留同样格式的工单号；
3. 找到没有 `password=...` 格式的自然语言密码。

Regex 可能把两个 11 位数字都删掉，并漏掉自然语言密码。LLM 可能理解语义，但也可能返回过宽范围或不稳定 JSON。Hybrid 可以补充语义遗漏，却可能继承 Regex 对工单号的误删。

这正是为什么脱敏不能只用一个“是否发现 PII”的指标。

## 6. 必须同时评价的指标

### 6.1 隐私保护指标

| 指标 | 含义 |
| --- | --- |
| Recall | Gold 敏感值中有多少被精确找到 |
| Residual Leakage | 脱敏后还有多少敏感值残留 |
| Partial-span Leakage | 敏感值是否只删掉一部分、仍留下可识别片段 |
| Critical-type Recall | 身份证、手机号、银行卡等高风险类型的单独召回 |

### 6.2 日志可用性指标

| 指标 | 含义 |
| --- | --- |
| Precision | 预测要删的内容中，有多少真的应该删 |
| Utility | 非敏感字符和业务上下文保留程度 |
| Protected-field Accuracy | 订单号、工单号、SKU、指标等必须保留字段是否被误删 |
| Typed Exact | 类型和精确 value 是否同时正确 |

### 6.3 工程可靠性指标

| 指标 | 含义 |
| --- | --- |
| Invalid JSON Rate | 模型返回无法解析结果的比例 |
| Timeout/Error Rate | 模型超时或调用失败比例 |
| Degraded Rate | Hybrid 退回 Regex 的比例 |
| p50/p95 Latency | 典型和尾部延迟 |
| Throughput | 单位时间可处理的文本量 |

### 6.4 为什么不能只说“接近 100% 脱敏”

“敏感原值在输出中消失”可以通过删除整句话实现，因此必须同时回答：

- 是精确删除，还是扩大范围删除？
- 是否误删了订单号或风险识别所需上下文？
- 是否只删除了敏感值的一部分？
- 模型失败时原文是否仍会落盘？
- 测试集是否覆盖真实生产表达？

公开复现中，Hybrid 在 18 个 Gold 敏感值中让 15 个完整字符串消失，比例为 83.3%；精确 value 的 micro recall 为 72.2%，micro precision 为 65.0%，并有 1 个 degraded 案例。这些是公开学习实验数据，不能写成公司项目指标。

## 7. 失败处理与生产边界

### 7.1 已在公开实现中验证的问题

- 本地 API 请求可能被系统代理错误转发，导致访问回环地址也返回 502；显式设置 `trust_env=False` 可以隔离本地 Ollama 请求。
- Qwen3 的 thinking 模式可能把生成预算耗尽在重复推理中，导致最终 content 为空；结构化抽取任务可以显式关闭 thinking。
- 小模型仍可能重复生成直到截断，返回无效 JSON。
- SDK 返回的 `datetime` 等对象不能直接交给标准 `json.dumps()`，需要先转成 ISO 字符串。
- 模型输出失败不应让整个批次无记录地中断；必须保存调用回执和失败状态。

### 7.2 公开教学实现采用的失败策略

```text
直接 LLM 输出无效
  → 标记 failed
  → 按没有完成脱敏计算残余泄漏
  → 继续其他案例

Hybrid 第二阶段输出无效
  → 标记 degraded
  → 回退 Regex 第一阶段结果
  → 继续其他案例
```

### 7.3 隐私优先生产环境的改进建议

以下是基于实验得到的工程建议，不标记为真实项目已完成：

```text
模型失败或输出无法校验
  → 不允许未经确认的原文本进入外部模型或正式日志库
  → 丢弃、隔离或进入受控人工检查区
```

这叫 fail closed。直接回退 Regex 虽然提高可用性，但对于 Regex 无法识别的医疗、地址和自然语言隐私，仍可能泄漏。

生产化还需要：

- 代表性真实样本的去标识化离线评测；
- 规则、模型、Prompt 和 Schema 版本管理；
- 灰度、回滚和失败告警；
- 原始文本、findings、回执和缓存的访问控制；
- 对订单号等关键业务字段建立保留策略；
- 预热、重复多轮测试并报告 p50/p95；
- 对高风险类型设置更严格的验收门槛。

## 8. 性能结论应该怎样讲

不能说“加 Regex 后 Hybrid 一定更快”。理论成本是：

```text
Hybrid 延迟 = Regex 延迟 + Hybrid 第二阶段 LLM 延迟
```

只有 Regex 让模型输入或输出明显减少，节省的模型时间才可能超过规则开销。

本次公开实验中：

```text
全部案例平均：
直接 LLM 约 1988 ms
Hybrid 约 1620 ms

去掉 medical 异常案例：
直接 LLM 约 891 ms
Hybrid 约 871 ms
```

差距缩小到约 20 ms，不能证明 Regex 构成稳定加速。调用顺序、模型预热、输出 token、系统调度和异常生成都会影响单轮均值。

严谨性能实验需要：

- 先预热模型；
- 交错或随机化策略执行顺序；
- 每个案例重复多轮；
- 同时记录输入/输出 token；
- 报告 p50、p95 和吞吐量。

## 9. 面试中的推荐讲述主线

### 9.1 30 秒版本

> 项目需要把理赔客服 ASR 文本交给后续模型做风险复审，但原始文本可能包含敏感信息，所以我在外部模型之前增加了规则和 AI 组合的脱敏环节。强格式信息先由 Regex 和校验算法处理，自然语言地址、密码等依赖上下文的内容由受控环境内的模型补充识别。检测结果统一成类型、原文和位置，再由确定性代码完成替换。这个设计的重点不是单纯追求召回，而是同时控制残余泄漏、误删和模型失败。

### 9.2 两分钟版本

> 脱敏是风险质检链路中的隐私边界，不是项目核心的风险分类能力。我们面对的是已有 ASR 文本，需要先经过关键词和内部模型筛选，再把候选文本交给后续模型复审。为了避免原始敏感文本直接进入外部模型，我采用了 Regex 与 AI 组合的脱敏方式。
>
> Regex 负责手机号、证件号、Token、显式密码字段等格式明确的内容，并结合校验算法减少误报；受控模型负责自然语言密码、地址、医疗信息等依赖上下文的内容。两边都只返回结构化 findings，包括类型、精确原文和位置，真正的替换由确定性代码从右向左执行，从而避免模型改写非敏感文本。
>
> 这套方法的关键取舍是，Hybrid 可以提高覆盖率，但不会自动修复 Regex 的误删。例如订单号与手机号格式相同，Regex 先删后，后续模型无法恢复。因此评价时不能只看“敏感值有没有消失”，还要看 Precision、Utility、残余泄漏、无效 JSON 和降级率。公开复现实验也暴露过小模型返回截断 JSON的问题，所以工程上还要设计校验、失败状态、隔离和回滚。

### 9.3 面试追问与回答重点

#### 为什么不用纯 Regex？

自然语言密码、地址和医疗信息没有稳定格式；规则无法可靠理解订单号和手机号的语义差异。

#### 为什么不用纯 LLM？

强格式信息用规则更快、更稳定；模型有延迟、误报和结构化输出失败问题。

#### 为什么模型只输出 findings，不直接输出脱敏全文？

为了校验 value 是否来自原文、精确控制替换范围、计算指标，并避免模型修改非敏感上下文。

#### Hybrid 最大的问题是什么？

如果 Regex 先执行了错误替换，后续模型不能恢复原值；Hybrid 提高覆盖率，不保证提高 Precision。

#### 模型输出坏 JSON 怎么办？

首先保存回执并标记失败，不能把异常当成空 findings；隐私优先场景应阻止未经确认的原文继续外传，进入隔离或受控人工检查。

#### 怎样评价脱敏效果？

同时看 Recall、Residual Leakage、Partial-span Leakage、Precision、Utility、关键字段保留率、Invalid JSON Rate 和 p95 延迟。

## 10. 面试表述红线

不要说：

- “项目已经实现接近 100% 的脱敏准确率。”
- “Hybrid 一定比纯 LLM 更快。”
- “使用本地模型就已经完全没有隐私风险。”
- “JSON Schema 能保证模型输出正确。”
- “风险识别查准率就是脱敏准确率。”
- “公开实验使用的 Qwen3/Ollama 就是公司内部真实技术栈。”
- “公开脱敏实验已经独立证明公司客诉改善。”

可以说：

- “项目采用规则与 AI 组合的脱敏方法，在文本进入外部模型前建立隐私边界。”

- “Hybrid 在公开样本上降低了残余泄漏，但仍会继承规则误删，并存在模型输出无效的工程风险。”
- “风险识别和脱敏指标分开评价；项目效果按当前手册中的用户确认口径说明。”
