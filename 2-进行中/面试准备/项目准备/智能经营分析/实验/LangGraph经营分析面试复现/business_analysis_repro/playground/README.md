## 模型到底拿到了什么知识

模型首先看到工具描述及理解任务的要求，不会一次收到整批公司报告。它在需要时调用：

1. `search_metrics`：通过名称、别名、子串和相似度召回候选 ID/标准名称/摘要。
2. `get_metric_definition`：按精确 ID 读取模拟目录的定义、单位、支持维度、枚举范围以及 SQL/平台配置。
3. `search_dimensions`：查维度名字，并返回该指标是否支持。
4. `search_dimension_values`：查枚举与所属维度，包括“全局存在、本指标不支持”的情况。
5. `search_business_knowledge`：查业务专题、方法、推荐指标及适用范围。
6. `finish_resolution`：提交结构化意图、指标、时间、分组和筛选；由程序检查后才能进入取数。

这是真实 Kimi Tool Calling：模型返回 `tool_calls`，程序运行函数，结果以 `ToolMessage` 回到同一次循环。取数 Agent 仍是普通 Python 函数；分析 Agent 是封装在函数内的有限模型决策与工具执行循环；外层 LangGraph 控制父图，用 Send 给同一个 worker 节点分发不同指标输入。没有接向量库、ES 或线上指标平台，搜索是本地小目录匹配。

程序先验证全部指标、维度、枚举与实际日期，再做日期语义辅助复核，然后分发独立任务。查询与比较数字由代码计算，分析方向由模型根据证据提出，结果按 job_id、revision、指标与完整范围校验后汇总。模型收到总体事实、分组覆盖数量、少量变化样例，以及分析步骤/假设/补查证据，完整表格由代码交付；摘要失败时保留已校验的数据表。自然语言和摘要仍依赖模型，不能把一次验收当作对所有表达的保证。

最多20个子任务、5个同时执行；同一任务最多40次模型请求，每次理解最多10轮工具循环，连续3次检索无进展提前澄清；最多四轮澄清和一次摘要重写。当前不做跨指标SQL合并，分析分支内的本期/前期仍顺序查询。

## 对话、State 与 Trace 在哪里

```text
.runs/playground/<conversation_id>/
  conversation.json                 # 网页消息、最近任务与等待状态
  tasks/<thread_id>/
    checkpoints.sqlite              # LangGraph 的状态历史、interrupt 恢复位置
    state.json                      # 本任务最后 State 的可读导出
    trace.jsonl                     # 逐事件日志，包含模型请求/响应与工具调用
    trace.html                      # 无需模型生成的可读回放
    graph.mmd                       # 本次主图拓扑
```

同一次澄清继续原 `thread_id`。已经答完后的新问题使用新 `thread_id`，显式带入最近三个已完成任务的摘要。网页刷新会从本机保存的会话恢复消息；“新对话”换一个 conversation ID。

点击每条回复开头的“查看执行路线”，可以看实际走过的父图节点、指标分支及内部函数调用，逐步回放并点击查看详情。下方“查看这次执行回放”保留完整日志，包括输入、工具返回、模型对话与 State 变化。原始日志不会自动拼到每个节点的模型上下文中，也不记录模型不可见的内部思考。
