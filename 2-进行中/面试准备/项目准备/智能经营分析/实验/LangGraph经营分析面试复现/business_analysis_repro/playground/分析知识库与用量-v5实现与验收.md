## 2. 当前实际执行顺序

```text
用户问题
  → 检索指标 / 枚举 / 业务知识，确认查询范围
  → 主图准入并拆分独立任务
      ├─ 查数：调用模拟查询函数
      └─ 分析：读 Skill → 两期查询 → 计算比较证据
                          ↓
                    Kimi 选择下一步
                    ├─ compare → 校验维度、过滤与预算 → 两期补查 → 回看结果
                    └─ finish  → 发现、假设、待核验事项
  → 汇总结果 → Kimi 流式生成报告 → 复核 → 交付表格、Trace、用量
```

父图仍是 `understand_request / clarify / metric_worker / gather_results / compose_reply / validate_reply` 六个节点。分析函数内部步骤是嵌套调用与日志事件，没有把每个步骤都扩成 LangGraph 节点。

- 独立指标仍可并行，进程内最多5个 worker；模型请求也共用5个名额。
- “先看渠道，再根据结果补查来源”留在同一个分析 worker 内，后一查询要等前一结果。
- 每个分析分支最多两次补查、三次模型决策；用户明确要求只补查一层/一次时，最多一次补查、两次决策。
- 原任务的指标、日期和筛选范围不能被补查放大。新增维度、枚举必须在该指标白名单内，相同查询不重复执行。
- 一个任务最多40次模型请求；局部分析失败会保留已查询的证据，并标明分析未完成。已有的安全查询重试也会计入 Trace 和请求数。

这里是短链路、有限的分析行动循环，并非通用长任务规划器。依赖识别使用 Prompt 和保守规则补充，尚未验证任意复杂中文依赖表达；也不跨指标合并 SQL。

### 一个真实执行例子

输入：“分析上周外卖险加入商户数的渠道变化，先按一级渠道比较，再根据结果选择一次获客来源补查，写简易报告。”

1. 工具得到总体 5,600 户次，前期 7,000 户次；主动触达减少714户次，为当前各渠道绝对降幅最大。
2. 模型提出“可能是商家端 APP 来源减少”，决定筛选主动触达，再按获客来源查询。
3. 工具实际返回：电销减少343户次，地推减少245户次，商家端 APP 减少126户次。
4. 模型调整解释方向：电销降幅最大，三来源均下降；关于外呼量、转化率、触达策略的解释仍是待验证假设。
5. 报告同时保留原4行渠道表、补查3行来源表和两份证据 ID。

这体现了根据证据改变分析方向，不能据此证明某个业务原因。方法和模型判断可能出错；完整数字、标准枚举名和单位以工具表格为准。未做分析质量基准评测。

### 模型实际生成什么

一次 `AnalysisAction` 的精简示例（为便于阅读缩短了原理由）：

```json
{
  "action": "compare",
  "reason": "主动触达渠道减少最多，进一步检查其获客来源",
  "hypothesis": "可能由商家端APP来源减少驱动，尚未验证",
  "group_by": ["source"],
  "filters": {"channel_l1": ["proactive"]},
  "finding": "",
  "evidence_ids": ["demo-2f6f42505d60-comparison"],
  "open_questions": []
}
```

`action/reason/hypothesis/group_by/filters/finding/evidence_ids/open_questions` 由模型提议。步数、预算、执行状态、是否准入、实际结果和新证据 ID 由代码写入。模型回显 `status`、`budget` 时仅忽略这两个程序字段，不允许模型改变预算；其他未知业务字段仍拒绝。

分析决策使用结构化 JSON，再由 Python 调用查询函数；指标检索阶段沿用真实 Kimi `tool_calls`。两处实现方式不同。分析步骤放在结果的 `investigation` 中进入 State/checkpoint，过程中每次决定和补查都会先写 Trace；当前循环中途不是独立的可恢复 LangGraph checkpoint。

## 3. 简易知识库与 Skill

| 内容 | 保存位置 | 当前检索或选择方式 |
| --- | --- | --- |
| 20个指标、维度、枚举、平台/SQL模拟配置 | `knowledge.json` | 名称、别名、子串和模糊相似度召回，精确ID读取与准入 |
| 5条业务知识 | `business_knowledge.json` | 关键词和别名匹配，返回来源、适用边界、推荐指标 |
| 4份分析方法 | `analysis_skills/*/SKILL.md` | 按已确认指标选择保费、渗透率、渠道或商户方法 |

这些 Skill 是应用运行时读取的本地方法文件，不是安装给 Codex 的全局技能。它们参考当前项目手册整理，标明实验草案来源，不冒充公司线上原件。

模型不会一次接收整批公司报告。理解阶段按需检索；分析阶段接收所选方法、指标定义、原范围、当前证据摘要、已执行步骤和剩余预算。变化排序基于工具的全量分组计算，模型上下文只取变化最大的6组；完整分组留在工具结果和网页中。

这是本地小型知识库，没有 embedding API、向量数据库或 ES。分数是匹配程度，不是答案正确概率。线上指标平台继续模拟，平台共享 Token 刷新服务没有实现；其错误分类和设计方案已在问题解答 Q13/Q14 中说明。

## 4. 用量如何一直统计

新的每条回复下方自动显示本轮请求数、输入/输出 Token、缓存输入和估算费用；澄清、失败、修复和检查调用也计费计数。Trace 在磁盘上持久保留，用量页面按日志重新计算，因此服务重启后可继续累计。

| 粒度 | 统计规则 |
| --- | --- |
| 一次模型请求 | 记录实际 `model_request` 与返回的 `usage` |
| 一轮用户输入 | 一次 `run_id`，包含本轮工具循环、分析和报告等模型请求 |
| 一个任务 | 一个 `thread_id`，包含等待用户补充后的多次恢复 |
| 一个会话 | 同一 `conversation_id` 下的所有任务 |
| 整个实验 | 当前 `.runs` 中保存的真实 Kimi 日志，去掉镜像事件重复；包括历史开发验收 |

只统计请求/响应事件，不把 State 快照和流式片段再加一次。缓存 Token 属于输入 Token 的一部分，不能重复加入总量。失败但返回 usage 的调用仍累计；缺 usage 的请求明确列为未知，不当作免费。

均值按引擎版本及任务类型分组，只纳入完成、有完整 usage、且分析调查完成的任务。部分失败保留费用，但不进入“完整完成任务均值”。分析任务可以含多个指标，不能把每个分析任务都当成固定成本。

本地滚动60秒峰值 RPM 按请求开始计，TPM 按收到 usage 的时刻计，只是客户端观测，不等于供应商精确的限流计量。5个并发名额也不是按分钟限流器。本轮未添加 LangSmith、账单平台、分布式限流或凭据服务。

价格参数核对于2026-09-09：Kimi K2.6 每百万 Token 普通输入 ¥6.5、缓存输入 ¥1.1、输出 ¥27；金额是按返回 usage 估算，最终以供应商账单为准。[官方价格](https://www.kimi.com/resources/kimi-k2-6-pricing)

## 6. 10–15个并行对话、每天30人的数量级

先采用本次两个简单完成样例：查数8,859 Token/6次调用，分析22,757 Token/9次调用；假设70%查数、30%分析，则每任务约 **13,028 Token、6.9次模型调用**。一个用户发一条消息，不等于只请求模型一次。

| 场景假设 | TPM需求 | RPM需求 |
| --- | ---: | ---: |
| 每60秒完成一批10项任务 | 130,284 | 69 |
| 每60秒完成一批15项任务 | 195,426 | 103.5 |
| 每120秒完成一批15项任务 | 97,713 | 51.75 |

这些是目标吞吐的公式换算，不是“打开15个聊天窗口就必然消耗这么多”。当前5个模型并发名额可能使任务排队。需要选购的额度还受延迟、请求突发、模型输出上限和平台账户规则影响。

| 每天30人，每人任务数 | 日任务数 | 日Token估算 |
| --- | ---: | ---: |
| 5项 | 150 | 约195万 |
| 10项 | 300 | 约391万 |
| 20项 | 600 | 约782万 |

按此次样例的缓存和输入输出比例，每天300项的费用机械外推约 **¥21.36**；这里只是价格量级，不是预算承诺。历史会话较长、澄清更多、多指标或补查更多时会增长。若使用两个已完成分析任务的均值（包含最初多分支和澄清），分析是32,633 Token/任务，300项混合任务约 **480万 Token/天**。

统计页会随着后续试玩增加样本，目前分析完整样本2个、查数完整样本1个，不能视为稳定生产均值。建议你正常试问后再读更新后的分布，不为收集数字额外跑大批付费压力测试。
