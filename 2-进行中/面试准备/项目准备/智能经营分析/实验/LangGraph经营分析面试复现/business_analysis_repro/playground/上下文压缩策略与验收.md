# 上下文压缩策略与实现

更新：2026-09-13。范围：本地 LangGraph 经营分析试玩，不连接公司系统。

## 原来有什么，现在改了什么

原来只是取最近 3 个已完成任务，每段答案最多 1,800 字符。没有摘要模型，没有 Token 触发阈值；更早的条件可能随着几句闲聊移出上下文。

现在使用：**短对话完整问答 + 旧对话滚动摘要 + 最近业务条件单独保留**。所有原始问答仍留在会话记录；当前需求、澄清、运行中补充继续由原来的 State/Inbox 处理，不进入旧历史摘要。

## 通常有哪些方法

| 方法 | 做法 | 主要取舍 |
|---|---|---|
| 截取窗口 | 只带最近若干消息或一定 Tokens | 简单，但早期约束可能丢失 |
| 滚动摘要 | 超过阈值后，用旧摘要和新变旧的消息生成新摘要 | 保留大意，需要额外调用，仍可能遗漏细节 |
| 结构化任务状态 | 独立保存指标、日期、筛选、待处理问题 | 关键字段可精确保留，需要定义字段和更新规则 |
| 按需读取历史 | 大表、旧工具结果等保存在外部，需要时再取 | 减少每次输入；需要检索或读取能力 |

LangChain 官方列出截取、删除、摘要及自定义策略，并提供可设触发阈值的摘要中间件。[官方短期记忆文档](https://docs.langchain.com/oss/python/langchain/short-term-memory)

Anthropic 的上下文工程文章讨论了压缩和结构化笔记，并强调压缩过度可能丢失关键细节。[官方上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

本实验采用滚动摘要与结构化业务条件。当前是自建 StateGraph，摘要在“理解需求”节点前部执行；没有为此迁移成另一套 Agent 框架。尚未给模型增加“自动检索任意历史原文”的工具；用户可在会话和 Trace 中追溯原始内容。

## 本版参数

| 参数 | 默认值 | 含义 |
|---|---:|---|
| 触发阈值 | 12,000 Tokens | 历史包超过此值时触发压缩 |
| 目标预算 | 8,000 Tokens | 给摘要和受保护的业务字段预留后，选择近期原文 |
| 近期原文预算 | 最多约 4,000 Tokens | 按完整问答选择，轮数不固定 |
| 摘要长度 | 约 1,200 Tokens | Prompt 要求约 600 汉字，程序另设长度上限 |
| 单批旧历史 | 约 10,000 Tokens | 大量历史分批总结 |
| 每次准备的摘要步骤 | 最多 3 次 | 避免首次迁入大量旧记录时无限总结 |

这些值是实验参数，不是 Kimi 官方限制。入口是 context_memory.py 中的 ContextPolicy；execute(context_policy=...) 可在测试或程序入口覆盖。

估算使用 tiktoken 的 cl100k_base，**不是 Kimi 的精确分词器，也不是计费 Tokens**。预算只覆盖历史包；系统 Prompt、工具定义、当前需求/澄清及本轮工具调用另占空间。本版没有实现整次模型请求的全局 Token 硬上限。

如果受保护的业务计划本身过长，优先保留其完整字段，并在 Trace 标记 over_budget。不能一边承诺保留全部指标，一边偷偷截断计划。

## 一次执行的顺序

1. server 从 conversation.json 读取所有完成问答，不再取最后 3 轮。完成前的澄清、执行中的插入消息也按角色顺序补回。
2. 程序从历史计划提取最近业务焦点 business_anchor。若最近在咨询口径，另保留上次查数/分析条件 last_data_task，避免口径任务把日期和筛选覆盖成空。
3. 当前需求及当前任务的澄清原文单独传入；不进行摘要或截断。
4. 检查摘要缓存是否仍对应同一段原始历史。清空、取消导致的历史变更会让旧缓存失效。
5. 短历史直接发送完整问答。长历史超过阈值时，保留最近原文，把新变旧的部分与旧摘要交给 Kimi 总结。
6. 新摘要原子保存到当前会话的 context-memory.json。下次复用；未再次超阈值时不调用摘要模型。
7. 主模型收到当前原话、近期问答、历史摘要和精确业务条件，继续决定回复、查询口径、查数或分析。
8. 日期复核只接收旧时间范围，不再接收旧筛选、旧答案等无关内容；它不能代替指标及条件校验。

摘要阶段仍使用进程内同一组模型并发名额、取消边界、调用上限和 Trace。不会把摘要内容流到聊天正文；正常回复继续用原生流式输出。

## 模型实际看到的结构

下面是结构示意，数值与文字均为示例：

~~~python
{
    "messages": [
        {"role": "human", "content": "改成本周，取消新商筛选"}
    ],
    "conversation_context": [
        {"question": "你好", "answer": "你好！", "task": None}
    ],
    "conversation_memory": {
        "summary": "此前讨论放心吃净保费，用户偏好简洁回答。",
        "business_anchor": {
            "question": "查上周放心吃净保费，只看新商",
            "task": {"jobs": [{"task": {
                "metric_id": "demo_metric_fx_premium",
                "intent": "query",
                "start_date": "2026-08-24",
                "end_date": "2026-08-30",
                "filters": {"merchant_age": ["new_merchant"]}
            }}]}
        },
        "last_data_task": None,  # 与业务焦点相同时不重复发送
        "covered_turns": 24,
        "summary_is_evidence": False,
        "degraded": False
    }
}
~~~

这里旧筛选依然保留作历史，但最新原话“取消新商筛选”优先。主模型仍需生成新的候选条件，并由程序检查后取数。摘要模型不能修改程序保存的业务字段，也不能提供新的指标口径。

如果用户转问其他指标，不能把旧筛选自动拼过去；指代有歧义则澄清。判断指代仍依赖模型，本版测试不能证明所有自然语言都不会误判。

## 存在哪里、在哪里看

| 位置 | 内容 |
|---|---|
| .runs/playground/<会话ID>/conversation.json | 原始聊天、所有完成任务；压缩不删除这些数据 |
| 同会话目录的 context-memory.json | 滚动摘要、覆盖位置、原始前缀哈希、降级标记 |
| tasks/<任务ID>/state.json 和 checkpoints.sqlite | 本任务状态；包含本轮使用的摘要及业务条件 |
| tasks/<任务ID>/trace.jsonl | 压缩输入、模型返回、实际 usage、压缩前后估算及实际历史包 |
| 回放页“本轮模型记住了什么” | 原文轮数、估算变化、摘要、独立业务条件、近期问答 |

点击聊天中的“查看这次执行回放”可查看该卡片。执行路线页展开“理解需求与拆解”，可以看到“准备上下文”和实际发生的“压缩旧对话”调用。旧 Trace 没有新事件，因此不会伪造压缩卡片。

API 返回的摘要调用 usage 会自动计入本轮对话、整个任务、会话以及 TPM/RPM 用量；不会因读取回放重复记账。页面上的历史估算变化不等于实际账单节省，摘要本身也需要 Tokens。

## 故障与边界

- 摘要失败：使用明确标记的原文摘录降级，保留精确业务条件；有调用但没有 usage 时计为“用量未知”。
- 单条历史过长：保留首尾摘录并注明中间省略；当前正在处理的用户原话不截断。
- 首次迁入超大历史：超过 3 个摘要步骤的部分明确标记未作语义摘要，不伪装全量记住。原文仍可追溯。
- 摘要缓存损坏：按原始会话重新构建。缓存保存失败不删除原文。
- 停止或改方向：控制流继续向外传播，不把取消当作可吞掉的摘要失败。
- 口径咨询：继续要求查询指标定义。历史摘要、旧助手文字都不能充当本轮口径证据。
- 适用范围：当前单机进程、已有会话锁。没有新增跨服务器共享缓存、多租户登录或向量记忆。

## 验收

离线：178 项测试通过，其中 14 项为本轮新增的上下文边界测试。覆盖短历史完整保留、长历史压缩、增量复用、重启读取缓存、历史变更失效、取消传播、故障降级、超长输入、澄清/插入消息、会话隔离、口径咨询后的原查数条件保留。

真实 Kimi + Chrome 已跑通以下 5 类场景，均观测到真实 SSE 正文片段和网页内容更新。使用独立测试会话；长历史是明确标注的验收夹具，不代表公司数据或真实历史问答。

| 场景 | 历史策略 | 结果 |
|---|---|---|
| 隔 4 轮闲聊追问输出偏好 | 5 轮原文全量保留，无摘要调用 | 正确回答表格、先结论再解释 |
| 33 轮历史后改成本周、取消新商筛选 | 约 18,461 → 3,666 Tokens；2 个摘要步骤 | 仍查放心吃净保费；日期 08-31 至 09-01，filters 为空，实际调用取数函数 |
| 追问“这个指标的口径” | 复用缓存，新增摘要调用为 0 | 调用 get_metric_definition 和 knowledge_agent |
| 再说“你好” | 复用缓存，新增摘要调用为 0 | 自然问候，不重新取数或输出指标目录 |
| 闲聊后问“刚才这个指标支持哪些维度” | 复用缓存，新增摘要调用为 0 | 查询同一指标定义，返回它支持的维度 |

5 个通过案例的实际正文片段数分别为 19、300、85、7、26；片段数不是 Tokens 数。回放卡片已在 Chrome 中渲染并截图检查。

首轮发现两项问题并保留失败记录：日期复核误把取消筛选当成时间问题；唯一指标的口径追问被过度澄清。修复分别为收窄日期复核上下文、明确唯一指标的指代承接规则。修复后对应案例重新通过，失败尝试不计作通过。

包含这些初次失败和重验，本轮共发出 25 次模型请求，24 次返回 usage，已知用量 82,938 Tokens（输入 81,230，输出 1,708，缓存读 33,792），参考费用约 ¥0.392。另 1 次连接失败没有 usage，费用未知。摘要阶段累计 4 次模型请求、18,201 Tokens，参考费用约 ¥0.102；这些已经包含在上述总计中。价格沿用项目 2026-09-09 参数，是参考估算，不是账单。
