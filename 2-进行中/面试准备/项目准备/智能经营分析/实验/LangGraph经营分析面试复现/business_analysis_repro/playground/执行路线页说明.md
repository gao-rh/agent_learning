# 执行路线页

2026-09-07：在现有学习实验中增加只读的 Trace 页面。展示的是实际执行记录，不是预先画出的理想架构，也不会为了回放再次运行任务。

## 从哪里打开

每条回答开头都有“查看执行路线”。正在执行时，进度区也有“查看实时执行路线”；旧完整日志页顶部可以跳转到路线页。

[打开本轮实际执行路线](http://127.0.0.1:8787/flow/afa3d7dcbcad4aa3/bcb6223465fa454a)。

这条旧记录实际走了 4 个分析分支，每个分析函数内部顺序查询本期和对比期，共 8 次取数。记录中的 6 次模型请求、19,311 Tokens 与 36.75 秒都是该任务的历史用量；本次新增页面没有调用模型。

## 怎么看

1. 默认显示完整路线：理解与拆解 → 多指标分支 → 汇总 → 摘要 → 校验。内部模型和工具调用可以展开。
2. 点击“逐步回放”，按照原日志的事件顺序高亮。每步约 0.6 秒，显示的耗时仍取自原记录；播放速度不等于实际运行速度。
3. 点击节点，右侧显示它解决的问题、结果摘要、调用方、内部调用及实际输入输出。模型节点还可以展开实际请求上下文和响应。
4. 拖动进度或用上一步、下一步。尚未执行到的节点不展示未来输入输出；多个黄色节点说明当时有多个分支同时运行。
5. 底部时间条共用一个时间轴，可以核对并行重叠。它聚焦指标执行窗口；模拟取数只有毫秒级，不代表线上数据库耗时。
6. 澄清后恢复会产生新的执行轮次，可用顶部选择器切换。任务仍在运行时每两秒刷新；“全部路线 / 跟随最新”回到最新位置。

主图方框是 LangGraph 节点。分析 Agent、取数 Agent 当前是 Python 函数；分析函数做两期查询、分组对齐和变化计算，没有自己的模型工具循环，也没有完整的业务原因归因能力。模型调用有单独标识，不能把节点输入 State 当成模型实际上下文。

## 实现与边界

| 文件 | 作用 |
| --- | --- |
| [flow_trace.py](flow_trace.py) | 按 run_id、span_id 和 parent_span_id 整理调用层级，保留重复执行、失败与澄清状态；按事件位置读取详情 |
| [flow_trace.html](flow_trace.html)、[flow_trace.css](flow_trace.css)、[flow_trace.js](flow_trace.js) | 路线图、逐步回放、时间轴和详情面板 |
| [server.py](server.py) | 提供 /flow 页面、/api/flow 概览及 /api/flow-node 详情，只读取日志 |
| [stream_chat.js](stream_chat.js)、[parallel_trace.py](parallel_trace.py) | 在对话页和完整日志页加入入口 |
| [test_flow_trace.py](../../tests/test_flow_trace.py) | 检查真实图执行投影、失败状态、回放隔离、恢复轮次和只读 HTTP 接口 |

数据仍保存在原来的 trace.jsonl。概览不携带大块 State 或模型上下文，点击节点后才按需读取详情。图中没有记录的调用不会凭空补出；进程结束但没有结束事件的记录显示“记录中断”。这不是模型内部思考展示，也不接 LangSmith 云服务。

验收：122 项本地测试通过，Ruff 与 JavaScript 语法检查通过；浏览器验证了原会话入口、四分支和八次取数、回放跟随、未来输出隐藏及输入展开。核对原任务日志未被修改。用户独立理解与使用效果仍待反馈。
