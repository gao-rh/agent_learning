- 模拟日期基准为 2026-09-01，原回答把它说成“今天”，容易与真实日期混淆。后续应明确显示模拟基准日；“今天与昨天”不应被无故替换成周比较。

## 采用哪个层次的并行

推荐先完成**多指标任务在图内并行，最后统一回答**。这是用户这次需求的直接对应。

| 方案 | 适用点 | 取舍 |
| --- | --- | --- |
| 单节点内 asyncio.gather / 线程池 | 很快并发几个独立工具请求 | 每个子任务的状态恢复、失败和 Trace 要自行管理，图上仍只看到一大块 |
| LangGraph Send 分发到同一个 worker 节点 | 指标数量动态、多任务分别记录与恢复 | 要扩展父 State 和结果合并规则，符合当前学习目标 |
| 为每个指标起独立进程/完整主 Agent | 强资源隔离等后续需求 | 对当前四指标演示过重，且重复理解和澄清 |

LangGraph 官方支持用 Send 将不同输入交给多个 worker 执行，再汇总结果：[工作流示例](https://docs.langchain.com/oss/python/langgraph/workflows-agents#creating-workers-in-langgraph)。

## 父图和分支职责

```text
理解多个指标、共同日期和深度要求
→ 指标/维度/枚举准入，统一处理必要澄清
→ 形成 jobs 列表
→ Send 并行分发，每个分支只接收自己的 job
    ├─ 放心吃订单渗透率：取两期数据，计算分组变化
    ├─ 取消险订单渗透率：取两期数据，计算分组变化
    ├─ 准时宝商家付费订单渗透率：取两期数据，计算分组变化
    └─ 放心吃可投保订单渗透率：取两期数据，计算分组变化
→ 汇总完成与失败结果，检查覆盖范围
→ 统一组织回答、检查与必要返修
```

图里只注册一个 `metric_worker`，运行时按 job 创建多份执行，每份有独立输入。主 Agent 统一理解、澄清和生成回答；分支复用现有 query_agent / analysis_agent 普通函数。

依赖前一步结果的步骤继续顺序执行，例如先读取指标定义才能校验支持的维度，先得到本期/前期数据才能比较。彼此独立的指标任务适合并行。

## State 变化

概念结构：

```python
# 设计草案，不是可直接运行的完整实现
ParentState:
    request_revision
    jobs: list[MetricJob]
    results_by_job_id: Annotated[dict, merge_job_results]
    pending_clarification
    final_reply

MetricJob:
    job_id
    metric_id
    current_period
    baseline_period
    group_by
    filters
    request_revision

WorkerInput:
    job: MetricJob
```

每个 worker 只返回自己 job_id 的结果。父 State 用 reducer 合并，不能让多个节点同时覆盖现有单个 result 字段。汇总时校验所有预期 job_id、版本、指标和范围，并按计划顺序展示，不能依赖完成先后顺序。

```python
# LangGraph 分发的核心形式；其余准入、reducer、重试和日志需要一并实现。
def dispatch(state):
    return [Send("metric_worker", {"job": job}) for job in state["jobs"]]
```

## “维度尽可能细”怎样落实

这里应转成每个指标自己的合法联合分组；共同维度名相同，也不能假定枚举范围相同。

本次四个指标都支持商户新老 × 外卖商户类型 × 主营一级品类，但允许组合数不同：

| 指标 | 理论合法组合数 |
| --- | ---: |
| 放心吃餐饮订单渗透率 | 2×3×3＝18 |
| 取消险餐饮订单渗透率 | 2×2×3＝12 |
| 准时宝餐饮订单渗透率（商家付费） | 2×3×2＝12 |
| 放心吃餐饮可投保订单渗透率 | 2×3×3＝18 |

这是当前演示白名单的交叉组合；实际取数可能有空组合。该例每期合计最多60组，两期最多120组。详细结果保留，回答优先呈现变化显著的组，同时明确完整覆盖范围。不能为了放在同一表里替取消险补出城市商家数据，或给准时宝补出不支持的甜点。

这里的指标范围不同，跨指标结果应按各自范围展示；需要严格可比口径时再统一明确交集，不能静默改变用户筛选。

## 并发、错误与恢复

- 先给单请求设置可配置并发上限，例如 4（后续用户指定并已实现为5）；服务级查询并发和模型 RPM/TPM 额度另外管理。图的并发上限不能代替供应商的额度控制。
- 分支中的本期/前期若可以一次取回则合并；否则可在共享限流器下并发，不能两层各开四并发而变成无限叠加。
- 普通业务失败返回带 job_id 的失败结果，保留成功分支；汇总明确“哪些完成、哪些失败”，不把三份成功说成四份全部完成。
- 可重试故障只重试相关工作，按 job_id/版本去重；checkpoint 和恢复语义配合框架验证，不能靠简单重跑整张图代替。
- worker 遇到需要澄清的业务问题时返回结构化说明，由父图统一询问用户，避免四个分支同时问四套问题。
- 旧 v3 checkpoint 保持原样；新状态结构使用版本隔离或明确迁移，不直接让新版图盲读旧的单指标 State。

[LangGraph 并行与恢复说明](https://docs.langchain.com/oss/python/langgraph/use-graph-api)。

## Trace 必须同步改造

现有可读回放按线性节点顺序整理，直接加入并行后会难以阅读；原始日志的共享序号和文件写入也需要并发保护。

- 一次用户请求对应父 trace；每个 job 对应一个子分支，带 job_id、metric_id、版本、父 span、起止时间。
- 事件写入统一串行化或加短临界区锁，原子分配事件序号；不能锁住整个查询过程。
- 将父 span 上下文带入 worker。模型调用配额同样要原子预占，避免多个分支同时看到剩余额度。
- 页面显示并行分支及各自状态，分支内展开工具/查询/分析/模型事件；不要将并发事件强行解释为上一节点→下一节点。
- 原始 JSONL 继续实时追加；页面后续再接事件流，使运行中的多个分支进度可见。现有 HTML 主要在每轮结束或澄清暂停时生成。

## 最小验收范围

1. 这次“四个都要”产生四个明确 job，四个都进入执行，统一回答。
2. 用可控制阻塞的测试替身证明分支时间重叠且不超过并发上限，不能只看总耗时猜测并行。
3. 只让一个分支失败，其他结果仍保留并正确标为部分完成。
4. 同名指标、不同枚举范围、联合分组和澄清恢复仍符合原约束。
5. 父 State 无结果覆盖、串数据或重复合并；成功分支恢复行为有测试。
6. Trace 能看到每个子任务的实际查询条件和父子关系。
7. 再抽取少量真实 Kimi 多指标样本，调用前说明案例和预计用量。

## 与“为什么变化”的边界

并行提高取数与计算吞吐，不会自动增加业务原因知识。当前模拟数据可以说明哪一组变化、分子分母如何变化；真正解释业务原因，还需要分析方法、业务事件和相关证据检索。该部分不能靠并发开关或单纯生成更长回答获得。
