# 复杂业务需求澄清实验

本模块只检验需求理解、必要澄清、业务知识使用和多轮任务确认，不执行SQL、分析、绘图或发布。属于小型隔离机制实验，未升级正式Agent父图。

先读[最新测试报告](../../测试报告-v2-2026-10-02-02-48-37.md)，网页入口为 <http://127.0.0.1:8770/>。下文 9 月 30 日成绩是历史记录，当前对错以最新报告为准。

## 已覆盖与实跑情况

首轮四例：多年报告、渠道连续追问、多指标条件例外、口径跨期比较。真实Kimi基线各一次，实际六轮助手响应；两轮因前序失败停止。另做五指标的一次通用字段提示对照。

结果和用量以合并报告、冻结批次、原始Trace为准，不把离线校准或重跑片段算作真实完整通过。四例之外的六类复杂计划没有实模结果。

## 固定数据与代码

- `fixtures/cases.json`：四个场景的首问、允许的历史及计划轮数。
- `fixtures/catalog.json`、`knowledge.json`：全部场景共享19项模拟指标条目、6维度与6条知识；两项付费方拆分明确不可用。
- `fixtures/rubrics.private.json`：评审要求、下一轮回复脚本；不进入运行模型。
- `fixtures/goldens.private.json`：校准任务格式的人工合法样本；不进入运行模型。
- `contract.py`：需求、当前任务、时间视图、分群、比较版本、替代关系和待解决项；公开准入只报告错误，不按标准补任务。
- `runtime.py`：使用原Kimi客户端和五个只读工具，独立的复杂计划提交循环。每轮用实际消息历史继续，保存原提交、校验、工具返回、用量和源码快照。
- `review.py`：独立私有评审。自动规则只能覆盖明确的结构要求，问句及等价任务分解仍需审阅。

当前版本的格式允许表达复杂关系。用户问句只需写入 `questions`，程序直接展示；旧 `question` 字段保留为可选说明。已读取且唯一的定义版本可由程序绑定，其余空字段不代表业务默认口径，结构解析成功也不代表完整需求确认。

## 复现方法

以下是以后有新运行授权时的固定入口。查看已有结果不需要重复执行模型。

```bash
# 在实验根目录执行，创建全新目录并冻结代码、模型配置、公开资料与评审资料
.venv/bin/python -m business_analysis_repro.complex_lab prepare .runs/新批次名
# 每次只跑一轮
.venv/bin/python -m business_analysis_repro.complex_lab step .runs/新批次名 C01 --live
```

运行后离线调用 `review_turn(案例目录, 轮号, human_passed=..., notes=...)`。只有实际问句覆盖了关键项且上轮通过审阅，才继续：

```bash
.venv/bin/python -m business_analysis_repro.complex_lab step .runs/新批次名 C01 --live --question-reviewed --reply '只填写被实际问到的信息'
```

后续用户追问同样通过 `--reply` 传入。禁止注入人工标准任务替换失败计划。旧批次校验源码哈希，不能混入改动后的代码；已经发生失败的主路径不得偷偷续跑。

单变量提示对照入口：

```bash
.venv/bin/python -m business_analysis_repro.complex_lab prepare .runs/新对照名 --cases C03 --guidance-file /绝对路径/通用字段说明.txt
```

本次对照提示原文保存在 `.runs/complex-contract-guidance-20260930/batch.json` 的 `guidance` 中；`input-comparison.json` 验证实际首请求只多了系统提示。使用固定模块读结果，无需逐次生成网站。

## 校准与边界

```bash
.venv/bin/pytest tests/test_complex_lab.py tests/test_complex_plan_feedback.py tests/test_case_viewer.py -q
```

校准覆盖八份合法阶段任务、遗漏条件、错误版本、来源及能力越界、日期、撤销和消息记录。替身不构成真实模型效果证据。C04保留了原自动判分和接受四单月任务等价拆分的人工审计；不能把自动规则偏严误当模型业务误解。

正式Agent的检查点、压缩、运行中插入消息、真实SQL及分析执行都未纳入此实验。费用使用项目已有价格参数，真实账单可能不同。


## 2026-10-01 的运行器改进

提交计划中的 `knowledge_refs` 工具 Schema 逐次更新，只列实际读取过的来源。非法引用反馈给模型，修正仍受原请求预算限制，原始提交继续保留；其他业务语义校验与私有评审不替模型补条件。批次源码快照改用共享的白名单冻结函数，不纳入凭证或运行日志。当前复杂实模失败没有重新跑，本轮离线机制回归通过不改变历史成绩。

## 2026-10-02 的提交接口调整

- `questions.owner=user` 是用户问句的唯一来源：按顺序展示并去掉重复文本，不要求再复制到 `question`。知识维护方、系统能力负责的问题不会自动转问用户。
- 只从实际 `get_metric_definition` 返回绑定版本：定义仅有一个版本，且覆盖任务期间时，补齐空的当期／基期版本。多版本、未读取、冲突或超出覆盖时不猜；已有版本不会被覆盖，日期、筛选和替代关系不会被补写。
- `delivery` 分别列内容与发布目标。只列 Wiki 时，公开校验明确指出缺少 `report/chart/table` 内容项，由模型按原用户需求修正。
- 公开校验未通过时，工具返回具体错误，模型可再次提交；每轮仍最多 8 次请求，批次 Token／费用预算不变。私有评审结果不会反馈成答案。

原始 `model_submissions.arguments` 保留；程序改动存入提交的 `program_normalization` 和工具返回，最终计划另存。用 C01 原提交离线核对：5 个任务、7 类需求均保留，原问句可显示，5 个 v1 可绑定，仍需补报告内容项；没有替用户接受合计替代。核对记录在 `.runs/offline-c01-adjustment-20261002.json`。该接口调整阶段的离线回归为 276 项通过；随后完整复测见下面的最新结果，历史成绩保留。


## 2026-10-02 最新复测

全部修改后的三道复杂题：C03 通过；C01 因两项缺口需求没有保留时间视图失败，C02 因任务未显式绑定曝光人群失败。渠道继承和月份比较本轮正确。续轮带入实际上轮计划，普通正文未提交计划时反馈给模型，必选规则缺项明确列出；每轮仍受原预算限制。全部离线回归为 282 项通过，详细过程见[最新报告](../../测试报告-v2-2026-10-02-02-48-37.md)。
