## 为什么会反复查枚举：是接口绑得太紧，不是没有区分指标和维度

指标是“放心吃总保费、订单量”；维度是“省份、渠道”；枚举是维度的取值，例如“安徽、江苏”或“钱包、首页”。**不存在另一类需要单独搜索的“指标枚举”。** 我前面的表述容易让人误会，需要更正。

代码已经有两层：维度字典保存取值及别名；每个指标另存它支持哪些维度、哪些取值。问题在于旧工具把两层绑在了一次调用里：查维度取值也必须传指标ID。旧查询循环又把“已检索证据”记成“指标ID＋维度ID＋枚举值”。所以给总保费查过安徽，换成净保费后，程序仍可能说证据没查齐。这不只是模型没被告知，而是工具签名与程序校验共同造成的重复。

具体证据在 [枚举工具定义](knowledge.py) 的 search_dimension_values，以及 [旧查询循环](../playground/parallel_model.py) 的 values_seen / grounded_values 检查。9月29日补日期后的双保费题曾因此没有完成。9月30日复杂实验复用了工具，但没有复用这段按指标逐一检查枚举的旧循环，不能把两套实验的失败混成一个原因。

**通用改法建议：**

1. 维度发现：把用户说法匹配到精确维度。
2. 维度枚举检索：例如查一次“省份里的安徽”，得到标准值。同一业务范围、同一维度定义及版本下复用结果。
3. 指标适用性检查：程序根据已读指标定义，检查这些维度和值是否受支持；可一次检查多个指标，不让模型重复查同一枚举。
4. 仅按维度分组时，确认维度存在且指标支持即可，不必遍历所有枚举；用户指定筛选值、别名不清或需要列举候选时才检索取值。

如果两个业务里的“新商”实际定义不同，应使用不同维度定义或版本，不能因为名字相同就共享。这里需要的是明确定义及适用范围，不是为每个自然语言说法补一条 Prompt。

还有一个展示细节：钱包渠道题曾把 merchant_type、channel 填在搜索词里，工具的“候选”列表为空，但同时返回了可用维度枚举。不能只看候选为空就断言“工具没给任何枚举”。默认阅读页原先强调候选，完整返回中仍保留了枚举；这两部分应一起看。

这次先说明并记录接口调整方案，没有在旧实验里静默改变工具和评分。接口修改后应新建对照批次验证，而不是覆盖旧Trace。

## 按月、按年、每年指定月份累计：澄清参数已经能表达

**这些不应因为模拟取数没接完就被判“不支持”。** 现有复杂任务的 View 已支持 month、year、annual_months，以及 months 月份列表。对“2021年1月1日至2026年8月31日，每年1—7月累计”，澄清后需要保存的是下表，不需要模型写聚合SQL。

| 参数 | 本题应记录的内容 |
| --- | --- |
| 总日期范围 | 2021-01-01 至 2026-08-31 |
| 按月展示 | 每个自然月一行，边界与总日期范围相交 |
| 按年展示 | 每个自然年一行；2026年只统计到8月31日，注明非全年 |
| 每年指定月份累计 | 每一年分别只取1、2、3、4、5、6、7月，再按年展示 |
| 指标口径 | 使用所选指标的定义及版本，聚合方法由工具负责 |

按年、按月是展示粒度，日期范围是取哪些时间；两者分开。“每年1—7月累计”也不等于从2021年起一直累计到当前年份，更不等于七个单月各自展示。用户已明确这些意思时，不应重复追问。

**本次补了可运行的小工具示例：** [time_view_preview.py](time_view_preview.py)。它为上述范围生成每日100元的模拟实收保费，共2,069行；同一函数根据时间视图参数生成68个月结果、6个年度结果、6个每年1—7月结果。没有模型调用、没有真实平台接口，也没有接入旧实验运行器。

| 可核对例子 | 工具实际结果 |
| --- | --- |
| 2024年2月，闰年 | 29天，2,900元 |
| 2026年按年展示 | 1月1日至8月31日，243天，24,300元，标记不是全年 |
| 2026年1—7月累计 | 212天，21,200元 |
| 另测仅1月和3月累计 | 62天，6,200元，没有混入2月 |

命令是在实验根目录执行 `.venv/bin/python -m business_analysis_repro.clarification_lab.time_view_preview`，结果保存到 `.runs/clarification-document-examples/time-view-preview.json`。跨月、跨年、闰年、末年不足整年和非连续月份检查均已运行通过。

这个示例只聚合可加总金额。年度去重商户数不能直接把每个月人数相加；渗透率应按正确分子分母重算，不能简单平均月比率。这属于指标工具的计算规则。澄清阶段只需正确选择指标、时间范围和展示方式，不因演示数据量或平台缺失额外要求用户解释。

多年报告题中，真正被设置为不支持的是两个付费方拆分指标，用于专门测试“存在能力缺口如何澄清”；不是上述时间视图不支持。后续正常能力测试应给足模拟能力，缺口测试单独保留。

### 8.3 四个失败分别是什么问题

按最新冻结结果，四个失败是：净保费题的来源编号混填、加入商户数题没有进入可续跑澄清、只看新商题删除分组、电销续查题混填历史任务编号。前两段逐题正文给出了完整问题，不能把四种情况都称为“模型理解能力差”。

**通用增量修改，不是为“只看新商”写补丁。** 当前方式让模型每轮重新生成整份任务；更稳妥的接口允许模型只表达“增加筛选、替换日期、删除分组、增加指标、另开新任务”等少量操作，再由程序合并。用户没有修改的字段默认继承。增加筛选不会自动删分组，切换新任务则不机械继承旧条件。这是一套适用于任意指标、维度和值的更新规则。

例如“只看线上，其他不变”，由维度检索确定“线上”属于哪个维度及其精确值，再提交该维度的筛选变更；不需要在 Prompt 中收集“只看线上、只看线下、只看安徽……”的全部句式。若“线上”在多个业务维度中都有合理含义，才询问用户。

**Prompt 只说明稳定规则。** 说明筛选与分组的区别、如何表达多值 OR、未改字段如何继承、字段各自含义；具体名称、别名、枚举和口径放在知识工具中。与用户无关的来源技术编号、指标固定口径由程序绑定。强制约束放执行前检查，不把“请仔细”当作可靠保证。

**修复后仍需要测模型。** 增量修改也可能选错目标或误判操作，所以要检查原始问题、本轮修改和合并后的任务，并保留模型首次输出。先用当前模型及同一套接口复测，再在相同条件下换模型对照；模型内部原因和收益不能从这一次记录推算。目前这些接口改动仍是方案，未借本次文档更新修改历史实验或重跑模型。

**已经做过的提示词对照：** 只补充“多值筛选放列表、同维度是OR、固定规则放哪个字段、比较版本怎么填”等通用说明，没有给本题答案，主要条件就正确了；最后被来源编号拼接错误拦截。说明字段约定值得改进，但一次对照不能证明稳定修复。更好的方向是让接口少暴露重复且可由程序推导的字段，而不是一直加长 Prompt。

### 9.4 为什么口径更新例需要更正自动评审

自动评审最初只接受两种专门比较任务：历史组使用历史展示枚举，可比组在同一个任务中同时填写当期和基期。模型实际用了四个单月任务：

| 实际任务 | 日期与版本 | 重算标记 | 关联需求和用途 |
| --- | --- | --- | --- |
| T1 | 6月，v1 | 否 | 历史组：还原当时看板 |
| T2 | 7月，v2 | 否 | 历史组：还原当时看板 |
| T3 | 6月，v2 | 是 | 可比组：按7月新口径重算6月 |
| T4 | 7月，v2 | 否 | 可比组：与重算后的6月比较 |

两个组分别关联不同需求集合，任务用途、视图说明与两张交付表都明确分开。回复还明确警示历史组不能解释成同口径增长，因此业务语义可以接受。

不过四项的比较方式字段都是“无比较”，没有单独的机器比较边。在接入真实计算之前，还需要将等价分解规范成明确的比较关系，不能只凭这些文字直接执行增长率计算。本轮只确认需求，所以将其记为**业务语义通过，执行格式待规范**。自动原判、人工理由和更正后的结果同时保留，查看器可展开审计记录；没有修改模型输出。

这也说明评测不能只和唯一一种标准JSON完全相等。需要检查业务关系是否等价，同时保留机器执行协议是否完整这一独立维度。

## 2. 最关键的错误：7 月变成 8 月

实际用户问题：

> 查2026年7月安徽的外卖餐饮活跃商户数及其中开通放心吃的数量，两个都按商户新老分组。

本次冻结的模拟基准日是 `2026-09-01`，并非电脑当天日期。模型在两个指标中都返回：

```json
{"period": {"mode": "calendar", "unit": "month", "offset": -1}}
```

程序按这个结构计算为 `2026-08-01` 至 `2026-08-31`，SQL 日期参数也是这两天。对于这个基准日，7 月应为 `offset=-2`，或直接提交 7 月的绝对起止日期。

链路是：**用户明确 7 月 → 模型相对月份填错 → 程序正确执行了错误条件 → SQL 成功 → 评审器比对用户标准后判错。** 首次偏差在模型提交，不在 SQLite 的计算。

尤其需要注意：本次合成数据里，7 月和 8 月恰好都有“新商 8、老商 8；其中开通各 4”。如果只检查数字或者接口成功状态，这次会漏判。评测必须同时检查日期、指标、筛选、分组和 SQL 的实际范围。

**边界：本次是隔离的小型实验父图，未接入正式父图中的 `validate_dates` 日期复核。** 正式实现见 [parallel_agent.py](../playground/parallel_agent.py)，搜索 `validate_dates`。因此确认的是“这次模型解析错、实验路径放行了”，还不能断言正式网页也一定会放行；正式日期复核是否能拦住该样本仍待验证。

**评审器本身也修了一处误判。** Q09 恢复失败后，旧版本评审器读到了上一轮 checkpoint 的 `inspection`，在原记录中错误标成“漏指标”。现在只读本次 `run_id` 下的提交与校验。原始记录保留不改，另附审计纠正，不能把那条旧标签算作模型漏指标证据。

批次 B 同时包含来源校验/字段说明修复，以及单轮调用上限从 6 调到 8；它用于故障复测，不是只改变一个变量的效果提升对照。两批原始版本与失败均保留。
