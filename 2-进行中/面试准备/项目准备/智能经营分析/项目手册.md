# 智能经营分析项目手册

> 2026-09-08 合并整理。汇总已保存的用户口述、后续修正与设计材料；整体文字为 AI 整理，不等同于逐段确认的面试终稿。公司代码、统计明细与生产日志未在本轮重新验收。

## 1. 项目是什么，为什么做

面向美团金融场景险的运营、业务与商分用户，让他们通过自然语言自助查口径、取数、分析和获取异常提醒。过去一项需求往往要经历业务说明、数据开发取数、口径确认、商分分析和反复解释，成本包含协作与排期等待。

项目把已有指标平台、数据集与数仓能力，同业务知识、分析方法和 Agent 流程连接起来。常规任务可以由业务自助完成；复杂策略判断及高影响结论仍可能需要专业人员参与。

本人负责 Agent 技术框架、流程和工具，联合业务、产品、商分及数据团队共建。底层查询接口由平台提供，不把平台与团队能力写成个人独立开发。

2026-09-09 本人补充：核心价值是加快“看数据—分析—决策”的业务运营循环。场景险底层数仓不是本人建设；公共营销约 2000 多个任务、90% 以上接手维护，以及触达链路的优化重建，属于另一段数仓经历。公共营销主要服务下游数仓和平台后端，基本不直接交付看板。

## 2. 能力怎样组织

| 层次 | 内容 |
| --- | --- |
| 数据咨询 | 业务知识、指标定义、标准名称、支持范围及维度口径 |
| 可信取数 | 指标、维度、时间澄清；查询参数组装；平台取数与脚本计算；结果校验 |
| 经营分析 | 完整专题报告、围绕局部问题的一层分析、开放式分析与后续追问 |
| 输出与交付 | 数字、表格、图表和报告；周报、定时分析、异常提醒 |
| 横向支撑 | 业务知识、用户记忆、上下文、缓存、执行约束与评测 |

这是便于阅读的分组，不把 Agent 角色、分析方法和交付入口重复算成同一层的业务能力。

**专题口径已于本轮确认：保费、渗透率、渠道归因、商户分析。** 原“用户留存归因”归入商户分析；这里的业务用户就是商户，商户分析还包含留存以外的分析。其他子分析的具体名称尚未给出，不补造清单。

## 3. 一次取数请求怎样执行

以“看一下上周新商餐饮渗透率”为例，按已有用户自述整理：

1. 主 Agent 识别指标表达并检索指标库，将“新商”匹配为商户类型维度中的筛选值。 用户可能只描述活动效果而不知道指标名称；模型会按诉求推荐候选指标，解释其含义及计算公式，协助选择。
2. 确定完整标准指标名、维度条件和时间。时间范围、输出粒度、整周总体比例与每日比例均值需要分别判断。 大部分情况会确认；明确命中流量分析等已知场景时，也可能直接给出分析结果。
3. 主 Agent 把已确认的取数参数交给取数 Agent。
4. 2026-09-09 补充的查询配置链路：指标确定唯一数据集或数据应用；应用内有多个模型，通过指标、维度和粒度确定对应模型及映射 SQL，再按业务线、数据集等结构化参数请求平台接口。粒度已由本人确认同时包含时间粒度与订单、商户等数据粒度。
5. 比例型指标通过封装脚本完成分子、分母取数、聚合和相除，减少模型操作中间值的机会。跨天去重人数等不可加指标仍需遵守自身定义。
6. 做基础结果检查，将数据和必要说明返回主 Agent，由主 Agent 组织回答。

人工在公司平台配置指标、维度、数据集和数据应用。最新口述明确 AI 主要帮助执行重复配置操作，早期“辅助草拟”的说法保留在历史口述。用户自述的实际检查包括标准指标名和参考范围检查，不能据此推导已逐字段校验完整查询语义。

平台主要查询原子指标及少量固定、简单的复合指标；复杂计算、特定过滤处理、MTD、目标达成及 Shapley 贡献分析由取数后的脚本处理。返回内容会标注查询方式、查询 ID 和数据集，用户可到平台追溯具体查询。

## 4. 核心机制与实际边界

| 机制 | 已有口述或材料支持的做法 | 仍需保留的边界 |
| --- | --- | --- |
| 指标标准化 | 原话优先检索；候选不唯一时展示标准名称与定义；按唯一 ID 路由查询 | 指标合法可查，不等于适用于目标业务事件 |
| 日期与比例计算 | 日期交给 Python 脚本，例如 Week 偏移 -1 输出上周范围；月环比等输入输出基期／当期；比例取数与计算封装为工具 | 脚本正确执行错误条件，结果仍不符合问题 |
| 全量数据与上下文 | 固定平台全量导出／下载参数，完整数据落文件；模型读前 200 行预览；代码读全量文件聚合 | 200 行仅用于预览，不是全量计算输入或完整性证明 |
| 多 Agent 分工 | 主 Agent 负责沟通与交接；取数 Agent 使用专有上下文、Prompt 和工具；分析 Agent 接收主题、目标、类别与核心指标 | 不推导具体并发 API、模型数量或量化收益 |
| 并行取数 | 一次需求的多项独立取数可并行 | 依赖前一步证据的下钻仍有先后关系 |
| 专题 Skill | 确认标准指标 → 匹配业务专题 → 专题 Skill → 判断执行深度 | 不存在覆盖全部指标的通用“指标异动 Skill”；局部问题不默认无限下钻 |
| 缓存 | 最新口述：超过十分钟的慢查询结果存入平台提供的 MySQL 云数据库，通过平台接口写入；独立查询可并行 | 不宣称专门的速度或时效 SLA；与旧口述“统一文件、首查更新”是否为同一类缓存尚未统一，更新键和失效规则仍未补齐 |
| 知识与记忆 | 业务知识用于事实和分析方法；用户记忆包含信息、偏好、连续性、经验复用及冲突选择 | 已实现的口述不等于所有写入、隔离与过期规则已验收 |
| 失败恢复 | 工具返回错误，Agent 判断可否修正、重试或说明限制 | 强制调用、预算与停止规则的运行时覆盖仍需按具体实现核对 |

## 5. 分析怎样做到按需深入

相同问法可能落在不同专题。先确认指标，再选择其所属专题；问法主要帮助判断要查数、看现状、问原因还是生成完整报告。

| 专题 | 已有方法或关注点 |
| --- | --- |
| 保费 | `保费 = 单均保费 × 订单渗透率 × 订单基数`；公式因子拆解、Shapley 贡献、目标达成与 Gap |
| 渗透率 | 趋势确认、分子分母变化、维度结构与贡献；区分商户渗透率和订单渗透率 |
| 渠道归因 | 全渠道 → 一级渠道 → 二级渠道 → 漏斗 → source；按问题位置选择入口 |
| 商户分析 | 包含原“用户留存归因”、商户活跃等分析；其他子方向和完整方法尚待补充 |

明确要完整专题报告时执行完整链路；只问局部原因时，在对应专题内先分析当前节点的一层，后续按追问深入。趋势、公式、维度、漏斗和 Gap 是专题内部可复用方法；五类拆法来自材料归纳，不宣称恰好发布过五个独立 Skill。

2026-09-09 分工补充：运营主要提供日常分析场景、关注指标和内容；商分主要提供专业拆解、公式及贡献度统计等具体方法，有限人力优先投入专题化或较大的问题；本人沟通并梳理、组织为可执行的分析方法和 Skill。不将商分表述为所有完整分析链路的提供者。

详细方法集中在[四类分析方向还原](资料/四类经营分析方向还原.md)。

## 6. 真实问题、处理方式与残留

| 问题 | 已记录处理或定位 | 当前结论 |
| --- | --- | --- |
| 平台只返回第一页或前 200 条 | 固定全量导出参数，全量落文件并由代码处理 | 已有实际做法口述；不把预览当全量 |
| 大结果直接挤入上下文 | 完整数据留文件，只回传预览、汇总与必要证据 | 与上一项合并说明，不再多处重复维护 |
| 复杂多指标请求遗漏维度条件 | Prompt 先列指标，再逐项整理维度并分别澄清；最新口述明确遗漏主要由用户发现，检测验证只能缓解 | 仍有少量残留；不宣称存在彻底阻断遗漏的程序校验 |
| 新人使用合法但不适用的指标 | 词义映射正确，但系统不知道目标事件应该用哪个指标；分析知识中的推荐指标用于缓解 | 事件—指标强适用性规则是否完整上线仍待验证 |
| 报告隐藏真实指标身份 | 查询与分析中仍保留标准指标，报告生成模型把标准名改为用户口语 | 问题在报告生成层；字段保护和生成后校验是否上线仍未确认 |
| 最终评测失败 | 后续回忆包含查询条件遗漏，以及执行报错、超时 | 覆盖此前“基本都是工具失败”的说法；无逐题日志，不编造比例 |
| 中期配置和单位问题 | 曾缺业务线／数据 ID 配置，输出有时乱加单位 | 历史迭代问题，不自动算入最终剩余 5% |
| 多轮上下文与业务别名 | 历史 Q06 是上下文丢失，Q08 是“下沉=代理”别名缺失 | 两件事分开；已撤回的“通知可能是 source 或渠道”例子不再采用 |

真实问题原句及逐条结果见[真实用户问题清单](资料/智能经营分析真实用户问题清单.md)。

## 7. 代表性案例：商户渗透率上升，订单渗透率下降

这是一份用户提供的案例，本轮未读取内部数据重新计算。

先校正时间：7 月整月相对 6 月，两种渗透率都上升；订单渗透率在 7 月中旬见顶、下旬起按周下降，8 月材料仅覆盖 1–12 日。不能简化成“7 月整月一个升、一个降”。

- 商户渗透率的分母是外卖活跃商户。分母下降快于活跃在保商户，比例可被动上升。
- 商家付费订单渗透率的分母是餐饮订单总量。分母增长快于商家付费投保订单，比例可被稀释。
- 同一业务的两个比例可能分别受存量与流量结构影响，必须对齐时间、指标身份与分子分母再解释。暑期、商户退出等深层原因仍属于原报告解释，未独立验证。

详细数表仅在复算时查归档中的“代表性分析案例”，不在多篇当前文档重复维护。

## 9. 项目演进与统一设计

2026-09-09 按难点补充：第一阶段为可靠取数，将自然周、同环比和定制基期／当期的规则从知识转入代码；第二阶段为分析方法沉淀，难点是从商分、业务和负责人的具体案例中提取、抽象分析思路；第三阶段暂称“辅助决策”，关注业务动作及发生时间的取得，“智能助理”仍是本人提出的替代名称，具体完成范围未补充。指标整体稳定，通常人工修改底表或平台配置；影响业务知识和方法时再改知识库或 Skill，分析方法持续小迭代，无全自动更新。


阶段复盘从 2025 年指标线上化和 Workflow，走到 2026 年春季的可靠取数、分析 Skill 沉淀，再到开放分析、缓存及统一引擎迁移。v3.0、v4、V13、V16 等来自不同材料，尚不作为已验证的发布表；也不与本地图的 v4 混用。

统一设计按“受控编排、专业 Agent、共享取数、结构化任务与证据”理解，不逐节点重新要求历史项目／平台／理想补充分类。`QuerySpec`、`AnalysisTask`、`DataEvidence` 是架构语义名称，未经映射不能宣称为公司真实类名。

近期 LangGraph 方向是父图、分析子图、共享取数子图各有 State，包装节点转换输入输出；模型提出动作，代码校验，图运行时执行；分析中途可以暂停澄清并恢复。该方向属于已确认设计，复现代码使用合成数据，不替代公司生产证据。具体见[方向确认](记录/2026-09-06-LangGraph技术架构方向确认.md)与实验 README。
