# 智能经分 Agent：持续评估、优化与维护 SOP

> 日期：2026-09-08。状态：**AI 建议草案，供讨论和选择采用**。依据项目口述资料及文末一手文章设计；未接入公司系统，未重跑历史 200 题，未验证实际收益。文中的流程、字段、发布门槛和维护节奏均为建议，不代表已经实施。
>
> 阅读方式：先看第 1 节总流程、第 3 节评价标准、第 10 节优先级；需要落地时查其余步骤和模板。

## 1. 核心判断与一页 SOP

你们已经有指标配置、取数工具、专题分析 Skill 和评测题库。下一阶段最值得建立的是：**每一次线上错误，都能变成可复现的用例；每一次修改，都能证明修好了什么、是否损害其他能力；每一次数据或业务口径变化，都能传递到 Agent 使用的知识和验证规则。**

这里有三个相互连接的循环：

- **单次任务内验证**：检查条件、数据和结果；有明确修复依据时有限重试，否则澄清、解释限制或转人工。它改善本次回答。
- **跨任务版本迭代**：收集问题 → 复现 → 定位 → 修改 → 对照评测 → 发布 → 观察。它改善后续一类回答。
- **数据与方法维护**：上游变化 → 找出受影响指标和 Skill → 同步修订 → 验证 → 生效。它防止原来正确的系统慢慢变错。

这些循环不要求给每个请求增加独立 Planner。你们已有的专题执行方式可以保留；本次先补质量反馈闭环。

| 步骤 | 具体操作 | 必须留下的产物 | 何时可以进入下一步 |
| --- | --- | --- | --- |
| ① 定义成功 | 分清查数、局部分析、完整报告，写清必需条件与完成标准 | 任务验收卡 | 业务与工程对“怎样算对”没有关键分歧 |
| ② 收集样本 | 汇集用户纠错、系统异常，并随机抽查表面成功的请求 | 带来源和抽样方式的案例池 | 有足够上下文，知道样本能支持什么结论 |
| ③ 固定并复现 | 固定版本、时间、数据及会话状态，确认参考依据 | 可重放用例、基线结果 | 可判断问题来自 Agent、数据还是评测装置 |
| ④ 定位并修复 | 找第一处有证据的偏差；改对应的配置、工具、Skill 或提示词 | 问题单、最小修改、正反用例 | 修改与故障原因有明确对应关系 |
| ⑤ 新旧对照 | 同条件比较目标场景、相关回归、关键场景和新请求 | 收益、退化、成本清单 | 满足事先约定的质量与成本门槛 |
| ⑥ 发布与观察 | 先内部或少量用户使用；保留旧版本和关闭入口 | 发布记录、观察结果、回退方式 | 实际运行没有新增严重问题，收益得到支持 |
| ⑦ 沉淀与维护 | 固化通过的用例；同步知识、方法与依赖；记录无效尝试 | 回归集、版本化资产、维护记录 | 线上实际加载的版本与发布版本一致 |

职责可以由同一个人兼任，不必先建复杂组织：**业务负责人确认业务口径与分析意义；工程负责人负责执行、版本和可靠性；评测维护者负责样本、参考依据和评分规则。** 自动作业承担收集、整理和运行，人负责关键事实和变更取舍。

## 2. 从你们现有基础出发

| 项目已有的基础或已知问题 | 证据状态 | 本次建议补什么 |
| --- | --- | --- |
| 指标名称、别名、ID、维度、公式等由人工配置；模型可辅助起草 | 用户口述 | 增加业务适用范围、生效时间、负责人及变更记录，具体字段按已有平台能力落地 |
| 主 Agent 理解需求，取数 Agent 查指标映射并调用平台接口；独立查询可并行 | 用户口述 | 检查条件在理解、传参、实际执行、输出间是否一致 |
| 比率通过脚本获取分子分母，汇总后相除 | 用户口述 | 保留该机制，补人群、时间、粒度一致性与分母为零检查 |
| 在线主要核对指标名称和宽泛数值范围，异常时检查原始值或返回错误 | 用户口述；未查生产代码 | 从“名称与数值合理”升级为“条件、数据完整性、计算、呈现有证据” |
| 最终 200 道题、95%；人工确认参考答案，模型核对数值；同一批题也参与调试 | 用户口述；未重跑原始日志 | 保留为回归资产；若要估计新请求效果，另做修改前的真实请求抽样 |
| 已发生多指标、多维度条件遗漏；曾有数据映射缺项、单位补错、业务意图与指标适用性错配 | 用户口述 | 优先围绕这些真实问题建对照样本与结构化检查 |
| 专题 Skill 按标准指标路由，区分局部一层分析与完整报告 | 已确认设计；字段细节并非全部确认实现 | 把适用条件、必要证据、计算方法、停止条件和验收案例写清 |
| 既有《评估体系 v0.3》已设计数据准确率、端到端成功、首错归因等 | AI 草案 | 本文将这些设计展开成操作流程，不宣称已有完整评测平台 |

对应本地依据见文末。**200 题上的 95% 可以说明该集合上的历史表现；它本身不能证明今天线上所有新问题也有 95%。** 不必推翻旧题库，也不必先建一个永久不动的测试集；先区分“检查已知能力有没有退化”和“了解新请求表现”两种用途。

## 3. 第一步：把“效果好”定义成能验收的结果

### 3.1 不同任务，用不同验收标准

| 任务 | 必须验证什么 | 不足以证明正确的信号 |
| --- | --- | --- |
| 指标咨询与澄清 | 标准身份、定义版本、业务适用范围；歧义是否真的解除 | 命中了名称相似的指标；任何问题都追问一次 |
| 业务取数 | 指标、筛选条件、时间、统计粒度、单位、数值及数据完整性符合要求 | SQL 可执行；指标名相同；数字在合理范围内 |
| 局部专题分析 | 正确取数；完成该专题的一层必要分析；解释有证据且按约定停止 | 内容长、图多；自动生成完整专题报告 |
| 完整专题报告 | 必需章节和关键问题覆盖；事实与计算正确；主要结论可追溯 | 模板齐全，但章节没有回答业务问题 |
| 开放分析 | 回答用户目标；关键事实可核验；方法适用；区分观察、假设与因果 | 和一份参考报告措辞相似；评审模型觉得“逻辑通顺” |
| 多轮任务与记忆 | 当前条件正确继承或覆盖；不混入其他用户、旧人群和旧时间条件 | 每条单轮问题都能回答正确 |
| 定时报告与文件交付 | 内容正确，文件真实存在并可访问，按要求交付且没有重复副作用 | Agent 说“已经生成/发送”；只看到工具被调用 |

**数值正确也可能没有回答对问题。** 例如“看新商户表现”与“看全部商户表现”可能使用同一个指标 ID，但适用人群不同；再例如，一个指标合法可查，却不适用于当前业务事件。这两类都需要检查。

### 3.2 建议的看板：两个主指标，配上解释它们的信号

| 指标 | 建议口径 | 使用边界 |
| --- | --- | --- |
| 数据准确率 | 在预先标记为应当返回数据的任务中，全部必需数据项都正确的任务数 / 该类有效评测任务数 | 漏指标、错误拒答、Agent 超时都不能从分母移除；分项正确率用于诊断，不能替代整题结果 |
| 端到端任务成功率 | 达到该任务预先约定的最终状态的任务数 / 有效评测任务数 | 多轮任务中，第一轮问了澄清问题不等于最终完成；不支持请求按既定规则解释或拒绝，可算正确处理，但需单独列出 |
| 实际解决情况 | 用户问题已解决、待补充、超出能力、转人工、放弃等分别统计 | 避免靠多拒答、多转人工提高“正确处理率”；采纳和满意不等于事实正确 |
| 成本与时延 | 同一窗口总运行成本 / 最终成功任务数；P50、P95 耗时及超时占比 | 失败尝试和重试成本也计入；不能只展示成功请求的速度 |
| 诊断信号 | 条件遗漏、数据未就绪、错误口径、失败重试、人工返工等的次数与占比 | 用于定位，不要求每个节点都做一个对外 KPI |

按专题、任务深度、单/多指标、单/多轮分别看。总体平均分提升，可能掩盖一个重要专题退化。均衡抽样的诊断集与按真实流量估计的整体效果分别报告；如果对高风险场景过采样，不能直接把样本平均数当作线上整体准确率。

评分保留 `Pass / Fail / 待复核 / Invalid`：

- `待复核`：缺少权威口径或证据，暂时无法判断。展示数量及可判定覆盖率，不能偷偷删除后报高分。
- `Invalid`：例如评测装置没有正确初始化、参考答案损坏，导致这次测量本身无效；单独修复和补测。
- Agent 在有效生产条件下调用失败、超时或输出错误，应记为任务失败，不用 `Invalid` 美化。

存在待复核结果时，不发布无说明的单一准确率。分别展示已确认通过数、失败数、待复核数及全量分母；“已确认通过数 / 全量”只表示已经证实正确的比例，不能当作完整判定后的准确率。

## 4. 第二步：建立能发现真实问题的样本与证据

### 4.1 三类案例池即可起步

| 案例池 | 来源 | 用途 |
| --- | --- | --- |
| 已知能力回归集 | 现有 200 题、历史修复案例、关键指标核对题 | 修改后检查旧能力是否退化 |
| 当前问题诊断集 | 用户纠错、超时、错误报告及其经过确认的变体 | 复现原因，检验修复是否针对一类问题 |
| 新请求抽查集 | 从近期真实请求中按专题和难度抽样，包括无人报错的请求 | 在针对这些题修改之前评分，了解当前未见请求的表现 |

收到一条差评时，尽量补到一句具体原因：“漏了华东筛选”“这里的新商户是按首单时间定义”“分母没有同步筛选”。用户纠错是线索，仍需查证；用户也可能引用旧口径。

**建议先人工走通约 10 个有代表性的案例，检验流程能否解释错误。** 这只是校准流程的起点，不能用来声称整体准确率稳定提高。之后抽样量取决于希望识别的改进幅度、波动和业务风险。

新请求如果用于验收候选版本，应先冻结候选，再评分；看过结果并据此调整后，它们就成为开发/回归案例。下一次要判断新请求表现，再补一批。评测参考答案不进入被测 Agent 的运行上下文或知识索引。

### 4.2 一条案例至少保存什么

| 字段 | 最小内容 |
| --- | --- |
| 请求与任务范围 | 原始问题、必要上下文、当前用户条件、任务类型、期望最终状态 |
| 运行版本 | Agent/工具/提示词/Skill/指标配置版本、实际模型标识；检索索引与评测器版本 |
| 数据环境 | 业务时间范围、时区、查询时刻、可用数据版本或快照、数据就绪状态 |
| 执行证据 | 标准指标及条件、实际工具请求与返回状态、结果引用、全量行数/文件、计算摘要 |
| 参考与评分 | 参考查询或可核验材料、口径确认者、容差、必须通过项、实际评分和复核结论 |
| 问题与修复 | 第一处有证据的偏差、受影响范围、修改版本、回归结果 |

保留可观察的输入、工具行为与输出即可，不需要记录模型私有思维链。敏感数据继续按公司既有权限与留存要求处理；常规看板可存结构化摘要，复现所需原始数据通过受控引用获取。

固定“查询日期”不一定固定答案：历史分区也可能回补。能用快照则固定快照；不能快照时，记录数据就绪状态，并让参考查询与被测执行面对可比的数据。若数据在两次查询间变化，应先解决可比性，不能直接归因于模型。

## 5. 第三步：用三层评分，既看答案也看证据

### 5.1 能写成规则的部分交给代码

优先校验：

1. 请求要求的指标和条件是否全部覆盖；不要求所有指标机械使用相同维度，而是逐项判断适用条件。
2. 用户要求、主 Agent 解析、传给取数 Agent 的参数、平台实际执行条件、最终报告之间是否一致。
3. 指标与维度组合、单位、粒度、时间边界和权限范围是否合法。
4. 数据是否已就绪，是否取得完整结果；空结果、真实零值、缺失值、失败是否明确区分。
5. 比率是否使用同人群、同时间和兼容粒度的分子分母；需要时汇总后相除，不平均每日比率。
6. 结果与参考数值/结果集是否一致，关键数字在报告中是否改写错；容差由单位与业务精度决定。

建议工具返回一个结构化“取数结果凭证”，至少包含：标准指标、实际执行条件、时间、粒度、单位、结果、数据来源与就绪状态。字段应由可信执行层记录，不能只把模型自行填写的声明当作证据。

上述一致性检查能发现条件在传递途中丢失，但**如果最初理解就错了，后面可能一致地执行错误需求**。所以仍要保留业务意图验收与人工抽查。

### 5.2 分析解释由模型辅助评审，业务争议由人确认

模型评审输入应包括：原始目标、必要上下文、实际取数证据、相关口径与方法、最终回答、明确评分项。评审输出应指出哪条事实或哪段证据支持判定；证据不足可判待复核。

对开放分析，可按四项分别评估：是否切题、结论是否有证据、方法是否适用、是否说明关键不确定性。对“用户可能采取什么动作”的有用性，可由业务负责人抽评。**缺少唯一标准报告，不代表无法验证其中的数字、数据范围和推断边界。**

关键数字错、人群错等设置为阻断项，不能靠语言流畅或结构完整的分数抵消。除非业务明确要求某些必经检查，否则不固定唯一工具调用顺序，也不要求与参考 SQL 字符串相同。

OpenAI 的内部 Data Agent 文章采用人工编写的参考 SQL，并结合生成查询及结果评估正确性。对你们的迁移点是：参考依据应能核验数据与语义；不必因为对方使用 SQL，就把你们的指标平台改成自由 Text-to-SQL。[来源](https://openai.com/index/inside-our-in-house-data-agent/)

### 5.3 评分器也需要校准

准备一小组人已经确认的对/错案例，刻意加入“数值看似正常，但漏条件”“结论流畅，但没有依据”等错误。检查规则与模型评审能否识别；人工既抽查判失败的，也抽查判通过的。

评分器、参考答案和口径都要有版本。更换评审模型或评分规则后，要重算可比基线，不能把评分标准放宽当成 Agent 进步。Anthropic 的评测文章强调多种评分方式配合，并通过轨迹检查和人工校准发现评分偏差；本文将其落实为上述规则、证据和复核分工。[来源](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 6. 第四步：沿证据找原因，把修改放在正确层

从用户需求开始，顺着解析、检索、取数、计算和报告找第一处偏差。如果证据不足，先补观测，不能仅凭最终错答认定某个 Agent 丢了条件。

| 原因 | 典型现象 | 优先修复位置 | 修复时要防止的新问题 |
| --- | --- | --- | --- |
| 业务意图或适用性错误 | 名称对了，但该指标不适合新商户、某次活动等目标 | 业务适用说明、指标选择规则、必要澄清 | 遇到清楚的问题也一律追问 |
| 配置或知识缺失 | 缺数据 ID、业务线映射、单位或枚举 | 权威配置与同步检查 | 模型临时猜一个值让调用成功 |
| 检索路由错误 | 正确信息存在，但取错专题/旧文档 | 元数据过滤、专题路由、召回与排序 | 无限制追加文档，干扰增加 |
| 条件传递遗漏 | 多指标请求只执行一部分；某个查询漏筛选 | 结构化条件清单、参数校验、执行覆盖检查 | 用一个指标的合法条件错误约束其他指标 |
| 数据质量与计算错误 | 数据尚未产完、关联重复、比率平均错 | 数据就绪检查、可信计算函数、粒度规则 | 为了“有答案”自动换时间或放宽筛选 |
| 分析方法不适用 | 将贡献分解当因果；跨人群比较得出错误结论 | 专题 Skill 的前提、方法和证据标准 | 模板越来越长，却缺少条件判断 |
| 输出层错误 | 取数正确，报告漏指标、换单位、改成含糊名称 | 结构化结果绑定、最终覆盖与引用检查 | 只比对文字，不验证报告实际数字 |
| 运行故障 | 超时、限流、重复提交、文件丢失 | 工具超时预算、分类重试、任务状态与幂等 | 无限重试；在评测中忽略真实依赖 |
| 记忆污染 | 沿用旧人群、旧时间或其他用户口径 | 作用域、有效期、冲突优先级、隔离测试 | 将一次个人偏好写成全局业务规则 |
| 评测自身有误 | 金标过期、评分误判、环境没初始化 | 参考依据、评分器、评测环境 | 调提示词去迎合错误答案 |

**每次集中修一个问题簇。** 同一种原因影响很多真实请求，通常比优化一条孤立难题更有收益。优先看错误严重性、实际覆盖面、发生频率与修复成本；不要只按差评数量排序，静默错误可能没人反馈。

必要时做定位实验：例如暂时提供已确认的正确元数据，观察同类问题是否恢复，以区分“没找到知识”和“有知识仍用错”。这种注入参考信息的运行只用于诊断，不能混入正式效果分数。

每个修复至少思考两种测试：**应该触发新规则的案例，以及不应该触发的相邻案例。** 例如修复新商户识别，同时检查明确问全部商户时不会错误套用新商户筛选。

## 7. 第五步：怎样证明一个改动确实有用

### 7.1 对照条件先对齐

旧版和候选版面对同一组请求、可比的数据状态、相同的会话/记忆初始状态，以及相同的评分标准。记录模型、工具、知识、缓存与并发配置；明确本次究竟改变哪一项。多个相关资产必须一起改时，作为一个版本包验收，不能声称已知道其中每项的独立贡献。

评测用隔离的用户和会话状态，重置或克隆记忆；避免第一轮运行的答案、缓存或经验泄漏给后一轮。评测最终态也要覆盖真实依赖：用到文件、授权、通知、外部工具的任务，要验证对应行为，而不只是模型文本。

工具自带评测能力也有覆盖边界。例如 Cortex 当前评测文档列出了 MCP、文件持久化及部分工具评分限制；选用平台评测前应逐项核对自己业务链路是否被测到。[来源](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-evaluations)

### 7.2 不只报一个新准确率

| 旧版 → 新版 | 要看什么 |
| --- | --- |
| 错 → 对 | 是否修复目标原因，还是这次碰巧成功 |
| 对 → 错 | 新增退化在哪些专题，是否涉及重要业务 |
| 错 → 错 | 是否原因变化；不要把更漂亮的错答算进步 |
| 对 → 对 | 成本、时延、输出完整性是否改善或恶化 |

每次报告至少给出：样本数、任务切片、四类变化数量、未判定/无效数、新增严重错误、成本和耗时。不要只展示净提升。

200 题从 190 题通过变成 191 题通过，只能先说本次多对了一题。模型随机波动、数据变化或题目组成都可能影响差值；对易波动的关键场景重复运行，样本充分时再分析差异的不确定性。不能挑一次最高分，也不能新版允许多次尝试、旧版只跑一次后直接比较。

首次成功与按生产策略有限重试后的最终成功可以同时记录，但比较时要统一策略，并计入重试成本。

### 7.3 发布门槛由业务决定，先写再测

建议采用以下门槛类型，具体数值留给实际基线与业务要求确定：

- 已知关键场景通过，且本次测试没有观察到新增严重错误；这不等于证明真实风险为零。
- 目标问题簇获得足够支持的改善；重要专题没有被总体平均数掩盖的退化。
- 成本和耗时在任务预算内，或增加的成本有足够质量收益。
- 口径/方法变化经过负责人的确认；线上加载与回退路径已检查。

低流量阶段先内部试用或限定用户、专题，不必强行做需要大量流量的 A/B 实验。若做影子运行，隔离通知和其他写入，防止同一个报告发两遍；若做流量比较，尽量保持同一用户/会话版本稳定，避免上下文混用。

发布后监测同类问题是否减少、无反馈抽查是否仍通过，以及成本和时延是否变化。发现严重错误可以先关闭受影响专题，再回退版本。**如果上游表或口径已发生不兼容变化，只回退提示词可能无效**，需恢复兼容资产或明确暂停该能力。

## 8. 第六步：让数据、口径和分析方法跟着变化

### 8.1 把依赖关系维护到够用的粒度

建议先建立简单清单，无需起步就做大型知识图谱：

```text
数据表 / 平台接口 / 业务定义
    → 指标与维度配置
    → 业务专题与分析 Skill
    → 对应评测案例、报告模板、检索索引及缓存
```

每个主要指标和 Skill 标记负责人、版本、生效时间、依赖与替代关系。**数据最后更新时间、业务规则生效时间、文档更新时间是三个不同概念。**

| 变化类型 | 触发后的 SOP | 主要验收项 |
| --- | --- | --- |
| 日常数据刷新或延迟 | 检查分区/批次就绪、完整性与异常；未就绪时说明可用范围 | “今天有数据”不等于今天的数据已经齐全 |
| Schema、接口或枚举变化 | 找影响指标 → 更新映射/适配 → 重放相关查询 → 同步索引与缓存 | 类型、粒度、单位、ID、筛选映射仍正确 |
| 指标业务口径变化 | 负责人确认新定义和生效范围 → 保留历史版本 → 更新配置、方法、参考答案 | 历史报告与新口径的关系明确，不把合法数值变化误报为 Agent 退化 |
| 分析方法变化 | 明确前提、目的及新增证据 → 修改专题 Skill → 新旧案例对照 → 复核结论 | 方法确实适用；没有把相关或贡献解释成因果 |
| 新业务或新数据源 | 先确认受支持的指标和问题范围 → 补少量关键案例 → 限定场景发布 | 不因检索到新表就宣称能分析全部新业务 |
| 废弃资产或口径冲突 | 标记废弃/替代、确定生效范围 → 检索排除旧版 → 检查仍依赖它的任务 | “Wiki 已改”与“Agent 仍加载旧索引”分开验证 |

一次变更应形成一个可追踪的兼容版本包：配置、工具、Skill、索引及相关评测引用彼此对得上。不同系统不一定能原子发布，可先双版本兼容、再切换；上线后检查实际加载版本。缓存键至少考虑影响答案的查询条件、数据/口径版本和授权范围，避免改了知识却读到旧答案。

Anthropic 的数据分析实践将数据模型、指标定义与相关 Skill 的维护连在一起，并要求人拥有业务定义。这里最适合你们借鉴的是“上游变更触发下游同步和验证”，具体仓库和发布实现可以适配你们的平台。[来源](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude)

### 8.2 专题 Skill 应包含一张“方法卡”

| 字段 | 需要回答的问题 |
| --- | --- |
| 适用范围 | 哪些指标、业务对象和问题适用？哪些不适用？ |
| 数据要求 | 需要什么粒度、观察窗口、对比基准、分子分母和数据就绪条件？ |
| 执行方法 | 必须完成哪些计算和核对？可复用哪个可信脚本？ |
| 解释边界 | 能证明什么，只能提示什么，缺什么证据不能下结论？ |
| 深度与停止 | 当前是局部一层分析还是完整专题报告？何时停止或要求补充信息？ |
| 验收与维护 | 至少有哪些适用/不适用案例？谁确认？何时生效？依赖哪些指标版本？ |

方法更新的典型坑：留存分析混淆不同入组日期；漏斗各阶段人群不一致；率的变化混入人群结构变化；贡献分解被写成因果归因；样本太小仍给确定结论；前后口径不同却直接比较。应把这些前提写进方法与用例，不能只要求模型“分析得更深入”。

关键指标可与可信报表或参考查询定期核对，但要明确独立性：两者共用同一错误源表时，结果一致只能支持“取数链路一致”，不能证明源数据真实无误。

## 9. 第七步：怎样让 Agent 自己参与进化

建议逐步自动化的是**发现问题、提出修复、运行验证和准备发布材料**。先让它成为一个能提交证据充分的修改建议的维护助手，再考虑受限的自动发布。

```text
线上反馈 / 随机抽查 / 数据变化 / 运行异常
    → 自动聚类、去重、整理证据
    → 生成候选用例和原因假设
    → 提出有来源的小范围修改
    → 在隔离环境运行对照与回归
    → 生成收益、退化、成本、影响范围报告
    → 按变更权限审核与发布
    → 监测实际效果，必要时回退
```

| 事项 | 建议自动化程度 | 边界 |
| --- | --- | --- |
| 收集日志、归类问题、识别知识可能过期 | 可自动 | 保留原始证据；自动归因只是候选 |
| 生成评测题、文档和 Skill 修改建议 | 可自动起草 | 不能将 AI 自己的答案直接变成权威标准 |
| 在已授权预算中运行评测、汇总版本差异 | 可自动 | 固定评分标准，不能隐去失败或改分母 |
| 已批准资产的同步、索引刷新、常规健康检查 | 可按既定流程自动 | 校验版本、兼容性和实际加载状态 |
| 用户私人偏好记忆 | 按既有记忆策略处理 | 明确用户作用域，不升级成组织级指标规则 |
| 指标定义、业务适用性、分析方法、权限或关键工具修改 | 建议由相应负责人确认后发布 | 影响业务事实或能力边界，需明确责任与回退方式 |
| Prompt/Skill 自动发布 | 闭环成熟后，才考虑允许范围内的低风险变更 | 必须预先授权范围、质量门槛和回退；试验失败自动停止扩散 |

Warp 在 2026 年 8 月介绍的方式是：外层维护任务读取反馈，提出小幅 Skill 修改，经过正常的 PR 审查和合并后供下次任务使用。这为“自进化”提供了一个可审阅的实现例子，不意味着系统可以盲目接受反馈或自行改业务真相。[来源](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)

对你们尤其需要守住三点：

1. **记忆、知识、方法分开治理。** “这个用户喜欢简短报告”可以是偏好；“新商户必须采用某个业务定义”必须有业务依据和生效范围。
2. **优化者不能自行改验收标准。** 候选版本不应通过删除失败案例、放宽金标或改评审提示词来获得通过。标准确需随业务变化时，另行确认并重建可比基线。
3. **自进化的成效也要评估。** 看人工维护耗时、真实错误率、错误修改建议比例、发布后回退次数，以及全流程成本。自动产出更多规则和文档本身不是进步。

一次请求里“再想一遍”“再调用一个评审 Agent”只属于本次任务内修正；只有形成经验证且可复用的资产变化，后续任务才有机会持续受益。这也不等于模型权重已经得到训练。

## 10. 哪些措施最值得优先做

以下顺序是结合你们已暴露问题的**收益假设**，没有实测提升幅度；应通过第 7 节验证。

| 优先级 | 措施 | 对你们的直接价值 | 怎样知道有没有用 |
| --- | --- | --- | --- |
| P0 | 条件清单贯穿解析、传参、实际执行、报告 | 针对多指标、多维度遗漏，以及输出丢条件 | 同类遗漏下降；清楚的简单问题没有多余澄清 |
| P0 | 结构化结果凭证与确定性计算检查 | 让错人群、错单位、数据未齐、错误比率不再靠模型“觉得合理”放行 | 静默错答检出增加；误拦截与时延可接受 |
| P0 | 200 题回归 + 修改前新请求抽查 + 首错归因 | 每次修改可比较，也能看到未被用户报告的问题 | 有新旧变化清单；能解释失败落在哪层 |
| P1 | 明确指标适用范围，收紧专题知识路由 | 解决“指标合法但不适用”及旧文档干扰 | 易混淆业务案例改善，不靠一味拒答 |
| P1 | 数据、指标、Skill、参考答案联动维护 | 减少上游变化引起的静默退化 | 变更影响能定位，线上版本一致，关键核对及时发现偏差 |
| P1 | 工具故障分类、有限重试与任务状态 | 避免暂时性故障直接失败或无限重试 | 最终成功提高，重试和尾部耗时受控 |
| P2 | 高价值复杂分析增加独立证据复核 | 针对事实正确但分析方法或结论有问题的场景 | 在同成本或可接受增量成本下，确实减少重要错误 |
| P2 | 更强模型、额外规划、更多 Agent 或微调 | 仅在证据表明瓶颈位于对应能力后尝试 | 通过隔离对照证明收益，保留无效尝试记录 |

你们当前不需要先重做架构。**先把已有能力做成“可观测、可验证、可维护”的系统，通常更容易找到真实收益来源。** 如果受限工具能力本身缺少业务需要的筛选，应该补平台能力或明确说明限制，不能只靠提示词要求模型完成。

## 11. 一个完整示例：从漏条件到可验证修复

以下为说明 SOP 的**合成例子**，不是公司真实数据或已证实的故障链路。

**请求**：“看一下上周华东新商户的支付转化率，只分析一层变化。”

假设该示例业务已明确：该指标为同一窗口、同一人群的支付人数 / 访问人数；“新商户”的定义另有已确认配置。参考数据如下：

| 人群 | 支付人数 | 访问人数 | 转化率 |
| --- | --- | --- | --- |
| 华东新商户 | 80 | 1,000 | 8% |
| 华东全部商户 | 120 | 1,200 | 10% |

1. **发现**：随机抽查发现报告给出 10%。指标名称正确、数字合理，但没有回答新商户人群。
2. **复现**：固定样例数据、口径、时区、解析出的起止时间、Agent 与 Skill 版本，确认 8% 的参考依据。
3. **定位**：假设执行证据显示主 Agent 已解析“新商户”，传给取数层时却缺了对应条件。此时才归因为传参遗漏；若源头就理解成全部商户，修复位置应不同。
4. **修复**：在已解析需求与工具请求间加入条件覆盖检查；缺关键条件时补齐合法参数再执行。平台不支持此筛选时，应解释限制，不能查询全部商户后继续包装成新商户结果。
5. **验证**：检查结果 8%、分子分母人群一致、报告标准名称与单位一致；只完成约定的一层分析。单凭这两行数据无法验证“变化原因”，还必须提供可比前期及方法所需的分解证据，否则应说明证据不足。
6. **防退化**：补“明确问全部商户”“第二轮改为全部商户”“两个指标支持不同筛选”“分母为零”“数据未就绪”案例，避免修复变成机械套筛选。
7. **发布与复查**：比较新旧版本的漏条件次数、误拦截、耗时和完整任务结果；限定场景试用后，观察真实多条件请求。

这个修复的价值来自一类条件遗漏被系统性发现与阻断。仅在总提示词后加一句“请不要遗漏条件”，可以作为候选改动，但不能替代执行证据与回归验证。

## 12. 维护节奏与可直接使用的模板

### 12.1 建议节奏，不是已创建的定时任务

| 时机 | 最小操作 | 输出 |
| --- | --- | --- |
| 每次请求 | 条件/数据/结果检查；异常分类；保存必要证据 | 可复查的执行记录 |
| 每次版本变更 | 目标场景和相关回归、新旧差异、关键场景核对 | 变更验收单 |
| 每次数据或口径变更 | 依赖影响检查、资产同步、相关参考答案复核 | 兼容版本与影响记录 |
| 每日或按数据产出节奏 | 数据就绪、重要查询核对、错误和超时异常 | 需要处理的问题清单；不把正常波动都当告警 |
| 每周 | 抽查无反馈请求、聚类失败、选主要问题、回看上周修改 | 一页质量与迭代记录 |
| 每月或业务大变更时 | 清理失效知识、评测覆盖与评分校准，复核长期成本收益 | 待修订资产和覆盖缺口 |

小团队可以从“每周 30–60 分钟复盘 + 随发布跑相关用例”试起，具体投入以实际流量和问题量调整。重点是闭环完成，会议时长与题目数量本身不是绩效。

### 12.3 变更验收单

```text
修改目的：解决哪类真实问题？影响哪些请求？
故障证据：第一处偏差在哪里？是否仍有未知项？
本次修改：改了哪些资产？为什么在这一层修改？
对照条件：数据、会话状态、模型、工具与评分版本是什么？
用例变化：新增了哪些应该触发 / 不应该触发的案例？
结果：旧错新对 __；旧对新错 __；均错 __；均对 __；待复核/无效 __。
重要退化：是否涉及关键专题、错误口径、权限或错误交付？
成本与耗时：每成功任务成本、P95、超时与重试有什么变化？
发布方式：适用用户/专题、观察窗口、负责人是谁？
回退方式：恢复哪些兼容版本？不能恢复数据时如何暂停能力？
发布后结论：收益得到支持 / 仍待观察 / 已回退；依据是什么？
```

### 12.4 用于面试的简短表达草案

“我们已有指标平台、专题分析方法和业务题库。持续迭代要把线上问题和抽样检查转成可复现用例，先区分口径、数据、工具、分析和输出问题，再在相应层修复。通过固定条件下的新旧对照，同时看收益、退化和成本，验证后发布并观察。数据和分析方法更新也纳入同一条变更链路。Agent 可以自动整理反馈、起草修改和执行评测，业务定义与关键发布仍有明确的责任边界。”

这是改进思路的表达，不应将尚未实施的流程讲成已经完成的项目成果。
