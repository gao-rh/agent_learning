# 让运营自助完成经营分析：Data Agent 的痛点、设计与实践

> v0.1 · 2026-09-08 · AI 草案，待共同审阅。本文依据已保存的项目口述与材料组织成文；整体论述为 Codex 提炼，尚未由用户逐段确认。本轮未检查公司代码或原始运行日志。实际做法、已确认架构方向和后续建议在相应段落中说明。

运营提出一个经营问题，往往只需要一句话：“这个活动效果怎么样？”或者“这个渠道的渗透率为什么下降了？”但要回答它，背后需要完成一系列专业工作：选择合适的指标，确认统计范围，找到数据来源，处理计算口径，再选择分析方法解释变化。

过去，这些工作通常由运营、数据开发和商分协作完成。我们的智能经营分析项目希望把其中可复用的专业能力放进系统，让运营和业务人员通过自然语言，自助取数并完成经营分析。用户既可以查一个数，也可以从一个局部异常开始追问，或者要求生成完整的专题报告。

实现这一目标，需要让业务问题、查询口径、实际数据与分析结论保持一致。本文沿着这条链路，说明我们遇到的主要问题、采取的解决方法，以及仍然存在的边界。

## 一、业务痛点：一次数据需求，需要跨越多道专业门槛

运营知道自己关心什么业务现象，却未必知道平台里应该查哪个指标、用什么维度、选择哪段时间。数据开发需要将业务语言翻译成查询需求；商分再判断怎样分析、结论能支持到什么程度。如果结果引发新的问题，相关人员还需要继续往返沟通。

这种工作方式的成本分布在整条链路上：需求翻译、口径确认、排期等待、查询计算、结果解释，以及后续追问。根据项目复盘中的使用反馈，传统看数流程至少需要等待半天，常规专题分析通常需要两到三天。这里的时间包含业务协作和等待，不能直接当作 SQL 或模型运行耗时。

我们的目标，是让常规需求不再以数据开发和商分介入作为前置条件，同时保留面对新业务、复杂判断和重要结论时的专业协作能力。项目建立在已有指标平台、数据集和数仓能力之上，由业务、产品、商分、数据与 Agent 技术团队共同建设。

## 二、技术难点：沿着一次分析请求，识别三个关键转换

用户看到的是一次对话，系统需要连续完成三个转换。前一步发生的错误，可能被后续正常执行的工具放大，最终形成一份看起来合理的报告。

| 转换 | 需要解决的问题 | 典型失败 |
| --- | --- | --- |
| 业务问题 → 明确口径 | 用户究竟要回答什么问题，应使用哪些指标、维度和时间范围 | 指标合法可查，却不适用于当前事件；复杂请求漏掉条件 |
| 明确口径 → 可靠数据 | 查询和计算是否完整地执行了已经确认的需求 | 只拿到预览数据；日期或比例计算错误；查询超时 |
| 可靠数据 → 经营判断 | 应采用什么分析方法、分析到哪一层、结论由什么数据支持 | 从错误入口展开；局部问题跑成完整报告；报告改变指标含义 |

检索、上下文管理、性能和评估贯穿这些转换。例如，指标定义已经存在但没有被找到，会影响第一步；全量明细挤满上下文，会干扰后续分析；报告改写标准指标名，则可能在最后一步破坏前面已经确定的口径。

因此，我们围绕每个转换建立对应的能力，并检查它们之间的任务与结果交接。

## 三、确定分析口径：让业务语言落到标准指标和查询范围

### 指标匹配与业务适用性是两个问题

以“看活动效果”为例，它可能涉及拉新、转化或收入，需要先明确业务目标。即使用户明确说“点击率”，仍可能指入口广告、尾随广告，或者希望按节点、分流组、整个活动观察。同一个公式也未必能用于所有资源位；某些范围缺少可靠数据时，查询得到数字不代表这个数字适合用于判断效果。

这些是本轮讨论用来说明难点的场景，不将它们全部认定为已经发生的项目事故。它们共同说明：系统既需要确认用户指的是哪个标准指标，也需要判断这个指标能否回答当前问题。

项目已有的指标平台提供了第一层基础。人工配置包含指标名称、别名、ID、所属数据集、支持维度、计算公式和常见分析场景；维度配置包含名称、别名、枚举及支持的指标。AI 可以辅助形成初稿，最终定义由人在平台上配置。

这些配置与查询能力共同构成了项目语义层的核心：把业务概念连接到可执行的数据定义。Agent 在此基础上检索和组装查询，底层接口由平台提供。

### 用标准身份、维度映射和澄清逐步收敛需求

实际取数链路先提取用户原始的指标表达，到指标库检索。完全匹配时确定标准身份；存在相近候选时，展示完整标准指标名供用户确认；原话没有合适结果时，再根据上下文补充检索。

例如“查询上周新商餐饮渗透率”，需要分别确定标准指标、“新商”和“餐饮”所属的维度及标准值，以及“上周”的日期范围。指标库还会返回支持维度、数据集和查询方式，Agent 根据这些元数据组装参数。对于不支持的指标与维度组合，取数引擎返回明确的不支持信息，再由 Agent 解释并提出可行替代方案。

业务用户适合澄清目标和统计对象；数据集、字段和接口参数等技术细节，应由系统依据配置处理。这能减少用户为了使用 Agent 而重新学习后端数据结构的负担。

### 用分析方法引导选择，同时保留未解决的边界

在指标身份匹配之外，我们已经在分析方法知识库中维护推荐指标。Agent 识别分析类型并读取对应知识后，可以据此选择更合适的指标集合。这是一种业务知识引导，尚未形成覆盖所有事件的强适用性校验。

复杂请求还会带来另一类问题：多个指标分别带有不同维度条件时，Agent 有时会遗漏部分条件。实际采取的办法是调整提示词，先拆出需要查询的指标，再逐个明确各指标的维度要求，分别澄清。这一问题仍有残留，不能将它表述为已经通过程序校验彻底解决。

## 四、可靠执行：把稳定规则封装进工具，让模型处理选择和解释

确定口径之后，日期、查询方式和计算规则中有大量可以明确实现的部分。项目演进中，我们逐步把这些规则从文档说明落实到工具和脚本。

相对日期由脚本转换为具体起止时间；指标 ID 用于定位查询方式和所需参数；比例型指标由封装脚本完成分子、分母取数及计算。以可加的点击次数和曝光次数为例，整体点击率应汇总分子分母后重算。去重人数等不可直接相加的量，需要遵循各自的指标定义，不能套用同一种聚合方式。

这种分工减少了模型自行计算和反复操作中间值的机会，但输入条件依然必须正确。脚本准确执行了一组错误筛选条件，仍然会得到不符合用户问题的结果。

### 取全数据与控制上下文，需要同时解决

我们曾遇到平台默认参数只返回第一页或前 200 条的问题。工具会正常返回数据，模型容易据此继续分析；但数据只是整体的一部分，结论可能已经偏离实际。另一方面，如果把大量明细全部塞进模型上下文，又会增加 Token 消耗，并干扰它对任务、口径和关键异常的关注。

项目实际采用的链路是：

```text
固定调用平台全量导出／下载接口
→ 将完整结果保存为文件
→ 模型读取前 200 行预览，了解格式和明显异常
→ 代码读取全量文件完成聚合与统计
→ 将汇总结果交给模型解释和检查
```

其中，全量数据来自平台导出接口；前 200 行只是格式和内容预览，不能证明全量数据正确。开发者固定可靠性相关的取数参数，避免把是否取全数据交给模型临时决定。完整数据保留在文件中，模型主要处理理解和表达需要的信息。

### 性能优化围绕重复工作展开

长周期分析曾需要反复查询多年历史数据。项目通过缓存常用历史结果、每天由首次查询触发当日数据更新来减少重复计算。一次需求中的多项独立取数也可以并行执行；依赖前一步分析结果的下钻，则需要等证据返回后再决定。

使用反馈认为缓存带来了明显提速，但目前没有统一的 P50、P95 和缓存命中率统计。缓存失效、历史数据回刷与并发首次更新等细节仍需另行说明，不能从“有缓存”推导出所有长周期查询都已稳定快速。

## 五、经营分析：按业务专题选择方法，按用户问题控制深度

取得数据之后，下一步是决定怎样分析。商分积累的经验提供了可复用的方法，包括关注哪些指标、采用什么比较基准、如何下拆、如何解释变化。

早期完整分析流程倾向于从总体开始，逐层进入局部。实际用户却常常已经知道异常发生在哪里，例如直接询问某个渠道的指标为什么下降。此时重新从全局跑一遍，会增加查询耗时，也可能偏离用户当前关心的问题。

项目因此把专题方法与具体执行范围结合起来。按最近确认的设计，路由顺序是：

```text
确认标准指标
→ 根据指标所属业务专题选择分析 Skill
→ 确定本次需要局部分析还是完整报告
→ 执行该专题相应的方法与查询
```

同样一句“今天为什么变化这么多”，问保费时需要结合目标、达成情况和驱动因素；问渗透率时则要按对应专题的方法理解变化。问法帮助判断任务意图，标准指标及其所属专题决定采用哪套业务方法。

执行深度也有明确区别：用户只问当前指标或某个维度的问题，就执行该专题针对当前节点的一层分析；用户继续追问，再进入下一层。明确要求完整专题报告时，才执行较长的完整链路。

趋势、公式拆解、维度下拆、漏斗等方法可以在专题内部复用。专题知识决定为什么分析、先看什么以及怎样解释，工具和脚本完成具体计算。这里不把这些方法都宣称为独立发布的 Skill，也不根据现有素材推算最终 Skill 数量。

这项设计使专业方法能够围绕用户当前的问题发挥作用，同时控制分析范围和不必要的查询。找到变化集中的对象或环节后，还应区分数据上的贡献解释与业务原因假设；重要原因判断需要相应业务事实支撑。

## 六、组织执行：让专业能力有边界，让必要条件能跨步骤保留

统一架构以受控编排器组织主 Agent、取数 Agent 和分析 Agent。三者的职责可以概括为：

| 角色 | 核心职责 | 需要交接的内容 |
| --- | --- | --- |
| 主 Agent | 理解问题、澄清、组织任务和最终回复 | 已确认的取数参数，或分析主题、类别、目标与核心指标 |
| 取数 Agent | 查元数据、调用查询与计算工具、检查结果和处理取数错误 | 实际查询指标、条件、结果及必要错误信息 |
| 分析 Agent | 按专题方法规划查询、解释数据、形成分析输出 | 分析结论及其数据依据 |

取数能力供直接查数和分析任务共同使用。拆出取数 Agent 的实际理由包括：隔离取数过程的上下文，集中维护专用提示词和工具，以及并行执行多项独立查询。这些边界也便于分别评测专业能力。

拆分同时引入了交接要求。减少上下文时，指标、时间、筛选范围和分析目标必须继续保留；不能用更短的上下文换取条件丢失。历史上发生过多轮追问未继承上下文的问题，但不能据此认定所有条件遗漏都发生在 Agent 交接环节。

在已确认的架构方向中，编排层管理允许的路由、执行边界和停止条件，Agent 在边界内完成澄清、方法选择和错误解释。后续 LangGraph 学习设计进一步表达了父图、分析子图和共享取数子图的状态与恢复方式；该学习设计不作为原生产系统具体实现的证明。

## 七、一次失败带来的认识：可信度必须延续到最终报告

项目中一位新员工曾使用了一个不适用于目标业务事件的指标，并将 Agent 生成的分析报告用于汇报。进一步复盘发现，Agent 对用户用词的映射本身是正确的：它匹配到了一个真实存在、能够正常查询的标准指标。问题在于，用户选错了观察该事件的指标，而 Agent 也缺少判断适用性的业务知识。

报告生成又放大了这个问题。查询和分析阶段仍然保留着标准指标身份，最终报告却将标准指标名改写为用户口语，读者更难发现实际查的是什么。

这次失败暴露出两个相互关联的缺口：选定指标时没有充分判断业务适用性；交付报告时没有保护已经确定的指标含义。对非专业用户而言，不能把识别这类错误的责任主要留给阅读报告的人。

项目现有的推荐指标机制可以缓解第一个问题。第二个问题对应的改进方向，是让关键数字继续关联实际查询指标、统计范围和单位，并在报告生成后核对一致性。这些属于待完善的机制，尚不能写成已经全部上线。

按照最近口述，线上取数检查主要核对返回指标名，并由模型结合较宽的参考范围关注零值等明显异常；异常时逐步排查参数、原子指标和计算，超时未解决则返回失败。该机制能够发现部分问题，但名称一致、数值合理都不足以独立证明查询口径正确。

## 八、评估与效果：说明我们验证了什么，也说明数字能代表什么

项目逐步积累了自行准备、AI 生成和线上真实用户问题。标准答案由 AI 先给出候选，再由人工逐题确认；评测时由模型对照标准答案判断取数结果。

根据用户最近明确的口述，最终 200 道业务取数题上的准确率为 95%。这组题兼用于迭代调试和效果验证，没有单独划分只用于最终测试的集合。因此，该结果用于描述这组业务题上的表现，不能直接替代全部线上新问题或开放经营分析的准确率。本轮未读取原始逐题日志。

剩余失败据用户回忆主要包括复杂请求遗漏部分查询条件，以及执行过程中的报错或超时。历史迭代中的全量数据、单位、映射配置等问题需要分别看待，不能全部归入最终未通过的题目。

对完整 Data Agent，我们已经讨论了更完整的三层评估框架：

| 层次 | 要回答的问题 |
| --- | --- |
| 顶层结果 | 数据任务是否取对；整项任务是否完成；首跑与重试后成功有何区别 |
| 流程诊断 | 错误首先发生在理解、澄清、任务组装、取数、分析还是报告环节 |
| 横向质量 | 延迟、成本、稳定性、连续性和权限边界是否满足要求 |

这是评估设计框架，不能将其全部视为已经上线的自动检查。它的价值在于帮助我们决定改哪里：正确知识不存在，需要补知识；知识存在但没有进入候选，需要改检索；候选已召回却选错，需要改选择和澄清；参数正确但执行失败，需要查工具与平台。

业务使用方面，已有记录覆盖约 20–30 名场景险产运与商分用户，普通业务更常用于取数，商分与少数资深业务使用更深入。项目也用于生成周报和初步分析，并支持用户在业务讨论中继续追问。根据使用反馈，常规专题分析从两到三天缩短至约一到两小时；这一范围不代表所有开放分析。覆盖人数也不等于日活或周活。

这些变化对应的业务价值，是缩短常规数据需求的等待，减少口径翻译和多角色往返沟通，让业务人员可以更快继续判断和追问。本人在项目中承担 Agent 技术框架主负责人角色，联合相关团队组织并推动这些能力落地；已有数据平台及团队成果保持各自的责任归属。

## 九、从这篇文章出发，下一步可以怎样优化

Anthropic 将自身自助分析中的主要错误归为概念歧义、数据与知识过时、检索失败，并围绕这些问题组织治理后的数据定义、知识、执行方法和验证。这个分类为检查我们的系统提供了参考；它没有证明我们具备相同实现，也不能用对方的效果数字替代本项目评测。[参考文章](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude)

结合现有问题，以下是值得评估的改进建议，尚未成为已确认实施计划。

**把推荐指标补充为可解释的选择依据。** 在已有分析知识中加入适用前提、常见混淆、反例和必要的澄清问题。优先覆盖已经反复遇到的业务场景，让 Agent 能说明为什么选这个指标，以及什么条件下不能用。

**围绕实际查询结果保护任务和报告中的关键事实。** 对复杂请求，可增加已确认指标与条件的逐项核对；对报告，可核对标准指标、范围和单位是否与实际查询一致。前者针对条件遗漏，后者针对最后表达阶段改变事实，两者需要各自验证效果。

**让知识变更与失败案例形成持续维护机制。** 为常用定义和分析知识保留维护来源、生效范围与版本；变更时检查相关案例。固定一组代表性问题观察单项修改前后的变化，分别记录召回、选择、参数、执行和表达中的错误。对新业务缺乏可靠依据时，保留未知，避免让模型自行补成确定规则。

这几项优化直接对应现有边界：让指标选择更有业务依据，让查询条件与最终表达更一致，让已经积累的知识和修复能够持续有效。

## 附记：怎样把零散经验组织成项目表达

本稿使用的写法是：**先说明业务需要，再沿分析链路定位问题，解释原因与机制，最后交代效果和剩余边界。** 章节顺序依据问题之间的关系安排，技术组件出现在它实际解决问题的位置。

| 原始经验 | 可以提炼出的项目表述 |
| --- | --- |
| 指标很多，名字相近，有些场景用不了 | 自然语言到标准口径的映射，同时存在指标身份与业务适用性问题 |
| 默认只返回 200 条，明细太多又挤满上下文 | 数据完整性与模型上下文需要分别管理，用全量文件和代码计算连接两者 |
| 用户已经知道哪个渠道异常，完整流程却从头查 | 专题方法需要支持用户当前的分析入口，并按任务要求控制深度 |
| 报告最后把标准指标名改成了口语 | 取数正确性需要延续到交付阶段，关键事实在生成文本时也要受保护 |
| 最终分数有了，但仍不知道哪里容易错 | 结果评测需要结合流程诊断，明确下一次应该修改哪一层 |

每条经验都可以按“场景 → 失败现象 → 原因 → 实际改动 → 效果 → 边界”继续补充。材料不足时，保留已知机制和未知效果，不用新增技术名词填满空缺。
