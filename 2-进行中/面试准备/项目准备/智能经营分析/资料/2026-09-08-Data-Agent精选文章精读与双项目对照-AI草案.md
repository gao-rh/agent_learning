## 先看结论：你最值得补的是什么

你已经有人工指标配置、确定性计算工具、专业 Agent 分工、分析 Skill、业务知识、用户记忆和案例驱动迭代的经验。继续读“Agent 会规划、调用工具、反思”这类介绍，新增收获有限。

这组资料对你最有价值的地方，是把已有经验推进到三个更具体的问题：

1. **知识怎样持续保持正确**：数据集、口径、分析 Skill 和评测题发生变化时，谁负责更新、怎样同步、怎样知道没有改坏。
2. **怎样验证整条业务链**：数字看起来合理，未必满足用户的全部条件；报告看起来自洽，未必保留真实指标身份；评测框架能够运行，未必覆盖文件、工具和权限路径。
3. **反馈怎样安全地变成下一版能力**：你的质检已经有自动 Prompt 调整和评测，进一步值得学习的是反馈来源、标签规则、发布审核与回退如何连起来。

**如果只选三篇：经分优先 A1 → A6 → A2；质检优先 A8 → A6 → A9。** 两条路线共享评测材料，不需要各读一套。如果目前还不清楚 Cortex 是什么，先用约 5 分钟读 A3 的定位与架构映射，再进入精读。时间是选读估计，不是完整理解所需时间。

| 名词 | 在这份报告里的意思 |

## 3. 逐篇精读与项目比较

### A1｜Anthropic 自助分析：重点是维护与验证，而非“再加一层 Skill”

**原文定位。** [How Anthropic enables self-service data analytics with Claude](https://claude.com/blog/how-anthropic-enables-self-service-data-analytics-with-claude) 是内部数据团队的工程复盘。正文依次讨论数据歧义、数据底座、权威资料、Skill、验证和附录模板。关键机制是缩小权威数据范围，区分知识导航与分析流程，让数据变更同时更新相关文档，并结合离线评测、单组件比较和线上纠错。它还公开了“直接开放大量历史 SQL 检索没有明显收益”的负面结果。

**与你的经分项目怎么对应。**

| 原项目位置 | 重合判断 | 真正值得补强的地方 |
| --- | --- | --- |
| 指标平台人工配置，标准指标决定查询方式 | 已有重合，P1 | 学习重点不必再停留在“人定义指标”。应检查配置变化后，Skill、索引、缓存与题目是否仍使用同一口径 |
| 商分方法沉淀为专题 Skill，含推荐指标 | 已有重合，P2、P3 | 为每个专题补清适用条件、禁止用途、缺数据时的停止条件，避免只有一条理想分析路径 |
| 200 题和线上错误回流 | 已有重合，P1 | 将一次变更与受影响题目关联，分别记录修复、退化和成本；已有完整评测草案 P4，新增工作应落到执行证据 |
| 查询正确但报告隐藏标准指标 | 明确缺口，P2 | 让结果中的指标身份、单位和时间成为报告可核对的字段，而不只要求“写清楚来源” |

**可迁移的小设计（AI 建议）。** 选择“渗透率”一个专题，把指标定义、相关数据集、日期工具、分析方法和回归案例列成依赖清单。若业务改变分母范围，变更说明应列出受影响的查询、报告模板、缓存和样本；由各自 Owner 判断需要重算还是只更新解释。它的价值是防止“数据已经改对，但 Agent 仍按旧说明工作”。这是维护机制，不要求推翻现有指标平台。

**对质检的借鉴。** 同样的依赖关系可用于“某类辱骂规则调整”：先确认规则适用范围与生效时间，再检查标注指南、Prompt、旧样本标签和复核说明。已有自动 Prompt 调整不等于业务规则的权威来源也应自动改变。

**读时要保留的判断。** 原文中的语义层优先指令，不等于代码已经封死所有绕行路径；其内部提升幅度也不能用来预测你的收益。“分析结果缺少容易获得的业务标准答案”不意味着 SQL、数据质量、单位和计算无法做确定性检查。对于你已发生的指标适用性问题，仅知道权威指标在哪里仍不够。

**重点章节：** `Skills`、`Validation`，附录中的数据完整性与报告要求。先读正文再看模板，避免把模板的每条要求都变成自己的新依赖。读完应能回答：**改了一个业务定义，系统怎样知道哪些知识和评测需要跟着变？**

### A2｜OpenAI 内部 Data Agent：最值得学的是“数据怎样生成”也成为上下文

**原文定位。** [Inside OpenAI’s in-house data agent](https://openai.com/index/inside-our-in-house-data-agent/) 介绍内部定制工具，不是可直接下载的完整产品。它把表使用、人工注释、代码提取的含义、组织知识、记忆和实时查询组织成六类上下文；离线加工可检索信息，运行时补查。质量部分使用人工标准 SQL，比较候选查询及执行结果；访问继承用户原有权限。

**已有重合。** 你的项目已经具备指标与维度元数据、业务知识、用户记忆、异常后继续排查、专业 Agent 分工。看到“多层上下文”无需理解为自己遗漏了整个架构。用户记忆按用户和 Task 组织、并有会话内与闲时整理两条写入链路，P3 已明确记录。

**最有增量的位置：超出标准指标覆盖、进入底表或 SQL 的路径。** 你在 P2 中已有选错数据路由、遗漏过滤或关联条件的案例。表名、字段名与简短描述不足以说明这些差异：

| 需要知道的问题 | 仅靠表说明可能缺什么 | 可补充的项目证据 |
| --- | --- | --- |
| 两张表都叫订单，应该查谁 | 是否排除测试单、取消单；是否只含某业务线 | 生产 SQL／转换逻辑中的过滤条件与负责人确认 |
| 周渗透率应该怎样算 | 来源是原始分子分母、预聚合比率，还是去重结果 | 源粒度、聚合状态及可重算方式 |
| 昨天的数据是否可用 | 分区存在但任务未完成；历史数据可能回刷 | 任务完成状态、数据就绪时间和来源版本 |

上表是迁移分析，不是对 OpenAI 公开字段的逐项复述。对你而言，可先把一个常出错数据集的“生产逻辑 → 已有配置”核对清楚，再考虑自动加工更多表；不必一开始就建全公司代码知识图谱。

**需要限制自动化的地方。** 代码体现“系统现在怎么算”，不必然体现“业务批准应该怎么算”。若代码与人工口径冲突，应产生带来源的差异记录，不能让模型自行覆盖指标平台。用户记忆可以保存个人偏好；正式指标变更需要独立的业务权威与审核。

**和 A1 的历史 SQL 结论是否矛盾？** 不构成直接矛盾。两篇材料采用的加工、检索和使用方式不同，实验环境也不同。对你的项目应比较“只加原始 SQL”“加入人工核对过的数据说明”等具体方案，不能概括为“历史 SQL 一定有用／没用”。

**对质检的相关性：中等。** 更适合启发输入数据说明，例如 ASR 的角色字段、切句规则、缺失字段的含义。它没有提供质检规则、噪声鲁棒性或分类效果的直接解法。

**重点章节：** `Context is everything`，优先看代码补充、组织知识、记忆、实时上下文；再看 `Moving fast without breaking trust`。读完应能回答：**哪个真实错误是增加表描述无法解决、必须回看数据生产逻辑才能解释的？**

### A3｜Cortex Agents 总览：用于理解职责分工，不当作完整开源架构

**原文定位。** [Cortex Agents](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents) 是 Snowflake 的托管平台文档：运行层组织计划、工具调用与后续判断；Analyst 面向结构化数据，Search 面向文档，并可接计算及其他工具。Agent 是可复用配置对象，Thread 保存跨轮会话，Run 表示一次请求。文档公开应用接口与运行行为，没有提供可据此完整自托管的核心服务源码。

**与你的架构按职责映射。以下是比较图，不是 Snowflake 内部实现图。**

| Cortex 公开概念 | 你项目中接近的职责 | 不能画等号的地方 |
| --- | --- | --- |
| 编排循环 | 主 Agent 组织任务、判断下一步 | 不能据此认定底层采用你拟定的父图／子图、状态机或 LangGraph |
| Analyst 工具 | 受控取数能力 | 你的路径包含指标平台接口与确定性脚本，不能统一改称 Text-to-SQL |
| Search 工具 | 业务知识检索 | 找到业务事件文档不等于证明它造成指标变化 |
| 代码计算工具 | 文件聚合与计算 | 可让模型生成代码的沙箱，与已有封装计算脚本的自由度不同 |
| Thread／Run | 会话与一次执行记录 | 持续会话不自动等于跨进程任务恢复、文件持久化或幂等完成 |
| 平台治理 | 权限、运行控制和观测底座 | 必须再区分平台提供与个人实现，P1、P5 |

**已有重合：高，新增架构思想有限。** 你的“主 Agent＋取数与分析能力分工”已经能解释其中大部分职责。它最大的价值是提供一个产品化对照，使你在面试中能说清哪些属于 Agent 业务设计、哪些属于公共运行平台。

**可补强：执行对象的身份与生命周期。** 在自己的学习复现里，明确一次分析的任务 ID、会话 ID、每次查询 ID、结果文件引用和执行状态。特别是取消后重问、跨轮追问和进程重启，应该分别测试；不能只因有聊天历史就声明原分析可恢复。P5 已有相关设计方向，因此这是细化与验证，非重新立题。

**对质检：架构对照价值大于改造价值。** 固定的筛选、脱敏、复核顺序本来适合 Python Workflow；不需要为了贴近 Cortex，把每一段都换成可以自由决定下一步的 Agent。

**关于“最成功之一”。** 可以把 Cortex 作为重要商业产品案例来学习；这份架构文档本身不证明市场排名或业务成功率。此前讨论的客户数量也不等于它对你的场景最适合。本报告按可学到的机制筛选，没有做独立市场份额排名。

### A4｜Semantic Views：你已经有语义定义，值得比较的是定义能被谁执行

**原文定位。** [Overview of semantic views](https://docs.snowflake.com/en/user-guide/views-semantic/overview) 把业务模型保存为数据库对象，包含逻辑表、关系、行级事实、聚合指标与维度，也可通过 SQL 查询。一个容易忽略的细节是：文档说明 Cortex 的相关路径会读取语义定义，再针对物理表生成 SQL；不能把所有路径都理解为直接执行同一种语义查询接口。

**已有重合。** P1 中的指标 ID、别名、公式、支持维度、数据集和维度枚举，已经承担相当多的业务语义工作。把这些能力称为“仅仅是配置，没有语义层”不准确。

**值得进一步比较的三个层次。**

1. **定义层：** 指标是什么、可按什么维度分析、公式和时间口径是什么。
2. **执行层：** 查询服务是否按这些定义生成或执行查询，还是模型参考文档后自行写出查询。
3. **检验层：** 最终实际查询是否遵守用户条件和适用规则。

你的比例脚本把分子分母查询、聚合和相除封装起来，是执行层的明确机制。不支持的维度组合由引擎返回不支持，也不是单靠自然语言提示。但复杂请求漏条件表明：已经有合法的定义和执行接口，仍不能证明每次查询包含了所有用户条件。

**可迁移的检查表（AI 建议）。** 不必立刻重建一套语义引擎。先选一个指标，核对以下内容是不是有唯一、可追溯的来源：

| 检查项 | 为什么与你的项目有关 |
| --- | --- |
| 源粒度与允许的目标粒度 | 日级去重不能自然推出跨日去重，已有比率脚本也不能覆盖全部聚合类型 |
| 连接关系与基数 | 多对多连接可能放大分子或分母；“SQL 能跑”不能识别全部错算 |
| 业务对象与分析场景 | 指标可查询不代表它适用于当前业务事件，正对应 P2 的新人案例 |
| 生效版本及来源 | 配置、文档、历史结果变化时，需要知道采用哪一版解释 |

这些是针对项目的补强建议，**不是该概览声称全部自动解决的能力**。业务事件适用性尤其不能因为采用 Semantic View 就视为闭环。

**对质检：借鉴形式，不能硬套模型。** 可以集中管理规则名称、适用场景、严重程度和生效版本，但这不是把主观语言判定直接变成 SQL 指标。比如“引用客户辱骂”和“客服主动辱骂”的区别，仍需要上下文及人工标准。

**重点章节：** `Why use semantic views?`、`Understanding semantic views`。注意区分产品的 facts／metrics 术语与通用数仓建模，不要反过来修改你已经明确的维度建模理解。读完应能回答：**你项目的一项规则，是描述给模型看、由接口执行，还是在结果阶段检查？**

### A5｜Cortex 构建最佳实践：工具还没选对时，详细知识可能根本读不到

**原文定位。** [Best Practices for Building Cortex Agents](https://www.snowflake.com/en/developers/guides/best-practices-to-building-cortex-agents/) 从业务范围、指令、工具、部署到性能给出示例。它区分数据定义、编排指令、回答格式和工具描述，特别强调工具选择时模型先看到名称与简介，而非完整数据模型。页面标注更新于 2026-06-15，并提示可能滞后于当前产品；部署版本功能的状态应另查当前文档。

**已有重合。** 你已经做了专业 Agent 隔离、专题分析路由、日期脚本与参数工具，也意识到常规流程不适合所有局部问题。这篇不需要重新从“一个 Agent 应有几个工具”开始学。

**真正的新切口是路由信息放置的位置。** 如果正确约束只写在某个 Skill 的第五页，而模型第一步没有选中这个 Skill，约束就不会起作用。针对 P2 的错路由和 P1 的漏条件，需要分别问：

| 出错时点 | 应检查的对象 | 不应只做的修补 |
| --- | --- | --- |
| 尚未选择工具／专题 | 名称、简介、数据覆盖与排除范围是否互相冲突 | 只给被漏选的 Skill 加更多正文 |
| 已选工具，参数不完整 | 用户条件与结构化参数之间是否有逐项对应 | 只改工具名，让它听起来更专业 |
| 返回数据后写错名称或单位 | 证据字段到报告的映射与验证 | 把事实保护当成“回答风格”要求 |

**工具描述的项目示例（新拟，非生产原文）。** 对某个封装指标查询工具，可以说明：它仅查询已配置标准指标，需要指标 ID、确定日期及过滤条件；日期来自日期工具；指标支持范围来自元数据；返回标准指标身份、单位和数据引用；对没有覆盖的维度应返回明确错误。哪些条件仍由模型判断、哪些由代码执行，应在实现文档中另列，不能认为写进描述就有了强校验。

**对质检：只借鉴职责划分，不借鉴自由路由。** 你的主链是固定 Workflow，省略脱敏或跳过人工确认不是允许模型自主选择的方案。可以改善每个模型步骤的输入说明和失败返回；不需要把确定顺序搬进一个“大 Prompt”让模型遵守。

**与本地设计的重合。** P5、P8 已经讨论父图与节点契约，新增收益是把文档约束落到正确位置并核对实际执行，而不是再画一张层次更多的图。

**重点章节：** `Tool descriptions` 的三个步骤、`Best practices between orchestration and response instructions`、`How to improve agent performance`。汽车业务示例主要看组织方式，不搬它的业务阈值或结论模板。读完应能回答：**某次失败最早出现在哪一层，应该修改哪个资产？**

### A6｜Cortex Agent evaluations：要精读评分机制，也要精读它没有测到什么

**原文定位。** [Cortex Agent evaluations](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-evaluations) 将答案、逻辑一致性、工具选择和工具输入输出分别评价，可使用参考答案或无参考评价。工具选择按调用名称匹配，不检查顺序；其他相关项使用模型判分。数据集可表达预期输出及调用，评测配置还可固定 Agent 与评分版本。

**先纠正“我们是不是还没有分层评测”。** P4 的完整评测草案已有顶层结果、流程诊断、横向质量、首错归因和确定性比较建议。与你的设计重合很高。值得补的不是再写一套指标名，而是把一条执行真正关联到输入条件、工具参数、中间结果和最终报告。

**用你项目的失败来确定评分对象。**

| 真实问题／适用场景 | 应检查什么 | 只看最终回答为什么不够 |
| --- | --- | --- |
| 经分复杂请求漏掉某个维度条件，P1 | 澄清结果、交接参数、最终查询的条件对应关系 | 一个落在正常范围内的数值也可能答错人群 |
| 指标合法，但不适用于业务事件，P2 | 业务问题的适用判据与指标选择证据 | 工具参数合法、数字正确，也可能无法回答实际问题 |
| 报告把标准指标改成用户口语，P2 | 结果中的标准身份与报告字段是否一致 | 只检查语言流畅或数值相等会漏掉证据身份丢失 |
| 质检漏检或误报 | 样本在哪一级被排除、复核依据与人工标签 | 最终日报无法解释究竟是预筛、初审、脱敏还是复审造成 |
| 报告生成后未成功交付 | 产物保存、通知回执与业务消费状态 | 内容分数高不等于整项任务完成 |

**最需要记住的覆盖限制。** 当前文档的 `Known limitations` 说明：MCP 工具不在该评测执行中调用；代码执行的沙箱文件保存与后续依赖存在限制；工具评分尚不覆盖部分代码执行／Skill 调用；依赖会话属性的行权限场景也有限制。因此，你的文件聚合、外部工具和权限链必须补独立验收，不能用一个平台总分代表它们都测过了。

**对你的迁移建议。** 经分先把标准指标、时间、过滤、单位与结构化结果做可检查的记录；能由程序判断的先用程序，开放分析的证据与表达再交给 Judge。质检则分开记录“样本处理完成”“风险标签正确”“人工复核完成”，避免一个总成功率混合不同目标。对于固定的质检链，顺序检查必须由自己的 Workflow 验证补上。

**两个容易误读的地方。**

- 自洽只能发现部分矛盾，不能替代事实来源。对你那个新人案例，整条链可能一致地使用一个不适用指标。
- 固定评分配置有助于比较，不等于模型评分从此完全确定。还应留下一批人工裁决的已知好／坏案例，检查 Judge 是否失准。文章没有证明你现有 Judge 的可靠性。

**重点章节：** `Dataset format`、`Tool selection and execution metrics ground truth`、`System metric versions`、`Known limitations`。权限授予与建表命令暂时不用细背。读完应能回答：**分数上涨时，如何排除只是题目、判分器或执行环境改变了？**

### A7｜Claude Tag 部署：最新增量在服务与观测，分析 Skill 本身与你高度重复

**原文定位。** [Self-service data analytics in Slack](https://claude.com/blog/self-service-data-analytics-in-slack-how-anthropic-deploys-claude-tag-for-ad-hoc-questions) 是 A1 的部署续篇，2026-08-13 发布。它把 Skill 持续更新到会话运行环境，记录所用版本与数据质量信号，并说明共享服务账号的读取边界。文章中的账号方式不提供逐用户行级权限；标注请求用户用于审计，不等于在查询时执行用户权限。

**已有重合。** 你的经分已经有业务知识、分析方法、周报和主动提醒。文章列举“留存分析、漏斗分析、业务事件检索”不构成一整套你没有的能力。更值得看的是这些能力怎样跨入口持续保持一致。

**对经分的三个具体增量。**

1. **验证实际用到哪个版本。** 只证明知识库已更新还不够；同一题从聊天入口、定时周报和复用任务发起，分别记录其加载版本与数据时间。旧会话是否保留旧方法、缓存何时失效，需要明确规则。
2. **把“正常但错”的答案也纳入抽查。** 负反馈率只覆盖愿意指出问题的人。你已有满意度口述，但非专家可能给错误报告好评；应把反馈信号与抽样正确性检查分开。
3. **事件检索提供线索，不直接提供因果结论。** 如果某渠道下跌同时存在活动变更，至少还要核对时间、影响人群、机制和其他可能原因。业务事件与指标适用关系仍需要独立判定。

**对质检最有价值的是输入边界，而不是 Slack 接入。** 你的脱敏发生在外部复审前。可以明确哪些字段根本不应进入后续步骤，哪些文本需要脱敏后保留上下文，再检查提示词、错误日志和自动反馈材料是否遵循同一边界。这是现有脱敏链的边界核对，不是在本轮断言你已经出现泄露。

**不要直接照搬账号方案。** 内部群聊面向共同授权人群，与不同业务线、不同人员各有可见范围，是两种不同需求。OpenAI 的逐用户权限继承与此文的共享账号机制也不能混成同一个“企业最佳实践”。本报告没有检查你公司的权限实现，不给它贴上任一模式标签。

**重点章节：** `Refresh skills...`、`Permission the service account deliberately`、`Instrument every answer`。已有的漏斗、留存与报告功能列表可快速扫过。读完应能回答：**同一个 Agent 换入口后，知识版本和数据权限是否仍是你预期的？**

### A8｜Warp 自改进：你已经有自动调 Prompt，重点是“什么反馈有权改变系统”

**原文定位。** [How Warp builds self-improving agents on Claude](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude) 描述两个循环：执行任务的基础 Skill，以及定期读取人工反馈、提出小范围修改的改进 Skill；修改经 PR 审核后生效。它强调反馈质量、验证和人工把关。这里的“改进”主要发生在指令／知识文件，不是在训练模型权重。

**与你的质检重合度很高。** P6 已明确自动 Prompt 调整与自动评测，不应再把“收集错误样本，让模型改 Prompt”当成全新方向。也不应因看见该文，就把你的项目改称“自主演化 Agent”。更准确的比较对象是现有质量迭代流程。

| 已有基础 | 本文能启发的下一层问题 | 建议补充的记录 |
| --- | --- | --- |
| 人工确认与三人标注 | 一次业务反馈与共识标签冲突时听谁的 | 反馈来源、依据、裁决状态，P6、P7 |
| 错误案例推动 Prompt 调整 | 这是个例遗漏、规则含糊，还是业务标准真的改变 | 失败类型与修改理由 |
| 自动评测 | 修复本例是否造成其他类别或场景退化 | 同一配置下的旧／新逐例结果 |
| Workflow 生产调用 | 评测通过后谁决定发布、如何回到上一版 | 发布版本与审核结果；当前材料未证明全自动上线 |

**一个与你场景贴合的例子（完全虚构）。** 一段文本里，客服引用客户此前说过的辱骂，模型却把它判成客服主动辱骂。不要只把该句加入“不算辱骂”的列表。更有价值的反馈是：指出说话人、被引用者、前后语境、适用规则以及为什么当前证据不足。

候选改动可以加强对“引用”和“主动表达”的区分，但需要同时检查两种反例：一是确实在引用而不应判违规；二是以“我是在引用”为掩饰、实际上仍对客户表达攻击。若脱敏或 ASR 已丢掉关键角色信息，继续调判定 Prompt 可能修错层，应返回输入质量或人工复核路径。

**对经分也有用，但要限制反馈作用域。** “以后给我表格”可以进入个人偏好；“这个词在我们团队对应某标准维度值”需要核对适用范围；“从今天起收入分母改了”则是业务定义变更，不能凭一次聊天直接写进全局指标。P3 已有记忆能力，新价值是明确哪些改动需要从记忆进入有 Owner 的知识资产。

**需要审慎理解的建议。** 文中的“写原则”适合开放判断；质检的明确违规条件、禁止出域字段和人工确认步骤仍应具体。泛化原则不能替代可审核的业务标准。文章案例也未证明这种循环对你的 376 条样本或线上通话一定有增益。

**重点章节：** `The loop in action` 和末尾问题表，尤其是错误反馈、可验证性与整体效果。读完应能回答：**系统是在修复错误，还是正在把某个人的一次偏好变成所有人的规则？**

### A9｜Genie 测试与监测：评测器的判定规则也是你需要审查的代码逻辑

**原文定位。** [Test and monitor a Genie Agent](https://docs.databricks.com/aws/en/genie-agents/monitor) 区分反馈、知识修改和正式评分。Chat 模式比较 SQL／结果，Agent 模式使用模型评测器；benchmark 每题从新会话开始。反馈本身不会直接改变 Agent。文档还列出结果比较的空集、额外列及行数上限等具体规则。

**与你项目重合的部分。** 人工确认答案、积累线上问题、迭代 Prompt 和记录评测结果，已有 P1、P6 支撑。P4 也已建议精确数值采用确定性比较，因此“用程序比较结果”是已有设计重合，不能算本轮首次发现。

**最有价值的深读点，是检查通用产品规则是否适合自己的任务。**

| 官方评分细节 | 对你的项目有什么启发 |
| --- | --- |
| Chat 模式把空结果列为 Bad | 经分问“是否存在符合条件的异常”时，空集可能正是正确答案；质检某日无违规也可能正确。不能复制统一规则 |
| Chat 模式把额外列列为 Bad | 应由任务契约区分：无害辅助列、违反输出约束、泄露不该出现的字段，不能一律同等处理 |
| Chat 模式只比较前 5,000 行，排序变化可能影响评价 | 你已经解决模型预览与全量计算分离；评测端同样不能让截断结果冒充全量对账 |
| 每个 benchmark 是新会话 | 单轮分数不能覆盖你已有的连续追问、Task 记忆和分析中途补条件 |

**与 A2 的差异很值得面试时讲。** OpenAI 的文章允许部分不影响答案的额外列，Genie 当前文档采取更严格的规则。这说明“正确”不只是选一个评测模型，还取决于事先规定哪些差异可接受。它不是谁天然更先进，而是评价契约不同。

**可迁移到经分的做法。** 为结构化取数定义“指标身份＋时间＋过滤条件＋维度键＋单位＋值”的比较契约；顺序是否重要、空值与空集、额外列、浮点容差、数据回刷，各有明确规则。全量结果可在文件端按业务键比较，不能只核对模型展示的预览。对开放报告则另外评价证据与解释。

**可迁移到质检的做法。** 先区分任务完成率、全量扫描覆盖、分类召回、人工确认率和最终处置。尤其需要追踪前级筛选排除的样本，才能检查漏检；仅复核最后输出的候选，无法估计前级遗漏。这里是根据你的级联链路提出的评测建议，不是 Genie 文档公开的客服质检方案。

**重点章节：** `Benchmarks`、`Chat mode ratings`、`Agent mode ratings`、`Response feedback`。读完应能回答：**有没有一种业务上正确的结果，会被当前评测器判错？反过来呢？**

## 5. 按你的项目收敛成四个可选借鉴点

以下是建议，不是新增实施任务。本轮没有调用模型 API 或运行实验。

### 选项一：先补一条查询的条件与证据一致性

**最直接对应已知问题：** 复杂请求漏条件、报告指标名或单位变化。资料入口 A5、A6、A9；本地 P1、P2、P5。

用一个合成问题贯穿：用户分别查询两个指标，每个指标的过滤条件不同。记录“用户已确认条件 → 交接参数 → 实际执行参数 → 结果 → 报告”。代码可以检查结构化字段前后是否丢失或被改写；从自然语言识别业务意图、判定指标是否适用仍需要额外依据。

选择它的好处是能直接解释你项目中的真实残留问题。限制是：字段一致性无法证明最初理解就正确，也无法证明底层数据本身正确。

### 选项二：把知识维护变成一个可回归的变更

**对应问题：** 口径、维度、数据集与 Skill 漂移。资料入口 A1、A2、A7；本地 P1、P3。

选择一个指标，设计一次脱敏的口径变更：列出变化依据、Owner、受影响资产、需要保留的历史解释和回归案例。若需要自动化，可先让 AI 提议差异，由人确认标准，再更新正式资产。

选择它的好处是充分连接你的数仓与 Agent 经验。限制是：有依赖清单不代表所有语义依赖已经自动发现，自动同步也不能替代业务审核。

### 选项三：审查质检自动 Prompt 迭代的完整闭环

**对应问题：** 反馈是否可信、个例修好是否伤害其他类别。资料入口 A8、A6；本地 P6、P7。

用脱敏或合成案例记录一次“错误类型 → 人工裁决 → 候选修改 → 对照结果 → 发布决定”。区分输入噪声、角色误识别、规则理解、上下文不足、脱敏语义损失，避免所有失败都交给 Prompt 层修补。

选择它的好处是能深入讲已有自动优化能力，不需要把项目换成新框架。限制是：如果没有前级排除样本的标签，单靠最终候选的复核仍无法判断完整链路召回。

### 选项四：给评测器本身准备反例

**对应问题：** 评测高分与实际可用性之间的距离。资料入口 A6、A9、A2；本地 P4。

可先人工构造少量已知结果：正确空集、错误但范围正常的数值、单位错误、漏条件、额外无害列、错误标准指标、部分结果与完整结果、报告与数据冲突。检查评测器会不会接受错误答案或拒绝正确答案。

选择它的好处是成本低，且两个项目都适用。若以后需要付费模型实验，按仓库偏好先限定小样本并另行说明调用与费用，不把本报告变成默认全量运行授权。
