# 运行中消息队列与即时插入 v0.4

> 用户2026-09-12更正需求：运行中发送的消息主要是补充与调整，也可能询问进度或终止；发送默认排队，可点击“立即插入”。本版替代v0.3的“每条新消息先停止旧任务”交互。本版已实施；最终验收数据见下方关联说明。

## 交互

1. 空闲时发送：开始一个任务。
2. 执行中发送：写入SQLite消息队列，立刻显示文字和排队状态，原任务继续。
3. 点击某条“立即插入”：标为待插入；下一个模型/工具安全位置由主Agent读取。点击不意味着取消。
4. 主Agent可回复进度、吸收业务背景/报告要求并继续，或调整查询范围，或明确停止。
5. 未点击插入的消息在当前任务结束后依次作为后续输入运行。
6. 新消息与停止有独立入口；保留“停止”按钮供用户直接停止当前任务。

## 决策与执行

新增普通Python消息控制器，所有插入决策由一个主Agent模型步骤按顺序处理。五个分析分支共用消息控制器，只有一个线程在安全位置消费消息；其他线程可以完成已发出的调用，随后等待该决策，不能自行回复用户。

| 新消息 | 主Agent可选动作 | 是否重查 |
| --- | --- | --- |
| 现在做到哪了 | 回复已记录进度，继续 | 否 |
| 结论写短一点 | 更新后续模型上下文，继续 | 否 |
| 这周做了活动，分析时考虑一下 | 当作用户提供的待验证背景，继续分析 | 不默认重查 |
| 只看新商 / 日期改成本周 | 更新有效需求，重新走指标、维度、日期准入 | 只复用范围仍一致的查询证据 |
| 再加一个指标 | 扩展有效需求并重新分发 | 相同查询可复用，其余新增 |
| 不用了，停止 | 设置取消标记，结束后续执行 | 否 |
| 含糊或有歧义的调整 | 说明需要澄清的点，保留原明确任务 | 不擅自改变范围 |

补充沿用同一个LangGraph thread_id；查询调整以新的task_revision记录，不伪装成另一个会话。无需重建独立后台Agent系统，也不强行中断已发出的调用。

## 存储和边界

- inbox_messages：按conversation_id/message_id去重，记录target_run、文字、delivery（queue/steer）、状态、主Agent回复与决策；连续消息按入库顺序消费。
- 控制表独立于会话文件锁；接收和查看队列不等待整轮执行。
- 消息入队和提升状态保存在控制库。主图在本轮结束时把已应用消息与指令写入检查点；运行中的指令由本次Steering对象持有，消费、模型决策、范围调整及证据复用写入Trace。
- 纯背景和格式补充进入后续分析/回答上下文，已查证据保留；中途改变报告要求时重写摘要，不重复取数。
- 改变范围时在旧分支安全退出后更新主图并继续同一任务。只复用本次任务内、指标/期间/分组/筛选完全匹配的查询结果；派生引用明确记录原证据和新revision。
- 模型调用名额等待与消息处理分开，避免五个分支持有模型名额又等待主Agent决策而死锁。
- 重启保留未消费文字，标为中断；不自动重放付费执行。

“立即插入”表示下一个安全位置处理，通常是当前单次调用返回；不要求等完整分析结束，也不表示能修改已经发送给模型的请求。

## 验收目标

默认排队不影响原任务；插入格式补充不重查；进度消息提前得到回复；条件调整同任务继续；证据可复用且不串范围；明确停止；批量消息有序且不丢失；并行分支无消费竞争/名额死锁；刷新、幂等、结束时消息到达和重启可恢复文字；旧功能回归；少量真实Kimi与网页操作。

LangGraph状态更新和后续路由使用[官方update_state接口](https://reference.langchain.com/python/langgraph/pregel/main/Pregel/update_state)，并显式指定as_node。消息队列和运行控制是本实验实现，不宣称本地StateGraph自动提供这套交互，也不声称复刻了Codex内部实现。

## 实施入口

代码阅读顺序、验收结果与实际用量集中在[消息队列与即时插入说明](../实验/LangGraph经营分析面试复现/business_analysis_repro/playground/消息队列与即时插入说明.md)。

改动范围时先通过 `update_state(config, None, as_node=END)` 清除尚未执行的旧步骤，再更新需求并继续；仅设置 `as_node` 不会清掉其他待执行步骤。旧消息保留在State，`request_start`标记最新完整需求的起点，避免日期校验把“上周”和后来修改的“本周”同时当作有效约束。
