## 先把几个名词分开

| 名词 | 在本实验中的意思 | 会自动发给模型吗 |
| --- | --- | --- |
| user_id | 登录用户身份；本机试玩尚未做账号系统 | 不会，服务端用于授权 |
| conversation_id | 网页里一段连续聊天 | 不会，只是业务标识 |
| thread_id | 一项 LangGraph 任务的存档标识 | 不会，也不是操作系统线程 |
| request_id | 一次用户发送的请求，用于防重复执行 | 不会 |
| State | 程序运行中的工作数据，如需求、计划、结果、状态 | 不会；节点自己选择哪些字段组成模型消息 |
| checkpoint | State 及图执行位置的持久化存档 | 不会 |
| Trace | 实际发生的模型、工具、节点和路由事件 | 不会；供人排错和程序统计 |
| 模型调用 | 一次发往 Kimi 的推理请求 | 这是计费和 RPM 统计的基本单位 |

一轮用户对话可能包含很多次模型调用。例如“用户问一次 → 搜指标 → 看定义 → 提交需求 → 检查日期 → 写回答 → 检查回答”，用户只发了一条消息，模型可能已调用六七次。

## Q01：SQLite 在这里做什么，底层是什么？checkpoint 的 SQL 呢？

SQLite 是嵌入式关系型数据库，支持表、SQL、索引和事务。Python 加载数据库库文件即可工作，不像 MySQL 那样通常需要另起一个数据库服务。持久化数据库一般是本地文件；内存数据库则随连接生命周期结束而消失。

当前有两种完全不同的用途：

1. `checkpoints.sqlite`：保存 LangGraph 执行状态，澄清后可以恢复。
2. 取数函数中的内存 SQLite：装入模拟行，执行参数化查询。这是在模拟查业务数据。

本机实际存档表的简化结构如下，已对照现有数据库读取：

```sql
CREATE TABLE checkpoints (
  thread_id TEXT NOT NULL,
  checkpoint_ns TEXT NOT NULL DEFAULT '',
  checkpoint_id TEXT NOT NULL,
  parent_checkpoint_id TEXT,
  type TEXT,
  checkpoint BLOB,
  metadata BLOB,
  PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);

-- 示意：读取某个任务、某个命名空间的最新存档。
SELECT checkpoint_id, type, checkpoint, metadata
FROM checkpoints
WHERE thread_id = ? AND checkpoint_ns = ?
ORDER BY checkpoint_id DESC LIMIT 1;
```

另有 `writes` 表，按 checkpoint、task_id、idx 保存节点写出的通道值，辅助恢复。BLOB 是序列化后的二进制数据，不是每个 State 字段都拆成 SQL 列。业务代码应通过 saver 读取和恢复，不直接改这些表。

SQLite 每个数据库文件同一时刻只有一个写入者；短事务、低写入压力下足够方便。多人访问网页不自动意味着 SQLite 不可用，要看写入频率、文件归属和实例数量。[SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)

## Q02：会话数据到底保存在什么地方？

当前目录如下：

```text
.runs/playground/<conversation_id>/
  conversation.json                 网页消息、完成任务摘要、等待/运行标记
  tasks/<thread_id>/
    checkpoints.sqlite              可恢复的图状态和执行位置
    state.json                      最后 State 的可读导出
    trace.jsonl                     实际事件流水
    trace.html                      人可以打开的回放
    graph.mmd                       本次图结构
```

网页刷新先读取 `conversation.json`；用户补充一个正在等待的问题时，后端用 `thread_id` 找 checkpoint，再通过 `Command(resume=...)` 继续。`state.json` 便于查看，不是用它代替 saver 恢复整张图。

已完成后的新问题在当前实现中创建新任务，显式带入最近三个已完成任务的摘要。你看到聊天连续，并不代表一直有一个 Python 函数挂在那里等待。服务重启后文件还在，但执行中进程突然退出的自动接管、任务租约等还没有做。

## Q03：整个 Agent 有哪些存储？State 和上下文是什么关系？

State 可以理解为“这项工作的工作簿”。字段和 status 枚举由我们定义；模型可以提议其中一部分内容，如指标选择、分析步骤，程序负责验证并写入。执行状态、证据 ID、调用次数和权限等由代码控制。

| 数据 | 当前实现 | 后续数据量大时的常见去向 |
| --- | --- | --- |
| 聊天消息 | conversation.json | 关系型数据库 |
| 执行状态 | 内存 + SQLite checkpoint | 持久化 checkpointer，例如 PostgreSQL |
| 业务查询结果 | Python 结构、State 和本地导出 | 结果文件/对象存储 + 结果索引 |
| 指标与维度配置 | knowledge.json | 指标平台/配置服务 |
| 业务方法与说明 | 本轮加入小型本地知识库 | 文档存储 + 检索索引 |
| 运行事件、费用 | JSONL Trace，本轮加入统计投影 | 日志/观测存储 |
| 用户长期偏好 | 尚未实现 | 按用户隔离的业务存储 |
| 结果缓存、共享凭据 | 尚未实现完整服务 | 内存、Redis 或凭据服务，各自独立 |

换节点时，LangGraph 根据节点的输入定义传递 State。当前父节点接收父状态，`Send` 指标分支只接收自己的 job。模型能看到什么，仍取决于 `SystemMessage/HumanMessage/ToolMessage` 怎么构造；State 有的字段也可以不发给模型。Trace 不自动混入上下文。

LangGraph 的 checkpointer 保存 thread 内的状态；Store 保存应用定义的跨 thread 数据。两者是可选的不同接口，不意味着框架自动替你建立全部存储。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

## Q04：临时结果、Excel、大结果放在哪里？

改造前实验的查询结果是 Python 列表，并没有自动写 Excel。小结果进入 State，因而也可能重复出现在 checkpoint 和 Trace 中。Excel 是交付格式，不必作为分析的主存储。

数据大时建议：工具完整取回或导出结果 → 写 Parquet/CSV 或对象存储 → 返回结果引用、行数、字段、期间、汇总和少量预览。后续计算通过结果引用读全量数据，模型只读必要摘要。千万不要把“预览 200 行”当成“用 200 行代表全量”。

```python
result_ref = {
    "result_id": "result-123",
    "uri": "results/result-123.parquet",
    "row_count": 120000,
    "metric_id": "demo_metric_x",
    "period": ["2026-08-24", "2026-08-30"],
    "preview": [],
    "summary": {},
}
```

生产服务还要维护归属、访问权限、保留期限、文件完整性和下载入口。State 只留引用可显著降低存档与上下文开销。本轮仅做小型模拟分析，不引入大规模结果存储系统。

## Q05：需要 ES 吗？它是什么角色？

当前没有 Elasticsearch。它可用于文档全文检索、日志搜索等，但不会替代业务数据库、checkpoint 或结果文件。

我们这里只有几十个指标和少量方法文档，本地关键词/别名检索足够演示“搜索 → 读取知识 → 带着证据分析”。规模、分词需求、多用户权限过滤和相关性要求上来后，再决定是否需要 ES。引入 ES 本身不会修复错误的指标选择或缺失的业务定义。

## Q06：LangChain/LangGraph 自带向量数据库吗？

本地已安装的 LangChain 包中有 `InMemoryVectorStore`：可以存放文档向量并做相似度搜索，适合实验；它不是独立部署、自动高可用的数据库。LangGraph 的 `InMemoryStore` 也可以配置语义检索，但 Store、向量检索和 checkpoint 是不同概念。

语义检索通常需要 embedding 模型：先把文档变成向量，再把查询变成向量，计算相似度。embedding 可以本地运行，也可以调用付费接口。生产持久化、权限、索引重建和文档版本仍需自己设计。

本轮简易知识库先用词项/别名匹配，不调用 embedding，避免为几十条资料增加服务与费用。检索分数只表示匹配程度，不是“答案正确概率”。以后可加入语义召回，再按精确指标 ID 和维度约束核对。

## Q07：10 个会话怎样共用 TPM/RPM？

同一服务里使用同一账户/模型额度的调用会竞争供应商限额。不要把创建多个本地 thread 或多个 API Key 当作自动获得多份额度；具体范围要看平台账户规则。

- RPM：一分钟内发了多少次模型请求，不是用户发了多少条消息。
- TPM：一分钟内的 Token 用量/供应商计量预算。
- 并发：某个时刻有多少请求尚未结束。
- 本地 max_calls：我们允许一个任务最多请求几次模型。

四者互不等价。当前 5 个 semaphore 名额只限制同时执行数量，不是完整的按分钟限流器。[Kimi 限速概念](https://platform.kimi.com/docs/pricing/limits)

估算先用：`RPM ≈ 每分钟完成任务数 × 平均每任务模型请求数`；`TPM ≈ 每分钟完成任务数 × 平均每任务输入输出 Token`。缓存可以降低费用，不应自行从 TPM 中扣掉缓存量。平台可能根据预估输出等做准入，客户端实测 usage 不是供应商计量器的精确复刻。

实际请求遇到 429 时要有界退避，并观察 Retry-After；不能让十个会话立即一起重试。本轮实现数量级统计和估算，尚不承诺分布式精确限流。

## Q08：多用户多会话如何续聊？每个人要一直占一个线程吗？

`thread_id` 是业务存档 ID，不是操作系统线程。常见服务是：收到请求 → 验证 user_id 有权访问 conversation_id → 读取任务 → 调用图 → 保存结果 → 返回。没有新请求时，状态存在存储里，不必一直占一个工作线程。

当前是本机 `ThreadingHTTPServer`，HTTP 请求期间使用服务线程；未来可换异步 Web 服务或队列 worker。这种 Web 框架选择不会改变 State 的含义。

“续着跑”有两种情况：正在等待补充的任务恢复原图；已完成后的新问题可新建任务并带入摘要，也可设计成同一 thread 开新一轮。我们目前采用前一种任务分割。这样容易看每个任务花费，也减少旧状态干扰。

多人版至少需要 conversation 所属用户校验、同会话请求串行或冲突处理、幂等请求 ID、任务运行标记和重启恢复。当前没有账号系统，不是已经实现了用户权限隔离。

## Q09：30 人使用，10–15 个会话并行，需要多少服务器资源？

模型在外部 API 上运行，本机主要做编排、HTTP 等待、读取文件和小规模计算，不需要为 Kimi 配 GPU。仅小结果的学习服务，可把 2–4 vCPU、4–8 GB 内存作为粗略试跑起点；这是工程假设，未做生产容量验收，也不是采购承诺。

更有用的内存估算是：基础进程内存 + 同时活跃任务数 × 每任务结果和消息内存 + 计算临时副本。若每次查几百 MB 并用 pandas 多次复制，结果大小会成为主因。CPU 重计算需要单独控制并发，不能照搬外部模型请求的并发值。

“15 个会话打开”没有请求时几乎不产生模型用量；“15 个任务同时开始”会排队争抢 5 个模型名额。需要实测响应时间、排队时间、失败率、内存峰值，再评估扩容。下文容量表是需求估算，不是十五会话真实压测结果。

## Q10：怎样把固定函数换成有分析能力的 Agent？

改造前已经有模型驱动的指标检索循环，但取数和分析是 Python 函数；分析函数固定做两期比较。外层 Trace 标成“tool”只能说明调用被观测，不能证明由模型决定调用。

最小分析循环可以是：

```text
输入已确认指标、期间、条件
→ 读取专题 Skill 和业务知识
→ 工具查询本期/前期
→ 模型读取结果，提出待验证假设和下一步动作
→ 代码校验动作，查询合法维度/筛选并计算
→ 模型读取新结果，结束或进行有限补查
→ 写出事实、假设、证据、未解决问题
```

关键是后一步真正依赖前一步结果，而不是提前把所有查询写死。模型可以选错分析方向，假设也可以被推翻；程序仍要确保指标、维度、时间合法，数字来自工具，失败明确可见。这样才能区分“有分析过程”和“业务推论完全准确”。

本轮做小型、有限循环，不开放任意 Python/SQL，不接真实线上平台。按既有五个并发名额运行独立指标分支；同一个分支的证据依赖仍顺序执行。

## Q11：指标知识、业务知识、平台口径怎样配合？

建议分三层：

1. 指标目录：名称、别名、ID、摘要，帮助搜索和消歧。
2. 精确口径：用 ID 读取单位、聚合方式、支持维度、枚举、业务线、数据集或 SQL 模板。
3. 业务方法：专题适用范围、推荐指标、分析顺序、常见假设和限制。

搜索“渠道归因”是在找方法/专题；它本身不一定是一个指标。旧版本一直把它当指标名搜索，这是 16 次调用仍没结果的直接原因。本轮让理解节点能搜索业务知识，并在未指定日期/分析对象时提出具体问题，避免无限换词搜索。

`knowledge.json` 保留精确指标配置；新知识库保存短文档及来源、证据状态和推荐指标。业务资料不会变成新的系统指令。模拟指标 ID、平台 dataset_id、business_line_id、SQL 表名等继续保留 demo 标记，不冒充公司真实配置。

## Q12：同一节点/跨节点上下文和 KV Cache 怎么设计？

同一个工具循环保留 `assistant(tool_calls) → tool(result)`，否则模型不知道工具查到了什么。跨节点则明确传递需求、已澄清条件、指标定义、必要结果和来源；不需要把全部 Trace 原样塞进去。

缓存是重复输入的计算复用，不是长期记忆。命中缓存的文本仍要在请求里，仍占上下文窗口，也仍可能计费。稳定系统提示和工具定义放前面，动态问题、证据放后面有利于复用；不能为了缓存携带一堆无关旧历史。

现在的最终回答节点主要读压缩后的事实。加入分析后，还要带分析步骤、证据 ID、假设和限制，否则模型只能复述数字。一次任务的 Token 应把理解、分析、生成、复核和重试都算进去，不只算最终回复。

## Q13：工具失败、鉴权失败怎么办？

| 失败类型 | 合适处理 | 不应做什么 |
| --- | --- | --- |
| 参数非法、枚举不支持 | 返回结构化错误，有限修正或向用户澄清 | 原样无限重试、默默丢条件 |
| 超时、网络中断、部分 5xx | 对安全读取有限退避重试 | 所有分支一起立即重试 |
| 429 | 按平台提示等待并降低速率 | 只增线程或复制 Key |
| 明确 Token 失效 | 获取有效版本后最多补试一次安全读取 | 把密钥交给模型修复 |
| 权限不足 | 停止并说明缺权限 | 不停刷新 Token |
| 空结果 | 说明当前范围没有数据 | 当成 0 或当成网络故障 |
| 部分指标失败 | 保留成功证据，列失败项及原因 | 把整批说成成功 |

若查询接口先创建异步任务，提交超时后要查提交是否已被接受，或用幂等键；不能直接再创建同样的昂贵任务。Trace 应记录工具参数摘要、错误类别、重试次数与对应原调用，排除凭据明文。

当前已有有限网络重试和部分失败交付，尚未完整实现所有平台错误恢复。这里是分层设计说明，不冒充真实鉴权接入验收。

## Q14：共享、每 24 小时更新的查询 Token 怎么做？

先确定平台所谓 24 小时是有效期还是固定更新时间，以及是否支持程序刷新、新旧 Token 是否有重叠有效期。不要仅凭“每天刷新”假设它使用 OAuth refresh_token。

工具客户端统一调用 TokenProvider。Provider 保存当前 token、expires_at、版本；快到期时在锁内刷新，其他请求等待或使用仍有效版本。若一个旧请求失败，先比较自己使用的版本与当前版本，已经换过则复用新版本，不重复刷新。

```text
用户请求 → 服务端权限检查 → QueryClient
                         → TokenProvider.get_valid_token()
                         → 发往指标平台
                         → 分类错误、有限恢复 → 结果
```

多进程/多实例不能只靠某个 Python 进程里的锁，需要共享凭据存储和唯一刷新协调；不要让所有实例每天同时刷新。刷新失败有界停止，不能把过期凭据继续无限传播。

共享平台身份并不代表所有访问用户权限相同；服务端仍要检查每个人可查询哪些业务线和数据。Token 只在工具层注入，不进入 Prompt、State、checkpoint 或 Trace。标准 Bearer 错误区分 `invalid_token` 与 `insufficient_scope`，实际平台是否遵循需要对接确认。[RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)

本轮平台仍用模拟方法，不做凭据刷新服务。

## Q15：需要规划模块吗？计划究竟长什么样？

单指标查数不需要额外模型写长计划。现有 jobs 是查询参数清单，只解决拆分与分发，不等同于“先看 A，根据结果再看 B”的分析计划。

小型分析可以由专题 Skill 给一个短步骤表，分析 Agent 随工具结果更新 todo，无需单独部署一个 Planner：

```json
[
  {"step": "比较总体与前期", "status": "done", "evidence_ids": ["e1"]},
  {"step": "按一级渠道找变化大的分组", "status": "done", "evidence_ids": ["e2"]},
  {"step": "围绕异常渠道补查来源", "status": "pending", "depends_on": ["e2"]},
  {"step": "汇总解释及待核验项", "status": "pending"}
]
```

计划要允许 skip/failed，不能为了把清单全部打勾而查询不支持的维度。本轮先实现有限分析循环与可读步骤；没有必要先做任意 DAG、长期任务排程和复杂重规划系统。

## Q16：为什么看起来没有流式？哪些阶段流式？

上一次同时存在两个原因：浏览器旧脚本没有 SSE；“渠道归因”停在理解检索，没有进入正文生成。刷新解决前者，分析入口和检索早停解决后者。

当前正文由模型真实流式返回，经 Trace 事件和 SSE 到网页。搜索、取数、分析步骤通过进度事件显示，不把工具 JSON 当成正文。短澄清/错误提示可以一次展示，无需人为把一段已生成文字拆成字符冒充实时推理。

流式草稿仍可能被后续校验撤回，页面应标示草稿；失败保留已取得的表格。SSE 重连只补读事件，不重复发起付费任务。

## Q17：Token、RPM/TPM、一天 30 人的数量级怎么估算？

先统一统计单位：

- 一轮：一次用户输入到一次助手回复，包含澄清和失败。
- 一个任务：从首次提问到完成/失败，可能跨多轮澄清；查询和分析分别统计。
- 一段会话：多个任务的累计。上述范围相互包含，不相加。

改造前日志里曾出现：一次查询约 10,607 Token、一次固定比较分析约 14,248 Token；渠道归因失败却用掉 91,579 Token。前两项只是少量历史示例，最后一项应列为失败开销，不能用来冒充正常任务均值。新增分析后需要重新测量。

先给一组**假设场景**帮助建立数量级：每个查询任务 12,000 Token、6 次模型请求；每个简易分析任务 30,000 Token、10 次请求；任务构成查询 70%、分析 30%。则混合平均每任务 17,400 Token、7.2 次请求。下面不是实测容量：

| 活跃人数 30 人 | 每人每日任务数 | 每日任务数 | 每日 Token | 每日模型请求 |
| --- | ---: | ---: | ---: | ---: |
| 轻度 | 3 | 90 | 156.6 万 | 648 |
| 中度 | 10 | 300 | 522 万 | 2,160 |
| 重度 | 20 | 600 | 1,044 万 | 4,320 |

若 10 个任务在 1 分钟内完成，需求约 174,000 TPM、72 RPM；15 个约 261,000 TPM、108 RPM。若持续每 30 秒完成一批，折算每分钟翻倍；如果只是单次突发则不要把它当持续负载。五个执行名额可能拉长完成时间，所以这不是当前系统保证能达到的吞吐。

本轮增加按真实日志更新的统计页，查询/分析分别显示样本量、平均轮数、Token、请求数、失败和缓存；估算可修改并发数、完成周期、人数及任务量。历史版本与新版本分开，样本少明确显示，遗漏 usage 不算成零。

费用必须拆成未缓存输入、缓存输入、输出，不能把总 Token 全部乘同一个价。统计页按标明日期的价目估算；真实扣款、优惠、账户其他项目消耗仍以供应商账单为准。

## Q18：这轮明确做什么、不做什么？

| 范围 | 本轮决定 |
| --- | --- |
| 简易知识库 | 本地可读文档，关键词/别名检索，记录来源，无 embedding 费用 |
| 分析 Skill | 四个专题的简化方法；允许分析假设不成立，保留事实/假设区分 |
| 分析执行 | 真实模型读结果、选下一步有限补查；工具仍校验参数 |
| 用量 | 每轮、任务、会话及项目累计；查数/分析样本与容量假设分开 |
| Trace | 继续本地可读全链路，加分析步骤和用量入口 |
| LangSmith | 不启用、不依赖云端 Trace；依赖包中存在不等于向云端上传 |
| 指标平台 | 继续模拟；不自建线上平台、不对接公司生产接口 |
| 生产能力 | 不把本轮实验等同于账号权限、分布式限流、共享 Token 刷新、生产容量验收 |
