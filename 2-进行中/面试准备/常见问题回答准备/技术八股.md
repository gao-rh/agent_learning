## 一、先看这 10 题

### Q01｜事实表有哪些类型？【今天已问】

**短答：按业务事实的记录方式，经典的三类是事务事实表、周期快照事实表、累积快照事实表。先讲一行代表什么，再讲适用场景。**

| 类型 | 一行代表什么 | 示例 | 更新与使用特点 |
| --- | --- | --- | --- |
| 事务事实表 | 某一时刻发生的一次业务事件，粒度必须明确 | 一笔支付、一条订单明细、一次触达事件 | 通常随事件追加；用于发生量、金额、事件分析 |
| 周期快照事实表 | 某个固定周期内、某个对象或维度组合的状态／汇总 | 每店每天库存、账户日末余额 | 每期形成快照；即使没有业务事件，也可能需要保留零或空值记录 |
| 累积快照事实表 | 一个有明确阶段的业务流程实例 | 一条订单履约明细，记录下单、支付、发货、签收时间 | 随里程碑推进更新同一逻辑行；用于进度、转化、阶段耗时分析 |

**追问：累积快照是不是把金额不断累加？** 不是。这里的“累积”是逐步补全流程里程碑。一条订单可能一直占一行，只更新支付时间、签收时间等字段。

**追问：全量表、增量表、拉链表算哪类？** 这是不同分类轴。全量／增量描述同步和加工方式；拉链描述历史版本保存方式，常用于维度历史。不能把它们与三种事实表简单并列。

**加分边界：** 还有无事实度量的事实表，见 Q24。事务事实表也可能因源数据纠错而修正，不能说“永远不能更新”。参考：[事务事实](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/transaction-fact-table/)、[周期快照](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/periodic-snapshot-fact-table/)、[累积快照](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/accumulating-snapshot-fact-table/)。

### Q02｜MapReduce 的完整过程是什么？【今天已问】

**短答：把输入切成逻辑分片，Map 并行处理并输出键值对，再通过 Shuffle 把同一分组的数据送到对应 Reduce，最后聚合输出。**

```text
输入文件 → InputFormat 生成 InputSplit → RecordReader 读记录
        → Map 输出中间 KV
        → 分区 + 缓冲 + 排序／溢写 + 合并（可选 Combiner）
        → Reduce 拉取自己的分区数据，归并、分组
        → Reduce 处理每组 → 输出并提交结果
```

**展开：** Partitioner 决定记录去哪个 Reducer；排序比较器决定顺序；分组比较器决定哪些键在一次 Reduce 调用中被视为同组。默认通常按同一 key 分组。Map 中间结果通常落本地磁盘，失败后可重算；最终结果通常写 HDFS 等目标存储。

**易错：** Map-only 作业可以没有 Reduce。框架对 Reduce 输入按 key 排序，Reduce 输出不会自动再次排序；即使按输入顺序输出，也不自动等于最终全局有序。Shuffle 细节见 Q41；完整推演见[深度学习 1.0：MapReduce 全过程](../资料/2026-09-16-大模型训练数据岗位系统教学-从概念到面试.md#chapter-6)。参考：[Hadoop Reducer API](https://hadoop.apache.org/docs/r3.4.2/api/org/apache/hadoop/mapreduce/Reducer.html)。

### Q03｜Map 阶段会发生数据倾斜吗？【今天已问】

**短答：会。如果倾斜指任务负载不均，Map 阶段也会；常见的热点 key 汇聚则主要影响 Shuffle 之后的 Reduce。两种情况要区分。**

| Map 端可能变慢的原因 | 例子 | 应对方向 |
| --- | --- | --- |
| 输入分片不均，或大文件不可切分 | TextInputFormat 读一个很大的 gzip 文件，整个文件交给一个 Mapper | 上游拆分；换适合并行读取的格式／压缩；调整 InputFormat |
| 输入字节接近，但计算量不同 | 某些记录 JSON 特别复杂，UDF 很重，数组展开产生大量行 | 先看记录长度与展开倍数；优化逻辑；把重数据单独处理 |
| 小文件或自定义切片导致任务负载不均 | 有的任务读取大量小文件，有的只读少量 | 合并文件／合理合并输入分片 |

**怎么判断：** 比较 Map task 的输入字节、输入记录数、输出记录数、CPU、GC、溢写与耗时。如果输入和计算量相近，只是某台机器慢，也可能是硬件、IO 或资源争用，不能全部叫数据倾斜。

**不要再说：** “Map 是按块平均分配，所以绝不会倾斜。”分片并不保证计算成本均匀；InputSplit 也不等于物理 Block。gzip 边界见 [Hadoop Job Input](https://hadoop.apache.org/docs/stable/hadoop-mapreduce-client/hadoop-mapreduce-client-core/MapReduceTutorial.html#Job_Input)。

### Q04｜你会怎么做数仓设计建模？讲完整流程。【今天已问】

**短答：先明确业务过程和消费需求，再结合源数据确定粒度、维度、事实，设计分层和物理实现，最后通过验收、调度和治理让模型稳定服务下游。**

| 步骤 | 需要讲清楚的事 | 产物 |
| --- | --- | --- |
| 1. 需求与业务调研 | 谁用、做什么判断、核心指标、时效、查询方式 | 需求范围、口径、验收标准 |
| 2. 源系统调研 | 实体关系、业务主键、状态流转、数据量、更新／删除方式、历史质量 | 源表关系、字段映射与风险 |
| 3. 主题与业务过程 | 划域，明确下单、支付、退款等业务过程；找公共维度 | 业务过程清单、总线矩阵 |
| 4. 逻辑模型 | 一行代表什么；主键；维度；事实；事实表类型；关联与历史规则 | 逻辑模型、指标定义 |
| 5. 分层与复用 | ODS 接入，DWD 明细，DIM 维度，DWS 公共汇总，应用层按需消费 | 模型依赖、公共与专用边界 |
| 6. 物理与加工设计 | 分区、格式、增量／全量、去重、迟到、幂等、调度依赖与资源 | 表结构、加工 SQL、任务方案 |
| 7. 验收上线 | 唯一性、总量／金额对账、状态与时间边界、性能、历史回刷 | 对账结果、DQC、发布方案 |
| 8. 运行治理 | SLA、血缘、文档、权限、成本、变更与下线 | 可持续维护的数据服务 |

**可以直接这样回答：**“我会先确认业务过程和下游需求，再调研源系统的实体、主键、状态和更新方式。逻辑建模时先定粒度，再定维度和事实，选择合适的事实表类型。之后把稳定的明细和公共指标沉淀到公共层，再按消费场景设计汇总与应用模型。落地时一起设计分区、增量、重跑和质量规则，上线前完成对账与性能验收，运行后关注 SLA、复用和成本。”

**理论锚点：** Kimball 四步法是“选业务过程 → 声明粒度 → 确定维度 → 确定事实”；它是上面逻辑建模环节的核心，不等于工程全流程。参考：[Kimball 四步法](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/four-4-step-design-process/)。

### Q05｜公共数仓的核心职责是什么？

**短答：把多方需要的业务事实、维度和指标建设成口径统一、可复用、质量可靠、按时可用的数据资产，降低下游重复建设与理解数据的成本。**

| 职责 | 具体要交付什么 |
| --- | --- |
| 统一表达业务 | 公共业务过程、实体标识、维度、指标口径 |
| 沉淀可复用模型 | 明细事实、共享维度、合理的公共汇总，明确使用边界 |
| 保证可靠交付 | 对账、质量规则、时效承诺、问题响应、兼容变更 |
| 提供可消费的数据 | 给业务数仓、应用后端、报表、算法或分析系统提供数据 |
| 控制建设和使用成本 | 减少重复计算、无效任务与存储，改善开发效率 |

**边界：** 公共数仓不等于“负责做所有报表”，也不要求把每个个性化需求都放进公共层。公共口径由谁确认、下游个性逻辑由谁承担，需要明确。

**回答个人经历时：** 可以联系你已说明的“公共营销数据主要供下游业务数仓和平台后端使用”，不要套成你负责看板，也不要把场景险底层建模说成自己做的。

### Q06｜数仓为什么分层？ODS、DWD、DIM、DWS、ADS 各做什么？

**短答：用分层隔离源系统变化、沉淀公共逻辑、减少重复计算，并让问题可追踪。层数和命名是工程约定，不能脱离业务机械套用。**

| 层 | 主要职责 | 常见误区 |
| --- | --- | --- |
| ODS | 接入源数据，保留必要历史与追溯信息，做必要标准化 | 把复杂业务汇总都塞在这里 |
| DWD | 按业务过程形成统一粒度的明细事实，清洗、去重、状态标准化 | 简单复制源表却不统一业务含义 |
| DIM | 维护共享的描述属性、编码、层级及历史版本 | 把 DIM 误当 DWD 后必经的一道串行加工层 |
| DWS | 面向稳定主题、粒度和复用需求沉淀公共汇总 | 每来一个报表就新增一张几乎相同的表 |
| ADS／应用层 | 为具体产品、报表、接口等组织结果 | 宣称所有公司必须叫 ADS，所有查询必须经过它 |

**追问：能不能 ODS 直接到 ADS？** 小型临时需求可以权衡，但反复直连容易造成重复逻辑、口径分叉和耦合。发现稳定复用需求后应沉淀公共模型；也不能为分层而制造空转任务。

### Q07｜DWS 的汇总粒度怎么确定？

**短答：由可复用的分析需求、下钻要求、指标可聚合性和存储计算成本共同决定。先写清“一行代表什么”，再决定保留哪些维度和时间粒度。**

例如多方都看“门店每天各渠道的支付表现”，可考虑“日期 × 门店 × 渠道”，保留支付金额和支付订单数。需要活动级分析时，已有模型若没保留活动维度就不能凭空下钻，应选更细模型或回到明细。

**追问：维度越多越好吗？** 不是。维度组合会膨胀，稀疏表也可能很大；保留有用的联合粒度，避免枚举所有组合。不同粒度可以有不同模型，但要有明确的路由、口径和复用理由。

**关键坑：** 金额可按口径汇总；日去重人数不能直接相加成周人数；比例不能直接相加。见 Q19。

### Q08｜事实、维度、指标和粒度怎么区分？门店 ID 算什么？

**短答：粒度定义一行代表什么；维度提供观察业务的上下文；事实记录业务过程中的测量或事件；指标是在明确统计口径下计算的业务量。**

以“一条订单明细”为粒度：商品、门店、用户、日期是维度上下文；购买数量、明细金额是事实度量；按成功支付状态统计的支付金额是指标。

**门店 ID／用户 ID：** 可以是维度的键，在事实表中通常作为关联维表的外键；高基数不妨碍它用于筛选、分组。ID 用数字存储，也不会因此变成可求和的指标。

**表里不只有维度和指标：** 还有业务键、状态、事件时间、版本、批次、分区、审计等字段；事实表也不等于所有列都是度量。逻辑上有些状态／日期属于维度属性，物理字段分类则更细。

### Q09｜怎么判断数仓做得好不好？

**短答：同时看数据可信度、交付时效、公共复用、消费效果和资源成本；每个衡量指标必须说明统计范围、分母与时间窗口。**

| 方面 | 可用指标／证据 |
| --- | --- |
| 可信 | 对账通过率、质量事故数与影响、关键字段完整性和唯一性 |
| 时效 | 关键链路按时产出率、延迟分布、恢复时间、SLA 达成 |
| 复用 | 公共模型被多少有效下游复用、重复模型减少多少、口径一致性 |
| 效率 | 同类需求交付耗时、公共资产查找和理解成本 |
| 成本 | 在相同业务范围下的计算／存储成本、无效任务占比 |

**追问：表越少、复用率越高越好吗？** 都不是单目标。过度合并会增加耦合、冗余与更新成本；复用统计要排除空跑、测试和无效下游。

### Q10｜两个系统的数对不上，或者报表指标错了，怎么排查？

**短答：先固定同一业务口径和数据截止点，再沿源数据、加工、关联、聚合、展示逐层对账，找出首次产生差异的位置。**

1. **对齐定义：** 指标、状态、分母范围、去重键、单位、时区、时间字段、时间区间、退款／取消规则。
2. **对齐数据版本：** 是实时数还是 T+1？分区是否完成？迟到数据、回刷和维表版本是否一致？
3. **拆差异：** 从总量到日期、渠道、门店等维度，定位差异集中区，再取业务主键样本。
4. **查加工链路：** 缺记录／重复 → Join 膨胀／漏匹配 → 过滤条件 → 聚合公式 → 展示换算。
5. **修复验证：** 修正后重算受影响范围，核对下游结果，补质量规则或回归用例。

**边界：** 数据和文档冲突时要回到业务约定、源系统和完整血缘核实，不能仅以某张表当前有数就判定业务口径正确；扣减也可能已经在上游做过。

## 二、建模与指标

### Q11｜维度建模、范式建模、星形和雪花模型是什么关系？

**短答：范式建模侧重实体关系和减少冗余；维度建模围绕业务过程组织事实与维度，方便分析。星形与雪花是维度模型的不同组织方式。**

| 方式 | 特征 | 取舍 |
| --- | --- | --- |
| 3NF 范式模型 | 按实体与依赖关系拆表，减少传递依赖 | 一致性、维护性较好；分析常要更多关联 |
| 星形模型 | 事实表连接相对扁平的维度表 | 容易理解、分析关联少；维度属性有一定冗余 |
| 雪花模型 | 维度按层级进一步拆分，如商品→品类→大类 | 减少部分冗余；增加关联和使用复杂度 |

Kimball 强调用一致性维度整合按业务过程构建的维度模型；Inmon 的经典路线强调企业级集成数仓，再支持下游集市。实际架构可以混合，不能把“3NF 永远慢、星形永远快”当结论。

**追问：1NF／2NF／3NF？** 1NF 要求关系属性符合原子取值等基本约束；2NF 在 1NF 上消除非主属性对候选键的部分依赖；3NF 进一步约束非主属性的传递依赖。口述可举“订单明细含复合键，却重复放只依赖订单号的订单信息”的例子，说明为什么会有冗余和更新异常。

### Q12｜概念模型、逻辑模型、物理模型分别做什么？

**短答：概念层讲有哪些业务实体和关系；逻辑层讲事实、维度、粒度、键和规则；物理层讲怎么在具体引擎上存和算。**

例子：概念层是“用户下订单、订单含商品、订单发生退款”；逻辑层确定订单明细和退款明细两个事实的粒度及关联；物理层决定 Hive 表字段类型、日期分区、ORC／Parquet、增量任务和调度。

**易错：** 只说建表字段和分区，是物理设计片段，不是完整建模。

### Q13｜总线矩阵和一致性维度有什么用？

**短答：总线矩阵用“业务过程 × 共享维度”组织规划，识别哪些过程可以使用一致的用户、商品、门店和日期维度。**

一致性不只是同名：编码含义、层级、属性定义、历史处理要兼容。这样支付和退款可以分别按共同维度汇总后对照，避免各域对同一门店、渠道各算一套。公共维度允许有适合特定业务的扩展属性，但公共部分需统一。

参考：[Kimball 一致性维度](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/conformed-dimension/)。

### Q14｜业务主键、代理键和复合键怎么用？

**短答：业务主键用于标识源业务对象；代理键是仓库分配的标识，便于隔离源系统变化和表示历史版本；复合键由多个字段共同确定唯一性。**

例如订单明细可能由“订单 ID＋明细行号”唯一确定，单用订单 ID 会误判重复。多系统接入时，源系统＋业务 ID 才可能全局唯一。SCD2 中同一个用户有多个历史版本，通常每个版本对应不同代理键。

**注意：** 具体引擎中的 `PRIMARY KEY` 声明可能只是约束信息，并不总会自动校验或去重；需要确认引擎语义。

### Q15｜缓慢变化维 SCD 有哪些处理方式？

**短答：常见是 Type 1 覆盖、Type 2 新增历史版本、Type 3 在列里保留有限的前后值，取决于是否需要按历史状态分析。**

| 方式 | 示例：商户从 A 城迁到 B 城 | 适用需求 |
| --- | --- | --- |
| Type 1 | 把城市覆盖为 B | 只关心最新信息，或修正错误 |
| Type 2 | 关闭 A 版本，新增 B 版本及有效期 | 按交易发生时的城市回溯 |
| Type 3 | 当前城市 B、上一城市 A | 保留有限次数的变化信息 |

**关键追问：** 历史订单到底按“当时城市”还是“现在城市”统计？这是业务口径，不是技术默认。事实表存历史维度版本键，或按事件时间关联有效区间，都需明确规则。参考：[Kimball Type 2](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-2/)。

### Q16｜拉链表怎么维护，怎么查某一天的状态？

**短答：每次属性变更时结束旧版本、生成新版本，通过生效和失效时间表示记录有效区间。建议使用左闭右开区间，避免边界同时命中两条。**

```sql
-- 逻辑示例：查看某时点 t 有效的维度版本
WHERE valid_from <= t AND t < valid_to
```

维护顺序：识别新增／变更／删除 → 关闭发生变化的旧版本 → 写入新版本 → 保留未变部分 → 检查同一业务键有效期无重叠、当前版本唯一。

**追问：一天内变两次怎么办？** 如果要保留日内历史，用时间戳或源版本序号；日级拉链只能表达所约定的日级状态。删除也要明确为失效或墓碑，不能让“源里没出现”自动等于删除。

### Q17｜事实先到、维度后到，或者历史维度更正了，怎么办？

**短答：先保留事实和可追溯业务键，必要时关联“未知维度”或推断成员，维度到齐后补全；历史修正按业务生效时间重建受影响的版本与关联。**

不能因为维表暂时缺一行，就用 Inner Join 悄悄丢掉事实。记录未匹配率与补全状态；维度补全后判断是否需要回刷历史汇总。还要区分业务真实变化与原先录错后的纠正，这两者不一定采用同一种历史口径。

### Q18｜退化维、角色维、杂项维、多值维是什么？

| 名称 | 短答与例子 |
| --- | --- |
| 退化维 | 订单号等仍有分组和追溯意义，但没有独立维表属性，因此保留在事实表中 |
| 角色维 | 同一日期维表按下单日期、支付日期、签收日期扮演不同角色 |
| 杂项维 | 将若干低基数标识／状态组合成维度；不是把所有无处安放的字段随便堆一起 |
| 多值维／桥接表 | 一个订单可能关联多个标签、多个参与人；用关联表表达，并明确计数和分摊规则 |

**易错：** 桥接表不是加上就解决重复汇总，跨成员求和仍可能重复；要确定按参与次数、去重对象，还是按权重分摊。参考：[Kimball 维度建模技术目录](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/)。

### Q19｜可加、半可加、不可加指标怎么区分？【重点】

| 类型 | 能否直接求和 | 典型例子 |
| --- | --- | --- |
| 可加 | 在该模型允许的维度上可以加 | 同币种、同口径且不重复的订单明细金额 |
| 半可加 | 某些维度可加，另一些不可加 | 日末余额可跨账户求和，不能跨日期求和当作余额 |
| 不可加 | 原值通常不能直接求和 | 比率、均价、去重人数 |

**比例的正确汇总：** 如果分子分母在目标维度上可加，先各自求和再相除。例如两天分别 1/10、9/90，总体是 10/100＝10%，不能把比例相加。均价通常用总金额／总数量；平均分组均价也未必正确。

**更难的边界：** 两天去重商户数分别为 10 和 20，不能断定周去重为 30；有重叠时必须集合去重。比率的分子／分母若本身是去重人数，同样不能简单按日相加。参考：[Kimball 可加性](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/additive-semi-additive-non-additive-fact/)。

### Q20｜一个指标的口径要定义哪些内容？原子、派生、复合怎么说？

**短答：至少明确业务含义、统计对象、计算方式、过滤范围、时间口径、去重键、维度与粒度、单位，以及来源和责任人。**

一种常用约定：原子指标表达基础测量，例如支付金额；派生指标加统计周期与业务限定，例如最近 7 天某渠道支付金额；复合指标通过多个指标运算，例如支付转化率。各平台命名略有差异，先说明所采用的约定。

**追问：同名指标口径冲突怎么办？** 找负责人和实际使用场景确认，明确版本／适用范围，给出迁移与回刷方案，不能只改展示名就认为解决。

### Q21｜“金额大于 100”会让指标变成维度吗？

**短答：不会因为参与过滤就自动变维度，要看统计阶段和使用角色。** 明细金额大于 100 是行级过滤；按商户汇总后总金额大于 100 是聚合结果过滤，通常用 `HAVING` 或外层查询。

如果先把金额加工成“0–100、100–500、500 以上”的分段标签，并按标签分组，得到的是用于分析的派生维度属性。不要用“能不能 Group By”作为唯一判断标准。

### Q22｜两张事实表直接 Join 为什么容易错？怎么避免？

**短答：关联粒度不匹配会造成多对多放大。先弄清两边主键与关系，再决定先汇总、按明细匹配、半连接或分别计算。**

例如某订单有 2 条商品明细、3 条退款明细，两表只按订单 ID Join 会得到 6 行，金额被重复累计。可以先分别聚合到订单粒度再关联；若要商品层退款，必须有可验证的明细映射，不能直接分摊。

**验收：** 比较 Join 前后业务主键数、行数、金额、匹配率；检查维表当前版本是否唯一。`DISTINCT` 不能修复错误业务关联，只可能暂时掩盖症状。

### Q23｜宽表有什么优缺点？何时拆，何时合？

**短答：宽表把常用属性和度量提前组织好，减少消费端关联；代价是冗余、变更耦合、写入成本以及潜在的粒度混乱。**

适合相同粒度、稳定复用、经常联合查询的字段。业务过程、更新频率、权限边界差异很大，或列太多而多数不用时考虑拆分。列式存储能减少读取无关列的成本，但不能消除写放大、血缘复杂和治理成本。

**不说：**“为了查询快，把所有表拼成一张表。”先确认粒度，不能把订单头金额复制到每条明细后直接求和。

### Q24｜事实表必须有数值指标吗？

**短答：不必须。无事实度量的事实表用维度组合记录事件或覆盖关系，分析时可以计数。**

例如“某学生某天参加某课程”记录一次出勤；“某商品某天参与某促销”记录可参与范围。把覆盖集合与真实发生集合对比，可以分析“应发生但未发生”的情况。数值列不是判断事实表的必要条件。

参考：[Kimball 无事实度量事实表](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/factless-fact-table/)。

### Q25｜如何用一个例子讲清业务过程与事实表的选择？

**短答：同一业务可用多个模型从不同角度表达，不应强行只选一种事实表。** 以下为触达业务教学示例，不代表本人已实施的表结构。

| 需求 | 模型选择 | 一行的粒度 |
| --- | --- | --- |
| 每次发送／回执发生了什么 | 事务事实表 | 一次具有唯一事件 ID 的发送或回执事件 |
| 每天各渠道发送、成功、点击多少 | 按约定构建日汇总／周期快照 | 日期＋渠道＋必要业务维度 |
| 一条触达从提交到送达经历多久 | 累积快照 | 一个触达实例，逐步补全里程碑 |

**必须先问：** 重试算一次发送还是新的尝试？成功按提交成功还是真实送达？点击是否多次？用哪个时间归属日期？这些决定粒度、去重和口径。

## 三、数据加工、质量与治理

### Q26｜全量、增量、快照、拉链怎么选择？

**短答：看数据规模、更新方式、历史追溯和恢复要求。** 小表全量简单但成本随规模增长；增量成本低但必须正确识别更新、删除、迟到和断点；快照方便看周期状态但历史空间大；拉链只保存变化版本，节省部分历史存储但加工更复杂。

不要用“今天分区”直接替代“今天变化的数据”：一条上月订单今天退款，也可能需要更新上月业务分区或新增今天退款事实。

### Q27｜CDC 是什么？怎么保证全量和增量衔接？

**短答：CDC 捕获插入、更新、删除等变化，常见方式是读取数据库变更日志。接入时需要协调初始快照与日志位点，保证边界处不丢不重。**

重点核实：快照一致性、日志起始位点、断点保存、源日志保留期、主键、事务边界和变更顺序。不能简单“先 SELECT 全表，再从当前时间读日志”，中间发生的变化可能漏掉；应使用连接器提供的快照与位点协议。

### Q28｜任务幂等怎么做？重跑如何不重复？

**短答：同一逻辑批次重复执行，结果应与成功执行一次一致。按任务类型采用分区替换、业务键 Upsert、事件去重或事务提交。**

| 方式 | 关键条件 |
| --- | --- |
| 重算并覆盖目标分区 | 输入截止点和计算逻辑确定；最好临时产出、验收后原子发布 |
| 按主键合并更新 | 有唯一业务键、版本顺序和删除语义 |
| 增量追加 | 用事件 ID／批次记录去重，不能每重试一次就再追加一次 |

**易错：** 幂等不等于把 `INSERT INTO` 改成 `INSERT OVERWRITE` 就结束了；还要控制并发写、动态分区范围、失败半成品和外部副作用。源数据变了，重跑输出变化不一定违反幂等，要明确输入版本。

### Q29｜补数、回刷和任务重跑如何安全执行？

**短答：先确认影响区间和依赖图，固定代码与输入口径，再从上游到下游分批重算，验收后发布。**

先问补的是漏数据还是改口径；核对源历史是否还在、维度取历史还是当前。避免与正常调度同时覆盖同一分区；评估下游重复消费和实时链路冲突。记录回刷批次、输入版本、目标范围、对账结果与失败恢复点。

### Q30｜上游改字段、改枚举、改口径，怎么处理？

**短答：通过数据契约和血缘确定影响，区分兼容变更与破坏性变更，验证后分阶段发布。**

新增可空字段通常较易兼容；改类型、重命名、重定义状态、改变主键或历史口径风险更高。做兼容映射／新版本并行、通知下游、对账和回刷；保留旧版退出时间。不能假设“表结构没变，业务含义就没变”。

### Q31｜离线数据迟到、订单后来退款，历史结果怎么办？

**短答：区分事件发生时间、入库时间和统计归属时间，明确初版数据与最终数据的截止规则。**

迟到可采用滚动回算受影响日期、增量更正或专门补数。退款可能按退款发生日统计，也可能用于重算原交易期净收入，必须按业务口径处理。不能无限回扫全历史；用变更键定位受影响分区，并建立对账窗口。

### Q32｜数据质量要检查哪些维度？

**短答：完整性、唯一性、有效性、一致性、及时性，以及可验证的业务准确性。技术规则和业务对账结合。**

| 类别 | 示例 |
| --- | --- |
| 完整性／唯一性 | 分区到齐；关键字段非空；订单明细主键唯一 |
| 有效性 | 状态枚举合法；时间顺序合理；业务约束成立 |
| 一致性 | 源与目标按主键、金额对账；跨表关系满足预期 |
| 及时性 | 截止时间前产出；延迟与新鲜度满足要求 |
| 波动监测 | 分渠道订单量异常；应考虑周末、节假日和业务活动 |

**追问：固定阈值可靠吗？** 适合明确业务约束；波动指标要结合历史基线、分组和告警误报。影响核心数据的强规则可阻断发布，弱规则可告警，责任人和恢复动作要明确。

### Q33｜SLA 怎么设计？凌晨任务没产出怎么办？

**短答：从业务消费截止时间反推链路时间预算，识别关键路径，监控上游就绪、执行耗时、数据新鲜度和最终可用性。**

排查时先区分等待依赖、排队、真正执行慢、写出慢和质量阻断。优先恢复核心消费：合理重试、补跑、资源调整，必要时使用明确标识的上一版本；不能静默把旧数据当新数据。恢复后对账、追根因，补容量或依赖保障。

### Q34｜元数据、血缘、数据目录分别是什么？

**短答：元数据描述数据；血缘描述数据从哪里来、经过什么加工、影响哪里；数据目录让人找到、理解并申请使用数据资产。**

元数据包括表结构、粒度、业务含义、负责人、权限、更新频率和运行统计。血缘可分表级与字段级，用于影响分析、排障、回刷和下线；动态 SQL、UDF、外部脚本可能让自动血缘不完整，需要补充运行证据。

### Q35｜数仓怎么降本？怎么证明优化有效？

**短答：先找主要成本来源，再做减少无效工作、提高复用、改善执行和存储生命周期，最后在相同业务与质量要求下比较收益。**

方向：下线无有效消费的任务、合并重复模型、减少重复扫描、增量替代不必要全量、合理分区与文件、压缩、过期清理和冷热分层。

**下线不能只看最近没人查：** 还要查任务依赖、接口调用、月季年任务、审计留存和责任人确认。衡量时同时看计算时长／资源量、存储、交付 SLA 和维护成本；变快不一定变便宜。

### Q36｜公共数据的权限与敏感信息怎么治理？

**短答：按数据分类分级、最小授权和使用场景设置表／列／行权限，必要时脱敏，保留访问审计与到期回收。**

控制还要覆盖导出文件、缓存、临时表和下游结果，不能只给原表加权限。业务标识做哈希不必然等于匿名化；相同标识仍可能被关联识别。面试先讲具体数据流上的权限边界，不堆安全术语。

## 四、Hadoop、MapReduce 与 Hive

### Q37｜HDFS 的架构是什么？NameNode 和 DataNode 各做什么？

**短答：NameNode 管文件命名空间、权限及文件到 Block 的映射等元数据；DataNode 保存实际数据块，通过心跳和块报告让系统掌握存活与副本状态。**

文件通常拆成多个 Block，以副本或特定纠删码策略获得容错能力。客户端拿到位置后直接读写 DataNode，数据内容不经 NameNode 中转。HDFS 更适合大文件的流式高吞吐访问，不适合把海量小文件当成关系数据库行来随机更新。参考：[HDFS 架构](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)。

### Q38｜HDFS 读写过程和 NameNode 高可用怎么讲？

**读：** 客户端向 NameNode 获取块位置，优先读合适的近端副本，校验失败或节点不可用时换副本。

**写：** 先由 NameNode 检查并分配目标节点；客户端把数据包送入 DataNode 复制流水线，逐级复制、确认。失败时重建流水线并按协议恢复。

**HA：** Active／Standby NameNode 通过共享编辑日志等机制保持可恢复状态，故障切换要防止双主。Secondary NameNode 主要做元数据检查点合并，**不是**直接等价于热备 NameNode。参考：[HDFS 架构](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)。

### Q39｜Block、InputSplit 和文件分区是什么区别？

**短答：Block 是存储划分；InputSplit 是一个 Map task 的逻辑输入范围；Hive 日期分区是表数据按分区列组织的方式。它们不是同一概念。**

Split 可与 Block 大小相关，但还受文件格式、压缩、InputFormat 和配置影响；一个 Split 可能跨块，也可能合并多个小文件。行跨 Split 边界时由 RecordReader 处理记录边界，不是随意截断一行。

参考：[Hadoop FileInputFormat](https://hadoop.apache.org/docs/stable/api/org/apache/hadoop/mapreduce/lib/input/FileInputFormat.html)。

### Q40｜Map、Reduce 的并行度怎么确定？

**短答：Map task 数通常由 InputSplit 数决定；Reduce task 数由作业配置或 SQL 引擎估算决定。实际同时跑多少还取决于资源。**

Map 太多会有调度开销，太少又可能并行不足；Reduce 太少容易单任务过大，太多增加 Shuffle 与小文件。不能只用“输入大小除以 128MB”作为通用精确答案。看格式、切片配置、实际执行计划和资源，而不是背固定值。

参考：[Hadoop Mapper](https://hadoop.apache.org/docs/stable/api/org/apache/hadoop/mapreduce/Mapper.html)。

### Q41｜Shuffle 具体做了什么？为什么贵？【重点】

**短答：Shuffle 让需要一起计算的数据重新分布到同一任务，包含分区、序列化、缓冲／溢写、网络传输、排序／归并等成本。**

在经典 MapReduce 中，Map 输出按目标分区组织，缓冲达到条件后排序溢写，多个文件再合并；Reducer 拉取来自各 Mapper 的自身分区，归并分组后计算。

**为什么贵：** 跨节点网络、磁盘 IO、排序 CPU、序列化和内存压力都可能成为瓶颈。优化通常是减少进入 Shuffle 的数据量、提前可合并聚合、避免无用列、选合适 Join、处理热点与分区大小。

**追问：同 key 一定一组吗？** 默认比较规则下通常如此；若自定义分组比较器，分组可基于 key 的一部分。分区规则必须保证同一逻辑组不会被分到不同 Reducer。参考：[Hadoop Reducer 的 Shuffle、排序和分组](https://hadoop.apache.org/docs/stable/api/org/apache/hadoop/mapreduce/Reducer.html)。

### Q42｜Combiner 有什么用？平均值能用吗？

**短答：Combiner 做 Map 端局部合并以减少网络传输，但可能执行零次、一次或多次，不能依赖其执行来保证正确性。**

合并运算必须能反复分组后仍保持最终结果，例如 SUM、MIN、MAX。平均值不能直接把局部均值再平均，但可传递 `(sum, count)`，合并后由最终 Reduce 相除。不能在 Combiner 中执行依赖全局数据或不可重复的副作用。

### Q43｜YARN 中 RM、NM、AM、Container 是什么？

**短答：ResourceManager 管集群资源调度；NodeManager 管节点资源与容器；ApplicationMaster 协调一个应用的执行并申请资源；Container 是一份分配给任务的运行资源。**

任务“很久没跑起来”可能是队列和资源等待，而不是 SQL 算得慢。先区分排队时间与执行时间，再讨论扩资源、队列或计算优化。

参考：[YARN 架构](https://hadoop.apache.org/docs/stable/hadoop-yarn/hadoop-yarn-site/YARN.html)。

### Q44｜Hive 是什么？一条 SQL 如何执行？

**短答：Hive 提供基于表和 SQL 的数据仓库能力，将 SQL 解析、语义分析和优化为可执行计划，交给所配置的执行引擎处理数据。Metastore 保存表结构、分区等元数据。**

流程可讲：SQL → 解析与语义校验 → 逻辑优化 → 物理计划 → 任务执行 → 结果。具体执行引擎取决于版本和平台；不能说“Hive 必然等于 MapReduce”，也不能把 Metastore 当成保存所有业务数据的数据库。

### Q45｜Hive 内部表与外部表有什么区别？

**短答：核心区别是数据生命周期由谁管理。Managed 表由 Hive 管理；External 表主要登记外部数据的位置和元数据。**

通常删除 Managed 表会删除其数据；External 表通常保留外部数据。但实际行为会受版本、表格式、PURGE／外部表清理属性和平台封装影响，不能保证“外部表 Drop 永远不删文件”。生产操作必须看表属性和存储管理规则。

参考：[Hive 表生命周期](https://hive.apache.org/docs/latest/language/managed-vs--external-tables/)；外部表清理的配置边界可核对 [HiveConf](https://apache.googlesource.com/hive/+/refs/heads/master/common/src/java/org/apache/hadoop/hive/conf/HiveConf.java)。

### Q46｜分区和分桶有什么区别？动态分区呢？

**短答：分区按列值划分数据，主要帮助裁剪扫描范围与生命周期管理；分桶按规则把数据划入固定数量的桶，可能用于抽样或特定关联优化。**

分区适合常用过滤和数据分布，例如日期；高基数用户 ID 直接分区易导致目录与小文件爆炸。动态分区是在写入时由记录的分区列值决定目标分区，需控制产生的分区数与覆盖范围。分桶不自动保证均匀，也不自动让所有 Join 免 Shuffle。

### Q47｜ORC、Parquet、行存、列存、压缩怎么回答？

**短答：行存适合一次读写整行；列存适合分析中扫描少数列、批量压缩和向量化。ORC、Parquet 都是常用列式格式。**

文件中的统计信息可帮助跳过无关数据块，实际效果取决于数据排序、谓词和引擎支持。压缩算法在压缩率与 CPU 开销间取舍；“文件被压缩”不等于不可并行切分，是否可切分要看**格式与压缩组合**。不要把文本 gzip 的结论套到所有列式文件。

### Q48｜ORDER BY、SORT BY、DISTRIBUTE BY、CLUSTER BY 区别？

| Hive 语法 | 作用 |
| --- | --- |
| ORDER BY | 保证最终全局排序，经典 MR 执行常形成单 Reducer 瓶颈 |
| SORT BY | 保证各分区内排序，不保证分区之间有序 |
| DISTRIBUTE BY | 按指定表达式分发记录，本身不保证排序 |
| CLUSTER BY | 按同一组表达式分发并在分区内排序，可理解为相应 DISTRIBUTE BY＋SORT BY |

**边界：** 表定义里的聚簇／分桶和查询里的 CLUSTER BY 要分清；其他引擎同名语法可能不同。参考：[Hive SortBy](https://hive.apache.org/docs/latest/language/languagemanual-sortby/)。

### Q49｜大表 Join 小表、大表 Join 大表怎么优化？

**短答：先保证关联语义，再过滤行、裁剪列、检查唯一性和统计信息，最后选合适的物理 Join。**

小表足够小且 Join 类型允许时，可广播到各执行端，减少大表重分布；要看展开后的内存，不只看压缩文件大小。两边都大，常用重分布后排序合并等策略，重点控制 Shuffle 量、倾斜和分区大小。稳定布局及引擎支持满足条件时，可利用分桶／共置减少网络。

只判断是否存在关联对象时可用 SEMI JOIN／EXISTS，避免带出右表多行；先聚合再 Join 需证明不会改变所需粒度。参考：[Hive Joins](https://hive.apache.org/docs/latest/language/languagemanual-joins/)。

### Q50｜数据倾斜如何定位和处理？【重点】

**短答：先用任务级统计证明负载不均，再找到导致不均的数据键或输入，按聚合／关联／读取场景分别处理。**

| 现象／成因 | 处理思路 | 不能忽略的边界 |
| --- | --- | --- |
| 少数 key 特别热 | 热点单独计算；聚合可加盐做两阶段汇总 | AVG 需带 sum/count，去重需保持集合语义 |
| Join 热 key 对应大量行 | 广播可广播的一侧；或热 key 分拆、选择性复制另一侧 | 两边随意随机加盐会漏匹配；多对多业务输出本来就可能巨大 |
| NULL／默认值集中 | 按业务语义单独处理，避免不必要重分布 | 不能为了性能直接丢掉应保留的记录 |
| 分区／文件负载不均 | 合理切分、合并、调整并行度 | 不可切分输入不能仅靠加 Reducer 修复 |

**判断依据：** Task 耗时、输入／Shuffle 字节、记录数、spill 和 key 频次分布。只有一个任务慢但数据量不大，也可能是 GC、磁盘、节点或外部服务问题。

**追问：增加 Reducer 能解决热点 key 吗？** 通常不能，单个 key 仍会去同一个逻辑分区；增加并行度主要帮助普通分区过大，热点需改变计算或分发方式。

### Q51｜为什么小文件有问题？怎么治理？

**短答：小文件增加元数据、列目录、打开文件和调度开销，实际计算时间可能远小于这些固定成本。**

从产生端控制分区粒度、输出并行度、批次和写入缓冲；在存储侧定期合并，湖表用相应 compaction；读取侧可合并小文件为合理输入任务。不能为了只输出一个文件就盲目 `coalesce(1)`，那可能把写入变成单任务瓶颈。

## 五、Spark 核心八股与性能

### Q52｜Spark 为什么通常比 MapReduce 快？

**短答：Spark 可以把多步计算组成 DAG，在同一应用里流水执行、复用缓存和中间结果，并通过 SQL 优化、代码生成等提高效率；不只是“全放内存”。**

MapReduce 的多作业链路常有更多落盘和调度开销。Spark 也会读写磁盘，Shuffle、spill 和缓存落盘都存在；对单次 IO 主导的任务不保证总是显著更快，更不能背固定倍数。

### Q53｜RDD、DataFrame、Dataset，Transformation 和 Action 是什么？

**短答：RDD 是分区的分布式数据集合；DataFrame 带结构化 Schema，优化器能理解列和表达式；Dataset 在支持它的语言中提供类型化 API。**

Transformation 描述变换，一般延迟执行；Action 请求结果或写出，触发计算。常用 SQL／DataFrame 更容易利用优化器；自定义逻辑才按需要用更底层 API。PySpark 主要使用 DataFrame，不应照搬 Scala 的类型化 Dataset 说法。参考：[Spark RDD 指南](https://spark.apache.org/docs/latest/rdd-programming-guide.html)。

### Q54｜Application、Job、Stage、Task、DAG 是什么关系？【重点】

**短答：一个应用包含 Driver 和执行资源，可以执行多个 Job；Job 根据 Shuffle 等依赖拆成 Stage；Stage 内按分区生成 Task；DAG 描述计算与依赖关系。**

一串可流水处理的窄依赖常在同一 Stage，跨 Shuffle 通常形成 Stage 边界。一个 Stage 一般每个待处理分区对应一个 Task。不要数 SQL 里有几个 SELECT 就说有几个 Job；缓存、广播子查询和 AQE 也会影响最终执行，应以执行计划和 UI 为准。

参考：[Spark 集群与执行单元](https://spark.apache.org/docs/latest/cluster-overview.html)。

### Q55｜宽依赖和窄依赖是什么？哪些算子会 Shuffle？【重点】

**短答：窄依赖中，每个父分区只被有限、确定的子分区依赖，通常可局部流水处理；宽依赖需要跨父分区重分布，典型表现是 Shuffle。**

常见窄依赖：`map`、`filter`、不重分布的 `coalesce`。常见 Shuffle：`groupByKey`、`reduceByKey`、`distinct`、`repartition`、排序与许多 Join。

**边界：** Join 是否 Shuffle 与两边现有分区、广播策略有关；已经满足所需 partitioner 的部分算子可免去新的 Shuffle。`reduceByKey` 常能先局部合并，比把所有 values 收集后再聚合更省传输。参考：[Spark RDD 指南](https://spark.apache.org/docs/latest/rdd-programming-guide.html)。

### Q56｜Spark Shuffle 和 MapReduce Shuffle 有什么区别？

**短答：两者都为跨分区计算交换数据，但 Spark 的 Shuffle 是 DAG 中的执行边界，不受一个作业只能 Map→Reduce 的固定两阶段接口限制。**

Spark 也会分区写出、拉取中间数据，并可能排序、spill 和做 Map 端合并，具体路径由算子、Shuffle 实现和版本决定。Spark RDD 的 Shuffle 结果不能一概理解为“像 Hadoop Reduce 输入一样按 key 排好序”；是否要求有序要看算子。

### Q57｜Spark 常见 Join 策略与 AQE 是什么？

**短答：常见有 Broadcast Hash Join、Sort Merge Join、Shuffled Hash Join。AQE 利用运行时统计调整部分物理计划。**

AQE 可以在支持的场景合并过小的 Shuffle 分区、优化倾斜 Join、调整 Join 策略。它不能修复口径错误、多对多重复，也不是所有热点聚合的万能解法。Hint 也不保证必定采用，必须看 Join 类型、内存和最终计划。参考：[Spark SQL 调优](https://spark.apache.org/docs/latest/sql-performance-tuning.html)。

### Q58｜cache、persist、checkpoint 区别？什么时候用？

**短答：cache／persist 用于复用计算结果，persist 可以选择存储级别；可靠 checkpoint 把结果保存为可恢复的截断点，避免过长血缘反复重算。**

缓存通常要在 Action 执行后才真正填充；内存不足可按存储级别落盘或重算。缓存没有复用收益就徒增成本，用完应释放。可靠 checkpoint 与 localCheckpoint 的容错能力不同。这里说的是 Spark 数据集检查点，不能与 Flink 的全作业状态一致性检查点直接混同。

### Q59｜Spark OOM、GC 时间长，怎么排查？

**短答：先分 Driver OOM 和 Executor OOM，再定位数据量、分区大小、算子与内存使用。**

Driver 常见风险是大结果 `collect`、过多元数据和任务；Executor 常见是过大分区、热点聚合、过大的广播表、缓存以及对象创建／反序列化开销。先减少数据、拆大分区、换聚合／Join 策略、控制缓存，再评估内存与每 Executor 并发。盲目加内存可能只是推迟失败。

参考：[Spark 内存与执行调优](https://spark.apache.org/docs/latest/tuning.html)。

### Q60｜一条 SQL 突然变慢，你如何优化？

**短答：用执行计划与运行指标定位瓶颈，再针对性改动，每次验证结果一致和资源变化。**

| 先看什么 | 可能问题 | 对应动作 |
| --- | --- | --- |
| 时间花在哪里 | 排队、扫描、Shuffle、Join、写出、提交 | 先确认不是单纯等资源或上游 |
| 扫描范围／行列数 | 分区裁剪没生效、过滤太晚、重复扫描 | 改谓词、裁剪列、复用中间结果 |
| Join 输出量／策略 | 关联膨胀、统计过期、广播不合适 | 修粒度、更新统计、调整策略 |
| Task 长尾／spill／GC | 倾斜、分区过大、对象开销 | 见 Q50／Q59 |
| 文件／存储 | 小文件、慢存储、输出并发失衡 | 合并文件、调整写入与布局 |

**验证：** 固定数据范围比较总耗时、资源耗用和关键结果；至少核对主键数、行数与核心金额。别只说“加资源、加缓存、加分区”。参考：[Spark SQL 调优](https://spark.apache.org/docs/latest/sql-performance-tuning.html)。

## 六、实时数仓、Kafka 与存储选型

### Q61｜离线和实时怎么选？Lambda、Kappa 是什么？

**短答：先看业务需要多快、允许怎样修正、成本和历史重算，再选架构。离线与实时不是先进和落后的区别。**

Lambda 用批、流两条链路兼顾全量准确与低延迟，代价是两套逻辑与口径一致性维护。Kappa 主要用流处理逻辑，通过重放历史完成重算，代价是日志保留、重放成本和有状态升级复杂度。

**追问：流批一体就天然一致吗？** 不会。还需统一时间、去重、维度版本、更新撤回与数据截止点。同一套 API 不等于所有数据语义相同。

### Q62｜Flink 和 Spark 有什么区别？

**短答：两者都能支持批流计算；比较时要明确 API、运行模式、延迟、状态规模、容错、生态与团队经验。**

Flink 强调有状态流处理、事件时间与连续处理能力；Spark 在 SQL、批分析和既有数据生态中广泛使用，Structured Streaming 常用微批执行，也存在其他模式。不要简单说“Flink 只能流、Spark 只能批”，也不要拿旧 DStream 的结论概括全部 Structured Streaming。

### Q63｜事件时间、处理时间、Watermark、窗口和迟到是什么关系？

**短答：事件时间是事情发生的时间，处理时间是系统当前处理时间；Watermark 表达事件时间进度，用来驱动窗口和定时器，不是保证以后绝不会再来旧数据。**

多输入算子通常受最慢的有效输入 Watermark 制约；空闲输入可配置 idle 检测，避免永远拖住进度。滚动窗口互不重叠，滑动窗口可重叠，会话窗口按不活动间隔分组。

**迟到处理：** 根据具体 API 与窗口策略，选择允许一定迟到并更新结果、侧输出、补数或按规则丢弃。允许迟到意味着下游可能收到修正结果，不能只会追加。参考：[Flink 时间概念](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/)。

### Q64｜Flink State 是什么？为什么会越跑越大？

**短答：State 保存跨记录的计算信息，如每用户累计金额、窗口中间值和去重集合。常见有 Keyed State 与 Operator State。**

Keyed State 按 key 分片；Operator State 归算子实例管理，并按规则参与恢复与重分配。状态膨胀常因 key 数不断增长、去重无过期、窗口无法关闭、Join 保留范围过大。TTL 和清理机制要匹配业务：把仍会被合法更新的数据提前清掉，会影响正确性。

### Q65｜Checkpoint 如何实现故障恢复？对齐与非对齐有什么区别？

**短答：Checkpoint 把源读取位置和算子状态保存成一致恢复点；失败后恢复状态并重放对应输入。Barrier 用于界定这个逻辑位置。**

多输入下，对齐检查点会协调各输入 Barrier，防止把界限前后的状态混在一起；非对齐检查点还保存部分在途数据，减少反压下等待对齐的影响，但可能增加快照数据与 IO。不能说“非对齐就没有 Exactly-once”，也不能忽略存储完成和协调确认。参考：[Flink Checkpointing](https://nightlies.apache.org/flink/flink-docs-stable/zh/docs/dev/datastream/fault-tolerance/checkpointing/)。

### Q66｜Exactly-once 是什么？开 Checkpoint 就够了吗？【重点】

**短答：Exactly-once 不是每条数据物理上只处理一次，而是失败恢复后，记录对受保障结果产生一次正确影响。开 Checkpoint 还不足以保证外部系统端到端 Exactly-once。**

需要：可重放的 Source、一致的算子状态，以及能与恢复语义配合的事务或幂等 Sink。普通 HTTP 请求、邮件、外部累加接口不会自动随作业状态回滚。

**追问：Upsert 就肯定行吗？** 还要有正确的主键、更新顺序和业务语义。按用户覆盖最新完整累计值可以设计幂等；反复执行“余额＋10”不是幂等。参考：[Flink 端到端保障](https://nightlies.apache.org/flink/flink-docs-stable/docs/learn-flink/fault_tolerance/)。

### Q67｜Savepoint 和 Checkpoint 区别？升级能直接恢复吗？

**短答：Checkpoint 主要服务运行中自动故障恢复；Savepoint 通常由用户触发，用于停止、迁移、升级等受控操作。二者都涉及状态快照，但生命周期和使用目的不同。**

恢复升级要检查算子 UID、状态名称与序列化兼容性、拓扑和并行度限制、最大并行度，以及连接器和输出提交行为。不能保证“改完代码都能从 Savepoint 启动”。关键链路要在兼容环境演练恢复。参考：[Flink Savepoints](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/savepoints/)。

### Q68｜Flink 反压、Kafka 积压怎么排查？

**短答：从源到 Sink 看吞吐与资源，再逆着反压传播找真正跟不上的下游环节。积压是现象，不等于 Kafka 自己坏了。**

看消费 lag、busy／idle／backpressured、CPU、GC、checkpoint 时间、状态大小、各分区负载与 Sink 延迟。可能是热点 key、同步 IO、慢外部库、输出限流、状态过大或资源不足。

对应措施是优化热点、批量／异步 IO、合理并行度、状态清理与下游容量；盲目提高 Source 并发会进一步压垮 Sink。参考：[Flink 反压监控](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/monitoring/back_pressure/)。

### Q69｜实时关联维表怎么选？维度更新会回改旧结果吗？

**短答：取决于要关联最新状态还是事件发生时的历史版本，以及维度大小、更新频率、查询延迟和状态成本。**

| 方式 | 适合什么 | 关键问题 |
| --- | --- | --- |
| 外部 Lookup／异步查询 | 维度在外部库，需要按键查询 | 缓存过期、外部容量、故障和最新／历史语义 |
| 广播维度 | 维度规模可控，需要本地访问 | 每份副本的内存、更新规则和一致性 |
| 版本化 Temporal Join | 需要按时间语义取相应版本 | 主键、时间属性、Watermark 和版本保留 |
| 普通流 Join | 两侧都随时间变化并需要维护关联结果 | 无界状态、撤回消息和保留范围 |

维度更新是否回改旧结果由 Join 语义决定；查询时取最新维度通常不会自动重算所有历史事实。

### Q70｜Kafka 的 Topic、Partition、Offset、Consumer Group？怎么保证顺序？

**短答：Topic 是逻辑消息类别，Partition 是有序日志与并行单位，Offset 是分区内位置；同一消费者组内，一个分区在某时刻通常由一个消费者负责。**

顺序只在分区内成立。若要求同一订单事件有序，应按订单 key 路由，并控制生产与消费处理顺序；扩分区、多个生产者、重试和消费端并发都要考虑。增加消费者超过分区数，通常不会提高该组有效消费并行度。参考：[Kafka 设计](https://kafka.apache.org/41/design/design/)。

### Q71｜Kafka 如何避免丢失和重复？为什么不能只说 acks=all？

**短答：生产确认、复制、消费提交与落地处理一起设计。** 生产端关注重试、幂等、`acks`；服务端关注副本、ISR 与 `min.insync.replicas`；消费端关注处理完成和提交位点的顺序。

`acks=all` 面向当前 ISR 的确认，不等于所有配置副本都已成功写入。消费后未提交就崩溃可能重复，先提交后处理失败可能丢处理。Kafka 内部事务保障也不自动扩展到任意外部数据库，因此还需事务配合或业务幂等。参考：[Kafka 交付语义](https://kafka.apache.org/41/design/design/)。

### Q72｜Hive／Spark、ClickHouse／Doris／StarRocks、HBase 怎么选？

**短答：先分计算引擎、分析服务和按键存储，再按访问模式选。**

| 需求 | 主要评估方向 |
| --- | --- |
| 大规模离线加工、全量重算 | 批计算吞吐、存储成本、调度与数仓生态 |
| 交互式筛选聚合、报表并发 | OLAP 引擎的列式执行、索引／物化视图、分布式 Join、导入更新与并发 |
| 按 RowKey 点查／范围查 | HBase 等存储的 RowKey 设计、访问局部性与热点 |

HBase 不能直接当成擅长任意多维 SQL 的 OLAP 数据库；RowKey 单调增长可能产生热点，可按访问模式设计散列前缀／预分区，同时权衡范围查询。

**“OLAP 能不能替代数仓？”** 要分清组织和建模职责与执行产品。换执行引擎不会自动完成公共口径、历史管理、质量与血缘。

### Q73｜数据湖、数据仓库、湖仓一体有什么区别？

**短答：数仓强调面向分析的集成、建模与治理；数据湖强调以较开放方式保存多类数据并供不同引擎使用；湖仓是在湖存储上增强表管理、事务、治理和分析能力。**

三者不是仅靠“存 HDFS 还是对象存储”区分。湖仓一体也不意味着所有引擎、所有流批作业天然兼容或同一结果；仍要治理 Schema、版本、更新删除、并发提交和消费口径。

### Q74｜Iceberg、Hudi、Delta、Paimon；COW、MOR、Compaction 要知道什么？

**短答：这些方案都试图让湖上的文件以可靠的表语义被管理，但组织方式、写入路径、更新和增量消费机制不同。选型结合引擎、变更率、读写延迟与运维。**

| 概念 | 必会答案 |
| --- | --- |
| 快照／事务提交 | 一次提交发布一组一致的数据文件和元数据变化，让读者按某个一致版本读取 |
| Copy-on-Write | 更新时重写受影响数据文件，读取通常较直接，更新可能写放大 |
| Merge-on-Read | 更新先写增量／日志等，读取时合并；降低部分更新成本，但增加读与整理开销 |
| Compaction | 合并小文件或增量片段、整理数据以控制读写放大；不是可随意删除历史的万能清理 |
| 快照过期／文件清理 | 要保护活跃读者、回溯需求和消费进度，不能只按文件年龄删 |

Iceberg 重点了解快照、元数据和 Schema／分区演进；Hudi 重点了解记录更新、COW／MOR 与增量查询；Delta 重点了解事务日志与其生态；Paimon 可关注主键更新、流式写入与增量消费。**具体特性需核对所用版本，没用过就讲原理与选型，不包装生产经验。** 参考：[Iceberg 规范](https://iceberg.apache.org/spec/)、[Hudi 表与查询类型](https://hudi.apache.org/docs/table_types/)、[Delta 入门](https://delta.io/learn/getting-started/)、[Paimon 主键表](https://paimon.apache.org/docs/master/primary-key-table/)。

## 七、SQL 与常见场景题

### Q75｜SQL 逻辑执行顺序、NULL、COUNT、WHERE／HAVING？

**短答：理解逻辑顺序才能判断过滤是在关联前后、聚合前后生效；优化器的实际执行顺序可能不同。** 可记为 `FROM/JOIN → WHERE → GROUP BY → HAVING → 窗口与 SELECT → DISTINCT → ORDER BY → LIMIT`，具体别名可见性和语法因引擎而异。

| 考点 | 参考答案 |
| --- | --- |
| WHERE／HAVING | WHERE 过滤输入行；HAVING 过滤聚合结果。窗口结果通常用子查询外层过滤，支持时可用 QUALIFY |
| COUNT(*)／COUNT(col) | 前者计行；后者只数该列非 NULL；COUNT(DISTINCT col) 数非 NULL 不同值 |
| NULL 比较 | 普通 `= NULL` 不得到 true，应使用 `IS NULL`；未知值不等于 0 或空字符串 |
| SUM 空集 | 通常是 NULL；是否转 0 取决于“无记录”是否可解释为业务零 |
| LEFT JOIN 陷阱 | WHERE 中要求右表字段等于某值，会过滤未匹配行；应按需求在右表子查询或 ON 中限制 |
| NOT IN 陷阱 | 子查询含 NULL 会影响三值逻辑；用明确 NULL 规则或 NOT EXISTS |
| UNION／UNION ALL | UNION 去重；UNION ALL 保留重复并通常减少去重成本 |

**注意：** `NULL=NULL` 不匹配，不代表 Group By 不会把 NULL 分为一组；这两个语义不同。

### Q76｜窗口函数、排名、取最新、累计值怎么写？

**短答：窗口函数在保留输入明细行的同时，按分组、排序和窗口范围计算结果；聚合 Group By 则通常压缩行。**

| 函数／模式 | 例子与坑 |
| --- | --- |
| ROW_NUMBER | 1、2、3；并列时也给不同序号，取最新必须有稳定的并列排序键 |
| RANK | 并列第一后可能是第三，即 1、1、3 |
| DENSE_RANK | 并列后不跳号，即 1、1、2 |
| LAG／LEAD | 取排序中的前／后一条，不一定是昨天／明天；日期有缺口要补齐或按日期关联 |
| 累计 SUM | 用明确的 `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`，区分 ROWS 与 RANGE 的并列值处理 |

```sql
-- 每个订单取最新状态；event_seq 用来打破同一更新时间的并列
SELECT order_id, status, updated_at
FROM (
  SELECT order_id, status, updated_at,
         ROW_NUMBER() OVER (
           PARTITION BY order_id
           ORDER BY updated_at DESC, event_seq DESC
         ) AS rn
  FROM order_changes
) t
WHERE rn = 1;
```

**追问：UDF／UDAF／UDTF？** UDF 通常逐行输入、标量输出；UDAF 多行聚合成结果；UDTF 可把一行展开为多行，如数组展开。展开后粒度会变化，要重新检查计数和金额。

### Q77｜连续登录 N 天怎么写？

**短答：先按用户和日期去重，再按日期编号；连续日期减去连续编号会得到同一分组键，最后统计每段长度。**

```sql
-- Spark SQL / Hive 常用写法；login_date 为 DATE 类型
WITH d AS (
  SELECT DISTINCT user_id, CAST(login_time AS DATE) AS login_date
  FROM login_events
), n AS (
  SELECT user_id, login_date,
         ROW_NUMBER() OVER (
           PARTITION BY user_id ORDER BY login_date
         ) AS rn
  FROM d
), g AS (
  SELECT user_id, login_date,
         DATE_SUB(login_date, CAST(rn AS INT)) AS grp
  FROM n
)
SELECT user_id, MIN(login_date) AS start_date,
       MAX(login_date) AS end_date, COUNT(*) AS consecutive_days
FROM g
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;
```

**边界：** 同一天多次登录先去重；跨时区先定义业务日期。题目若限定某月，要明确只算月内连续还是允许跨月延伸。SQL 方言不同，日期减法函数需要调整。

### Q78｜次日留存怎么算？为什么分母容易错？

**短答：先定义 cohort，例如“当天首次注册用户”；分母是该 cohort 的人数，分子是其中第二天发生指定活跃行为的人数。留存率不是第二天总活跃／第一天总活跃。**

```sql
-- users：每用户唯一，register_date 为业务日期
-- daily_active：按 user_id + activity_date 去重
SELECT u.register_date,
       COUNT(*) AS new_users,
       COUNT(a.user_id) AS retained_users,
       1.0 * COUNT(a.user_id) / COUNT(*) AS retention_d1
FROM users u
LEFT JOIN daily_active a
  ON u.user_id = a.user_id
 AND a.activity_date = DATE_ADD(u.register_date, 1)
-- 只统计次日已经完整到齐的 cohort
WHERE DATE_ADD(u.register_date, 1) <= CAST('2026-09-09' AS DATE)
GROUP BY u.register_date;
```

**追问：DAU 可以相加得到 MAU 吗？** 不可以，跨天存在重复用户；回到用户集合去重，或采用能合并且符合误差／准确性要求的集合表示。精确 Bitmap 要处理 ID 映射和空间；HLL 是近似基数估计，不能假装无误差。

### Q79｜API 每页 100 条、最多 1000 条、限制 QPS，怎么拉一年数据？

**短答：先澄清“最多 1000 条”是总结果截断还是一次请求限制，然后按可查询维度把数据切成不会超限的范围，再做限流、断点、幂等与对账。**

设计顺序：确认日期／ID 筛选、稳定排序、游标和快照能力 → 按时间分段，超限继续细分 → 范围内游标分页 → QPS 限流与有限重试／退避 → 持久化已完成范围和游标 → 按业务键与版本写入 → 对账补漏。

**必须说的边界：** 若 API 没有任何切分／导出能力且永远只返回前 1000 条，无法保证完整取出更多数据，需要提供方支持；不能用多线程解决逻辑不可达。分页期间数据变化也可能造成页码偏移，应优先稳定游标或固定快照。

### Q80｜给你订单、支付、发货、售后，如何从零建模？【完整示例】

**短答：先按业务过程拆事实并确定各自粒度，再用共享维度关联；根据发生量、周期状态、全流程耗时分别选模型。**

| 步骤 | 示例回答 |
| --- | --- |
| 明确需求 | 是统计支付金额、跟踪履约阶段，还是分析客诉原因？时效和历史口径是什么？ |
| 调研关系 | 一单多少明细、几次支付、几个包裹、几次退款？业务主键和状态变更日志是什么？ |
| 事务事实 | 订单明细按 order_id＋line_id；支付按 payment_id；退款按 refund_id；包裹事件按唯一事件键 |
| 公共维度 | 用户、商户、商品、渠道、日期；明确历史版本与不同日期角色 |
| 周期状态 | 若要看每天未完成订单量，建设按日状态快照，明确统计截止时点 |
| 流程跟踪 | 若订单级里程碑可确定，建设订单累积快照；拆包／多次发货应保留包裹明细，订单完成时间按规则推导 |
| 公共汇总 | 按稳定的日期、商户、渠道等组合汇总可加度量；去重和比例单独处理 |
| 工程落地 | 增量与更新撤回、分区、重跑、迟到、DQC、血缘、权限、SLA |
| 验收 | 主键唯一；各状态流转合理；支付退款分开对账；关联后不重复；历史时点可追溯 |

**面对“承单、送达、售后、评价定位问题”追问：** 给出明确的阶段里程碑和耗时，再按维度定位异常环节。流程可能有取消、重试、多次售后，不能只用一列“最终状态”替代完整事件历史。

### Q81｜实时计算用户累计支付金额，退款、重复、乱序怎么办？

**短答：先定义累计是支付流水总额还是净额，以稳定事件键或业务版本去重，维护可恢复的用户状态，向下游输出按主键覆盖的最新结果或正确的变更流。**

支付成功事件增加金额；退款是否扣减以及何时归属按口径决定。重复事件不能再加一次；若源提供订单状态更新，要计算前后变化，不能每次更新都把全额重加。乱序要依据业务版本／事件序号，不能让旧状态覆盖新状态。

还要解决启动时的历史累计与增量衔接、状态恢复、外部写入幂等及定期离线对账。**全历史累计不可以随意用短 TTL 清掉状态**；确需清理时，要有可靠基数和后续恢复办法。

## 八、面试前最后扫一遍：容易失分的表达

| 不准确的说法 | 更严谨的说法 |
| --- | --- |
| Map 不可能倾斜 | Map 的输入和计算负载也可能不均；热点 key 汇聚主要看 Reduce／Shuffle 后 |
| 事实表就是增量、全量、拉链三种 | 经典业务建模分类是事务、周期快照、累积快照；它们与加工方式是不同轴 |
| 累积快照就是不断累加数值 | 它随业务流程补全并更新里程碑 |
| 数仓建模就是 ODS→DWD→DWS→ADS | 先调研业务与源数据，确定粒度、维度和事实，再讨论分层与落地 |
| 用户 ID 枚举太多，所以不是维度 | 高基数不妨碍其作为维度键和分析筛选条件 |
| 指标被拿来过滤就变维度 | 先区分明细过滤、聚合过滤和加工后的分段属性 |
| 周比例就是每天比例的平均 | 先明确问总体比例还是日均比例；组成项可加时才可先汇总再相除 |
| 日去重人数加起来就是周人数 | 跨日有重叠，需要在目标范围去重 |
| Join 多了行就 DISTINCT | 先检查粒度与关联基数，不能掩盖错误关系 |
| 增加 Reducer 就能解决热点 key | 同 key 仍可能进同一个分区，需改计算或分发方式 |
| Spark 都在内存，不落盘 | Shuffle、spill、缓存和检查点都可能涉及磁盘 |
| 开 Checkpoint 就端到端不重不丢 | 还需要可重放 Source 和配合恢复语义的 Sink |
| 外部表永远不会删数据 | 要看版本、表属性、PURGE 和平台管理规则 |
| 重跑就是再执行一次 SQL | 输入版本、目标范围、幂等、并发、依赖和验证都要控制 |
| 公共数仓就是给业务出报表 | 核心是可信、可复用的数据资产与稳定服务；下游也可以是数仓和应用后端 |

## 九、被要求结合个人项目时，怎么接

**先区分“理论上会怎么做”和“实际我负责过什么”。** 你已说明：公共营销数据是自己的建设／维护范围，触达有完整优化与重建经历；智能经分的场景险源数仓由其他团队建设。下面是复习提示，不新增个人事实。

| 面试官问 | 从你的哪段经历展开 | 最少要带出的信息 |
| --- | --- | --- |
| 完整建模流程 | 触达链路优化与重建 | 业务过程、源数据、粒度、事实和维度、消费方式、验证 |
| 公共数仓价值 | 公共营销数据支持 | 谁复用、统一了什么、如何稳定服务业务数仓／后端 |
| 存量治理 | 大量交接任务的维护 | 如何找依赖、识别风险、排优先级；数字只说真实可确认的 |
| 指标与口径 | 指标平台及数据知识配置 | 指标、维度、粒度、模型映射，平台和个人职责边界 |
| 最大难点 | 选一个你确实解决过的问题 | 原因判断、候选方案、取舍、你的动作、结果证据 |

**卡住时可用的开头：**“我先明确一下这里的业务粒度和统计时间，因为这两个会影响模型选择。”“这个组件细节我没有在生产中主导过，我先从原理和排查顺序回答。”不要把设计参考答案改说成自己的落地事实。
