### 参考实现（Codex 新写，不是面试原代码）

按题目示例假设：每条调用具备 id/name/args，id 为字符串等可哈希值，tools 是工具名到同步函数的映射，args 用作关键字参数。采用一次 execute_calls 调用内的缓存；普通工具异常属于 Exception。字段缺失、异步工具或进程退出信号不属于这版题目实现范围。

```python
def execute_calls(calls, tools):
    cache = {}
    results = []

    for call in calls:
        call_id = call["id"]

        if call_id in cache:
            results.append(cache[call_id])
            continue

        name = call["name"]
        if name not in tools:
            result = {"id": call_id, "ok": False, "error": "unknown tool"}
        else:
            try:
                value = tools[name](**call["args"])
            except Exception as exc:
                result = {"id": call_id, "ok": False, "error": str(exc)}
            else:
                result = {"id": call_id, "ok": True, "value": value}

        cache[call_id] = result
        results.append(result)

    return results
```

`**call["args"]` 把字典按关键字参数传给工具，见 [Python 参数解包](https://docs.python.org/3/tutorial/controlflow.html#unpacking-argument-lists)。这里按题目要求将工具的普通异常转成失败结果；不使用裸 except 吞掉 KeyboardInterrupt、SystemExit 等控制信号，见 [Python 异常处理](https://docs.python.org/3/tutorial/errors.html#handling-exceptions)。

### 面试时应主动说出的边界

1. **失败也缓存。** 第一次工具抛异常后，同 ID 再出现，返回第一次失败；本题没有授权自动重试。未知工具也是第一次结果，要缓存。
2. **同 ID 以第一次为准。** 即使后面出现不同 name/args，依本题要求仍复用首次结果；生产系统可另定“检测冲突并拒绝”的协议，但不能悄悄改题目语义。
3. **不同 ID 即使 name/args 相同，也分别执行。** ID 标识一次调用，name 用于找到函数。按工具名去重会错误合并两个合法调用。
4. **重复输入不能被删掉。** 输入有三条，输出就有三条；cache 负责去重执行，results 负责保留位置。
5. **False、0、None 都可以是成功值。** 成功与否取决于是否正常返回，不用返回值真伪判断执行是否发生。
6. **保证范围是本次函数调用。** 再调用一次 execute_calls 会有新缓存；不保证进程重启、跨批次或多实例中的去重，也不保证工具无限挂起时继续执行。

除工具执行和结果载荷的成本外，字典平均查找条件下遍历开销 O(n)；结果列表 O(n)，缓存 O(u)，u 为不同 ID 数。重复位置复用同一结果对象符合本题要求；若调用方需要独立修改结果，复制策略需要额外约定。

### 生产追问怎样回答得更具体

可以先说：“基础版的边界是单次、串行、内存缓存。我会先保证调用身份和结果关联，再补运行边界，最后考虑性能。”接着按下面顺序展开；不必一次实现全部内容。

| 优先讨论 | 具体问题与合理方向 | 不应混淆的地方 |
| --- | --- | --- |
| 输入与权限 | 先校验调用结构，再从当前用户/Agent 可用的注册表找工具，校验参数与资源范围 | 工具名存在并不代表所有用户都能操作所有资源；不给模型工具描述也不等于完整授权控制 |
| 调用与结果关联 | 保留 call ID；可附加工具名便于日志与展示 | 同一工具可以执行多次，工具名不能替代调用 ID；厂商协议的调用 ID 也不自动成为跨业务请求的幂等键 |
| 执行失败与状态 | 区分输入错误、明确执行失败、超时后结果未知；定义超时、取消、重试与去重作用域 | 超时不代表工具没有产生副作用；简单再次执行可能重复操作。持久化缓存也不能单独解决执行成功、结果未落盘的空隙 |
| 性能与顺序 | 确认调用无依赖且允许并发后，再限制并发数；结果按原索引放回 | 模型一次返回多个调用，不保证它们在业务上相互独立；并发还会引入同 ID 同时未命中缓存的竞争 |
| 可观测与可用结果 | 记录关联 ID、耗时、错误类别和执行状态；返回脱敏、可操作的错误 | 对用户暴露完整堆栈或凭证不等于“错误详情更充分”；生产结果还需考虑体积和序列化 |

工具结果通过调用 ID 与模型请求关联，可参照 [Anthropic 工具调用协议](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。本题的返回字典是简化接口，不是某一厂商的完整消息结构。

## 关键技术纠正

**一次工具调用到底由谁执行。** 以客户端工具为例，应用发送消息和工具描述，模型返回调用 ID、名称与参数；应用校验并执行，将结果与对应 ID 一起回传，再请求模型继续。模型生成调用不等于工具已执行；子 Agent 也可能是由程序路由启动的普通应用逻辑。[Anthropic：处理工具调用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。这是官方协议示例，不证明本项目实际使用该 SDK。

Q22 可练成以下轨迹，而不是背固定次数：用户提出订单任务→模型请求读取文档→应用返回提取结果→模型需要补充的目录信息/澄清→应用或用户提供结果→程序校验结构化查询及身份→取数执行→回传带来源的结果→模型回答。每一步都标“谁决定、谁执行、输入输出是什么”；已有文档文本或目录缓存时，部分调用可以省略。

**批量工具调用与并行执行要分开。** 同一次响应可包含多个调用，但应用可根据依赖和副作用决定并行或串行；即便拒绝某个调用，也应按协议返回与其 ID 对应的错误结果，避免模型等待不存在的结果。[Anthropic：并行工具使用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)。不能把工具名称当作唯一调用 ID：同一个工具可以有多个不同参数的调用。

**token 被盗这个假设必须正面回答。** 对 bearer token 而言，持有有效凭证的人通常可以使用它所代表的权限，因此凭证要在存储和传输中受保护；有效期只是缩短滥用窗口。[RFC 6750](https://www.rfc-editor.org/info/rfc6750/)。应用还需结合真实系统讨论最小权限、服务端会话绑定、撤销和审计。录音未提供足够证据证明这些都已实现。

**恢复与幂等是两个相关但不同的问题。** 持久 checkpoint 保存执行状态、支持恢复；内存存储不能提供跨进程持久性。[LangGraph：Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。恢复可能重放任务，外部副作用需要相应的幂等设计，不能只靠重启前的内存缓存。[LangGraph：Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)。这些是可参考的设计，不是对现有项目的实现认定。

**“五次至少一次对”不等于稳定。** 假设某题五次结果为“错、错、对、错、错”：该题在“至少一次成功”口径下通过，但五次成功比例只有 20%，第一轮失败。应保留逐次结果、运行配置和题目级分布，分别说明首次成功、多次重复表现，以及允许重试后的成本与时延。不能用这一口径把 91% 的单次表现改称稳定 100%。这个例子用于区分定义，不重新计算录音中的真实指标。
