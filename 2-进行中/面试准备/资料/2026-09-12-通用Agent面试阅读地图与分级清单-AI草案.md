# 通用 Agent 面试阅读地图与分级清单

> 整理与核验日期：2026-09-12。用途：通用 Agent 应用研发、平台与工程设计方向的面试准备。本文是 Codex 的阅读建议草案，不表示用户已采用这些优先级或已掌握内容。
>
> 共 43 组主体资料、6 类评测基准入口。重点是设计、评测、自迭代；同时覆盖工具、上下文、记忆、多 Agent、持久运行、安全、成本和行业变化。这里的“通用”主要指能跨工具、文件、网页和软件环境完成任务的软件 Agent；机器人控制、基础模型预训练与完整强化学习课程不在本清单范围内。

## 先看这个判断

面试准备最值得建立的一条主线是：**如何让 Agent 完成真实任务，如何证明它完成了，以及如何通过可验证的反馈持续改进。** 围绕这条主线，很多零散名词能连起来。

Harness 可以先理解为“模型外面让 Agent 持续工作的运行系统”，通常涉及工具调用循环、上下文组织、环境访问、状态保存、检查和恢复。不同作者对边界的划分略有不同。Evals 是用任务、环境和判定规则来衡量表现；Trace 是一次运行中可观察到的调用、返回和事件记录，不等于模型全部内部思考。

你的基础文章已经扫过，所以《Building effective agents》降为速览。优先投入评测、上下文和运行系统，再读自迭代案例；多 Agent、协议和模型训练按面试需要展开。这个顺序是本次建议，不是行业统一标准。

### 优先级和阅读深度

- **P0：优先读。** 能支撑主要面试问题；下面 10 篇组成第一轮。
- **P1：按需深入。** 面试涉及对应主题时读，不要求一次读完。
- **P2：背景与概念源头。** 用于建立认识和追问，暂不要求论文细节。
- **正文核对：** 本次核对了主要论点与相关关键段落，不表示逐段翻译、实验复现或完整代码审计。
- **文档核对：** 阅读官方文档中的相关机制。动态文档以核验日为准；无法确认发布日期时明确标注。
- **概览核对：** 论文以摘要、方法简介为主，仓库以 README 为主，系列文章以目录为主。

| 自迭代与训练 | 反馈修改记忆、方法、代码还是模型权重？怎样验证泛化？ | R04、R09、R24–R27、R43 |
| 可靠性与持久运行 | 超时、中断、重试、恢复、人工接管怎样落地？ | R06、R07、R33、R34 |
| 安全与权限 | 外部文本如何影响动作？哪些限制必须由运行环境执行？ | R35、R36 |

RAG 放在上下文与知识获取中理解：它解决把相关外部信息提供给模型的问题；Agent 可以决定是否检索、改写查询和继续找证据。RAG 的检索器设计、索引和重排仍是独立知识点，本清单没有重新展开一整套检索课程。

## 六、几个必须分清的概念与取舍

### 1. “自迭代”到底迭代哪一层

下表是跨文章综合出的分类，不是一种统一产品标准。

| 层次 | 变化的东西 | 典型资料 | 验证重点 |
| --- | --- | --- | --- |
| 当前任务自纠错 | 下一步动作、查询、计划 | R07、R12、R42 | 新动作是否修复实际失败；是否进入无限重试。 |
| 记忆更新 | 用户偏好、已确认事实、历史经验 | R28、R43 | 来源可信、时效与冲突；有无错误跨任务传播。 |
| 方法与提示词优化 | Prompt、Skill、工具描述 | R05、R09、R26 | 留出任务是否提高；旧能力和其他场景有无退化。 |
| 代码与运行系统优化 | 路由、工具实现、上下文策略、恢复逻辑 | R02、R04、R24 | 真正运行候选版本，测结果、成本、稳定性和副作用。 |
| 模型训练 | 模型权重或可训练参数 | R27；R25 为自动训练实验案例 | 奖励是否可靠、训练/评测是否隔离、样本外效果及训练成本。 |

**建议的应用工程闭环：** 收集真实运行记录 → 人工核实并分类失败 → 建立可复现任务与独立判定 → 提出局部改动 → 在开发集迭代 → 在未参与优化的留出集检查 → 小范围验证真实效果 → 记录版本并支持回退。这个闭环是基于 R01、R04、R09、R24 的综合建议；不是这些案例都已经完整证明的统一流程。

### 2. 什么时候需要规划

综合 R11–R13：步骤少、路径明确的任务可以直接工具调用或固定工作流；目标复杂、存在依赖或需要中途根据证据调整方向时，显式计划更有价值。长期任务通常还需要可恢复的任务状态，这与“让模型每轮输出一段规划”是两件事。

面试可以举例：改一个明确配置通常不需要单独 Planner；调研多个方案、比较约束再形成可交付成果，适合先拆任务。规划应记录目标、约束、待验证假设和完成条件，过早锁死未知的实现细节可能让错误传递到后续步骤。

### 3. 多 Agent 的上下文到底共享还是隔离

综合 R08、R12、R13：执行者需要父任务已获得的事实时，继承上下文可能减少重复调查；评审者需要独立判断时，独立上下文有助于减少锚定。两者都需要明确交付接口，不能假定“全部共享最好”或“全部隔离最好”。

### 4. 评测总分、过程与结果怎样一起看

综合 R01、R18、R24：结果验证回答“任务完成了吗”，过程记录帮助解释“为什么失败”，单项关键指标防止严重缺陷被平均分掩盖。还要先检查判分器得到的上下文是否完整，否则可能把合法操作判成违规。

### 5. 为什么换强模型后还要重新检查架构

R10、R13 提供了具体例子：原来为模型弱点增加的反复提醒、上下文重置或其他固定步骤，后来可能产生额外成本。**工程上的建议是逐项做消融对比**：移除某机制后，任务完成度、失败类型、成本与延迟如何变化；不能根据“模型更强了”直接删掉所有约束。

### 6. 持久化为什么不等于可靠执行

R06、R33 解释运行状态与保存机制；在此基础上的工程推论是：恢复后如果重放了“发消息、创建订单”等外部动作，还需要幂等标识、执行结果记录或人工处理不确定状态。Checkpoint 只能回答保存了什么，不能单独保证外部世界发生了几次。
