### 一、怎么开始与决策

<a id="q01"></a>
#### Q01｜Agent、Workflow、Harness 分别是什么？什么时候值得用 Agent？

**短答：** Workflow 的主要执行路径由程序预先组织，节点中也可以调用模型；Agent 允许模型结合当前状态和反馈决定下一步行动。Harness 是把模型、工具、上下文、状态、执行约束和结果验证接起来的运行系统。选型先看任务是否需要动态决策，以及收益能否覆盖额外的不确定性和成本。

**准备到位：** 能用“固定报表生成”和“用户不断补充要求的调研任务”说明选择理由。别只背组件名，要指出哪个决策由模型做、哪个约束由代码执行。

**继续追问：** 固定工作流中有一个自主查询节点，这个系统算不算 Agent？可以描述为混合系统，解释实际控制边界，比争论唯一名称更有用。

<a id="q02"></a>
#### Q02｜从用户输入到最终结果，一次 Agent Loop 到底怎么运行？

**短答：** 系统先装配指令、状态、消息和可用工具，模型生成回答或结构化工具调用；运行时校验并执行工具，将调用与结果对应后放回后续上下文，再让模型决策。循环受任务完成条件、调用/时间/费用预算、错误策略和用户中止控制。

```text
用户目标 → 组装上下文 → 模型决策
                         ├─ 工具请求 → 校验/授权 → 执行 → 记录结果
                         │                               ↓
                         │           更新状态与上下文 → 下一轮模型决策
                         │
                         └─ 提议完成 → 验证成果 → 通过则返回
                                                未通过则更新状态后继续
```

**准备到位：** 能写出不依赖框架的伪代码，并解释调用标识、工具错误、最大轮数、没有结果时的退出状态。

**易错：** 模型输出“完成”只是一个信号；发邮件、改文件、创建订单是否成功，要核对相应系统或成果。工具返回的文字也不是新的高优先级指令。

本组岗位依据：[J01](来源核验.md#J01)、[J06](来源核验.md#J06)、[J07](来源核验.md#J07)。机制参考：[2026 年的运行系统分层说明](https://www.anthropic.com/engineering/managed-agents)。

### 二、怎么规划与做事

<a id="q03"></a>
#### Q03｜ReAct 与 Plan-and-Execute 怎么选？用户问题模糊时怎么办？

**短答：** ReAct 强调行动与反馈交替；Plan-and-Execute 先形成任务拆解，再推进执行，必要时重规划。简单、确定的任务不一定需要独立 Planner。需要多阶段交付、存在依赖或预算约束时，显式计划更有价值。会改变正确性、授权或交付范围的缺失信息，应先澄清；影响很小且可逆的细节可用明确假设推进。

**准备到位：** 给同一个任务写出目标、约束、依赖、完成条件和一个重规划触发点。例如分析收入下降，先确认时间与指标口径，再决定查哪些证据。

**继续追问：** 计划执行到一半发现初始假设错误怎么办？保留有效证据，修改任务状态与计划，废弃不适用的后续动作，并控制重规划次数和成本。

<a id="q04"></a>
#### Q04｜怎么保证工具选得对、参数对、执行结果也对？

**短答：** 工具契约要明确用途、适用条件、输入字段、返回值和失败含义。模型负责提出调用，系统负责检查工具是否存在、参数结构是否合法、业务语义是否成立、当前用户是否有权限；执行后检查真实结果，并把可处理的错误反馈给模型。涉及写操作还需处理重复执行与结果未知。

**准备到位：** 以查询工具为例说明 `metric_id`、日期范围、粒度、权限、空结果、超时与数据来源；说明哪些能由 Schema 检查，哪些必须查询业务规则。

**易错：** JSON 合法不等于指标选对；HTTP 200 不等于业务成功；模型说有权限不等于服务端鉴权通过。

本组岗位依据：[J02](来源核验.md#J02)、[J04](来源核验.md#J04)、[J06](来源核验.md#J06)、[J08](来源核验.md#J08)。这里的工具契约与异常例子为工程准备建议。

### 三、怎么记住关键信息

<a id="q05"></a>
#### Q05｜Context Engineering 是什么？上下文太长怎么处理？

**短答：** 它决定每轮让模型看到什么信息、怎样组织、哪些暂时不放入。常用手段是按需检索、限制工具返回、去重、保留近期细节、压缩历史和保存结构化任务状态。完整会话记录可以存于上下文窗口之外；摘要负责索引与交接，需要时仍能找回原始证据。

**准备到位：** 画出自己的上下文分区：规则、用户最新要求、当前任务状态、近期交互、检索证据、必要工具定义。说明压缩时必须保留目标、已确认约束、未完成动作、失败信息及证据位置。

**继续追问：** 摘要丢了关键字段怎么办？保留可回查原件和稳定 ID，再用跨轮任务验证保真度；不能承诺“摘要天然无损”。

<a id="q06"></a>
#### Q06｜短期记忆、长期记忆如何设计？冲突和过期怎么办？

**短答：** 当前会话和执行状态通常属于短期范围；跨任务仍有价值的偏好、事实或经验可以进入长期记忆。每条记忆应有来源、作用域、时间、确认状态和撤销方式。检索先按用户、项目与权限过滤，再选择相关内容；当前明确要求可覆盖历史默认偏好，业务事实则需核对权威来源和有效时间。

**准备到位：** 解释“用户曾要求中文”“本次要求英文”和“数据库显示地址已变”分别怎么处理。说明 AI 建议未被接受时，为什么不能直接写成用户决定。

**继续追问：** 用户只说“同意”怎么办？要结合此前建议及对话指向解析，不能只从最后一句提取关键词。

本组岗位依据：[J01](来源核验.md#J01)、[J02](来源核验.md#J02)、[J05](来源核验.md#J05)。机制参考：[会话与上下文的区别](https://www.anthropic.com/engineering/managed-agents)、[官方记忆概念文档](https://docs.langchain.com/oss/python/concepts/memory)。

### 四、怎么分工与验收

<a id="q07"></a>
#### Q07｜为什么用多 Agent？什么时候一个 Agent 更合适？

**短答：** 多 Agent 可以支持相对独立的任务并行、专门的工具或上下文，以及独立评审，但也增加协调、重复检索、延迟和错误传播。判断应围绕任务能否拆分、共享状态是否复杂、结果是否容易验收；用同样任务和预算比较单/多 Agent 的质量与成本。

**准备到位：** 说明一个值得拆的边界和一个不值得拆的边界。继续已有调查的执行者可继承相关上下文；独立评审者需要成果和判定标准，未必需要继承原方案的全部推理。

**易错：** 对话上下文隔离不等于文件系统、数据库或工具权限也已隔离；多开角色不会自动形成独立判断。

<a id="q08"></a>
#### Q08｜怎样评测 Agent？“成功率”到底怎么定义？

**短答：** 一道评测题应包含用户任务、初始环境、可用工具与权限、成功条件和资源限制。最终成果、环境变化、交互质量和约束遵守可分别判定。多次试跑观察稳定性，并报告分母、任务分布、版本和预算；不能只看最终回答是否流畅。

**准备到位：** 写出三类题：正常完成、应澄清或拒绝、工具失败后恢复。每题说明看哪个实际证据判定；允许多种合法路径，只有必要的授权或业务规则才约束具体步骤。

**继续追问：** 多试几次总能成功，能叫稳定吗？“至少成功一次”和“每次都可靠”回答的是不同问题，需要分别报告。

本组岗位依据：[J01](来源核验.md#J01)、[J02](来源核验.md#J02)、[J04](来源核验.md#J04)、[J07](来源核验.md#J07)。机制参考：[9 月的多 Agent 上下文文章](https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness)、[Agent 评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

### 五、怎么判断与排错

<a id="q09"></a>
#### Q09｜LLM-as-a-Judge 可靠吗？怎样避免“自己给自己打高分”？

**短答：** 可执行、可查询的结果优先直接验证；语义质量用明确的评分规则让模型辅助判断，并用人工标注校准。判分器要拿到任务、必要上下文和约束，允许信息不足；检查错判通过、错判失败、顺序与表达风格偏差。优化者与判分过程保持独立，修改评分规则也要记录版本。

**准备到位：** 设计一个“回答很漂亮，但数据错了”的反例，解释为什么单一综合分可能掩盖关键失败，以及怎样设置必要条件。

**继续追问：** Judge 给低分一定是 Agent 差吗？也可能是题目不清、环境故障、缺少工具定义或判分规则错误，应回看证据。

<a id="q10"></a>
#### Q10｜Agent 答错了，你怎样定位根因？

**短答：** 先保留可复现的输入、模型与配置、工具及知识版本、运行环境，再沿 Trace 检查：目标理解 → 资料检索 → 决策/规划 → 工具选择与参数 → 执行 → 结果综合。找到最早可确认的偏离点，同时区分模型问题、工具/数据问题、状态问题和判分器问题。

**准备到位：** 选一个具体错误，说清哪条证据证明根因，改哪里，以及哪道回归题能防止再次发生。Trace 记录请求、参数、返回、状态与时延；不把猜测当成模型真实内部原因。

**继续追问：** 结果错了但所有工具都执行成功怎么办？检查工具是否适用、口径与条件是否正确、最终表达是否忠实于证据。

本组岗位依据：[J01](来源核验.md#J01)、[J03](来源核验.md#J03)、[J04](来源核验.md#J04)。机制参考：[评测与判分](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Google 的失败分析与专项指标案例](https://developers.googleblog.com/driving-the-agent-quality-flywheel-from-your-coding-agent/)。

### 六、怎么持续可靠地运行

<a id="q11"></a>
#### Q11｜长任务中断后怎么继续？怎样避免重复执行？

**短答：** 把任务状态和执行记录保存在可恢复存储中，记录任务标识、当前步骤、已完成成果、待处理调用、预算和版本。恢复时区分“未执行”“已执行”“结果未知”，再决定继续、重查、重试或人工介入；外部写操作需要业务幂等或对账机制。

**准备到位：** 画出“工具已产生效果，但系统还没存下成功结果就崩溃”的时序，解释重启后如何确认，而不是直接再次执行。

**易错：** 有 Checkpoint 不代表外部副作用自动只发生一次。内存保存器不能跨进程崩溃保存状态；重试策略也不能代替业务补偿。

<a id="q12"></a>
#### Q12｜你会怎样持续优化 Agent？“自迭代”具体改什么？

**短答：** 先从真实失败中选问题，固定任务与判定标准，再提出局部改动：Prompt、工具描述、检索、上下文策略、Skill、运行代码或模型。运行候选版本，与基线比较；在未参与优化的任务上检查收益和退化，再小范围验证并保留回退路径。

**准备到位：** 给出一条“失败 → 归因 → 改动 → 验证”的链，说明本轮到底改了哪一层。把记忆写入、改 Skill、改代码和训练权重分开说。

**继续追问：** 原来那几道错误题都对了，为什么还不能宣布成功？可能只适配了已见样本，也可能提高质量的代价是成本、延迟或其他能力退化。

本组岗位依据：[J01](来源核验.md#J01)、[J02](来源核验.md#J02)、[J05](来源核验.md#J05)、[J06](来源核验.md#J06)。机制参考：[状态持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[运行系统与会话记录](https://www.anthropic.com/engineering/managed-agents)、[改进闭环](https://developers.googleblog.com/driving-the-agent-quality-flywheel-from-your-coding-agent/)。

### 工具与知识：Q13—Q16

<a id="q13"></a>
#### Q13｜Function Calling、MCP、Tool、Skill 有什么区别？

**回答骨架：** Tool 是可执行能力；Function Calling 是模型输出工具选择和参数的一类接口机制；MCP 标准化应用与工具/资源服务之间的交互；Skill 组织可按需加载的任务方法、说明和资源。它们可以组合，不能互相替代。MCP 不负责替你设计 Agent 的全部循环，Skill 也不会自动赋予访问权限。

**准备一个例子：** 一个查询函数由 MCP Server 暴露，Host 获取定义供模型选择；分析 Skill 告诉 Agent 什么时候查、查后怎么分析。

**进阶边界：** MCP 的握手与发现机制要按具体协议版本回答。本轮核对的是 2026-07-28 版本，不能直接照搬旧版本的连接流程。参考：[MCP 架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)、[Skill 规范](https://agentskills.io/specification)。岗位依据：J02、J03、J08。

<a id="q14"></a>
#### Q14｜工具或 Skill 有几百个，怎么选、怎么加载？

**回答骨架：** 先按权限与场景过滤，再按名称、描述或检索缩小候选，最后让模型选择。Skill 可先加载名称和触发描述，选中后读正文，细节资源再按需访问。还要处理同义工具、工具版本变动、检索漏选和找不到可用能力。

**准备一个例子：** 区分“工具候选没召回”和“候选已给出但模型选错”两类问题；分别测候选覆盖、误调用、任务完成率与成本。工具少时，复杂检索层未必值得引入。

参考：[渐进加载规范](https://agentskills.io/specification)、[2026 年按需工具与成本实践](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)。岗位依据：J03、J06、J08。

<a id="q15"></a>
#### Q15｜普通 RAG 与 Agentic RAG 有什么区别？检索效果差怎么处理？

**回答骨架：** 固定 RAG 通常按预设链路检索后生成；Agentic RAG 允许系统动态决定是否查、查什么来源、是否改写或继续检索。先定位知识缺失、召回遗漏、排序失误还是生成不忠实，再选择修复措施。并非增加一次反思就一定更好。

**准备一个例子：** 专有词适合精确匹配，语义改写需要语义检索；混合召回与重排也要比较收益。说明文档解析、切分、元信息、权限、更新与引用分别在哪一步生效。

**边界：** 本轮保留它作为 Agent 获取知识的手段；向量索引底层和 GraphRAG 算法全家桶不作为第一轮任务。参考：[官方检索指南](https://docs.langchain.com/oss/python/deepagents/retrieval)。岗位依据：J02、J03、J04。

<a id="q16"></a>
#### Q16｜怎么证明上下文压缩和记忆有帮助？

**回答骨架：** 同一批跨轮任务分别使用原策略和新策略，观察约束保持、关键事实回忆、任务成功、错误记忆使用、隐私隔离及成本。构造“很早给出关键要求，后来发生修正”的题，检查能否恢复正确状态。不要用摘要读起来顺不顺作为唯一标准。

**准备一个例子：** 原要求只查某区域，后续又改了日期；看压缩后是否保留两个约束，以及相邻任务会不会错误复用。这个实验是建议设计，尚未代用户运行。

参考：[记忆写入与检索的取舍](https://docs.langchain.com/oss/python/concepts/memory)、[用户变更的专项评测](https://developers.googleblog.com/driving-the-agent-quality-flywheel-from-your-coding-agent/)。岗位依据：J01、J02、J05。

### 协作与可靠性：Q17—Q20

<a id="q17"></a>
#### Q17｜多个 Agent 怎么通信、汇总状态和结束？

**回答骨架：** 任务消息应明确目标、输入、约束、交付物和完成条件；结果应包含状态、证据、失败原因及未完成项。共享数据由明确的写入规则处理，不能让多个角色随意覆盖。父任务负责依赖、预算、取消和汇总；失联、部分成功、过期结果都有对应状态。

**准备一个例子：** 两个查询并行、一个失败时，能否继续？两个结论冲突时，按证据与规则处理，必要时重新查或请人判断，不能只让第三个模型投票。

参考：[多 Agent 上下文设计](https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness)。岗位依据：J02、J04、J06。

<a id="q18"></a>
#### Q18｜工具超时、报错、脏数据时，什么时候重试、降级或转人工？

**回答骨架：** 区分暂时故障、参数问题、权限不足、业务拒绝和执行结果未知。暂时故障可有上限地退避重试；参数错误先修正；无权限不能用换工具绕过；写操作结果未知先查询或对账。降级必须说明结果损失，补偿要看业务是否可逆。

**准备一个例子：** “支付请求超时”和“天气查询超时”为什么不能用同一种重试逻辑？说明外部动作是否已发生，以及幂等键由谁保证。

岗位依据：J02、J04、J07；是依据岗位可靠性要求设计的工程场景题。

<a id="q19"></a>
#### Q19｜任务突然变慢、Token 成本增加，怎么分析？

**回答骨架：** 先拆等待、模型输入处理/生成、工具、循环次数和多 Agent 协调耗时，比较失败重试、检索量、输入长度与缓存命中。并行只用于没有依赖的部分；模型切换、上下文调整、缓存和预算优化都要同时看任务质量。

**准备一个例子：** 一次任务多了十轮，是信息不足导致反复查，还是工具一直失败？首先看 Trace，再决定减步骤、修工具或换模型。区分模型前缀缓存与业务结果缓存；后者还要处理时效与用户权限。

参考：[9 月成本与效果优化文章](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)。岗位依据：J03、J04、J05。

<a id="q20"></a>
#### Q20｜如何防止提示注入、越权操作和敏感信息泄漏？

**回答骨架：** 外部网页、文档和工具结果属于可能不可信的数据；其文字不能自行取得指令权限。工具服务按用户身份和资源范围鉴权，限制文件/网络/命令能力，凭证与不可信执行环境隔离。对高影响动作设计可审查的确认和审计，并测试实际越权路径。

**准备一个例子：** 网页要求把客户文件上传到外部地址，系统在哪几层阻断？不能只回答“Prompt 写禁止泄漏”；输出脱敏也覆盖不了工具直接外传。

参考：[2026 年运行环境与凭证隔离实践](https://www.anthropic.com/engineering/managed-agents)。岗位依据：J02、J04、J07。

### 人机协作、选型与交付：Q21—Q24

<a id="q21"></a>
#### Q21｜用户中途改要求、要求停止，系统怎么处理？

**回答骨架：** 先更新目标与任务版本，再决定哪些动作取消、哪些结果仍有效、哪些已发生的外部效果需说明或补偿。旧任务回包要检查是否仍适用于当前目标。审批等待应保存具体待批动作与参数；审批通过后也需确认对象或环境没有变化。

**准备一个例子：** 报告正在取数时用户改成另一月份；旧月份查询晚返回，怎样避免覆盖新结果？区分发出取消请求、执行确认停止、已经产生副作用三种状态。

参考：[中途变更是否被遵守的评测案例](https://developers.googleblog.com/driving-the-agent-quality-flywheel-from-your-coding-agent/)。岗位依据：J02、J04、J07。

<a id="q22"></a>
#### Q22｜怎么选模型？换更强模型一定能解决问题吗？

**回答骨架：** 用代表性任务比较指令遵循、工具调用、长上下文、必要模态、质量、延迟、费用与部署约束。错误也可能来自工具、数据或 Harness，不能全部归因于模型。升级后重新检查旧提示词和编排是否仍有价值，按任务需要选择推理预算。

**准备一个例子：** 如果两个模型最终正确率接近，但一个需要更多工具重试，怎样比较整条任务成本？温度设为零也不等于整套系统严格可复现。

参考：[模型变化后的运行策略调整](https://www.anthropic.com/engineering/managed-agents)、[成本与预算](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)。岗位依据：J02、J06、J07。

<a id="q23"></a>
#### Q23｜为什么用某个框架？换框架或自己写会失去什么？

**回答骨架：** 围绕模型/工具接入、状态、持久化、暂停恢复、可观测、部署与扩展比较。先说明实际需求，再解释框架提供的能力和你补的部分。以 LangGraph 为例，线程状态检查点与跨线程 Store 分别承担不同范围的信息保存；存储方案决定能否跨进程恢复。

**准备一个例子：** 说明一个框架 API 背后的机制；去掉这个 API 后需要补哪些代码。熟悉一个实际用过的框架即可，不要求把所有框架源码都读一遍。

参考：[LangGraph 持久化机制](https://docs.langchain.com/oss/python/langgraph/persistence)。岗位依据：J01、J02、J06。

<a id="q24"></a>
#### Q24｜讲一个你做过的 Agent：为什么做、你做了什么、怎样证明有用？

**回答骨架：** 用户与任务 → 原方法的限制 → 选择 Agent 的理由 → 实际链路 → 个人实现和依赖边界 → 一次失败及改进 → 有分母、有时间范围的效果证据。能讲清一个最小闭环，比列十个技术名词更能支撑后续追问。

**准备一份材料：** 一张实际架构图、一份工具定义、一个失败案例、一组有口径的效果数字。没有数据就说明没有；本地复现、目标设计和公司生产实现分开讲。

本题只提供组织结构。个人项目事实仍回到[项目准备](../../项目准备/README.md)，不从本页参考答案反向补造经历。岗位依据：J01—J08 的实际交付要求。

<a id="q25"></a>
### Q25｜Data Agent 怎样保证查询结果在业务上正确？

**回答骨架：** 明确任务与指标口径、时间、粒度和适用范围，找到可用数据或查询能力，校验参数与权限，执行后核对返回含义，报告保留来源和单位。生成 SQL 时还要检查关联关系、过滤条件、聚合口径与执行限制；SQL 能跑只证明语法和访问路径的一部分。

**准备一个例子：** 一个“查得到数据，但选错指标或粒度”的任务，如何发现和阻止？这是基于 [J05](来源核验.md#J05) 数据智能交付要求设计的专项，不是已确认原题或个人事故记录。

<a id="q26"></a>
### Q26｜Data Agent 为什么需要领域知识或图谱？什么时候普通检索就够？

**回答骨架：** 先列要表达的实体、关系、定义和适用性。稳定的规则与查询映射可以直接结构化维护；需要跨实体关系检索或多跳路径时再评估图谱收益。向量相似不自动表达业务关系；引入图谱也带来构建、更新、冲突与评测成本。

**准备一个例子：** 用户说法相似但适用指标不同，或两个实体相关却不相似；解释你需要的是同义检索、明确映射还是关系推理。岗位依据：[J05 图谱与知识挖掘](来源核验.md#J05)，例子为 Codex 扩展。

<a id="q27"></a>
### Q27｜如何设计一个能修改代码并验证成果的 Coding Agent？

**回答骨架：** 为模型提供受控的文件读取、搜索、编辑和命令执行能力，明确工作目录与约束；小步修改，检查差异，运行相关验证，记录失败后修正。长任务维护当前目标、已有改动和待办；多执行者要明确文件/分支的写入责任和合并验证。

**准备一个例子：** 测试通过但修复了错误需求，或 Agent 修改测试掩盖缺陷，验收怎么识别？“会使用 AI 编码工具”与“开发过 Coding Agent”是不同经历。岗位依据：[J06](来源核验.md#J06)、[J07](来源核验.md#J07)。

<a id="q28"></a>
### Q28｜调研或办公 Agent 怎样做到有证据、可交付，而不是只生成长文本？

**回答骨架：** 先定义交付物与检查标准，再获取有时间和来源的材料，区分事实、推断和未知；生成时保留引用或对象标识，交付前核对关键结论及真实文件/系统状态。停止条件围绕需求是否满足、还有哪些关键缺口与剩余预算，不以篇幅为准。

**准备一个例子：** 文档内容正确但表格被改坏，或引用页面并不支持结论，如何判分？岗位依据：[J03 办公场景](来源核验.md#J03)、[J04 企业知识场景](来源核验.md#J04)；调研例子为场景扩展。

<a id="q29"></a>
### Q29｜如何比较两个 Agent/Harness，避免基准分数误导？

**回答骨架：** 固定任务、环境、工具、预算和可比的模型配置；记录版本与重复尝试，分别报告完成质量、稳定性、关键违规、时延与成本。检查数据泄漏、环境残留、判分器错误和任务代表性。公开基准只测特定能力，不能直接等同业务收益。

**准备一个例子：** A 允许十次重试，B 只一次；分数高是否说明 A 的设计更好？能先指出比较条件，再设计公平对照。岗位依据：[J01](来源核验.md#J01)、[J06](来源核验.md#J06)、[J07](来源核验.md#J07)。

<a id="q30"></a>
### Q30｜什么时候需要 SFT 或 Agentic RL，而不是继续改 Prompt/Harness？

**回答骨架：** 先定位是否为模型能力/行为的系统性缺口，并确认任务、工具、数据和判分本身可靠。SFT 利用示范行为，RL 利用奖励反馈优化策略；都要有合适的数据、独立评测和训练预算。改记忆、改 Skill 或语言反思通常不等于更新模型权重。

**准备到位：** 能说明轨迹来源、奖励对应的实际目标、留出任务和奖励投机风险。只有 JD 明确以训练为主要职责时，才进一步准备具体算法推导；本页不声称覆盖 Agent 算法岗全套知识。

岗位依据：[J02 的训练优化职责](来源核验.md#J02)、[字节 AI Platform 算法岗位](https://jobs.bytedance.com/experienced/position/7599598898747656453/detail)。

## 怎样判断自己准备好了

每道题按三个动作检验，暂不自动写入掌握状态：

1. **讲机制：** 不看材料，用约一分钟说清问题、实现方式和边界。
2. **落到例子：** 用自己的真实项目，或明确标为教学的例子，说明输入、状态、工具、结果与证据。
3. **接住失败：** 回答“这一步错了怎么办”，给出定位和验证方法。

第一轮可复用的材料只有四份：**实际架构图、一个工具契约、一段失败及恢复过程、一组可判分任务。** 同一份材料可以支撑多个问题，不必为 30 题各造一个项目。

本轮不展开：Java/JVM/JUC、Redis/MySQL/Kafka 底层、网络与操作系统全套、分布式资源调度、传统数仓组件、与 Agent 无关的手撕题。目标 JD 或面试通知明确要求时，再单独补充；这不构成“大厂一定不考基础”的保证。
