整理：Codex｜日期：2026-09-15｜用途：数据开发 SQL 手撕与口述复习

本文包含 **19 类题型、29 段完整参考 SQL**。题目和样例为学习用途编写或改编，不代表某公司真题频次，也不记录个人掌握状态。每一节都能独立阅读；表名在不同题中重复时，按该题自己的字段和样例建表。

## 怎么用

1. 先读“题目与口径”和样例，自己口述：输入一行是什么、输出一行是什么。
2. 写出各层步骤，再看参考 SQL。查询层数服务于正确的数据粒度，不把层数少直接等同于性能好。
3. 用预期结果核对，再检查该题的反例和边界。提交成功与独立理解分别判断。

### 统一约定

- **使用 Hive SQL，面向 Hive 3.1+/4.x 的常用语法，不使用 `WITH AS`。** 力扣通常使用其提供的数据库方言；链接是练习入口，本文 SQL 不保证不改写就能直接提交。
- 日期字符串统一 `yyyy-MM-dd`；时间字符串统一 `yyyy-MM-dd HH:mm:ss`，采用同一业务时区。日期运算使用日期函数，标准格式字符串排序可按时间先后解释。
- 除题目明确允许 NULL 的字段外，主键、关联键、日期时间和金额均非空且有效；已清除无效格式。是否允许重复，由每题单独说明。
- 小样例中的日期是数据，查询不写死某一天。1000 元、7 天、Top10 等是题面给定阈值。
- 每节表结构表已经给出列名、Hive 类型与含义；紧随其后的样例表就是输入。金额与比例显示的小数位不改变数值含义。
- 默认给出可解释的通用答案。生产执行还要按业务时间范围裁剪分区，并检查 Join、排序、去重与热点分组的代价。

## 01. 条件聚合：每日订单与支付指标

**练习链接与对应关系：** 相近练习：[1193. 每月交易 I](https://leetcode.cn/problems/monthly-transactions-i/)。原题按月份、国家聚合；本文改成每日订单指标，增加去重用户数。

### 题目与口径

订单表一行代表一笔订单。按下单自然日输出订单数、支付成功订单数、支付成功用户数、支付成功金额、订单支付成功率。
`status` 只有 `paid`、`unpaid`、`cancelled`；只有 `paid` 计入成功。成功率=成功订单数/全部订单数，取消单也在分母中。金额为非负数，结果比例为 0～1 小数，保留 4 位。
只输出有订单的日期；支付人数按用户去重，不是成功订单数。日期均按下单时间，不能解释成按实际支付时间统计。

**输入表 `order_log`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单唯一键 |
| user_id | STRING | 用户 |
| order_time | STRING | 下单时间 |
| amount | DECIMAL(18,2) | 订单金额 |
| status | STRING | 订单状态 |

**样例数据：**

| order_id | user_id | order_time | amount | status |
| --- | --- | --- | --- | --- |
| 1 | U1 | 2026-09-01 09:00:00 | 100 | paid |
| 2 | U1 | 2026-09-01 10:00:00 | 50 | paid |
| 3 | U2 | 2026-09-01 11:00:00 | 80 | unpaid |
| 4 | U3 | 2026-09-01 12:00:00 | 20 | cancelled |
| 5 | U2 | 2026-09-02 09:00:00 | 60 | unpaid |

### 记住的步骤

1. `日期 ← TO_DATE(下单时间)`
2. `按日期分组：全部订单 COUNT；成功订单条件 SUM；成功用户条件 COUNT DISTINCT；成功金额条件 SUM`
3. `成功率 ← 成功订单数 / 全部订单数`

### 参考答案

```sql
-- Q01
SELECT TO_DATE(order_time) AS dt,
       COUNT(*) AS order_count,
       SUM(IF(status = 'paid', 1, 0)) AS paid_order_count,
       COUNT(DISTINCT IF(status = 'paid', user_id, NULL)) AS paid_user_count,
       SUM(IF(status = 'paid', amount, 0)) AS paid_amount,
       ROUND(SUM(IF(status = 'paid', 1, 0)) * 1.0 / COUNT(*), 4) AS paid_rate
FROM order_log
GROUP BY TO_DATE(order_time)
ORDER BY dt;
```

**预期结果：**

| dt | order_count | paid_order_count | paid_user_count | paid_amount | paid_rate |
| --- | --- | --- | --- | --- | --- |
| 2026-09-01 | 4 | 2 | 1 | 150 | 0.5000 |
| 2026-09-02 | 1 | 0 | 0 | 0 | 0 |

### 为什么这样写／容易错在哪里

- 不能先 `WHERE status='paid'`，否则失败订单消失，分母被改成成功订单数。
- 未成功的用户用 NULL 参与 `COUNT(DISTINCT ...)`；不能填 0，否则可能额外算出一个“用户”。
- 本题每个输出组至少有一笔订单，分母不会为 0。若要求无订单日期也输出，要补日期表并重新处理零分母。
- 金额已是一单一行。如果输入是商品明细，先处理订单粒度，再计算订单数和订单金额。

## 02. 未匹配关联：访问但未交易

**练习链接与对应关系：** 对应练习：[1581. 进店却未进行过交易的顾客](https://leetcode.cn/problems/customer-who-visited-but-did-not-make-any-transactions/)。本文使用自建简化样例。

### 题目与口径

`visit` 一行是一次访问，`trade` 一行是访问中发生的一笔交易。一场访问可以有多笔交易。
找出有“未发生任何交易的访问”的用户，统计各自未交易访问次数。一个用户有其他已交易访问，也仍可入选。
输出一行代表一个用户；只返回未交易次数大于 0 的用户。

**输入表 `visit`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| visit_id | BIGINT | 访问唯一键 |
| user_id | STRING | 用户 |

**样例数据：**

| visit_id | user_id |
| --- | --- |
| 1 | U1 |
| 2 | U1 |
| 3 | U2 |
| 4 | U3 |

**输入表 `trade`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| trade_id | BIGINT | 交易唯一键 |
| visit_id | BIGINT | 所属访问 |
| amount | DECIMAL(18,2) | 交易额 |

**样例数据：**

| trade_id | visit_id | amount |
| --- | --- | --- |
| 11 | 1 | 30 |
| 12 | 1 | 40 |
| 13 | 4 | 20 |

### 记住的步骤

1. `访问表作为保留侧，按 visit_id 左关联交易表`
2. `筛选交易唯一键为空的访问`
3. `按用户 COUNT(*)，得到未交易访问次数`

### 参考答案

```sql
-- Q02
SELECT v.user_id, COUNT(*) AS no_trade_visits
FROM visit v
LEFT JOIN trade t ON v.visit_id = t.visit_id
WHERE t.trade_id IS NULL
GROUP BY v.user_id
ORDER BY v.user_id;
```

**预期结果：**

| user_id | no_trade_visits |
| --- | --- |
| U1 | 1 |
| U2 | 1 |

### 为什么这样写／容易错在哪里

- 按 `visit_id` 匹配，不能仅按用户关联。U1 有一次已交易访问，也有一次未交易访问。
- 用右侧非空唯一键判断未匹配；不能用允许为空的金额判断。
- 若题目改成“从来没有交易的用户”，需要在用户层面判断是否存在交易，当前 SQL 不适用。
- `NOT IN` 的子查询含 NULL 时可能使结果不符合预期；面试时优先明确空值约束，或使用相应的 `NOT EXISTS` 写法。

## 03. 多表关联：避免订单金额重复累计

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目与口径

`orders` 一行代表一个订单；`order_item` 一行代表一种商品明细；`refund` 一行代表一次退款。一个订单可有多个商品明细和多次退款，关联键均有效。
按用户输出订单总额、购买件数、退款总额和净金额。购买件数是明细数量之和，不扣除退货件数；净金额=订单总额−退款总额。无退款按 0 处理。
只统计 orders 中的订单。订单金额以 orders.amount 为准，不能从商品表猜测。

**输入表 `orders`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单唯一键 |
| user_id | STRING | 用户 |
| amount | DECIMAL(18,2) | 整单金额 |

**样例数据：**

| order_id | user_id | amount |
| --- | --- | --- |
| 1 | U1 | 100 |
| 2 | U1 | 50 |
| 3 | U2 | 100 |

**输入表 `order_item`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| item_id | BIGINT | 明细唯一键 |
| order_id | BIGINT | 订单 |
| quantity | BIGINT | 购买数量 |

**样例数据：**

| item_id | order_id | quantity |
| --- | --- | --- |
| 11 | 1 | 1 |
| 12 | 1 | 2 |
| 13 | 2 | 1 |
| 14 | 3 | 1 |

**输入表 `refund`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| refund_id | BIGINT | 退款唯一键 |
| order_id | BIGINT | 订单 |
| refund_amount | DECIMAL(18,2) | 退款额 |

**样例数据：**

| refund_id | order_id | refund_amount |
| --- | --- | --- |
| 21 | 1 | 20 |
| 22 | 1 | 10 |
| 23 | 3 | 5 |

### 记住的步骤

1. `商品明细按订单汇总件数；退款明细按订单汇总退款额`
2. `订单 LEFT JOIN 两张订单粒度汇总表`
3. `按用户 SUM 金额、件数和退款额；计算净额`

### 参考答案

```sql
-- Q03
SELECT o.user_id,
       SUM(o.amount) AS order_amount,
       SUM(COALESCE(i.item_count, 0)) AS item_count,
       SUM(COALESCE(r.refund_amount, 0)) AS refund_amount,
       SUM(o.amount) - SUM(COALESCE(r.refund_amount, 0)) AS net_amount
FROM orders o
LEFT JOIN (
    SELECT order_id, SUM(quantity) AS item_count
    FROM order_item GROUP BY order_id
) i ON o.order_id = i.order_id
LEFT JOIN (
    SELECT order_id, SUM(refund_amount) AS refund_amount
    FROM refund GROUP BY order_id
) r ON o.order_id = r.order_id
GROUP BY o.user_id
ORDER BY o.user_id;
```

**预期结果：**

| user_id | order_amount | item_count | refund_amount | net_amount |
| --- | --- | --- | --- | --- |
| U1 | 150 | 4 | 30 | 120 |
| U2 | 100 | 1 | 5 | 95 |

### 为什么这样写／容易错在哪里

- 订单 1 有两条商品、两条退款。直接把三张明细表关联，会得到 2×2=4 行，整单金额变成 400。
- 最后 `DISTINCT` 不能可靠修复金额；`SUM(DISTINCT amount)` 也不对，因为不同订单可能金额相同。
- 两个子查询都输出“一单一行”，连接后仍然“一单一行”，此时才可以安全累计订单金额。
- 先聚合还能缩小关联输入，但实际性能要看执行计划和数据倾斜。

## 04. 排名与 Top N：前三档工资、第二高工资

**练习链接与对应关系：** 对应题型：[185. 部门工资前三高的所有员工](https://leetcode.cn/problems/department-top-three-salaries/)（本文用部门 ID 展示，省去部门名关联）；[176. 第二高的薪水](https://leetcode.cn/problems/second-highest-salary/)。

### 题目与口径

题 A：输出各部门工资最高的三个不同档位中的所有员工。并列员工全部保留；不足三档则全部返回；NULL 工资不参与。
题 B：求全公司第二高的不同工资，输出恰好一行。没有第二个不同工资时，这一行的结果必须为 NULL。

**输入表 `employee`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| emp_id | BIGINT | 员工唯一键 |
| dept_id | STRING | 部门 |
| salary | DECIMAL(18,2) | 工资，可为 NULL |

**样例数据：**

| emp_id | dept_id | salary |
| --- | --- | --- |
| 1 | A | 100 |
| 2 | A | 90 |
| 3 | A | 90 |
| 4 | A | 80 |
| 5 | A | 70 |
| 6 | B | 40 |
| 7 | B | NULL |

### 记住的步骤

1. `过滤 NULL 工资`
2. `A：按部门分区、仅按工资降序 DENSE_RANK；外层筛排名≤3`
3. `B：全公司按工资降序 DENSE_RANK；筛排名=2 后用无 GROUP BY 的 MAX 保证空集也返回一行`

### 答案 A：每部门前三档

```sql
-- Q04A
SELECT dept_id, emp_id, salary, salary_rank
FROM (
    SELECT dept_id, emp_id, salary,
           DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS salary_rank
    FROM employee WHERE salary IS NOT NULL
) t
WHERE salary_rank <= 3
ORDER BY dept_id, salary DESC, emp_id;
```

**预期结果：**

| dept_id | emp_id | salary | salary_rank |
| --- | --- | --- | --- |
| A | 1 | 100 | 1 |
| A | 2 | 90 | 2 |
| A | 3 | 90 | 2 |
| A | 4 | 80 | 3 |
| B | 6 | 40 | 1 |

### 答案 B：全公司第二高

```sql
-- Q04B
SELECT MAX(salary) AS second_highest_salary
FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS salary_rank
    FROM employee WHERE salary IS NOT NULL
) t
WHERE salary_rank = 2;
```

**预期结果：**

| second_highest_salary |
| --- |
| 90 |

### 为什么这样写／容易错在哪里

- `ROW_NUMBER` 每行不同；`RANK` 并列同名次且后续跳号；`DENSE_RANK` 并列同名次且不跳号。
- A 要三个工资档，用 DENSE_RANK。若要最多三名员工，用 ROW_NUMBER 并加 emp_id 打破并列；若要“前三个位置及其并列”，用 RANK。
- DENSE_RANK 的窗口排序不能额外加 emp_id，否则同工资不再并列。最终展示排序可以加 emp_id。
- B 的外层 MAX 用来把零行变成一行 NULL，同时合并第二档的多名员工；不是在原表直接 MAX 求第二高。

## 05. 每组首末记录：最新状态与首次支付订单

**练习链接与对应关系：** 首单类相近练习：[1174. 即时食物配送 II](https://leetcode.cn/problems/immediate-food-delivery-ii/)。原题在用户首单上统计即时配送比例，本文练习取首条完整记录。

### 题目与口径

题 A：订单状态日志中，一个订单有多次状态变化。取每个订单最新的一条完整状态记录；时间相同时，以更大的 log_id 为最新。
题 B：从支付订单表中取每个用户的第一笔成功支付订单及其金额。按 pay_time 升序，时间相同时取 order_id 较小的一笔；从未成功支付的用户不输出。
两个问题都要保留该条记录的其他字段，不能把“最大时间”和“最大状态值”各自拼起来。

**输入表 `order_status_log`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| log_id | BIGINT | 日志唯一键 |
| order_id | BIGINT | 订单 |
| update_time | STRING | 状态更新时间 |
| status | STRING | 状态 |

**样例数据：**

| log_id | order_id | update_time | status |
| --- | --- | --- | --- |
| 1 | 101 | 2026-09-01 09:00:00 | created |
| 2 | 101 | 2026-09-01 10:00:00 | paid |
| 3 | 101 | 2026-09-01 10:00:00 | refunded |
| 4 | 102 | 2026-09-01 09:00:00 | created |

**输入表 `purchase_order`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单唯一键 |
| user_id | STRING | 用户 |
| pay_time | STRING | 支付时间；非 paid 行的值不用于计算 |
| amount | DECIMAL(18,2) | 订单额 |
| status | STRING | paid 或 cancelled |

**样例数据：**

| order_id | user_id | pay_time | amount | status |
| --- | --- | --- | --- | --- |
| 1 | U1 | 2026-09-01 09:00:00 | 100 | paid |
| 2 | U1 | 2026-09-05 10:00:00 | 50 | paid |
| 3 | U2 | 2026-09-03 09:00:00 | 70 | paid |
| 4 | U3 | 2026-09-03 10:00:00 | 40 | cancelled |
| 5 | U1 | 2026-10-01 09:00:00 | 20 | paid |

### 记住的步骤

1. `先明确只在有效订单中找，还是在全部状态日志中找`
2. `按业务键分区，时间＋稳定唯一键排序，生成 ROW_NUMBER`
3. `外层筛 rn=1，保留完整记录`

### 答案 A：最新状态

```sql
-- Q05A
SELECT order_id, log_id, update_time, status
FROM (
    SELECT order_id, log_id, update_time, status,
           ROW_NUMBER() OVER (
               PARTITION BY order_id ORDER BY update_time DESC, log_id DESC
           ) AS rn
    FROM order_status_log
) t
WHERE rn = 1
ORDER BY order_id;
```

**预期结果：**

| order_id | log_id | update_time | status |
| --- | --- | --- | --- |
| 101 | 3 | 2026-09-01 10:00:00 | refunded |
| 102 | 4 | 2026-09-01 09:00:00 | created |

### 答案 B：首次支付订单

```sql
-- Q05B
SELECT user_id, order_id, pay_time, amount
FROM (
    SELECT user_id, order_id, pay_time, amount,
           ROW_NUMBER() OVER (
               PARTITION BY user_id ORDER BY pay_time, order_id
           ) AS rn
    FROM purchase_order WHERE status = 'paid'
) t
WHERE rn = 1
ORDER BY user_id;
```

**预期结果：**

| user_id | order_id | pay_time | amount |
| --- | --- | --- | --- |
| U1 | 1 | 2026-09-01 09:00:00 | 100 |
| U2 | 3 | 2026-09-03 09:00:00 | 70 |

### 为什么这样写／容易错在哪里

- A 按时间倒序；B 按时间升序。仅背“rn=1”不够，要解释排序方向。
- 用最大时间回连原表，遇到同一时刻多条记录可能返回多行；题面要求一条时要指定裁决规则。
- `MAX(status)` 是状态字符串的大小，不等于最新状态。
- B 查的是完整输入历史中的首笔成功支付；不能先只截取最近一个月，再称为历史首单。

## 06. 留存：按首登日期计算次日与 7 日留存

**练习链接与对应关系：** 基础练习：[550. 游戏玩法分析 IV](https://leetcode.cn/problems/game-play-analysis-iv/)。本文扩展为按首登日分组、多周期与观察期判断。

### 题目与口径

`login_log` 保存截至 as_of_date 的完整登录历史，允许同一天多次登录；所有输入登录日期均不晚于该截止日。`report_config` 恰好一行，表示数据已完整到哪一个自然日。
按首次登录日期输出新增用户数、次日留存人数和留存率、7 日留存人数和留存率。第 N 日留存指首登日期加 N 个自然日当天再次登录。
分母都是该首登日的新增用户数。观察日尚未到达时，对应留存人数和比例都返回 NULL；到达且无人回访时返回 0。比例保留 4 位。

**输入表 `login_log`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | STRING | 用户 |
| login_dt | STRING | 登录日期 |

**样例数据：**

| user_id | login_dt |
| --- | --- |
| U1 | 2026-09-01 |
| U1 | 2026-09-02 |
| U1 | 2026-09-02 |
| U1 | 2026-09-08 |
| U2 | 2026-09-01 |
| U2 | 2026-09-03 |
| U3 | 2026-09-03 |
| U3 | 2026-09-04 |
| U4 | 2026-09-08 |

**输入表 `report_config`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| as_of_date | STRING | 数据完整截止日 |

**样例数据：**

| as_of_date |
| --- |
| 2026-09-08 |

### 记住的步骤

1. `按用户 MIN(login_dt)，确定首登日期；按用户＋登录日对活跃记录去重`
2. `首登用户左关联其首登后第 1、7 日的活跃记录`
3. `按首登日：分母 COUNT DISTINCT 用户；分子 SUM(对应日期命中标志)`
4. `用截止日检查观察期，未成熟时返回 NULL`

### 参考答案

```sql
-- Q06
SELECT a.first_dt,
       COUNT(DISTINCT a.user_id) AS new_users,
       IF(DATEDIFF(p.as_of_date, a.first_dt) >= 1,
          SUM(IF(DATEDIFF(b.login_dt, a.first_dt) = 1, 1, 0)), NULL) AS d1_users,
       IF(DATEDIFF(p.as_of_date, a.first_dt) >= 1,
          ROUND(SUM(IF(DATEDIFF(b.login_dt, a.first_dt) = 1, 1, 0))
                * 1.0 / COUNT(DISTINCT a.user_id), 4), NULL) AS d1_rate,
       IF(DATEDIFF(p.as_of_date, a.first_dt) >= 7,
          SUM(IF(DATEDIFF(b.login_dt, a.first_dt) = 7, 1, 0)), NULL) AS d7_users,
       IF(DATEDIFF(p.as_of_date, a.first_dt) >= 7,
          ROUND(SUM(IF(DATEDIFF(b.login_dt, a.first_dt) = 7, 1, 0))
                * 1.0 / COUNT(DISTINCT a.user_id), 4), NULL) AS d7_rate
FROM (
    SELECT user_id, MIN(login_dt) AS first_dt
    FROM login_log GROUP BY user_id
) a
CROSS JOIN report_config p
LEFT JOIN (
    SELECT DISTINCT user_id, login_dt FROM login_log
) b ON a.user_id = b.user_id
   AND DATEDIFF(b.login_dt, a.first_dt) IN (1, 7)
GROUP BY a.first_dt, p.as_of_date
ORDER BY a.first_dt;
```

**预期结果：**

| first_dt | new_users | d1_users | d1_rate | d7_users | d7_rate |
| --- | --- | --- | --- | --- | --- |
| 2026-09-01 | 2 | 1 | 0.5000 | 1 | 0.5000 |
| 2026-09-03 | 1 | 1 | 1 | NULL | NULL |
| 2026-09-08 | 1 | NULL | NULL | NULL | NULL |

### 为什么这样写／容易错在哪里

- 右侧用户日已经去重，每个用户在第 1 日最多匹配一行、第 7 日最多匹配一行，因此各分子可以直接条件 SUM。
- 一个用户可以同时匹配第 1、7 日，分母仍要 COUNT DISTINCT，不能 COUNT(*)。
- 日期条件放在 ON 中保留未回访用户；放到外层 WHERE 会丢掉分母中的未留存用户。
- 用户首次登录时间各不相同，SQL 没有写死一个统一起始日。as_of_date 是数据完整截止日，也不能简单用最大有事件日期代替。
- 全历史首登通常由增量首访表维护。只读统计窗口中的登录记录会把老用户误判成新用户。
- 跨首登日合并留存率，应对观察期已成熟的人群先汇总分子分母，再相除。

## 07. 复购：月内复购率与首购到二购间隔

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目与口径

输入 purchase_order 一单一行、包含完整历史，字段与样例在本节重列。
题 A：按支付月份统计购买用户数、当月至少成功支付两单的用户数、复购率。两单可以在同一天；取消单不计；月份采用支付时间，只输出有成功订单的月份。
题 B：对至少成功支付两单的用户，输出首购日期、二购日期和相隔自然日数。按完整支付时间、order_id 排序；同一天两单的间隔为 0。

**输入表 `purchase_order`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单唯一键 |
| user_id | STRING | 用户 |
| pay_time | STRING | 支付时间；非 paid 行的值不用于计算 |
| amount | DECIMAL(18,2) | 订单额 |
| status | STRING | paid 或 cancelled |

**样例数据：**

| order_id | user_id | pay_time | amount | status |
| --- | --- | --- | --- | --- |
| 1 | U1 | 2026-09-01 09:00:00 | 100 | paid |
| 2 | U1 | 2026-09-05 10:00:00 | 50 | paid |
| 3 | U2 | 2026-09-03 09:00:00 | 70 | paid |
| 4 | U3 | 2026-09-03 10:00:00 | 40 | cancelled |
| 5 | U1 | 2026-10-01 09:00:00 | 20 | paid |

### 记住的步骤

1. `过滤 status=paid`
2. `A：按月份＋用户 COUNT 订单，再按月份统计用户数及次数≥2的人数`
3. `B：按用户对有效订单排序；保留前两单；条件取首日、二购日并 DATEDIFF`

### 答案 A：月内复购率

```sql
-- Q07A
SELECT pay_month, COUNT(*) AS buyers,
       SUM(IF(order_count >= 2, 1, 0)) AS repeat_buyers,
       ROUND(SUM(IF(order_count >= 2, 1, 0)) * 1.0 / COUNT(*), 4) AS repeat_rate
FROM (
    SELECT SUBSTR(pay_time, 1, 7) AS pay_month, user_id, COUNT(*) AS order_count
    FROM purchase_order WHERE status = 'paid'
    GROUP BY SUBSTR(pay_time, 1, 7), user_id
) t
GROUP BY pay_month ORDER BY pay_month;
```

**预期结果：**

| pay_month | buyers | repeat_buyers | repeat_rate |
| --- | --- | --- | --- |
| 2026-09 | 2 | 1 | 0.5000 |
| 2026-10 | 1 | 0 | 0 |

### 答案 B：首购到二购

```sql
-- Q07B
SELECT user_id,
       MIN(IF(rn = 1, TO_DATE(pay_time), NULL)) AS first_dt,
       MIN(IF(rn = 2, TO_DATE(pay_time), NULL)) AS second_dt,
       DATEDIFF(MIN(IF(rn = 2, TO_DATE(pay_time), NULL)),
                MIN(IF(rn = 1, TO_DATE(pay_time), NULL))) AS gap_days
FROM (
    SELECT user_id, pay_time,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY pay_time, order_id) AS rn
    FROM purchase_order WHERE status = 'paid'
) t
WHERE rn <= 2
GROUP BY user_id
HAVING COUNT(*) = 2
ORDER BY user_id;
```

**预期结果：**

| user_id | first_dt | second_dt | gap_days |
| --- | --- | --- | --- |
| U1 | 2026-09-01 | 2026-09-05 | 4 |

### 为什么这样写／容易错在哪里

- 月内两次购买、历史老客再次购买、首购后 30 日内复购，是不同指标，不能共用同一个分母和时间过滤。
- 若输入是订单商品明细，必须先按 order_id 去重或汇总，不能把两件商品当两笔订单。
- 本题按订单次数统计；若改为至少两个购买日，需要按日期去重。
- B 先过滤成功订单再排序；否则取消单可能挤占第一、第二的位置。

## 08. 累计计算：首次累计消费达到 1000 元

**练习链接与对应关系：** 累计窗口相近练习：[1204. 最后一个能进入巴士的人](https://leetcode.cn/problems/last-person-to-fit-in-the-bus/)。原题累加排队体重，本文累加消费金额。

### 题目与口径

输入为完整统计范围内的成功支付订单，一单一行，金额严格大于 0。累计从输入中每个用户的第一笔订单开始，不包含范围外的期初余额。
题 A：输出每个用户有支付日期的当日金额、累计金额。题 B：输出每个支付用户首次在日末累计达到或超过 1000 元的日期，未达标返回 NULL。
结果按天判断，不要求定位当天第几笔达标；1000 是题目阈值，日期不写死。

**输入表 `payment_order`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| order_id | BIGINT | 订单唯一键 |
| user_id | STRING | 用户 |
| pay_time | STRING | 支付时间 |
| amount | DECIMAL(18,2) | 正金额 |

**样例数据：**

| order_id | user_id | pay_time | amount |
| --- | --- | --- | --- |
| 1 | U1 | 2026-09-01 09:00:00 | 400 |
| 2 | U1 | 2026-09-01 10:00:00 | 200 |
| 3 | U1 | 2026-09-02 09:00:00 | 500 |
| 4 | U2 | 2026-09-01 09:00:00 | 800 |

### 记住的步骤

1. `先汇总到用户＋日期，一行代表用户一天`
2. `按用户和日期累计 SUM(day_amount)`
3. `条件 MIN：在累计≥1000的日期中取最早一天；保留未达标用户`

### 答案 A：每日累计

```sql
-- Q08A
SELECT user_id, dt, day_amount,
       SUM(day_amount) OVER (
           PARTITION BY user_id ORDER BY dt
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS cumulative_amount
FROM (
    SELECT user_id, TO_DATE(pay_time) AS dt, SUM(amount) AS day_amount
    FROM payment_order GROUP BY user_id, TO_DATE(pay_time)
) d
ORDER BY user_id, dt;
```

**预期结果：**

| user_id | dt | day_amount | cumulative_amount |
| --- | --- | --- | --- |
| U1 | 2026-09-01 | 600 | 600 |
| U1 | 2026-09-02 | 500 | 1100 |
| U2 | 2026-09-01 | 800 | 800 |

### 答案 B：首次达标日期

```sql
-- Q08B
SELECT user_id, MIN(IF(cumulative_amount >= 1000, dt, NULL)) AS first_reach_dt
FROM (
    SELECT user_id, dt, day_amount,
           SUM(day_amount) OVER (
               PARTITION BY user_id ORDER BY dt
               ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
           ) AS cumulative_amount
    FROM (
        SELECT user_id, TO_DATE(pay_time) AS dt, SUM(amount) AS day_amount
        FROM payment_order GROUP BY user_id, TO_DATE(pay_time)
    ) d
) t
GROUP BY user_id ORDER BY user_id;
```

**预期结果：**

| user_id | first_reach_dt |
| --- | --- |
| U1 | 2026-09-02 |
| U2 | NULL |

### 为什么这样写／容易错在哪里

- 不能先 WHERE cumulative_amount≥1000 再按用户分组，那样未达标用户会整行消失。
- 窗口显式指定从第一行到当前行的 ROWS 范围；累计前先按用户日聚合，避免同日多行影响解释。
- 若要求定位订单，需要按支付时间＋订单唯一键排序，直接在订单粒度累计。
- 如果有退款负数，累计可能回落；“首次曾达到”“日末达到”“最终仍达到”要分别定义。

## 09. 滑动窗口：最近 7 个自然日营业额

**练习链接与对应关系：** 相近练习：[1321. 餐馆营业额变化增长](https://leetcode.cn/problems/restaurant-growth/)。本文增加日期缺失时的补零规则，输入已汇总到天。

### 题目与口径

`daily_sales` 已按日期汇总，一日最多一行，缺行表示该日销售额为 0。`calendar` 是连续且不重复的日期表，覆盖完整输入区间；其间没有未知、未到货的数据日期。
按 calendar 中的日期输出当天及前 6 个自然日的销售总额和日均额。只有从 calendar 起点开始积满 7 天后才输出；平均数固定除以 7，包含零销售日期，保留 4 位。
本例 calendar 从 9 月 1 日到 8 日，故只输出 7、8 日。真实报表若从某日开始展示，输入日期表要向前多提供 6 天，展示过滤放在窗口计算后。

**输入表 `calendar`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| dt | STRING | 连续自然日，唯一 |

**样例数据：**

| dt |
| --- |
| 2026-09-01 |
| 2026-09-02 |
| 2026-09-03 |
| 2026-09-04 |
| 2026-09-05 |
| 2026-09-06 |
| 2026-09-07 |
| 2026-09-08 |

**输入表 `daily_sales`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| dt | STRING | 业务日期，唯一 |
| amount | DECIMAL(18,2) | 当日总额 |

**样例数据：**

| dt | amount |
| --- | --- |
| 2026-09-01 | 100 |
| 2026-09-02 | 200 |
| 2026-09-04 | 400 |
| 2026-09-07 | 700 |
| 2026-09-08 | 80 |

### 记住的步骤

1. `calendar 左关联每日金额，缺失金额补 0`
2. `按日期计算 ROWS BETWEEN 6 PRECEDING AND CURRENT ROW 的 SUM 和 COUNT`
3. `筛 COUNT=7；平均额=7日总额/7`

### 参考答案

```sql
-- Q09
SELECT dt, amount_7d, ROUND(amount_7d / 7.0, 4) AS avg_7d
FROM (
    SELECT c.dt,
           SUM(COALESCE(s.amount, 0)) OVER (
               ORDER BY c.dt ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
           ) AS amount_7d,
           COUNT(*) OVER (
               ORDER BY c.dt ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
           ) AS day_count
    FROM calendar c
    LEFT JOIN daily_sales s ON c.dt = s.dt
) t
WHERE day_count = 7
ORDER BY dt;
```

**预期结果：**

| dt | amount_7d | avg_7d |
| --- | --- | --- |
| 2026-09-07 | 1400 | 200 |
| 2026-09-08 | 1380 | 197.1429 |

### 为什么这样写／容易错在哪里

- 只有补齐日期并保证一天一行后，“最近 7 行”才等于“最近 7 个自然日”。
- 不能先在 sales 上 AVG(amount)，那是有销售日期的平均值，不是 7 个自然日的日均额。
- 日表若有多个门店，先确认目标是全站还是门店。门店日窗口需要完整门店×日期骨架，并 PARTITION BY 门店。
- 迟到或缺数不能自动当零；本题已明确缺行代表真实零销售。

## 10. 同比与环比：按自然月对齐

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目与口径

`monthly_sales` 一行是一个自然月的营业额，month_start 是该月第一天；已有月份的金额可以为 0。缺失月份代表没有可用数据，不能擅自补零。
对每个已有月份输出本月金额、上月金额、去年同月金额、环比增长率和同比增长率。增长率=(本期−对比期)/对比期；对比期缺失或金额为 0 时返回 NULL。保留 4 位。

**输入表 `monthly_sales`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| month_start | STRING | 月初日期，唯一 |
| amount | DECIMAL(18,2) | 月度金额 |

**样例数据：**

| month_start | amount |
| --- | --- |
| 2025-01-01 | 100 |
| 2025-02-01 | 0 |
| 2026-01-01 | 150 |
| 2026-02-01 | 180 |
| 2026-04-01 | 200 |

### 记住的步骤

1. `确认输入一月一行；若是明细先按月汇总`
2. `分别按本月减1个月、本月减12个月左关联`
3. `缺失或零基期输出 NULL，否则计算增长率`

### 参考答案

```sql
-- Q10
SELECT c.month_start, c.amount,
       p.amount AS prev_month_amount,
       y.amount AS prev_year_amount,
       IF(p.amount IS NULL OR p.amount = 0, NULL,
          ROUND((c.amount - p.amount) * 1.0 / p.amount, 4)) AS mom_rate,
       IF(y.amount IS NULL OR y.amount = 0, NULL,
          ROUND((c.amount - y.amount) * 1.0 / y.amount, 4)) AS yoy_rate
FROM monthly_sales c
LEFT JOIN monthly_sales p ON p.month_start = ADD_MONTHS(c.month_start, -1)
LEFT JOIN monthly_sales y ON y.month_start = ADD_MONTHS(c.month_start, -12)
ORDER BY c.month_start;
```

**预期结果：**

| month_start | amount | prev_month_amount | prev_year_amount | mom_rate | yoy_rate |
| --- | --- | --- | --- | --- | --- |
| 2025-01-01 | 100 | NULL | NULL | NULL | NULL |
| 2025-02-01 | 0 | 100 | NULL | -1 | NULL |
| 2026-01-01 | 150 | NULL | 100 | NULL | 0.5000 |
| 2026-02-01 | 180 | 150 | 0 | 0.2000 | NULL |
| 2026-04-01 | 200 | NULL | NULL | NULL | NULL |

### 为什么这样写／容易错在哪里

- 2026 年 4 月的上一行是 2 月，但上一个自然月是 3 月。直接 LAG(amount) 会把月份对错。
- 如果先补齐月份，可以用 LAG；年度对齐仍要保证完整连续月份和足够历史。
- 用月初日期统一表示月份，避免月末日期在 ADD_MONTHS 时发生月底截断歧义。
- 本题不计算当月未结束时的可比同期；若要求截至同一天同比，需要另定截断规则。

## 11. Top N＋占比：城市前十与区域总额

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目

订单表 `orders`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户 ID |
| city_id | STRING | 消费发生的城市 |
| dt | STRING | 业务日期，格式 `yyyy-MM-dd` |
| amount | DECIMAL(18,2) | 订单金额，非空且大于 0 |

城市维表 `city_region`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| city_id | STRING | 城市 ID，每个城市恰好一行 |
| region_id | STRING | 所属区域 ID |

订单中的每个城市都能匹配维表。求每天每个城市消费金额前 10 的用户，输出：日期、城市、区域、用户、用户在该城市的消费金额、城市内名次、区域当日总消费、该用户在该城市消费占区域当日总消费的比例。

明确口径：

- 输出粒度为 **日期＋城市＋用户**；同一用户在不同城市的消费分别统计。
- 每个城市每天最多 10 行；金额相同时，用户 ID 小的排前面。
- 占比为 0～1 的小数，保留 4 位。分母是整个区域当天的总消费，包含没有进入 Top10 的用户。

### 样例

`orders`：

| user_id | city_id | dt | amount |
| --- | --- | --- | --- |
| 1 | C1 | 2026-09-01 | 40.00 |
| 1 | C1 | 2026-09-01 | 60.00 |
| 2 | C1 | 2026-09-01 | 100.00 |
| 3 | C1 | 2026-09-01 | 50.00 |
| 4 | C2 | 2026-09-01 | 150.00 |
| 5 | C2 | 2026-09-01 | 100.00 |

`city_region`：

| city_id | region_id |
| --- | --- |
| C1 | A |
| C2 | A |

预期结果：

| dt | city_id | region_id | user_id | user_amount | city_rank | region_amount | region_ratio |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-09-01 | C1 | A | 1 | 100.00 | 1 | 500.00 | 0.2000 |
| 2026-09-01 | C1 | A | 2 | 100.00 | 2 | 500.00 | 0.2000 |
| 2026-09-01 | C1 | A | 3 | 50.00 | 3 | 500.00 | 0.1000 |
| 2026-09-01 | C2 | A | 4 | 150.00 | 1 | 500.00 | 0.3000 |
| 2026-09-01 | C2 | A | 5 | 100.00 | 2 | 500.00 | 0.2000 |

样例每个城市不足 10 人，所以全部保留；超过 10 人时只保留前 10 人，但区域分母仍包括所有人。

### 记住的步骤

1. `按日期＋城市＋用户汇总金额，再关联唯一城市区域表`
2. `在完整数据上同时算城市排名和区域总金额`
3. `最后筛城市排名≤10，计算用户城市金额/区域总金额`

### 参考答案

```sql
-- Q11:城市 Top10 与区域占比
SELECT
    dt,
    city_id,
    region_id,
    user_id,
    user_amount,
    city_rank,
    region_amount,
    ROUND(user_amount * 1.0 / region_amount, 4) AS region_ratio
FROM (
    SELECT
        a.dt,
        a.city_id,
        b.region_id,
        a.user_id,
        a.user_amount,
        ROW_NUMBER() OVER (
            PARTITION BY a.dt, a.city_id
            ORDER BY a.user_amount DESC, a.user_id ASC
        ) AS city_rank,
        SUM(a.user_amount) OVER (
            PARTITION BY a.dt, b.region_id
        ) AS region_amount
    FROM (
        SELECT
            dt,
            city_id,
            user_id,
            SUM(amount) AS user_amount
        FROM orders
        GROUP BY dt, city_id, user_id
    ) a
    INNER JOIN city_region b
        ON a.city_id = b.city_id
) t
WHERE city_rank <= 10
ORDER BY dt, city_id, city_rank;
```

### 怎么理解与追问

先把多笔订单合并成一行“用户当天在该城市的消费”，再关联区域。内层窗口同时算城市排名和完整的区域总额，外层才筛选 Top10。

- `ROW_NUMBER`：本题要求最多 10 行，且明确了同额时按用户 ID 决定先后。
- 如果题目要求“第 10 个位置的并列用户都保留”，可用仅按金额排序的 `RANK`；如果要求“前 10 种不同金额”，用 `DENSE_RANK`。这两种口径都可能超过 10 行。
- 维表一个城市多行会放大消费金额，不能靠最后 `DISTINCT` 修复。
- 订单先聚合再关联可以缩小关联输入。两个窗口的分组不同，可能产生额外 Shuffle；不要只根据 SQL 层数猜执行代价。
- 本题金额均为正，区域分母一定大于 0。若包含退款、允许分母为 0，应明确净消费口径，并使用 `IF(region_amount = 0, NULL, ...)`。

## 12. 行列转换：支付方式汇总与反向展开

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目 A：行转列

支付表 `payment`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户 ID |
| pay_type | STRING | 支付方式，只包含 `alipay`、`wechat` |
| amount | DECIMAL(18,2) | 每笔支付金额，非空 |

每个用户输出一行，包含 `alipay_amount、wechat_amount`。同一方式有多笔支付时求和，没有该方式的支付则填 0。

样例：

| user_id | pay_type | amount |
| --- | --- | --- |
| 1 | alipay | 40.00 |
| 1 | alipay | 60.00 |
| 1 | wechat | 50.00 |
| 2 | wechat | 20.00 |

预期结果：

| user_id | alipay_amount | wechat_amount |
| --- | --- | --- |
| 1 | 100.00 | 50.00 |
| 2 | 0.00 | 20.00 |

### 记住的步骤

1. `按用户分组，对每种方式分别 SUM(IF(...))`
2. `反向时分别 SELECT 每个金额列，补方式名称，再 UNION ALL`
3. `缺失方式填0，明确反向只能恢复汇总行`

### 参考答案 A

```sql
-- Q12A:行转列
SELECT
    user_id,
    SUM(IF(pay_type = 'alipay', amount, 0)) AS alipay_amount,
    SUM(IF(pay_type = 'wechat', amount, 0)) AS wechat_amount
FROM payment
GROUP BY user_id
ORDER BY user_id;
```

`IF` 决定本行金额属于哪一列，`SUM` 汇总同一用户的多笔支付。这里要求总金额，使用 `SUM`；换成 `MAX` 会漏掉其他支付。

如果题目要求“每个用户每天一行”，把日期字段加入 `SELECT` 和 `GROUP BY`，不用把日期写死在查询里。

### 题目 B：列转行

假设上面的结果已保存为宽表 `payment_wide(user_id, alipay_amount, wechat_amount)`。

将两种支付金额转为 `user_id、pay_type、amount` 三列。每个用户固定输出两行，金额为 0 的行也保留。

```sql
-- Q12B:列转行
SELECT
    user_id,
    'alipay' AS pay_type,
    alipay_amount AS amount
FROM payment_wide

UNION ALL

SELECT
    user_id,
    'wechat' AS pay_type,
    wechat_amount AS amount
FROM payment_wide
ORDER BY user_id, pay_type;
```

预期结果：

| user_id | pay_type | amount |
| --- | --- | --- |
| 1 | alipay | 100.00 |
| 1 | wechat | 50.00 |
| 2 | alipay | 0.00 |
| 2 | wechat | 20.00 |

**它恢复的是各方式的汇总金额，不能恢复用户 1 原来的 40、60 两笔明细。** 固定少量列用 `UNION ALL` 很直观；数组或 Map 拆行可再复习 `LATERAL VIEW EXPLODE`，本次不展开。

## 13. 会话切分：相邻行为间隔超过 30 分钟

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目

用户行为表 `user_behavior`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| event_id | BIGINT | 唯一事件 ID |
| user_id | BIGINT | 用户 ID |
| event_time | STRING | 行为发生时间，精确到秒 |

同一用户的行为按时间排序，**相邻两次行为间隔超过 30 分钟，后一次开始新会话**；恰好 30 分钟仍是同一会话。第一条行为开始第 1 次会话，允许跨自然日。

输出 `user_id、session_id、session_start、session_end、event_count、duration_seconds`。会话时长定义为最后一次行为减去第一次行为，单次行为的会话时长为 0。

### 样例

| event_id | user_id | event_time |
| --- | --- | --- |
| 1 | 1 | 2026-09-01 09:00:00 |
| 2 | 1 | 2026-09-01 09:20:00 |
| 3 | 1 | 2026-09-01 09:50:00 |
| 4 | 1 | 2026-09-01 10:21:00 |
| 5 | 2 | 2026-09-01 23:50:00 |
| 6 | 2 | 2026-09-02 00:10:00 |

预期结果：

| user_id | session_id | session_start | session_end | event_count | duration_seconds |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 2026-09-01 09:00:00 | 2026-09-01 09:50:00 | 3 | 3000 |
| 1 | 2 | 2026-09-01 10:21:00 | 2026-09-01 10:21:00 | 1 | 0 |
| 2 | 1 | 2026-09-01 23:50:00 | 2026-09-02 00:10:00 | 2 | 1200 |

### 记住的步骤

1. `按用户分区、事件时间和事件ID排序，用 LAG 取上一条时间`
2. `第一条或相邻间隔>1800秒标记1，其他0`
3. `累计 SUM 标志形成会话号，再按用户＋会话号汇总`

### 参考答案

```sql
-- Q13:用户会话切分
SELECT
    user_id,
    session_id,
    MIN(event_time) AS session_start,
    MAX(event_time) AS session_end,
    COUNT(*) AS event_count,
    UNIX_TIMESTAMP(MAX(event_time))
        - UNIX_TIMESTAMP(MIN(event_time)) AS duration_seconds
FROM (
    SELECT
        event_id,
        user_id,
        event_time,
        SUM(is_new_session) OVER (
            PARTITION BY user_id
            ORDER BY event_time, event_id
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS session_id
    FROM (
        SELECT
            event_id,
            user_id,
            event_time,
            IF(
                prev_time IS NULL
                OR UNIX_TIMESTAMP(event_time)
                    - UNIX_TIMESTAMP(prev_time) > 1800,
                1,
                0
            ) AS is_new_session
        FROM (
            SELECT
                event_id,
                user_id,
                event_time,
                LAG(event_time) OVER (
                    PARTITION BY user_id
                    ORDER BY event_time, event_id
                ) AS prev_time
            FROM user_behavior
        ) t1
    ) t2
) t3
GROUP BY user_id, session_id
ORDER BY user_id, session_id;
```

### 怎么理解

对用户 1：

| 时间 | 与上一次间隔 | 是否新会话 | 累加后 session_id |
| --- | --- | --- | --- |
| 09:00 | 无上一条 | 1 | 1 |
| 09:20 | 20 分钟 | 0 | 1 |
| 09:50 | 30 分钟 | 0 | 1 |
| 10:21 | 31 分钟 | 1 | 2 |

判断的是相邻行为的间隔，所以一个会话的总时长可以超过 30 分钟。

### 关键边界与大数据追问

- `DATEDIFF` 计算天数，不能拿来比较分钟；这里先换成 Unix 秒数。
- 两次窗口都按 `event_time、event_id` 排序，让同一秒的多条事件有稳定顺序。不同事件 ID 的行为都保留；脏数据重复应先按事件 ID 清洗。
- 不能按 `user_id、dt` 分区，否则跨天会话会被强制切断。
- 只读当天分区会把当天首条行为误认成新会话。判断边界至少需要前一条历史行为；若还要延续会话编号、开始时间和累计统计，应保留上一批的未结束会话状态。

## 14. 有序漏斗：浏览→加购→支付

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目

用户事件表 `user_event`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户 ID |
| event_type | STRING | `view` 浏览、`cart` 加购、`pay` 支付 |
| event_time | STRING | 事件时间，精确到秒 |

按业务自然日统计：

- `view_uv`：当天发生浏览的去重用户数。
- `cart_uv`：当天存在“浏览时间 < 加购时间”的去重用户数。
- `pay_uv`：当天存在“浏览时间 < 加购时间 < 支付时间”的去重用户数。
- `view_to_cart_rate = cart_uv / view_uv`。
- `cart_to_pay_rate = pay_uv / cart_uv`。
- `view_to_pay_rate = pay_uv / view_uv`。

所有转化率保留 4 位小数，分母为 0 时返回 `NULL`。同一天可有多次浏览、加购、支付，只要存在一条合法顺序就算转化。

本题是**用户级、同日、严格时间先后**漏斗，不要求同一商品或同一订单，也不要求三个事件在日志中相邻。同一秒发生的两个步骤不算有严格先后。日期有相关事件才输出，无事件日期不补行。

### 样例

以下均发生在 2026-09-01。为缩短表格，只展示时间部分；表内实际保存完整日期时间字符串。

| user_id | event_type | event_time 的时间部分 |
| --- | --- | --- |
| 1 | view | 09:00:00 |
| 1 | cart | 09:05:00 |
| 1 | pay | 09:10:00 |
| 2 | cart | 08:55:00 |
| 2 | view | 09:00:00 |
| 2 | pay | 09:20:00 |
| 2 | cart | 09:25:00 |
| 2 | pay | 09:30:00 |
| 3 | pay | 08:00:00 |
| 3 | view | 09:00:00 |
| 3 | cart | 09:10:00 |
| 4 | view | 09:00:00 |
| 5 | cart | 09:00:00 |
| 5 | pay | 09:10:00 |

预期结果：

| dt | view_uv | cart_uv | pay_uv | view_to_cart_rate | cart_to_pay_rate | view_to_pay_rate |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-09-01 | 4 | 3 | 2 | 0.7500 | 0.6667 | 0.5000 |

用户 2 的有效链路是 `09:00 浏览 → 09:25 加购 → 09:30 支付`；用户 3 的支付早于浏览，不算支付转化；用户 5 没有浏览，不进入漏斗。

### 记住的步骤

1. `为用户当天每行事件附上最早浏览时间`
2. `再附上最早浏览之后的最早加购时间`
3. `压到用户日粒度，产生浏览、有效加购、有效支付标志`
4. `按日期 SUM 标志，计算三个转化率`

### 参考答案

```sql
-- Q14：有序用户漏斗
SELECT dt, view_uv, cart_uv, pay_uv,
       IF(view_uv = 0, NULL, ROUND(cart_uv * 1.0 / view_uv, 4)) AS view_to_cart_rate,
       IF(cart_uv = 0, NULL, ROUND(pay_uv * 1.0 / cart_uv, 4)) AS cart_to_pay_rate,
       IF(view_uv = 0, NULL, ROUND(pay_uv * 1.0 / view_uv, 4)) AS view_to_pay_rate
FROM (
    SELECT dt, SUM(has_view) AS view_uv, SUM(has_cart) AS cart_uv, SUM(has_pay) AS pay_uv
    FROM (
        SELECT user_id, dt,
               MAX(IF(first_view_time IS NOT NULL, 1, 0)) AS has_view,
               MAX(IF(first_cart_time IS NOT NULL, 1, 0)) AS has_cart,
               MAX(IF(event_type = 'pay' AND event_time > first_cart_time, 1, 0)) AS has_pay
        FROM (
            SELECT
                user_id,
                dt,
                event_type,
                event_time,
                first_view_time,
                MIN(IF(
                    event_type = 'cart' AND event_time > first_view_time,
                    event_time,
                    NULL
                )) OVER (
                    PARTITION BY user_id, dt
                ) AS first_cart_time
            FROM (
                SELECT
                    user_id,
                    TO_DATE(event_time) AS dt,
                    event_type,
                    event_time,
                    MIN(IF(
                        event_type = 'view',
                        event_time,
                        NULL
                    )) OVER (
                        PARTITION BY user_id, TO_DATE(event_time)
                    ) AS first_view_time
                FROM user_event
                WHERE event_type IN ('view', 'cart', 'pay')
            ) t1
        ) events_with_steps
        GROUP BY user_id, dt
    ) user_day
    GROUP BY dt
) daily
ORDER BY dt;
```

### 怎么理解

1. 最内两层窗口仍保留事件行，依次附加最早浏览、该浏览之后的最早加购。
2. `events_with_steps` 外按用户和日期分组，MAX(0/1) 将一个用户的多行事件折成三个“是否达成”标志。一行变为一个用户的一天。
3. `daily` 按日 SUM 用户标志，得到各阶段人数，最后计算转化率。
4. 这里 MAX 是把重复事件行折成用户标志所必需的一层；不能用 SUM 标志直接把同一用户的多次支付算成多人。

本题只要求存在一条同日合法顺序，没有额外最大时长限制。越早完成一个有效步骤，越容易满足后续步骤，所以最早的有效浏览与加购足够判断。

### 关键反例与大数据追问

- **不能分别取三种事件的全天最小时间再比较。** 用户 2 的最早加购在浏览之前，但后面仍有一次合法加购；直接取全天最小值会漏算。
- **不能只判断三种事件是否都出现过。** 用户 3 三种事件都有，但先支付后浏览，不满足顺序。
- 本题按天隔离；今天浏览、明天支付不算同日转化。若改为“浏览后 24 小时内”或必须关联同一商品、订单，需要重新定义分组和匹配条件，不能照搬答案。
- 生产运行可在原始表读取处加业务所需范围的分区条件；不要对分区字段套日期函数后才过滤。本题 `TO_DATE(event_time)` 是确定业务日，不代表自动完成分区裁剪。
- 该写法没有三次明细自连接，在识别有效步骤后收敛到用户日粒度再汇总；高频用户的窗口分区仍可能成为瓶颈。

## 15. 最大同时在线：直播间峰值人数

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目

有直播观看记录表 `live_log`，一行代表某用户的一次完整观看区间。

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| room_id | STRING | 直播间 ID |
| user_id | BIGINT | 用户 ID |
| enter_time | STRING | 进入时间 |
| leave_time | STRING | 离开时间 |

求每个直播间的最大同时在线人数，输出 `room_id、max_online_users`。

约定：

- 在线区间为 **`[enter_time, leave_time)`**，进入时算在线，离开时不再算在线。
- `enter_time < leave_time`；没有重复记录，同一用户在同一直播间的观看区间不重叠。
- 本题统计输入数据覆盖的完整区间，不按天拆分；只输出有观看记录的直播间。

### 样例

| room_id | user_id | enter_time | leave_time |
| --- | --- | --- | --- |
| R1 | 1 | 2026-09-01 10:00:00 | 2026-09-01 10:10:00 |
| R1 | 2 | 2026-09-01 10:05:00 | 2026-09-01 10:15:00 |
| R1 | 3 | 2026-09-01 10:10:00 | 2026-09-01 10:20:00 |
| R1 | 4 | 2026-09-01 10:12:00 | 2026-09-01 10:18:00 |
| R2 | 5 | 2026-09-01 09:00:00 | 2026-09-01 09:05:00 |
| R2 | 6 | 2026-09-01 09:05:00 | 2026-09-01 09:10:00 |

预期结果：

| room_id | max_online_users |
| --- | --- |
| R1 | 3 |
| R2 | 1 |

### 记住的步骤

1. `进入产生+1，离开产生−1，UNION ALL 合并事件`
2. `先按房间＋时刻合并净变化，再按时间累计`
3. `按房间取累计人数的最大值`

### 参考答案

```sql
-- Q15:每个直播间最大同时在线人数
SELECT
    room_id,
    MAX(online_users) AS max_online_users
FROM (
    SELECT
        room_id,
        event_time,
        SUM(delta) OVER (
            PARTITION BY room_id
            ORDER BY event_time
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS online_users
    FROM (
        SELECT
            room_id,
            event_time,
            SUM(delta) AS delta
        FROM (
            SELECT
                room_id,
                enter_time AS event_time,
                1 AS delta
            FROM live_log

            UNION ALL

            SELECT
                room_id,
                leave_time AS event_time,
                -1 AS delta
            FROM live_log
        ) t1
        GROUP BY room_id, event_time
    ) t2
) t3
GROUP BY room_id
ORDER BY room_id;
```

### 怎么理解

进入产生 `+1`，离开产生 `-1`。先把同一直播间、同一时刻的变化合并，再按时间累加。

R1 的计算过程如下：

| 时间 | 净变化 | 变化后在线人数 |
| --- | --- | --- |
| 10:00 | +1 | 1 |
| 10:05 | +1 | 2 |
| 10:10 | 0（一个离开、一个进入） | 2 |
| 10:12 | +1 | 3 |
| 10:15 | -1 | 2 |
| 10:18 | -1 | 1 |
| 10:20 | -1 | 0 |

如果题目只问各时段人数，取 `t3` 中的 `room_id、event_time、online_users` 即可；一行表示从当前事件时间到下一个事件时间之前的人数，最后一行表示离场后的 0 人。

### 关键边界与大数据追问

- **为什么不能用 `UNION`？** 多个用户可能同一时刻进入，不能把相同的 `+1` 事件去重。
- **为什么先按时刻汇总？** 避免同时进出被随意排成先进入、后离开，产生不存在的瞬时峰值。
- **同一用户重叠观看怎么办？** 当前算法会数成多个连接。若要求去重用户数，必须先合并同一用户在同一房间的重叠区间。
- **按某一天统计能直接只读当天进入的记录吗？** 不能，跨天观看会漏掉。需要纳入当天开始前仍在线的区间，或补上期初在线人数，再处理当天变化。
- 大房间可能产生倾斜；先按房间和时刻聚合能缩小排序数据量。最终 `ORDER BY` 仅方便阅读，大批量落表通常不需要全局排序。

## 16. 中位数与 P90：先明确分位数定义

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目

员工表 `employee`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| emp_id | BIGINT | 员工 ID，唯一 |
| dept_id | STRING | 部门 ID |
| salary | DECIMAL(18,2) | 工资，允许为空 |

求每个部门工资的中位数，输出 `dept_id、median_salary`。

规则：忽略工资为 `NULL` 的员工；同工资的不同员工都要计入，不能去重。奇数人数取中间一人的工资，偶数人数取中间两人工资的平均值。只输出至少有一名非空工资员工的部门。

### 样例

| emp_id | dept_id | salary |
| --- | --- | --- |
| 1 | A | 1000.00 |
| 2 | A | 2000.00 |
| 3 | A | 9000.00 |
| 4 | B | 1000.00 |
| 5 | B | 2000.00 |
| 6 | B | 3000.00 |
| 7 | B | 10000.00 |
| 8 | C | 1000.00 |
| 9 | C | 1000.00 |
| 10 | C | 9000.00 |
| 11 | D | NULL |

预期结果：

| dept_id | median_salary |
| --- | --- |
| A | 2000.00 |
| B | 2500.00 |
| C | 1000.00 |

### 记住的步骤

1. `先过滤 NULL，保留同工资的不同员工`
2. `按部门排序编号，同时统计有效人数 n`
3. `中位数取 floor((n+1)/2)、floor((n+2)/2) 的工资平均`
4. `P90 扩展采用最近秩定义：取第 ceil(0.9×n) 个样本`

### 参考答案

```sql
-- Q16:各部门工资中位数
SELECT
    dept_id,
    AVG(salary) AS median_salary
FROM (
    SELECT
        dept_id,
        salary,
        ROW_NUMBER() OVER (
            PARTITION BY dept_id
            ORDER BY salary, emp_id
        ) AS rn,
        COUNT(*) OVER (
            PARTITION BY dept_id
        ) AS cnt
    FROM employee
    WHERE salary IS NOT NULL
) t
WHERE rn IN (
    FLOOR((cnt + 1) / 2.0),
    FLOOR((cnt + 2) / 2.0)
)
GROUP BY dept_id
ORDER BY dept_id;
```

### 怎么理解

| 有效人数 cnt | 第一个中间位置 | 第二个中间位置 | 实际取值 |
| --- | --- | --- | --- |
| 1 | 1 | 1 | 第 1 行 |
| 3 | 2 | 2 | 第 2 行 |
| 4 | 2 | 3 | 第 2、3 行 |
| 5 | 3 | 3 | 第 3 行 |
| 6 | 3 | 4 | 第 3、4 行 |

`IN` 中两个位置相同时，一行只保留一次。对筛出来的一行或两行求 `AVG`，统一处理奇数和偶数。

### 关键边界与大数据追问

- 必须使用逐行编号 `ROW_NUMBER`。相同工资代表不同员工，不能用 `DENSE_RANK` 把他们压成一个位置。
- `NULL` 要在计算人数和编号之前过滤，不能算完人数再排除。
- 本题使用明确的“中间两项平均”定义，答案按此定义计算。若允许近似分位数，Hive 有 `PERCENTILE_APPROX`；其结果不能直接当作这个精确定义的等价替代，应先确认精度和分位数口径。
- 精确中位数需要组内排序，大部门可能成为瓶颈。不要为了避免排序直接把重复工资去掉，那会改变结果。

### P90 扩展题的口径

使用本节同一份员工数据，按最近秩定义，P90 为排序后第 `CEIL(0.9×有效人数)` 个工资。它与插值分位数、近似分位数可能不同；这里只输出有有效工资的部门。

### 扩展答案：按最近秩定义求精确 P90

```sql
-- Q16B
SELECT dept_id, salary AS p90_salary
FROM (
    SELECT dept_id, salary,
           ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary, emp_id) AS rn,
           COUNT(*) OVER (PARTITION BY dept_id) AS cnt
    FROM employee WHERE salary IS NOT NULL
) t
WHERE rn = CEIL(cnt * 0.9)
ORDER BY dept_id;
```

**预期结果：**

| dept_id | p90_salary |
| --- | --- |
| A | 9000 |
| B | 10000 |
| C | 9000 |

## 17. 集合条件：买过 A 和 B、没买 C；买齐目标商品

**练习链接与对应关系：** B 对应题型：[1045. 买下所有产品的客户](https://leetcode.cn/problems/customers-who-bought-all-products/)。本文明确购买记录可以含目标外商品，先关联限定集合。

### 题目与口径

`purchase` 一行代表一条成功购买记录，同一用户可重复购买同一商品。`target_product` 保存指定目标商品，product_id 唯一，本题保证至少一行。
题 A：找出买过 A、买过 B、从未买过 C 的用户，允许购买其他商品。
题 B：找出买齐 target_product 中所有商品的用户，允许重复购买和购买目标集合之外的商品；输出用户去重。

**输入表 `purchase`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | STRING | 用户 |
| product_id | STRING | 商品 |

**样例数据：**

| user_id | product_id |
| --- | --- |
| U1 | A |
| U1 | A |
| U1 | B |
| U2 | A |
| U2 | B |
| U2 | C |
| U3 | A |
| U3 | X |
| U4 | B |
| U4 | A |
| U4 | X |

**输入表 `target_product`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| product_id | STRING | 目标商品，唯一 |

**样例数据：**

| product_id |
| --- |
| A |
| B |

### 记住的步骤

1. `A：按用户检查 A、B 命中数>0且 C命中数=0`
2. `B：先与目标集合内关联，只留下目标商品购买记录`
3. `B：按用户统计目标商品去重数，与目标总数比较`

### 答案 A：包含与排除

```sql
-- Q17A
SELECT user_id
FROM purchase
GROUP BY user_id
HAVING SUM(IF(product_id = 'A', 1, 0)) > 0
   AND SUM(IF(product_id = 'B', 1, 0)) > 0
   AND SUM(IF(product_id = 'C', 1, 0)) = 0
ORDER BY user_id;
```

**预期结果：**

| user_id |
| --- |
| U1 |
| U4 |

### 答案 B：买齐目标集合

```sql
-- Q17B
SELECT p.user_id
FROM purchase p
INNER JOIN target_product t ON p.product_id = t.product_id
CROSS JOIN (
    SELECT COUNT(*) AS target_count FROM target_product
) n
GROUP BY p.user_id, n.target_count
HAVING COUNT(DISTINCT p.product_id) = n.target_count
ORDER BY p.user_id;
```

**预期结果：**

| user_id |
| --- |
| U1 |
| U2 |
| U4 |

### 为什么这样写／容易错在哪里

- A 不能先 WHERE product_id IN ('A','B')，那会删掉 C 的证据，错误放过 U2。
- B 先限制目标集合再数。U3 买了 A、X，虽然总共有两种商品，也没有买齐 A、B。
- COUNT DISTINCT 防止 U1 重复购买 A 被误认为买了更多种商品。
- 若允许目标集合为空，要先定义候选用户全集；通常“买齐空集合”对全集都成立，当前非空目标写法需要调整。

## 18. 区间合并：去除重叠后的真实在线时长

**练习链接与对应关系：** 通用场景练习，本节直接提供完整题面与答案。

### 题目与口径

一行代表一个用户的一段在线区间，区间为 [start_time,end_time)，且 start_time<end_time。重复、交叠、包含关系均允许；同用户首尾相接的区间也合并。
题 A：输出每个用户合并后的不重叠区间及其秒数，一行代表一个合并区间。题 B：按用户输出所有合并区间的总在线秒数。跨天照常计算。
只统计表中出现的用户；原始 interval_id 唯一，即便时间区间重复也有独立 ID。

**输入表 `online_interval`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| interval_id | BIGINT | 区间唯一键 |
| user_id | STRING | 用户 |
| start_time | STRING | 开始时间 |
| end_time | STRING | 结束时间 |

**样例数据：**

| interval_id | user_id | start_time | end_time |
| --- | --- | --- | --- |
| 1 | U1 | 2026-09-01 09:00:00 | 2026-09-01 10:00:00 |
| 2 | U1 | 2026-09-01 09:10:00 | 2026-09-01 09:20:00 |
| 3 | U1 | 2026-09-01 09:30:00 | 2026-09-01 09:40:00 |
| 4 | U1 | 2026-09-01 10:00:00 | 2026-09-01 10:10:00 |
| 5 | U1 | 2026-09-01 11:00:00 | 2026-09-01 11:15:00 |
| 6 | U2 | 2026-09-01 23:50:00 | 2026-09-02 00:10:00 |

### 记住的步骤

1. `按用户分区、开始时间等排序，求不含当前行的历史 MAX(end_time)`
2. `第一条或 start_time>此前最大结束时间时开启新段`
3. `累计断点生成组号；组内 MIN(start)、MAX(end) 合并`
4. `合并后算每段秒数，按用户求和`

### 答案 A：合并区间

```sql
-- Q18A
SELECT user_id, grp,
       MIN(start_time) AS merged_start, MAX(end_time) AS merged_end,
       UNIX_TIMESTAMP(MAX(end_time)) - UNIX_TIMESTAMP(MIN(start_time)) AS duration_seconds
FROM (
    SELECT user_id, interval_id, start_time, end_time,
           SUM(is_new) OVER (
               PARTITION BY user_id ORDER BY start_time, end_time, interval_id
               ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
           ) AS grp
    FROM (
        SELECT user_id, interval_id, start_time, end_time,
               IF(prev_max_end IS NULL OR start_time > prev_max_end, 1, 0) AS is_new
        FROM (
            SELECT user_id, interval_id, start_time, end_time,
                   MAX(end_time) OVER (
                       PARTITION BY user_id ORDER BY start_time, end_time, interval_id
                       ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING
                   ) AS prev_max_end
            FROM online_interval
        ) p
    ) m
) g
GROUP BY user_id, grp
ORDER BY user_id, grp;
```

**预期结果：**

| user_id | grp | merged_start | merged_end | duration_seconds |
| --- | --- | --- | --- | --- |
| U1 | 1 | 2026-09-01 09:00:00 | 2026-09-01 10:10:00 | 4200 |
| U1 | 2 | 2026-09-01 11:00:00 | 2026-09-01 11:15:00 | 900 |
| U2 | 1 | 2026-09-01 23:50:00 | 2026-09-02 00:10:00 | 1200 |

### 答案 B：真实总时长

```sql
-- Q18B
SELECT user_id, SUM(duration_seconds) AS total_online_seconds
FROM (
    SELECT user_id, grp,
           MIN(start_time) AS merged_start, MAX(end_time) AS merged_end,
           UNIX_TIMESTAMP(MAX(end_time)) - UNIX_TIMESTAMP(MIN(start_time)) AS duration_seconds
    FROM (
        SELECT user_id, interval_id, start_time, end_time,
               SUM(is_new) OVER (
                   PARTITION BY user_id ORDER BY start_time, end_time, interval_id
                   ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
               ) AS grp
        FROM (
            SELECT user_id, interval_id, start_time, end_time,
                   IF(prev_max_end IS NULL OR start_time > prev_max_end, 1, 0) AS is_new
            FROM (
                SELECT user_id, interval_id, start_time, end_time,
                       MAX(end_time) OVER (
                           PARTITION BY user_id ORDER BY start_time, end_time, interval_id
                           ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING
                       ) AS prev_max_end
                FROM online_interval
            ) p
        ) m
    ) g
    GROUP BY user_id, grp
) merged
GROUP BY user_id ORDER BY user_id;
```

**预期结果：**

| user_id | total_online_seconds |
| --- | --- |
| U1 | 5100 |
| U2 | 1200 |

### 为什么这样写／容易错在哪里

- 第三条区间 09:30～09:40 与上一条 09:10～09:20 不重叠，但仍被第一条 09:00～10:00 包含。只 LAG(end_time) 会错误断段。
- 历史 MAX 的窗口必须到 1 PRECEDING，不包含当前行；否则合法区间总有 start<自身end，会掩盖断点。
- 首尾相接也合并，所以断点是严格 >。若业务不合并相接区间，改成 >=；两种规则的总时长相同，但区间数量不同。
- 原始时长直接求和会重复累计重叠部分；先合并，再求和。

## 19. 连续登录：严格连续、每个间隔可缺一天、整段最多缺一天

**练习链接与对应关系：** 连续思想相近练习：[180. 连续出现的数字](https://leetcode.cn/problems/consecutive-numbers/) 与 [601. 体育馆的人流量](https://leetcode.cn/problems/human-traffic-of-stadium/)。原题的行序／ID 连续条件与本文日期连续不同，不能直接照搬判定字段。

### 题目与口径

登录记录一行代表一次登录，同一用户同一天可重复出现。输出满足条件的去重用户 ID；“至少三天”均指至少三个实际登录日期，不能把没登录的日期计入人数或天数。
题 A：存在连续至少 3 个自然日登录。
题 B：存在实际登录至少 3 天的一段，相邻两次登录最多相差 2 个自然日，允许多个间隔各缺一天。
题 C：存在实际登录至少 3 天的一段，但整段合计最多缺 1 个自然日。例如 1、2、4 满足，1、3、5 不满足。
本题只问是否存在，不求题 C 的最大段长度。不要把 C 的存在性写法误用为完整分段算法。

**输入表 `login_log`：**

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | STRING | 用户 |
| login_dt | STRING | 登录日期 |

**样例数据：**

| --- | --- |
| U1 | 2026-09-01 |

| U2 | 2026-09-04 |
| U3 | 2026-09-01 |
| U3 | 2026-09-02 |
| U3 | 2026-09-05 |
| U4 | 2026-09-01 |
| U4 | 2026-09-01 |
| U4 | 2026-09-02 |
| U5 | 2026-09-01 |
| U5 | 2026-09-02 |
| U5 | 2026-09-10 |
| U5 | 2026-09-11 |
| U5 | 2026-09-20 |
| U5 | 2026-09-21 |
| U6 | 2026-09-01 |
| U6 | 2026-09-03 |
| U6 | 2026-09-05 |
| U7 | 2025-12-30 |

### 记住的步骤

1. `三题都先按用户＋日期去重`
2. `A：用户内日期排序编号；日期减编号形成段键；按用户＋段键 COUNT≥3`
3. `B：LAG 取上次日期；差>2标记断点；累计断点形成段号；按段 COUNT≥3`
4. `C：取前第2个实际登录日期；与当前日期跨度≤3天就存在合格的3次登录`

### 答案 A：严格连续

```sql
-- Q19A
SELECT DISTINCT user_id
FROM (
    SELECT user_id, dt, DATE_SUB(dt, CAST(rn AS INT)) AS grp
    FROM (
        SELECT user_id, dt,
               ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY dt) AS rn
        FROM (
            SELECT DISTINCT user_id, login_dt AS dt FROM login_log
        ) d
    ) r
) g
GROUP BY user_id, grp
HAVING COUNT(*) >= 3
ORDER BY user_id;
```

### 答案 B：每个间隔可缺一天

```sql
-- Q19B
SELECT DISTINCT user_id
FROM (
    SELECT user_id, dt,
           SUM(is_new) OVER (
               PARTITION BY user_id ORDER BY dt
               ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
           ) AS grp
    FROM (
        SELECT user_id, dt,
               IF(prev_dt IS NULL OR DATEDIFF(dt, prev_dt) > 2, 1, 0) AS is_new
        FROM (
            SELECT user_id, dt, LAG(dt) OVER (PARTITION BY user_id ORDER BY dt) AS prev_dt
            FROM (
                SELECT DISTINCT user_id, login_dt AS dt FROM login_log
            ) d
        ) p
    ) m
) g
GROUP BY user_id, grp
HAVING COUNT(*) >= 3
```

### 答案 C：整段总共最多缺一天，只判断存在

```sql
-- Q19C
SELECT DISTINCT user_id
FROM (
    SELECT user_id, dt,
           LAG(dt, 2) OVER (PARTITION BY user_id ORDER BY dt) AS two_logins_ago
    FROM (
        SELECT DISTINCT user_id, login_dt AS dt FROM login_log
    ) d
) t
WHERE DATEDIFF(dt, two_logins_ago) <= 3
ORDER BY user_id;
```

**预期结果：**

| user_id |
| --- |
| U1 |
| U2 |
| U7 |

### 为什么这样写／容易错在哪里

- A 连续时日期和序号同步增加，日期减序号保持同一个值。段键不一定是 0，要使用完整日期运算。
- A 必须先去重再编号；最后按用户＋段键分组，COUNT 是每段实际登录天数。只返回用户时不必再求最长长度。
- B 的新段标志是 1、0、1、0…，必须累计成 1、1、2、2…；直接按标志分组会把不同段合并。
- B 把断点条件 >2 改成 >1，也能求严格连续。两种题面先确认允许缺失的范围。
- C 去重后，三次相邻登录的缺失天数=首末日期差+1−3，因此最多缺一天等价于首末日期差≤3。若更长的一段合格，其中的前三次登录也合格；所以检查三次就足以回答“是否存在”。LAG 不足两条时返回 NULL，过滤自然不通过。
- `CAST(rn AS INT)` 明确日期函数的天数参数。若单个用户的不同登录日期数可能超出 INT 范围，需要另行选用适当日期运算；面试正常日期跨度不存在这个问题。

## 通用口述与自查

每题尽量完整说出这条链：**输入粒度 → 去重或预聚合 → 关联／窗口 → 每层产生的字段 → 最终分组与筛选 → 边界样例**。

| 需要解释的问题 | 常见错误 |
| --- | --- |
| 最终一行代表什么？ | 用户、订单、用户日混用 |
| 去重什么、在哪里去重？ | 订单明细当订单；工资重复被误删 |
| 窗口分区、排序、范围是什么？ | 跨用户累计；7行当7天；累计范围含义不清 |
| 比例的分母包含谁？ | 先筛成功或Top N再算整体分母 |
| 未匹配、空集、NULL 怎么输出？ | LEFT JOIN 变成内连接；缺第二高时返回0行 |
| 相等边界怎么处理？ | ≥3写成>3；30分钟、同时进出、相接区间含糊 |
| 数据范围完整吗？ | 当月第一单冒充历史首单；跨天会话被切断 |
