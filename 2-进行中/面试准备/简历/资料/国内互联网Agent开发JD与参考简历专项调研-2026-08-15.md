### 1.3 最关键的纠偏

Agent 开发 JD 并不等于把“LangChain、RAG、Prompt”写进技能栏。它更像一种新的应用/后端工程：

> **把不确定的模型能力接入确定的业务系统，并通过编排、状态、校验、评测、权限和降级，把任务从“能演示”做到“能交付”。**

这比上一轮笼统的“大模型应用”描述更接近你的真实经历。

## 2. JD 对当前经历的具体影响

### 2.1 智能经营分析应该如何对齐 Agent JD

它不只是 BI 问答或 RAG 项目，而是一套面向业务任务执行的 Agent：

1. **任务判断**：Agent 自主判断用户诉求，并在查数与分析两类执行模式间选择；
2. **工具路由**：先识别指标支持范围，指标平台优先，长尾需求再走 SQL；
3. **可靠性**：为不同路径声明可信边界，用领域数据知识校验范围、关系和空结果；
4. **分析编排**：固定专题走 Workflow，临时分析由 Agent 按需组装 Skill/Tool；
5. **知识与归因**：混合检索业务知识和事件，沿维度逐层下钻，再结合事件解释异常；
6. **评测闭环**：百题集、阶段性迭代、真实用户 badcase；
7. **主动执行**：定时巡检并通过大象触达，而非只等用户提问；
8. **业务结果**：核心查数自助完成，常规分析报告显著缩短。

这里最像 JD 的不是“向量库”，而是 **任务编排、工具调用、可靠性、Eval、主动执行和系统集成**。

### 2.2 活动自动化配置应该如何对齐 Agent JD

该项目最有价值的部分不是底层配置 Skill，而是把业务意图变成安全的系统动作：

- Agent 理解运营想配置什么；
- 映射到十余类平台 Skill / Workflow；
- 补全活动类型、模板和参数；
- 调用营销平台接口；
- 人工确认后才正式生效。

这直接对应 JD 中的工具集成、流程自动化和 human-in-the-loop。但必须继续说明：底层 Skill 由平台提供，个人负责业务规则、意图与平台能力的衔接。

### 2.3 理赔客服风险质检不应承担主项目角色

这条链路能证明安全边界、模型级联、脱敏和人工审核，但准确率约 30%，召回和客诉改善未知。对于 Agent 开发简历，它最多补充“安全与人在回路”的经历，不足以成为前三屏重点。

### 2.4 灰记可以补哪个 JD 缺口

灰记适合补“产品与工程所有权”，不是补论文：

- 产品目标、事实/计划边界；
- 结构化输出与用户确认；
- 状态版本、Outbox、幂等、恢复；
- 本地优先与敏感数据边界；
- 自动测试和真实设备验收。

但它不能替代美团的生产业务证据，也不能把 AI 生成的代码写成个人手写实现。

- 高鹏至的五页研究型 CV：虽然有 Agent 工作，但核心定价依赖团队、模型、论文和研究成果，不适合当前路线。
- 焦睿锜的大模型应用简历：以 RAG、文档智能、微调和全栈为主，不够聚焦 Agent 任务执行。

## 4. Agent 开发简历的语言模式

### 4.1 一个项目需要出现四种句子

| 句子作用 | Agent 开发写法 | 不要写成 |
| --- | --- | --- |
| 任务与责任 | 面向谁、执行什么任务、个人负责哪一段 | “负责智能 Agent 平台建设” |
| 架构与取舍 | Agent/Workflow 如何分工，为什么这样选 | “使用先进 Agent 框架” |
| 稳定与评测 | 校验、降级、审批、测试集、badcase 怎么做 | “准确率高、效果良好” |
| 业务结果 | 用户、任务量、时效或质量发生什么变化 | 把孤立数字放在侧栏卡片 |

候选示例，暂不作为 v0.2 正文：

> 主责场景险经营分析 Agent 的任务编排与数据可靠性链路，面向约 20–30 名产运和商分用户，将指标查询、固定专题分析与开放式分析接入统一对话入口。

> 按任务确定性拆分执行模式：固定专题采用 Workflow 保证分析口径，临时分析由 Agent 按需组合 Tool/Skill；查数优先路由至指标平台，长尾需求降级为 SQL 并向用户提示可靠性边界。

> 建立 100 题离线评测集并结合真实用户 badcase 迭代，综合准确率达到 80%+；指标平台覆盖范围内核心取数接近 100%，常规分析报告由人工 2–3 天缩短至约 1–2 小时。

这三条分别证明：ownership、Agent 设计判断、Eval 与业务结果。它们比罗列 RAG、向量库、Prompt 更符合 Agent 开发 JD。

### 4.2 技能栏应该写什么

正式版技能栏建议只保留四组：

1. **Agent 工程**：任务编排、Tool/Skill、Workflow、自主路由、结构化输出；
2. **可靠性与 Eval**：数据校验、降级、human-in-the-loop、离线评测、badcase 迭代；
3. **知识与数据**：混合检索、事件知识、指标平台、SQL/数仓；
4. **工程基础**：真实使用的 Java/Python/SQL、接口/任务/测试等。

不把未使用的 LangChain/LangGraph 写进美团技术栈，也不为了匹配 JD 补写 Memory、多 Agent、Sandbox、高并发或微调经验。

## 5. “没有论文”对这条路线意味着什么

在本轮筛选的 Agent 开发 JD 中，核心要求是工程实现、系统设计、任务编排、可靠性、评测和业务交付；论文不是普遍必选项。论文主要影响 Agent 算法、后训练和研究型 Infra 岗，而这些本来就不是当前最可信的主投方向。

真正的风险不是没有 Agent 论文，而是下面两项尚未写实：

1. 美团项目中你亲自编写和维护的代码、服务、脚本、接口、任务与部署边界；
2. 除准确率以外的 Agent 工程指标，例如任务成功率、失败类型、重试/降级、执行耗时、线上稳定性。

下一轮访谈应该优先补这两项，而不是补论文叙事。

## 7. 下一步需要补证据，而不是继续搜论文

在开始 v0.2 前，最有价值的是确认以下事实：

- 智能经营分析中你实际写了哪些服务、脚本、工具定义、Prompt/规范、定时任务和评测程序；
- Agent 运行失败时是否有超时、重试、兜底、人工接管或回放机制；
- 100 题集的分母、判定规则和 80%+ 的具体范围；
- 指标平台路径“接近 100%”是何种样本与时间窗口；
- 活动配置十几分钟的耗时来自系统日志还是运营反馈；
- 是否存在可以脱敏展示的流程图、评测表或 badcase。

这些问题直接对应 Agent 开发 JD，也决定简历能否从“会用内部平台”提升为“能做生产级 Agent 工程”。

## 8. 本轮结论

1. 主路线收窄为 **Agent 开发工程师**，不再使用泛大模型或论文型候选人作为核心对标。
2. 当前最匹配的是业务/数据 Agent 开发，不是模型算法，也不是纯 Agent Infra。
3. 没有 Agent 论文不构成这条路线的核心缺口；生产工程证据和个人代码边界更重要。
4. 参考简历以 Mumong、刘冉、冉熙的 Agent 工程内容为主，只借鉴各自最强部分，不整份照抄。
5. v0.2 仍采用两页单栏技术简历，但视觉设计要在正文成熟后再单独制作和逐页检查。
