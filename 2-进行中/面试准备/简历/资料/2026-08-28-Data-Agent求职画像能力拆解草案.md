## 术语确认

- 本轮将语音中的“Martin Agent”暂按 **Multi-Agent** 理解。
- 在本人确认前，不把“Martin Agent”作为正式术语记录。

## 深度标尺

| 级别 | 含义 | 面试证据 |
| --- | --- | --- |
| L1 了解 | 知道概念、适用场景和主要限制 | 能说明是什么、什么时候不用 |
| L2 能实现 | 能独立完成小型可运行方案 | 有代码、链路和基本测试，能解释关键参数 |
| L3 能落地 | 能面向真实业务设计、评测、诊断和迭代 | 有失败案例、指标、可靠性控制、观测和取舍 |
| L4 能建设平台/算法 | 能设计通用底座、规模化运行或训练优化体系 | 有 Runtime/Infra、数据飞轮、后训练或大规模平台证据 |

当前业务型 Data Agent 的主要求是：关键链路达到 **L3**；框架和高阶机制按重要性达到 **L2–L3**；不要求整体达到 L4。

## 核心能力分为五类

### 1. Agent 应用与编排工程

必须达到可落地深度：

- 将自然语言需求拆成澄清、规划、检索、工具调用、验证、分析和报告等状态与步骤。
- 掌握结构化输出、Tool Calling、状态管理、条件分支、循环、超时、重试、幂等和失败恢复。
- 能设计短期上下文、任务状态和长期记忆的边界，避免把所有历史对话直接塞进上下文。
- 理解单 Agent、确定性工作流和 Multi-Agent 的取舍，不能把角色数量当作架构能力。
- 能调试模型、工具、检索、状态传递和最终生成之间的错误归因。

最低合格证据不是“使用过 LangChain”，而是能够完整解释一条任务为什么成功、为什么失败、怎样重跑和怎样验证。

### 2. Data Agent 专项能力

这是业务型 Data Agent 区别于通用 Agent 的核心：

- **SQL 与 Text2SQL**：复杂查询、跨表关联、聚合、窗口函数、时间口径、SQL 生成、校验、只读执行和失败修复。
- **Schema Linking**：从问题识别相关库、表、字段、指标和实体，控制无关 Schema 噪声。
- **指标与语义层**：指标名称、业务定义、统计粒度、维度、时间范围、适用场景、版本和负责人。
- **业务口径可信性**：SQL 可执行不等于答案正确；必须验证指标适用性、业务定义和结果解释。
- **数据元信息**：数据目录、血缘、质量、时效、权限和变更历史。
- **分析能力**：能把模糊问题转成可验证的分析假设、查询计划和决策结论，而不只返回一段 SQL。

### 3. 评测、可靠性与安全

这类能力在高质量 JD 中不是加分项，而是核心能力：

- 建立覆盖典型、边界、歧义、越权和失败场景的评测集。
- 分开评估 Schema/指标召回、SQL 执行正确性、业务口径准确性、任务完成率和报告可信度。
- 记录 Trace：模型输入输出、检索证据、工具参数、SQL、执行结果、重试和最终结论。
- 支持 Bad Case 分类、回归测试、模型/Prompt/检索方案对比和版本上线门槛。
- 具备只读账号、表/行/列权限、敏感字段脱敏、SQL 限制、超时/行数限制、审计和 Prompt Injection 防护意识。
- 能同时关注延迟、Token/模型成本、任务成功率和人工接管率。

### 4. 后端与工程化能力

- Python 应达到能写可维护服务的程度，而不是只会 Notebook。
- 能设计 API、异步任务、数据库访问、缓存、队列或任务状态存储。
- 理解并发、超时、重试、限流、熔断、幂等、日志、Tracing、监控和告警。
- 能用 Docker 完成部署，具备基本的测试、CI/CD 和配置/密钥管理能力。
- 能说明模型服务、Agent 服务、工具服务和数据源之间的接口与故障边界。

对于一年左右经验的候选人，不要求证明自己建设过大规模 Agent Runtime，但必须证明可以交付一个可靠的 Agent 应用服务。

### 5. 业务理解与产品化能力

- 能从用户问题中识别业务目标、分析对象、指标、维度、时间范围和决策动作。
- 在信息不足时主动澄清，而不是编造默认口径。
- 能和业务、商业分析、数据、产品及后端团队共同定义成功标准。
- 能把一次分析沉淀成可复用的指标知识、分析 Skill、工具或评测 Case。
- 能量化回答是否真正帮助了用户，而不是只展示技术链路跑通。

## Agent 技术要求到什么程度

| 技术 | 业务型 Data Agent 建议深度 | 是否核心 | 达标表现 |
| --- | --- | --- | --- |
| Prompt / 结构化输出 | L3 | 核心 | 能约束输入输出、处理歧义、修复格式错误，并用评测验证调整效果 |
| Tool Calling / Function Calling | L3 | 核心 | 能定义 Schema、校验参数、处理超时/重试/幂等/权限和工具错误 |
| RAG | L3 | 核心 | 能完成语料治理、切分、Embedding、混合检索、Rerank、元数据过滤、引用和检索评测 |
| Text2SQL | L3 | 核心 | 能做 Schema Linking、SQL 生成与校验、只读执行、修复循环及业务正确性评测 |
| LangChain | L2 | 工具，不是能力本体 | 能使用和调试常用抽象，也能脱离框架解释模型、Retriever、Tool 和状态如何连接 |
| LangGraph | L3 | 如果写进项目或简历则需达到核心深度 | 能设计 State、Node、条件边、循环、Checkpoint、人工中断、重试和恢复，并解释状态一致性 |
| Multi-Agent | L2–L3 | 常见但非必选 | 能实现协调者/专业节点协作，定义任务边界、共享状态、交接、冲突和失败恢复；能说明为何不使用单 Agent |
| Memory | L2–L3 | 常见核心 | 能区分会话上下文、任务状态、用户偏好、长期知识和经验，并设计写入、检索、更新和过期策略 |
| MCP | L2 | 常见加分/逐渐接近基础项 | 能封装并接入数据工具，理解能力发现、参数 Schema、权限和错误边界，不要求实现协议底层 |
| GraphRAG / 知识图谱 | L1–L2 | 加分项 | 知道何时关系检索优于普通 RAG，能完成小型实体关系/多跳检索方案并做对照评测 |
| Agent Eval / Observability | L3 | 核心 | 有 Case、指标、Trace、错误分类、回归和方案对比，不把一次 `passed` 当成效果证明 |
| SFT / RLHF / RLAIF | L1 | 业务型岗位加分 | 理解目的、数据和成本；除非投算法岗，不要求亲自建设训练流水线 |
| Runtime / Sandbox / 大规模调度 | L1–L2 | 平台岗核心、业务岗加分 | 业务岗需理解安全执行和隔离；不要求达到专家岗的平台建设深度 |

## RAG、GraphRAG 和 Multi-Agent 的边界

### RAG：需要深入，但重点是“检索正确性”

Data Agent 的 RAG 不只是检索业务文档，还可能检索：

- 表和字段 Schema；
- 指标定义、维度和计算口径；
- 业务术语与别名；
- 经过验证的 SQL；
- 数据权限和质量规则；
- 历史分析经验与 Bad Case。

需要能分别诊断候选召回、重排、上下文组织和最终生成，而不是看到最终答案正确就认为 RAG 有效。

### GraphRAG：不是当前硬门槛

只有在问题强依赖关系和多跳推理时，Graph/知识图谱才明显有价值，例如：

`业务事件 → 可用指标 → 计算方法 → 表/字段 → 权限 → 证据`

当前更现实的要求是理解知识图谱、关系约束和多跳检索，并能做一个可审计的小型原型。没有生产证据时，不应把 GraphRAG 写成既有项目技术栈。

### Multi-Agent：会做，也要会不用

合格深度包括：

- 能把澄清、数据检索、分析和报告拆成专业节点；
- 明确各节点输入输出和共享状态；
- 处理交接失败、重复调用、并行冲突、成本和错误传播；
- 能用评测证明拆分带来的收益；
- 当确定性工作流或单 Agent 更可靠时，敢于不用 Multi-Agent。

## 数据侧到底需要多深

### 对当前业务型 Data Agent：Spark/Hadoop 不是首要深化方向

| 数据能力 | 建议深度 | 原因 |
| --- | --- | --- |
| SQL | L3 | Data Agent 的直接执行语言和可信性基础 |
| 指标体系 / 语义层 | L3 | 决定业务问题和数据之间能否正确映射 |
| Text2SQL / Schema Linking | L3 | 当前核心岗位的直接要求 |
| 数据质量、血缘、权限、时效 | L2–L3 | 决定答案是否可信、可追溯和合规 |
| 数仓建模 | L2–L3 | 需理解事实表、维表、粒度、分层、快照和口径；不要求重新证明完整建仓能力 |
| Spark SQL / 分布式计算 | L2 | 能使用、排查常见问题，理解分区、Shuffle、倾斜和资源成本即可 |
| Hadoop 生态内部原理 | L1–L2 | 了解存储与计算链路；当前不必深入调度、源码或集群内核 |
| OLAP 引擎 | L2 | 理解查询特性和性能边界，能做基本诊断 |
| 数据平台/调度系统建设 | L1–L2 | 业务型岗位为加分；数据平台型 Data Agent 才需要升到 L3–L4 |

因此，当前更值得深化的是：

1. SQL、指标语义和业务口径；
2. Text2SQL 的检索、生成、校验与评测；
3. 数据权限、质量、血缘和结果证据；
4. Agent 编排、可靠性、评测与工程化。

Spark、Hadoop 和完整数仓建设经验可以作为已有数据背景证明保留，但不应挤占当前准备 Agent 核心链路的时间。

## 三类岗位的深度差异

| 能力 | 业务型 Data Agent | 数据平台型 Data Agent | 算法型 Data Agent |
| --- | --- | --- | --- |
| Agent 编排与工具调用 | L3 | L3 | L2–L3 |
| SQL / 指标 / 语义层 | L3 | L3 | L2 |
| RAG / Text2SQL | L3 | L3 | L3 |
| 后端工程 | L3 | L3–L4 | L2–L3 |
| Spark/Hadoop/数据平台 | L1–L2 | L3–L4 | L2 |
| Eval / Observability | L3 | L3–L4 | L4 |
| 模型微调 / RL | L1 | L1–L2 | L3–L4 |
| 业务分析与产品化 | L3 | L2 | L2–L3 |

## 加分项

- GraphRAG、知识图谱和多跳关系推理有真实对照实验。
- 做过 Agent 评测平台、数据飞轮、自动回归或 LLM-as-Judge 校准。
- 具备复杂 Multi-Agent、长任务、Checkpoint、人工接管或失败恢复实践。
- 熟悉 MCP、Skill、Connector 和企业工具生态接入。
- 有高并发、分布式、可观测、成本优化和生产故障复盘。
- 有数据目录、语义层、血缘、权限或数据治理产品经验。
- 有 SFT、偏好优化、RL、模型推理部署或多模态经验；主要面向算法挑战岗。
- 有开源贡献、技术文章、Benchmark 或可公开复现的完整项目。

## 当前画像的一句话版本

> 能把业务问题编排成可执行的数据分析任务，通过语义层、RAG/Text2SQL 和受控工具访问获得可信数据，并用评测、可观测和安全机制把 Agent 做成可交付服务的后端/Agent 工程师。
