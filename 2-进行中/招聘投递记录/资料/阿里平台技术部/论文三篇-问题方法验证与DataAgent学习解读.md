# 三篇论文：问题、方法、验证，以及你该学什么

个人学习用 · 整理日期：2026-09-05。本文是中文解读与学习建议；全文译文单独保存，便于连续阅读。

## 先分清三条路线

| 论文 | 最主要的问题 | 关键做法 | 对你的面试价值 |
| --- | --- | --- | --- |
| SMQ | Agent 知道想查什么，却找不准表、字段、口径和连接 | 先写受约束的语义查询，再编译成 SQL 片段 | 理解语义资产怎样被 Agent 使用；最适合先读 |
| UModel | 数据、实体、关系与访问方式散在各处，Agent 很难连续调查 | 对象化建模、关系导航与统一查询接口 | 学习实体关系建模与服务接口设计 |
| Sema-SQL | 一部分问题根本不是普通 SQL 能表达的 | 关系算子与 LLM 语义算子组成混合查询计划 | 理解 Agent 后面的查询规划、执行与成本控制 |

SMQ 的作者单位不是阿里；UModel 有阿里参与合作；Sema-SQL 作者来自阿里与密歇根大学。这是论文署名关系，不能推出 DataWorks 已采用三篇里的具体方案。[SMQ](https://arxiv.org/abs/2606.31041v1)、[UModel](https://arxiv.org/abs/2606.04799)、[Sema-SQL](https://arxiv.org/abs/2604.23477v2)

这里最容易混淆的是“语义”两个字：**语义层主要描述数据的业务含义；语义算子则让模型参与数据处理。** 给 GMV 定义口径与让模型总结客户评论，是两类工作。

## 一、SMQ：把“理解业务”与“拼对 SQL”拆开

[中文全文译文](论文-SMQ语义层Agent-中文译文.md) · [英文原文](https://arxiv.org/html/2606.31041v1)

### 1. 它真正解决什么问题？

用户说“分渠道看上月净收入”，数据库里可能只有缩写字段、订单明细、退款流水和历史渠道映射。直接生成 SQL，模型需要同时完成：

- 理解“净收入”包含哪些款项；
- 判断订单、退款和渠道应该怎样连接；
- 选择时间字段、聚合粒度和 SQL 方言；
- 再把这些决定组合为可执行程序。

SMQ 的核心不是让模型背更多 SQL，而是把相对稳定、可复用的业务映射提前放进语义模型。Agent 在业务概念上选择，编译器负责其中可以确定化的查询构建。

### 2. 它具体怎样工作？

先为数据库整理语义模型：给数据元素命名、解释含义，定义物理表达式、维度、度量、指标和连接。Agent 可以查阅这些元素。

随后，Agent 生成 SMQ，其核心字段是 `metrics`、`filters` 和 `group_by`。引擎把它转换为目标方言 SQL，并返回少量预览数据。遇到复杂问题，Agent 会取回多个查询片段，继续用 CTE、窗口函数等组织最终 SQL，然后执行。

理解这个方案的关键是两条边界：

1. 语义模型负责“业务词与数据怎么对应”；它不是临时把整份 Schema 塞进提示词。
2. SMQ 只覆盖常用查询核心；论文并没有让所有复杂 SQL 都经过完整的确定性编译。

例如，下列是帮助理解的自拟表达，不是原论文或 DataWorks 的正式接口：

```json
{
  "metrics": ["net_paid_amount"],
  "filters": [{"field": "paid_date", "op": "between", "value": ["2026-08-01", "2026-08-31"]}],
  "group_by": ["channel"]
}
```

它的意义不是 JSON 更整齐，而是后台有机会在执行前检查：指标存在吗？该维度允许用于这个指标吗？连接会不会重复计数？时间字段是否匹配指标口径？

### 3. 作者怎么验证？

论文在 Spider2-snow 的 547 个企业查询任务上报告 515 个成功，即 94.15%。模型为 Gemini 3 Pro preview，Agent 每题最多 20 轮。虽然架构支持多个后端，这张主结果表对应 Snowflake 评测；按 SQLite、BigQuery 等分类是数据来源分类。

应注意成绩分布：Snowflake 来源的小类为 10/18，明显弱于总体。这比单记一个 94.15% 更值得学习：平均成绩很高，仍可能遮住特定场景的薄弱点。

整体实验支持“这套系统能完成较复杂的企业查询”。但它没有在完全相同基础模型、知识输入与预算下干净地隔离语义层的单独贡献；也没有证明语义模型可以低成本自动生成。整理过的模型本身就是关键输入。[论文第 VII—VIII 节](https://arxiv.org/html/2606.31041v1)

### 4. 它与你的 Data Agent 有什么关系？

如果你的 Agent 已经会“理解问题—检索—生成 SQL—执行—解释”，SMQ 提供了一个改造方向：不要让每次问答重新发现同样的业务规则，而是把这些规则变成稳定、可版本化、可检查的资产。

你可以对照自己的项目检查：

- “指标口径”目前是提示词、文档片段，还是结构化对象？
- 检索返回的是相似文本，还是连同公式、维度、连接和适用范围的完整指标？
- SQL 出错后，能区分检索遗漏、语义选错、编译错误和最终组合错误吗？
- 修复一道问题，是只加一个例子，还是沉淀了可迁移规则？

这些是迁移建议，不表示你现有项目已经实现了这些能力。

### 5. 最应该学什么？

优先看 III—V 节，弄清语义模型、SMQ 与 Agent 工具循环。再看 VII—VIII 节，理解评测与维护成本。

最值得练的不是复刻榜单，而是：手写一个包含两张事实表、一张维表、三个指标的语义模型，设计三种非法查询，并说清它们应在哪一步被拒绝或要求澄清。

面试可能追问：“为什么不直接 Text-to-SQL？”好的回答应解释可复用知识、约束检查和定位错误的收益，同时承认语义模型维护与表达能力的成本。

## 二、UModel：让 Agent 面对业务对象，而不只是分散的数据接口

原题：*UModel: An Agent-Ready Observability Data Modeling Method at Scale*，2026-06-03。[论文入口](https://arxiv.org/abs/2606.04799)

### 1. 论文中文概述

UModel 面向可观测性与故障诊断：将实体、观测数据、知识及关联统一建模，以 U-SPL 和 MCP 支持 Agent 按对象查询、沿关系调查，并用任务型工具整理证据。作者在 138 个注入故障上比较同类 ReAct Agent：带冗余惩罚的定位指标 LA 从 55.96 升至 64.08，增加 8.12 个百分点；另有组件消融和工具层级对比。作者报告了阿里云生产应用。这些结果支持该场景下的模型与接口组合价值，不等于 DataWorks 问数效果。[论文](https://arxiv.org/html/2606.04799v1)

原论文图 2，用一个对象关系示例理解它的建模方向：

![UModel 原论文图 2：对象与观测数据的关联示例](https://arxiv.org/html/2606.04799v1/example.png)

### 2. 从公开实现继续理解“怎么做”

比抽象地说“知识图谱”更有用的是看它暴露的模型边界。官方 UnifiedModel 仓库把实体类型、数据集、存储位置与链接分开；业务对象不必等同于一张物理表。这个语义运行层也不替代底层数仓。[对象图语义层说明，固定版本](https://github.com/alibaba/UnifiedModel/blob/c36450a2e9b7c398aa1d79c42cb9d13a91cc6f8b/docs/zh/concepts/object-graph-semantic-layer.md)

查询服务统一接受 `.umodel`、`.entity`、`.entity_set`、`.topo` 等入口。一个很重要的实现细节是：在所查版本的 Query Service 中，`get_logs`、`get_metrics` 可把实体字段映射到数据集，再映射到存储查询，返回下游计划；**返回计划并不等于已经执行查询**。知识与工具的实际运行也有独立 Runtime 职责。[Query Service 指南，固定版本](https://github.com/alibaba/UnifiedModel/blob/c36450a2e9b7c398aa1d79c42cb9d13a91cc6f8b/docs/zh/guides/query-service.md)

这里用的是公开仓库 2026-08 的版本，不能当成六月论文实验代码的逐行说明。

### 3. 怎样迁移到你的 Data Agent？——原创设计练习

以“门店昨天成交下降”为例，可以先把对象建模为：

- 门店：唯一标识、所属区域、业务状态；
- 成交指标：口径、粒度、时间范围、可用维度；
- 数据集：订单与退款等来源；
- 关联：门店属于区域，订单发生于门店，退款关联订单；
- 分析方法：按渠道比较、按时段分解、检查数据延迟。

这时，Agent 不必从几十张表里临时猜门店编码，也不应因为两个字段都叫 `id` 就连接。它先确定对象和关系，再选择分析方法与数据。

需要进一步思考：业务关系存在，不代表统计上有因果关系。“某渠道下降”和“这个渠道导致整体下降”的证据要求不同；对象图只帮你组织调查，并不替你完成因果验证。

### 4. 怎么学习它的验证思路？

重点学“数据表示改变后，如何判断 Agent 真正受益”，可以为你自己的项目设计对照：

- 固定模型、任务集、上下文和调用预算，只变更数据接口；
- 将“能否找到全部必要证据”与“最终答案评分”分开；
- 记录工具错误、重复查询、证据压缩丢失和调查路径；
- 既统计平均值，也看困难样本和退步样本。

这是建议你采用的评测设计，不是声称原论文已经满足全部条件。

面试可能追问：“什么时候值得建图？”可以答：当跨对象、多跳关系和可复用映射确实构成主要困难时；只有少量固定指标的问数，不一定需要引入完整对象图运行时。

## 三、Sema-SQL：让“数据库计算”和“模型理解”进入同一个查询计划

[中文全文译文](论文-Sema-SQL-v2-中文译文.md) · [英文原文 v2](https://arxiv.org/html/2604.23477v2)

### 1. 它解决的不是普通 NL2SQL

即使 SQL 写得完全正确，数据库也未必能完成这些任务：

- 两家系统中的客户名称不同，需要判断是否同一实体；
- 所需属性不在库中，需要补充外部知识；
- 用户要分析一堆评论，而不是对结构化数值求和。

Sema-SQL 因此引入混合关系代数 HRA，把普通选择、投影、连接、聚合，与模型驱动的过滤、映射、连接、排序、汇总放在一个声明式计划里。

对你的岗位而言，论文中的“语义模型生成”只是前置环节之一，主线是混合查询系统，不能因为名称含 Sema 就当作 DataWorks 语义生成服务的设计文档。

### 2. 它的三个阶段

**生成。** 用带业务解释的模式信息为模型提供上下文；筛选相关表列及必要连接；把问题拆成算子步骤；为 LLM UDF 写清输入、输出与自然语言任务；解析失败后利用错误反馈修正。语义算子的成本更高，生成时需要解释为什么普通 SQL 不够。

**优化。** 先利用传统数据库优化关系部分，再考虑昂贵 UDF 的位置。比如先用 SQL 将“某年的比赛参赛者”过滤出来，再让模型判断国籍类别。反过来，若便宜且高选择性的语义过滤能大幅减小后续连接，也可能值得提前执行。不是一律“越晚调用模型越好”。

**执行。** 针对语义连接，把两侧记录分批，让一次调用判断多组匹配。批次越大不一定越好：上下文空间、记录长度、输出量和任务难度都会影响准确率与成本。论文同时讨论模型调用数与 Token，而不是只看 SQL 时间。

### 3. 作者怎么验证？数字应该怎样读？

基准为 TAG 的 80 个问题，加上作者扩展的 40 个问题，共 120 个，覆盖 5 个领域。实验使用四个基础模型，比较 Text-to-SQL、混合问答和语义算子系统，并进行生成组件消融、计划优化和连接算法对比。

| 报告结果 | 正确含义 | 不应理解成 |
| --- | --- | --- |
| 93.3% | 最优配置下查询生成正确率 | 最终回答准确率 |
| 89.2% | Claude 配置下端到端答案准确率 | DataWorks 产品准确率 |
| 时间下降 28%、Token 下降 21% | 在发生优化变换的 33 条查询上比较 | 所有 120 题都获得同等收益 |
| 语义连接调用减少 93.3% | 10 个连接案例上的平均调用缩减 | 准确率提高 93.3% |

对照也有不对称之处：LOTUS、Palimpzest 使用专家编写流水线；某些排序和总结答案由模型 Judge 评分。因而应同时看“是否自动生成”“答案质量”“调用成本”，不能只按一列准确率给系统排优劣。[第 VI 节与表 2—5](https://arxiv.org/html/2604.23477v2)

### 4. 顺着公开代码，实际学到了什么？

本次静态阅读了固定提交里的两个文件，没有执行付费模型实验。

第一个是 [schema_generator.py](https://github.com/semasql/SEMA-SQL/blob/b4866921ad0843c73a6966aca0cdd89082da1cf1/src/semasql/db_utils/schema_generator.py)。其生成路径先读取 SQLite 结构和已有 CSV 字段说明，再采样列值，调用模型生成 YAML。文件中使用 YAML 解析检查输出能否读入。

这个原型很有启发，但它也说明：**“生成了一份可解析 YAML”与“生成了可靠的企业语义层”之间还有明显工程距离。** 最值得补充的学习点是来源定位、跨表关系校验、业务冲突处理、质量评测和增量更新，而不只是提示词写法。

第二个是 [symbolic_verification.py](https://github.com/semasql/SEMA-SQL/blob/b4866921ad0843c73a6966aca0cdd89082da1cf1/src/semasql/core/symbolic_verification.py)。该模块的符号建模范围有限，不能仅凭“用了 Z3”就认为完整 SQL 语义已被证明。具体检查见附录；没有据此推断整个项目的实验无效。

### 5. 它与你的 Data Agent 有什么关系？

如果你的需求主要是“把指标算对”，应先解决语义模型与普通 SQL，不要急着增加 LLM UDF。

当需求包含评论分析、实体匹配等内容时，这篇才直接有用。例如，先用 SQL 筛选某地区本月有投诉的订单，再用模型把投诉文本分类，最后聚合占比。你需要能解释：

- 哪些步骤可以确定性计算，哪些真的需要模型；
- 类别定义改变后，旧结果能否复用；
- 一条文本分类错误，怎样传导到最终比例；
- 批量推理如何同时评价成本和质量。

特别要避免把“模型知道的常识”自动当成业务事实。若分析依赖外部人口、公司归属等数据，实用系统更适合接入有时间与来源的事实数据，或明确标记推断性质。

### 6. 最应该学什么？

先读第 3 节语义上下文与问题分解，再读第 4—5 节成本和执行，第 6 节练习评测解读。HRA 的全部形式化细节可以放后面。

面试可能追问：“SQL 先过滤再调用模型，总是更好吗？”回答应包含选择率、单次调用成本、批处理效率和算子依赖；任何重排都要满足实际支持的等价条件。

## 四、把三篇连接到你可能负责的工作

以下是学习上的分工图，不是 DataWorks 内部架构：

```text
现有 SQL / 元数据 / 业务规则
              ↓
生成与维护语义资产                  ← 你关注的岗位假设
              ↓
    ┌─────────┼──────────┐
    ↓         ↓          ↓
指标/查询接口  对象关系访问   混合查询计划
参考 SMQ     参考 UModel    参考 Sema-SQL
    └─────────┼──────────┘
              ↓
Agent 使用数据完成分析任务
              ↓
任务质量、成本和人工修正反馈
```

三个方向共同提醒你：Agent 能力并不只来自模型。数据如何描述、查询怎样表达、接口返回什么、错误在哪里被发现，都会影响最终结果。

但你的阅读重心应与岗位假设一致：**先弄懂如何生产并验证高质量语义资产，再研究 Agent 怎样消费它；混合语义执行作为扩展能力。**
