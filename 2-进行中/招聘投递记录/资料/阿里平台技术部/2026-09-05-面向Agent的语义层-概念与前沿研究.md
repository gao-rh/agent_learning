## 1. 重新理解岗位定位

用户本轮判断：“它应该语义层这个东西是核心，但下面三个我觉得不一定是核心。”这里对应上一轮并列提出的公共层、流批架构、质量与 SLA。

Codex 重新阅读后的判断：描述 1 明确要求主导面向 Agent 的新型语义层设计与落地，并改变数据资产的消费方式，是最有辨识度的目标。描述 2、3 说明候选人还需具备数据交付和运行保障能力。上一版题目覆盖面较广，容易给人几个方向同等重要的印象，应调整为“围绕语义层理解相关的数据工程能力”。这是对 JD 的解释，实际工作占比和面试权重仍待团队核实。

按这个定位，核心问题是：如何把企业已经积累的数据、业务定义与使用经验，建设为多个 Agent 能发现、正确理解和可靠调用的公共能力。

## 2. 语义层具体是什么

语义层为物理数据提供业务概念、计算规则、关系及消费接口。例如，使用者说“支付金额”，系统需要知道对应哪项定义、哪些记录、什么时间口径、可以按哪些维度分析，以及怎样计算。传统 BI 已经需要这类能力；Agent 增加了自然语言消歧、动态选择资产、多步探索和上下文供给的需求。[dbt MetricFlow](https://docs.getdbt.com/docs/build/about-metricflow)、[Snowflake Semantic Views](https://docs.snowflake.com/en/user-guide/views-semantic/overview)提供了可执行语义建模的产品实例。

语义层通常表现为逻辑模型和服务，可以采用 YAML、数据库对象、关系图、查询编译器等形式。大体量业务数据仍可保存在原来的数仓或湖仓；是否物化、预聚合或建设实例图，取决于查询需求。

下面是为了说明机制设计的例子，业务规则均是假设，不代表阿里真实口径：

用户问：“2026 年 8 月，华东地区的客单价是多少？”

| 需要明确的语义 | 示例中的约定 |
| --- | --- |
| 指标定义 | 客单价 = 有效支付金额 / 有效支付订单数 |
| 分子分母范围 | 都排除测试订单；是否扣除退款另有明确约定 |
| 事实粒度 | 一行一个订单；重复事件不能产生额外订单 |
| 时间 | 按支付时间，使用上海时区，区间为 8 月 1 日至 9 月 1 日左闭右开 |
| 地区 | 采用订单成交时的收货地区，与商家所在地不同 |
| 聚合规则 | 先汇总金额和订单数再相除，不能直接平均各日客单价 |
| 数据映射 | 将这些业务概念关联到实际字段、表达式和允许的连接路径 |

这张表中的规则一部分可编码成结构化字段、表达式和校验条件，一部分需要业务说明和例子。关键在于区分“供模型理解的说明”和“执行时真正生效的约束”。写在 Prompt 中的规则不会自动变成数据库约束。

一个概念性的请求可以是：

```json
{
  "metric": "average_paid_order_value",
  "filters": {"shipping_region_at_purchase": "east_china"},
  "time_range": {
    "start_inclusive": "2026-08-01",
    "end_exclusive": "2026-09-01",
    "timezone": "Asia/Shanghai"
  }
}
```

这是本文原创示意接口。系统还需根据已发布定义解析它、校验调用者权限和维度兼容性，然后生成具体查询。请求短并不表示底层逻辑简单；复杂性被放进了可复用的模型和执行服务。

## 3. 近期工作可以归纳为四个方向

以下是 Codex 对本轮来源的归纳，并非学界统一分类；几个方向可以组合。

### 方向一：让语义定义参与查询执行

将指标、维度、数据关系和物理表达式显式建模，Agent 提出结构化查询意图，由引擎解析和编译。这个方向有利于复用复杂计算规则，也面临表达能力与灵活性的取舍。

2026-06-30 的 [A Semantic-Layer-Mediated Agent for Natural Language to SQL over Heterogeneous Enterprise Databases](https://arxiv.org/html/2606.31041v1) 使用 SMQ 中间表示与确定性 SQL 编译器。复杂查询仍由 Agent 在编译片段上补充。论文报告 Spider2-snow 547 题上达到 94.15%，但依赖逐库整理的语义知识；对照系统可用知识不同，作者也讨论了针对题集整理语义层的过拟合风险。当前为预印本，页面注明已投 FITAT 2026。

与岗位的联系：可能需要建设“语义对象 → 查询接口 → 执行计划”的能力，并明确长尾查询怎样扩展、怎样验证。

### 方向二：建设资产的业务含义和使用知识

大型数仓常有多个名字相近、用途不同的资产。Agent 除了找到候选，还需要了解实体、适用场景、不适用场景、计算口径和示例用法。

2026-07-30 的 [A Structured Knowledge Infrastructure for Domain-Specific Data Asset Discovery](https://arxiv.org/html/2607.27748v1) 报告了小红书商业广告数仓的实践：图引导候选筛选、意图路由和场景排序，并向下游提供资产标识及相关知识片段。论文明确记录适用与不适用场景，也采用专家审核维护更新。其评测主要是资产命中与知识覆盖，未验证端到端 SQL 答案准确率；主要基线是旧的 BM25 式检索，不能据此宣称全面胜过所有向量检索。当前为预印本，已投 DAI 2026 Industry Track。

与岗位的联系：元数据和血缘的价值会落到“如何生成并维护可靠的业务语义”；检索需要判断候选能否用于当前问题。

### 方向三：扩展为对象、关系和业务知识模型

当 Agent 需要跨对象探索时，可以把客户、订单、服务等定义成有类型的对象，声明属性、关系、约束及数据绑定。本体是这种业务概念体系的一种表达；知识图谱可承载其中的对象和关系。具体系统未必需要 RDF/OWL 或专门的图数据库。

2026-06-03 的 [UModel: An Agent-Ready Observability Data Modeling Method at Scale](https://arxiv.org/html/2606.04799v1) 将实体、遥测和专家知识组织为对象及语义关系，并提供统一查询语言 U-SPL。作者报告阿里云部署经验，还将查询封装成面向任务的分析工具，以减少主 Agent 处理原始查询和结果的负担。它属于可观测性与故障诊断研究，不能直接视为流通中心数仓方案。

[Microsoft Fabric Ontology 官方文档](https://learn.microsoft.com/en-us/fabric/iq/ontology/overview)也体现了实体类型、属性、关系、规则及数据绑定的产品方向；访问时仍标为 preview。JD 的“可推理”与此相关，但仅凭这三个字，不能确认团队要建设完整本体系统。“能沿关系查询”也不自动意味着能证明业务因果。

### 方向四：从现有资产自动提取并持续修正语义

值得研究的建设方法包括：读取加工代码与元数据、抽取候选定义、解决来源冲突、人工确认业务含义、测试并发布、根据反馈更新。这里存在两个不同场景：用 Agent 帮助建设语义层，以及让业务 Agent 消费语义层。

[阿里云 DataWorks：Data Agent 语义分析](https://help.aliyun.com/zh/dataworks/user-guide/data-agent-semantic-analysis)提供了具体实现入口：结合 SQL、调度任务和表元数据生成 YAML，包含数据集、指标、派生公式与 AI 上下文，支持人工编辑后加载到 Agent 会话。文档体现的是自动提取和上下文供给，尚不足以证明其全部业务规则由确定性编译器强制执行。页面未显示可核实的完整更新日期，本条使用 2026-09-05 访问日期。

2025-03-31 的 [Snowflake Agentic Semantic Model Improvement](https://www.snowflake.com/en/blog/engineering/agentic-semantic-model-text-to-sql/)则展示用多个 Agent 改善关系、描述与指令并评估结果的思路。这是一篇明确标注年份的厂商工程文章，实验使用筛选后的四个 BIRD 数据域；本文借鉴其改进流程，不将其提升幅度当作通用承诺。

## 4. 一个可讨论的建设流程

以下是结合上述方向提出的设计草案，不是某篇论文或阿里内部系统的原图。

```text
业务定义、加工 SQL、表结构、血缘、报表及已验证问答
  → 提取候选语义，保留来源并暴露冲突
  → 建立有类型的实体、指标、维度、关系和适用条件
  → 业务确认、静态检查、查询验证，发布版本
  → 提供资产发现、定义读取、受控查询等接口
  → Agent 根据问题选择语义对象、澄清歧义并调用
  → 记录结果和失败，更新定义并回归验证
```

其中需要认真设计的工程问题包括：

- 一个定义应引用哪些可核查证据？SQL、注释和业务文档冲突时如何处理？加工代码反映当前实现，业务制度反映预期含义，两者都不能无条件代替另一方。
- 什么内容必须结构化？主键、连接关系、计算表达式、版本等应尽可能可解析；说明、反例和业务背景可以补充模型上下文。
- 查询不满足声明的粒度、时间或维度约束时，接口应返回什么错误或澄清信息？
- 多个 Agent 能否共享一套定义？调用时如何取得一致的定义版本、数据时点和身份权限？
- 什么变化需要重新验证？表结构更新、指标改口径、模型升级、检索策略变化都可能改变结果。

2026-08-17 的 [Snowflake 内部 Context Layer 实践](https://www.snowflake.com/en/blog/snowflake-internal-context-layer-for-ai-agents/)强调语义模型的版本、评审、测试和真实用户问题评测，也讨论底层性能对 Agent 的影响。它解释了 JD 为什么同时要求数据工程能力：语义模型要在实际数据与运行条件下提供服务。

## 5. 怎样判断研究真的有效

需要分别观察三个环节，避免用一个指标替代全部效果：

| 环节 | 需要验证的结果 | 典型误判 |
| --- | --- | --- |
| 发现 | 能否找到正确资产及其使用知识 | Hit@10 很高就宣称回答准确 |
| 理解与计划 | 是否选对指标、时间、实体、维度和适用条件 | SQL 可以执行就认为语义正确 |
| 执行与回答 | 结果、权限、时效、解释是否符合预期 | 只比较一次结果相同，忽略数据边界 |

验证集应包含未参与语义定义编写的问题，以及同义不同义、粒度变化、退款/迟到、跨期、权限和来源冲突等反例。评估自动建设时，还需检查定义来源准确性、维护成本与跨域泛化。

2026-04-28 的预印本 [Semantic Layers for Reliable LLM-Powered Data Analytics](https://arxiv.org/abs/2604.25149)报告，在一个零售数据集的 100 个问题上，增加手工编写的 4 KB 业务说明，使三个模型的准确率各提升 17—23 个百分点。这支持显式提供业务含义的价值，但实验是单数据集、单轮查询，不能证明复杂执行服务已被替代。本轮仅核对摘要与提交信息。

## 6. 建议先读哪些资料

阅读建议属于本次草案，不自动写成正式学习计划。

1. [DataWorks 语义分析](https://help.aliyun.com/zh/dataworks/user-guide/data-agent-semantic-analysis)：中文，先看其输入和产物，获得具体印象。
2. [dbt MetricFlow 概念](https://docs.getdbt.com/docs/build/about-metricflow)：理解指标、维度、关系如何参与 SQL 生成。
3. [SMQ 论文](https://arxiv.org/html/2606.31041v1)：重点看 III—V、VIII，理解 Agent 与编译器的职责和表达范围。
4. [小红书资产知识论文](https://arxiv.org/html/2607.27748v1)：重点看知识结构、场景标注、评测定义和维护流程。
5. [UModel](https://arxiv.org/html/2606.04799v1)：需要理解跨对象分析与更广义 Agent 数据接口时再看。

补充入口：[Databricks Agent metadata](https://docs.databricks.com/aws/en/uc-semantics/agent-metadata)（页面更新 2026-07-17）展示指标如何附加展示名称、格式和同义词；[Apache Ossie](https://github.com/apache/ossie)及[核心规范](https://github.com/apache/ossie/blob/main/core-spec/spec.md)展示跨工具交换语义模型的方向。Ossie 访问时为 Apache 孵化项目，原名 Open Semantic Interchange。标准交换格式与具体查询执行、业务定义正确性是不同问题。

## 7. 对面试准备的具体修正

原题目可以保留作覆盖清单，但应先围绕这五个问题组织理解：

1. 面向 Agent 的语义层究竟存什么，提供什么接口，解决什么数据消费问题？
2. 怎样从现有 SQL、元数据、指标平台和业务知识建设它，并处理冲突和变更？
3. Agent 的自然语言意图怎样映射成可执行、受约束的请求？
4. 描述、场景知识、关系图、确定性计算各承担什么职责？
5. 怎样证明 Agent 选对并用对了数据，而非只展示几个成功案例？

流批、公共模型和质量治理的相关追问可以围绕语义层展开：不同引擎能否兑现同一口径，模型粒度是否支撑所需指标，语义定义与数据是否同时有效。尚不能推断这些技术不会单独考察。
