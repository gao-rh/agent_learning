# DataWorks：现在做成了什么，具体怎么做

个人学习用 · 核验日期：2026-09-05。以下以官方产品文档和公开源码为依据；界面描述来自文档，不是登录你的云账号后的实测。

## 结论先说

从公开功能看，DataWorks 已不只是“给模型一份字段字典，让它写 SQL”。目前可辨认出三块：**知识生产与检索、语义模型生成与维护、Agent／ChatBI 消费。**

你提出“可能去改进语义生成服务”的判断与这些产品模块吻合，是值得按此准备的工作假设；但具体归属应在面试里确认。尤其不要将 Context Graph、语义分析任务、DataWorks Semantic Skill 和 UModel 当成同一个东西。

## 1. 知识库：范围较广的知识生产与检索

官方入口叫 Context Graph（知识库）。它以实例方式管理个人或企业知识，页面可浏览业务域、语义知识和资产关系。输入可以来自工作空间资产，也可以补充业务文档；自动生成会利用元数据、代码、血缘等，可选采样画像。

文档写明首次全量、后续增量和每日更新；构建经过生成、发布及索引环节，成功的新版本才生效，失败保留旧版本，并避免旧任务覆盖新结果。采样失败的表可能跳过，因此任务完成不代表每张表都获得了同等完整的知识。[Context Graph 官方说明](https://www.alibabacloud.com/help/zh/dataworks/user-guide/dataworks-knowledge-base-user-guide)

**我的理解：** 这一层的产品价值是把零散技术信息变为能查找、能解释业务、能持续维护的共享知识。做得好不好，不应只用“生成了多少描述”衡量。

## 2. 语义分析任务：更接近你关注的生成服务

在 Data Agent 设置中心可创建语义分析任务，选择业务域、代码空间、重点表和参考资料。文档描述两路分析：读取实际 SQL／调度加工逻辑，分析重点表元数据，再交叉验证合并。

产物以 YAML 表达，包含 `ai_context`、`metrics`、`metric_formulas`、`datasets`。界面支持运行历史、日志、图谱与源码联动查看、编辑和下载。当前该入口重点表为 MaxCompute，单任务最多 30 张，建议先聚焦 5—10 张核心表。[语义分析官方说明](https://help.aliyun.com/zh/dataworks/user-guide/data-agent-semantic-analysis)

这里已能回答“具体在生成什么”：既有业务说明，也有指标表达式、派生公式、物理字段映射和问答上下文。它不是单纯替字段补中文注释。

### 怎么理解这些产物？

下面是为面试准备设计的概念解释，不是对官方 YAML Schema 的完整复刻：

| 信息类型 | 要回答的问题 | 最常见的业务错误 |
| --- | --- | --- |
| 全局上下文 | 这个业务域如何划分？默认时间和数据层级是什么？ | 将业务常识错误套到特殊业务 |
| 指标定义 | 这个指标究竟怎么算？ | 字段名相同但状态、去重或退款口径不同 |
| 派生公式 | 基础指标如何组合？ | 分子分母不是同一人群或时间范围 |
| 数据集与映射 | 具体落在哪些表列？怎么连接？ | 粒度不匹配，多表关联后重复计数 |

**你要解决的困难很可能藏在右边这一列，而不是 YAML 的语法。**

## 3. 消费端已经有两条可见路径

### 路径 A：Data Agent 使用语义制品

新版 Data Agent 官方称基于 Qwen Code，并已在公共云全面开放。交互从旧版侧边栏扩展为全页面实例与会话：实例关联工作空间和 Serverless 资源，界面管理任务、模型和扩展；覆盖开发、治理及分析工作流，也可启用 ChatBI 技能进行问数。[新版 Data Agent](https://help.aliyun.com/zh/dataworks/user-guide/new-data-agent/)

扩展页将 **DataWorks Semantic** 定义为语义 YAML 制品的拉取、快照和回滚工具，将 **DataWorks ChatBI** 定义为数据集选择与分析会话工具。因此，Semantic Skill 是“把产物接到 Agent 工作流”的入口，不能据其名字认定它就是后端生成引擎。专家套件还能组合 Skills、MCP、上下文等组件。[管理扩展](https://help.aliyun.com/zh/dataworks/manage-extensions)

### 路径 B：ChatBI 数据集自动使用语义知识

ChatBI 支持多种数据源，但当前文档中的“开启语义分析”选项仅适用于 MaxCompute。保存数据集时可创建或更新关联任务；结果页有状态、索引文件和 YAML，并提供图谱／源码查看及重跑。启用后，问答会自动召回语义知识。[ChatBI 数据集](https://help.aliyun.com/zh/dataworks/user-guide/dataset-for-chatbi)

所以，要区分三种状态：**后台已生成、消费端已同步、当前这次提问实际召回。** 它们并不是同一件事。

## 4. 这些名字到底是什么关系？

下表是按公开职责进行的阅读归类，不是官方组织架构或内部部署图。

| 名称 | 最适合怎样理解 | 别混淆成什么 |
| --- | --- | --- |
| Context Graph | 知识生产、管理与检索产品入口 | 任意可视化图都等于同一个内部图数据库 |
| 语义分析任务 | 生成和编辑结构化语义产物的任务入口 | 整个平台所有知识生产功能 |
| DataWorks Semantic | Agent 侧操作语义制品的技能 | 后端生成算法本身 |
| ChatBI | 面向数据集的问数与分析消费端 | 语义层的全部用途 |
| Data Agent | 组织工具、代码和技能完成任务的智能体环境 | 单个 Text-to-SQL 模型 |
| UModel / Sema-SQL | 相关公开研究与实现参考 | 已获证实的 DataWorks 内部组件 |

前五项的职责依据上文各官方页面；最后一项的机构和源码关系见[三篇论文解读](论文三篇-问题方法验证与DataAgent学习解读.md)。

目前无法从公开页面确认：两个知识生产入口是否共享核心引擎、语义制品是否遵循完全相同的模型协议，以及你面试的团队分别负责哪些层。

## 5. “具体怎么做”——已知的流程与仍未知的算法

**公开资料能支持的功能流程**是：限定资产范围，收集技术与业务材料，生成结构化语义，供人查看修改，发布或同步到消费入口，再用于检索与分析。

**公开资料还不足以解释**：SQL 是否先经过哪一种 AST 解析器；关系推断如何打分；多源冲突怎样裁决；用了哪些专用模型或训练数据；是否采用 SMQ 式编译器；核心图存储是什么；质量门槛的具体数值是什么。

“文档说交叉验证”不等于我们已经知道了交叉验证的算法。准备面试时，应该能提出一套可落地设计，但明确这是自己的方案。

### 一个贯穿全链路的原创例子

假设你接手的指标叫“日实付金额”，现有材料为：

- 字段注释：支付金额；
- 加工 SQL：仅汇总已支付订单，并排除测试订单；
- 产品文档：有些报表还会扣减退款；
- 两张表都叫 `pay_amt`，但一张以订单为粒度，另一张以门店日为粒度。

此时让模型输出“pay_amt = 实付金额”没有解决真正的问题。

你可以这样设计服务：

**① 固定证据。** 保留 SQL 版本、任务节点、表达式位置、字段来源与文档段落。避免来源已变，而解释仍引用旧定义。

**② 抽取结构。** 从 SQL 中找聚合、过滤、去重、时间、连接以及上游依赖。字段名称只是线索，不能替代计算逻辑。

**③ 生成候选。** 将“已支付、排除测试、是否扣退款、订单粒度还是门店日粒度”等作为显式信息。金额单位和时间含义没有证据时，标记待确认。

**④ 检查冲突。** SQL 能说明当前程序怎么算，产品文档可能说明业务希望怎么算。二者不同不一定谁写错，可能是版本、场景或缺陷问题；应保留差异供确认，而不是让模型自行投票。

**⑤ 验证并发布。** 用已标注样本检查过滤、粒度和公式，再以测试问题观察消费效果。发布资产版本，并记录检索索引和消费者绑定版本。

**⑥ 根据变更更新。** 如果 SQL 改成排除部分退款，定位受影响的指标、下游问答与缓存，而不是重新生成全部内容。

这是你可以在面试里展开的方案；不是声称 DataWorks 已使用以上每一步。

### 一份值得生成的语义记录是什么样？

下面只是教学用契约，不可直接当作 DataWorks 配置上传：

```yaml
id: commerce.daily_paid_amount
version: candidate-2
grain: [store_id, paid_date]
definition:
  aggregation: sum
  amount_column: paid_amount
  conditions:
    - order_status = 'paid'
    - is_test_order = false
  refund_policy: unresolved
evidence:
  - kind: sql_expression
    source: job_daily_store_payment
    source_version: example-revision-17
  - kind: business_document
    source: payment_metric_notes
review:
  state: needs_business_confirmation
  reason: 退款处理在代码与文档中不一致
```

重点是可用事实、证据和待确认项分开，而不是这些字段名本身。

## 6. 做到什么程度了？

我的判断是：**已经能看到产品化工作流和消费接入，但无法据此给语义质量打一个可信的准确率。**

| 维度 | 目前可下的判断 | 还需要的证据 |
| --- | --- | --- |
| 产品形态 | 有任务、产物、编辑与消费入口 | 目标账号实际开放的范围 |
| 运维形态 | 可见历史、日志、版本与增量等机制 | 大规模运行稳定性、失败恢复与成本分布 |
| 语义质量 | 能表达比字段注释更丰富的知识 | 标注规范、独立测试集、错误分类和人工修正率 |
| 使用效果 | 已对接问数和 Agent 工作流 | 同条件前后对照，尤其复杂场景收益 |
| 核心实现 | 有功能说明及外围开源线索 | 生成算法源码或足够详细的技术披露 |

这里的未知不是“他们没做”，而是**公开证据尚不能判断做到多好**。

设置中心还提供模型使用量等运行统计，但 Token、请求量反映使用与成本，不替代业务语义正确率。[设置中心](https://help.aliyun.com/zh/dataworks/user-guide/data-agent-system-settings)

### 如果你负责效果，应该看哪些数？

以下是面试设计建议：

1. 资产覆盖率：应分析的表／指标中，多少真正拿到了足够证据？跳过的算不算分母？
2. 语义准确率：公式、过滤、粒度、连接等分别正确多少？不要只评中文描述通顺度。
3. 人工成本：一百个候选有多少要改，平均改多久，重复运行会不会抹掉人工成果？
4. 更新质量：源变更后多久消费端可用，遗漏影响了哪些查询？
5. 下游效果：同一模型、同一问题与预算下，查询准确率、澄清率、延迟如何变化？
6. 单位成本：每个“通过验收且被使用的语义资产”花费多少，而不是单次调用多便宜。

## 7. 面试里最值得确认的五个问题

这些问题可以帮你判断实际工作内容，不只是展示读过论文。

- 我理解团队已有语义分析与消费流程。这个岗位主要负责生成质量、模型服务化，还是数据公共层与消费接入？
- Context Graph 的知识生产与语义分析任务，是共用引擎还是不同产品线？我们负责哪一段？
- 现在最主要的错误是指标口径、表关系、覆盖率，还是更新后召回不到？有怎样的标注和评测集？
- 人工修订与自动重生成如何合并？衡量改进更看离线准确率，还是用户修订成本与下游任务成功率？
- 这个岗位能否端到端负责一项效果改进：定位问题、构建评测、修改服务、上线观察？
