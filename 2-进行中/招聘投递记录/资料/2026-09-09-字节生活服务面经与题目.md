### 数04｜参考答案

**先说：** 一个数开需求要走完“需求确认、模型与口径设计、开发、验证、上线、运行维护”，交付标准是数据能被下游正确、稳定地使用。

2. 找数据源和可复用模型，确认主键、关联关系、增量方式、历史变更及上下游依赖。
3. 开发抽取和加工逻辑，配置调度、质量规则、负责人及必要的权限。
4. 做样本核对、全量对账、边界测试和性能检查，再与业务验收。

**回答重点：** 需求澄清、正确性验证和上线后的责任都要讲到。这是通用流程，不代表你每个项目都实际实施了全部步骤。

### 数06｜参考答案

**先说：** 建模是在业务需求与源数据约束下，明确业务过程、数据粒度、实体关系和指标的组织方式。面试里常比较关系／ER 建模与维度建模，但“两种模型”也可能指星形与雪花，需要先确认。

关系模型强调实体、关系和规范化，便于统一与减少冗余；维度模型围绕业务过程，用事实与维度支持分析。二者可以出现在同一数仓的不同层。

**落地顺序：** 选业务过程 → 定粒度 → 定维度 → 定事实。例如先明确“一行是一笔订单还是一条订单明细”，再决定放哪些金额及商品属性，不能先堆字段再猜粒度。

依据：[Kimball 建模四步](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/four-4-step-design-process/)。

### 数07｜参考答案

**先说：** 范式主要用于减少不合理冗余及插入、更新、删除异常；日常重点掌握 1NF、2NF、3NF，追问再讲 BCNF。

- 1NF：属性在所采用的数据域中取单值，不把重复组塞进一个字段；“原子性”与建模的数据域有关。
- 2NF：在 1NF 上，非主属性对每个候选键都完全依赖，不只依赖复合候选键的一部分。
- 3NF：直观上避免非主属性对键的传递依赖。严格地说，对每个非平凡函数依赖 X→A，X 是超键或 A 是主属性。
- BCNF：进一步要求每个非平凡函数依赖的决定因素都是超键。

**例子：** 选课表键为“学号＋课程号”，学生姓名只依赖学号，应拆到学生表；学生表里的院系电话由院系决定，可再拆院系表。

**易错点：** 候选键不只有选定的主键；主属性指属于任一候选键的属性。分析数仓允许有目的的反规范化，但要管理冗余带来的一致性问题。

依据：[Microsoft：数据库规范化](https://learn.microsoft.com/en-us/previous-versions/troubleshoot/microsoft-365/microsoft-365-apps/access/database-normalization-description)、[Cornell：3NF 与 BCNF 的形式定义](https://www.cs.cornell.edu/courses/cs4320/2008fa/slides/20081114_fds.pdf)。

### 数08｜参考答案

**先说：** 事实表记录某个确定粒度上的业务事件或状态，维度表提供理解、筛选和分组这些事实所需的描述背景。

例如订单明细事实表记录“一笔订单的一件商品”的数量、金额，并带日期、门店、商品等维度键；门店维度表记录门店名称、类型、城市等属性。Store ID 在事实表里通常是维度外键，在维度表里是业务键或被代理键映射；取值多不会让它变成度量。

**追问：** 事实表不必有数值度量，报名、到场等事件可以建无事实度量的事实表。订单号也可能作为退化维度直接保留。金额是否大于某阈值是一项过滤条件，不会自动改变金额本身的业务语义。

依据：[Kimball 维度建模理论](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/)。

### 数09｜参考答案

**先说：** 星形模型把中心事实与周围维度直接关联，业务人员容易理解，查询路径比较清楚，也便于复用一致的维度和指标。

维度属性适当反规范化后，用户不必沿许多层小表寻找城市、品类等属性。代价是属性冗余，需要统一维度加工、历史变化和质量管理。

**易错点：** 星形不等于“只有一张大宽表”，也不是任何查询都一定最快。雪花模型把维度进一步规范化，选择要看层级复杂度、维护成本和查询负载。连维度前还要确认关联键和历史版本唯一，否则事实会被重复放大。

依据：[Kimball 维度建模理论](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/)。

### 数10｜参考答案

**先说：** 分层是为了隔离源系统变化、复用公共加工逻辑，并让数据来源和责任可追踪。

- ODS 保留接入数据及必要的历史、增量信息，便于追溯。
- DWD 形成统一、清洗后的业务明细；DIM 管理公共维度。
- DWS 面向常见分析粒度沉淀可复用汇总。
- ADS 或应用层按具体消费需求组织输出，可以服务接口、下游数仓或报表。

**易错点：** 这些名称是常见实践，并非强制标准。DWM 可以按复用价值增加；并非每个需求都要逐层落表，层数多也不自动代表设计好。应该解释每层消除了什么重复或隔离了什么变化。

### 数13｜参考答案

**先说：** 抽取先保证数据完整、可重跑；建模再明确业务过程、粒度和复用边界。

小表可按周期全量获取；大表按更新时间等做增量，或通过 CDC 获取变更。增量必须明确游标、重复处理和删除事件，不能只取“今天创建”的记录而漏掉历史订单退款。

接入后保留源标识、业务主键、事件／更新时间和处理批次；统一类型、去重、处理主键与维度关系，再构建明细和汇总。用源端总量、关键金额及明细样本核对，重跑同一批数据应获得一致结果。

**易错点：** 仅以更新时间增量可能漏物理删除和迟到数据；使用重叠窗口时要有幂等去重。这里是通用设计，具体机制要由源系统能力决定。

### 数14｜参考答案

**先说：** MapReduce 把输入分片交给多个 Map，按 Key 对中间结果分区、排序与分组，再由 Reduce 聚合并输出。

流程是 InputFormat／RecordReader 读记录 → Map 生成键值对 → 分区并在缓冲区排序、溢写 → Reduce 拉取对应分区、归并 → 对每组 Key 调用 Reduce → OutputFormat 写结果。Map 可以做解析、过滤、映射，不只是简单读取。

**追问：** Combiner 是可选的本地合并，不能依赖其必然执行；求均值不能把局部均值直接平均，应传 sum 和 count。一个 Map 通常对应一个输入 split，而不是机械对应一个 HDFS block；只有 Map、无 Reduce 的作业也存在。

依据：[Hadoop MapReduce 原理](https://hadoop.apache.org/docs/r3.4.2/hadoop-mapreduce-client/hadoop-mapreduce-client-core/MapReduceTutorial.html)。

### 数15｜参考答案

**先说：** 宽窄依赖看父 RDD 分区与子 RDD 分区的依赖关系。窄依赖中，一个父分区只被一个子分区依赖；宽依赖可能把同一父分区的数据分发到多个子分区，典型实现是 Shuffle。

map、filter、union 通常是窄依赖；需要跨分区聚合、排序或重分区的操作通常产生宽依赖。是否真的 Shuffle，还取决于已有分区方式。

**Job／Stage：** Action 触发计算调度；DAGScheduler 按 Shuffle 依赖划分 Stage，同一 Stage 内可以流水处理窄依赖算子，每个需要计算的分区形成 Task。

**易错点：** 不要把“一段 SQL＝一个 Job”或“Stage 数＝SQL 中聚合数＋1”说成固定公式。子查询、广播、缓存复用、AQE 等会影响实际执行，应看最终物理计划与 Spark UI。

依据：[Spark 3.5.7 RDD 指南](https://spark.apache.org/docs/3.5.7/rdd-programming-guide.html)、[Spark 作业调度](https://spark.apache.org/docs/3.5.7/job-scheduling.html)。

### 数16｜参考答案

**先说：** Spark 里说 DAG，要先明确是 RDD 血缘、SQL 计划还是调度后的 Stage 图。

RDD 血缘图的节点及依赖描述数据由哪些输入和转换产生，包含分区、依赖、计算函数等信息，支撑执行和故障重算；它不是把全部业务记录存进图里。

SQL 先产生逻辑计划，再经优化得到物理计划；调度阶段按依赖组织 Stage 和 Task。因此“DAG 存 SQL 还是存数据”不能直接二选一，应该先确认讨论的是哪层。

依据：[Spark EXPLAIN](https://spark.apache.org/docs/3.5.7/sql-ref-syntax-qry-explain.html)、[Spark 3.5.7 RDD 指南](https://spark.apache.org/docs/3.5.7/rdd-programming-guide.html)。

### 数17｜参考答案

**先说：** Shuffle 是把上游分区的数据，按下游需要的分布规则重新分配。跨节点时涉及网络，并可能伴随序列化、排序和磁盘读写。

按键聚合／Join 常按键哈希分区，范围排序可以按键范围分区，repartition 也会重分布。map、filter 通常在本分区执行，不必 Shuffle。

**追问：** “相同键要一起处理”不等于“必然新增一次 Shuffle”；如果已有可复用的分区分布，某些操作可以避免重新分发。多分区 sortBy 通常需要全局重分布；只有本分区排序则不保证全局有序。

依据：[Spark 3.5.7 RDD 指南](https://spark.apache.org/docs/3.5.7/rdd-programming-guide.html)。

### 数18｜参考答案

**先说：** 两者都需要把中间数据从生产端传给消费端；区别在执行模型和 Shuffle 组织方式，不能概括成“MR 落盘，Spark 不落盘”。

MR 的 Shuffle 连接 Map 与 Reduce，Map 输出按 Reducer 分区并排序，Reduce 拉取、归并后按 Key 分组。Spark 可以在一个 DAG 中有多个 Shuffle 边界，每一段连接两个 Stage；现代常见实现是 sort-based shuffle，也会产生本地磁盘文件。

Spark 的优势还来自多阶段统一调度、流水执行和数据复用。是否排序、如何聚合、内存与磁盘的占用，应根据算子、Shuffle 实现与版本解释，不能把名称相同当作实现完全相同。

依据：[Hadoop MapReduce 原理](https://hadoop.apache.org/docs/r3.4.2/hadoop-mapreduce-client/hadoop-mapreduce-client-core/MapReduceTutorial.html)、[Spark 3.5.7 RDD 指南](https://spark.apache.org/docs/3.5.7/rdd-programming-guide.html)。

### 数19｜参考答案

**先说：** 数据倾斜是分区工作量显著不均，表现通常为少数 Task 特别慢，不能只凭“整个任务慢”判断。

**排查与处理：** 看 Task 时长、输入与 Shuffle 数据量、溢写和 GC；再核对热门 Key、空值和分区规则。Join 可以广播真正能容纳的小表、把热点 Key 单独处理，或使用适用版本的 AQE 倾斜 Join 优化。聚合可以预聚合，必要时加盐后两阶段汇总。

**易错点：** 单个热点键不一定能靠增加普通分区数拆开。加盐后 sum 可再求和，avg 要合并 sum／count，精确 distinct 不能直接把分桶去重数相加。倾斜修复必须先保证结果语义不变。

依据：[Spark 监控指标](https://spark.apache.org/docs/3.5.7/monitoring.html)、[Spark SQL 性能调优](https://spark.apache.org/docs/3.5.7/sql-performance-tuning.html)。

### 数22｜参考答案

**先说：** 先定位问题发生在“解析规划、读、算、写”哪个环节，再区分结果错误与运行故障。

- 解析规划：字段或表不存在、类型不兼容、权限不足、计划膨胀。
- 读：分区未裁剪、全表扫描、源数据缺失或不可读。
- 算：关联放大、数据倾斜、Shuffle 过大、内存不足、GC 或磁盘溢写。
- 写：小文件、目标存储瓶颈、权限、提交失败；重试还可能产生重复。

**做法：** 用 EXPLAIN 看算子、过滤和数据交换，用 UI／日志找第一个异常位置，并核对输出粒度、条数和关键总量。不能看到 OOM 就只加内存，也不能把 SQL 成功结束等同于数字正确。

依据：[Spark EXPLAIN](https://spark.apache.org/docs/3.5.7/sql-ref-syntax-qry-explain.html)、[Spark 监控指标](https://spark.apache.org/docs/3.5.7/monitoring.html)。

### 数23｜参考答案

**先说：** Join 顺序可能影响性能，但 SQL 书写顺序不一定就是执行顺序，优化器可能重排。

中间结果规模、过滤选择性、统计信息和广播策略会改变成本。先在语义允许的范围内过滤、投影、预聚合，更新统计信息，再用 EXPLAIN 判断实际关联顺序、Build 侧和 Shuffle。

**易错点：** “小表永远写左边／右边”不是跨引擎规律；外连接也不能像内连接一样任意交换。把右表过滤条件从 ON 移到 WHERE，可能改变 LEFT JOIN 的保留行，性能优化不能悄悄改结果。

依据：[Spark SQL 性能调优](https://spark.apache.org/docs/3.5.7/sql-performance-tuning.html)、[ClickHouse Join 优化](https://clickhouse.com/docs/guides/joining-tables)。

### 数24｜参考答案

**先澄清：** 原帖的 reduceBy 名称不完整。若指 PySpark RDD.reduceByKey 与 RDD.sortBy，它们分别解决“按键聚合”和“排序”问题，并非两个 Spark SQL 函数。

reduceByKey 输入键值对，用满足结合律和交换律的函数合并同键值，可在 Map 侧先合并，减少传输。sortBy 根据 key 函数安排记录顺序，不把同键记录合成一条。

例如键值对按用户求金额合计适合 reduceByKey；把合计结果按金额排列才是 sortBy。两者是否发生新的 Shuffle 要看分区条件与分区数，不能仅用函数名判断。

依据：[RDD.reduceByKey](https://spark.apache.org/docs/3.5.7/api/python/reference/api/pyspark.RDD.reduceByKey.html)、[RDD.sortBy](https://spark.apache.org/docs/3.5.7/api/python/reference/api/pyspark.RDD.sortBy.html)。

### 数25｜参考答案

**先说：** 小文件常由写入频率高、输出任务或分区过多、历史补数与碎片化写入造成。问题在于元数据、文件打开和任务调度等固定开销被放大。

先统计每个业务分区的文件数、大小分布、写入批次和查询开销，再选择降低过细写入频率、调整写入并行度、合并历史小文件，或使用表格式提供的 compaction。

**易错点：** 合并要与并发写入、覆盖范围和读者可见性协调；不是随便拼文件。也不要为了“只有一个文件”统一 coalesce(1)，这可能制造单点瓶颈。目标文件大小应结合数据量、压缩、存储和查询负载设定。

依据：[HDFS 架构](https://hadoop.apache.org/docs/r3.4.2/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)、[Spark SQL 性能调优](https://spark.apache.org/docs/3.5.7/sql-performance-tuning.html)。

### 数26｜参考答案

**先说：** 可以沿数据流分成接入、存储、计算、服务，以及贯穿全程的调度与治理。

接入负责抽取或接收变更，Kafka 常承担事件传递、缓冲和重放；HDFS／对象存储承载大规模文件；Spark、Flink 负责加工计算；ClickHouse、Doris、StarRocks 等可承担分析查询服务。调度处理依赖和运行，治理管理元数据、质量、口径及权限。

**重点：** 讲清各组件解决的问题和衔接关系，不把产品名字逐个背出来。组件能力有重叠，分类是解释工作链路的方法，不是互斥且唯一的技术分类。

依据：[Kafka 官方介绍](https://kafka.apache.org/intro/)、[Apache Doris 概览](https://doris.apache.org/docs/dev/getting-started/what-is-apache-doris/)。

### 数27｜参考答案

**先说：** MySQL 是数据库，HDFS 是分布式文件系统，不处于同一抽象层。MySQL 管表、SQL、索引及相应存储引擎的事务；HDFS 管文件、块、复制和分布式读写。

典型 MySQL InnoDB 适合按键访问与行级更新；HDFS 面向大文件、高吞吐的数据读写，通常由 Hive、Spark 等计算引擎读取加工，不能把它当作直接支持任意行更新的数据库。

**文件格式：** HDFS 可以保存字节文件，CSV、JSON、Parquet、ORC、Avro 都可以放；文件能存进去，不代表每个上层计算引擎都能解析。HDFS 的普通复制也不等于数据库事务。

依据：[HDFS 架构](https://hadoop.apache.org/docs/r3.4.2/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)。

### 数28｜参考答案

**先说：** NameNode 管命名空间和块位置信息，DataNode 保存数据块并汇报状态；客户端通常直接和 DataNode 交换业务数据。

读：客户端向 NameNode 查询块位置，再按位置从合适的 DataNode 读取，故障时尝试其他副本。写：先申请创建及块目标，数据沿 DataNode pipeline 传输复制，确认信息沿链路返回，结束时完成文件提交。

**易错点：** NameNode 不承担全部文件内容的中转。SecondaryNameNode 做检查点相关工作，不是可直接替换 Active 的热备；高可用要区分 Active／Standby 机制。读写流程还要区分普通复制与纠删码配置。

依据：[HDFS 架构](https://hadoop.apache.org/docs/r3.4.2/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)。

### 数29｜参考答案

**先说：** 分析型数据库针对大量扫描、过滤和聚合优化，常见技术包括列式存储、压缩、向量化执行和分布式并行。

ClickHouse、Doris、StarRocks 都可承接分析负载，但具体选型应看查询类型、关联复杂度、数据更新模式、实时性、并发、成本及团队维护能力。以相同数据、正确查询语义和合理资源配置做测试，比简单背“谁更快”有用。

**易错点：** 了解原理不等于实际使用过，面试时把认知和自己的使用经历分开；也不要沿用“ClickHouse 不支持 Join”这类过时说法。

依据：[Apache Doris 概览](https://doris.apache.org/docs/dev/getting-started/what-is-apache-doris/)、[ClickHouse Join 优化](https://clickhouse.com/docs/guides/joining-tables)。

### 数30｜参考答案

**先说：** StarRocks 常见四类表：Duplicate Key 保留明细和重复行；Aggregate 按键对值列按指定方式聚合；Unique Key 对同键数据保留更新后的值；Primary Key 使用主键模型支持更新、删除等场景。

选择要由“是否需要原始明细、预聚合、频繁更新／删除”决定。主键模型与 Unique Key 的实现和能力不同，不能只因都能更新就视为完全一致。

**Join 比较：** StarRocks 有优化器和多种数据分发／Join 策略；ClickHouse 也有多种 Join 算法且持续演进。不能无条件断言 SR 一定胜过 CK。应对齐版本、数据分布、是否可共置、过滤、统计信息、并发和资源，再比较计划与实测。

依据：[StarRocks 表模型](https://docs.starrocks.io/docs/table_design/table_types/)、[StarRocks 执行计划](https://docs.starrocks.io/docs/best_practices/query_tuning/query_planning/)、[ClickHouse Join 优化](https://clickhouse.com/docs/guides/joining-tables)。

### 数31｜参考答案

**先说：** 要先问清分区指表分区、计算分区还是 Kafka 分区，因为目的和调参代价不同。

- 表分区：按日期等组织数据，利于裁剪和生命周期管理；粒度太细会增加元数据与小文件。
- Spark 计算分区：决定并行任务的数据范围；过少可能单任务很重，过多增加调度开销。
- Kafka 分区：影响并行读写和分区内顺序；增加分区不能让同一消费组在单个分区上无限并行。

**易错点：** 增加分区不保证线性提速，也未必拆得开热点键。还应检查业务键的路由和顺序要求，避免扩分区后改变业务预期。

依据：[Kafka 官方介绍](https://kafka.apache.org/intro/)、[Spark SQL 性能调优](https://spark.apache.org/docs/3.5.7/sql-performance-tuning.html)。

### 数32｜参考答案

**先说：** Kafka 主要负责持久化事件、缓冲、解耦和重放；Flink 从事件流中持续计算，做清洗、关联、窗口聚合等处理，并把结果写到目标系统。

例如订单事件进入 Kafka，Flink 按商户计算窗口金额，再写到分析存储。业务事件时间、乱序迟到和状态恢复主要在计算链路中处理。

**追问：** Kafka 能重放，不代表整条链路自然不重不漏。端到端语义还依赖 Source 可恢复位置、算子状态检查点，以及 Sink 的事务或幂等能力；只说“开了 Checkpoint 就完全 Exactly Once”不完整。

依据：[Kafka 官方介绍](https://kafka.apache.org/intro/)、[Flink 容错与端到端语义](https://nightlies.apache.org/flink/flink-docs-stable/docs/learn-flink/fault_tolerance/)。

### 数33｜参考答案

**先说：** 批流一体希望让同一份业务口径同时服务实时增量和历史重算，但不意味着批和流的执行行为完全相同。

一种参考设计：日志／CDC 接入 → 保留可重放的明细 → 共用 Schema、维度与指标定义 → 实时作业提供低延迟结果，批作业处理历史回补与校准 → 统一结果表或明确覆盖规则。

**需要讲清：** 有界与无界输入、事件时间、迟到修正、维度历史、去重主键、补数和实时任务的冲突、结果验收。引擎可以用 Flink 的批／流能力，也可以组合不同引擎；关键是保证语义和运维规则一致，不是只选择一个工具。

依据：[Flink 批／流执行模式](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/execution_mode/)。

### 数35｜参考答案

**先说：** 规范要能在开发和发布流程中被检查，不能只写文档。

先把命名、分层、主键与粒度、字段类型、公共维度引用、分区与生命周期、负责人等规则说清楚；可机械检查的放到模板、开发校验或发布门禁中，业务口径和合理例外由评审确认。

### 数36｜参考答案

**先说：** 指标去重先比业务语义，不能只按名称或 SQL 文本判断。

### 数44｜参考答案

**先说：** 普通聚合把一组输入汇成一行，窗口函数通常保留输入行，并在指定窗口上产生每行的结果。

常见聚合有 sum、count、avg、min、max；窗口常见 row_number／rank／dense_rank、lag／lead，以及带 OVER 的 sum 等。要说明 PARTITION BY 分组、ORDER BY 排序和 frame 的范围。

**易错点：** count(*) 统计行，count(列) 不计 NULL；avg 忽略 NULL，但零值会参与平均。ROWS 表示物理行范围，不等于自然日；滚动七行只有在每天恰好一行且无断日等条件下才等于滚动七天。

### 数45｜参考答案

**先说：** row_number 在窗口内按 ORDER BY 的规则给每行分配从 1 开始的唯一序号。

例如按用户取最新事件：ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY event_time DESC, event_id DESC)，外层筛 rn=1。event_id 是时间相同时的稳定决胜字段，需要在当前数据中确实能消除并列。

执行时引擎要满足窗口要求的数据分布和排序，可能需要 Exchange 与 Sort；不能说它固定采用某一种独立排序算法。

**区别：** row_number 对并列也给不同序号；rank 并列同名次且跳号；dense_rank 并列同名次而不跳号。窗口排序不保证最终查询输出的全局顺序。

依据：[Spark SQL 窗口函数](https://spark.apache.org/docs/3.5.7/sql-ref-syntax-qry-select-window.html)、[Spark EXPLAIN](https://spark.apache.org/docs/3.5.7/sql-ref-syntax-qry-explain.html)。

### 数46｜参考答案

**先说：** UDF 是用户自定义函数的总称；在 Hive 面试的常见分类里，标量 UDF 是一行输入产生一个值，UDAF 把多行聚合成一个结果，UDTF 可以把一行展开成多行、多列。

例如自定义业务编码解析适合标量函数，自定义可合并统计适合聚合函数，展开复杂数组可用表生成函数。explode 是内置的典型展开操作，不意味着要自己实现它。

**使用原则：** 内置函数能清楚表达时优先内置；确实有稳定的自定义逻辑再写 UDF。要考虑 NULL、异常、确定性、类型和执行开销。跨语言 UDF 可能增加序列化成本，也可能限制某些优化；不同 Spark／Hive 版本的 API 不要混用。

依据：[Apache Hive UDF 分类](https://hive.apache.org/docs/latest/language/hive-udfs/)。

**先说：** 动态分区是在写入时，由每行数据中的分区字段值决定写到哪个分区；静态分区则在语句中写定分区值。

### 数48｜参考答案

**先说：** 先按用户和时间排序，用 lag 找上一次访问；达到断开阈值时标记新 Session，再累加标记生成分组号，最后汇总起止时间和时长。

**示例假设：** 表名 visits，timestamp 为秒，NULL 时间已排除；这里将相隔恰好 30 秒视为断开，用 >=30。若确认是“超过 30 秒才断开”，仅改成 >30。重复的同秒记录不改变起止时间，先按用户和秒去重。

```sql
WITH base AS (
  SELECT DISTINCT user_id, timestamp AS ts
  FROM visits
  WHERE user_id IS NOT NULL AND timestamp IS NOT NULL
), lagged AS (
  SELECT user_id, ts,
         LAG(ts) OVER (PARTITION BY user_id ORDER BY ts) AS prev_ts
  FROM base
), marked AS (
  SELECT user_id, ts,
         CASE WHEN prev_ts IS NULL OR ts - prev_ts >= 30
              THEN 1 ELSE 0 END AS is_new
  FROM lagged
), grouped AS (
  SELECT user_id, ts,
         SUM(is_new) OVER (
           PARTITION BY user_id ORDER BY ts
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
         ) AS session_no
  FROM marked
)
SELECT user_id,
       CASE WHEN MAX(ts) = MIN(ts) THEN 1
            ELSE MAX(ts) - MIN(ts) END AS session_time,
       MIN(ts) AS start_ts, MAX(ts) AS end_ts
FROM grouped
GROUP BY user_id, session_no;
```

**易错点：** 时间差是与上一次访问比较，不是与本 Session 的第一条比较。不能对每个 Session 的时长一律加 1。

依据：[Spark SQL 窗口函数](https://spark.apache.org/docs/3.5.7/sql-ref-syntax-qry-select-window.html)。

**题干未给全。** 先确认是连续自然日、允许中断几天，还是达到 N 天的用户。下面用常见的“每个用户最长连续自然日登录天数”作自拟示例，采用 Spark SQL／Hive 常见日期函数。

```sql
WITH days AS (
  SELECT DISTINCT user_id, TO_DATE(login_time) AS dt
  FROM login_events
  WHERE user_id IS NOT NULL AND login_time IS NOT NULL
), ranked AS (
  SELECT user_id, dt,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY dt) AS rn
  FROM days
), islands AS (
  SELECT user_id, dt,
         DATE_SUB(dt, CAST(rn AS INT)) AS island
  FROM ranked
), streaks AS (
  SELECT user_id, island, COUNT(*) AS streak_days
  FROM islands
  GROUP BY user_id, island
)
SELECT user_id, MAX(streak_days) AS longest_streak
FROM streaks
GROUP BY user_id;
```

**原理：** 连续日期和行号同步增长，日期减行号保持不变；断日后会产生新组。必须先按用户、自然日去重，否则一天多次登录会破坏分组。先统一业务时区，限定日期范围还可能截断跨边界的连续段。

### 数52｜参考答案

```python
odds = [n for n in range(101) if n % 2 == 1]
print(odds)
```

range 的右边界不包含在内，所以用 101 表示包含 100 的候选范围；结果为 1、3……99。也可用 list(range(1, 101, 2))。推广到 N 时，时间和输出空间都为 O(N)。

### 数53｜参考答案

**先确认编码规则：** 是调用者指定类别映射，还是按首次出现顺序。下面采用首次出现映射为 0，第二个不同值为 1；空输入返回空列表，超过两个类别报错。

```python
def encode_binary(values):
    mapping, result = {}, []
    for value in values:
        if not isinstance(value, str):
            raise TypeError('输入必须是字符串')
        if value not in mapping:
            if len(mapping) == 2:
                raise ValueError('超过两个类别')
            mapping[value] = len(mapping)
        result.append(mapping[value])
    return result
```

时间 O(n)，映射额外空间 O(1)，返回结果空间 O(n)。若跨批次用于同一数据链路，映射必须固定并复用；每批重新按首次出现分配会导致同一个类别的含义翻转。

### 数54｜参考答案

**先说：** 回文两边成对出现，因此至多允许一个字符出现奇数次，其余必须为偶数；空串也可以视为回文。

```python
from collections import Counter

def can_permute_palindrome(text):
    return sum(count % 2 for count in Counter(text).values()) <= 1
```

时间 O(n)，空间 O(k)，k 是不同字符数。是否忽略大小写、空格、标点应先确认；代码将它们视为普通字符，不悄悄清洗。

依据：[Python Counter](https://docs.python.org/3/library/collections.html#collections.Counter)。

### 数55｜参考答案

**先说：** 数组支持按下标快速随机访问，内存布局通常更连续、遍历局部性好；链表以节点指针连接，定位某个位置通常需要顺序遍历。

数组随机访问 O(1)，中间插入／删除通常要移动元素，O(n)；链表在已拿到相应节点及必要前驱时可 O(1) 修改链接，但查找位置一般为 O(n)。双向链表额外保存前驱，消耗更多空间。

**易错点：** 不能说“链表所有插入删除都 O(1)”。Python list 是动态数组式容器，不是链表；它连续存储的是对象引用，不能等同于所有对象内容也连续。

依据：[Python 数据结构](https://docs.python.org/3/tutorial/datastructures.html)。

### 数56｜参考答案

**题干缺少通行规则，不能给唯一标准解。** 必须先问：水位升高是淹没道路使通路减少，还是让更多位置可以进入？起点和终点能否被淹？

若格子有高度 h，约定只有 h≥水位 w 才可走，目标是仍连通的最大 w：对候选高度二分，每次用 BFS／DFS 检查可达性。可行性随水位升高单调变差。设 V 为格子数，排序离散高度及二分检查的总时间为 O(V log V)，空间 O(V)。

若约定格子高度≤水位才可进入，可行性随水位升高变好；常见问题应是“最小可达水位”。直接问最大值若没有上界，通常没有有限答案。不要把这两类题混成一题。

### 数57｜参考答案

**先确认交易规则。** 下面分别给“最多一买一卖”和“可多次交易但同时最多持一股”，均无手续费、冷冻期，且允许不交易。它们是常见版本，不是已恢复的原题约束。

```python
def max_profit_once(prices):
    minimum = float('inf')
    best = 0
    for price in prices:
        best = max(best, price - minimum)
        minimum = min(minimum, price)
    return best

def max_profit_unlimited(prices):
    return sum(max(0, prices[i] - prices[i - 1])
               for i in range(1, len(prices)))
```

一次交易维护“此前最低价”和最大收益；无限次版本累加每段正涨幅。两者时间 O(n)、额外空间 O(1)，空序列和持续下跌都返回 0。若有 K 次上限、手续费或冷冻期，应改为对应状态转移，不能继续无条件累加涨幅。
