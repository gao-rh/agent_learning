## 营销自动化 Agent 通常怎样工作

可以用一条业务链路理解：**运营目标 → 查数据与分析人群 → 制定策略 → 校验与执行 → 观察效果 → 调整策略**。

公开产品中，Amazon Ads Agent 可以根据自然语言需求分析数据、生成 SQL、创建受众和广告活动，并批量调整预算、节奏等设置；变更会交给用户检查、批准。这说明 Agent 的价值包括数据分析、方案生成与工具执行，不能只按“生成营销文案”理解。[Amazon Ads Agent 官方介绍](https://advertising.amazon.com/zh-cn/solutions/products/ads-agent)

底层仍需要完整的营销数据与执行系统。阿里云 Quick Audience 的公开功能包括数据整合、标签与人群分群、事件触发营销，以及短信、推送、邮件、Webhook 等触达方式。这是营销链路组成的证据，不代表本面试团队采用该产品。[Quick Audience 官方介绍](https://www.alibabacloud.com/en/product/quickaudience?_p_lc=1)

结合这些资料与 JD，可把待理解的系统拆成三部分；下面是用于理解的架构归纳，尚未核实为淘天团队实现：

| 部分 | 主要做什么 | 示例 |
| --- | --- | --- |
| Agent 与算法 | 理解目标、查询数据、选择工具、生成和比较方案；必要时训练模型 | 为召回流失用户生成分群条件、优惠方案与评估查询 |
| 实时数据与策略执行 | 更新用户画像和特征，匹配规则，调用预测或决策服务 | 加购后未购买，满足条件后进入相应营销流程 |
| 工程服务与效果反馈 | 管理任务、预算、状态和触达；处理并发与故障，回收效果数据 | 防止重复发券，限制触达频率，追踪执行失败和实验结果 |

Flink 官方的 Broadcast State 示例把用户行为流按用户分区，把可更新的行为模式广播给各个并行任务，再匹配“加购后退出”等模式。它展示了动态规则与逐用户事件处理如何协同。[Flink 官方示例](https://flink.apache.org/2019/06/26/a-practical-guide-to-broadcast-state-in-apache-flink/)

**由此推断，一种可行设计是让 Agent 生成并发布策略，由实时服务执行大量用户事件。** 不必让每条行为都触发一次完整的大模型推理。JD 的“千万级 QPS”没有给出统计边界，后续需要确认指事件吞吐、策略服务请求还是其他接口，不能直接当作大模型推理吞吐。

## 模型微调与后训练：先区分这几个概念

后训练通常指基础模型预训练之后，为特定能力、行为或偏好继续训练。微调会更新模型参数；仅修改提示词、加入 RAG 或接入工具，本身不等于微调。SFT、DPO 等涉及训练目标和数据组织，LoRA 主要解决“怎样少更新一些参数”。[SFT 官方文档](https://huggingface.co/docs/trl/sft_trainer)、[LoRA 论文](https://arxiv.org/abs/2106.09685)

| 方法 | 入门理解 | 营销 Agent 中可能怎样用（示意，非该团队事实） |
| --- | --- | --- |
| SFT：监督微调 | 给模型正确示范，让它学习输入与期望输出的对应关系；示范也可以包含工具调用 | 用人工审核过的运营需求、规划步骤和正确工具调用训练模型。[文档](https://huggingface.co/docs/trl/sft_trainer) |
| LoRA：低秩适配 | 冻结基础权重，训练额外的低秩参数，减少需要更新的参数量 | 用较小训练成本做 SFT 或偏好训练；它可以与这些方法组合，并非 SFT 之后必跑的一步。[论文](https://arxiv.org/abs/2106.09685) |
| DPO：直接偏好优化 | 对同一输入提供较好与较差的回答，让模型更偏向较好的一个 | 比较合规、可执行的方案和漏掉约束的方案；通常使用已有偏好对，不是 PPO 那种在线采样的训练流程。[论文](https://arxiv.org/abs/2305.18290) |
| PPO：近端策略优化 | 根据采样结果的奖励更新策略，并控制更新幅度 | 在可控环境中，以任务完成度等信号改进决策；先明确奖励和约束。[论文](https://arxiv.org/abs/1707.06347) |
| GRPO：组相对策略优化 | 对同一问题生成一组候选，按组内相对奖励评价并更新模型 | 为同一任务采样多个方案，用可验证的完成情况打分。[文档](https://huggingface.co/docs/trl/grpo_trainer) |

准备时需要分清三件事：

- **训练谁**：大语言模型、转化率预测模型，还是优惠选择策略？营销场景中的强化学习不一定就是大模型后训练。
- **数据与奖励从哪里来**：示范是否正确，偏好由谁判断，奖励能否可靠计算？“格式正确、工具成功”与“带来真实增量转化”是不同评价目标，不能混用。
- **哪些信息应走工具**：最新用户标签、账户状态、库存和预算应实时查询。把这些易变事实记进模型参数，不能替代数据系统。这是本次调研的设计建议。

## 周五准备范围备注（AI 草案）

这里只保留候选范围，具体投入和深度到周五再决定；不代表要在一天内学完，也不代表已经完成准备。

| 方向 | 周五开始时可用的代表问题 |
| --- | --- |
| 营销 Agent 架构 | 一个召回任务如何从需求变成圈人、策略和工具调用？预算、频控与审批在哪一层检查？怎样用实验评估增量效果？ |
| 后训练与训练数据 | SFT 样本和 DPO 偏好对各长什么样？LoRA 改了哪些参数？PPO 与 GRPO 如何使用奖励？训练、离线评测与上线验证如何区分？ |
| 高并发基础 | QPS、并发数、平均延迟与 P95/P99 各指什么？如何定位瓶颈？缓存、连接池、异步队列、分区和扩容分别解决什么问题？ |
| 微服务可靠性 | 如何拆分任务、策略与触达服务？超时后是否重试？如何限流、熔断、降级，避免重复发券？如何通过日志、指标和 Trace 定位跨服务失败？ |
| 数据与状态一致性 | Kafka 重复消费如何处理？Flink 事件时间、状态、检查点和反压如何影响链路？数据库更新成功但触达消息未发出怎么办？ |

两个适合串起八股的场景：

- **发券超时但实际成功**：重试可能重复执行，应讨论幂等键、结果查询、有限重试和退避；过度重试还会放大下游负载。[AWS 重试与退避模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/retry-backoff.html)
- **活动状态已提交，但消息未发送**：数据库与消息系统双写可能不一致，可了解事务发件箱模式；消息仍可能重复，消费者依然需要幂等处理。[AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
