## 1. 假设业务与问题

某订阅产品希望比较两批注册用户的付费转化。业务明确约定：

> 一个合格注册用户，在注册后的 7×24 小时内至少发生一次金额大于零、状态为成功、且不是人工开通的支付，就算完成转化。

员工和测试账号不属于合格注册用户。这个指标只统计是否发生合格付款，不是净收入、有效订阅数或退款后的净转化；后续退款不会倒改本教学指标的已发生转化。

“付费”如果业务没有这样定义，就不能直接套用此示例。

## 3. references/semantic-layer.md 示例正文

### 快速说明

- 业务范围：新注册用户的首阶段付费转化；不覆盖续费、流失、净收入。
- 使用对象：产品与增长分析人员。
- 覆盖程度：仅覆盖 `paid_conversion_7d` 和注册渠道拆分。
- 默认时区：UTC；示例时间字段均为 `timestamptz`。
- 注册区间：左闭右开 `[cohort_start, cohort_end)`。
- 观察区间：每个用户的 `[registered_at, registered_at + 7 days)`。
- 成熟条件：整个批次的观察窗口都被可信数据完整性截止时间覆盖。
- 说明：`data_complete_before` 表示“该时间之前的数据已确认完整”，不等于数据库中出现过的最大时间戳。

### 实体与术语

| 实体 | 表示什么 | 不表示什么 | 标识 | 粒度 |
| --- | --- | --- | --- | --- |
| 注册用户 | 一个独立客户实体 | 一次登录、一次付款、一个设备 | `customer_id` | 每个用户一个实体 |
| 合格注册用户 | 注册时间在目标区间，且明确不是员工、不是测试账号 | 全站活跃用户、所有历史用户 | `customer_id` | 每个用户只计一次 |
| 合格付款 | 金额大于零、成功、非人工开通的付款事件 | 失败扣款、免费试用、人工开通 | `payment_id` | 每次付款一个事件 |
| 转化用户 | 观察窗口内至少有一笔合格付款的合格注册用户 | 付款事件数、付款总金额 | `customer_id` | 每人最多一次 |

若 `is_employee` 或 `is_test` 为空，不能自行当成 false；先将其视为数据质量问题，检查是否会改变分母，再说明处理方式。

### 关键指标

| 字段 | 定义 |
| --- | --- |
| 指标 ID | `paid_conversion_7d` |
| 中文名 | 注册后 7 日付费转化率 |
| 分母 | 注册区间内的合格注册用户数 |
| 分子 | 分母用户中，在个人 7 日窗口内至少有一次合格付款的人数 |
| 公式 | 分子 ÷ 分母 |
| 聚合时间 | 按注册 Cohort |
| 支付时间字段 | `paid_at`，而不是入库时间 `recorded_at` |
| 标准排除 | 员工、测试账号；付款侧排除失败、零金额和人工开通 |
| 分母为零 | 返回未知／不适用，不自动写成 0% |
| 权威来源 | 虚构的 `DEMO-METRIC-001` 指标定义；真实使用前需替换 |
| 定义版本 | 教学示例 v1；不是任何真实业务的批准版本 |

### 标准过滤与维度

| 条件或维度 | 默认逻辑 | 允许覆盖的情形 |
| --- | --- | --- |
| 注册用户范围 | `registered_at >= cohort_start AND registered_at < cohort_end` | 用户明确改变注册批次 |
| 内部账号 | `is_employee = false AND is_test = false` | 单独分析内部账号时另起明确口径 |
| 付款资格 | `status = 'succeeded' AND amount > 0 AND provisioning_type = 'self_service'` | 改指标定义时说明变更，不继续冒用旧指标 |
| 观察窗口 | `paid_at >= registered_at AND paid_at < registered_at + 7 days` | 30 日等指标使用另一个明确名称 |
| 注册渠道 | `signup_channel`，记录注册时的渠道 | 不能用付款时的营销渠道替换而不说明 |
| 地区 | 示例字段 `signup_region`，注册时地区 | 如改用当前地区，需要说明业务问题变化 |

示例假设 `signup_channel` 和 `signup_region` 是注册时的稳定属性；现实中如果字段会被覆盖，应使用历史快照或有效期关联。

### 关键表与关联

| 表 | 一行是什么 | 键与字段 | 适用与限制 |
| --- | --- | --- | --- |
| `analytics.customers` | 一个注册用户 | 主键 `customer_id`；`registered_at`、`is_employee`、`is_test`、`signup_channel`、`signup_region` | 用户主表必须在本指标范围内保持一人一行 |
| `analytics.payment_events` | 一次付款事件 | 主键 `payment_id`；`customer_id`、`paid_at`、`recorded_at`、`status`、`amount`、`provisioning_type` | 一个用户可能对应多笔付款 |

两表通过 `customer_id` 一对多关联。计算转化时，可以用 `EXISTS` 判断是否出现合格付款，或先压到一人一行，再和注册人群关联。直接 Join 后 `COUNT(*)` 会把有多笔付款的人重复计算。

数据完整性由可信的流水线状态或水位提供，查询 `MAX(paid_at)` 只能证明存在某条较新数据，不能证明更早的所有事件已经到齐。

### 查询模式：按注册渠道统计 7 日转化

输入条件：

- 注册区间已经明确。
- 注册和付款数据的可信完整性均已核实。
- 使用应用已确认的 `data_complete_before`。
- 应用在执行前保守检查 `cohort_end + 7 days <= data_complete_before`。如果不满足，报告观察不完整，或经明确说明改选完整批次；不能偷偷过滤未成熟用户后仍称结果代表整个原批次。

下面是未运行的骨架。命名参数适用于类似 psycopg 的绑定方式；应用需要校验参数、使用 UTC 并提供真实表结构。

```sql
WITH eligible_users AS (
    SELECT
        customer_id,
        registered_at,
        signup_channel
    FROM analytics.customers
    WHERE registered_at >= %(cohort_start)s
      AND registered_at < %(cohort_end)s
      AND is_employee = FALSE
      AND is_test = FALSE
), user_outcomes AS (
    SELECT
        u.customer_id,
        u.signup_channel,
        EXISTS (
            SELECT 1
            FROM analytics.payment_events p
            WHERE p.customer_id = u.customer_id
              AND p.paid_at >= u.registered_at
              AND p.paid_at < u.registered_at + INTERVAL '7 days'
              AND p.status = 'succeeded'
              AND p.amount > 0
              AND p.provisioning_type = 'self_service'
        ) AS converted_7d
    FROM eligible_users u
)
SELECT
    signup_channel,
    COUNT(*) AS eligible_users,
    COUNT(*) FILTER (WHERE converted_7d) AS converted_users,
    COUNT(*) FILTER (WHERE converted_7d)::numeric
        / NULLIF(COUNT(*), 0) AS conversion_rate_7d
FROM user_outcomes
GROUP BY signup_channel
ORDER BY signup_channel;
```

这个写法避免多笔付款放大人数，但仍依赖用户主表唯一、付款事件语义正确、数据完整等前提。没有注册用户时，分组查询可能直接没有结果行；不能把“无返回行”和“返回 0%”混为一谈。

### 已知坑点

| 坑点 | 为什么错 | 应检查什么 |
| --- | --- | --- |
| 按付款周除以当周注册数 | 分子和分母不属于同一人群 | 分子必须来自分母用户的个人窗口 |
| 周一立即评估上周全部注册用户 | 很多用户尚未观察满 7 日 | 批次结束与可信完整性截止的关系 |
| 付款 Join 后直接计数 | 一个用户多次付款会重复贡献 | 用户粒度、`EXISTS` 或预聚合 |
| 平均各渠道转化率 | 渠道人数不同会造成权重错误 | 汇总分子与分母再相除 |
| 直接把渠道 null 行删掉 | 改变总体分母，可能美化指标 | 保留“未知渠道”或解释覆盖缺口 |
| 看到新版发布就认定因果 | 时间相近不是充分证据 | 实验、对照、替代解释 |
| 看到最新事件就认定数据齐全 | 晚到和缺分区可能同时存在 | 流水线完整性信息与质量检查 |

### 相关看板与未解决问题

假设一个看板统计“当周所有付款用户”，它可用于观察交易趋势，不能直接拿来校验本指标。应先统一人群、时间归属、付款资格和观察窗口。

真实业务需要继续确认：账号合并怎样回溯；重复注册怎样处理；支付成功状态是否会被覆盖；付款延迟与补数怎样影响历史读数。这些都没有在本教学模型中完整覆盖。

## 5. 把模板变成可验收的知识

还没有运行下面的案例；它们用于下一步制作固定测试数据：

| 输入案例 | 预期结果 |
| --- | --- |
| 用户在注册第 2 日和第 3 日各付款一次 | 转化用户只计 1 人 |
| 用户在注册前有付款 | 不因此计入注册后 7 日转化 |
| 用户恰好在注册 7×24 小时的边界付款 | 右边界不包含，不计入 |
| 用户只有零金额或失败付款 | 不转化 |
| 员工或测试账号有成功付款 | 分子和分母都排除 |
| 非内部属性为空 | 报告并核查数据质量，不能静默假设 |
| 当前 Cohort 尚未观察完整 | 不下整体下降结论 |
| 两个渠道分别为 1/2 和 9/90 | 总体为 10/92，不是两个比率的简单平均 |
| 支付数据出现较新记录但有缺失分区 | 不能宣称数据完整 |

能解释并用固定数据验证这些边界，才说明语义层开始成为可执行、可检验的知识。
