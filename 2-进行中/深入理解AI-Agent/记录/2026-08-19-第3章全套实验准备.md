- Codex 的环境安装、冒烟和历史 `validation/latest.json` 都不算用户学会。

### 实验 3-1 的定位修正

- 3-1 本质上是端到端记忆能力评估，不是用单一自变量定位根因的因果实验。
- 它用三层各 20 个用例分别覆盖直接事实回忆、多会话检索与消歧、跨会话综合与主动服务。
- 每个会话结束后只保留新的记忆状态；处理下一个会话时不得回看更早的原始对话。最终在一个新会话中只根据最终记忆回答新问题，再由独立 LLM Judge 评分。
- 输出不达标只能说明端到端能力失败；要定位是写入、更新、检索、推理还是行动策略失败，还要检查逐会话 memory state、最终回答和调用 receipts。

### 3-1/3-2 链路与“消融”的修正

- 记忆更新是递推状态转换：`M_t = Writer(M_{t-1}, H_t)`。第 `t` 次调用只给 Kimi K2.6 上一版记忆和当前新会话，不再提供更早的原始会话。
- 只有全部历史会话处理完后，才在新会话中执行 `A = Answerer(M_n, Q)`；不是每次记忆更新后都回答一道题。
- 3-1 固定 `enhanced_notes` 和 Kimi K2.6，使用同一条链路评估三层能力：单会话事实回忆、多会话多实体消歧、跨会话综合与主动服务。它是分层端到端评估，不是消融。
- 3-2 固定同一案例和模型，平行比较 `notes / enhanced_notes / json_cards / advanced_json_cards` 四种表示。这是四臂受控比较；因为四种表示并非在同一系统上逐项移除组件，所以不是最严格的经典消融。
- 经典组件消融将在 3-6 通过 sparse / dense / fusion / reranker 链路体验。

### Rollout 与上下文压缩的边界

- 用户原始问题：rollout 是否等于全量原始轨迹；发生 compaction 后，rollout 保存的是压缩前还是压缩后内容。
- 修正：必须区分“磁盘上的追加式事件账本”和“下一次模型调用使用的工作上下文”。rollout 对 Codex 可观测事件近似追加式原始账本，但不是完整网络抓包，也不包含所有隐藏内部状态。
- 当前第 3 章任务的 rollout 实测约 15.4 MB、1201 行，保留消息、工具调用/结果、reasoning 项、Token 事件和其他运行事件。它在 2026-08-21 22:24、22:55（北京时间）出现两次 `compacted`，分别位于 JSONL 第 437、884 行。
- compaction 没有改写或删除第 437/884 行之前的旧事件；它追加 `compacted` 记录。该记录包含 `replacement_history`，由保留的 user/developer 消息和一个不透明 `compaction` 项组成；后续新事件继续追加在其后。
- 因此磁盘 rollout 同时拥有压缩前原事件和压缩后 replacement history；但下一次模型调用采用压缩后的工作上下文，不会继续把此前全部 assistant/tool 轨迹逐字塞回模型。
- 官方 Responses Compaction 文档同样描述输出为用户消息加一个 opaque compaction item；它用于继续对话，不应被当作可读摘要解析。
- Phase 1 Memory 的安装版 Prompt 以 `rollout_contents` 为来源，但当前 rollout 已达 15.4 MB，不能据此声称提取模型必然逐字收到全部文件。未核对加载器的过滤、重建和截断实现前，只能确认“来源是 rollout”，不能确认“全文件无损进入一次模型调用”。

- 证据边界：该结果为中文 `teaching_proxy`，且由同一模型写记忆并回答，没有独立 LLM Judge，因此不等于官方 3-1 验收通过。用户对记忆内容的分类解释仍为待继续。
- 用户观察：保留的记忆并非单纯“太多”，更核心的问题是没有区分重要与不重要信息，将不同性质的内容整体堆在一起，读起来混乱；它更像一份会话摘要，不应直接当作生产长期记忆。
- Codex 严格补充：该判断对当前 `M1` 基本成立；但实验 3-1 的目标不是教一种理想长期记忆结构，而是建立三层端到端记忆能力评估。Layer 1 只证明直接事实在“写入→隔离原文→回答”链路中没有丢失；它不能证明记忆精简、安全、可检索或适合上线。
- 结论状态：Layer 1 的“任务通过不等于记忆合格”已理解；3-1 完整三层目标仍为待继续，需通过 Layer 2 和 Layer 3 观察实体消歧、状态更新与跨会话综合。

### Layer 3 单案例的四种记忆表示实测

- 用户改变本轮执行方式：不再逐轮确认；固定一个有三段历史会话的案例，让 Codex 连续跑完 `notes / enhanced_notes / json_cards / advanced_json_cards`，分别提供完整中文对话、M1/M2/M3、最终回答和简要分析。
- 用户明确本轮不把隐私保护作为评价维度，重点跟随官方案例判断最终问题能否正确回答；报告据此使用 precision、recall、reasoning、proactivity 和 hallucination veto，并只保留证据边界说明。
- 固定案例为 `layer3_01_travel_coordination`：三段会话分别是护照续期、达美东京航班和 Chase 信用卡准备；消息数为 78 / 88 / 80。最终问题要求跨三段会话主动给出东京出发前待办。
- 四条链路都使用中文教学副本、Kimi K2.6、相同 Writer/Answerer/Judge 和同一递推隔离规则；Writer 每轮只看上一版记忆和当前会话，Answerer 只看 M3，Judge 才重新获得原始三段会话。
- Notes 从 60 增长到 118、167 条，M3 为 32,582 字符，总调用 51,613 tokens；核心事实多数存活，但选择性差，最终回答漏掉用新护照号码更新预订，并加入无来源的“护照更新证明/紧急旅行文件”。
- Enhanced Notes 从 8 增长到 10、13 段，M3 为 2,872 字符，总调用 17,932 tokens；核心事实保留和最终行动覆盖最好。同模型 Judge 给出 4/4/4/4，但人工核对发现“羽田机场可用 Priority Pass”和“机票保障由公司负责”没有原文依据，因此不是干净通过。
- JSON Cards 的 M3 为 6 个顶层类别、6,508 字符，总调用 18,748 tokens；三轮信息基本存活，但 `passport_update_deadline=72_hours_before_departure` 这一字段把“更新达美预订中的护照号”语义绑定得不够明确，Answerer 错把它当成续护照截止日；记忆还生成了不存在的“公司规定航班必须刷公司 AmEx”。
- Advanced JSON Cards 三轮始终只有 2 张护照卡，M2/M3 原样漏掉航班和信用卡整轮信息；最终回答因此漏掉 DELTA-JMK892、Priority Pass 和保险限制。它说明 schema 字段更丰富只约束输出形状，不保证 Writer 会吸收新会话。
- 官方评估标准与权威对话存在内部冲突：对话说加急续期 2–3 周，标准却写即使加急也需 5–7 周。Judge Prompt 规定以原始对话为权威，因此该数字不用于比较表示优劣。
- 自动 Judge 本身也不可靠：它漏检 Enhanced Notes 的无来源事实，还在 Advanced Cards 的回答中指控了实际并未出现的“5–7 周”。自动分数和人工逐源核对必须分开呈现。
- 当前结果支持用户此前的观察：全量事实堆积不等于长期记忆。进一步得到的新区分是，最终失败至少分为写入整轮丢失、记忆语义绑定错误、Answerer 使用错误、Judge 误判四层，不能只用一个总分解释。
- 完整产物位于 `实验/chapter3-memory-rag-labs/reports/layer3_01_travel_coordination-zh/`；证据等级仍是 `teaching_proxy`，不是 3-1/3-2 官方完整验收。
- 结论状态：实验产物已生成并核对；用户尚未完成阅读与解释，因此学习状态仍为 `待继续`。

### Notes 与两种 JSON Cards 的表示边界

- 用户观察：本次 Notes 实际长成 `entity / attribute / value` 属性记录，不像摘要；Enhanced Notes 反而更符合对摘要的直觉。用户进一步质疑 JSON Cards 与 Advanced JSON Cards 的效果差距和 Advanced 方案的实际优势，认为本例几乎看不出收益。
- 严格修正：Notes 表示的核心是“一个复杂陈述拆成多个可独立使用的原子事实”，不是“整段摘要”。官方评估 Prompt 只要求数组和原子事实，没有规定数组元素必须是字符串；Kimi 因而自行选择了属性对象。它是本次模型对 Prompt 的具体实现，不是 Notes 的唯一或必然格式。
- 代码边界：完整示例系统的 `NotesMemoryManager` 实际把每条 Note 存成 `content: str`，外加 note_id、session_id、时间和 tags；Notes 与 Enhanced Notes 甚至共用同一个存储 Manager，差别主要来自生成 Prompt。当前 `run_evaluation.py` 则不经过 Manager 的 add/update/delete，而是让 LLM 每轮直接返回并替换完整 memory state，所以本次看到的属性对象不能代表 Manager 的固定存储 schema。
- Enhanced Notes 明确要求“上下文段落数组”，所以更像用户直觉中的摘要；它牺牲原子级更新和精确检索便利，换来实体、事件和关系的自然语言上下文。
- 普通 JSON Cards 设计为 `category → subcategory → key → value` 的稳定路径，优势是精确定位、单字段更新和结构化检索；Advanced Cards 设计为 `category → card_key → 完整事件/人物卡`，额外保留 backstory、person、relationship、timestamp、status、facts 和来源元数据，理论优势在版本、冲突、溯源和事件生命周期管理。
- 用户对本例的判断成立：旅行案例主要考跨领域聚合，没有真正的“同一事项多次反转、旧版本作废”压力，因此 Advanced Cards 的额外字段大多只是成本，没有被题目转化为收益。本次它还发生 M2/M3 整轮漏写，实测反而显著更差。
- 要验证 Advanced Cards 的真实主张，应换用包含反复修改和明确 superseded 状态的案例，例如官方 `layer2_12_contradictory_financial_instructions`：同一笔转账金额、日期和参考号连续变化，最终只有 WT-89089 有效。若仍只用当前旅行案例，就不能据此断言 Advanced Cards 普遍无用，只能说“本例没有展示其优势，且 Writer 失败”。
- 结论状态：Notes/Enhanced Notes 的直觉差异与两种 JSON 的理论边界已解释，用户是否认可及能否自行复述仍为 `待继续`。

### Notes 失败归因、生产用法与 Codex 实际记忆形态

- 用户进一步假设：本次 Notes 可能因为没有生成预期记忆格式才表现差；并追问四种方式在真实系统中的使用位置，以及 Codex 是否全部采用 Enhanced Notes。
- 因果边界：属性对象本身仍满足“原子事实数组”的宽泛外层约束，不能据此直接判定格式非法。真正可观察的偏离是缺少重要性门槛、数量上限、合并和淘汰，导致 M3 膨胀到 167 条。最终回答错误还包含 Answerer 的时间推理和无来源补充，因此“属性对象导致低分”尚未被单变量实验证明。
- 实验设计限制：当前 Answerer 每次获得完整 M3，没有针对 Notes/JSON 做逐条检索或路径查询。这使 Notes 的原子检索、JSON 的路径读取等真实工程优势没有进入链路，只比较了 LLM 面对整份表示时的端到端效果。
- 生产系统通常不是四选一：原始事件日志负责可追溯；原子 Notes 保存稳定偏好和可独立更新事实；Enhanced Notes 保存会话/事件摘要；JSON 状态保存明确业务字段；带来源、状态和版本的 Cards 只用于需要冲突、审计和生命周期的实体。回答前再按问题检索所需层，而不是把所有长期记忆全部注入。
- OpenAI 官方当前可核对的是 Responses compaction：它返回用户消息和一个用于继续会话的不透明 compaction item；官方公开页没有说明 Codex 桌面端本地长期记忆目录的完整 schema，因此不能把 compaction 当成 Enhanced Notes，也不能用公开文档补全内部长期记忆实现。
- 本机只读实测显示 Codex 采用混合形态，而非全部 Enhanced Notes：session rollout 是追加事件日志；ad-hoc notes 是短原子规则；`rollout_summaries/` 是带 thread/cwd/rollout_path 元数据的任务摘要；`raw_memories.md` 按线程和任务保存 outcome、preference signals、reusable knowledge、failures、references，最接近富卡片；`MEMORY.md` 是 Task Group/任务/关键词/偏好/可复用知识/失败经验的层级索引；`memory_summary.md` 是始终注入的紧凑用户画像和主题摘要，最接近 Enhanced Notes。
- 结论状态：生产混合记忆架构和本机 Codex 文件形态已给出当前证据；Notes 低分的精确因果仍为 `待验证`，需要固定模型与案例，只修改 Notes 的 schema、重要性阈值、条数上限和检索方式后重跑。

### 用户复核：Layer 2 Judge 假阴性

- 用户原始判断：Kimi 的回答没有明显问题，只是比标准更详细；不理解为什么会被判不合格。
- 逐项复核后确认用户判断成立：回答完整呈现 Honda 的已预约服务、Tesla 的未预约状态，并在末尾询问是否协助安排 Tesla；这已经以功能等价方式完成官方标准要求的“呈现两辆车的信息，然后询问”。
- Judge 自行增加了标准中不存在的强约束：必须在回答开头显式指出歧义、必须逐字询问“你指哪辆车”。官方标准实际写的是先呈现两车信息再询问，Kimi 的回答顺序与之相符。
- 因此自动 Judge 将 recall、reasoning、proactivity 压到 3/2/2 属于假阴性，把话术偏好混同为能力缺失。更合理的人工参考分为 precision 4、recall 4、reasoning 3、proactivity 3，无幻觉，满足核心通过条件。
- 可选表达增强仍存在：开头直接说“您有两辆车”，结尾问“您准备为哪辆车安排服务？”会让歧义更显式；但这是质量提升，不应作为本题失败门槛。
- Codex 对上一轮结论的纠正：此前过度顺从 Judge，把它描述成“显式消歧话术不足导致未通过”；严格复核后应改为“回答通过，Judge 误判”。
- 结论状态：用户已正确识别回答功能完整；Judge 假阴性的机制解释仍待用户确认，因此暂记 `待继续`。
