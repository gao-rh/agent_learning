> 继续下一个实验吧

## 用户理解

- 用户已确认实验 3-9 收口，进入实验 3-10。
- 用户提出两种可能目的：前缀是否用来帮助 AI 在召回内容中找到原文部分，还是核心只是提高正确文本块的召回和排名。
- 严格结论：3-10 的直接目标是后者；“帮助 AI 找到原文”只在“帮助检索器召回承载原文的正确 chunk”这个意义上成立。

## Codex 反馈

### 1. 实验想解决什么

普通 RAG 分块后，某个 chunk 可能只剩下“（四）解释法律；（五）……”，丢掉了它原本属于“全国人民代表大会常务委员会的职权”这个标题。当查询里出现“常务委员会有哪些职权”时，该块因缺少身份词而难以被 BM25 找到。

实验 3-10 在建索引之前，让 LLM 为每个 chunk 生成一个简短的“它是谁、在哪、讲什么”前缀，再把前缀与原文一起建索引。这要解决的是“孤儿分块”问题。

### 2. 两条受控链路

```text
Plain
全文 -> 分块 -> 只索引原始 chunk -> 同一批查询 -> 排名

Contextual
全文 -> 分块 -> LLM 读全文+目标 chunk -> 生成前缀
     -> 索引“前缀 + 原始 chunk” -> 同一批查询 -> 排名
```

两条链路的文档、分块、查询、Gold Chunk 和检索算法都应保持相同；唯一变量是索引文本里是否增加上下文前缀。

### 3. 前缀在什么时候生成

它在**文档入库/建索引时**生成，不是在用户提问时生成。每个 chunk 原则上只需生成一次；文档或分块变更后才重新生成。它增加的主要是索引时成本，查询时不需要每次再调前缀模型。

当前在线 campaign 的核心 Prompt：

```text
System:
为目标文本块生成简短的中文检索前缀。
前缀必须说明该块来自哪份文档、所属章节/条款、主体与主题，
使孤立文本能被准确检索。不得添加源文没有的事实。
只输出前缀，不要解释。

User:
完整源文档：<document>...</document>
目标文本块：<chunk>...</chunk>
```

### 4. 具体案例

查询：

> 全国人民代表大会常务委员会有哪些职权？

Gold Chunk 的原文从“（四）解释法律”开始，后续继续罗列“审查计划和预算调整、监督国务院等机构、撤销违法法规、任免人员……”，但分块边界把“第六十七条 全国人民代表大会常务委员会行使下列职权”及前三项留在了上一块。

历史在线 LLM 为它生成的前缀：

> 《中华人民共和国宪法》第三章国家机构第一节全国人民代表大会，全国人民代表大会常务委员会职权及工作机制

前缀把查询中的“全国人大常委会”和“职权”补回了这个原本缺少标题的块。

### 5. 评估什么

- `Recall@1/3/5`：Gold Chunk 是否出现在前 1/3/5。
- `MRR`：Gold Chunk 排名越靠前，分数越高。
- 分别比较 BM25、Dense 和 RRF Hybrid 的 plain/contextual 版本。
- 记录前缀生成的 Token、延迟和估算成本。

### 6. 历史证据与当前可复现边界

历史验收产物的 SHA-256 与 `validation/latest.json` 完全一致，可以确认历史记录未被篡改。它使用 2 篇法律、22 个文本块、15 条查询、豆包前缀模型和 Qwen3-Embedding-0.6B。

历史主要结果：

| 方法 | Plain Recall@1 | Contextual Recall@1 | Plain MRR | Contextual MRR |
|---|---:|---:|---:|---:|
| BM25 | 60.0% | 80.0% | 0.7508 | 0.8556 |
| Dense | 86.7% | 93.3% | 0.9222 | 0.9667 |
| Hybrid | 73.3% | 86.7% | 0.8444 | 0.9133 |

索引阶段共用 228,734 tokens，当时估算 0.033918 美元；前缀生成约 61.8 秒，Embedding 约 365.5 秒。这些是历史环境数据，不是当前本机重跑数据。

当前仓库缺失 `document_store.json`，所以 README 里的默认离线命令会直接失败。验收证据内保留了完整 plain chunk、在线生成前缀和排名，因此可以用它恢复一份可追溯的离线语料；但不能手写前缀后宣称完成真实上下文生成实验。

还有一个结果不一致：README 的离线表格声称 BM25 Recall@1 从 60% 提升至 86.7%，并把上述旗舰案例描述成前缀后排名第 1；但可验证的历史在线证据显示 BM25 Recall@1 为 60% -> 80%，旗舰案例只从第 16 升至第 12。Dense 在该案例中前缀前后都是第 1，Hybrid 从第 6 升至第 5。因此 README 的“旗舰案例”不能代表在线 campaign 运行结果。

### 7. 前缀究竟帮助了哪一层

```text
用户问题
  -> 检索器用“前缀 + 原文”计算相关性
  -> 正确 chunk 更容易进入 Top-K
  -> 系统把该 chunk 的原文和来源交给 LLM
  -> LLM 基于原文组织答案
```

前缀的直接作用是**帮检索器找对 chunk**，不是在 chunk 内自动定位哪一句是答案。

- 如果“找到原文”指召回包含原文的正确文本块：**是**，这就是它的核心作用。
- 如果“找到原文”指在已召回的大块里自动标出精确句子：**不是**，这需要另外的 passage extraction、reranker、引文/高亮逻辑或 LLM 阅读。

前缀若也随 chunk 送入 LLM，可以辅助模型理解“这段是谁的什么内容”，但这是可能的二级收益。实验 3-10 只计算 `Recall@K` 和 `MRR`，没有比较最终答案，所以它**没有直接证明**前缀能提升生成答案的正确率。

生产实现可将字段分开：

```text
search_text  = 上下文前缀 + 原始 chunk   # 用于 BM25 / Embedding 排名
evidence_text = 原始 chunk                  # 作为可引用的原文证据
metadata      = 文档 ID + 章节 + 页码/行号  # 用于追溯
```

### 8. 市场实践与成本边界

用户进一步提问：

> 现在通常的实验手段会做这件事情吗？分块之后再做一个总结，是不是很贵？

第一个纠正：Contextual Retrieval 不是普通的“再摘要一遍 chunk”。Anthropic 的实现是让模型根据完整文档为目标 chunk 生成通常约 50–100 tokens 的**定位语境**，补全文档、主体、时间、章节和主题。其官方实验还指出，把同一份“通用文档摘要”附到每个块上收益很有限，所以关键是 chunk-specific，而不是摘要得更长。

当前工程中，“分块后保留语境”是常见目标，但“每个 chunk 都调 LLM 生成前缀”并不是普遍默认。通常按成本从低到高选择：

| 方法 | 是否每块调 LLM | 成本 | 典型用法 |
|---|---|---|---|
| 标题/章节路径/文档 ID 作为前缀 | 否 | 最低 | 结构良好的 Markdown、法条、产品文档 |
| 相邻句重叠、语义分块 | 否，或只在分块阶段用轻量模型 | 低 | 避免标题与正文被粗暴切开 |
| 父子/层次分块 | 否 | 低到中 | 用小块精确检索，命中后返回大块上下文 |
| 规则或结构化元数据前缀 | 否 | 低 | 已知文档名、部门、时间、人物、页码 |
| LLM chunk-specific context | 是 | 中到高 | 高价值、更新不频繁、孤儿分块明显的语料 |

若对一篇 `D` tokens 的文档切成 `C` 块，且每次都重复传入全文，未缓存的输入量大约为：

```text
输入 tokens ≈ C × D + 所有目标 chunk tokens
```

因此文档越长、分块越细，重复读取全文的成本越高。常见优化：

1. 对同一文档使用 Prompt Cache，只对全文做一次缓存写入，各 chunk 请求复用缓存。
2. 只提供章节/父块/相邻窗口，不是每次都提供整本文档。
3. 仅对上下文不完整、指代严重或检索失败率高的 chunk 生成前缀。
4. 使用便宜的小模型、批处理和并发；将结果按“文档哈希 + chunk 哈希 + Prompt 版本”缓存。
5. 先跑 Plain 基线；只在 `Recall@K` 和最终答案的收益值得时才上线。

Anthropic 在其特定假设下（800-token chunk、8k-token 文档、50-token 指令、100-token 前缀），配合 Prompt Caching 估算每 100 万文档 tokens 的一次性上下文化成本约 1.02 美元。这是特定模型、定价和缓存条件下的历史估算，不是所有服务的通用价格。

实验 3-10 的 22 个 chunk 历史运行消耗 228,734 tokens，当时按豆包价格估算仅约 0.033918 美元；这是小语料和便宜模型的结果，放大到大型、高频更新知识库时仍必须单独算账。

## 阶段总结

### 一句话结论

实验 3-10 通过在建索引时为“失去标题和主体的孤儿 chunk”补充简短定位前缀，让 BM25 和 Embedding 更容易把承载原文的正确块排入 Top-K。

### 完整链路

```text
完整文档
  -> 分块
  -> 向 LLM 提供“全文/父级语境 + 目标 chunk”
  -> 生成简短的 chunk-specific 定位前缀
  -> 对“前缀 + 原文”建 BM25/Embedding 索引
  -> 用同一批查询检索
  -> 比较 Plain 与 Contextual 的 Recall@K / MRR
```

这是**索引时增强**，不是查询时改写，也不是每次问题都重新生成前缀。

### 历史实验观察

| 方法 | Plain Recall@1 | Contextual Recall@1 | 观察 |
|---|---:|---:|---|
| BM25 | 60.0% | 80.0% | 前缀补回主体、章节和主题词，提升最明显 |
| Dense | 86.7% | 93.3% | 原本语义召回已较强，进一步提升较小 |
| Hybrid | 73.3% | 86.7% | 稀疏与稠密都受到前缀影响 |

主要改善的是排名靠前能力，尤其是 `Recall@1` 和 MRR；当 `K` 较大、Plain 本来已能召回正确块时，改善空间通常更小。

### 前缀做什么，不做什么

- 它帮检索器找到包含原文的正确 chunk。
- 它不负责在大 chunk 内自动标出精确答案句。
- 它不会修复索引中根本不存在的原文。
- 它若也送入 LLM，可能帮助理解主体和归属，但 3-10 没有评测最终答案，不能宣称生成正确率已提升。

### 实验设计要点

1. Plain 和 Contextual 必须使用相同的原文、分块、查询和 Gold Chunk。
2. 唯一变量应是索引文本是否附加前缀。
3. 需要同时报告逐查询排名，不能只看一个平均值。
4. 需要单独评测召回、最终问答、前缀幻觉与生成成本。

### 成本和生产选型

- LLM 前缀是一次性索引成本，但若每个 chunk 都重复读全文，会随文档长度和块数快速放大。
- 实验的 22 块历史运行很便宜，但不能外推到大型高频更新知识库。
- 生产中应先用标题路径、元数据、语义/层次分块和父子召回；只在评测证明值得时，对高风险孤儿 chunk 生成 LLM 前缀。
- 建议分存 `search_text = 前缀 + 原文`、`evidence_text = 原文` 和可追溯 `metadata`。

### 当前证据边界

- 历史 evidence/receipts/manifest 的哈希已验证一致，但这不等于当前本机重跑。
- 当前本地缺少 README 默认命令所需的 `document_store.json`。
- README 声称的 60% -> 86.7% 和“旗舰案例升至第 1”，与可验证的在线 evidence 不一致；应以逐查询证据为准。

## 适用场景判断

用户追问：

> 什么场景会用这个呢？还是说现在一般都会用？

严格结论：**成熟 RAG 通常都会想办法保留分块的上下文，但 LLM 生成 chunk-specific prefix 只是其中一种较贵的高级方案，并非普遍默认。**

适合使用 LLM 上下文前缀的典型特征：

| 特征 | 例子 | 为什么有用 |
|---|---|---|
| chunk 大量使用指代或省略 | 会议/客服对话中的“就订这个”“还是用上次那个” | 前缀补回“这个”的主体、时间和决定 |
| 长文档分块切断标题 | 法律、合同、政策，chunk 从“（四）……”开始 | 前缀补回条款主体和所属章节 |
| 多份文档有高度相似表述 | 多家公司多个季度的财报 | 前缀补回公司、报告、年度和季度 |
| 技术文档/代码块离开上层后含义不清 | 函数体不含模块、类名和调用关系 | 前缀补回仓库路径、模块、类与功能 |
| 知识库高价值且更新不频繁 | 法律库、企业制度、审计资料 | 一次性索引成本容易摊薄，错误召回代价较高 |

通常不应直接使用的场景：

- chunk 本身已包含完整标题、主体和答案语境。
- 已有结构化字段可以直接补充，如产品 ID、客户 ID、部门、时间、条款号。
- 数据高频更新，每次变更都需要重新生成大量前缀。
- 数据本来应用 SQL/过滤条件精确查询，而不是依赖文本检索。
- 语料高度敏感，不允许将全文发给外部模型，且本地模型不具备可靠生成能力。
- Plain 基线已达到要求，没有与缺失语境相关的召回失败。

生产中的建议顺序：

```text
结构化分块/保留标题
  -> 元数据前缀
  -> 重叠或父子分块
  -> 混合检索 + 重排
  -> 评测仍显示孤儿 chunk 失败
  -> 只对高风险 chunk 生成 LLM 前缀
```

是否值得使用，应同时满足：

1. 错误主要来自“切块后缺失身份/时间/主题”，而不是 Gold 原文缺失。
2. 简单的标题、元数据或父子分块不足以解决。
3. 评测证明 Recall/MRR 和最终答案确实改善。
4. 改善的业务价值足以覆盖索引成本、延迟与前缀幻觉风险。

## 发散联想

- Contextual Retrieval 类似在每个 chunk 上粘一张“来源和身份标签”，但这张标签是 LLM 根据全文生成的自然语言，不是单纯的文档 ID。
- 它与查询改写是两个不同方向：查询改写改变“用什么词搜”，上下文前缀改变“被搜的块包含什么词”。
- 前缀如果写错主体、条款或时间，会把 chunk 稳定地索引到错误语义下，因此需要质量抽检和重建策略。
