# 2026-08-19 Embedding 向量长度与角度

## 原始问题

> 我刚刚看到它说 Embedding 通常是基于角度来做判断的，不是用大小，主要是为了判断语义的差别。难道大小就不能代表语义的差别吗？虽然我之前也一直用的是角度，但我从来没有想过这个问题。通常的 Embedding 向量，它的长度和角度分别代表什么？

来源：[《AI Agents in Depth》第 3 章“稠密嵌入”](https://bojieli.github.io/ai-agent-book/book/chapter3/#%E7%A8%A0%E5%AF%86%E5%B5%8C%E5%85%A5%E4%BB%8E%E8%AF%8D%E6%B1%87%E5%85%B3%E8%81%94%E5%88%B0%E8%AF%AD%E4%B9%89%E7%90%86%E8%A7%A3)

## 用户理解

- 以往实际使用 Embedding 时一直采用角度（余弦相似度）判断相似性。
- 当前假设：既然向量方向可以承载语义关系，向量长度也可能承载某种语义差别；不应未经分析就认定长度没有意义。

## Codex 反馈

### 核心判断

- 用户的怀疑是对的：向量长度**可以**承载信息，但它没有跨模型通用的固定语义。
- 角度也不是天然等于语义；是模型的训练目标和检索指标把“方向接近”训练成了“语义相关”。
- 对两个文本的通用语义相似度，通常优先使用余弦相似度，因为它消除了模长造成的缩放影响。
- 一个向量的模长是“该点距原点多远”，是单个样本的径向属性；两个文本的语义差异是成对关系。不能默认用两个模长之差代替语义距离。

设向量 \(x=r_xu_x\)、\(y=r_yu_y\)，其中 \(r\) 是模长，\(u\) 是单位方向，则：

\[
x\cdot y=r_xr_y\cos\theta
\]

因此，点积同时使用长度和角度；余弦相似度只使用角度；欧氏距离同时受到长度与角度影响。若所有向量都做了 L2 归一化，模长都等于 1，点积就是余弦相似度，欧氏距离与余弦相似度也会给出相同排序。

### 长度与角度应怎样解释

| 几何量 | 在常见语义检索中的解释 | 重要边界 |
| --- | --- | --- |
| 方向 / 夹角 | 训练后常被用来表达特征组合或语义模式是否相近 | 不是数学上天然具有语义；只在特定模型空间内有效 |
| 模长 / 范数 | 未归一化时可能携带信息量、词频、显著性、置信度或训练造成的尺度等信号 | 含义依模型、层、池化、损失函数而变；不能默认解释为“语义更多”或“文本更长” |
| 点积 | \(模长_1\times 模长_2\times 方向相似度\)，会同时偏好方向相近和模长较大的向量 | 是否合理取决于模型是否按点积目标训练 |
| 欧氏距离 | 同时比较径向位置和方向 | 单位向量上与余弦排序等价；未归一化时会受尺度影响 |

### 对原书表述的修正

书中“长度对应文本长度或频率”适合作为说明余弦会消除尺度的入门直觉，但不是通用事实：

- 书中举例的 BGE-M3，其官方实现将稠密向量 L2 归一化，输出模长为 1；因此文本长短不会直接表现为最终向量模长。
- OpenAI Embedding 输出也默认归一化到长度 1。
- 原始 BERT 的上下文隐藏状态也不能直接等同于“适合余弦检索的句向量”；Sentence-BERT 正是通过孪生/三元组结构把 BERT 改造成可用余弦相似度比较的句向量模型。
- 对未归一化的静态词向量，研究发现模长可能编码词带来的信息增益；这说明“长度完全没有语义信息”同样不准确。

更严格的表述应是：**若任务目标是语义相似检索，并且模型按余弦相似度训练或输出已归一化，就应把方向作为主要检索信号；原始模长即使有信息，也需要专门验证其含义，不能直接当作通用语义距离。**

### 资料

- [BGE-M3 官方说明](https://github.com/FlagOpen/FlagEmbedding/blob/master/docs/source/bge/bge_m3.rst)：稠密表示使用归一化后的 `[CLS]` 隐状态。
- [Sentence-BERT 论文](https://aclanthology.org/D19-1410/)：训练可用余弦相似度比较的句向量。
- [Norm of Word Embedding Encodes Information Gain](https://aclanthology.org/2023.emnlp-main.131/)：在特定词向量模型中，平方模长可编码相对共现分布的信息增益。
- [OpenAI Embeddings FAQ](https://help.openai.com/en/articles/6824809-embeddings-faq)：输出默认 L2 归一化，余弦与欧氏距离产生相同排名。

### 继续追问：ANN 为什么有“基于树”和“基于图”

#### 用户问题

> 啥叫基于树？啥叫基于图？树状的连接吗？语句不是一条横线吗？

#### 核心纠正

- “语句是一条横线”描述的是文本进入模型前的 token 顺序。
- ANN 索引面对的不是句子内部的词，而是大量句子或文本块已经生成的向量。每个向量可以看成高维空间中的一个点。
- 树和图是组织这些向量点的索引结构，不是语言的句法树，也不是在句子里的词之间连线。

```text
句子 / 文本块 → Embedding 模型 → 一个高维向量点

很多文本块 → 很多向量点 → 用树或图建立 ANN 索引
```

#### 基于树：反复切分空间

以 Annoy 为例，它用随机超平面把一批向量点分成两边，再对子区域继续二分，最后形成树。中间节点主要表示“该往哪一半空间走”的切分规则，叶子节点保存少量候选向量。查询时沿树快速缩小范围，不再逐个比较全部向量。Annoy 实际会建立多棵树组成森林，以减少一次随机切分漏掉真实近邻的概率。

```text
全部向量点
├── 空间 A
│   ├── A1
│   └── A2
└── 空间 B
    ├── B1
    └── B2
```

#### 基于图：把相近的向量点连起来

以 HNSW 为例，每个节点本身通常就是一个向量点，边连接若干相近的点。查询从某个入口开始，不断比较“周围哪个邻居更接近查询向量”，然后沿边跳过去。HNSW 还增加了多层结构：上层节点少、长距离边多，用于快速跨越大范围；下层节点多、局部边密，用于精细搜索。

```text
较稀疏的上层：       A ───────── D
                      │           │
较密集的底层：   A ─ B ─ C ─ D ─ E
                       ╲   │   ╱
                           F
```

#### 两者的本质区别

| 问题 | Annoy 式树索引 | HNSW 式图索引 |
| --- | --- | --- |
| 怎么组织向量 | 反复切分空间，放进不同分支 | 向量点作为节点，近邻之间连边 |
| 怎么查询 | 连续回答“查询点在哪一边”，进入少量叶子候选 | 从入口沿着越来越近的邻居跳转 |
| 直觉 | 查目录、缩小区域 | 按地图导航、沿道路接近目的地 |
| 为什么是近似 | 早期切错分支可能漏掉边界附近近邻 | 贪心导航和有限候选搜索可能没遍历到真实最近点 |

资料：

- [Annoy 官方仓库](https://github.com/spotify/annoy)：使用随机投影和树；每个中间节点以随机超平面把空间分成两个子空间，并建立多棵树。
- [HNSW 原始论文](https://arxiv.org/abs/1603.09320)：使用分层的近邻图，上层承担较长距离导航，下层完成局部近邻搜索。

### 继续追问：精确检索、ANN 建索引与查询过程

#### 用户原有想法

> 和所有的向量做匹配，看哪个角度最小，都算一遍也挺快的。

这个方案是成立的，名称是精确最近邻检索（exact k-NN / brute-force search）：查询向量分别与全部 \(N\) 个、每个 \(d\) 维的向量计算相似度，再排序取前 \(k\) 个，单次查询计算量约为 \(O(Nd)\)。小数据集、低查询量、批量 GPU 矩阵乘法或必须保证精确结果时，它可能就是更好的方案。

ANN 是 Approximate Nearest Neighbor，近似最近邻。它不是某一个固定算法，而是一类问题和方法：预先建立索引，让每次查询只访问一小部分候选向量，以牺牲少量召回率换取更低延迟和更高吞吐。Annoy、HNSW 都是 ANN 的实现。

#### Annoy 的树怎样形成

1. 取得全部文本的 Embedding 向量。
2. 从当前的一组向量点中抽取两个点，构造到二者等距的超平面。
3. 按向量落在超平面的哪一侧，把这一组点分成两组。
4. 对两个子组递归切分，直到叶子只保留少量向量 ID。
5. 使用不同的随机切分重复多次，形成多棵树的森林。

查询时，不只沿一棵树固定走到底，而是综合多棵树，优先展开更可能包含查询点的分支；达到 `search_k` 一类候选预算后，对收集到的候选向量计算真实距离并返回前 \(k\) 个。增加树数量或候选预算通常提高召回率，但会增加内存、构建时间或查询计算。

#### HNSW 的图怎样形成

HNSW 通常逐个插入向量：

1. 新向量随机获得一个最高层级；多数点只在底层，少数点会出现在上层。
2. 从当前入口点和最高层开始，沿已有边寻找更接近新向量的节点。
3. 逐层下降，在每一层为新节点选择若干近邻并建立边。
4. 邻居也增加指向新节点的边；若某节点连接过多，则按规则保留有限个、有导航价值的邻居。

这样逐步得到“上层稀疏、下层密集”的近邻图。查询时从上层入口开始，若某个邻居离查询向量更近就跳过去；到达当前层局部最优后下降一层。底层不只走单一路径，还维护一批候选节点继续扩展，最后对候选计算真实距离并返回前 \(k\) 个。`efSearch` 越大，考察候选越多，通常召回率越高但查询越慢。

#### 为什么不总是全量计算

若有一百万个 768 维 float32 向量，原始向量数据约为 3.1 GB。一次暴力查询不仅要做约 7.68 亿维度乘加，还要扫描大量内存。单次或批量 GPU 搜索可能仍可接受，但当数据继续扩大、并发查询增多或只有 CPU 时，重复全量扫描会成为主要成本。ANN 的价值不是让小数据集从“不能搜”变成“能搜”，而是用索引避免每次都扫描全库。

#### 概念关系

```text
目标：找最近的 k 个向量（k-NN）
├── 精确搜索：全部计算，保证找到真正的前 k 个
└── 近似搜索（ANN）：少算大部分向量，更快但可能漏掉少数真实近邻
    ├── 树索引：Annoy 等
    └── 图索引：HNSW 等
```

### 继续追问：HNSW 的邻居边、局部最优与准确性

#### 用户假设

- 图可能按相似度区间划定区域：与某个向量的相似度落在一定范围内，就连接到它。
- 如果图不能保证建得正确，查询可能只找到局部最优；HNSW 也许接受这个近似结果。

#### 边不是按固定相似度区间建立

HNSW 通常不给每个向量设置一个固定的“相似度达到多少就连边”阈值，也不把空间划成彼此独立的区域。原因是不同区域密度不同：统一阈值会让密集区产生大量边、稀疏区没有足够边，甚至使图断开。

更接近实际的理解是：每个节点只保留至多约 \(M\) 个有导航价值的邻居。候选以距离近为重要依据，但邻居选择还会考虑方向和覆盖的多样性，避免所有边都挤向同一个小团簇。边表示“从这里可以有效走向那个附近节点”，不是业务关系或严格的相似度区间。

#### 插入一个新向量时怎样连边

1. 随机决定新节点能够出现到多高的层；所有节点都在底层，只有少数节点进入高层。
2. 从最高层入口开始，沿现有边靠近新向量的大致位置。
3. 逐层下降；在需要插入的层使用比单一路径更宽的候选搜索，找出一批近邻候选。
4. 从候选中选择不超过 \(M\) 个近且分布较好的节点，建立通常为双向的连接。
5. 若旧节点的边数超限，则重新选择并剪掉部分边。

`M` 控制每个节点大致保留多少连接；`efConstruction` 控制建图时愿意搜索多大的候选池。候选池越大，通常图质量和召回率越高，但建图越慢、内存成本也可能更高。

#### 查询不是只接受第一次局部最优

- 上层主要使用贪心导航：只要邻居中有更接近查询的点就继续走，当前层走不动后下降一层。
- 到底层后维护一个候选优先队列，同时探索多条有希望的路线，而不是只沿唯一一条边前进。
- `efSearch` 控制查询时保留和探索多少候选。它越大，越有机会绕过坏的局部最优，但耗时越高；极端情况下退化为检查更多节点。

分层长距离连接、邻居多样性和底层多候选搜索共同降低卡在局部最优的概率，但不能提供 exact k-NN 的绝对保证。若必须保证真实最近邻，只能执行精确全量搜索；ANN 常用 Recall@k 衡量近似结果覆盖了多少真实 Top-k。

#### 图没建好的表现与验证

| 原因 | 可能表现 | 常见处理 |
| --- | --- | --- |
| `M` 太小 | 图连接不足，存在导航瓶颈 | 增大 `M` 后重建 |
| `efConstruction` 太小 | 插入时选错或漏掉好邻居 | 增大建图候选预算后重建 |
| `efSearch` 太小 | 图本身尚可，但查询探索不足 | 增大查询候选预算，无需重建 |
| 距离函数或归一化不匹配 | 索引中的“近”不是模型定义的“相关” | 按模型要求统一 cosine、dot 或 L2，并重建 |
| 长期插入、删除或数据分布变化 | 局部连接质量下降 | 用真实查询集复测，必要时压缩或重建 |

验证不能只看延迟：应抽取一批代表性查询，先用全量精确搜索得到真实 Top-k，再比较 HNSW 的结果，计算 Recall@k。例如真实 Top-10 命中 9 个，则该查询 Recall@10 为 0.9。之后联合调整 `M`、`efConstruction` 和 `efSearch`，选择召回率、内存、建图时间与查询延迟之间的取舍。

### 继续追问：图索引相比树索引的优势

#### 用户问题

> 图既然缺点这么多，二分法又效率很高，图的优点在哪？

#### 核心纠正

一维有序数组中的二分查找可以每次安全排除一半数据，因为目标值只可能在一边；高维最近邻搜索没有这种保证。空间切分后，查询点虽然落在切分面一侧，它的真实最近邻仍可能在另一侧，尤其当查询靠近边界或维度很高时。要提高召回率，树索引必须回溯多个分支、检查更多叶子或建立多棵随机树，因此不能把它直接等同于始终 \(O(\log N)\) 的一维二分查找。

#### HNSW 的主要优势

- **高维下的召回率—延迟表现通常更好**：图直接保存数据点之间的近邻关系，不依赖一组固定切分面；上层长距离边负责快速接近目标区域，底层局部边负责精细搜索。
- **适应不规则数据分布**：密集簇、稀疏区和弯曲的数据流形不必被硬切成层层矩形或半空间；重叠的邻居连接可沿真实数据分布导航。
- **可调查询质量**：调整 `efSearch` 即可在同一索引上改变查询速度与召回率，不一定重建；树索引也有搜索预算，但高召回时可能需搜索更多树和叶子。
- **较自然地支持增量插入**：HNSW 可为新向量搜索邻居并连边；Annoy 的主要索引是构建后只读，新增数据通常需要重建。

#### 代价与选择边界

| 维度 | Annoy 式树森林 | HNSW 图 |
| --- | --- | --- |
| 查询思想 | 空间切分后访问若干叶子 | 沿近邻边和长距离边导航 |
| 高维、高召回 | 可能需要多树和大量回溯候选 | 通常具有更好的召回率—延迟折中 |
| 内存 | 可做成紧凑、可内存映射的静态文件 | 需额外保存大量边，通常更耗内存 |
| 构建 | 相对直接，适合静态批量构建 | 建图和邻居选择较重 |
| 更新 | 构建后主要只读，更新常需重建 | 支持逐个插入，但长期增删仍需监测退化 |
| 适合场景 | 静态数据、内存和文件共享重要、可接受多树近似 | 高维大规模、低延迟高召回、需要增量写入 |

因此不是“图全面优于树”，而是 HNSW 用更多建图时间和内存，换取高维检索中更好的查询效率和召回率。小规模数据仍可优先精确搜索；静态、内存敏感的数据可考虑 Annoy；高维且重视在线召回率与延迟时，HNSW 往往更合适。最终选择必须在同一数据和查询集上比较 Recall@k、P95/P99 延迟、吞吐、内存和构建/更新时间。

## 发散联想

- “角度代表类别、长度代表强度”可以用作部分模型的直觉，但不能当作 Embedding 的普遍定义。
- 在 RAG 中选择 cosine、inner product 或 L2 之前，应先查模型卡和训练方式，并确认向量数据库是否自动归一化。
- 可以做一个小实验：对同一模型输入短句、重复多次的同义文本和无关文本，分别观察原始向量模长、归一化后的余弦、点积与欧氏距离；但必须先确认 API 是否只返回单位向量，否则无法研究原始模长。
