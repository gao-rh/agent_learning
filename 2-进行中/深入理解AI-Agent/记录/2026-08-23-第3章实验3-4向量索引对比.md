# 2026-08-23 第 3 章实验 3-4：ANNOY 与 HNSW 向量索引对比

## 原始问题

> 行，然后下一个实验吧。

> 现在你是用什么检索的？就是 Codex 是用什么检索的？应该是都用的，精确检索加语义检索。然后 ANNOY 这个应该用得多一点吧？HNSW 现在 Claude、Pi Agent、Codex 都用的是哪一种方法？

> 索引的准确率大吗？这个生成的准确率大概什么样子？它召回多少？是只把那个词上下多少个字符弄出来吗？

> 3-4 实验主要想表明什么？HNSW 这些方法有中文名吗，如何发音？这两种方法是不是一种更适合增量插入，一种查询或初始构建更快？

## 用户理解

- 用户把“精确检索/近似检索”与“语义检索”理解为可以直接相加的同一层方法，并推测 Codex 同时使用精确检索和语义检索。
- 用户进一步推测 ANNOY 可能比 HNSW 使用得更多，希望用 Claude Code、Pi 和 Codex 的真实实现来理解索引选择。
- 用户已经主动拆出了初始构建、在线查询和增量插入三个维度，但当前仍倾向于把两种索引固定概括成“一种增量更好、另一种查询或构建更快”。

## 实验目标

本实验不再比较记忆的写入格式，而是研究：文本已经经过同一个真实 Embedding 模型变成向量以后，怎样用近似最近邻索引更快地找回相近向量，并量化近似搜索带来的速度、召回、空间和更新代价。

## 受控变量

- 固定同一个真实 Embedding 模型。
- 固定同一批文档、文档向量、查询和查询向量。
- 用全量点积排序得到精确 Top-k，作为索引召回率的真值。
- 只替换向量索引后端：ANNOY 或 HNSW。

## 可观察指标

- `Recall@k`：近似索引找回了多少个精确 Top-k 结果。
- 索引构建时间。
- 查询延迟，至少观察均值和 p95。
- 序列化索引大小，作为空间开销的一项代理指标。
- 新增一批文档时是否需要完整重建，以及更新后的 `Recall@k`。

## 本机基线运行

### 配置

- 模型：`Qwen/Qwen3-Embedding-0.6B`
- 模型 revision：`97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3`
- CPU；向量维度 1024；随机种子 37。
- 300 篇模板文档、20 个查询、`Top-k=10`、每个查询重复 5 次。
- 初始索引 240 条，随后新增 60 条。
- ANNOY：本机 macOS ARM 健康检查失败，按官方脚本切换到 Linux aarch64 Docker；HNSW 在 macOS 宿主机运行。

### 执行过程

- 第一次运行在完成 Embedding 后失败：本机 ANNOY 健康检查仍不通过，Docker 回退又因 OrbStack 尚未启动而连接不到 `docker.sock`。这不是 Embedding 或 HNSW 失败，也没有形成完整比较结果。
- 启动 OrbStack 后，`orb start` 命令本身报告等待超时，但随后 `orb status` 为 `Running`，`docker info` 正常返回 Server 29.4.0。
- 原参数第二次运行成功，实验状态为 `passed`。

### 结果

| 指标 | ANNOY | HNSW |
| --- | ---: | ---: |
| 初始 `Recall@10` | 1.000 | 1.000 |
| 构建时间 | 20.595 ms | 47.039 ms |
| 查询均值 | 0.200 ms | 0.159 ms |
| 查询 p95 | 0.298 ms | 0.204 ms |
| 序列化索引大小 | 1,396,720 bytes | 1,018,716 bytes |
| 新增 60 条耗时 | 6.230 ms | 21.457 ms |
| 是否完整重建 | 是 | 否 |
| 更新后 `Recall@10` | 1.000 | 1.000 |

Embedding 总耗时约 107.227 秒；ANNOY 容器准备与运行的额外墙钟时间约 37.972 秒，不包含在表中的 ANNOY build/query 微基准里。

### 当前解释

- 两种索引 `Recall@10=1.0` 只表示都完整复现了精确向量 Top-10；不表示 Top-10 对真实用户问题一定相关。
- 数据只有 300 条、主题模板明显、参数也较充足，因此结果很容易饱和，不能用来证明大规模召回没有差别。
- ANNOY 新增 60 条虽然计时更短，但它确实重新构建了整个索引；小数据下全量重建仍很便宜，不能据此推断数据增长后比 HNSW 增量插入更有扩展性。
- ANNOY 在本次序列化文件大小上反而更大，说明教材的“ANNOY 通常更省内存”不是每组参数下的必然结果；当前只测文件大小，而且 `n_trees=50` 与 HNSW `M=16` 的结构参数不同，不能等同于进程 RSS。
- ANNOY 在 Docker/Linux 中运行，HNSW 在 macOS 宿主机运行；因此构建和亚毫秒查询数字只能作为本次运行记录，不能作为严格的跨算法性能排名。
- 本实验不做“关键词命中后截取上下若干字符”。300 篇输入中的每一篇短文就是一个完整检索单元，`top_k=10` 表示每个查询返回 10 篇完整短文的文档 ID。
- 官方 `ANN Recall@10` 的分母是精确向量搜索返回的 10 篇：两种索引对 20 个查询共 200 个位置全部复现，因此是 `200/200=100%`。
- 若额外把同一主题的 15 篇文档都定义为语义相关，则两种索引返回的 200 篇全部同主题，`Precision@10=200/200=100%`；但每个查询最多只取 10 篇，所以面向全部相关文档的 `Recall@10=200/300=66.7%`，这已是当前 `top_k=10` 下的理论上限。
- Embedding 本身不直接产生“准确率”；需要先规定相关性标签、检索单元和 `k`，再计算 precision、recall、MRR 或 nDCG。当前同主题标签非常简单，只能证明这批模板数据上的主题区分，不能代表真实问答语义质量。

## 当前教学边界

- `Recall@k` 在这里衡量的是 ANN 对“精确向量检索结果”的还原程度，不等于最终问答正确率，也不直接评价 Embedding 的语义好坏。
- ANNOY 与 HNSW 的比较必须使用同一批向量和查询；分别重新生成向量会把 Embedding 波动混进索引差异。
- 本机历史预检发现 macOS ARM 上的 ANNOY 扩展存在自查询异常，正式比较前必须先做健康检查；异常时不能把该后端数字当成实验结论。
- “关键词/语义”决定如何表达相关性；“精确/近似”决定如何执行邻居搜索，二者不是同一层分类。
- 当前 Codex 本地记忆读路径公开实现是：先注入压缩后的 memory summary，再由模型用关键词搜索 `MEMORY.md`，按需读取命中的 rollout summary；本次会话实际使用的是 `rg` 关键词/正则搜索，不是已公开的向量索引。
- Codex、Claude Code 和 Pi 的公开代码库探索工具都以文件名匹配、关键词/正则搜索和按路径读取为核心。模型可以语义理解用户问题并生成搜索词，所以整体行为看起来有语义能力，但这不等于底层使用 Embedding、ANNOY 或 HNSW。
- 厂商没有公开的云端检索实现不能从产品表现反推。只有在官方文档或源码明确出现向量模型和索引时，才能断言使用了某种 ANN。
- ANNOY 仍适合轻量静态索引，但现代动态向量数据库中 HNSW 更常见；这不代表编码 Agent 的默认源码检索会使用 HNSW。
- `ANNOY` 是 `Approximate Nearest Neighbors Oh Yeah`，通常按英文单词 `annoy` 发音，中文没有统一译名，可称“基于随机投影树森林的近似最近邻索引”。
- `HNSW` 是 `Hierarchical Navigable Small World`，通常逐字母读作 H-N-S-W，中文常译“分层可导航小世界图”。
- 3-4 的稳定结论不是“ANNOY 查询一定更快”或“HNSW 全面更好”，而是：固定向量和查询、用精确 Top-k 作真值后，联合比较 recall、构建、查询、空间和更新行为。ANNOY 通常更偏静态批量构建；HNSW 更自然支持增量插入，并常用更多建图时间和内存换取较高召回—延迟表现；具体快慢必须实测。

## 结论状态

- 实验 3-4：已理解

用户已经能从初始构建、在线查询、增量插入、近似索引召回率几个维度解释 ANNOY 与 HNSW，而不是把它们简化成固定的“谁更快”。2026-08-26 用户确认进入下一实验；是否进一步放大数据规模绘制召回—延迟曲线属于可选扩展，不作为 3-4 收口的必要条件。
