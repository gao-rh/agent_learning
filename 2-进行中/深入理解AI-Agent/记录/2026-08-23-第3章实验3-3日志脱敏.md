## Codex 反馈

- 3-3 不是单纯验证“能否遮住手机号”，而是控制输入不变，对比 `Regex`、`Local LLM`、`Hybrid` 三种日志脱敏策略。
- 三条链路都应输出可定位的发现项：敏感信息类型、原文值、起止位置和置信度；随后替换敏感片段，并与人工标注答案比较。
- 核心评价维度包括：精确率、召回率、类型与文本的精确匹配、脱敏后残余泄漏、非敏感内容可用性和延迟。
- 误报和漏报的代价不对称：漏报会留下隐私风险，误报会破坏排障所需的日志内容；只汇报一个综合分数不足以解释方案是否可用。
- 官方受控样例同时覆盖规则明显的结构化秘密、依赖语义的自然语言隐私、真假相似值混合以及纯负例。
- 对用户预测句的实测结果：规则没有识别中文自然语言中的 `Blue moon over river 77`，却把 `order_id=13800138000` 中的数字识别为手机号，得到“密码泄漏、订单号误删”的反向结果。
- 将密码改写为 `password: hunter2xyz。order_id=...` 后，`secret_assignment` 规则从密码值一直匹配到文本末尾，把订单号和说明一起吞掉；原因是未把中文句号 `。` 设为值的终止符。
- 已建立独立源码导读《实验 3-3 源码逐行导读：不用 LangChain，Python 直接调用 Ollama》。当前源码未使用 LangChain；主实验由普通 Python 直接调用 `ollama.Client.chat()`，Apache 指本地 Qwen 模型元数据中的 Apache 2.0 开源许可证，不是运行框架。
- 已新增独立可运行文件 `实验/chapter3-log-sanitization-learning/experiment_3_3_fully_annotated.py`：包含完整 12 案例、Regex 规则和校验、Ollama 调用、Hybrid、精确区间替换、六类指标、CLI 与 JSON 输出，并按 13 个代码模块加入详细中文注释。
- 完整代码在真实运行中补齐四个工程边界：为本地 Ollama 客户端设置 `trust_env=False`，避免系统代理把回环地址请求变成 502；对结构化抽取设置 `think=False`，避免 Qwen3 把生成预算耗尽在重复 thinking；将坏 JSON 记为 LLM `failed`、Hybrid `degraded` 并继续批次；将 SDK 返回的 `datetime` 转成 ISO 字符串后再写 JSON。
- 真实完整批次已完成：`qwen3:0.6b`、temperature 0、seed 37、thinking false；12 案例 × 3 策略，24 次 Ollama 调用，22 次 JSON 解析成功、2 次 medical 坏 JSON（直接 LLM 一次、Hybrid 第二阶段一次）。结果文件 SHA-256 为 `c787be1d0b81c63bf424522bcc624d440f4d646d89359250976d4a49985a6141`。
- 聚合结果：Regex precision 0.417 / recall 0.500 / leaks 9 / utility 0.954 / 0.078 ms；LLM precision 0.597 / recall 0.625 / leaks 6 / utility 0.768 / 1988 ms，含 1 个 failed；Hybrid precision 0.597 / recall 0.792 / leaks 3 / utility 0.852 / 1620 ms，含 1 个 degraded。
- 当前数据支持“Hybrid 降低残余泄漏”的结论，但不支持“Hybrid 全面最好”：它仍继承 Regex 对订单号等数字的误删，且 medical 案例中 LLM 输出无效；LLM/Hybrid 在 address 等案例中还会通过过宽区间做到“Gold 不再残留”，同时 exact recall 与 utility 很差。
- Hybrid 平均延迟低于直接 LLM 不是“Regex 加速模型”的证据：去掉 direct/hybrid 都输出满 1200 token 的 `medical` 异常案例后，两者平均延迟分别约 891 ms 与 871 ms，只差约 20 ms；Hybrid 的平均 prompt token 仅从 177 降至 174.2，成功响应的平均 completion token 反而从 95.6 增至 97.2。逐案例中 Hybrid 有时更快、有时更慢，例如 `mixed_context` 为 1289 ms 对 640 ms。
- 当前执行顺序始终是每个案例先 direct LLM、再 Hybrid LLM；首轮模型热身、系统调度和异常重复生成都会污染一次性平均延迟。`medical` 中 Regex 没有命中，因此两次 LLM 输入相同、completion 均为 1200，但延迟约 14.1 秒与 9.9 秒，说明差异主要来自运行波动。
- 若要检验真实性能，应预热模型、交错或随机化调用顺序、重复多轮，并报告 p50/p95；理论上 Hybrid 的成本是 `Regex + 第二次 LLM`，只有 Regex 真正缩短了模型输入或输出时，才可能抵消额外开销。
- 对“不能上生产”的表述做出纠正：不是 Hybrid 原理上不能生产化，而是当前 12 条教学实验不足以证明它能直接覆盖更广泛生产流量。若业务目标是隐私优先、允许多删，并具备失败时隔离/丢弃原日志的机制，Hybrid 可以进入受控生产或灰度。
- 本次 Hybrid 共面对 18 个 Gold 敏感值，完整 Gold 字符串从结果中消失 15 个，即 83.3%；精确 value 的 micro recall 为 13/18=72.2%，micro precision 为 13/20=65.0%，另有 1 个 degraded 案例。它不支持“全数据接近 100%”的结论。
- 用户重点关注的 `mixed_context` 单案例确实做到两个 Gold 敏感值均不再出现，但同时误删订单号 `13912345679`，并把密码后的句号包含在敏感区间中；因此“完整敏感值消失率 100%”与“精确脱敏且保留业务日志”是两种不同验收口径。

## 发散联想

- 强格式信息未必需要 LLM；正则、校验和及格式验证通常更便宜、更稳定。
- LLM 即使“理解到这里有隐私”，若没有返回原文中的精确片段或位置，也可能无法可靠执行替换。
- Hybrid 的目标是让规则处理确定性强的长尾之外常见模式，再让本地模型处理依赖上下文的语义型隐私。
- Regex 本身不能仅凭 11 位数字判断它是手机号还是订单号；要降低误报，需要引入字段上下文、日志结构、允许/拒绝字段表或语义分类，而不是只扩大数字正则。
