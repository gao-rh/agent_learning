## 三、指标速查

| 指标 | 回答的问题 | 不能证明什么 |
|---|---|---|
| Precision | 返回/识别的内容中，有多少是正确的 | 不能说明是否漏掉大量正确内容 |
| Recall | 全部正确目标中，找回了多少 | 不能说明结果是否夹杂很多噪声 |
| Recall@K | 前 K 个结果覆盖了多少 Gold | 不等于最终问答正确率 |
| ANN Recall@K | 近似索引复现了多少精确向量 Top-K | 不评价 Embedding 本身是否符合用户语义 |
| MRR | 第一个相关结果排得多靠前 | 不关心后续相关结果是否完整 |
| nDCG@K | 前 K 名整体排序质量 | 依赖可靠的相关性标签 |
| Hallucination veto | 是否出现足以否决答案的无来源/矛盾事实 | 仍依赖 Judge 是否判断正确 |
| Utility | 脱敏后有多少非敏感日志仍可用于排障 | 不代表隐私泄漏已经为零 |
| Citation recall | 检索上下文是否包含 Gold 页/块 | 不证明回答真正使用了这些证据，也不惩罚大量噪声 |
| Silhouette | 聚类内部是否紧、不同簇是否分离 | 不证明聚类具有业务因果意义 |
| p50/p95 latency | 常见与尾部请求耗时 | 单次冷启动平均值不能代表稳态性能 |
| Token/费用 | 模型链路的资源成本 | 不代表输出质量 |

## 四、所有实验的方法、指标与结果

### 3-1：三层用户记忆能力评估

**想解决的问题**

固定一种记忆链路，观察它能否完成三种逐渐变难的任务：Layer 1 直接事实回忆、Layer 2 多实体/状态消歧、Layer 3 跨会话综合与主动服务。

```text
M(t) = Writer(M(t-1), 当前新会话 H(t))
全部会话结束后：Answer = Answerer(M(n), 新问题 Q)
```

Writer 下一轮不再看到旧原始会话；最终 Answerer 只看到最终记忆，不看到原始历史。

**指标**

- Precision / Recall / Reasoning / Proactivity，各 1–4 分。
- Material hallucination veto。
- 通过条件：无重大幻觉，且 Precision、Recall、Reasoning 均不低于 3。
- 辅助观察：逐轮记忆状态、Writer/Answerer 错误归因、Token、延迟。

**实际结果**

- Layer 1 中文航空单例：最终确认号和往返座位回答正确；Writer + Answerer 共 3,928 tokens。
- 但记忆同时保留完整卡号、CVV、出生日期、地址等大量高敏感和无关信息，并自行补入原文没有明确给出的机场代码。因此“答对事实”不等于“长期记忆合格”。
- Layer 2 多车辆案例：Enhanced Notes 能区分 Honda 已预约和 Tesla 只讨论、未预约；仍保存大量与当前问题无关的保险细节。
- 作为补充的英文 10 用例样本中，固定 Enhanced Notes 为 5/10 通过：Layer 1 为 1/2，Layer 2 为 2/4，Layer 3 为 2/4。样本很小且部分 benchmark criteria 与源对话冲突，不能外推为总体准确率。

**最终结论**

3-1 教会的是“分层评估端到端记忆能力”，不是证明某一种记忆格式适合生产。最终失败必须继续拆成 Writer 写入、状态更新、Answerer 使用和 Judge 判分四个阶段。

**状态**：学习阶段已收口；官方 60 用例完整复现未做。

### 3-2：四种用户记忆表示比较

**想解决的问题**

固定案例、模型和递推更新规则，只改变记忆表示：Notes、Enhanced Notes、JSON Cards、Advanced JSON Cards。

**指标**

- 与 3-1 相同的四维 1–4 分与 hallucination veto。
- 最终通过率、生成失败数。
- 记忆大小、Token、费用、延迟和格式稳定性。

**英文 10 用例 × 4 格式抽样结果**

Writer/Answerer 为 Kimi K2.6，独立 Judge 为 GPT-5.6 Sol；40 个 arm 中 39 个生成成功、1 个 Advanced arm 触发 16,384 输出上限。

| 格式 | 独立 Judge 通过率 | 平均总 Token/成功 arm | 平均累计延迟 | 平均估算费用 |
|---|---:|---:|---:|---:|
| Notes | 5/10，50% | 10,181 | 75.7 秒 | ¥0.1353 |
| Enhanced Notes | 5/10，50% | 10,294 | 82.5 秒 | ¥0.1376 |
| JSON Cards | 3/10，30% | 13,012 | 111.3 秒 | ¥0.1839 |
| Advanced JSON Cards | 4/10，40% | 21,007 | 186.1 秒 | ¥0.3111 |

全部成功 arm 合计 523,928 tokens，估算 ¥7.3688。Advanced 比 Notes 约 2.06 倍 tokens、2.46 倍延迟，并多出一次生成失败。

**人工观察**

- Notes 可能膨胀成接近全量事实索引，缺少重要性筛选；10 例中还出现 2 次结构漂移。
- Enhanced Notes 通常最像自然语言事件摘要，在三会话旅行单例中保留核心信息最好，但最终答案仍添加无来源事实。
- JSON/Advanced 的结构使实体、状态和来源更容易检查，却不保证 Writer 一定写对、也不保证 Answerer 会使用正确字段。
- Advanced 的优势主要是显式生命周期，如 `planned / initiated / active / superseded`；本次没有用程序化字段查询，整个 JSON 仍一次性塞给 Answerer，因此结构优势没有充分发挥。
- 本样本不支持书中“Advanced 在高层任务表现最好”的强结论，只支持“Advanced 更重、更慢，在部分冲突状态题有优势”。

**状态**：学习阶段已收口；不是官方 60×4 完整排名复现。

### 3-3：Regex、Local LLM 与 Hybrid 日志脱敏

**想解决的问题**

控制同一批日志输入，对比规则、本地小模型和混合方案识别与遮盖敏感信息的能力，同时保护排障所需的非敏感字段。

**指标**

- 精确匹配 Precision / Recall。
- 残余泄漏数 `leaks`。
- 非敏感信息可用性 `utility`。
- 平均延迟、失败/降级数量。
- “完整 Gold 字符串是否消失”与“精确识别区间”分开计算。

**本机 12 案例结果**

| 方法 | 聚合 Precision | 聚合 Recall | 残余泄漏 | Utility | 平均延迟 |
|---|---:|---:|---:|---:|---:|
| Regex | 0.417 | 0.500 | 9 | 0.954 | 0.078 ms |
| Local LLM | 0.597 | 0.625 | 6 | 0.768 | 1,988 ms |
| Hybrid | 0.597 | 0.792 | 3 | 0.852 | 1,620 ms |

Hybrid 的 micro 精确值口径是 Precision `13/20=65.0%`、Recall `13/18=72.2%`；18 个 Gold 中有 15 个完整字符串消失，即 83.3%。聚合值与 micro 值不同，是因为计算平均方式不同。

**最终结论**

- Hybrid 明显减少残余泄漏，但会继承 Regex 对订单号等相似数字的误删，也会受到 LLM 坏 JSON 和过宽区间影响。
- “某个案例敏感值全部消失”不等于“精确脱敏且保留所有业务字段”。
- Hybrid 平均更快主要由异常长输出和运行波动造成，不证明 Regex 天然给 LLM 加速；性能实验应预热、随机化顺序并报告 p50/p95。
- 当前教学样本能支持灰度/受控使用方向，不能单独证明生产全流量接近 100%。

**状态**：已理解；本机完整教学批次已运行。

### 3-4：ANNOY 与 HNSW 近似向量索引

**想解决的问题**

固定相同 Embedding、文档向量和查询向量，只切换 ANN 索引，比较近似搜索对精确向量 Top-K 的还原、速度、空间和增量更新行为。

**指标**

- ANN `Recall@10`。
- 构建时间、查询均值/p95。
- 序列化索引大小。
- 插入新数据是否需要重建、更新后 Recall。

**本机结果：300 文档、20 查询、1024 维、Top-10**

| 指标 | ANNOY | HNSW |
|---|---:|---:|
| 初始 Recall@10 | 1.000 | 1.000 |
| 构建时间 | 20.595 ms | 47.039 ms |
| 查询均值 | 0.200 ms | 0.159 ms |
| 查询 p95 | 0.298 ms | 0.204 ms |
| 序列化大小 | 1,396,720 B | 1,018,716 B |
| 新增 60 条耗时 | 6.230 ms | 21.457 ms |
| 是否完整重建 | 是 | 否 |
| 更新后 Recall@10 | 1.000 | 1.000 |

**最终结论**

两者都复现精确向量 Top-10，但不代表返回内容对用户问题一定相关。ANNOY 在 Docker/Linux、HNSW 在 macOS 宿主机，绝对延迟不能作为公平算法排名。真正稳定的结论是：ANNOY 更偏静态批量构建，HNSW 更自然支持增量插入；具体召回—延迟—空间必须在自己的规模和参数上实测。

**状态**：已理解；本机基线已运行。

### 3-5：从零实现 BM25 稀疏检索

**想解决的问题**

打开 BM25 黑盒，观察分词、倒排索引、IDF、TF 饱和和文档长度归一化如何共同排序，以及纯词法检索为什么必然漏掉无词面重叠的同义表达。

**指标**

- 手算分数与代码结果误差。
- `Recall@5`、`Precision@5`、MRR。
- 逐词 IDF/TF 贡献和候选文档。

**本机结果**

- 手算与引擎得分均为 `1.1373125642781259`，误差 0。
- 4 条精确词查询：`Recall@5=1.0`、`MRR=1.0`。
- 同义词查询 `cat`：相关文档只有 `kitten/feline`，返回空；`Recall@5=0`、`MRR=0`。
- `HTTP 404 error` 中，命中三个词的 `doc_6` 得分 4.9943 排第 1；只命中 `error` 的 `doc_9` 得分 1.2954 排第 2。

**最终结论**

单词查询中 IDF 对所有命中文档是共同常数，通常只缩放分数；多词查询中各词 IDF 不同，会改变加和后的排名。候选没召回时应改分词、同义词、查询扩展或混合检索，不要误调 `k1/b`；候选已召回但排序错误时，才诊断 TF 饱和、长度惩罚和字段权重。

**状态**：已理解；正式本机验收 `passed`，运行 ID `20260826T134350Z-3_5-d9ec6778`。

### 3-6：BM25、Dense、融合与神经重排

**想解决的问题**

在同一评测集上比较 BM25、稠密向量、RRF、归一化加权融合和 RRF 后 Cross-Encoder 重排，理解候选生成、融合和重排的职责边界。

**指标**

- `Recall@3`、MRR、`nDCG@3`。
- 平均端到端延迟。
- 重排前后的逐查询名次变化。

**本机结果：20 文档、12 查询**

| 链路 | Recall@3 | MRR | nDCG@3 | 平均延迟 |
|---|---:|---:|---:|---:|
| BM25 | 0.8333 | 0.7917 | 0.8026 | 19.45 ms* |
| Dense | 1.0000 | 1.0000 | 1.0000 | 242.99 ms |
| RRF | 1.0000 | 1.0000 | 1.0000 | 262.45 ms |
| Weighted | 1.0000 | 0.9583 | 0.9692 | 262.45 ms |
| RRF + Cross-Encoder | 1.0000 | 0.9028 | 0.9276 | 282.90 ms |

`*` BM25 平均值被 jieba 首次加载约 225 ms 拉高，中位数只有 0.09 ms。

**最终结论**

- 当前小样本中 Dense 与 RRF 最好；BM25 在零词汇重叠和中英跨语言查询上漏召回。
- Weighted 会受归一化范围、离群值和权重影响；RRF 也可能同分并依赖 tie-break。
- 英语 MS MARCO Cross-Encoder 把一个英文语义查询和一个中文查询降级，使 MRR 从 1.0 降到 0.9028。重排器更复杂，不代表必然更好。
- 重排只能重排候选池中的内容，不能恢复稀疏和稠密两路都没召回的文档。

**状态**：已理解；本机完整验收 `passed`，运行 ID `20260826T141455Z-3_6-91780eb2`。

### 3-7：RAPTOR 与 GraphRAG 结构化索引

**想解决的问题**

比较树状层次摘要与实体关系图：RAPTOR 面向宏观概括和层次下钻，GraphRAG 面向关系连接和多跳路径。重点不是 Intel 指令集，而是知识组织结构。

**指标**

- Gold 页 citation recall。
- 外部 Judge 0–4 分。
- 人工原子条件覆盖分。
- Graph 显式路径生成率、实体/关系证据覆盖。
- 查询延迟、建索引 Token 与成本。

**历史真实运行与人工复核：8 题 × 2 链路**

| 链路 | Citation recall | 自动 Judge 均分 | 人工复核 | 满足完整 4 分 |
|---|---:|---:|---:|---:|
| RAPTOR | 0.9583 | 4.0 | 30/32，均分 3.75 | 6/8 |
| GraphRAG | 0.9583 | 3.5 | 25/32，均分 3.125 | 4/8 |

- Graph 完整产物有 124 实体、123 关系、8 社区；仅 23/124 实体带原文证据，28/123 关系带 `evidence_quote`。
- 4 道多跳题中只有 2 道生成 `explicit_paths`，且依赖人工 path hints 和无向图最短路径。
- RAPTOR 8 次查询有 7 次 Top-1 是叶子摘要，多数成功不是高层树导航的独特收益。
- RAPTOR 建索引 36,732 tokens；GraphRAG 82,672 tokens，约为前者 2.25 倍；全链路 178,721 tokens。

**最终结论**

树和图只有在结构正确时才有价值。摘要会漏精确条件，实体会重复/误合并，错误关系会产生“看似完整的错误推理链”。最终答对不证明图路径生效；必须查看检索轨迹并回到原始证据。当前教学实现缺 Flat 基线和去结构消融，不能证明 RAPTOR/GraphRAG 优于普通混合检索。

**状态**：已理解；离线教学运行与历史答案/轨迹人工审计完成，没有在本轮重新产生完整索引。

### 3-8：Agentic RAG 与单次 RAG

**想解决的问题**

固定同一法律语料、BM25、Top-K 和回答任务，只改变检索控制方式：原问题搜索一次，或由 Agent 反复执行“拆解、改写、搜索、检查缺口、补搜”。

**指标**

- 查询规划和领域术语改写质量。
- 严格证据命中：至少用“法律名称 + 法条号”作为主键。
- 最终回答依据、Judge 0–4 分。
- 搜索次数、模型调用、Token、延迟。

**实际结果**

- 语料为 288 份法律、21,372 个法条 chunk；每次 BM25 Top-5，Agent 最多搜索 4 次。
- 复合问题原句只召回过失致人重伤基础法条，漏掉醉酒责任和累犯/前科分支。
- 官方离线脚本声称证据召回 `33% → 100%`，但子查询由人工写死，且 Gold 强行加入题面没有“驾驶机动车”前提的危险驾驶条款，因此该数字不能代表真实 Agent。
- 自然拆解查询的目标排名分别为第 6、第 5、前 50 未命中；人工加入“累犯、从重处罚、有期徒刑”等答案导向词后才全部升至第 1。主要增益来自领域查询改写，不是“拆开问题”本身。
- GPT-5.6 Sol 单例盲测：自主找到过失致人重伤、醉酒责任和累犯例外三条有语义依据的分支，并继续查前科的酌定影响。
- Kimi K2.6 单例盲测：3 次模型调用、4 次本地搜索，8,068 tokens、约 62.2 秒；只成功召回醉酒责任，重复一次基础查询，未召回基础法条和累犯条款，但在证据不足时保持克制。

**最终结论**

Agentic RAG 的能力应拆为问题拆解、查询改写和迭代补证。人工 oracle 查询只能表示检索器的上界，不能冒充 Agent 能力；单例中 Sol 的查询构造和纠错优于 Kimi，但不能当模型排行榜。书中现有量化结论不采信。

**状态**：已理解；离线对照、本机 Kimi 单例与 Sol 盲测完成。

### 3-9：Agentic RAG 检索用户原始会话

**想解决的问题**

不把历史对话压缩成 Notes/Cards，而是分块建立 BM25 索引，让 Agent 调用 `search_user_memory` 逐轮找回原始证据。

**指标**

- Gold marker 覆盖率。
- Top-K 召回内容与状态绑定。
- 搜索轮数和桥接实体是否出现。
- 最终回答是否完整使用证据。

**本机双车案例结果**

- 默认 `Top-K=3`：单次检索已召回 Honda、Tesla 和“Tesla 最终未预约”；多轮规则主要补回 Honda 确认号 `FS-447291`。脚本标记覆盖率报告 50%→100%，但不能证明消歧从失败变成功。
- `Top-K=1` 消融：首轮只看到 Honda；后续只能继续追查 Honda，Tesla 始终缺失。Gold marker 为 0%→50%，仍不完整。
- 历史真实 Agent 只搜一次并遗漏 Tesla，Judge 却判通过，说明自动通过率偏宽。

**最终结论**

Agentic 记忆检索可以深挖已经出现的线索，不能凭空发现首轮完全没有暴露的实体。实体出现也不等于状态正确；“讨论过、已预约、取消、被覆盖”必须单独评测。

**状态**：已理解；本机离线默认与 Top-K=1 对照已运行。

### 3-10：上下文感知检索

**想解决的问题**

文档分块后，chunk 可能失去标题、主体和时间，成为“孤儿块”。在建索引时为每块生成 50–100 tokens 左右的定位前缀，再索引“前缀 + 原文”。

**指标**

- `Recall@1/3/5`、MRR。
- BM25、Dense、RRF Hybrid 的 plain/contextual 对照。
- 前缀生成 Token、延迟和成本。

**可验证历史结果：2 篇法律、22 chunks、15 查询**

| 方法 | Plain Recall@1 | Contextual Recall@1 | Plain MRR | Contextual MRR |
|---|---:|---:|---:|---:|
| BM25 | 60.0% | 80.0% | 0.7508 | 0.8556 |
| Dense | 86.7% | 93.3% | 0.9222 | 0.9667 |
| Hybrid | 73.3% | 86.7% | 0.8444 | 0.9133 |

历史索引阶段 228,734 tokens，估算 0.033918 美元；前缀生成约 61.8 秒，Embedding 约 365.5 秒。

README 另称 BM25 `60%→86.7%`，但与 evidence 不一致；应以上表的 `60%→80%` 为准。所谓旗舰问题中，BM25 只从第 16 升至第 12，并未升到第 1。

**最终结论**

上下文前缀的直接作用是帮助检索器把正确 chunk 排入 Top-K，不是在 chunk 内标出答案句，也没有直接证明最终问答一定提升。成熟系统通常先保留标题/元数据、改善分块和父子召回，只对高风险孤儿块使用 LLM 前缀。

**状态**：已理解；历史 evidence 已验证，本轮未重新生成前缀；默认离线命令缺 `document_store.json`。

### 3-11：结构化状态卡片 + 可检索原始对话

**想解决的问题**

组合两种互补表示：Advanced JSON Card 负责“当前是什么”，Contextual BM25 检索原始会话负责“为什么、证据是什么”。当前代码不是双重检索：卡片整份直接注入，只有原始对话经过 BM25。

**指标**

- 60 案例的通过率和四维 Judge 得分。
- Hallucination rate。
- Plain / Contextual / Dual Layer 三组消融。
- Token、调用数和逐例差异。

**历史自动 Judge 报告**

| 层级 | Plain | Contextual | Dual Layer |
|---|---:|---:|---:|
| Layer 1 | 19/20，95% | 19/20，95% | 19/20，95% |
| Layer 2 | 15/20，75% | 15/20，75% | 20/20，100% |
| Layer 3 | 13/20，65% | 18/20，90% | 18/20，90% |
| 总计 | 47/60，78.33% | 52/60，86.67% | 57/60，95% |

该历史 campaign 共 448 次 API 调用、2,232,168 tokens；本轮只读取、复算和人工抽查，新增外部 API 调用为 0。

**人工审计结果**

- 多信用卡案例中，BM25 漏掉 Amex，卡片成功补回并纠正推荐，属于真实核心增益。
- 同一答案又声称 Amex 可 1:1 转 United 等无来源/错误事实，Judge 仍给满分。
- 开店案例 Gold 要求区分“2 月可做面包、4–5 月才能烘焙”，Plain/Contextual 都没答全却被判通过；Dual 又被旧卡片中的 3 月目标锚定。
- 保修案例的 Judge 判词与 Gold、答案本身互相矛盾。

**最终结论**

95% 只能称为“该 Judge 下的报告通过率”，不能当真实准确率。双层记忆确有互补性，也会因卡片过时、写错或 Answerer 盲信卡片而退化；生产系统必须增加卡片—原文冲突检测、来源和更新时间、原始证据优先规则与卡片修正机制。

**状态**：已理解；历史全量结果已复算并抽查，未重新消费 API。

### 3-12：从历史文本中抽取结构化知识

**想解决的问题**

让 LLM 从大量案件中自下而上发现候选 schema，再按 schema 抽取逐案特征，用传统算法聚类为案件原型，最后让 Agent 基于原型统计分析留出案件。

```text
案例文本 + 罪名/刑期标签
→ 因子发现
→ schema 合并
→ 逐案结构化抽取
→ 向量化/KMeans
→ 原型与刑期分布
→ 留出案件匹配和谨慎建议
```

这不是用户记忆 JSON Card，而是数据集级 `schema + 特征表 + 统计原型`。

**指标**

- Schema 因子数量和模块完整性。
- 每罪名 KMeans 候选 k 与轮廓系数。
- 原型数量与样本量。
- 留出建议的 prototype grounding、numeric fidelity、uncertainty/caution、usefulness，各 1–4 分。
- 标签泄漏检查、免责声明、调用数和 Token。

**历史正式运行：360 训练 + 60 留出**

- Schema：16 个通用因子；盗窃/故意伤害/诈骗扩展因子分别为 12/12/11。
- 聚类：盗窃选 k=5、silhouette=0.0614；故意伤害选 k=4、0.2174；诈骗选 k=2、0.1427；共 11 个原型。
- 12 条留出建议的 Judge 均分：原型依据 3.75、数字忠实 3.583、不确定性与谨慎 3.75、可用性 3.583。
- 117 次 API 调用、958,190 tokens、0 调用错误。
- 存在仅 1 个训练样本的原型；代表留出盗窃案被匹配到该原型的 4 个月统计，而其隐藏真实刑期为 8 个月。

**最终结论**

历史 `passed` 证明正式数据、分割、调用回执、聚类和建议产物齐全，不证明预测可靠。三个最佳 silhouette 都偏低、原型样本量不稳定，也没有系统的字段抽取 Gold accuracy；当前只能确认流水线机制可行。实际项目应由 LLM 发现候选字段，领域专家审核和版本化 schema，再批量抽取与留出验证。

**状态**：待继续。机制和历史结果已讲解；约 10 个案例的抽样字段核对尚未运行，用户尚未最终确认。

## 五、用户提出的全部核心问题及最终答案

以下合并了重复表达和“继续下一个”等流程性消息，保留所有实质问题。

### A. 用户记忆、上下文与 Codex Memory

1. **3-1 到底在做什么，是三个案例还是消融？** 3-1 固定 Enhanced Notes，评估三层任务能力；3-2 才固定案例比较四种表示。3-2 是四臂对照，不是严格逐组件移除的经典消融。
2. **记忆什么时候写？** 教材在每个 YAML 会话结束后由评估循环显式调用 Writer；不是模型回答过程中自动发生。生产系统常用同步关键事实 + session/run 后异步提取 + 周期整理。
3. **Writer 下一轮能看到全部历史吗？** 不能；只看到上一版记忆和当前新会话。最终 Answerer 只看最终记忆和新问题。
4. **四种记忆结构是什么？** Notes 是原子事实；Enhanced Notes 是带上下文段落；JSON Cards 是固定层级对象；Advanced Cards 增加实体、关系、来源、时间和状态。
5. **为什么 Notes 不是摘要？** Notes 的目标是可独立更新和检索的原子事实，不要求一定是自然语言摘要；本次 Kimi 还把它实现成属性对象，这是模型具体输出，不是 Notes 唯一格式。
6. **Advanced JSON 为什么没明显更好？** 结构只约束表示，不保证 Writer 吸收新会话，也不保证 Answerer 用对字段；当前实验还把整份 JSON 一次性注入，没有发挥字段查询优势。
7. **失败是记忆错还是回答用错？** 两者都有。已分别观察 Writer 污染、schema 生命周期丢失、记忆正确但 Answerer 漏用，以及输出上限失败。
8. **Codex 为什么知道以前的信息？** 当前对话上下文、压缩后的工作上下文、跨任务 memory summary/索引和项目内学习记录是不同层；不是每次回答都读取所有历史原文。
9. **Rollout 是全量原始轨迹吗？** 它是追加式可观测事件账本，不是完整网络抓包。Compaction 会追加替代工作上下文，不删除磁盘中此前事件；下一次模型调用使用压缩后的上下文。
10. **超长轨迹怎样生成长期记忆？** 当前只确认 Codex Phase 1 从 rollout 生成 raw memory/rollout summary，再由 Phase 2 全局归并；具体是否逐块 Map-Reduce 仍待专项验证。
11. **ChatGPT Pro 是否等于 API 额度？** 不等于。ChatGPT/Codex 订阅与 OpenAI API 独立；Kimi 会员与 Kimi 开放平台 API 也独立。

### B. 3-3 脱敏

1. **怎样删密码但保留像手机号的订单号？** 不能只靠 11 位数字正则；应结合字段名、结构化日志、allowlist/denylist、校验规则和语义上下文。密码正则还必须正确处理中文标点终止边界。
2. **Apache 是什么，是否使用 LangChain？** Apache 2.0 是本地模型许可证；实验代码用普通 Python 直接调用 Ollama，不使用 LangChain。
3. **为什么 Hybrid 看起来更快？** 异常长输出、固定调用顺序、热身和系统波动污染均值；当前证据不支持 Regex 天然加速 LLM。
4. **接近 100% 脱敏为什么不能直接上生产？** 单例的“敏感字符串消失”可能同时误删订单号；生产需要同时验证漏报、误报、日志可用性、失败降级和分布漂移。

### C. 3-4 至 3-6 检索基础

1. **精确/近似检索与语义检索是什么关系？** “精确/近似”描述邻居搜索算法，“关键词/语义”描述相关性表示，不是同一层分类。
2. **ANN Recall 是 Embedding 准确率吗？** 不是；它只比较近似索引与精确向量 Top-K。Embedding 质量需要人工相关性标签和 Recall/MRR/nDCG。
3. **Top-K 返回词上下多少字符吗？** 不是；返回预先定义的文档或 chunk 检索单元。
4. **ANNOY/HNSW 如何发音与选型？** ANNOY 通常按英文 `annoy` 读；HNSW 逐字母读，中文常译“分层可导航小世界图”。前者偏静态，后者更适合动态增量。
5. **单词查询的 IDF 不是常量吗？** 对固定语料单词查询是共同常数，通常不改变命中文档相对顺序；多词查询中不同 IDF 无法提出求和号，会改变排名。
6. **多词 BM25 怎样综合？** 各查询词倒排列表取并集；每篇文档逐词计算贡献并相加，没有额外“全词命中奖励”。
7. **BM25 分母为什么这样设计？** TF 分子分母共同形成饱和；`k1` 控制饱和速度；`b` 在不做长度校正与完整相对长度校正之间插值。
8. **什么时候调 `k1/b`？** 关键词重复虚高可降 `k1`；天然长且主题集中的文档被误罚可降 `b`。相关文档根本没进候选时，不应调这两个排序参数。
9. **BM25 与 Dense 怎样融合？** RRF 按名次加和；Weighted 先各路 min-max 再按权重加和。都按 `doc_id` 合并候选，不拼接向量。
10. **重排能补召回吗？** 不能；Cross-Encoder 只能重排候选池已有文档，且语言/领域不匹配会降级。
11. **BM25 除速度外纠正什么？** 它提供订单号、错误码、版本号、字段名等精确字面锚点，抑制 Dense 的语义过度泛化和编号混淆。

### D. 3-7 结构化索引

1. **ADDPS、AVX、SSE、XMM、YMM 是什么？** 它们只是实验语料中的指令、指令集扩展和寄存器；不是理解结构化索引的前置知识。
2. **RAPTOR 和 GraphRAG 分别做什么？** RAPTOR 预计算摘要层次；GraphRAG 预计算实体、关系和社区。
3. **生成的图能不能看？** 可以；可视化暴露了 `XCR0/XCR0 register` 等重复节点，说明实体归一化是核心质量问题。
4. **图没建好会怎样？** 漏边导致多跳断路，错误边比漏边更危险；语义文本召回可能兜底，但成功就不再能归因于图路径。

### E. 3-8 与 3-9 Agentic 检索

1. **问题拆解为什么能让三个目标都排第一？** 仅拆解不能保证；官方查询还加入领域术语和答案导向词，因此更接近 oracle 查询改写。
2. **子查询是写死还是模型生成？** 离线脚本写死；完整 campaign 才由模型在 ReAct 循环中生成。
3. **强模型能否生成高质量拆解？** 单例中 Sol 可以，Kimi 能识别支线但检索改写较弱；稳定性仍需多题重复实验。
4. **多轮模型调用怎样实现？** Python Harness 保存 `messages`，执行 tool call，把 `tool_call_id + 搜索结果` 追加后重新调用模型；API 不会自动记忆和循环。
5. **一次检索漏掉第二辆车，Agent 后续能补吗？** 若首轮完全没有第二辆车的桥接线索，后续通常无法凭空追查；Top-K=1 对照已验证。
6. **市场上 Top-K 是否都保留几十个？** 应区分候选、重排后结果和最终上下文。可从候选 20–50、重排后 5–20、最终上下文 3–10 起步，再按评测调整。

### F. 3-10 与 3-11 上下文和双层记忆

1. **上下文前缀是帮助 AI 找原文还是提高排名？** 直接作用是提高正确 chunk 的召回和排名；不是在块内标出答案句。
2. **是否所有系统都会给每个块做 LLM 摘要？** 不会。先用标题路径、元数据、重叠/父子分块；高价值、低频更新、孤儿块严重时再生成 chunk-specific 前缀。
3. **双层记忆是哪两层？** 上层是 Advanced JSON Card 当前状态，下层是可检索原始对话证据。
4. **它是双重搜索吗？** 当前实验不是；卡片整份直接加载，只有历史对话经过 Contextual BM25。
5. **原始对话算记忆吗？** 狭义上是历史记录，不是抽取后的长期记忆；在 Agent 架构中可称情节记忆或可检索记忆档案。
6. **双层结果是什么？** 自动报告 78.33%→86.67%→95%，但人工审计发现假通过、幻觉和旧卡片锚定；只能确认互补性，不能确认真实 95%。
7. **实验运行成本怎么控制？** 本轮没有重跑 60 案例；后续付费实验默认抽约 10 个代表案例，运行前说明调用量、Token 和费用。

### G. 3-12 结构化知识抽取

1. **是不是先发现 JSON Card 字段，再从原文填写？** “先发现字段再抽取”正确，但产物是数据集级 schema/特征表，不是用户记忆卡片。
2. **这是不是记忆抽取？** 不是狭义记忆抽取，而是离线知识发现和特征工程；产物以后可以被 Agent 当知识使用。
3. **实验核心是什么？** LLM 负责发现和填写语义字段，传统算法负责聚类与统计，Agent 基于可追溯统计解释和追问。
4. **需要学什么？** 区分 schema discovery 与 extraction、训练与留出隔离、`null` 与 `false`、相关性与因果性，以及逐层验收。

## 六、贯穿全部实验的最终学习结论

1. **先定义检索/记忆单元和 Gold，再讨论准确率。** 没有人工相关性、状态或原子事实标准，单个分数没有意义。
2. **候选召回、答案使用和 Judge 判分必须分开。** 召回正确不等于答案正确；答案看起来正确也可能使用了无来源知识；Judge 也会假通过和假失败。
3. **复杂度不会带来单调增益。** Advanced JSON、GraphRAG、Agentic 循环和 Cross-Encoder 都出现过更贵但更差的案例。
4. **结构化的价值主要是可操作和可审计。** JSON/Card/schema 让字段、状态和来源更容易查询与验证，但结构本身不保证内容正确。
5. **原始证据必须保留。** 摘要、卡片、图和原型都是派生物；出现冲突时必须能够回到原始对话、原始 chunk 或原始案件。
6. **混合系统通常优于四选一。** 生产系统常同时保留事件日志、结构化状态、BM25、Dense、可选图/树和重排，再按问题类型路由。
7. **实验应做分层消融。** 固定语料、模型、查询、Top-K、Prompt 和 Gold，每次只改变一层；人工 oracle 只能表示上界，不能冒充 Agent 能力。
8. **成本要按阶段计算。** 记忆重写和索引构建通常是离线/会话后成本；Dense、Agent 多轮和重排增加在线延迟；完整实验必须同时报告质量、Token、费用和尾延迟。
9. **小样本用于理解机制，不用于证明生产稳定性。** 当前后续默认抽样约 10 个代表案例；全量运行必须有明确新增学习价值并由用户确认。
