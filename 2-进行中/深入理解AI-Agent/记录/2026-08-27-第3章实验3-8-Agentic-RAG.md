## Codex 反馈

### 1. 实验真正改变的变量

两条链路使用同一份中文法律语料、同一个按法条分块的 BM25 检索器、相同的 `Top-K=5` 和回答模型。唯一有意改变的是“谁来控制检索过程”：

```text
非 Agentic RAG
用户问题 -> 原问题检索一次 -> Top 5 法条 -> LLM 回答

Agentic RAG
用户问题 -> LLM 判断缺什么 -> 生成检索词 -> BM25 Top 5
         -> LLM 阅读结果 -> 仍缺什么则继续搜索 -> 汇总证据并回答
```

因此，本实验不是在比较 BM25 和语义检索，也不是比较两个回答模型，而是在比较固定检索管道与由 Agent 主导的动态检索循环。

### 2. 实验材料

- 语料：288 份中文法律文档，共 21,372 个按法条切分的 chunk。
- 数据集：7 道题，源码标成 3 道 `easy`、4 道 `hard`。
- 简单题示例：`正当防卫是怎么规定的？`
- 复合题示例：`醉酒过失致人重伤且有盗窃前科，应如何量刑？`
- 检索：中文分词后的 BM25，每次返回前 5 个法条 chunk。
- Agent 最大搜索预算：4 次。

### 3. 要观察的四层结果

1. **查询规划**：Agent 把原问题改写或拆成了哪些检索词？
2. **证据召回**：金标准法条命中了几个？
3. **回答质量**：最终结论是否完整、是否只依据检索证据？
4. **工程代价**：搜索次数、LLM 调用次数、Token 和延迟增加了多少？

关键区别是：证据召回率只衡量“材料找没找到”，不是答案正确率。找到正确法条后，模型仍可能理解错；没找到时，模型也可能靠参数知识猜对，但这违反了受控 RAG 的证据边界。

### 4. 两种运行层级必须分开

- `compare_offline.py`：不调用 LLM。Agent 侧的子查询由数据集预先写好，只能验证“如果问题被正确分解，多次检索是否有帮助”，不能证明 Agent 真能自主分解。
- `campaign.py`：由回答模型现场决定搜索词并走 ReAct 工具循环，才是端到端 Agentic RAG；另用一个 LLM Judge 评分。

### 5. 预审发现的实验设计风险

在运行前审计历史真实凭据，发现不能直接接受 README 的漂亮结论：

1. `hard_1` 到 `hard_3` 都只要求一个法条，本质上是单跳题，只是原问题的 BM25 表述不容易命中；它们更接近“查询改写题”，不是真正多跳题。
2. 复合题的金标准包含“危险驾驶罪”法条，但题目只说“醉酒过失致人重伤”，没有明确说驾驶机动车。这个金标准可能强行加入了题目没有给出的事实。
3. Judge Prompt 规定 4 分最好、1 分错误，但历史 Judge 多次在理由中写“回答正确、全面”，同时给 1 分。聚合的 `judge_correctness` 因而不可直接解释为正确率。
4. 历史复合题中，Agent 实际只召回 3 个金标准法条中的 2 个，却仍被实验汇总当作支持整体假设的结果。
5. 历史回答使用了没有出现在检索证据中的累犯知识，Judge 却没有稳定识别，说明“有引用”不等于“所有结论都被引用支持”。

这使实验 3-8 同时成为一个评测设计案例：需要区分“代码执行通过”“验收字段为 true”和“科学结论可信”。

### 6. 第一次离线运行：原始整句与三类分解查询

本机使用当前代码、288 份法律文档和 21,372 个法条 chunk 运行 BM25，`Top-K=5`。

原始整句：`醉酒过失致人重伤且有盗窃前科，应如何量刑？`

- 正确的过失致人重伤法条（刑法第二百三十五条）排第 4，成功召回。
- Top 5 还混入故意伤害、滥用职权致重伤、危险方法致重伤和交通肇事等高词面重合但并非本题直接答案的法条。
- 醉酒刑事责任（刑法第十八条）没有进入 Top 5。
- 累犯及其过失犯罪例外（刑法第六十五条）没有进入 Top 5。

分解查询结果：

| 子问题 | 查询 | 正确法条排名 |
| --- | --- | ---: |
| 基础量刑 | `过失伤害他人致人重伤 有期徒刑` | 第 1 |
| 醉酒责任 | `醉酒的人犯罪 刑事责任` | 第 1 |
| 前科/累犯 | `盗窃前科 累犯 从重处罚 过失犯罪` | 第 1 |

对用户预测的修正：第一类确实会受到多个“致人重伤”法条干扰，所以说它“麻烦”有依据；但它仍是原始整句唯一命中的核心类别。真正完全漏召回的是第二、三类，原因是用户词“醉酒、前科”与目标法条中的完整表达“醉酒的人犯罪应当负刑事责任、累犯”之间存在词汇和概念转换。

官方离线脚本给出的复合题证据召回率为 `33% -> 100%`。这个数字只是按数据集预设的三个金标准法条计算；由于其中包含题面未明确支持的危险驾驶条款，暂不能把 `100%` 直接当作语义上完全正确。

### 7. 第二次受控运行：自然拆解与答案导向改写

为检验用户的质疑，增加一组不含法条编号、不预塞答案关键词的自然问题，与官方预设查询比较。目标法条在全库 BM25 中的实际排名如下：

| 类别 | 自然拆解查询 | 自然排名 | 官方预设改写 | 预设排名 |
| --- | --- | ---: | --- | ---: |
| 基础量刑 | `过失致人重伤怎么处罚` | 第 6 | `过失伤害他人致人重伤 有期徒刑` | 第 1 |
| 醉酒责任 | `醉酒会不会影响刑事责任` | 第 5 | `醉酒的人犯罪 刑事责任` | 第 1 |
| 前科/累犯 | `以前有盗窃前科会不会影响这次过失致人重伤的量刑` | 前 50 未命中 | `盗窃前科 累犯 从重处罚 过失犯罪` | 第 1 |

实验支持用户的质疑：自然拆解并不保证排名第一，甚至可能因改变查询词而让原已命中的基础量刑法条从第 4 降到第 6、掉出 `Top-K=5`。官方预设查询同时做了三件事：

1. 把复合问题拆成多个子问题；
2. 把用户语言改写成法律术语，如“前科”改写为“累犯”；
3. 加入接近答案正文的高判别词，如“从重处罚”“有期徒刑”。

因此“三个第一”主要证明“领域知识充分、接近金标准的查询改写”有效，不能单独归因于“拆解”。原离线脚本更接近 oracle 上界实验：假设 Agent 已经生成了理想查询，再测检索器能否找回证据。要检验 Agent 能力，必须让模型在不知道金标准的情况下现场生成查询。

### 8. 写死子查询与真实模型生成必须分开

实验代码有两条不同链路：

- `compare_offline.py` 直接读取数据集中的 `subqueries` 并逐条搜索。这三个查询是人工预先写死的，不调用 LLM。
- `campaign.py` 把 `search_law` 暴露为工具，System Prompt 只要求“先分解问题并搜索；复杂问题对每个独立法律问题迭代搜索”。具体查询由回答模型在 ReAct 循环中现场生成，最多搜索 4 次。

历史真实运行使用 `doubao-seed-1-6-250615`，在复合题中生成了：

```text
醉酒过失致人重伤 盗窃前科 量刑
醉酒 犯罪 量刑
盗窃前科 量刑影响 刑法
前科 量刑影响 刑法
```

这个模型识别到了“醉酒”和“前科”是独立支线，但没有把“前科”进一步改写为关键法律术语“累犯”，也没有生成官方预设的高判别查询。因此，真实 LLM 可以生成有用拆解，但本次证据不支持“它能稳定生成 oracle 级查询”。

更严重的是，历史统计宣称 Agent 命中了目标“第六十五条”，实际命中的却是《铁路法》第六十五条：

```text
第六十五条 在列车内，抢劫旅客财物……
```

原因是 `article_hits()` 只在所有结果文本中检查“第六十五条”这个字符串，没有同时核对法律名称或文档 ID。不同法律都可能有同号法条，所以历史 `2/3` 证据召回被错误抬高；按“法律名称 + 法条号”严格核对，模型并没有召回目标《刑法》第六十五条。

当前可下的结论是：

1. 强模型具备从用户语言推断领域术语的可能性；
2. 能否生成高质量子查询取决于模型领域知识、Prompt、工具返回和迭代预算；
3. 不能用人工 oracle 子查询的结果代表真实 Agent 能力；
4. 必须直接评估“生成的查询”和“法律名称 + 法条号”的真实证据命中。

### 9. GPT-5.6 Sol 盲测

先澄清模型与 Key：本轮之前没有调用豆包，也没有读取或使用豆包 Key。`doubao-seed-1-6-250615` 只是本地资料中 2026-07-29 历史运行凭据的配置字段；将其表述得像本轮模型调用属于 Codex 沟通错误。当前盲测使用 Codex 提供的 GPT-5.6 Sol 子 Agent，不调用外部模型 API，不需要任何豆包、Kimi 或 OpenAI API Key。

盲测约束：只给 Sol 原始问题、本地 `search_law` BM25 工具和 4 次搜索预算；禁止读取 `evaluation/`、`validation/`、README、实验脚本和本学习记录，避免人工子查询与金标准泄漏。

Sol 自主生成的四轮查询及目标证据：

| 轮次 | 模型查询 | 关键结果 |
| --- | --- | --- |
| 1 | `过失致人重伤 量刑 刑法` | 《刑法》第 235 条排第 4，找到基础法定刑 |
| 2 | `醉酒的人犯罪 刑事责任 刑法` | 《刑法》第 18 条排第 1，找到醉酒不免责 |
| 3 | `盗窃前科 累犯 从重处罚 刑法` | 目标《刑法》第 65 条排第 3，明确过失犯罪排除在一般累犯之外 |
| 4 | `前科 劣迹 酌情从重 量刑指导意见 过失犯罪` | 《刑法》第 65 条排第 1，同时找到过失定义；未找到一般前科酌定从重的直接规范 |

本次结果表明 Sol 不仅把问题拆成了基础罪名、醉酒责任和前科影响三条支线，还自主完成了“前科 -> 累犯”的领域术语转换，并在第三轮结果后继续查询一般前科是否构成酌定量刑情节。它没有因为题目出现“醉酒”就擅自加入危险驾驶，而是指出致伤方式不明、可能存在其他罪名，这比数据集的固定金标准更符合题面边界。

结论边界：这是一个模型、一道题、一次运行，只能证明 GPT-5.6 Sol **能够在该案例中**产生高质量拆解，不能证明它稳定可靠。要估计稳定性，需要固定 Prompt 与语料，对多道未见题重复运行，并按“法律名称 + 法条号”、查询覆盖率、无根据扩展和搜索成本分别评分。

### 10. 阶段总结（待用户确认）

实验 3-8 的核心机制已经覆盖：传统 RAG 将原问题检索一次后直接回答；Agentic RAG 把检索变成工具，由模型根据问题和中间证据反复执行“拆解、改写、搜索、检查缺口、继续搜索、综合回答”。它的潜在增益不是简单来自“多搜几次”，而是来自三个可分离能力：

1. **问题拆解**：识别一个复合请求中的多条独立信息需求；
2. **查询改写**：把用户语言转换为知识库中的领域术语；
3. **迭代纠错**：根据本轮结果判断缺口并调整下一轮查询。

当前证据支持的有限结论：

- 单次原问题检索会遗漏复合问题中的部分证据。
- 人工 oracle 查询能显著提高 BM25 召回，但不能代表真实 Agent 能力。
- 自然拆解并不保证提升，甚至可能让正确法条掉出 Top 5；领域术语改写才是本案例排名提升的关键。
- GPT-5.6 Sol 在一次盲测中能自主完成“前科 -> 累犯”转换并逐轮补证，证明强模型具备这种能力。
- 简单明确问题通常没有必要承担多轮 Agent 搜索的额外调用、Token 和延迟；生产系统更适合先路由，再按复杂度升级。

当前实验不能支持的强结论：

- 不能采信“复杂题 8% -> 100%”为真实 Agent 提升，因为离线子查询是人工写死的，且金标准含题面未支持的危险驾驶法条。
- 不能采信历史证据召回，因为只核对法条号，把《铁路法》第六十五条误算成《刑法》第六十五条。
- 不能采信历史 Judge 汇总，因为评分方向与文字理由矛盾，并漏判无证据结论。
- 不能根据一道题、一次 Sol 运行推断模型稳定性，也还没有完成 Kimi K2.6 与 Sol 的公平盲测比较。

如果学习目标是理解 Agentic RAG，本节已经足够，可以收口；如果目标是验证书中的量化结论，则必须重新设计数据集、严格证据标识、修复 Judge，并在多道未见问题上重复运行。当前建议是不继续为原实验追加模型费用，把“如何做可靠评测”留到第 7 章统一深化。

### 11. Kimi K2.6 真实盲测

使用本地 `MOONSHOT_API_KEY` 调用 `kimi-k2.6`，开启 thinking；不给模型人工子查询或金标准，只提供与 Sol 同一原问题、本地 BM25 `Top-K=5` 工具和 4 次搜索预算。不调用 Judge。

第一次请求失败，明确原因是 Kimi API 不允许 `thinking=enabled` 与 `tool_choice=required` 同时使用。保留 thinking，将工具选择改为 `auto`，并在 System Prompt 中要求第一步必须搜索后重试成功。该失败与 Key、余额和模型名无关。

Kimi 在两轮模型决策中并行用完四次搜索：

| 搜索 | Kimi 查询 | 关键结果 |
| --- | --- | --- |
| 1 | `过失致人重伤罪 量刑` | 未命中《刑法》第 235 条；Top 5 被故意伤害等相似法条占据 |
| 2 | `醉酒 刑事责任能力` | 《刑法》第 18 条排第 4，成功召回醉酒责任 |
| 3 | `过失致人重伤罪` | 基本重复第一次查询，仍未命中第 235 条，浪费一次搜索预算 |
| 4 | `累犯 刑法 量刑` | 命中第 74 条“不适用缓刑”，但未命中目标第 65 条的累犯构成和从重规则 |

运行数据：`kimi-k2.6` 返回，4 次搜索，约 62.2 秒；累计 5,866 prompt tokens、2,202 completion tokens、8,068 total tokens。

最终回答表现：

- 正确引用第 18 条，说明醉酒不免除刑事责任。
- 对盗窃前科保持谨慎：只找到累犯不适用缓刑的第 74 条，没有找到第 65 条，因此拒绝判断是否构成累犯及从重处罚。
- 明确承认未找到第 235 条，拒绝给出具体基础量刑。
- 虽然模型通过参数知识知道应继续找第 235 条和第 65 条，但它没有把这项认识转化为新的高质量检索词；这是典型的“规划方向正确、工具执行和迭代改写失败”。

与本次 Sol 单例对照：

| 维度 | Kimi K2.6 | GPT-5.6 Sol |
| --- | --- | --- |
| 识别三条支线 | 做到 | 做到 |
| “前科 -> 累犯”转换 | 做到 | 做到 |
| 命中第 235 条 | 未命中 | 第 4 |
| 命中第 18 条 | 第 4 | 第 1 |
| 命中目标《刑法》第 65 条 | 未命中 | 第 3，后续第 1 |
| 根据失败改写查询 | 较弱，重复搜索 | 较强，继续搜索酌定从重依据 |
| 证据不足时克制 | 做到 | 做到 |

这不是严格的模型排行榜：仅一道题、各一次运行，Sol 通过 Codex 子 Agent 执行，Kimi 通过 OpenAI 兼容 API 工具循环执行，Harness 并不完全相同。当前只能得出：在这一个案例中，Kimi 能完成问题拆解和关键术语识别，但 Sol 的查询构造与迭代纠错明显更有效。

### 12. 多轮模型调用如何实现

“一轮模型调用”和“一次工具搜索”不是同一件事。模型调用是向 Kimi API 发送一次完整 `messages`；工具搜索是在本地执行一次 BM25。一个模型响应可以同时包含多个 `tool_calls`，所以一轮模型调用可能触发多次搜索。

外层 Python Harness 维护状态，模型 API 本身不会在独立 HTTP 请求之间自动记住上一轮。核心循环如下：

```python
messages = [system_message, user_message]
search_budget = 4

while True:
    response = call_kimi(messages, tools=[search_law])
    messages.append(response.assistant_message)

    if not response.tool_calls:
        return response.content

    for call in response.tool_calls:
        rows = local_bm25_search(call.arguments["query"])
        messages.append({
            "role": "tool",
            "tool_call_id": call.id,
            "content": rows,
        })
        search_budget -= 1

    if search_budget == 0:
        return call_kimi(messages + ["预算用完，请根据现有证据作答"])
```

`tool_call_id` 用来告诉模型“这份结果对应刚才哪一次工具请求”。下一轮再次发送整个 `messages`，模型才看得到自己先前搜索了什么、返回了哪些法条，从而决定补搜或作答。

本次 Kimi 的实际时间线：

```text
模型调用 1
  输入：System + 原始问题
  输出：2 个工具调用
        ① 过失致人重伤罪 量刑
        ② 醉酒 刑事责任能力

本地搜索 1、2
  分别返回两个 Top 5，追加为 role=tool 消息

模型调用 2
  输入：System + 原问题 + 上一轮两个工具调用 + 两份 Top 5
  输出：2 个新工具调用
        ③ 过失致人重伤罪
        ④ 累犯 刑法 量刑

本地搜索 3、4
  返回两份 Top 5；搜索预算耗尽

模型调用 3
  输入：截至目前的完整 messages + “预算已用完，只按证据回答”
  输出：最终答案
```

所以本次统计是 **3 次模型 API 调用 + 4 次本地 BM25 搜索**，不是 4 次模型调用。累计 Token 会把三次 API 请求分别使用的输入和输出相加；由于后续请求携带之前的工具结果，Context 通常逐轮变长。

本次 Kimi 特有的参数边界：thinking 模式不兼容 `tool_choice=required`，因此改用 `tool_choice=auto`，并由 System Prompt 要求第一步必须搜索。隐藏思考内容没有打印或手工注入；Harness 只持久传递可观察的 assistant tool calls、tool results 和最终文本。

### 13. 最终总结（待用户确认）

实验 3-8 比较同一法律语料、同一 BM25 和同一 `Top-K=5` 下的两种控制方式：普通 RAG 把原问题搜索一次后直接回答；Agentic RAG 由 Harness 循环调用模型和搜索工具，让模型拆解问题、改写查询、阅读结果、补搜证据并最终回答。

本实验真正要学习的不是“多搜几次更好”，而是把 Agentic 检索能力拆成三个环节：

1. 找出复合问题包含哪些独立信息需求；
2. 把用户语言转换成知识库中的领域词汇；
3. 根据本轮搜索失败或缺口改写下一轮查询。

本地实验显示：原问题单次搜索只覆盖一部分证据；自然拆解不保证排名提升；人工 oracle 查询由于加入“累犯、从重处罚”等接近法条的词，可以把目标推到第一，但不能代表真实模型能力。真实盲测中，Kimi K2.6 和 GPT-5.6 Sol 都识别了三条法律支线并想到“前科 -> 累犯”；在这一单例中 Sol 的查询构造和失败后补搜更有效，Kimi 仅召回醉酒责任，但在证据不足时保持了克制。

多轮实现由 Python Harness 控制，而不是模型 API 自动循环。本次 Kimi 是 3 次模型调用和 4 次本地 BM25 搜索；每一轮都重新发送不断增长的 `messages`，其中包含模型工具请求、`tool_call_id` 和搜索结果。

书中原实验的量化结果不能直接采信：离线子查询人工写死，复合题金标准含题面未支持的危险驾驶法条，证据匹配只比较法条号导致同号法律误命中，Judge 评分方向与文字理由冲突，且样本和重复次数不足。

最终可保留的工程结论：

- 简单、明确问题优先走一次检索，降低延迟和 Token。
- 复合问题或证据不足时，再升级为 Agentic RAG。
- 评测必须分别检查查询规划、严格证据命中、最终回答依据和成本。
- 证据主键至少应包含“法律名称 + 法条号”，不能只用法条号。
- 人工理想查询只能作为上界，不得冒充真实 Agent 结果。

建议收口口径：**Agentic RAG 的机制已理解；书中当前量化结论不采信；本单例中 Sol 的查询改写优于 Kimi，但模型稳定性和公平排名留待严格评测。**

## 发散联想

- 生产系统通常不会让所有问题都进入昂贵的 ReAct 循环，而会先路由：简单问题走一次检索，复杂/证据不足的问题再升级为 Agentic RAG。
- Agentic RAG 的核心能力不是“多搜几次”，而是根据已返回证据判断缺口并调整下一次查询；若只是预先写死子查询，它仍是工作流，不是 Agent 自主决策。
- “问题拆解”和“查询改写”是两个变量：前者决定搜索几条支线，后者决定每条支线使用什么词。实验若同时改变两者，就无法把增益只归因于拆解。
- 评测必须把检索、生成和评审拆开，否则“检索改善但答案没改善”或“答案碰巧正确但没有证据”会被混成一个分数。
