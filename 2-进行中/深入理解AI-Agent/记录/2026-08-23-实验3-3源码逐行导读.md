## 五、先看懂输入：`CASES` 与 Gold

一条测试用例大致长这样：

```python
{
    "id": "natural_password",
    "text": "用户说：我网银的登录口令是‘Blue moon over river 77’，请帮我记住。",
    "gold": [
        ("password", "Blue moon over river 77")
    ],
}
```

三个字段分别表示：

- `id`：案例名称。
- `text`：真正交给三个策略的相同输入。
- `gold`：人工提前标好的正确答案。

Gold 使用 `(type, value)`：

```python
("password", "Blue moon over river 77")
```

意思是：

```text
敏感信息类型 = password
应该从原文中删除的精确字符串 = Blue moon over river 77
```

Gold 不是模型生成的。如果 Gold 也由被测模型生成，实验就会变成模型自己给自己判卷。

## 六、Regex 链路逐步解释

### 1. `_RULES` 是规则表

每条规则包含：

```python
(
    category,     # 类型，例如 cn_phone
    placeholder,  # 替换文本，例如 [REDACTED_PHONE]
    pattern,      # 编译后的正则
    group,        # 真正要删除哪个捕获组
    validator,    # 可选校验函数
)
```

手机号规则：

```python
(
    "cn_phone",
    "[REDACTED_PHONE]",
    re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"),
    0,
    None,
)
```

逐段解释：

```text
(?<!\d)   左边不能紧挨着数字
1         第一位必须是 1
[3-9]     第二位必须在 3 到 9 之间
\d{9}     后面再跟 9 位数字
(?!\d)    右边不能紧挨着数字
```

它只能判断“形状像手机号”，不能判断：

```text
order_id=13800138000
```

中的数字其实是订单号。

### 2. `sanitize()` 收集候选

教学化简后，相当于：

```python
candidates = []

for priority, rule in enumerate(RULES):
    for match in rule.pattern.finditer(text):
        value = match.group(rule.group)

        if rule.validator and not rule.validator(value):
            continue

        candidates.append({
            "category": rule.category,
            "value": value,
            "start": match.start(rule.group),
            "end": match.end(rule.group),
            "priority": priority,
        })
```

这里不会立刻修改原文，只是先记录候选及位置。

### 3. Validator 降低误报

例如银行卡不能只判断“13～19 位数字”，还会经过 Luhn 校验：

```python
if validator and not validator(value):
    continue
```

中国身份证也会验证校验码。

但手机号规则没有类似校验器，所以任何符合数字形状的订单号都可能误报。

### 4. 重叠候选只保留一个

同一串字符有时会同时匹配不同规则。代码按规则优先级排序，如果一个新候选与已接受候选重叠，就丢弃新候选。

```python
if 和任何已接受区间发生重叠:
    continue
```

这避免一段文本被重复替换。

### 5. 根据位置重建文本

不要在从左到右遍历时原地替换，否则第一次替换改变字符串长度，后面的 `start/end` 就会失效。

Regex 实现采用分段重建：

```text
原文 0 到第一个 start
+ 第一个 placeholder
+ 第一个 end 到第二个 start
+ 第二个 placeholder
+ 最后一段文本
```

## 七、LLM 链路逐步解释

### 1. Prompt 告诉模型做什么

`campaign.py` 中的 System Prompt 要求模型：

- 检测日志中的敏感信息。
- 返回原文中的精确子串。
- 区分真实隐私与字段名、说明文字、产品编号、指标、显式诱饵。
- 返回 `type / value / start / end / confidence`。
- 不要自行改写或直接脱敏原文。

最后一条很重要：模型只负责“指出哪里应该删”，替换动作由确定性的 Python 代码完成。

### 2. JSON Schema 规定返回形状

模型必须尽量返回：

```json
{
  "findings": [
    {
      "type": "password",
      "value": "Blue moon over river 77",
      "start": 16,
      "end": 39,
      "confidence": 0.97
    }
  ]
}
```

JSON Schema 只能约束“字段结构”，不能保证内容判断一定正确。例如模型仍可能：

- 把订单号判断成手机号。
- `start/end` 算错。
- 返回原文中不存在的改写文本。
- 类型写错。

### 3. 真正的模型调用

原理上的核心只有这一句：

```python
response = client.chat(**request)
```

其中 `request` 包含：

```python
request = {
    "model": "qwen3:0.6b",
    "messages": [
        {"role": "system", "content": SYSTEM},
        {"role": "user", "content": text},
    ],
    "format": SCHEMA,
    "options": {
        "temperature": 0,
        "seed": 37,
        "num_predict": 1200,
    },
    "stream": False,
}
```

参数含义：

| 参数 | 含义 |
| --- | --- |
| `model` | Ollama 中已经下载的模型名称 |
| `messages` | System Prompt 与原始日志 |
| `format` | 输出必须遵守的 JSON Schema |
| `temperature=0` | 尽量降低随机性 |
| `seed=37` | 固定随机种子，提高重复实验的一致性 |
| `num_predict=1200` | 限制最多生成多少 token |
| `stream=False` | 等完整结果生成后一次返回 |

### 4. `normalize_findings()` 修复常见位置问题

模型返回的 `start/end` 不一定可靠。代码检查：

```python
text[start:end] == value
```

如果不相等，就退回：

```python
start = text.find(value)
end = start + len(value)
```

如果 `value` 根本不存在于原文，则丢弃该发现。

这是一个重要安全边界：模型说“有密码”还不够，必须给出能在原文中定位的精确字符串。

但 `text.find(value)` 也有局限：同一个值出现多次时，它永远先找到第一次出现的位置。

## 八、Hybrid 链路逐步解释

官方当前实现是：

```python
# 第一步：Regex 找候选
regex_hits = regex_findings(original_text)

# 第二步：立刻把 Regex 候选替换掉
regex_redacted = redact(original_text, regex_hits)

# 第三步：LLM 只看已经处理过的文本
remaining_hits = llm_findings(regex_redacted)

# 第四步：把 LLM 新找到的内容映射回原文
mapped_hits = map_back_to_original(remaining_hits)

# 第五步：合并
hybrid_hits = regex_hits + mapped_hits
```

它的优点是：

- LLM 不会反复识别 Regex 已经能稳定发现的内容。
- 交给 LLM 的敏感信息更少。
- 规则负责便宜的强格式模式，模型补语义型遗漏。

它的关键缺点是：

```text
Regex 如果误删，LLM 无法恢复。
```

例如 Regex 把订单号替换成 `[REDACTED_CN_PHONE]` 后，LLM 根本看不到原订单号，自然不能告诉系统“刚才删错了”。

因此，这个 Hybrid 更擅长提高 Recall，不天然保证提高 Precision。

工程上更稳妥的一种变体是：

```text
Regex 只生成候选，不立即替换
  ↓
确定性高的候选直接接受
  ↓
模糊候选交给 LLM 复核
  ↓
汇总最终 findings
  ↓
只执行一次替换
```

但这是改进建议，不是当前官方代码已经实现的事实。

## 九、`redact()` 为什么从后往前替换

假设原文中有两个敏感片段：

```text
AAAA 123456 BBBB 987654 CCCC
```

若先替换左边，字符串长度改变，右边的原始下标会失效。

所以代码按照 `start` 从大到小替换：

```python
for finding in sorted(findings, key=lambda x: x["start"], reverse=True):
    result = (
        result[:finding["start"]]
        + "[REDACTED]"
        + result[finding["end"]:]
    )
```

先改右边不会影响左边的下标。

在替换前，代码还会处理重叠候选：优先接受置信度更高的发现项。

## 十、指标代码在算什么

假设 Gold 是：

```python
gold = {
    ("password", "hunter2xyz"),
    ("cn_phone", "13912345678"),
}
```

模型预测是：

```python
predicted = {
    ("password", "hunter2xyz"),
    ("cn_phone", "13912345679"),  # 实际是订单号
}
```

### Precision

```text
正确预测数量 ÷ 全部预测数量
= 1 ÷ 2
= 0.5
```

它反映“删掉的内容里有多少真的该删”。订单号误删会降低 Precision。

### Recall

```text
正确找到的 Gold 数量 ÷ 全部 Gold 数量
= 1 ÷ 2
= 0.5
```

它反映“所有应该删的内容找全了吗”。手机号漏掉会降低 Recall。

### Typed Exact

不仅 `value` 要正确，`type` 也要正确：

```text
(password, hunter2xyz)              正确
(secret, hunter2xyz)                value 对、type 错
(password, password: hunter2xyz)    返回范围也错
```

### Residual Leakage

执行替换后，再检查 Gold 中的敏感原值是否还存在。

```python
residual_leaks = [
    value for value in gold_values
    if value in redacted_text
]
```

这是最直接的隐私风险指标。

### Utility

它估算误删了多少非敏感字符：

```text
Utility = 1 - 误删字符数 / 全部非敏感字符数
```

订单号被删会降低 Utility。

### Latency

每条链路从开始到结束的毫秒数。Hybrid 的延迟是：

```text
Regex 延迟 + Hybrid 中第二次 LLM 调用延迟
```

## 十一、`agent.py` 和 `campaign.py` 的差别

| 维度 | `agent.py` | `campaign.py` |
| --- | --- | --- |
| 主要用途 | 演示、日志文件、会话批处理 | 3-3 三路受控实验 |
| 调用模型 | Ollama；失败时可选 OpenRouter 回退 | 只用本地 Ollama |
| 输出结构 | `type + value` | `type + value + start + end + confidence` |
| 模型响应 | 流式输出 | 非流式，一次返回 |
| 替换方式 | 根据 value 全文不区分大小写替换 | 根据 start/end 精确替换 |
| Regex 对照 | 不负责三路对照 | 有 |
| Hybrid | 没有 | 有 |
| Gold 指标 | 主要是性能统计 | 有 Precision、Recall、泄漏、Utility |

`agent.py` 中有一个安全检查：只接受确实出现在输入原文中的 `value`。这能阻止模型凭空生成一个不存在的“敏感值”并尝试替换。

但它通过 `re.sub(..., flags=re.IGNORECASE)` 替换某个值的所有出现位置。这也意味着：如果同一个字符串在一个地方是密码、另一个地方是公开编号，它会把两处都替换。

## 十二、教学等价版：把整个实验压缩成一段代码

下面不是可直接替换官方源码的实现，而是帮助你建立脑内骨架：

```python
import json
import time
import ollama

# ------------------------------------------------------------
# 1. 人工测试集：text 是输入，gold 是标准答案
# ------------------------------------------------------------

CASES = [
    {
        "id": "mixed_context",
        "text": (
            "call me at 13912345678; "
            "order 13912345679; "
            "password: hunter2xyz"
        ),
        "gold": [
            ("cn_phone", "13912345678"),
            ("password", "hunter2xyz"),
        ],
    }
]


# ------------------------------------------------------------
# 2. Regex 路线：调用已有规则引擎
# ------------------------------------------------------------

def run_regex(text):
    # 官方实现会返回脱敏文本以及每个命中的类型、值和位置。
    _, raw_hits = regex_sanitizer.sanitize(text)

    # 统一成实验使用的数据结构。
    return [
        {
            "type": hit["category"],
            "value": hit["value"],
            "start": hit["start"],
            "end": hit["end"],
            "confidence": 1.0,
        }
        for hit in raw_hits
    ]


# ------------------------------------------------------------
# 3. LLM 路线：Python 直接调用 Ollama，不经过 LangChain
# ------------------------------------------------------------

def run_llm(client, text):
    response = client.chat(
        model="qwen3:0.6b",
        messages=[
            {
                "role": "system",
                "content": "找出敏感信息，返回精确原文和位置。",
            },
            {
                "role": "user",
                "content": text,
            },
        ],
        format=SCHEMA,
        options={"temperature": 0, "seed": 37},
        stream=False,
    )

    # Ollama 返回的 content 是 JSON 字符串，不是已经解析好的 dict。
    parsed = json.loads(response["message"]["content"])
    return parsed["findings"]


# ------------------------------------------------------------
# 4. 替换：先处理右边，避免左侧替换改变后续下标
# ------------------------------------------------------------

def redact(text, findings):
    result = text

    for item in sorted(
        findings,
        key=lambda x: x["start"],
        reverse=True,
    ):
        start = item["start"]
        end = item["end"]
        label = item["type"].upper()

        result = (
            result[:start]
            + f"[REDACTED_{label}]"
            + result[end:]
        )

    return result


# ------------------------------------------------------------
# 5. Hybrid：官方当前是 Regex 真正替换后，LLM 再看剩余文本
# ------------------------------------------------------------

def run_hybrid(client, original_text):
    regex_hits = run_regex(original_text)
    regex_redacted_text = redact(original_text, regex_hits)

    # LLM 看不到已经被 Regex 替换掉的原文。
    llm_remaining_hits = run_llm(client, regex_redacted_text)

    # 官方代码还会把这些值重新映射回 original_text 的位置。
    mapped_hits = map_back_to_original(
        original_text,
        llm_remaining_hits,
    )

    return regex_hits + mapped_hits


# ------------------------------------------------------------
# 6. 判卷：把预测值与人工 Gold 比较
# ------------------------------------------------------------

def evaluate(case, findings):
    gold_values = {value for _, value in case["gold"]}
    pred_values = {item["value"] for item in findings}

    true_positive = gold_values & pred_values

    precision = (
        len(true_positive) / len(pred_values)
        if pred_values else 0
    )

    recall = (
        len(true_positive) / len(gold_values)
        if gold_values else 1
    )

    redacted_text = redact(case["text"], findings)
    residual_leaks = [
        value for value in gold_values
        if value in redacted_text
    ]

    return {
        "precision": precision,
        "recall": recall,
        "residual_leaks": residual_leaks,
        "sanitized_text": redacted_text,
    }


# ------------------------------------------------------------
# 7. 主循环：同一案例跑三条链路，再分别判卷
# ------------------------------------------------------------

client = ollama.Client()

for case in CASES:
    regex_hits = run_regex(case["text"])
    llm_hits = run_llm(client, case["text"])
    hybrid_hits = run_hybrid(client, case["text"])

    print("Regex:", evaluate(case, regex_hits))
    print("LLM:", evaluate(case, llm_hits))
    print("Hybrid:", evaluate(case, hybrid_hits))
```

看完这段后，最应该形成的不是逐行背诵，而是这个骨架：

```text
准备输入和 Gold
  → 运行三个检测器
  → 检测器只返回 findings
  → 确定性代码执行 redact
  → 与 Gold 比较
  → 聚合指标
```

## 十三、当前代码最值得留意的边界

1. `main.py` 与 `campaign.py` 是两套入口，不要混读。
2. `agent.py` 名叫 Agent，但没有规划—工具—观察循环。
3. JSON Schema 约束格式，不保证语义正确。
4. Regex 的 `confidence=1.0` 只是代码硬编码，不代表它在语义上绝对正确。
5. 当前 Hybrid 可以补 Regex 漏报，却不能恢复 Regex 误删。
6. `text.find(value)` 遇到同值多次出现时可能映射到错误位置。
7. `agent.py` 的 token 数只是 `字符数 // 4` 的粗略估计，不是模型真实 tokenizer 结果。
8. `agent.py` 有 OpenRouter 回退；严格的 `campaign.py` 没有，后者才能保证被测模型确实是本地 Qwen3。
9. Regex 密码规则对中文标点边界处理不完整，刚才已经实测会吞掉后续内容。
10. 这个实验的核心是“检测 + 可执行定位 + 替换 + 判卷”，不是让 LLM 直接输出一份改写后的日志。
