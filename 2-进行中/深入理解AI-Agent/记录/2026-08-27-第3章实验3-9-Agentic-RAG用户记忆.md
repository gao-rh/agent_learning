# 2026-08-27 第 3 章实验 3-9：用 Agentic RAG 检索用户对话记忆

## 原始问题

> 进入下一个吧

## 用户理解

- 用户确认实验 3-8 按最终总结收口并进入实验 3-9。
- 用户的首次预测：“容易漏车，如果一次检索没有返回两辆车信息就容易漏。”
- 这个预测准确指出了 Agentic RAG 的“桥接线索”依赖：后续查询可以深挖已发现的实体，但不会自动知道首轮完全没出现的第二辆车。

## Codex 反馈

### 1. 实验要解决的问题

实验 3-9 把 3-8 的 Agentic RAG 从共享法律知识库迁移到用户个人记忆：不再搜索法条，而是搜索用户过去的原始对话。

它与实验 3-1/3-2 的区别：

- 3-1/3-2 在每段会话后用 LLM 提取并改写长期记忆，旧原文不再提供给下一轮记忆写入器。
- 3-9 不先把对话压缩成 Notes 或 Cards，而是把原始历史对话按固定窗口切成 chunk，建立检索索引；新会话中的 Agent 需要时调用 `search_user_memory` 找回相关原文。

### 2. 代表案例：两辆车的保养状态

历史对话包含两辆车和两个业务会话：

1. 保险会话确认用户拥有 `2019 Honda Accord` 和新增的 `2023 Tesla Model 3`，两辆车同时保留。
2. 保养会话中，用户为 Honda 预约 Firestone 的 30K 保养：11 月 24 日周五 8:00，折后 369.99 美元，确认号 `FS-447291`。
3. 同一保养会话也讨论了 Tesla 的轮胎换位，但用户最后说先只处理 Honda，因此 Tesla 没有真正预约。

新问题翻译为：

> “我需要给我的车预约保养。你能告诉我现在已经预约了哪些服务吗？”

合格答案必须同时说明：用户有两辆车；Honda 已预约及其关键信息；Tesla 只讨论过但未预约；最后追问用户这次指哪辆车。

### 3. 数据如何进入检索库

```text
多个历史会话的原始消息
  -> 每 20 轮切一个固定窗口（离线演示；窗口之间可重叠）
  -> 每个窗口成为一个 memory chunk
  -> 对 chunk 建 BM25 索引
  -> 当前问题触发 search_user_memory
  -> 取回相关原始对话块
  -> LLM 根据证据回答
```

历史完整 campaign 使用每块 8 轮、重叠 2 轮、每次 `Top-K=4`，与离线演示的默认 20 轮、`Top-K=3` 不同，不能混用数字。

### 4. 两种“Agentic”实现必须区分

- `offline_demo.py` 不调用 LLM。它从首轮结果用正则抽取车辆实体，再写死查询模板 `<车辆> service appointment scheduled`，属于确定性规则模拟。
- 完整 campaign 才由 LLM 现场调用 `search_user_memory` 并决定是否补搜，属于真实 ReAct Agent。

### 5. 预审发现的历史问题

离线演示以 `FS-447291` 和 `Model 3` 两个字符串作为决定性证据标记，报告单次检索 50%、规则多轮检索 100%。但“出现 Model 3”不等于“证明 Tesla 未预约”，因此指标只验证实体出现，没有完整验证状态绑定。

历史真实 LLM campaign 在同一案例中只生成一次查询 `scheduled car services`，随后立即 `SEARCH_COMPLETE`。最终答案只报告 Honda 预约，遗漏 Tesla 和消歧追问；Judge 的文字理由明确指出该遗漏，却仍给 precision/recall/reasoning 各 3 分并判定通过。这说明历史 Layer 2 `75%` 通过率存在宽松 Judge 风险，不能直接当作真实能力结论。

### 6. 2026-08-27 本机实际运行：官方默认 `Top-K=3`

参数：每块 20 轮，重叠 2 轮，共 2 个会话、6 个记忆块，本地 BM25，无 LLM。

原问题单次检索的 Top-3：

| 排名 | 得分 | 记忆块 | 实际包含的核心证据 |
|---|---:|---|---|
| 1 | 5.516776 | `auto_service_001#1-20` | Honda 30K 保养、11 月 24 日周五 8:00 |
| 2 | 4.752828 | `auto_insurance_001#1-20` | Honda + Tesla 两辆车同时存在 |
| 3 | 4.038630 | `auto_service_001#19-38` | Tesla 轮胎换位被讨论，但用户最终只保留 Honda；Honda 折后 369.99 美元 |

因此，这次实际的单次 Top-3 并没有“漏车”，也没漏掉“Tesla 最终未预约”。它缺的是位于最后一块的 Honda 确认号 `FS-447291`。

规则版 Agentic 检索从首轮结果中抽取出 `Honda`、`Tesla`、`Honda Accord`、`Tesla Model`，又发出 4 个模板查询，新增找回 `auto_service_001#37-47`，其中包含最终确认时间和 `FS-447291`。脚本因而报告标记覆盖率从 50% 到 100%。

但这个“50% 到 100%”不等于“从不能消歧到能消歧”：它的两个 Gold Marker 只是 `FS-447291` 和 `Model 3`，没有单独检查“Tesla 最终未预约”。而单次 Top-3 实际已找回了这个关键状态。更准确的本轮结论是：**多轮查询补回了 Honda 确认号；这个默认单例没有证明只有 Agentic RAG 才能完成双车消歧。**

### 7. 边界对照：只改成 `Top-K=1`

这不是书中默认结果，而是专门验证用户预测的小型消融：

- 首轮只返回 `auto_service_001#1-20`，只出现 Honda。
- 规则只能抽取 `Honda` 和 `Honda Accord`，后续也只会追查 Honda。
- 多轮检索成功补回 Honda 确认号，但 Tesla 仍然完全缺失。
- 标记召回率：单次 0%，规则多轮 50%；两者都不能完整消歧。

这验证了用户的机制判断：**Agentic 检索并非凭空知道缺什么，它需要首轮召回提供“还有另一辆车”的桥接线索。**

同时发现一个展示层 bug：`Top-K=1` 的表格明确显示 Tesla 未召回、无法完整消歧，但脚本底部仍打印“最终把两辆车的服务状态都取回”。这是一段未根据实际结果分支的固定文案，不能当作实验证据。

## 发散联想

- 3-9 展示了另一种长期记忆路线：保留原始事件记录并按需检索，而不是只保留会话后的抽象摘要。
- “没有预约”“后来取消”“旧指令已被替换”属于负面或状态变化事实，比检索一个明确编号更难；只召回实体名不足以回答状态问题。
- 生产系统可以同时保留原始轨迹索引和结构化长期记忆：前者提供证据与追溯，后者提供低延迟状态读取。

## 阶段总结

### 一句话结论

实验 3-9 想表明：对用户原始对话做记忆检索时，Agent 可以根据首轮线索继续补搜，但它不能凭空发现首轮完全没有暴露的实体或事实。

### 实验链路

```text
原始历史对话
  -> 按固定轮数切成 chunk
  -> 建立 BM25 索引
  -> 当前问题发起首轮检索
  -> 从召回块中发现车辆实体
  -> 对已发现的车辆补充查询
  -> 合并证据后回答
```

### 实际观察

- 默认 `Top-K=3`：单次检索已召回 Honda、Tesla 以及“Tesla 最终未预约”；规则多轮检索主要补回 Honda 确认号。
- 只改成 `Top-K=1`：首轮只看到 Honda，后续也只会追查 Honda，Tesla 始终丢失。
- 因此，多轮检索的效果受制于首轮召回的“桥接线索”，不是只要加了 Agent 就一定能补全。

### 评测上的问题

- 脚本用 `Model 3` 和 `FS-447291` 两个字符串充当 Gold Marker，不能完整检查“Tesla 最终没有预约”这种状态关系。
- 默认实验的 50% -> 100% 主要表示两个字符串是否出现，不足以证明答案从“无法消歧”变成“能完整消歧”。
- `Top-K=1` 时表格显示 Tesla 未召回，但脚本仍打印成功文案；展示文案不是实验证据。
- 历史真实 LLM 运行还出现“答案漏掉 Tesla，Judge 却判通过”，说明评测器也需要单独验证。

### 真正需要掌握的四点

1. **Agentic RAG 是迭代补证，不是魔法补全。**它的后续行动依赖已看到的线索。
2. **分块、`Top-K` 和查询改写共同决定召回。**不能只把结果归因于模型能力。
3. **实体出现不等于状态正确。**长期记忆要区分“讨论过”“已预约”“取消了”和“被新决定覆盖”。
4. **评测必须拆层。**分别检查候选证据是否召回、模型是否正确使用证据、Judge 是否正确判分。

## Top-K 实践补充

### 原始问题

> 现在市场上通常的是 Top 多少，是不是都保留几十个？

### 核心纠正

必须区分三个数：

1. `candidate_k`：BM25/向量/混合检索首先召回的候选数。
2. `rerank_top_n`：重排后保留的高质量候选数。
3. `context_k`：最终真正放进 LLM 上下文的 chunk 数。

市场上没有一个统一的 Top-K，但可以用下列范围作为起始配置，然后用自己的评测集调整：

| 阶段 | 常用起始范围 | 含义 |
|---|---:|---|
| 无重排的简单 RAG | 3–8 | 召回结果直接进入 LLM，数量不宜过大 |
| 有重排的首轮候选 `candidate_k` | 20–50 | 先保召回，允许保留几十个 |
| 难题、混合检索或多路融合候选 | 50–150 | 成本和延迟更高，需要重排和去重 |
| 重排后 `rerank_top_n` | 5–20 | 压缩为更相关的证据集 |
| 最终进入 LLM 的 `context_k` | 常见 3–10；复杂多跳可到 10–20 | 受 chunk 长度、上下文窗口、噪声、延迟和费用限制 |

这些是基于当前官方产品默认值和官方工程示例归纳的起始范围，不是严格的市场占比统计。例如：Azure 语义重排处理首轮 Top 50；Anthropic 的 Contextual Retrieval 实验用 150 个初候选重排为 20 个上下文块；AWS Bedrock Knowledge Bases 默认最多返回 5 个块；Pinecone 的混合检索示例将 52 个去重候选重排为 10 个。

对用户记忆场景，可以从“初召回 10–30，重排后进上下文 3–8”开始；Agentic 多轮检索则可每轮取 3–5 个，跨轮去重后再总体控制上下文数量。这只是起点，必须同时画召回率、答案正确率、Token、延迟和成本曲线。
