# AI 训练数据岗位能力项总表

> 版本：2026-09-03 调研稿。能力优先级与学习顺序尚未由用户确认，因此不是正式学习计划；“准备了环境、写出了代码”也不等于“已理解”。

## 核心结论

这类岗位的本质，不是传统 ETL 换一个 AI 名字，也不只是组织人工标注，而是：

> 把原始、多源、多模态数据稳定地加工成可训练、可追踪的数据资产，再通过训练与评测证明某个数据版本确实改善了模型能力。

完整能力由三条主线交叉组成：

1. **数据工程**：大规模 Pipeline、分布式处理、稳定性、版本和治理。
2. **数据算法与模型**：清洗、去重、质量建模、标注、合成，以及必要的模型训练能力。
3. **评测闭环**：从模型短板定位专项数据，用可复现的对照实验量化数据贡献。

对当前转型而言，最短路径不是从零改做纯算法研究，也不是先学完所有 Agent 框架，而是：

> 复用已有的数据工程与多模态模型经验，补齐现代 LLM/VLM 训练数据方法和“数据—训练—评测”闭环，再把 Agent 引入数据生产流程。

## 样本与统计边界

- 本次共归档 **30 个去重岗位族、32 份独立 JD 正文**，详情见[岗位总目录](岗位JD/岗位目录.md)。
- 其中 27 个岗位族为 A 级官方证据，3 个为 C 级镜像证据；C 级样本可帮助理解能力要求，但不能当作当前有效 HC。
- 上海 AI 实验室的网页、文档与 PDF、代码三个独立 JD 在市场数量中合为一个岗位族，但能力编码保留三份正文。
- 下表以 32 份独立 JD 为分母，使用关键词交叉检查并结合人工语义编码；同一 JD 内重复出现只计一次。
- 频次只用于区分共同底座与岗位专项，不代表整个招聘市场的精确占比，也不代表低频能力没有价值。

## 市场能力信号

| 能力信号 | 命中 JD | 应如何理解 |
| --- | ---: | --- |
| 数据质量、评分或质检 | 30/32 | 赛道最稳定的共同目标，必须能定义、测量并改进质量 |
| LLM / 大模型 | 28/32 | 需要理解训练阶段与数据需求，不要求人人研究模型结构创新 |
| 数据 Pipeline / 生产链路 | 25/32 | 岗位不是一次性脚本，强调持续、自动化的数据生产系统 |
| 清洗与过滤 | 24/32 | 规则、统计、模型共同参与，且需要分析误杀与漏放 |
| 模型评测或数据验证 | 24/32 | 数据是否有价值最终要由模型能力或可靠代理指标证明 |
| 分布式或大规模处理 | 23/32 | 需要理解分区、Shuffle、IO、资源、吞吐和容错 |
| Python | 25/32 | 最稳定的编程语言；“会写脚本”不足以覆盖工程要求 |
| VLM / 多模态 | 21/32 | 多数 JD 写“多模态”而不是 VLM 缩写，不能按字面低估 |
| 稳定性、恢复与可复现 | 19/32 | 生产链路必须可重跑、可诊断、可恢复 |
| 治理、资产或权限 | 19/32 | 数据来源、版本、处理记录、授权边界都属于交付物 |
| 预训练 | 18/32 | 是最常见训练阶段，但不少在架岗位也覆盖后训练 |
| 采集与寻源 | 18/32 | 不只是爬虫，还包括数据源策略、授权、覆盖与成本 |
| 解析、去重、标注 | 各 15/32 | 都是训练数据生命周期中的核心算子 |
| 合成、增强或改写 | 14/32 | 已从加分项逐渐进入主流程，但必须有质量控制 |
| Spark | 16/32 | 当前样本中最稳定的分布式框架，可作为第一主框架 |
| 可观测、监控或告警 | 14/32 | 需要看到数据分布、质量、吞吐、成本和异常变化 |
| 数据闭环或飞轮 | 14/32 | 核心区分点是能否从评测反推数据动作 |
| 数据版本、血缘或可追踪 | 11/32 | 文字频次不算最高，但它是可复现对照实验的前提 |
| PyTorch 或深度学习训练 | 11/32 | 不一定要求训练基础模型，但要能跑通小模型、scorer 或微调 |
| Ray | 13/32 | 值得作为第二框架，尤其适合 Python 原生和模型推理任务 |
| Agent / 智能体 | 9/32 | 是有前景的专项增强，不是全部训练数据岗位的统一入口门槛 |
| 后训练、SFT 或 RL | 至少 10/32 | 在当前存量岗位中信号较强，不能只懂预训练语料 |
| SQL / SQL 引擎 | 3–6/32 | 只按 SQL、或连同 MySQL/DuckDB 计算会得到不同结果；仍是工程基础，但不是本轮转型主课 |
| Shell / Linux | 2/32 | 作为生产基本功保持可用，不值得单独形成长学习主线 |

## 完整能力图谱

### 1. Python 与软件工程

| 能力项 | 需要学到什么程度 | 可验收证据 | 优先级 |
| --- | --- | --- | --- |
| Python 数据处理 | 熟练处理 JSONL、Parquet、Arrow、图片和流式记录；能写生成器、批处理和并发任务 | 对同一数据集完成可配置、可重复的处理程序 | P0 |
| 工程结构 | 使用模块、类型标注、配置、日志、CLI、依赖锁定和清晰的目录边界 | 不改代码即可切换数据源、规则和输出版本 | P0 |
| 测试 | 为解析、过滤、去重、评分和异常路径写单元测试与小型集成测试 | 核心算子有正常、边界和失败样例 | P0 |
| 异常与恢复 | 理解超时、重试、幂等、断点续跑、坏样本隔离和失败重放 | 人为制造失败后能够从检查点恢复，不重复污染结果 | P0 |
| 性能分析 | 能定位 CPU、内存、网络与磁盘瓶颈，理解批大小、并发和序列化开销 | 提供处理吞吐、资源和优化前后对比 | P1 |
| SQL / Shell / Linux | 能查询分布、抽样、核对结果并完成常规生产诊断 | 用 SQL 复核 Pipeline 指标，用 Shell 完成可重复运行 | 维持项 |

### 2. 数据存储、Pipeline 与分布式处理

| 能力项 | 需要学到什么程度 | 可验收证据 | 优先级 |
| --- | --- | --- | --- |
| 数据 Schema | 设计样本 ID、内容、来源、模态、授权、处理状态、质量分和版本字段 | 一份带字段约束、示例和演进规则的数据契约 | P0 |
| 格式与存储 | 理解 JSONL、Parquet、Arrow、对象存储和分区组织的取舍 | 同一数据比较体积、读取速度和随机访问能力 | P0 |
| 端到端 Pipeline | 打通采集、解析、清洗、去重、评分、抽样、版本发布 | 一条 CLI 或工作流可从原始数据生成可训练版本 | P0 |
| 编排与依赖 | 理解 DAG、任务依赖、重跑边界、缓存、中间产物与 backfill | 某一步失败后只重跑必要节点 | P0 |
| Spark | 能写 DataFrame 作业并解释分区、Shuffle、倾斜、Join、缓存和小文件问题 | 在规模化样本上完成去重或统计任务，并给出执行计划解释 | P0 |
| Ray | 掌握 task、actor、Dataset，以及 CPU/GPU 混合批推理的基本模式 | 把模型评分任务从单机扩展为并行批处理 | P1 |
| Flink / Hadoop / MaxCompute | 理解适用边界；目标岗位明确要求时再加深 | 能说明流处理、离线批处理和托管平台的选择理由 | P2/按岗 |
| 稳定性与可观测 | 记录吞吐、延迟、失败率、数据量、质量分布、成本和告警 | 一张运行报告能定位哪批数据、哪个算子发生异常 | P0 |
| 资源与成本 | 理解小文件、重复计算、模型调用、GPU 空转和存储成本 | 在质量不下降前提下降低一次 Pipeline 的时间或成本 | P1 |

### 3. 训练数据全生命周期

| 环节 | 必须掌握的内容 | 可验收证据 | 优先级 |
| --- | --- | --- | --- |
| 寻源与采集 | 数据源覆盖、代表性、许可、增量策略、失败重试和原始快照保留 | 原始区不可变，能追溯每条数据的来源和采集批次 | P0 |
| 解析与标准化 | 正文抽取、编码、格式恢复、模态元数据、异常文件隔离 | 建立解析成功率及失败类型统计 | P0 |
| 清洗与过滤 | 规则、统计和模型过滤；理解噪声、低信息量、广告、乱码与异常样本 | 每条过滤规则都有命中率、抽样精度、误杀分析 | P0 |
| 精确去重 | 哈希、规范化和跨文件重复识别 | 精确重复可复现删除，并保留簇 ID 与代表样本 | P0 |
| 近似与语义去重 | MinHash/LSH、感知哈希、embedding 相似度，以及阈值取舍 | 报告重复召回、误合并和规模变化 | P0 |
| 抽样与配比 | 数据分层、长尾覆盖、难例、去偏、mixture 和课程式采样 | 两个配比版本有明确假设、分布差异和评测结果 | P1 |
| 标注体系 | 标签定义、正反例、边界例、标注指南、抽检和仲裁 | 指南可让不同标注者稳定处理同一批样本 | P0 |
| 一致性与质检 | Gold set、交叉标注、Kappa/ICC 或任务适配的一致性指标 | 能区分标签问题、指南问题和任务本身的主观性 | P1 |
| 质量建模 | 质量 rubric、规则分、分类器、scorer/ranker、分层阈值 | 质量分能解释，并与人工抽检或模型表现建立联系 | P0 |
| 合成与增强 | LLM 改写、蒸馏、模板、图文生成和难例合成；控制重复、偏差和幻觉 | 合成数据与真实数据分开标识，并经过独立质量与效果验证 | P1 |
| 版本发布 | 数据版本、变更清单、统计摘要、已知限制、回滚和 Dataset Card | 任意模型实验能够还原到精确数据版本 | P0 |

### 4. LLM、VLM 与训练基础

| 能力项 | 需要学到什么程度 | 可验收证据 | 优先级 |
| --- | --- | --- | --- |
| Transformer 与 Tokenization | 理解 token、上下文长度、attention、位置编码和 tokenizer 对数据的影响 | 能分析一批数据的 token 分布、截断和异常编码 | P0 |
| 预训练数据 | 理解语料组成、数据 mixture、采样、污染、重复和规模—质量取舍 | 为一个小型预训练实验设计数据版本与假设 | P0 |
| 后训练数据 | 区分 SFT、Preference、DPO、RLHF/RLAIF/RLVR 的样本结构与质量标准 | 能构造并验证一种 instruction 或 preference 数据格式 | P0 |
| VLM / 多模态基础 | 理解图文对齐、caption、视觉编码器、跨模态表征和模态缺失问题 | 对一批图文对做一致性、质量和难例分析 | P1 |
| PyTorch | 能实现 Dataset/DataLoader、训练循环、损失、优化器、checkpoint 和评测 | 独立训练小模型或完成 LoRA 微调，并解释训练曲线 | P0 |
| Hugging Face 生态 | 能使用 Datasets、Transformers、Tokenizers、PEFT 和常见数据 collator | 从本地版本化数据完成一次可复现微调 | P0 |

| 分布式训练 | 先理解 DDP/FSDP/DeepSpeed 的目的和边界，不以训练大底模为初期目标 | 能解释何时需要数据并行、参数分片或模型并行 | P2 |

### 5. 评测、实验与数据飞轮

| 污染与泄漏 | 识别训练—测试重复、近似污染和答案泄漏 | 对训练集和评测集执行可解释的污染检查 | P0 |

| Proxy 与离线指标 | 理解代理指标与最终模型能力可能不一致 | 验证质量分、人工偏好或小模型结果与目标评测的相关性 | P1 |

## 学习优先级

### P0：先形成可投递的共同底座

P0 不是“看过”，而是要在一个完整项目中同时证明：

1. Python 工程化与测试。
2. 原始数据到训练数据的端到端 Pipeline。
3. 清洗、精确去重、近似去重、质量 rubric 和抽样质检。
4. Spark 的规模化处理；理解 Ray 的用途与基本模型。
5. Parquet/Arrow、Schema、数据版本和来源追踪。
6. LLM/VLM 的预训练与后训练数据基础。
7. PyTorch + Hugging Face 的小模型训练或 LoRA 微调。
8. 独立评测、污染检查、Badcase 和 v0/v1 对照实验。
9. Pipeline 的失败恢复、日志、质量指标和可复现运行。
10. 一轮“数据—训练—评测—数据”闭环。

### P1：让项目从合格变成有竞争力

1. Ray 批推理和模型评分。
2. 自动标注、scorer/ranker 与 Model-as-Judge 校准。
3. 数据合成、改写、蒸馏和难例生成。
4. 图像 + 文本多模态质量与对齐。
5. 数据配比、控制变量、贡献量化和代理指标验证。
6. 数据资产目录、成本优化、隐私、版权和生命周期。
7. 用 LLM/VLM/Agent 编排数据生产，但保留代码准入和失败回退。

### P2：只按目标岗位选择一条专项

## 难点与时间估计

### 真正的难点

1. **从“把数据处理完”升级到“证明数据改变了模型”**：这是传统数据工程与训练数据工程的最大分界。
2. **质量没有统一真值**：需要把业务目标转成 rubric、抽样方案、错误分类和可校准指标。
3. **控制变量很难**：模型、训练参数、数据规模和评测集同时变化时，不能归因于某个数据动作。
4. **多模态错误更隐蔽**：图像本身清晰不代表图文一致，caption 正确也不代表覆盖目标能力。
5. **大规模可靠性**：小脚本有效不代表亿级数据下仍可恢复、可追踪、可控成本。
6. **Agent 专项的可执行性**：轨迹必须能回放，环境必须能复现，结果必须能自动验证。

### 以当前背景估算

假设每周投入 12–15 小时，并且历史项目证据能够部分恢复：

| 目标 | 估计投入 | 完成边界 |
| --- | ---: | --- |
| 恢复旧项目并完成能力缺口诊断 | 3–5 天 | 能明确哪些已有、哪些确实需重学 |
| 补齐 P0 并做出一个最小闭环项目 | 8–10 周 | 能讲清 Pipeline、质量、训练、评测和版本 |
| 加入 P1 多模态、合成、Ray 与 AI Native 能力 | 再 4–6 周 | 项目与目标 JD 有明显贴合，而非通用 Demo |
| 深入一个 P2 专项 | 再 4–8 周 | 能通过专项岗位的深入追问与项目审查 |

因此，目标不是先学习半年再投递。更现实的边界是：**约 10–14 周形成可面试的核心证据，同时继续投递；5–7 个月形成更扎实的训练数据竞争力。** 时间会受算力、可用公开数据、旧项目可恢复程度和每周投入影响。

## 第一个学习模块的验收定义

建议从“训练数据 Pipeline 的最小闭环”开始，而不是从零散概念或框架 API 开始。

目标产物是一条小而完整的链路：

```text
原始图文数据
  → Schema 与不可变原始快照
  → 解析和清洗
  → 精确 / 近似去重
  → 质量评分与抽样质检
  → 数据集 v0 / v1
  → 小模型训练或 LoRA 微调
  → 独立评测与 Badcase
  → Dataset Card 与数据变更结论
```

只有同时满足以下条件，才算完成：

- 能解释每个数据算子的目标、误杀、漏放和适用边界。
- 原始数据不被覆盖，任一处理结果能追溯来源、代码、参数和版本。
- Pipeline 可重复运行，失败可恢复，核心算子有测试。
- 固定模型与训练参数，只改变数据版本。
- v0/v1 不只比较数据条数，还比较模型能力、退化项和 Badcase。
- 最终结论明确回答“哪类数据变化改善了什么能力”，并说明不能证明的部分。

这会成为后续多模态、合成、Ray 和 Agent 数据生产的共同底座。
