> 本次只讨论智能经营分析 Agent 的记忆模块和知识库模块。先完整记录真实实现，再区分已完成能力、实现细节、问题边界和后续建设；暂不写简历或面试答案。

## 本次范围

1. 记忆模块：目标、存储内容、读写链路、冲突处理、实际效果和后续改进。
2. 知识库模块：知识类型、加工、检索、使用方式、可靠性和后续改进。

## 记忆模块

### 用户原始口述

> 记忆模块我们的设计是有用户信息、用户偏好，然后就是为了多会话的连续性、历史分析经验的复用、冲突记忆的选择正确，主要是解决这些信息。你看要不要补充。现在更多的是去准备我做完的和接下来继续做的，上面肯定都已经做了。

### 2026-08-22 用户补充的真实实现

以下内容由用户补充确认，属于原项目事实；其中尚未说清的字段和数据库、Wiki 分工继续标为待核对。

#### 用户记忆的组成

- 用户长期记忆；
- 会话摘要；
- 会话详情；
- 分析经验，其中分析经验属于用户长期记忆，而不是与用户长期记忆平级的独立域。

这些记忆以用户为作用域，并按 Task/专题组织。每个 Task 下存在完整的 `Memory` 和压缩后的 `Memory Summary`。Task 记录用户围绕某个专题做过哪些事情、当前进行到什么程度，并关联该专题下的历史分析经验。

#### 两条写入链路

1. **会话内主动写入**：用户明确要求保存，或者 AI 判断某项内容值得长期保留时，Agent 调用工具写入长期记忆。
2. **闲时批量整理**：系统在闲时拉取活跃用户的完整对话记录，再由 AI 抽取和整理需要保存的用户信息、用户偏好、跨会话任务状态和历史分析经验。

#### 当前已确认的存储位置

- 数据库；
- Wiki。

数据库和 Wiki 分别承载哪些对象、哪一侧是权威事实源、是否存在双向写入或同步，尚待用户补充。

#### 保存内容

| 内容 | 已确认示例 | 主要组织方式 |
| --- | --- | --- |
| 用户关键信息 | 与用户后续取数、分析相关的关键信息 | 用户长期记忆 |
| 用户偏好 | 数据呈现偏好、可视化偏好、分析方向偏好 | 用户长期记忆 |
| 多会话连续性 | 用户按 Task 做了什么、已完成什么、当前进行到什么程度 | Task/专题 |
| 历史分析经验 | 分析过什么主题、使用了什么数据、生成了什么可视化、报告链接、实际效果 | 长期记忆中的 Task 经验 |

这里的“会话详情”是完整过程证据，“会话摘要”是压缩后的会话级信息；它们与 Task 下的 `Memory`、`Memory Summary` 的准确对应关系尚待补充。

### 已完成能力

以下五项由用户明确确认为已经实现，不是 Codex 建议：

| 已完成能力 | 当前能够确认的目标 | 实现细节状态 |
| --- | --- | --- |
| 用户信息 | 让 Agent 了解当前用户的基础信息 | 保存字段、来源和更新方式待补充 |
| 用户偏好 | 让 Agent 按用户习惯提供查询或分析 | 偏好类型、学习方式和覆盖规则待补充 |
| 多会话连续性 | 新会话能够延续此前交流和分析上下文 | 保存粒度、召回条件和续接方式待补充 |
| 历史分析经验复用 | 后续问题可以复用过去有效的分析经验 | 经验对象、用户私有/团队共享范围待补充 |
| 冲突记忆选择 | 多条记忆冲突时选择正确、适用的内容 | 冲突判定、排序和时效机制待补充 |

### 当前可以形成的目标层

```text
用户是谁
  + 用户通常怎样查数和分析
  + 上一次或历史会话做到了哪里
  + 过去哪些分析路径有效
  + 多条历史信息冲突时当前应采用哪一条
→ 为本轮 Agent 编排提供个性化、连续且可复用的上下文
```

这说明该模块并非简单保存聊天记录，而是在解决四类问题：个性化、跨会话状态、经验复用和冲突治理。

### 建议补充梳理的机制维度

以下是 Codex 为完整项目复盘提出的追问维度，不代表项目尚未实现，也不代表后续必须全部建设：

| 机制维度 | 需要回答的问题 | 面试官为什么会关注 |
| --- | --- | --- |
| 记忆对象 | 用户信息、偏好、任务状态、分析经验分别以什么结构保存 | 判断是否只是聊天摘要，还是可治理的数据对象 |
| 作用域 | 记忆属于单用户、单会话、单业务角色、团队还是全局 | 判断隔离、复用和数据泄漏风险 |
| 写入 | 谁提取记忆，什么时候写，是否需要用户确认 | 判断记忆污染和错误写入风险 |
| 检索 | 根据什么查询记忆，召回多少，怎样排序 | 判断记忆是否真正参与 Agent 决策 |
| 注入 | 记忆以原文、摘要、结构化字段还是工具结果进入上下文 | 判断 Token 成本和模型可控性 |
| 冲突 | 新旧记忆、用户明确表达与历史推断冲突时如何处理 | 对应用户已实现的“冲突记忆选择正确” |
| 时效 | 是否有时间戳、版本、有效期和过期策略 | 经营分析偏好、负责业务和口径都会变化 |
| 更新删除 | 如何纠正错误记忆，能否删除或覆盖 | 判断是否具备可维护性和用户控制 |
| 权限隐私 | 不同用户能否读到彼此信息，团队经验怎样脱敏共享 | 企业场景的基本安全边界 |
| 评估 | 怎样知道召回的记忆有帮助、没有误导当前任务 | 判断模块效果是否可度量 |

### 可能还应纳入的业务问题

在用户已确认的五项之外，以下内容值得核对是否已经存在于实现中：

1. **未完成任务续接**：不仅记住历史聊天，还能知道某次分析做到哪一步、用了哪些指标、下一步是什么。
2. **用户纠错与反馈复用**：用户纠正过指标、维度或分析习惯后，后续是否能避免重复犯错。
3. **默认参数复用**：常用业务范围、时间口径、维度和报告格式是否可作为默认值，同时允许本轮覆盖。
4. **分析证据复用**：复用过去分析经验时，是否同时保留当时的数据周期、指标和结论适用条件，避免把旧结论当成当前事实。
5. **可解释召回**：Agent 能否说明本轮使用了哪条历史记忆，以及为什么选择它而不是冲突项。

这些是待核对项，不能写成已完成能力。

### 记忆与知识库的初步边界

| 内容 | 更倾向记忆 | 更倾向知识库 | 当前待确认点 |
| --- | --- | --- | --- |
| 某用户负责哪个业务 | 是 | 否 | 是否有组织系统作为权威来源 |
| 某用户习惯看的指标和维度 | 是 | 否 | 是显式设置还是行为推断 |
| 某次对话已经澄清的参数 | 是 | 否 | 保存多久、是否跨会话 |
| 某用户过去采用的分析路径 | 是 | 可能 | 只给本人复用还是会沉淀成团队经验 |
| 经过审核的通用分析方法 | 否 | 是 | 是否以 Skill 或知识对象保存 |
| 指标定义、业务事件、权威口径 | 否 | 是 | 与指标库、业务知识库怎样分层 |

最需要追清的是“历史分析经验复用”：如果只复用某个用户自己的历史路径，它属于记忆；如果被抽象、审核后供所有用户使用，它更接近知识库或 Skill。两者的可信等级和更新流程不应相同。

### 待讨论主线

## 当前优先追问

先从记忆的完整读写链路开始：一次对话中的信息怎样被判断为值得记忆、以什么结构写入；下一次会话又怎样检索、排序并注入 Agent。冲突选择是这条链路中的关键分支。
