## 原始口述

### 本轮原始口述

> 首先呢，Token 消耗量这件事情每天在 8000 万左右。然后其实这个东西也是有部分用户用的特别多，然后有些用户用的不多，然后有些用户也用的特别好，有些用户也很夸张。
>
> 例如，我们之前出现过一个场景，就是一个新来的，他不太懂指标名字，然后用一些错误的术语，导致 Agent 找到了错误的指标，然后用错误的指标去做了一个分析报告。然后这个新来的员工呢，还拿这个分析报告去大领导那汇报了。然后那个大领导就找过来说我们的这个 Agent 的分析报告不行。当然，中层他们是知道的，就是一些老员工他们一眼就能看出来这个东西算错了，但是新员工不具备这个判断能力，还拿这个去大领导汇报了。这就是我们的一个苦恼的问题。
>
> 然后我们的这个 Agent 呢，它是分为几个时期的。第一个时期我们核心是想把它做成一个好的智能取数工具，目标就一个，数据算得准，并且不瞎扯。这一部分我们的核心做的事情呢，就是把所有的事情尽可能地用代码去表达，并且有澄清、实施、验证三个步骤。
>
> 澄清这一部分就是我们到最后一定要让用户选择我们指定的一些指标库里面的指标名，就是不会让他随便编名字，这个很重要，不能用近义词代替。我们有很多谐音的指标名，包括用户很多都没有说清楚。例如他要看一下同期的叉叉情况，他压根都没有说指标，甚至没有说基期是哪一期、同期又比的是哪一期，就是哪一期比哪一期，这一块我们都会让他做一个确认。初步的判断呢，我们是有一个大概的规范和逻辑，然后从记忆里面也会提。
>
> 第二阶段呢，我们就是在做分析。分析这块核心就是让商分总结分析思路。其实也不仅仅是商分，就是商分、运营加我们一起来思考这个运营思路，然后由我来把它做成 Skill。我们最终的形式是 Skill，因为 Skill 就够用了，搭工作流还挺麻烦的，相对而言还更麻烦一点。而且说实话 Skill 够用了。我们去年全是工作流，我们去年搭了两三个工作流，跑得还行，但是搭得很麻烦。
>
> 然后第三阶段呢，就是最后一阶段。刚才说的那个用户随便分析了，他没有命中我们任何的一个分析思路，他是按他自己的想法去让它做了一个分析，然后就拿着给汇报去了。第三阶段也是这样，我们就希望它能做一个智能分析，就是参考我们的分析方法，自己去按用户制定的一些诉求去做一些分析。
>
> 然后这一阶段呢，我们的核心命题其实是准。我们的指标计算已经非常非常准，意图识别不是特别准，但能满足用户的需求，就是一次说不准，它会澄清，然后再跟他继续说。这个其实业务反馈也不多，其实也还好。核心就是它脱离了——我们允许它去做一些自由的分析的时候，它容易命中不到。命中不到我们的库呢，它就查不成功。查不成功，AI 就会自己去整活。整活就很容易整一些错的出来。

## 项目复盘整理

### 1. 三阶段演进不是功能堆叠，而是逐步放开模型自由度

| 阶段 | 主要任务 | 确定性来源 | 模型自由度 | 主要风险 |
| --- | --- | --- | --- | --- |
| 第一阶段：智能取数 | 把用户问题转换成可信指标结果 | 标准指标库、代码、澄清、规则校验 | 低 | 指标或时间条件理解错误 |
| 第二阶段：固定分析 | 复用成熟的业务分析方法 | 商分/运营经验沉淀的 Skill | 中 | 分析方法覆盖不足或规则维护成本上升 |
| 第三阶段：开放分析 | 应对未预先定义的临时问题 | Agent 参考已有方法自主组合 | 高 | 未命中受控能力后仍生成貌似合理的错误报告 |

目前最有价值的项目判断是：第一、第二阶段依靠收紧自由度获得了稳定性；第三阶段为了提高问题覆盖面放开自由度后，可靠性边界没有同步收紧。

### 2. 新员工事故不是单一的“意图识别不准”

这条失败链路至少包含四层问题：

1. **业务目标与指标未对齐**：用户要分析 A 事件，却使用了真实存在但不适用于该事件的 B 指标。
2. **合法性检查替代了适用性检查**：指标名可以正常匹配，指标也可以成功查询，因此现有指标库和执行链路没有阻断。
3. **开放分析失败后继续生成**：没有命中受控分析方法或查询资产时，系统没有停止或降级。
4. **结果缺少可见的可信边界**：报告足够完整、像真的，但新员工无法从结果中看出指标选择、证据来源或低置信度。

因此，这个问题不能只靠“继续提高意图识别准确率”解决。即使整体意图识别率很高，只要在高影响报告上允许错误指标静默通过，仍然会发生同类事故。

### 3. 用户能力越弱，系统越不能把最终校验责任留给用户

老员工能识别错误，不代表 Agent 的结果可靠。相反，新员工正是更依赖 Agent 的用户，也是最缺少业务判断能力的用户。若产品只依靠用户自己发现错误，实际上会让风险集中在最需要帮助的人身上。

从系统设计上看，第三阶段缺少的可能不是更多分析方法，而是“未覆盖时如何安全失败”的明确机制，例如：

- 未确认标准指标，不进入正式计算和分析；
- 未命中已有分析方法时，明确标记为探索性分析；
- 关键结论必须展示指标口径、数据来源和分析步骤；
- 查询失败或证据不足时停止生成，不允许用语言补齐数据；
- 用于向上汇报的报告增加人工复核或发布确认门槛。

这些是 Codex 根据本轮事故做出的设计推论，尚不代表项目已经实现。

### 4. “澄清—实施—验证”可以成为项目的核心架构主线

当前口述已经能形成一条较强的技术表达：

```text
自然语言诉求
  → 根据规范和记忆形成候选理解
  → 让用户确认标准指标、基期、对比期和分析范围
  → 通过代码或受控工具执行
  → 对结果做数据与业务规则校验
  → 输出结果、口径和可信边界
```

这里仍需继续厘清：“实施”阶段具体调用哪些工具，“验证”阶段有哪些规则，以及验证失败后是重试、重新澄清、降级还是直接拒答。

### 5. Skill 与 Workflow 的取舍需要进一步讲清机制

目前可以确认的是：团队实践中，两三个 Workflow 能运行但搭建麻烦，最终发现 Skill 足以承载分析方法。还不能直接得出“Skill 一定优于 Workflow”。后续需要补充：

- Skill 中具体保存的是分析步骤、选择条件、工具说明，还是 Prompt；
- Skill 是否由 Agent 动态选择和组合；
- Workflow 麻烦在编排、状态传递、修改、调试还是平台操作；
- 哪些强约束步骤仍然不能只依靠 Skill。

### 6. Token 规模暂时只能证明系统调用量较大

“每天约 8000 万 Token”是重要规模信息，但单独不能证明用户价值或系统效果。后续至少需要区分输入/输出 Token、定时任务/人工对话、不同模型以及统计周期，才能用于解释成本、使用强度或优化空间。

## 问题与方案索引

### 当前已经识别的核心问题—解法链

| 项目问题 | 已采用的方案 | 当前效果 | 尚未解决的边界 |
| --- | --- | --- | --- |
| 用户指标表达模糊、近义或错误 | 标准指标库选择；确认指标、基期和对比期 | 受控指标计算很准 | 非标准术语仍可能被错误映射 |
| 大模型在确定性计算中容易自由发挥 | 尽可能代码化；使用澄清、实施、验证三步链路 | 智能取数成为稳定底座 | 具体失败处理机制待补充 |
| 业务分析经验难复用 | 商分、运营、技术共同总结，再由用户制作成 Skill | Skill 足以支持多类成熟分析 | Skill 覆盖范围和选择机制待补充 |
| Workflow 建设维护成本较高 | 从 Workflow 转向更轻量的 Skill | 用户认为效果够用、维护更简单 | 哪些场景仍需 Workflow 待说明 |
| 长尾分析需求无法预定义 | 允许 Agent 参考已有方法进行开放式分析 | 扩大了问题覆盖范围 | 未命中时会自由生成错误内容 |
| 新员工无法识别错误报告 | 当前未形成已确认解法 | 暴露了严重的信任与发布风险 | 需要核对项目后来是否增加阻断、证据展示或人工审核 |

### 当前项目主线

项目亮点不只是“搭了 Agent、做了取数和分析”，而是经历了一个清晰的工程演进：

> 先把高确定性的取数链路做准，再把专家分析方法沉淀为 Skill，最后尝试开放式分析；开放自由度后，又通过真实事故认识到 Agent 必须在能力未命中时安全失败，不能把专业校验责任转移给新用户。

其中最后一句目前是 Codex 的总结，后续需结合项目实际采取的措施校正，不能提前写成已经解决。

## 追加口述：项目演进回顾

### 原始口述

> 首先这个项目是从去年就开始的。去年也是为了好用好查，就是一开始为的是那个指标平台，用户可以自由地去取数，做了指标线上化。然后既然指标做了线上化，有接口查了，然后当时 AI 也已经开始火了，我们就做了一堆工作流。
>
> 然后今年是“龙虾”爆火嘛，然后我们也是借用去年沉淀下来的数据基础去做了这个智能分析的一个 Agent。这个 Agent 一开始的定位就是要替代商分，就是让每一个运营都有自己的商分，这个商分就是我们这个 Agent。
>
> 然后我们最初的目标呢，大概可能从 3 月份到 4 月份应该都在解决数据准确性的问题。解决的方案呢，我们其实更多的都是工程细节，核心的思路其实就是脚本化、澄清和验证。就是有一个澄清的过程，然后尽量不走思考推理、走代码，因为指标怎么支持、指标从哪里查，这个其实都是固定的。
>
> 我们原本写的是一个规范文档，后面就改成了工具。我们其实要求 AI 强制去查一下这个指标是否支持、它支持的方法是什么，然后让它后面用什么方法。包括各种概念，什么本期、当期、同比、月同比，什么日期，自然周从哪里开始到哪里，包括各种复合指标的计算，都脚本化了。它其实只用做好选择题就好。其实这个阶段还是一个路由器阶段，但是这个阶段就已经非常非常好用了，这个时候用户就已经开始各种夸了。
>
> 后面的一个阶段就是做分析，大概 4 月份到 6 月份吧。我们陆续跟商分合作，沉淀了四种大方向的分析思路，包括什么流量分析、流量移动分析、商户移动分析、保费情况分析、保费情况精算。思路基本上是 Skill 的形式，基本就是工作流吧，就是用 Skill 的形式实现了我们去年做的那种工作流。它同时具有一定的自由度，可以选定时间、角度、指标类型以及大方向。
>
> 这一块其实很顺。遇到的最大问题是，我们一开始想的是用户从头开始分析，但实际上用户是从中间一段开始分析。例如我们要分析流量，Skill 的思路是从整体看，先看我们今天保费涨了还是减了；涨了，是哪里涨、哪里减；涨得最多的那里又分为险种，险种下面分不同渠道，渠道又分不同措施，一层层看。
>
> 但运营的实际场景是，他们可能直接负责一个 source、一类 source。他直接看到这个 source 降了，就直接问这个 source 什么情况，其实需要直接到漏斗。但用户也不会说它是个 source，可能直接说“通知情况”。“通知”这个概念在 source 跟渠道都有类似概念，AI 可能直接把它当一个渠道来分析，做了一大堆，但用户要的不是那个东西。
>
> 2026-08-30 校正备注：用户明确表示不理解“通知可能指 source 或渠道”这一例子。当前将本段作为旧语音转写 / 上下文缺失保留，不再用作项目事实或正式案例。
>
> 我们的 Skill 整体也是从头分析，容易从很上面开始跑，就非常非常慢；从用户那个地方开始生成其实就很快。然后我们就改变了 Skill 的思路，改成“原能力”的视角。我们提供能力跟方向，没有直接写成一个大的分析，把它解构了。它其实分为两种：一种下拆分析，另一种是漏斗分析。整个大分析就是下拆、再下拆、再下拆，下拆到底，然后再漏斗。Skill 本身还一直在做一些细节，包括把这些东西脚本化、做澄清，其实都是细的工程工作。
>
> 第三阶段就是 8 月份吧，就是我走的前一个月开始。因为大部门想把整个数据智能统一收口到一个引擎。用户量最大的业务有专门团队做这个引擎，所以我们的所有东西都迁移到他们那里去了。说实话，在解决我们的问题上远不如我们的，我们业务一直用我们的。但有些东西就是这样，所以我不想在这做了。这是题外话。
>
> 这一阶段核心做的就是智能分析，核心还是不出错。它的能力已经绝对够了，远超出他们的预期。现在就是有时候会出错，导致信任度没有特别高。尤其对于新人来说，他容易太信任；老员工挺信任，但他们有判断力，他们最终用这个出的报告基本上没出过问题。新员工没有判断力，AI 出什么他就说是什么，会导致很多问题。所以这个阶段一个是解决速度问题，另一个是解决这个准确性、信任问题。
>
> 速度问题，我们这个加速核心还是缓存的逻辑，因为能快非常非常多。我们这数一查就查半个小时、十几分钟，尤其看两三年的。尤其是看三年以上的，我们把所有东西都缓存好了，常用分析的都放在统一文件，然后每天有第一个人查了之后，就会把当天的更新上，历史的都在。
>
> 不准的问题，我初步的思路还是有校验。那个错的核心就是“用的对的指标”，然后也没有校验说这个指标压根不在我们的指标库里面。加一个指标库，这个就解决了。

## 项目问题—方案—结果—边界

### 问题一：自然语言指标表达不稳定，模型不适合自由计算

**为什么难**

- 用户可能使用非标准名、近义词或谐音。
- “本期、当期、同比、月同比、自然周”等包含明确但容易混淆的时间语义。
- 复合指标的计算和指标支持范围本身是确定性业务规则。

**实际方案**

1. 先用规范文档约束 Agent。
2. 后来把确定性规范改造成工具。
3. 强制 Agent 查询指标是否受支持以及对应的查询方法。
4. 将日期语义、周期边界和复合指标计算脚本化。
5. 让模型主要完成候选选择和路由，而不是自行推理计算。
6. 通过用户澄清和结果验证完成闭环。

**结果**

- 用户口述该阶段已经非常好用，并获得大量正向反馈。
- 与之前确认的“核心指标平台取数准确率接近 100%”方向一致，但仍受指标平台覆盖范围限制。

**边界**

- 当前仍需补充工具输入输出、强制调用机制、验证规则以及失败后的处理方式。

### 问题二：专家分析流程默认从全局开始，但用户经常从局部异常进入

**为什么难**

- 商分总结的完整方法通常是“总体变化 → 分层下钻 → 局部原因 → 漏斗”。
- 运营往往只负责某个 source 或局部业务，已经知道异常点，提问会直接从中间节点开始。
- 用户使用的业务词可能横跨多个数据层级；例如“通知”可能指 source，也可能指渠道。
- 如果 Skill 无视用户当前所在层级，从总体重新跑，既答非所问又显著增加查询时长。

**实际方案**

- 不再把一个专题写成只能从头执行的大 Skill。
- 将完整分析解构为更基础的分析能力，目前明确口述了“下拆分析”和“漏斗分析”。
- Agent 根据用户当前的问题节点、方向、时间和指标类型选择分析入口。
- 对层级和业务概念继续做澄清，将可确定部分脚本化。

**结果**

- 能从用户当前异常节点开始执行，避免无用的全局扫描。
- 用户口述从该节点开始分析会明显更快。

**边界**

- “下拆分析”和“漏斗分析”怎样选择、能否组合、各自调用什么工具仍待补充。
- “原能力”的准确说法待确认。

### 问题三：长周期查询慢，影响 Agent 分析体验

**为什么难**

- 一次数据查询可能需要十几分钟到半小时。
- 两三年或三年以上的长周期分析会反复读取大量不再变化的历史数据。

**实际方案**

- 缓存常用分析需要的历史数据。
- 将历史结果放在统一文件中复用。
- 每天由第一个查询触发当日数据更新，历史部分继续复用。

**机制理解**

这接近“历史数据预缓存 + 当日数据惰性刷新”的设计：把稳定历史数据和变化中的当日数据分开处理，避免每次请求重算完整时间范围。

**结果与边界**

- 用户口述速度提升非常明显，但尚未提供优化前后的精确 P50/P95 时延。
- 仍需补充缓存键、文件格式、并发首查、失效机制、数据回刷和错误缓存治理。

### 问题四：开放分析能力足够，但错误报告会破坏信任

**为什么难**

- 模型能够生成完整、流畅的分析报告，错误不一定在形式上暴露。
- 老员工能依靠业务经验发现异常，新员工却更容易把结果直接当成事实。
- 报告一旦进入向上汇报，单个错误会放大为对整个 Agent 的不信任。

**当前实际状态**

- 用户明确认为该阶段的重点已从“能力够不够”转为“能不能稳定不出错”。
- 老员工使用报告基本没有出过问题，但这个结果包含人工业务判断，不能等同于 Agent 自身准确率。
- 新员工错误汇报案例证明，仅依赖用户审核不是可靠的系统边界。

**用户此前的初步方案**

- 增加指标库校验，阻止不在受控指标库中的指标进入正式分析。

**本轮澄清后的边界**

- 事故中的 B 指标本身就在指标库中，因此“指标是否存在”的成员校验无法解决这个问题。
- 真正缺少的是“业务问题/事件与指标是否适配”的语义校验，而不是再检查一次指标名称是否合法。

**尚未确认**

- 该校验是已经完成、迁移后由统一引擎实现，还是用户离开前提出但未落地。
- 除指标库成员校验外，是否还实现了来源展示、置信提示、报告审核或失败拒答。

## 指标澄清与查询路由

### 用户原始口述

> 澄清阶段会要求 Agent 去我们的指标库中检索这个指标。这个是模糊搜索的方法，也没有做语义向量，就是纯粹的模糊搜索。把搜索到的结果，如果能完全匹配，就直接用了；如果不能完全匹配，就向用户澄清：“你要查的是不是这个？这个的定义是……”然后用户选择了之后，它再去查。
>
> 这里匹配到的指标也会描述它的查询方式，例如它支持指标平台查询，还是仅支持 SQL；SQL 的话是否给了模板。

### 当前确认的执行链路

```text
用户输入指标表达
  → Agent 调用指标库检索
  → 纯字符串模糊搜索，不使用语义向量
  → 判断是否与标准指标名完全匹配
      ├─ 完全匹配：直接采用该指标
      └─ 非完全匹配：向用户展示候选指标及定义，由用户选择确认
  → 读取指标对应的查询方式
      ├─ 支持指标平台：走指标平台查询
      └─ 仅支持 SQL：检查是否提供 SQL 模板，再进入 SQL 查询路径
```

### 指标库当前承担的职责

指标库至少不是一个单纯的名称列表，它同时承担：

1. **标准指标解析**：把用户表达映射到标准指标名。
2. **定义展示**：模糊匹配时向用户展示候选指标的业务定义。
3. **查询路由**：描述指标应走指标平台还是 SQL。
4. **SQL 资产发现**：当指标只支持 SQL 时，说明是否存在可复用模板。

指标库是否还保存维度、粒度、可用时间范围、权限、数据源、负责人或质量状态，当前尚未确认。

### 机制判断

- 选择纯字符串模糊搜索而非向量检索是合理的保守设计：指标名是受控枚举，召回候选后由用户确认，比模型自行做语义近似映射更容易审计。
- 但“名称完全匹配”只证明用户输入与某个合法指标名相同，不能证明该指标符合用户真实业务意图。用户可能准确输入了一个真实存在、但语义上选错的指标。
- 非完全匹配路径通过“候选名称 + 指标定义 + 用户确认”降低歧义；其效果取决于候选数量、排序质量，以及新用户能否看懂定义。
- 当前仍未回答最初的硬约束问题：Agent 是否在运行时必须调用指标库，还是主要依赖 Prompt、规范或 Skill 指令。用户本轮明确了调用后的行为，但未说明跳过调用时系统是否会阻断。

### 面试官可能继续追问的实现细节

1. 模糊搜索具体使用什么匹配方法，返回 top-k 还是阈值内全部候选？
2. 多个候选相似时怎样排序；没有候选时是拒答、转 SQL，还是让用户重新描述？
3. 一个问题包含多个指标时，是逐个确认还是统一确认？
4. 指标定义是否足以让新用户区分相似指标，有没有展示单位、粒度、适用场景和例子？
5. 指标平台和 SQL 路由信息存放在指标库的哪些字段中？
6. SQL 模板怎样参数化，怎样限制表、维度和时间范围？
7. 指标库更新后，Agent、缓存和评测集怎样保持一致？

### 与新人错误报告事故的已确认关系

事故路径现已明确：

```text
用户要分析 A 事件
  → 选择/表达了 B 指标
  → B 指标是指标库中的合法指标，名称能够匹配
  → Agent 能够正常查询并持续计算 B 指标
  → 系统没有验证“A 事件是否应该使用 B 指标”
  → 新员工也不知道 A 事件应使用 A 指标
  → 错误指标贯穿整份分析报告
  → 报告被用于向上汇报
```

因此，这次事故不是检索召回失败，也不是指标计算错误，而是**业务分析目标与指标之间的适用关系没有被建模和校验**。

### 当前指标库的能力缺口

现有指标库能够回答：

- 这个指标是否存在；
- 这个指标的定义是什么；
- 这个指标走指标平台还是 SQL；
- SQL 是否有模板。

但它不能回答：

- 分析 A 事件应该优先使用哪些指标；
- B 指标是否适用于 A 事件、当前分析层级和业务对象；
- 当用户选择的指标与分析目标不一致时，是否必须阻断并重新澄清。

严格来说，缺少的是一层“分析目标/业务事件—指标”的适用关系，而不是简单增加更多指标名称。

### Codex 提出的候选补法（尚未确认项目已实现）

1. 为常见业务事件或分析目标维护允许使用、推荐使用和禁止使用的指标集合。
2. 在 Skill 中显式声明每类分析方法需要的核心指标、辅助指标和适用条件。
3. 在执行前输出并校验“我要分析什么 → 选择什么指标 → 为什么该指标适用”。
4. 无法证明事件与指标之间存在已知关系时，强制向用户澄清，不能因为指标可查就继续生成报告。
5. 在最终报告中展示分析对象、实际使用指标及其定义，降低新用户把合法但不适用的指标当成正确指标的风险。

这些是基于事故根因提出的设计候选，不得写成项目已经落地的方案。

### 仍需确认

- 业务事件与正确指标之间的关系，后来是否被写进 Skill、业务知识库、规则表或其他资产。
- 事故发生后是否真正上线了阻断逻辑，还是只形成了改进思路。
- 标准指标名是在查询结果、分析中间状态还是报告生成阶段丢失的。

## 新人事故补充：Agent 的词义判断其实正确

### 用户补充口述

> 新员工说的是一个模糊的词，Agent 判断为 B。它那个词基本没什么歧义，确实指的就是 B。但是他不懂，所以说成了 B。我们的指标太多了，确实不懂行的人可能弄错。
>
> 这件事的核心是，AI 不知道这个事件应该用哪个正确指标。并且在最后的分析报告中，它没有使用实际查询指标的标准指标名，而是用了分析过程中用户跟它交互时说的那些词。

### 对事故根因的进一步纠偏

为了避免 A、B 的字母在多轮口述中发生指代变化，下面改用“目标事件、应选指标、实际查询指标、用户口语”四个中性名称。

此前若把问题描述为“意图识别错误”并不准确。当前更严格的事故链是：

1. 新员工使用了一个业务口语，该口语的词义基本没有歧义。
2. Agent 将它映射到某个标准指标，这一步词义判断本身正确。
3. 该标准指标是指标库中的合法指标，能够正常查询和计算。
4. 但 Agent 不知道目标事件应该使用哪个正确指标，也就无法判断当前实际查询指标是否适用。
5. 报告生成时没有展示实际查询指标的标准名称，而是沿用了用户口语。
6. 最终报告既使用了不适用的指标，又隐藏了该指标的标准身份，使用户和复核者更难发现问题。

因此这次事故属于：

> **局部词义解析正确，但缺少“业务事件—指标”的领域映射；同时标准指标身份没有完整传递到最终报告。**

它不是传统意义上的指标检索错误、意图分类错误或数值计算错误。

### 两个相互放大的工程缺口

| 缺口 | 当前系统做到了什么 | 缺失了什么 | 直接后果 |
| --- | --- | --- | --- |
| 领域适用性 | 能把用户口语解析到一个合法指标，并知道怎么查询 | 不知道某类业务事件应该使用哪些指标，也不会检查事件—指标是否匹配 | 合法但不适用的指标能够一路计算成功 |
| 指标身份传递 | 查询阶段已经落到具体标准指标 | 报告没有强制保留标准指标名，而让模型沿用用户口语 | 读者看不到真正查了什么，错误更难被发现 |

第二个缺口不是单纯的展示瑕疵。对于数据分析报告，指标标准名属于证据和来源的一部分。如果最终文字可以自由改写指标名，那么系统即使查询了结构化、可审计的数据，也会在最后一步丢失可追踪性。

### 指标数量多带来的产品问题

这次事故还说明，标准指标库解决了“统一名称和查询路径”，但没有完全解决“非专家如何选对指标”：

- 指标数量多，相似或相关概念多；
- 新员工不知道业务问题应该对应哪个指标；
- 即使定义展示准确，新员工也未必具备判断定义是否适合当前任务的知识；
- 用户确认只能证明他点击了某个候选，不能证明选择在业务上正确。

因此“让用户确认”不是绝对安全边界。对非专家用户，系统不仅要确认用户说的是哪个词，还要知道该业务事件通常该用什么指标，并在报告中如实展示最终查询的标准指标。

### 更严格的数据传递方式（Codex 候选，尚未确认项目实现）

查询链路不应只向后传递一个自然语言名称或数值，而应传递结构化指标对象，例如：

```text
MetricEvidence
  - metric_id
  - canonical_name
  - user_alias
  - definition
  - query_route
  - dimensions
  - time_range
  - value
  - provenance
```

其中 `canonical_name` 与 `metric_id` 应贯穿指标选择、查询、分析和报告生成，不能由模型自由改名；`user_alias` 只能作为“用户原始说法”附带展示。

在此基础上，可以形成两个校验点：

1. **执行前**：根据目标事件检查所选指标是否属于推荐或允许集合，无法证明适用时重新澄清。
2. **报告前**：每个关键数值必须绑定实际查询的 `metric_id` 和标准指标名，报告不得只使用用户口语替代。

这能分别解决“选错指标”和“报告隐藏真实指标”两个问题。但它目前只是根据事故提出的设计候选，不代表项目已经实施。

### 当前首要待确认

用户已确认：标准指标身份在查询和分析链路中仍然存在，是最后的报告生成模型把标准指标名改写成了用户交互时使用的口语。

因此该问题已经定位到**报告生成层对事实字段缺少保护**，而不是指标检索工具或分析中间状态丢失了标准指标。

更准确的修复方向应是：

- 标准指标名、指标 ID 等事实字段不允许由模型自由改写；
- 报告正文涉及数值时，必须从结构化查询结果中引用标准指标名；
- 生成后校验报告中的指标名是否与实际查询指标一致；
- 用户口语可以作为别名解释，但不能替代标准指标名。

这些仍是 Codex 提出的修复方向，是否在项目中落地尚待确认。

## 周报自动化与周会实时问答

### 用户原始口述

> 我们还有周报自动化。业务每周会有一个大周会，这个周会他们会拿这一周的各种分析数据，其实就是一些标准的大指标。这个叫周报，他们会做分析。我们的 Agent 会自动化生成这个周报，并且在他们提出一些问题后，会实时地去做反馈。
>
> 大部分场景下，他们会遇到这个问题：大老板说这个不对，然后让手底下运营去看。运营其实大部分都会懵，就会去问我们的 AI，然后把 AI 回答的结果贴上去。这也是常见的一个使用场景，所以我们的准确性非常重要。

### 使用链路

```text
每周固定大周会
  → 汇总本周标准大指标
  → Agent 自动生成周报及初步分析
  → 管理者在会议或会后提出问题/质疑
  → 运营需要快速解释
  → 运营向 Agent 继续追问
  → Agent 实时查询或分析并返回答案
  → 运营将回答直接贴回讨论或汇报材料
```

### 这不是单一功能，而是两个连续模式

| 模式 | 触发方式 | 主要输入 | 输出 | 主要要求 |
| --- | --- | --- | --- | --- |
| 周报自动生成 | 每周固定触发 | 本周标准核心指标 | 周报和初步分析 | 数据稳定、口径统一、格式固定 |
| 会议追问响应 | 管理者临时提出问题 | 周报上下文和临时业务问题 | 实时补充分析或解释 | 速度快、理解上下文、不能编造 |

### 为什么准确性在该场景中尤其重要

1. **结果直接进入管理讨论**：Agent 的周报和临时回答会被运营用于周会或向上反馈。
2. **追问具有时间压力**：运营面对管理者质疑时，需要快速给出解释，没有充足时间重新走人工取数流程。
3. **使用者未必具备独立分析能力**：运营可能不知道该如何定位原因，会直接依赖 Agent 的答案。
4. **答案可能被原样转发**：从 Agent 到管理者之间缺少稳定的专家复核层。
5. **单次错误会放大信任损失**：错误不仅影响一个查询，还会让管理者质疑整份周报和系统能力。

因此，该项目的可靠性目标不能只定义为“查询成功”或“数字计算正确”，还需要覆盖：

- 使用了正确的业务指标；
- 报告展示真实的标准指标名；
- 分析结论与查询证据一致；
- 不确定或能力未覆盖时明确暴露边界；
- 临时追问不能因为时间压力而跳过必要澄清和校验。

### 当前能够形成的使用价值

- 自动承担固定周报的数据汇总和初步分析工作。
- 在管理者临时追问时，为运营提供即时的取数和分析支持。
- 让原本缺少独立分析能力的运营能够更快回应业务问题。

以上是使用方式和用户口述价值；目前尚缺周报生成数量、节省时长、真实使用频率、人工复核比例和回答采纳率等量化证据。

### 需要趁内部环境核对的细节

1. 周报由定时任务、固定 Workflow、Skill 还是其他机制触发。
2. 周报包含哪些标准指标和分析模块，是否使用固定模板。
3. 周报生成后是否有人审阅，再进入周会或发送给业务。
4. 会中追问是否自动携带本周周报上下文，还是运营需要重新描述问题。
5. 实时回答使用缓存中的周报数据，还是重新调用指标平台/SQL 查询。
6. 周报和追问结果是否展示标准指标名、查询时间、数据来源或其他证据。
7. 每周生成耗时、人工节省时长、追问量、回答采纳方式和典型失败案例。
