# 项目定位与业务边界材料

> 当前状态：项目最高层定位已由用户重新确认，并已用于终稿 v1.2；以下继续保留来源、历史口径和边界。

## 2026-08-31｜用户确认的最终项目定位

用户纠正：项目不是“把数据转换成结论的 Agent”。它的主语是运营和业务，核心是：

> **这是一个可以自助、自由取数并进行经营分析的 Agent。运营和业务不需要依赖数据开发，不需要依赖商分，也不需要专业的数据知识，就可以取到准确的数据并进行经营分析。**

终稿据此采用以下定位：

- 面向场景险运营和业务人员的一站式自助取数与经营分析 Agent；
- 将指标口径、数据查询和商分分析方法内化为系统能力，对用户隐藏专业数据复杂度；
- “自助”强调用户可独立完成常规任务，“自由”强调不局限于固定看板和预设报告；
- 底层的受控取数、Skill、证据和评估是实现该定位的技术手段，不是项目最高层定义。

此前“把可信数据转化为经营结论”的概括已撤回，不再作为项目定位。

## 2026-08-31｜需求分类与文档层级校正

用户进一步确认：

- 项目价值还包括节省大量协作成本，不只是节省取数和分析耗时；
- “临时监控”应改为“异动分析”；
- 需求中必须包含探数、取数、看数，即用户为了查看某个数值或判断某件事而先获取数据；
- 分析能力统一称“经营分析”，也可用“数据分析”作通俗说法；
- “固定分析”统一改称“常规经营分析”；
- 原终稿中的“项目真正解决的核心问题”实际写的是技术难点，必须与业务核心问题分开。

终稿采用以下层次：

1. 业务核心问题：运营和业务依赖数据开发、商分和专业数据知识，时间与协作成本高；
2. 用户需求：取数类（探数、取数、看数）与分析类；
3. 分析类形态：经营分析（开放式）、异动分析、常规经营分析；
4. 核心技术难点：如何同时做到自助、自由、准确、低门槛和有边界。

“证据契约”不是用户确认的项目术语，而是 Codex 对结构化任务和结果传递的抽象。该词已从项目顶层和技术主叙事中撤回，改为直接说明 Agent 之间需要传递标准指标、查询参数、实际数据来源和结果依据。

## 已经较清楚的内容

1. 业务领域与项目形态：美团金融场景险业务的自助取数与经营分析 Agent。
2. 项目起点：先完成指标线上化和接口化，再基于数据底座发展 Agent。
3. 核心服务对象与愿景：让运营和业务无需依赖数据开发、商分或专业数据知识，即可自己取得准确数据并完成经营分析。
4. 核心业务任务：可信取数、复用成熟分析方法、支持局部异常和开放式分析。
5. 关键业务风险：新员工更依赖 Agent，却更缺少识别错误指标和错误报告的能力。
6. 表达边界：“不依赖数据开发和商分”指常规取数与经营分析可由用户自助完成，不等于取消专业角色或省略复杂、高影响任务的复核。

## 待补或待最终确认的内容

1. **原有流程与痛点基线**：引入 Agent 前，运营如何提取数或分析需求，由谁处理，通常耗时多久，核心瓶颈是什么。
2. **用户和场景边界**：核心用户到底包括哪些运营、商分、管理者或其他角色；他们分别用于即时查数、临时分析、周报还是追问。
3. **产品能力外边界**：系统只做取数、解释和报告，还是会直接执行业务动作；哪些高风险任务必须人工复核；哪些请求应拒答或降级。
4. **愿景、目标与实际结果的区分**：用户自助模式、平台级准确率目标和具体业务线交付不能混写。
5. **项目和统一平台的业务边界**：场景险业务线自建什么，平台提供什么，迁移前后的“这个项目”指代哪个范围。

## Codex 初步判断

现有材料足以写出“项目定位与业务边界”的第一版，但还不足以封口。最值得下一轮集中确认的是：原有业务流程、核心用户与使用场景、系统明确不做什么，以及迁移前后的项目范围。
