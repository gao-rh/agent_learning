### 文档中已标明为用户确认的实际实现

1. 开发者固化工具参数，直接调用平台全量导出 / 下载接口，不依赖 AI 自行翻页拼全量结果。
2. 全量查询结果保存为文件，AI 只阅读前 200 行预览；聚合与统计由下游代码直接读取全量文件，AI 再检查聚合结果。
3. 指标优先使用用户原始表达检索指标库；完全匹配则确定标准身份，非完全匹配则展示标准候选让用户确认，原话无结果时再用模型理解补充检索。
4. 相对时间和具体日期范围交给确定性脚本计算，不由模型心算。
5. 用户问题被拆为指标、维度 / 维度值和时间，分别经指标库、维度库和时间脚本标准化。
6. 指标库返回指标支持的维度、数据集和查询方式；AI 基于受控元数据组装参数，取数引擎执行并返回不支持的组合，AI 再解释并推荐替代路径。
7. 分析方法知识库中保存各类分析的推荐指标，用于缓解业务事件与指标不适用问题；用户已明确该方法只是软引导，不是强适用性校验。

### 问题归属边界

文档已将问题分成两类：

1. **智能经分项目直接问题**：业务事件—指标适用性、报告标准证据丢失、多轮上下文丢失、底表 / SQL 口径与路由、维度和业务别名覆盖、分析方法与知识长尾、长周期性能、评测结论可信度。
2. **主要属于统一平台的共性问题**：无人值守认证与权限、API / MCP / 工具路径漂移、无效重试、文档和消息交付尾端失败。

## 2026-09-07｜记录 002：项目难点与亮点候选判断

> 状态：Codex 根据现有材料形成的面试表达候选，待用户确认。以下排序表示面试价值，不代表已经替代原始事实记录。

### 总判断

项目最核心的技术难点不是让模型查询数据或生成报告，而是：

> 在用户不具备专业数据知识、需求表达又可能模糊且开放的情况下，让 Agent 仍然能够自助、自由地完成准确取数和经营分析。

这意味着系统必须同时解决语义理解、数据正确性、分析开放性、工程性能和质量评估问题。单独实现自然语言转 SQL、工具调用或报告生成，都不足以完成这一目标。

### 核心难点候选

#### 1. 把模糊的业务表达转换为可执行、可校验的数据任务

用户使用的是业务简称、近义词、业务黑话和相对时间，而底层执行需要确定的指标、维度、维度值、时间、粒度和查询方式。难点不只是识别用户说了什么，还要确保：

- 用户口语对应正确的标准指标；
- 指标支持用户要求的维度；
- 时间范围和同比、环比口径正确；
- 比率和复合指标按正确公式重算；
- 指标虽然合法可查，也确实适用于当前业务事件。

其中“指标身份匹配正确”与“指标适用于当前业务问题”是两个不同层次；历史真实错误说明后者仍是需要持续治理的边界。

#### 2. 在开放分析能力与结果可信度之间取得平衡

固定 Workflow 稳定但覆盖范围有限，完全开放的 Agent 灵活却容易错误路由、无依据推理或生成看似合理的结论。系统既要允许用户从任意局部异常开始，又不能让模型绕过标准数据链路自由猜测。

这一难点要求将 Agent 的自主决策限制在明确的工具、数据、权限、预算、循环和停止条件之内，并让分析结论能够回到实际查询的数据依据。

#### 3. 把商分经验从隐性方法变成可复用、可组合的分析能力

经营分析不是一次固定计算。商分会根据当前现象选择趋势、下拆、漏斗、贡献、目标 Gap 等不同方法，并依据中间结果决定是否继续下钻。

项目需要把这些专家经验沉淀为 Skill 和基础分析能力，同时避免把它们重新固化成只能从头运行的大流程，使 Agent 能够从用户当前关注的异常节点开始组合执行。

#### 4. 处理大数据量、长耗时与有限模型上下文之间的矛盾

长周期查询耗时较长，平台返回还可能存在分页上限；如果把全部明细直接放进模型上下文，会同时造成数据不完整、Token 浪费和上下文污染。

因此需要同时保证底层取得全量数据，并限制模型只读取必要的结构、汇总和样例。这不是单纯的性能优化，也是结果完整性和分析稳定性问题。

#### 5. 建立能够定位真实失败位置的评估体系

最终答案写得通顺，并不能证明指标、日期、维度、原始数据和分析过程正确；开放分析又往往不存在唯一标准答案。

项目需要同时评估数据准确率、端到端任务成功率和各关键过程，并区分首跑成功与重试后的最终成功。对于确定性字段、开放分析和高价值争议题，还需要分别使用程序校验、Judge 和人工复核。

### 核心亮点候选

#### 1. 业务定位完整：从自助取数延伸到经营分析闭环

项目不是单一的问数机器人、NL2SQL 工具或报告生成器，而是让运营和业务在不依赖数据开发、商分和专业数据知识的情况下，自助、自由地取到准确数据并继续完成经营分析。

它同时创造两类业务价值：通过减少常规取数、分析投入及多轮跨角色沟通实现降本；通过缩短等待、分析和业务响应时间实现增效。

#### 2. 用“确定性工程 + Agent 判断”实现有界自主

模型负责理解问题、澄清、规划、选择方法和解释结果；代码和受控工具负责日期、公式、聚合、权限、Schema、重试和停止条件。项目没有把正确性主要寄托在 Prompt 上，也没有退回到完全写死的 Workflow。

#### 3. 直接取数和分析内部取数共享同一可信数据链路

分析 Agent 不绕过取数能力直接访问底层数据。直接查数和经营分析都复用标准指标、维度、查询路由、权限、完整性和质量校验，使分析结果能够追溯到实际查询的数据和标准指标身份。

#### 4. 将专家分析方法拆成可组合的原子能力

项目从完整大 Workflow 演进到趋势、下拆、漏斗、贡献等可组合能力，由 Agent 根据用户已有信息和当前异常位置选择分析入口。这个设计同时降低无效查询，提升常规经营分析复用性，并为开放式经营分析提供基础积木。

#### 5. 用文件承载全量数据，隔离模型上下文

底层固定获取全量数据并保存为文件，代码直接读取全量文件完成聚合；模型只接收预览、Schema、汇总、异常和必要样例。这一机制同时解决平台静默分页、全量数据污染上下文和高 Token 消耗问题。

#### 6. 评估从“答案分数”扩展到端到端质量诊断

三层评估体系既看数据准确率和端到端任务成功率，也检查意图、澄清、取数、分析、记忆、成本、延迟、安全和不编造，并通过首错定位和线上失败回流支持持续迭代。

#### 7. 有真实使用和效果，而不是演示型原型

项目覆盖约 20–30 名场景险产运和商分用户；传统取数至少等待半天，常规分析从 2–3 天缩短至约 1–2 小时，历史整体表现约 90%。这些结果能够证明项目进入了真实业务流程，但精确活跃度、采纳率和统一性能指标仍未统计。

### 面试表达优先级建议

如果只能选择一项难点和三项亮点，建议优先讲：

1. **核心难点**：在开放自然语言入口下，怎样保证非专业用户取数和分析的端到端正确性；
2. **亮点一**：确定性工程与 Agent 判断分工，形成受控但不僵化的执行方式；
3. **亮点二**：统一可信取数链路，并让分析结论能够追溯到标准指标和真实数据；
4. **亮点三**：将商分方法拆成可组合能力，兼顾高频常规分析和开放式分析。

大结果集处理和三层评估体系适合作为后续技术追问中的强化亮点。

### 不宜单独包装成亮点的内容

- “使用了多 Agent、RAG、Tool Calling、记忆”等技术名词本身不是亮点，必须说明它们解决了什么真实问题；
- “历史整体表现约 90%”是结果，不是技术亮点，且不能替代分层评估说明；
- 业务事件与指标适用性目前只有推荐指标等缓解措施，不能表述为已经完成全场景强校验；
- 平台提供的底层能力不能直接改写为个人独立完成的成果。
