# 2026-08-28 智能经营分析项目与面试准备整体骨架确认

> 状态：模块划分角度和处理顺序已确认；具体日历排期尚未确认。

## 已确认事实

- 距离实际面试至少还有两周以上，当前目标不是尽快拼出面试话术。
- 以现有智能经营分析项目为底座，先确定最优目标架构，再逐模块补充、实现和验证，最后进入面试。
- 不把“历史事实”和“理想方案”组织成两条并行讨论主线；后续围绕统一目标方案推进，并保留尚需实现或验证的事项。
- 采用“项目叙事 + 端到端链路 + 横向保障”的划分角度。
- 项目全景必须是第一个模块，不能直接从调用链或技术组件开始。

## 未知项

- 第一场实际面试日期。
- 每天或每周可投入的时间。
- 哪些优化只需形成可解释设计，哪些需要在 LangGraph 脱敏复现中编码验证。
- 若实现范围明显超过学习复现，后续使用哪个独立仓库承载正式开发。

## 本次关键问题

经营分析项目应按什么角度划分模块，并以什么顺序推进，才能既完整讲清项目，又逐步补齐技术实现、验证证据和面试追问？

## 方案比较

| 方案 | 优点 | 主要问题 |
| --- | --- | --- |
| 按时间阶段划分 | 项目故事连贯 | 同一技术模块会在多个阶段重复出现 |
| 按技术组件划分 | 架构清晰，方便准备技术问题 | 容易变成技术拼盘，弱化业务问题和演进原因 |
| 项目叙事 + 端到端链路 + 横向保障 | 同时保留项目全景、真实执行链路和技术深度 | 需要先完成全景，再逐块进入机制细节 |

## 用户决定

> 已确认采用“项目叙事 + 端到端链路 + 横向保障”，先确定总骨架，再逐模块闭环。

正式顺序如下：

| 顺序 | 模块 | 核心范围 |
| --- | --- | --- |
| 1 | 项目全景与演进 | 背景、用户、问题、目标、阶段、能力版图、业务价值和个人职责 |
| 2 | 整体架构与完整调用链 | Agent、状态、入口、Tool、数据产物、循环和失败分支 |
| 3 | 可信取数链路 | 澄清、标准指标、时间维度、指标平台/SQL、证据与校验 |
| 4 | 分析引擎与知识体系 | 分析方向、下拆与漏斗、Skill、Workflow、知识库和组合机制 |
| 5 | Memory 与 Context | 用户、Session、Task、历史经验的保存、召回、注入、纠错和隔离 |
| 6 | 报告、评测与可靠性 | 报告证据、幻觉、错误指标、重试、拒答和人工复核 |
| 7 | 性能与生产工程 | 缓存、预计算、调度、并发、Token、成本、Trace、监控和恢复 |
| 8 | 业务落地与总复盘 | 周报、实时追问、告警、规模、价值、成败案例、协作和优化 |
| 9 | 面试总装 | 项目介绍、架构图、问题映射、连续追问和岗位版本 |

面试问题不作为独立技术模块。每个模块完成时同步处理相关面经问题；第 9 块只做汇总、交叉追问和模拟验收。

## 模块闭环标准

每个模块依次完成：

1. 确定目标设计与选型理由。
2. 补充关键实现或等价脱敏复现。
3. 用正常案例、Bad Case、失败恢复和 Trace 验证。
4. 映射面试调研中的直接问题和延伸问题。
5. 形成 30 秒结论、2～3 分钟展开和连续追问答案。
6. 用户能够脱稿解释并经追问验证后，再确认该模块的掌握状态。

## 对计划的影响

- 下一步只处理第 1 块“项目全景与演进”，暂不进入 Agent 编排、记忆、缓存或评测实现细节。
- 项目全景闭环后，再用一条代表性业务请求进入第 2 块完整调用链。
- 现有 LangGraph 面试复现作为机制验证支线，不替代项目主线，也不倒写成原项目生产技术栈。
- 具体两周排期、检查日期和每日投入，待模块 1 的信息量和实际可用时间明确后再确认。
