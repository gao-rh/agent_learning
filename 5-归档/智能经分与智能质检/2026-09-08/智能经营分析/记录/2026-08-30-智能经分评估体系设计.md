## Codex 反馈

### 从头重建的当前骨架

#### 用户理解

整个 Agent 最重要的两个顶层指标是：

1. **数据准确率**：最终结果中的指标名称与指标数值是否对应、是否正确；
2. **端到端任务成功率**：最终是否真正解决了用户的问题。

主体流程再按能力拆解：

1. **意图识别**：判断用户到底要解决什么任务；
2. **信息澄清与任务组装**：判断是否澄清了对应任务所需的全部信息，是否进行了适当拆解，并将信息正确组装后发送给对应 Agent；
3. **专业 Agent 执行**：
   - 分析 Agent：是否给出了正确的数据请求参数、图表是否正确、报告是否做好；
   - 取数 Agent：是否取到了正确数据、是否标注数据来源；
4. **跨会话记忆**：评估多会话连续性；
5. **成本**：评估整个 Agent 的资源消耗。

#### Codex 当前收敛

评估体系暂分为三个层次：

| 层次 | 回答的问题 | 当前候选指标 |
| --- | --- | --- |
| 顶层结果 | 整个 Agent 最终有没有做好 | 数据准确率、端到端任务成功率 |
| 主链路诊断 | 如果没做好，错在哪一层 | 意图识别、澄清与任务组装、取数 Agent、分析 Agent |
| 横向能力与效率 | 跨任务、跨会话是否可持续 | 多会话连续性、成本 |

需要保留的最小口径校正：

- 数据准确率只统计包含数据事实的任务；纯业务知识咨询等无数值任务不进入其分母。
- 对含数据任务，数据准确应是端到端任务成功的硬门槛：报告写得好但数据错误，不能算任务成功。
- 数据准确不能只比较裸数值，还必须确保数值绑定到正确指标和查询条件；具体最小字段以后再逐项确认。
- 成本不是一种业务能力，而是横向效率指标；后续至少区分单任务成本与单个成功任务成本。

本轮先确认以上层级关系，不继续设计具体用例、字段和阈值。

#### 外部事实

| 方案 | 主要评估设计 | 对当前项目的启示 |

| Databricks Genie | 使用真实业务问题建立最多 500 道 Benchmark；Chat 模式用标准 SQL 的结果集与生成结果比较，Agent 模式用评估说明和 LLM Judge 判整份响应；同时监控用户反馈、使用量和问题趋势 | 分开评“数据结果正确”与“复杂 Agent 响应是否完成任务”；图表和报告需要额外评审 |

#### 对当前分层的判断

用户提出的三层结构方向合理，而且与成熟方案有明确对应：

1. **数据准确率 + 端到端任务成功率**对应成熟方案中的结果集正确性与最终答案 / 任务正确性；
2. **意图、澄清与任务组装、取数 Agent、分析 Agent**对应工具选择、工具输入输出与轨迹级诊断；
3. **跨会话记忆与成本**属于项目特有能力和横向效率维度。

需要补充但不推翻原结构的三个边界：

1. 数据准确率仅适用于含数据任务，并应校验指标身份、查询条件与结果的绑定；成熟方案通常以执行结果为主，而不是要求 SQL 文本完全一致。
2. 端到端任务成功至少要区分首跑成功与经过澄清 / 重试后的最终成功，避免重试掩盖不稳定性。
3. 横向层除成本外，还应至少保留延迟 / 稳定性 / 回归，以及权限、安全拒答与不编造的硬门槛；线上用户反馈与使用量用于发现新问题，但不能替代离线正确性评测。

| 层次 | 正式候选内容 |
| --- | --- |
| 顶层结果 | 数据准确率；端到端任务成功率（首跑 / 最终） |
| 主链路诊断 | 意图识别；澄清与任务组装；取数 Agent；分析 Agent |
| 横向质量 | 跨会话记忆；成本；延迟 / 稳定性 / 回归；权限与安全拒答 |

### 顶层指标一：数据准确率

#### 用户口述的实际评测设计

用户将数据准确率定义为：对于一个取数 / 查数问题，Agent 最终获得正确数据结果的概率。

实际测试分为两类：

1. **单轮直接取数**：用户已经明确说出所需指标，验证 Agent 能否直接取得正确数据；
2. **需要澄清的取数**：使用一个简单模型扮演用户，与 Agent 完成澄清过程，验证最终能否取得正确结果。

取数题覆盖的复杂度包括：

- 简单取数；
- 当期与基期对比；
- 复杂维度；
- 比率型指标的平均值；
- 涉及公式计算的复杂指标；
- 各主要业务数据类别。

评测集初始为 20 条，之后逐步扩展到 200 条。

以上内容记录为用户口述的历史事实；题库版本、每类题量、Ground Truth 来源和实际运行统计尚未在本轮核验。

#### Codex 结构化理解

数据准确率可以先保持一个简单总公式：

```text
数据准确率 = 最终数据结果正确的有效取数任务数 / 有效取数任务总数
```

但报告时至少分开呈现：

```text
直接取数准确率
经澄清后的最终取数准确率
按取数题型分层的准确率
```

单轮测试的最小流程是：固定问题与 Ground Truth -> Agent 取数 -> 将最终结果与 Ground Truth 比较。

澄清测试的最小流程是：为用户模拟器保存完整隐藏任务 -> 只给 Agent 不完整初始请求 -> Agent 提问 -> 模拟用户按隐藏任务回答 -> Agent 取数 -> 将最终结果与同一 Ground Truth 比较。

为了让 20 条与 200 条结果可比较，需要保留题库版本和题型构成；如果题目分布发生变化，两个总体准确率不能直接解释为系统能力上升或下降。

#### Ground Truth 补充确认

用户确认：200 条题目的标准结果均经过人工确认，并且冻结了查询日期和版本。

因此当前可以确认：

- 每道题存在人工确认的标准结果；
- 动态数据通过固定查询日期和版本转化为可重复比较的评测条件；
- 同一批题可以用于 Agent 版本间回归比较。

#### 验证器补充确认与更正

用户先口述为程序自动比较，随后明确更正：历史实现实际使用大模型判断生成结果是否正确，即 LLM-as-a-Judge，并非确定性程序验证。已确认不变的判定口径是：一道题涉及的结果必须全部正确，整题才算通过，不使用部分得分。

因此数据准确率评测卡当前收敛为：

| 项目 | 已确认设计 |
| --- | --- |
| 被测能力 | 取数 / 查数任务最终获得正确数据结果 |
| 评测集 | 200 条人工确认标准结果的题目，冻结查询日期和版本；从最初 20 条逐步扩展 |
| 题型覆盖 | 简单取数、当期 / 基期对比、复杂维度、比率型指标平均、公式型复杂指标及各主要业务数据类别 |
| 测试模式一 | 单轮明确请求，直接验证最终取数结果 |
| 测试模式二 | 简单模型扮演用户完成澄清，再验证最终取数结果 |
| 历史验证器 | LLM-as-a-Judge：由大模型比较生成结果与人工确认的标准结果 |
| 单题判定 | 全部校验项通过才算该题通过；任一项不通过则整题失败 |
| 总指标 | 通过题数 / 有效运行题数 |
| 必要拆分 | 单轮直接取数准确率、澄清后最终取数准确率、各题型准确率 |

数据准确率的高层测试设计：待继续。需要进一步确认 LLM Judge 的提示词、输出格式、模型版本、一致性复核方式和历史运行证据。

#### 确定性程序验证的实现判断

程序化验证的复杂度取决于 Agent 输出边界：

- 如果评测器能够读取结构化取数结果，包括标准指标 ID / 名称、维度键、数值、单位和查询日期，复杂度通常为低到中等；主要工作是规范化后做集合与数值比较。
- 如果评测器只能读取自由文本报告，复杂度明显更高；需要先稳定抽取其中的数据事实，抽取错误会污染准确率。

当前推荐的候选方案是混合验证：

1. 数据结果使用确定性程序验证；
2. 自然语言是否完整回答、解释是否合适等语义质量继续使用 LLM Judge 或人工复核；
3. 澄清流程单独评估，不让 Judge 用“最终数字正确”掩盖错误澄清路径。

确定性结果验证的最小流程：

```text
结构化 Ground Truth
-> 结构化 Agent 结果
-> 统一单位 / 精度 / 空值 / 行顺序
-> 按指标和维度键对齐
-> 比较缺失项、额外项与数值
-> 全部通过才判整题通过
```

以上是未来改进建议，不代表历史评测已经程序化实现。

#### 用户最终确认

当前正式采用并对外描述的验证方式是 **LLM-as-a-Judge**，与历史实际实现保持一致；不把确定性程序验证写入当前方案。程序化比较仅作为本次讨论过但未采用的备选。

当前数据准确率口径最终收敛为：

```text
输入：人工确认、冻结查询日期和版本的标准结果
运行：单轮明确取数，或简单模型扮演用户完成澄清后取数
验证：LLM Judge 比较 Agent 最终结果与标准结果
单题通过：题内结果全部正确
数据准确率：通过题数 / 有效运行题数
```

为保证回归可解释，后续若形成正式评测文档，应记录 Judge 模型、Judge Prompt 和评测版本；这属于复现信息，不改变当前验证方案。

### 顶层指标二：端到端任务成功率

#### 用户口述的实际评测设计

端到端任务成功率覆盖的不只是取数任务，还包括分析任务及其他多种任务。评测关注 Agent 的最终结果是否符合预期，主要包括：

- 数据是否准确；
- 分析结论是否合理；
- 是否采用或命中了预期的分析思路；
- 总体结果是否正确、是否解决任务。

每道任务提供参考答案，由大模型将 Agent 最终结果与参考答案比较并评分，即使用 LLM-as-a-Judge。

以上记录为用户口述的历史评测方式；当前尚未核对任务类型构成、参考答案结构、Judge 评分区间、成功阈值、Judge 是否读取完整轨迹，以及历史实际得分。

#### Codex 当前收敛

需要区分两个指标：

```text
端到端任务得分 = LLM Judge 对单题输出的评分

端到端任务成功率
= 达到成功阈值且满足硬门槛的任务数 / 有效任务总数
```

如果历史评测只计算平均分而没有定义通过阈值，更准确的名称是“平均任务得分”，不能直接称为“任务成功率”。

当前建议的最小判定原则：

1. 对包含数据的任务，数据错误时整题不能判成功；
2. 参考答案应说明必须覆盖的事实、分析要求和禁止出现的结论；
3. 除非业务明确要求固定方法，不宜只接受一条唯一分析路径，应允许能够由数据支持的等价分析思路；
4. Judge 模型、Prompt、评分 Rubric、参考答案版本和成功阈值需要一起版本化。

以上为口径校正，尚待用户确认历史 Judge 的评分区间与成功阈值。

#### 用户确认的历史判定方式

用户确认：历史评测主要使用“通过 / 不通过”二元判定，不关注连续分数。不通过的任务会进一步检查具体失败原因，并据此改进系统。

#### Codex 对标后的推荐

对于需要做版本回归和上线判断的 Data Agent，推荐采用：

```text
最终结果：Pass / Fail
诊断结果：失败阶段 + 失败原因 + 判断依据
```

不要求输出无明确业务含义的连续总分。LLM Judge 最小输出候选为：

```json
{
  "pass": false,
  "failure_stage": "data | task_completion | analysis | report | safety",
  "reason": "可核对的失败原因",
  "evidence": "与参考答案或输出对应的依据"
}
```

通过条件应由参考答案 / Rubric 明确，而不是让 Judge 自由理解：

1. 数据型任务的关键数据正确；
2. 用户要求的必要部分全部完成；
3. 分析结论由数据支持；
4. 任务明确指定分析方法时正确执行；未指定时允许合理替代路径；
5. 不出现与证据冲突的结论、越权行为或编造。

汇总时保留：总体任务成功率、各任务类型成功率、主要失败原因分布。失败归因用于定位改进方向，不与 Pass / Fail 混成一个平均分。

为了控制 LLM Judge 自身误判，正式回归应固定 Judge 模型、Prompt、Rubric 和参考答案版本；对边界案例、Judge 理由不足的案例和少量通过案例进行人工抽检。

### 主链路诊断一：意图识别

当前开始讨论主体流程的第一个诊断模块。已确认的四类意图为：

1. 取数；
2. 业务知识咨询；
3. 分析；
4. 口径查询。

本模块暂只判断请求应进入哪条任务链，不在此处评估后续信息澄清、参数组装、工具结果或最终任务完成情况。

- 意图识别评测设计：待继续

#### 用户疑问：复合分析编排错误是否属于意图识别错误

用户回忆历史项目几乎没有出现过意图识别错误，并追问：一个分析任务需要依次取数、查询口径、获取业务知识、完成分析和生成报告时，如果主 Agent 的整套编排出错，是否也应算作意图识别错误。

#### Codex 反馈：主目标与能力调用分层

意图识别只判断用户最终想完成什么主任务；执行主任务所调用的能力属于规划与编排层。

例如：

```text
用户目标：分析 A 指标下降原因
主意图：分析
可能的能力链：口径确认 -> 取数 -> 业务知识 -> 原因分析 -> 报告
```

只要系统正确识别“分析”为主目标，后续漏步骤、顺序错误、选错工具或没有恢复原任务，都不应自动归为意图识别错误。

当前候选失败分类：

| 首个错误 | 归因 |
| --- | --- |
| 把分析请求当成纯取数，只返回一个数字 | 意图识别 / 主目标判断错误 |
| 已识别为分析，但没有拆出必要的取数或口径步骤 | 任务规划与分解错误 |
| 规划了正确步骤，但调用了错误 Agent / 工具 | 编排或工具选择错误 |
| 工具正确，但指标、日期、维度等输入错误 | 任务参数 / 工具执行错误 |
| 数据和分析过程正确，但最终报告遗漏或改写事实 | 报告生成 / 任务完成错误 |

结合用户的历史观察，四类粗粒度主意图可能不是当前主要失败来源。建议保留一个小型回归集监控边界案例，不把它作为主要优化指标；将更大评测投入放在任务理解、规划分解和编排执行。

当前主链路候选需要增加一个独立模块：**任务规划、分解与编排**。它位于澄清 / 任务组装之后、专业 Agent 执行之前。

#### 外部调研：公开 Data Agent 是否单独评测意图识别

#### 对历史“几乎没有意图错误”的解释

这一现象是合理的，可能同时包含三层原因：

1. 四类标签数量少、语义差异较大，明确表达的单任务本身不难；
2. 历史数据集主要为取数正确性设计，可能更集中于已明确指标、日期和维度的问题，不一定覆盖意图边界；
3. 一些原本被笼统称为“主 Agent 理解错了”的错误，按当前定义应归入澄清、任务分解、工具选择或参数组装，而不是意图分类。

因此，现有证据可以支持“在已有明确表达测试集上，四类主意图不是主要故障点”，暂时不能支持“真实复合请求中的请求理解与编排已经解决”。

#### 现有 200 条是否足够

不能只看总题量，需要先确认这 200 条是否都标注了主意图，以及四类、复合请求和边界请求的分布。

若把每条测试近似看作独立且来自目标分布，使用零失败时的经验上界 `3 / n`：

- 200 条全部零意图错误，只能粗略说明总体真实错误率的 95% 上界约为 1.5%；
- 如果四类平均各 50 条且每类零错误，每类错误率的 95% 上界仍约为 6%；
- 若某个少数类只有 10 条，即使零错误，也几乎不能证明该类稳定。

该计算只是统计直觉；真实测试题往往同源、相似且非独立，覆盖质量比公式更重要。

建议不急于单纯扩充总题量，而是先把现有 200 条补充以下标签并查看分布：

```text
expected_primary_intent
explicit_single_or_composite
clear_or_ambiguous
required_supporting_capabilities
observed_first_error_stage
```

随后单独建立意图边界回归集，重点覆盖：

- “查 A 的值”与“分析 A 为什么下降”；
- “A 是什么业务概念”与“A 指标的计算口径是什么”；
- “查 A 并分析原因”这类显式复合目标；
- 需要结合上文才能判断的省略表达；
- 业务黑话、相近指标、零匹配和多候选；
- 超出能力范围、无法判断或应继续澄清的请求。

汇总时至少报告四类召回率、混淆矩阵、复合 / 歧义子集准确率，而不只报告一个总体准确率。若这些边界题仍基本不出错，意图识别可以保留为轻量回归护栏，把主要评测资源投入后续的澄清、任务规划与编排。

- 外部是否存在意图 / 路由错误：已理解
- 公开结果与本项目指标的可比边界：已理解
- 现有 200 条的意图覆盖是否充分：待验证
- 意图识别的指标定位：已确认不作为重点指标；保留必要的诊断标签、边界回归和失败归因，不单独投入大量评测资源

#### 下一环节候选：需求理解、澄清与任务确定

按主链路顺序，下一项建议讨论“需求理解、澄清与任务确定”。该能力不再重复判断四类主意图，而是判断当前信息是否足以进入后续执行，并把用户需求整理成对应 Agent 可执行的完整任务。

候选能力边界：

```text
已知主任务
-> 提取已有信息
-> 判断 ready / need_clarification
-> 识别缺失、冲突和歧义信息
-> 必要时一次性澄清
-> 合并多轮答案并保持原任务
-> 形成完整任务参数，交给取数 / 分析 / 咨询能力
```

这一环节重点区分三类错误：漏问必要信息、多问不必要信息、虽然完成对话但最终任务参数组装错误。是否将其作为下一项正式闭环，待用户确认。

#### 用户补充：历史项目未单列任务理解指标

用户确认历史项目没有为任务理解单独设置指标，询问行业中通常怎样衡量这一能力。

#### 外部常见做法与本项目映射

任务型对话领域通常不使用笼统的“理解得分”，而是评估模型维护的对话状态。Schema-Guided Dialogue 的代表指标包括：Active Intent Accuracy、Requested Slot F1、Average Goal Accuracy 和 Joint Goal Accuracy。其中，Joint Goal Accuracy 要求一轮中的全部槽位赋值同时正确，最接近本项目“最终任务是否形成正确”。

Data Agent 产品又常把这一层隐含在后续指标中。例如 Snowflake Cortex Agent 使用期望工具名、工具输入和工具输出评估工具选择与工具执行；Databricks Genie 主要评估真实业务问题的最终响应，并允许 Agent 在无法回答时提出澄清问题，但没有公开独立的任务理解指标。

- [Schema-Guided Dialogue 论文中的评测定义](https://cdn.aaai.org/ojs/6394/6394-13-9619-1-10-20200517.pdf)
- [Snowflake Cortex Agent Evaluations](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-evaluations)
- [Databricks Genie 对话行为](https://docs.databricks.com/aws/en/genie-agents/talk-to-genie)

#### Codex 建议：一项主指标加少量诊断指标

为延续项目现有的 Pass / Fail 风格，不建议建立大量平均分。候选主指标为：

**任务形成成功率**：在零轮或若干轮必要澄清后，Agent 形成的最终任务状态与人工标准任务完全一致，并且满足执行门槛的案例比例。

单条案例只有同时满足以下条件才通过：

1. 信息不足或冲突时没有提前执行；
2. 所有必要信息已经获得；
3. 指标、时间、维度、范围、分析目标等适用于本题的任务字段均正确；
4. 没有擅自补充改变任务语义的参数；
5. 多轮澄清后保留原始目标和用户已经确认的信息；
6. 交给后续 Agent 的任务包可以直接执行。

该指标相当于项目版的 Joint Goal Accuracy：整题全部正确才 Pass，不按正确字段比例给部分分。

为了定位失败原因，保留三组诊断指标：

| 诊断指标 | 回答的问题 |
| --- | --- |
| 澄清决策正确率 | 应执行时是否直接执行；应澄清时是否阻止执行并发起澄清 |
| 必要澄清覆盖率与冗余澄清率 | 该问的问题是否问全；不需要问的问题是否被多问 |
| 任务参数正确 / 完整情况 | 最终缺了什么、填错了什么、是否凭空增加参数 |

另将“一次澄清闭环率、平均澄清轮数、Token 与延迟”作为效率指标，不与任务形成正确性混在一起。一次性把可同时发现的缺失信息问全是优选行为，但如果问题本身必须根据上一轮回答才能暴露下一处歧义，不应机械要求只能问一轮。

候选测试仍分两类：

1. **信息已经完整**：验证能否直接形成正确任务，且不多问；
2. **需要澄清**：由固定规则或简单用户模拟器回答，验证是否最终形成正确任务、是否提前执行以及澄清是否冗余。

以上为候选设计，尚待用户确认。

#### 澄清指标进一步收敛

用户认为澄清没有必要设置很多专门指标，提出以“澄清成功率”为主，并询问是否需要同时设置澄清正确率和完整率。

Codex 建议：只将**澄清成功率**作为结果指标；“正确”和“完整”作为单条案例通过的共同条件，不再并列成两个主要指标。

```text
澄清成功率
= 成功完成澄清的案例数 / 确实需要澄清的案例数
```

单条案例必须同时满足以下条件才算澄清成功：

1. 问的是本题真实缺失、冲突或歧义的信息，问题语义正确；
2. 所有阻止任务继续执行的必要信息均已澄清完整；
3. 用户回答后，系统正确吸收答案并恢复原任务；
4. 澄清完成前没有提前执行高风险或不可逆步骤。

因此，“澄清正确率”和“澄清完整率”可以保留为失败分析维度：错问属于正确性失败，漏问属于完整性失败；不必作为对外报告的两个独立 KPI。

为了避免系统通过“凡事都追问”获得较高澄清成功率，另保留一个反向护栏：

```text
无效澄清率
= 信息已经足够却仍发起不必要澄清的案例数 / 信息已经足够的案例数
```

最终候选指标保持为“一正一反”：需要澄清的题看澄清成功率；无需澄清的题看无效澄清率。平均轮数和一次澄清闭环率仅作为效率观察项。

#### 澄清指标最终确认

用户确认：本项目澄清能力直接使用一个**澄清成功率**即可，不再单列澄清正确率、澄清完整率、无效澄清率或轮数等指标。正确、完整、吸收用户回答、恢复原任务以及澄清完成前不提前执行，均作为单条案例是否通过的判定条件；失败后可记录漏问、错问、多问、未吸收答案等原因，但不形成独立 KPI。

- 澄清能力指标：已确认
- 核心指标：澄清成功率
- 计分方式：整条任务 Pass / Fail

### 编排边界校正：不新增统一的主 Agent 编排模块

Codex 曾建议在澄清之后增加“任务规划、分解与编排”环节。用户指出：项目中澄清完成后，分析任务由分析 Agent 自己规划和执行，取数任务也由取数 Agent 自己完成内部编排，不存在一个统一的主 Agent 详细执行链规划环节。

据此校正为两层：

1. **主 Agent 只负责一级交接**：保留主目标和已澄清参数，将任务交给取数 Agent、分析 Agent，或由主 Agent 完成知识 / 口径咨询；这里只检查是否交给了正确能力，不展开专业执行步骤。
2. **专业 Agent 负责内部编排**：取数 Agent 如何查指标和组织查询，归入可信取数能力；分析 Agent 如何取证、选择分析路径、迭代下钻和生成结果，归入数据分析能力。

因此，不再设置一个横跨两类专业 Agent 的独立“任务规划、分解与编排”模块。若发生编排错误，按错误所在 Agent 归因：主 Agent 交错对象属于任务交接错误；取数 Agent 内部步骤错误属于取数失败；分析 Agent 内部步骤错误属于分析失败。

- 独立主 Agent 详细编排模块：撤回
- 下一块：从数据知识咨询、指标口径查询、可信取数和数据分析等实际专业能力中继续选择

#### 轻度执行协调：不单列指标

用户补充：主 Agent 或专业 Agent 仍可能面对轻度协调问题，例如多个独立取数是否并行，以及复合请求中取数与分析的先后关系。但这些问题通常存在多条合理执行路径，不容易为每道任务标注唯一正确轨迹，也不值得专门建立一个编排准确率。

最终处理方式确认如下：

1. 并行或串行本身不判对错，由任务依赖、资源、成本和实现条件决定；
2. 不要求 Agent 命中唯一标准执行顺序，只要求满足必要依赖并完成用户显式目标；
3. 最终数据是否正确由数据准确率覆盖，分析是否成立由分析 / 端到端任务成功率覆盖；
4. 并行带来的收益或浪费通过延迟、成本、工具调用次数等系统指标观察；
5. 只有违反硬依赖、遗漏复合目标、重复调用明显失控，或在无数据证据时提前生成结论，才记录为执行协调失败。

因此，轻度编排不设独立指标，必要时只作为 Trace 中的失败原因标签或效率诊断项。

- 轻度编排是否独立评测：已确认不单列指标

### 专业能力一：业务知识与指标口径咨询

用户确认：业务知识咨询不需要拆出多项指标，只看**业务知识咨询准确率**。测试题提供人工确认的参考答案或必要知识点，最终回答整体正确才 Pass。

```text
业务知识咨询准确率
= 回答正确的业务咨询任务数 / 业务知识咨询任务总数
```

单题判定至少覆盖：回答是否解决用户问题、关键业务事实是否正确、是否与权威知识冲突、是否出现无依据编造。知识库确实没有答案时，能够明确说明无法确定而不是编造，也按该题预设的正确行为判定。

失败后再结合 Trace 做原因归类，不分别建立 KPI：

1. 没有召回正确知识；
2. 没有调用工具或调用了错误工具；
3. 工具输入错误；
4. 已获得正确知识但没有使用；
5. 使用知识时误读、遗漏或改写错误；
6. 知识库没有依据但模型自行编造。

- 业务知识咨询核心指标：已确认
- 核心指标：业务知识咨询准确率
- 计分方式：整条任务 Pass / Fail；过程项仅用于失败归因

#### 指标口径查询并入同一评测方法

用户确认：指标口径查询与业务知识咨询使用相同的评测结构，不再单独展开一套指标。两类任务可统一称为**咨询回答准确率**，并在数据集中保留 `业务知识 / 指标口径` 任务类型，必要时按类型查看结果。

```text
咨询回答准确率
= 正确回答的业务知识与指标口径咨询任务数
  / 业务知识与指标口径咨询任务总数
```

单题仍按 Pass / Fail 判定。指标口径题的参考答案来自权威指标元数据，回答与标准定义、计算逻辑和适用范围一致才通过。业务知识库与指标工具的差异不形成新的结果指标，只在失败归因时区分：知识未召回、指标未匹配、工具未调用或调用错误、获得正确来源后误读，以及无依据编造。

- 业务知识咨询与指标口径查询的评测方法：已确认合并
- 统一核心指标：咨询回答准确率

### 专业能力二：可信取数

#### 用户描述的复杂取数链路

用户以复杂场景说明取数 Agent 的处理过程：先解析 MTD 和比较日期范围，再取得构成目标指标的原子指标；对于比率型指标，分别取得分子、分母，先各自汇总后再相除；如果还要求同比，则分别计算当期与基期结果，再计算变化。

#### 概念校正与标准化表达

“上一个自然月月初至与当期同日”是 MTD 环比基期，不是 MTD 同比基期。假设评估基准日为 2026-08-15：

```text
当期 MTD：2026-08-01 ～ 2026-08-15
MTD 同比基期：2025-08-01 ～ 2025-08-15
MTD 环比基期：2026-07-01 ～ 2026-07-15
```

月底天数不同、当天数据是否完整、业务日还是自然日等情况不能由模型临时猜测，需要由冻结的业务日历和数据时效规则决定。

若目标为比率型指标，正确聚合方式为：

```text
当期比率 Rc = Σ当期分子 / Σ当期分母
基期比率 Rb = Σ基期分子 / Σ基期分母
```

不能先计算各明细行比率后做简单平均，除非指标口径明确规定如此。

一般增长率公式为：

```text
同比或环比增长率 = (当期值 - 基期值) / 基期值
                  = 当期值 / 基期值 - 1
```

如果比较对象本身是比率型指标，还需由指标口径明确用户要的是：

```text
相对变化率 = (Rc - Rb) / Rb
百分点变化 = Rc - Rb
```

两者不能混用。

该类复杂取数任务可标准化为以下可诊断链路：

```text
时间语义解析
-> 当期 / 基期日期范围确定
-> 目标指标拆为原子指标
-> 分别取当期 / 基期原子数值
-> 按目标维度汇总分子与分母
-> 计算当期 / 基期派生指标
-> 计算同比、环比或百分点变化
-> 返回带指标名称、期间和来源的最终结果
```

总体仍只由数据准确率判断整题 Pass / Fail；日期解析、原子取数、聚合方式、派生公式和比较公式保留为失败归因节点。为了能够定位问题，复杂题的标准答案除最终数值外，还应冻结当期 / 基期日期范围、原子指标值和公式版本，但这些不新增独立业务 KPI。

### 剩余模块与指标压缩盘点

用户提出：前述业务能力最终基本都只看准确率，希望一次盘点剩余需要讨论的内容；如果都可以使用一个准确率，就不再逐项展开。

Codex 当前建议统一采用一套计分形式：

```text
某类任务通过率 = 该类整题 Pass 的任务数 / 该类有效任务总数
```

有唯一标准答案时称“准确率”；存在多条合理路径、需按 Rubric 判断完成情况时称“任务成功率”。二者计算形式相同，差别只在单题判定依据。

| 剩余模块 | 最小结果指标 | 是否还需要专门讨论 | 主要原因 |
| --- | --- | --- | --- |
| 数据分析 | 分析任务成功率 | 需要 | 分析没有唯一答案，需要确认 Pass / Fail Rubric、证据要求和允许的等价分析路径 |
| 报告与可视化 | 可并入分析 / 端到端任务成功率 | 可快速收口 | 图表数值、结论、来源和用户要求任一关键项错误则整题 Fail；美观只在确实有产品要求时另做人工验收 |
| 跨会话连续性与记忆 | 跨会话任务成功率 | 需要简要确认测试场景 | 不仅要正确记住，还要正确更新、忽略不该使用的信息并避免跨用户泄露 |
| 定时任务与主动交付 | 定时任务成功率 | 需要简要确认测试装置 | 一题通过需同时满足按时触发、结果正确、成功交付和不重复执行 |
| 工具异常恢复 / 降级 | 故障注入子集的任务成功率 | 不设独立业务指标 | 在正常任务中注入超时、空结果、限流等故障，仍按最终任务是否完成判定，并记录恢复原因 |
| 权限与安全 | 安全违规率 / 硬门槛 | 需要确认边界 | 低概率严重违规不能被总体平均准确率掩盖 |
| 稳定性 | 重复运行成功率、系统错误率 | 属于横向指标 | 同题多次运行或长时间运行是否稳定，不等同于答案准确率 |
| 延迟 | P50 / P95 延迟 | 属于横向指标 | 衡量响应和交付速度 |
| 成本 | 单任务平均成本及 P95 | 属于横向指标 | 衡量模型、Token 和工具调用消耗 |
| 可观测性 | 关键 Trace / 字段记录完整性 | 更接近验收条件 | 决定失败能否被定位，不是用户任务正确率 |

按此压缩后，真正值得继续讨论的业务内容只剩三项：

1. 数据分析任务怎样判 Pass / Fail；
2. 跨会话记忆题怎样构造；
3. 定时任务怎样模拟时间、触发和交付。

报告与可视化可以并入分析 / 端到端判定；异常恢复可以并入故障注入子集。横向层只需最后确认安全、稳定性、延迟和成本的口径与门槛。以上为盘点草案，尚待用户确认。

### 专业能力三：数据分析

#### 用户确认的分析任务分类

分析任务分为两类：

1. **固定分析任务**：存在预设或明确指定的分析方法；判断是否使用正确方法、查询数据是否准确、生成图表是否正确。
2. **开放分析任务**：不规定唯一分析思路；判断数据是否准确、图表是否正确。分析思路本身不做优劣评判，只要不是无依据编造、明显违背数据或逻辑即可。

#### 指标收敛

两类任务统一使用一个主指标：

```text
分析任务成功率
= 通过的分析任务数 / 有效分析任务总数
```

报告时可以按 `固定分析 / 开放分析` 查看子集结果，但分析方法正确率、数据准确率和图表正确率不再各自形成新的 KPI，只作为整题通过条件和失败原因。

固定分析任务的单题通过条件：

1. 使用任务指定或标准答案要求的分析方法；
2. 方法所需的数据查询正确；
3. 必要计算和图表数据正确；
4. 图表中的时间、指标、维度、图例和数据表达不产生错误或误导；
5. 最终文字结论不与数据和图表冲突。

开放分析任务的单题通过条件：

1. 使用的数据查询正确；
2. 必要计算和图表正确；
3. 事实性结论能够由数据、图表或已取得的业务知识支持；
4. 不把未验证假设写成事实，不出现与证据冲突的解释。

开放分析明确不评：是否命中一条预设的唯一分析路径、分析思路是否最优、是否得出与参考答案完全相同的洞察。不同但有证据支持的分析路径均可通过。对于原因分析，可以把未验证方向明确标注为“假设 / 待验证”；若直接编造成已经成立的原因，则整题失败。

- 分析任务分类：已确认
- 核心指标：分析任务成功率
- 固定分析判定：方法、数据、图表和结论底线全部通过
- 开放分析判定：不评思路优劣，只检查数据、图表与基本证据可信性
- 报告与可视化：并入分析任务判定，不单列 KPI

#### 数据分析历史评测实施补充

用户补充并确认的历史做法：

- 分析离线题量不大，每一种分析大约只有 5 道题；具体分析类型数量与总题量尚未核实；
- 固定分析任务有人工参考答案；
- 开放分析任务没有参考答案；
- 测试运行到报告生成结束，最终报告中包含数据和图表；
- LLM Judge 只查看最终报告并做判断；
- 历史分析任务成功率约为 70%；
- 另一个数据准确率结果在 90% 以上；
- 分析能力后续迭代主要依赖线上问题，逐个排查失败 Case，而不是持续扩充离线分析集。

据此，历史测试流程可以写为：

```text
少量人工分析题
-> 运行分析 Agent 直到生成含数据和图表的最终报告
-> 固定分析：Judge 将最终报告与参考答案比较
-> 开放分析：Judge 无参考答案地检查报告
-> 输出 Pass / Fail
-> 汇总分析任务成功率
-> 线上问题继续沉淀并逐 Case 定位改进
```

这里需要保留一个验证边界：开放分析没有参考答案，且 Judge 只看最终报告，因此它能够判断报告是否自洽、图文是否明显冲突、结论是否明显无依据，但不能仅凭最终报告独立证明其中数据来自正确查询。历史项目中“数据准确率 90% 以上”来自数据准确率评测，不能直接替代每一道开放分析题的数据 Ground Truth。

若未来改进开放分析评测，可将分析 Agent 使用的结构化数据结果或数据 Trace 一并提供给 Judge，用于验证报告中的数据与证据一致性；这是改进建议，不代表历史实现。

当前仍待核实：每种固定 / 开放分析的具体类型与总题量、Judge 模型 / Prompt、70% 和 90% 对应的题集版本与运行报告。

### 用户校正：不能只确定指标，必须闭环测试方法

用户指出：本轮讨论目标不是只为每个能力取一个指标名称，还需要确定怎样评价、怎样执行测试任务、怎样验证，以及怎样计算指标。即使多个能力最终都用“准确率 / 成功率”，其数据集、环境、运行流程和验证器也不同，不能因此一次性只确认指标后跳过测试设计。

Codex 接受该校正。后续每个能力至少使用以下最小评测卡闭环：

| 项目 | 必须回答的问题 |
| --- | --- |
| 1. 被测能力与通过条件 | 这项能力测什么；单条任务什么情况下 Pass / Fail |
| 2. 测试任务与标准答案 | 题从哪里来、覆盖哪些类型；标准答案或 Rubric 包含什么 |
| 3. 测试执行方式 | 怎样初始化环境、向 Agent 输入什么、工具和数据使用哪个版本、是否需要用户模拟器、何时结束 |
| 4. 验证方式 | 使用程序、LLM Judge 还是人工；验证器能够看到最终答案、任务状态、工具结果或 Trace 中的哪些证据 |
| 5. 指标计算与报告 | 分子、分母、无效运行怎样处理；是否按任务类型拆分；失败原因怎样记录 |

失败归因仍是必要的调试信息，但不必为每个失败节点增加 KPI。

按这张最小评测卡重新检查当前进度：

| 能力 | 已经确认 | 尚未闭环 |
| --- | --- | --- |
| 可信取数 / 数据准确率 | 200 条人工标准、冻结日期版本；单轮和模拟澄清；复杂题型；LLM Judge；整题 Pass / Fail；计算公式 | Judge Prompt / 模型版本等复现信息仍待核实，但高层评测方法基本完整 |
| 澄清 | 澄清成功率和单题通过条件 | 澄清题怎样构造、隐藏完整任务怎样保存、用户模拟器怎样回答、Judge 看什么仍需设计 |
| 业务知识与指标口径咨询 | 咨询回答准确率和失败归因 | 题库来源、知识库 / 指标元数据快照、参考答案结构、Judge 运行流程仍需设计 |

因此，除可信取数外，前面几项目前只是“指标与能力边界已确认”，不能表述为完整评测方案已经收口。下一步应按最小评测卡逐项补齐执行与验证方法。

### 历史实施补充：澄清与咨询类隔离测试

#### 取数澄清测试

用户回忆：项目初期曾对取数任务的澄清能力做独立测试，覆盖单个指标和多个指标的澄清。测试集约为 50 题，但用户使用了“应该是”的表述，因此精确题量仍待历史材料核实。

已确认的历史流程：

```text
人工梳理隐藏目标
-> 向被测 Agent 发送不完整的首轮用户问题
-> 便宜模型扮演用户回答澄清问题
-> 被测 Agent 继续询问或调用任务提交工具
-> 提交成功，或超过最大交互轮次后停止
-> 检查最终传给数据 Agent 的任务内容
-> LLM Judge 判定整题 Pass / Fail
```

用户模拟器获得的信息包括：首轮用户问题，以及用户最终想查询的指标语义；模拟器不会直接得到真实标准指标名称，以免把答案泄露给被测 Agent。对于多指标题，隐藏目标包含多个待确认指标的语义。

该隔离测试的观察终点是被测 Agent 调用任务提交 / 交接工具，并将澄清后的任务传给数据 Agent，而不是等待数据 Agent 真正完成取数。工具可以验证调用是否满足接口要求；语义层面再由 LLM Judge 判断提交内容是否与隐藏目标一致。

候选单题通过条件可据此收敛为：

1. 在最大允许轮次内完成任务提交；
2. 提交工具调用通过接口校验；
3. 传给数据 Agent 的单个或多个目标指标，与隐藏指标语义一致；
4. 没有遗漏、多加或错误替换目标；
5. 对话中获得的其他必要条件被正确写入交接结果。

```text
澄清成功率
= 在轮次上限内正确提交任务的案例数
  / 有效澄清测试案例总数
```

仍待历史材料核实：精确题量、最大轮次、提交工具名称和字段、接口校验规则、LLM Judge 模型与 Prompt、当时的实际成功率。

#### 业务知识与指标口径咨询隔离测试

用户补充：业务知识支持和指标口径查询在开发初期也分别由人工梳理问题形成数据集，并做过单独测试。其结果由参考内容与 LLM Judge 判断；但当前尚未确认题量、题型分布、知识库 / 指标元数据版本、Judge Prompt 和历史结果。

用户进一步补充并确认的历史实现：

- 业务知识与指标口径咨询题量不大，合计约 20～50 题；题目和参考答案均由人工整理；
- 业务知识来源是一份由业务人员梳理的知识文档；
- 指标口径与指标元数据通过接口查询；
- LLM Judge 只查看最终回答并与人工参考答案比较；
- 如果回答错误，再检查知识 / 指标内容是否已经成功召回，以区分召回问题与生成使用问题；
- 用户回忆历史准确率接近 100%，但当前没有运行报告或原始结果用于核验，因此只记录为用户口述历史结果。

据此，该能力的历史高层评测卡已经基本闭环：人工小题集与参考答案 -> 连接业务知识文档和指标接口运行 -> Judge 只评最终回答 -> 错题查看 Trace / 召回 -> 计算整题准确率。仍缺的主要是精确题量、题集版本、Judge 模型 / Prompt 和可核验的历史结果。

#### 从能力隔离测试转向端到端回归

上述澄清、业务知识和指标口径测试主要服务于项目初期的能力开发与定位。后期不再持续单独关注这些能力指标，而是直接运行端到端测试；遇到失败后再检查具体 Case 和 Trace，判断错误发生在澄清、知识召回、口径工具、取数、分析或报告环节。

当前可将历史评测策略概括为：

```text
开发初期：人工小题集 -> 能力隔离测试 -> 快速定位与调试
系统成型后：端到端基准 -> 整题 Pass / Fail -> 失败 Case 回溯归因
```

这两阶段不是相互替代：隔离测试适合开发某项能力和固定回归；端到端测试用于判断真实任务最终是否解决。历史项目后期以端到端为主是用户确认的事实，是否仍保留少量自动隔离回归题作为现行推荐，尚待决定。

#### 跨会话连续性与记忆

测试题主要来自线上已有记忆和原会话内容：先选择线上已经产生记忆的历史会话，再根据之前提到的信息设计后续问题。题量约 10 题；用户回忆跨会话连续成功程度在 90% 以上，但使用了“大概 / 应该”的表述，当前未取得题集和运行结果核验。

历史高层流程可还原为：

```text
选择已有线上会话及已写入记忆
-> 根据原会话设计后续问题
-> 在后续会话向 Agent 提问
-> Agent 检索并使用已有记忆回答或继续任务
-> 判断是否正确续接上下文
-> 计算跨会话连续成功率
```

```text
跨会话连续成功率
= 正确使用已有记忆完成续接的案例数
  / 有效跨会话测试案例数
```

该测试主要证明“已有记忆的读取与使用”，不能自动证明记忆写入、错误记忆纠正、冲突更新、应遗忘信息处理或跨用户隔离。历史验证者、精确 Pass / Fail Rubric、题量和 90% 以上结果仍待材料核实。

历史测试与运行流程：

```text
每日定时触发
-> 执行数据与分析任务
-> 生成报告文档
-> 生成报告摘要
-> 向群聊发送摘要消息
-> 检查任务和交付是否成功
```

用户口述定时任务测试与运行结果为 100% 成功；当前未确认统计周期、计划运行次数、失败重试是否计入，以及该 100% 是仅指触发 / 交付链路还是同时包含报告内容正确。

建议在记录中区分两层历史事实：

1. **定时交付成功率**：应运行的每日任务中，按期完成报告文档与群消息交付的比例；用户口述为 100%。
2. **报告与告警业务效果**：报告内容正确性可以验证，但“是否足够好、告警是否有用”没有固定离线指标，主要根据业务实时反馈持续调整。

```text
定时交付成功率
= 按要求完成报告与群消息交付的计划任务数
  / 应执行的计划任务总数
```

报告内数据与分析正确性沿用数据准确率和分析任务成功率，不重复建立新的定时任务内容准确率。

### 正确的讨论单元

每次只选择一项能力，并使用同一张“能力评测卡”把它闭环：

1. **能力定义**：系统在什么输入和边界下，应做出什么可观察行为；
2. **基准任务**：用哪些类型的测试任务覆盖正常、歧义、边界和失败场景；
3. **任务来源**：历史真实问题、生产失败、人工设计、参数化生成各占什么作用；
4. **环境扮演者**：用户、上下文、指标平台、数据库、工具、故障和人工角色怎样提供状态与反馈；
5. **验证器**：结果、状态、工具参数、轨迹、安全约束分别怎样判定；
6. **测试流程**：怎样初始化、运行、交互、终止、记录和回放；
7. **评估指标**：能力得分、关键失败率、稳定性、延迟与成本怎样报告；
8. **通过边界**：什么证据只能说明局部能力，什么证据才能说明端到端可用。

“基准”不再作为脱离能力的第一项单独设计，而是每项能力对应的一组可重复任务与验证装置。

### 能力边界第一轮校正

#### 用户理解

1. 意图识别、路由、澄清和任务理解可能属于同一个能力。
2. 数据咨询和指标口径应拆成两个能力：前者对应知识库，后者对应查询工具。
3. “可信取数”可以理解为取数准确性。
4. 分析方法选择 / 规划与分析执行 / 下钻可以先合成一个分析能力。
5. 报告生成包括画图、报告效果，以及一个语音转写为“素颜”的要素；Codex 推测可能指“溯源”，尚待用户确认。
6. 跨会话连续性和记忆有效性可以合成一个能力。
7. 用户暂不理解“工具异常恢复、降级与人工介入”具体指什么。
8. 定时任务可以作为一个独立能力。

#### Codex 反馈草案

- 从用户任务角度，意图识别、任务理解、路由和澄清可以合成“请求理解与任务形成”这一项完整能力；评测时仍要保留意图、槽位、路由和澄清决策四个子标签，否则失败后无法定位原因。
- 数据知识咨询与指标口径查询可以分开评测，因为二者依赖的数据源、工具路径和 Ground Truth 不同。知识库或查询工具是实现机制，不是能力名称本身。
- “取数准确性”是评估指标，不是完整能力定义。“可信取数”还需要覆盖指标 / 字段、时间、维度、过滤、权限、查询执行、结果校验和证据保真。
- 分析方法选择、任务规划、执行和迭代下钻可以先合成一个“数据分析”能力，并在验证器中保留过程子分。
- 报告与可视化可以合成一个输出能力，候选子维度包括结构完整性、图表选择、数值一致性、标准指标身份、证据溯源、结论支持度和可读性。
- 跨会话连续性与记忆有效性可以合成一个顶层能力，但需用“跨会话事实保持、偏好使用、历史分析复用、冲突更新、错误记忆隔离”等不同测试组诊断。
- 工具异常恢复、降级与人工介入更适合作为注入到取数、分析和定时任务中的横向可靠性场景，而不是独立的用户业务能力；除非系统确实把它实现为可独立调用的恢复 Agent / 能力。
- 定时任务有独立的触发、幂等、数据新鲜度、失败重试和交付状态，适合保留为独立能力。

### 能力一：需求理解与任务确定

用户确认按能力逐个分析。当前先确认这项能力的测试边界，不提前确定题库、验证器或通过阈值。

#### 能力边界候选

| 方案 | 通过条件 | 边界 |
| --- | --- | --- |
| A. 只测意图与路由 | 正确分类并选择下一能力 | 不能证明具体任务条件已经理解正确 |
| B. 测到可执行任务或正确澄清 | 正确识别任务类型、提取必要条件，并输出“直接执行 / 集中澄清 / 不支持”之一 | 不要求真正查询数据或生成最终回答 |
| C. 测完整最终回答 | 从用户输入一直执行到最终结果 | 会把理解、取数、分析和报告错误混在一起 |

Codex 当前建议 B。该能力的可观察终点是以下三种状态之一：

1. 形成结构化、可执行的任务并路由到下一能力；
2. 识别全部关键缺失或冲突信息，并发起一次集中澄清；
3. 判断请求不在能力范围内，进入能力探索 / 重路由或明确拒绝。

“可执行任务”候选字段包括：任务类型、业务对象、标准指标或候选指标、时间范围、维度、过滤条件、比较基准、分析目标和交付要求。具体哪些字段是每类任务的必填项，尚待后续按任务类型确认。

#### 用户进一步校正

用户认为这项能力当前没有现成“基准”，并将它拆成两部分：

1. **意图识别**：判断用户请求是分析任务、纯取数任务还是咨询任务；
2. **按意图理解并补足下一步所需信息**：
   - 取数任务需要识别指标名、日期、维度、指标数量及具体指标；
   - 分析任务需要判断用户希望进行什么分析；
   - 咨询任务需要判断应获取哪类知识或使用哪个查询工具。

用户同时指出，咨询场景中的实际知识获取或工具查询有一部分属于后续能力；当前能力主要验证是否已经获得进入下一步所需的充足信息。

#### Codex 校正与收敛

这里不需要寻找外部公开 Benchmark。当前更准确的名称是“需求理解内部评测集”或“能力测试集”。只有当任务、输入、期望状态、环境、验证器、版本和重复运行协议固定后，它才成为项目内部可重复比较的 Benchmark。

第二部分不宜只命名为“澄清能力”，因为：

- 信息充分时，应直接生成下一步任务参数，不应为了测试澄清而强行追问；
- 信息不足、冲突或存在多个合法解释时，才触发澄清；
- 因此更准确的名称是“任务参数理解与完备性判断”，澄清只是其中一种动作。

该能力暂收敛成两个子能力：

1. **意图识别与一级路由**：输出 `取数 / 分析 / 咨询`；对未知或不支持请求保留 `无法确定 / 不支持` 边界。
2. **任务参数理解与完备性判断**：按意图生成下一步所需结构化参数；若参数不足，则输出缺失 / 冲突字段及集中澄清问题。

咨询分支在本能力中的终点是：区分数据知识咨询与指标口径查询，并形成查询主题或指标对象。知识库是否召回正确内容、指标工具是否返回正确口径，留到后续对应能力评测。

#### 四类意图与复合任务：用户补充

用户确认项目中的意图共四类：

1. 取数；
2. 业务知识咨询；
3. 分析；
4. 口径查询。

真实问题通常可能是复合任务。典型流程是：用户希望查询某个指标，但系统没有唯一匹配到标准指标，或者匹配到多个相似指标；系统需要向用户介绍候选指标分别解决什么问题、怎样计算，再让用户确认具体目标，确认后继续原取数任务。

#### Codex 反馈：从单标签分类改为主目标与能力链

四类意图不能只按互斥单标签分类评测，需要区分两种复合情况：

1. **用户显式提出多个目标**：例如“查询 A 指标，并分析它为什么下降”；主任务包含取数与分析。
2. **完成主目标所产生的支撑子任务**：例如用户只想查询 A 指标，但指标消歧需要临时进入口径查询和用户确认，之后再返回取数。

因此候选理解结果应至少表达：

```text
primary_goal
explicit_goals
supporting_steps
current_state
resume_target
```

以指标消歧为例：

```text
主目标：取数
当前状态：指标未唯一确定
支撑步骤：查询候选指标口径 -> 解释差异 -> 用户确认
恢复目标：携带已确认 metric_id 返回原取数任务
```

这一流程的评测不能只检查“是否分类为取数”，还需要检查：

- 是否保留原始取数目标和其他已确认参数；
- 是否发现指标未匹配或多候选；
- 是否调用了正确的口径查询能力；
- 是否完整、忠实地说明候选指标的用途和计算口径；
- 是否在用户确认前阻止正式取数；
- 用户确认后是否绑定正确的标准指标 ID，并恢复原任务而不是丢失上下文。

为了区分 Agent 编排错误与指标工具错误，后续测试应分两层：

1. **隔离评测**：使用固定的模拟指标元数据工具，专门验证候选解释、确认门槛、状态保存和任务恢复；
2. **集成评测**：连接真实或脱敏的指标查询工具，验证完整指标检索与消歧链路。

以上为讨论草案，尚未确认成正式测试结构。

#### 指标未唯一匹配的两条真实路径

用户进一步确认两种不同情况：

1. **完全搜不到指标**：第一次指标检索为零命中；大模型根据用户表达和上下文，尝试寻找近似指标。
2. **直接搜到多个相近指标**：指标查询返回几个很接近的标准指标，需要介绍差异并让用户确认。

Codex 将两条路径整理为：

```text
用户指标表达
└── 首次指标检索
    ├── 唯一权威匹配 -> 绑定标准指标 -> 继续原任务
    ├── 多个近似匹配 -> 查询并解释候选口径 -> 用户确认 -> 继续原任务
    └── 零匹配 -> 模型生成近义词 / 业务对象 / 搜索条件 -> 再次检索
        ├── 找到近似候选 -> 标记为候选并解释 -> 用户确认 -> 继续原任务
        └── 仍无候选 -> 明确无法确定，向用户索取更多信息或安全停止
```

安全边界草案：模型可以负责理解用户表达、生成搜索关键词和选择下一次查询策略；候选指标、定义、公式、适用范围和标准指标 ID 必须来自权威指标元数据工具。没有来源的模型记忆不能作为标准指标事实。

两条路径应使用不同的诊断指标：

| 路径 | 主要验证点 |
| --- | --- |
| 零匹配后近似探索 | 搜索改写是否合理、目标指标是否进入候选集、探索轮次是否受控、仍无结果时是否安全停止 |
| 多候选消歧 | 候选是否完整、介绍是否忠实于元数据、差异是否足以帮助选择、是否等待用户确认 |

共同验证点包括：原任务参数保持、确认前不执行、确认后绑定正确 `metric_id`、恢复原取数 / 分析任务。

待确认边界：如果零匹配后只找到一个近似候选，因为它不是权威的唯一匹配，Codex 建议仍向用户确认，而不是自动当作标准指标执行。

## 发散联想

- 现有材料中的场景险 100 题、27 道分级题、平台 500+ 题和 Benchmark 2.0 的 2,000 题规划不是同一个评测集，不能合并题量或准确率。
- 自动生成的 L1 标准指标直查题适合做取数子基准，但不能自动证明多轮澄清、开放分析、报告证据和异常恢复能力。
- 离线标准题适合验证能力与回归；生产 Trace 适合发现真实分布和未知失败；高价值失败可以脱敏后沉淀为回归题。
