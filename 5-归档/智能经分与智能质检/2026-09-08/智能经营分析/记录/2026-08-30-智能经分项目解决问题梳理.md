# 2026-08-30 智能经分项目解决问题梳理

## 原始问题

智能经分项目究竟解决了哪些问题？如何把项目的功能覆盖转换成清晰、可追问的业务问题表达？

## 用户理解

> 第一点是取数。取数覆盖了 100 多个原子指标，覆盖了核心分析需要的所有指标；有 100 多个维度，每一个指标通常会支持 10 个维度左右。
>
> 第二点是分析，分为保费、渗透率、渠道归因、用户留存归因。

### 追加口述：平台查数和文档阅读的参数问题

> 用平台查数和看文档时，有些参数会导致它默认只看到第一页或前 200 条数据，但我们实际需要更多。AI 用不好这一部分参数。

当前确认的现象是：平台查数与文档阅读都可能因默认参数只返回部分内容，AI 未能稳定地修改参数或继续获取后续内容。具体平台、工具、参数名、最大值和是否存在翻页标记尚待核对。

### 追加口述：大量查询结果直接进入上下文

> AI 会直接把返回的大量数据全部加载到上下文里去读，导致上下文爆炸并且混淆。解决方案是返回的数据只看预览，主体存到文件里，后续的聚合统计直接进行文件操作。

严格的机制表达是：模型上下文只接收小量预览、数据结构、总条数以及文件引用；全量数据作为文件资产保存；后续聚合、过滤和统计由代码或数据处理工具直接读取文件执行，最后只把结构化汇总和必要样例返回模型。

### 用户确认的实际实现

1. 工具参数由开发者固化为“获取全部数据”，不向 AI 暴露或交由 AI 选择“只获取 200 条”之类的参数。
2. 全量查询结果保存为文件，不整体注入模型上下文。
3. AI 只抽样阅读前 200 行，用于判断数据格式和内容是否明显异常。
4. 下游聚合和统计直接读取全量文件执行，不依赖模型对明细逐行计算。
5. 统计完成后，AI 再检查聚合结果的合理性。
6. 平台本身提供全量文件的导出 / 下载接口；项目调用该接口后直接下载文件，下载文件就是完整数据。因此项目不依赖 AI 自行翻页来构造全量结果。

该方案当前作为用户确认的项目实现记录；具体工具名、参数名和文件格式尚未记录，但不影响当前对完整链路的理解。

### 用户确认的指标匹配与时间处理方案

#### 指标匹配

1. 模型先从用户问题中拿到用户需要的指标表达。
2. 优先使用用户原始表达到指标库检索和匹配。项目没有为“用户原话优先”专门设计 Prompt。
3. 如果能与指标库中的标准指标完全匹配，则确定指标身份并继续。
4. 如果无法完全匹配，指标库返回语义接近的标准指标候选。Agent 展示完整标准指标名，询问用户是否要查询该指标。
5. 如果用户原始表达没有查出合适结果，模型再按自己对用户意图的理解重新组织查询词检索。
6. 实际多数情况能找到候选指标，然后由用户在候选中确认最接近的指标。

这是“检索定位标准身份 + 候选澄清”，不是模型凭内部知识直接生成一个指标名。

#### 相对时间与日期范围

- 所有相对时间和具体日期范围都由脚本计算和返回。
- 模型不自行心算“本周、上周、近一周、同比、环比”对应的起止日期。
- 目前已确认确定性日期脚本这一机制；自然语言时间表达如何被转成脚本参数尚未在本轮展开。

#### 业务事件与指标适用性：已有缓解措施

- 这是在指标身份匹配机制之后才暴露的新问题：标准指标能够正确匹配、查询和计算，但仍可能不适用于当前业务问题。
- 已有做法是：当 Agent 判定用户的请求属于某类分析问题时，同时给出该类分析推荐使用的指标。
- 推荐关系的实际载体是“分析方法知识库”：每种分析方法的知识中会提到应使用哪些指标。
- Agent 命中并读取对应的分析方法知识后，获得推荐指标，并以此引导后续的指标选择和分析。
- 该做法能将模型和用户引导到常见、较合适的指标集合，降低任意选择指标的概率。
- 用户明确认为这只能缓解问题，不能完全解决业务事件与指标的适用性。

#### 指标、维度与维度值的拆分和标准化

用户给出的具体案例是：

> 查询上周新商餐饮渗透率。

这个问法不能只提取一个“渗透率”就直接查询，还需要回答：

- “渗透率”对应哪一个标准指标；
- “新商”属于哪一个标准维度，对应什么标准维度值；
- “餐饮”属于哪一个标准维度，对应什么标准维度值；
- “上周”对应什么确定的起止日期。

用户确认的解决方案是：

1. AI 先将用户问题拆分成指标、维度 / 维度值和时间三类要素。
2. 指标表达单独到指标库检索，确定标准指标。
3. “新商”、“餐饮”等维度值表达分别到维度库检索，确定它们属于哪个标准维度及对应标准值。
4. “上周”继续使用确定性时间脚本转换为起止日期。

用户进一步确认，指标库中的一个指标不仅提供标准身份，还能同时返回：

- 该指标支持的维度；
- 该指标应从哪个数据集查询；
- 该指标支持的查询方式。

因此指标库在项目中实际承担的不只是指标名检索，还包含指标的维度契约与查询路由元数据。

当用户要求的维度不在该指标的支持维度中时：

1. AI 根据指标库、维度库和时间脚本返回的元数据，自行组装完整的查数参数。
2. AI 将组装好的参数交给取数引擎执行。
3. 当指标—维度组合不支持时，系统 / 取数引擎将“该维度不支持”的信息返回给 AI，而不返回正常查数结果。
4. AI 向用户解释当前指标不支持该维度。
5. AI 再根据已知的指标、支持维度和查询方式，向用户推荐其他可行方案。

这形成“知识 / 元数据提供可用契约，AI 组装参数，取数引擎执行并返回能力边界，AI 解释错误并选择恢复路径”的分工。

严格的结构化表达可写成：

```text
MetricSpec
  - canonical metric
  - supported dimensions
  - dataset / query route
  - supported query method
FilterSpec[]
  - canonical dimension
  - canonical dimension value
TimeSpec
  - start date
  - end date
```

当前只记录项目的实际拆分与检索机制，不自行补充“新商”和“餐饮”对应的具体标准维度名。

当前先将项目解决的问题分为两层：

1. 取数：让核心经营指标可以按适用维度查询。
2. 分析：在已取得的数据之上，按四类业务分析方向解释经营现象。

## Codex 反馈

- “100 多个原子指标、100 多个维度、单指标通常支持约 10 个维度”目前是用户口述的覆盖范围，尚未核对统计口径。
- “100 多个维度”可能是全局维度池，“每个指标约 10 个维度”可能是单指标的适用维度子集；这一关系需用户确认。
- 当前说法主要描述了“系统有什么能力”，还不足以完整说明“项目解决了什么问题”。还需补充引入 Agent 前的原流程、受阻人群、核心痛点及可核对的改变。
- “保费”暂按用户原话保留，不自动改为“保费分析”或“保费归因”。
- 本轮给出的四类为“保费、渗透率、渠道归因、用户留存归因”；此前记录中的口述名称存在语音转写不确定性，后续应以用户本轮确认的正式名称为准。
- “默认只有第一页或前 200 条”不应只归类为普通工具调用失败。工具可能成功返回一个形式正常但不完整的结果，Agent 若没有检查总条数、页码、续页标记或结果完整性，就可能将局部数据当成全量证据。这属于“静默的数据完整性失败”。
- 将全量表格文本直接注入 LLM 上下文，不仅会带来 Token 和上下文窗口压力，还会让大量相似行淹没任务要求、指标定义和关键异常。这是“大结果集上下文污染”，不是单纯的模型窗口不够大。
- 分页问题和大结果集问题是一组需要同时约束的数据传输边界：底层必须获取完整数据，但模型上下文不应承载全量数据。
- “前 200 行预览”能发现列缺失、格式错乱、单位异常和明显的空值等问题，但不能单独证明全量数据准确或完整。如果数据按时间、地域或业务类型排序，前 200 行还可能存在系统性的抽样偏差。
- 该项目的全量完整性主要来自平台导出 / 下载接口的契约：项目下载完整文件，而不是将分页预览结果拼接成全量。总行数、查询完成状态或校验和可作为额外的运行时防护，但不是已确认实现的前提。
- “完全匹配就没问题”只能理解为“指标标准身份已确定”。它不能证明该指标适用于当前业务事件；此前新人错误汇报事故已证明，合法且可查的指标仍可能选错。
- 候选澄清解决的是“用户到底指的是哪个标准指标”；事件—指标适用性解决的是“这个业务问题应不应该用该指标”，二者不能合并。
- “分析类型 → 推荐指标”仍然是软引导，不是适用性证明。它不会自动覆盖：分析类型本身判错、同类分析下不同业务事件使用不同指标、新业务未进入推荐集、用户坚持使用非推荐指标等情况。
- 因为推荐指标存在于分析方法知识中，所以它还依赖三个前提：分析方法被正确命中，对应知识包含完整且最新的推荐指标，Agent 实际按该知识执行。它是知识驱动的软约束，不是运行时强制校验。
- “新商”和“餐饮”在用户口语中更像维度值或业务标签，而不是完整的标准维度名。因此维度库不仅要检索“有没有这个词”，还要返回“它属于哪个维度字段、标准值是什么”。
- 指标库已具备“该指标支持哪些维度”的元数据，并会在组合不支持时向 AI 返回明确的不支持信息。确定性部分是“该组合不可用”；由 Agent 负责的是如何向用户说明，以及推荐哪一条替代路径。
- 数据集和查询方式也来自指标库，这使标准指标身份可以继续决定后续的数据路由，而不需要模型脱离元数据自行选表或猜测查询方式。
- 上一条不代表普通代码会替 AI 生成最终查数参数。实际上是 AI 基于这些受控元数据组装参数，然后交给取数引擎；不能将这条链路误述为“工具全自动生成 QuerySpec”。
- 因此对外表达应写成“按分析类型推荐指标，缓解非专家选错指标”，不能写成“完成了业务事件—指标的完整语义层和强校验”。

### 智能经分项目直接问题

| 问题 | 当前已有做法 | 为什么还没有完全解决 |
| --- | --- | --- |

| 多轮追问上下文丢失 | 当前尚未确认稳定解法 | Q06 中追问未正确继承上一轮的分析对象、数据来源和限定条件 |

| 分析方法与业务知识长尾 | 商分方法沉淀为 Skill / 分析方法知识 | 评测中仍有分析方法、指标口径、业务知识缺失和稳定错路由；开放分析未命中知识时可能生成不可靠内容 |
| 长周期与复杂查询性能 | 历史数据缓存、当日数据更新 | 真实案例仍有十几分钟、几十分钟乃至 2 小时以上的任务；缓存命中范围、失效和并发首查仍未完整复盘 |

### 主要属于统一平台的共性问题

- 认证和权限在无人值守任务中失效；
- API / MCP / 工具路径漂移；
- 同一根因被反复重试，缺少停止条件；
- 报告、文档或消息生成后，交付尾端仍可能失败。

这些问题来自平台级 Trace，可以作为项目所处底座的背景，但不能全部写成场景险智能经分项目自身的失败。
