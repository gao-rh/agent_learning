### 第四批：保费链路分析逻辑拆解

来源：O04。原文完整保存了指标名称、三因子 Shapley 闭式公式、目标 Gap 算例、话术模板与常见场景；以下为结构化整理和公式核查。

#### 核心业务链路

统一公式为：

> `P = A × R × Q`

- `P`：保费。
- `A`：单均保费。
- `R`：订单渗透率。
- `Q`：订单基数。

| 险种 | P | A | R | Q |
| --- | --- | --- | --- | --- |
| 放心吃 | 放心吃净保费规模 | 放心吃单均保费 | 放心吃餐饮订单渗透率 | 外卖餐饮订单量（不含取消单） |
| 准时宝（商家付费） | B 端准时宝净实收保费（商家付费） | 对应单均保费 | 对应餐饮订单渗透率 | 外卖餐饮订单量（不含取消单） |
| 准时宝（平台采购） | B 端准时宝净实收保费（平台采购） | 对应单均保费 | 对应餐饮订单渗透率 | 外卖餐饮订单量（不含取消单） |
| 取消险 | 取消险净实收保费 | 取消险单均保费 | 取消险餐饮订单渗透率 | 外卖餐饮订单量 |

O04 明确区分：放心吃 / 准时宝的 `Q` 是非取消订单量，取消险的 `Q` 是全量订单量。因此取消率上升会直接缩小前两类险种的分母基数，但按该材料定义不会缩小取消险的 `Q`。

#### Shapley 归因与目标 Gap

- 基期 `P₀=A₀R₀Q₀`，当期 `P₁=A₁R₁Q₁`，总变动 `ΔP=P₁-P₀`。
- 三因子 Shapley 贡献满足 `Φ_A + Φ_R + Φ_Q = ΔP`。O04 给出的三个闭式公式与三因子全排列平均的定义一致，本次用数值计算做了加总核对。
- 环比 / 同比分析展示贡献值与 `Φ_i/ΔP`；当 `ΔP=0` 时后者无定义，只展示贡献值。
- 目标达成场景把目标因子值作为基准：`Gap=P₁/P₀-1=ΔP/P₀`，因子对 Gap 的贡献为 `Φ_i/P₀`，三项加总等于 Gap。
- 前提是目标 `P₀` 与三个目标因子满足 `A₀R₀Q₀=P₀`，否则 Shapley 分解闭合的是“实际保费与因子乘积目标之差”，不是声明的保费目标差。

#### 原文给出的分析顺序

1. 保费下降：先看订单基数 `Q`，再看渗透率 `R`，最后看单均保费 `A`，然后用 Shapley 定量归因。
2. 渗透率下降但保费持平：检查 `A` 或结构变化是否抵消 `R` 的下降。
3. 取消险保费异常增长：先看大盘订单基数，再看渗透率策略，最后看单均保费或费率变化。

这是一套候选分析方法，是否已经进入生产 Skill、由谁实现、何时上线和是否回归验证，当前材料没有说明。

#### 第四批公式与表述核查

1. **章节引用笔误**：目标达成率部分写“把 2.3 节中的基期替换为目标值”，按结构应指向前面的 2.2 Shapley 拆解。
2. **下标笔误**：`P₀` 若表示基期实际保费，对应因子应仍是 `A₀/R₀/Q₀`；原文写成 `A₁/R₁/Q₁ 均为基期实际值`，与后续当期下标冲突。
3. **“自身达成率”不能由 Shapley 贡献反推**：因子自身达成率应分别直接计算 `A₁/A₀`、`R₁/R₀`、`Q₁/Q₀`。它与 `Φ_i/P₀` 不是同一个量。
4. **原算例是近似示意，不是严格闭合算例**：若三个因子自身达成率严格为 99%、95%、96%，则总 Gap 为 −9.712pp，Shapley 贡献约为 −0.956、−4.876、−3.881pp，而不是整齐的 −1、−5、−4pp；102%、105%、101% 同理得到总 Gap +8.171pp。
5. **`ΔP` 接近 0 时的建议写反了**：原文称此时“各因子贡献值都很小、关注占比更稳健”。实际上总变动接近 0 可能来自较大的正负贡献互相抵消；而 `Φ_i/ΔP` 会因分母接近 0 变得极不稳定。此时应优先展示 `Φ_i` 或 `Φ_i/P₀`，隐藏或弱化占比。
6. **取消险分母存在跨材料冲突**：O04 与 O02 的标准答案都指向全量外卖餐饮订单量；O03 的一个失败题却把“不含取消单”列为取消险口径的关键限定。三份材料不能同时成立，必须回到正式指标定义核对。

#### Step 2 Shapley 公式复核

文档使用 `M=S×T`：`M` 为某渠道加入商户数，`S` 为渠道占全渠道比重，`T` 为全渠道加入商户数。

后文推导出的标准两因子 Shapley 分解是：

- 占比因子贡献：`ΔS × (T₀+T₁)/2`
- 总量因子贡献：`ΔT × (S₀+S₁)/2`
- 两项加总：`ΔM=M₁-M₀`

但 Step 2 表格和“最终公式”实际写成：

> `C_doc = ΔS × (T₀+T₁)/2 + S₀×ΔT`

它把总量因子从 `ΔT×(S₀+S₁)/2` 改成了 `S₀×ΔT`，因此不再等于该渠道的实际变化 `ΔM`。使用文档自己的示例复算：

| 一级渠道示例 | 实际变化 `ΔM` | 文档公式 `C_doc` | 标准两因子 Shapley 两项之和 |
| --- | ---: | ---: | ---: |
| 钱包 | −80.00 | −82.18 | −80.00 |
| 开门营业 | −36.00 | −36.00 | −36.00 |
| 金刚位 | −2.00 | −0.50 | −2.00 |
| 商家成长 | −2.00 | −1.32 | −2.00 |
| 合计 | −120.00 | −120.00 | −120.00 |

`C_doc` 仍能在全部渠道层面加总闭合，是因为所有渠道的 `ΣΔS=0`、`ΣS₀=1`；但单渠道结果不是后文所推导的标准 Shapley 总贡献，也不是该渠道实际变化。这里需要做一个明确选择：

- 如果要表达渠道实际对总下降的贡献，直接使用 `ΔM_i` 即可，天然满足 `ΣΔM_i=ΔT`。
- 如果要拆解渠道自身变化的“占比效应 / 大盘效应”，使用完整的两因子 Shapley 两项，并分别展示；两项加总仍为 `ΔM_i`。
- 如果坚持使用 `C_doc` 作为自定义归因分配，应另行命名、解释经济含义，不能继续称为后文标准 Shapley 公式。

| --- | --- | --- | --- |

原文提出“整体置信度取三层最低值”，这是一个保守的门槛式聚合方案，优点是任一关键环节证据不足都会降级；缺点是它不是统计意义上经过校准的成功概率，而且不能说明到底是哪一层拖累。因此展示时应同时保留总等级、分层等级、降级原因和建议动作。

#### 评估粒度与展示草案

O08 明确提出：复杂用户请求可能触发多次查询，置信度应在**查询粒度**计算，而不是只给整段回答一个总分。示例把一个复杂请求拆成核心指标、评级 / 客群下钻、渠道 / 场景下钻、预估和多组 Vintage 查询，并分别展示：

- 综合置信度；
- 指标理解准确性；
- 查询准确性；
- 结果准确性；
- 降级原因，例如没有标准 SQL、属于模型外推或出现数据异常；
- 本次查询实际使用的时间、客群等参数。

原始示例含内部表名、负责人、具体过滤条件和业务数值，已完整保存在 Git 忽略的 O08；为避免把内部资产信息带入可提交记录，本整理稿只保留结构。

1. O01 中的底表口径错误、缺少过滤条件、上下文丢失和业务同义词缺失，可以分别落到查询层、理解层，而不是统一归为“答案错误”。

#### 第八批待核对与修正项

1. **置信度与准确率分开命名**：没有 Ground Truth 时，系统计算的是“证据强度 / 风险等级”，不是已知的真实准确概率。展示列若写“指标理解准确性、查询准确性、结果准确性”，容易被误解为已经验证；更稳妥的是“理解证据、查询证据、结果质量证据”。
2. **VQR 匹配不能直接判高可信**：还应校验认证查询版本、语义模型版本、参数槽位、时间解释、权限、数据源新鲜度和是否发生 Schema 漂移。
3. **结果合理性不是正确性**：完整、新鲜、无明显异常只能作为 DQC 证据；错误口径也可能返回非常合理的数字。
4. **预测值需要单独类型**：预估 / 模型外推不是普通取数。即使查询和结果校验正常，也应展示模型版本、预测截止日、误差区间或历史回测，不能只用“低置信度”概括。
5. **认证查询需要生命周期**：除验证人和验证时间外，还需要业务 Owner、适用范围、版本、失效条件、复核周期、依赖资产及回归状态。
6. **复杂请求总等级的聚合方式未定**：是所有查询取最低、按高风险查询取最低、还是将低置信查询单独隔离，不应只由展示样例隐含决定。
7. **外部产品事实待核验**：Snowflake `confidence` 字段的确切语义、Looker Verified Queries 状态、Fabric 展示范围及 Anthropic 示例字段都需回查所列官方来源后，才能写入稳定的行业对标结论。

### 第九批：Benchmark 2.0 建设方案

来源：O09。原文提出平台级数据助手 Benchmark 2.0 的出题策略、自动出题方式、长尾题来源和 2,000 题规模规划，并给出支付银行卡领域的 3 道 JSON 样例。样例中的内部链接和具体业务结果只保留在 Git 忽略的原文，本整理稿只记录评测结构。

#### 出题结构与规模

Benchmark 2.0 采用“核心指标 + 长尾问题”的组合：

| 类型 | 来源 | 规划占比 | 数量 | 主要覆盖 |
| --- | --- | ---: | ---: | --- |
| 核心指标 | 实时指挥中心、元方报表 | 80% | 1,600 | 日 / 周 / 月、高频指标、同比环比及渠道、场景、客群拆分 |
| 长尾问题 | Benchmark 1.0 与晓笛真实使用记录 | 20% | 400 | 真实业务表达、组合筛选条件与低频需求 |

| 业务线 | 总占比 | 核心指标题 | 长尾题 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 微贷 | 25% | 400 | 100 | 500 |
| 保险 | 20% | 320 | 80 | 400 |
| 支付 | 35% | 560 | 140 | 700 |
| 风险 | 20% | 320 | 80 | 400 |
| 合计 | 100% | 1,600 | 400 | 2,000 |

原文中的数量和占比计算可以闭合。80% / 20% 及各业务线权重是建设策略，不等同于真实用户流量分布；当前材料没有给出该配比的历史问题频次或风险权重依据。

#### 核心指标自动出题

核心题计划由 `eval-question-generator` Skill 从报表中提取指标名称、数据日期、筛选条件和结果，统一生成 L1、`sql_write` 题。原文声明生成过程会检查指标名、时间、答案格式和重复题，并记录业务域、来源、版本、标准结果及备注。

样例题结构包含：

- `question_id`、业务域、难度、题型、来源、创建时间和版本；
- 自然语言问题；
- `ground_truth_validation`、`ground_truth_sql`、`ground_truth_result`；
- 报表来源备注。

三个样例都属于支付银行卡领域、L1、`sql_write`，分别覆盖单指标直查、带业务场景过滤、月同比变化。样例的 `ground_truth_validation` 和 `ground_truth_sql` 均为空，Ground Truth 实际只保存了格式化结果字符串。

#### 长尾问题人工筛选

长尾题有两个来源：从 Benchmark 1.0 复用典型问题，以及从晓笛使用记录筛选真实案例。当前方案尚未说明：

- “典型 / 有代表性”的抽样标准；
- 用户原话如何脱敏、去重和避免泄漏内部信息；
- 标准答案由谁制作、几人复核、分歧如何裁定；
- 长尾题如何分配 L1 / L2 / L3、`sql_write` / `no_sql`、单轮 / 多轮和分析任务；
- 被复用题是否已进入 Skill、知识库或 Prompt，从而产生评测集污染。

#### 能力覆盖边界

O09 的建设目标写为评估“业务理解、取数及 SQL 生成能力”，但 80% 的自动核心题被固定为 L1 `sql_write`，因此更直接衡量的是标准指标直查。若没有额外题型，以下能力覆盖不足：

1. 业务知识与指标口径问答；
2. 上下文追问、歧义澄清和多轮状态保持；
3. 多指标、多维度、长周期与复杂比较方向；
4. 分析规划、异动归因、报告完整性和业务建议；
5. 错误数据源、权限不足、数据缺失、超时和安全拒答等失败场景。

因此 2,000 题规模不能直接代表端到端经营分析 Agent 的完整覆盖。需要按能力层和任务类型另做覆盖矩阵。

#### Ground Truth 与评测可靠性风险

1. **只有结果字符串不够可复现**：样例缺少标准 SQL 与验证记录，无法判断报表值对应的筛选条件、聚合、数据版本和取数时间。
2. **动态报表可能漂移**：历史分区回刷、指标定义调整或展示格式变化都可能让旧答案失效。应冻结数据快照或记录资产版本、参数和验证时间。
3. **结果相等不代表查询等价**：偶然得到同一数值的错误 SQL 仍可能通过单点答案，需要多日期、多维值或轨迹校验降低巧合通过。
4. **格式化答案不宜作为唯一 Ground Truth**：百分比、金额单位、千分位和舍入应拆成类型化数值、单位、精度和展示字符串，避免把展示差异误判为数据错误。
5. **自动生成题仍需质量抽检**：题目去重、日期替换防护和结果正确性是生成器声明的能力，尚需抽样报告证明。
6. **需要控制评测污染**：题目、标准查询或同构示例若进入运行时 VQR、知识库或 Skill，应从独立盲测集中隔离；否则评到的是记忆与匹配，而非泛化。

#### 与既有材料的关系

1. O06 记录 Benchmark 2.0 当时处于业务线初审后的校准阶段，并计划后续复审与定稿；O09 是建设方案，二者都不能单独证明 2,000 题已经全部建成。

#### 主要失败链路

1. **无人值守认证**：定时任务容器缺少可持续的用户级认证，令数据查询在 token 过期后等待手机确认或因应用身份无项目权限而失败。Agent 即使诊断正确，也无法在当前权限边界内完成。
2. **接口与工具漂移**：起源 API 返回 404 / API 错误，MCP server 名称或路径不匹配，知识附件未打包，导致 Agent 在多个候选端点和路径之间反复尝试。
3. **停止条件缺失**：同一根因被不同命令、认证方式、项目组和数据通道重复尝试，造成 20～40 分钟耗时与高成本，却没有提升成功概率。
4. **工具调用格式不兼容**：环境变量赋值、命令替换和注释被执行层当成命令名或路径拒绝。报告表面呈现为“PATH 问题”，更可能是 Agent 生成的调用格式与执行工具协议不匹配，需要单独归因。
5. **语义与元数据映射错误**：年龄维度虽出现在元数据中，查询却只返回日期；后续 Agent 又错误解释为“Doris 没有分区概念”，被用户指出没有按 Skill 规则处理分区字段与时间维度映射。用户追问 clarify 工具为何未识别，样本结束时仍未回答。
6. **交付尾端不可靠**：报告 / 数据分析可能已经完成，但文档写入、图片上传或消息卡片发送失败或返回空内容，导致端到端任务仍不完整。

1. **组件绑定错误**：一个组件只返回极少数据行，无法形成趋势；核对看板组件后切换到正确组件，并同步修正规格和字段映射。

#### V16 的可解释架构

O13B 将 Skill 拆成三条独立执行路径：

1. **口径查询**：从业务知识文件定位指标定义与计算口径；
2. **数据查询**：通过数据集、日期与比率计算脚本执行查数、同比环比和维度下钻；

横向支撑包括环境与认证、意图路由、日期范围处理、比率型指标聚合、维度编码、监控和错误兜底。这个结构和 O11 的平台级叙事一致：大模型负责意图和编排，确定性脚本负责高风险的数据计算。

#### 开发分享中的真实故障与设计原则

O13C 记录了一组很适合面试说明的工程问题：

| 故障 / 风险 | 根因 | 形成的规则 |
| --- | --- | --- |
| 认证顺序错误 | 先执行查询、后请求认证 | 认证作为所有执行路径的前置门禁 |
| 澄清与认证相互干扰 | 未完成任务参数确认就进入外部动作 | 先确定指标、时间、维度，再触发认证 |

### 第十五批：业务知识层建设规划

来源：O15，用户称其为“文档第三部分”。本轮只基于用户粘贴文本整理，没有访问其中任何产品手册、周会、WBR、MBR、OP 或 PRD 链接。

#### 四类业务知识与当前状态

| 分类 | 主要内容 | 期望用途 | 原文当前状态 |

| 业务基础知识 | 三险种定义、业务流程、承保到理赔链路、费率与核心规则 | 基础问答、业务语义理解 | 部分可用；文档存在，但未结构化为 AI 可直接消费格式 |
| 周会 / WBR / MBR | 目标拆解、阶段重点、策略、复盘、决策和 Action | 当前上下文、策略追踪、分析目标对齐 | 待建设；记录丰富但没有结构化摘要 |

这意味着目前能确认的是：**知识源已经被识别并形成分类规划，但除少量基础知识外，尚未证明已经结构化、入库、可检索或接入生产 Agent。** 原文“AI怎么用”列描述的是目标能力，不能当作现有效果。

#### 更适合 AI 的知识分层

四类材料的更新频率和使用规则不同，不适合全部作为普通长文切片混在一个知识库：

1. **稳定概念层**：险种定义、业务流程、术语、费率结构；按险种与规则版本管理。
2. **目标策略层**：OP 目标、季度策略、指标映射；必须带适用周期和正式 / 草案状态。
3. **决策上下文层**：WBR / MBR 的结论、Action、Owner、截止日期和策略变化；强调时间线。
4. **业务事件层**：PRD 上线、规则变化、灰度范围和口径影响；用于异常发生时的事件关联。

这样既能支持“放心吃是什么”的静态问答，也能支持“2026 年 4 月当时为什么关注某指标”的历史时点查询，避免把今天的策略错误地应用到过去。

#### 候选结构化字段

| 字段组 | 建议字段 |
| --- | --- |
| 身份与分类 | `knowledge_id`、知识类型、险种、业务链路、主题 |
| 内容 | 事实 / 规则 / 决策 / Action / 目标 / 事件、结构化摘要 |
| 时间 | `effective_from`、`effective_to`、发生时间、上线时间、提取时间、更新时间 |
| 来源 | 源文档 ID、版本、章节或节点、原文证据、来源类型 |
| 责任与状态 | Owner、审核人、草案 / 已确认 / 已失效、置信等级 |
| 数据关联 | 指标 ID、维度 ID、策略 ID、项目 ID、影响方向、口径变更范围 |
| 安全 | 密级、可见范围、安全屋要求、是否允许进入模型上下文 |

这里最关键的是**有效期、来源版本和状态**。没有这些字段，Agent 即使召回了文本，也无法判断它是否仍然有效。

#### 检索与回答的可靠性要求

更稳妥的业务知识使用链应是：

> 识别问题的业务对象与查询时点 → 按知识类型和有效期检索 → 处理多来源冲突 → 返回结论与来源 → 将知识只作为分析背景，不替代数据证据

需要明确的规则包括：

- 当前问题优先使用仍在有效期内、已审核的正式知识；
- 历史问题按 `as-of` 时间检索，不能注入今天的目标和策略；
- 多份文档冲突时，不能由模型自行拼接，应按正式程度、有效期和 Owner 决策；
- PRD “计划上线”与真实上线事件分开，未验收不能用来解释已发生异动；
- WBR 讨论、Action 和最终决策分开，避免把讨论意见当成业务事实；
- 输出策略归因时标为“相关事件候选”，除非有数据验证，不能直接写成因果结论。

#### 与现有经分能力的连接

1. **O04 保费归因**：OP 目标可以映射到 A / R / Q 的目标值，形成目标 Gap 拆解；目标乘积是否闭合仍需数据校验。
2. **O05 / O13 渠道异动**：WBR 决策和近期 PRD 上线可作为异常解释候选，但必须与数据变化时点对齐。
3. **O12 WBR 自动化**：报告模板可以读取当期目标、策略和 Action，但不能把历史文档内容无条件复制到本期。
4. **O01 / O03 真实失败**：业务同义词、默认口径和“代理=下沉”等问题可进入术语 / 规则层，并转成回归题。
5. **O06 / O11 记忆能力**：业务知识与用户记忆不是一回事。业务知识应由组织审核和版本管理，不能因某次用户纠错直接覆盖正式规则。

#### 当前方案仍缺的关键机制

- 没有说明文档怎样自动发现、增量同步和去重；
- 没有定义结构化知识的实际存储形式、索引和检索接口；
- 没有定义文档更新后旧知识如何失效；
- 没有定义冲突规则、审核人和发布流程；
- 没有说明来源引用怎样进入最终回答；
- 没有知识检索评测集、命中率、时点正确率或回答采纳率；
- 没有当前已入库的知识条数、覆盖率和生产 Trace；
- 没有定义文档密级和模型可见范围。

因此，现阶段更适合称为“业务知识源盘点与结构化规划”，不宜写成“已建设完整业务知识库”或“Agent 已自动理解业务策略”。

### 第十六批：魔数 BI SQL 查询 Skill

来源：O16，本地附件《魔数-BI-SQL查询》。本轮只读取附件文本，没有执行其中的埋点、Node.js 安装、Talos 安装 / 登录、SQL、权限或模板操作，也没有访问附件中的下载和反馈链接。

#### 受控查询流程

O16 描述的是一个建立在 Talos CLI 上的官方查询 Skill。所有路径共享两道环境前置检查，然后按用户意图进入七条互斥路径：

| 路径 | 用户意图 | 主要步骤 |
| --- | --- | --- |
| A | 提供完整 SQL 并要求执行 | SQL 预检查 → 执行 |
| B | 自然语言、SQL 骨架或要求修改 SQL 后执行 | 搜索表结构 → 生成 SQL → 预检查 / 修复 → 执行 |
| C | 只查表结构 | 搜索表结构 |
| D | 只检查 SQL | SQL 质量检查，不执行 |
| E | 只生成 SQL | 搜索表结构 → 生成 SQL → 质量检查，不执行 |
| F | 查询 BI 项目组权限 | 查询项目组列表 |
| G | SQL 模板操作 | 检索、执行、创建或更新模板 |

执行层还有三项明确约束：同一时刻只允许一个查询任务、步骤必须串行、阻断级预检失败不得进入执行。这些规则降低了重复提交、跳过检查和并发状态混乱的风险。

#### 它能保证什么，不能保证什么

| 能力 | O16 可以提供 | O16 不能独立保证 |
| --- | --- | --- |
| 环境 | Node.js 与 Talos CLI 可用性检查 | 公司内依赖长期稳定 |
| 路由 | 完整 SQL、自然语言、只检查等意图区分 | 业务指标和口径理解正确 |
| 生成 | 先取表结构再生成 SQL | 选中的表就是正确业务数据源 |
| 预检 | 语法、语义和成本层面的阻断 | 比率分母、时间口径、维度映射正确 |
| 执行 | 单任务提交、等待和返回结果 | 结果值就是业务 Ground Truth |
| 模板 | 模板检索、执行和维护 | 模板仍有效、适用当前场景 |

因此 O16 进一步证明：**“SQL 可以通过预检并执行成功”只是执行正确性，不是数据与业务正确性。** O01 / O03 中走错数据表、缺过滤条件、维度语义不一致等问题，仍需要场景险业务 Skill、语义层和结果验证解决。

#### 国内 / 海外与数据安全

O16 会根据当前请求选择国内或海外 Region；没有关键词时默认国内，混合意图则要求澄清。这个规则比完全猜测更安全，但仍应与 O14 的业务线、项目组和 C4+ 安全屋约束组合：

- Region、业务线、项目组和数据密级是四个独立参数，不能只判断 Region；
- 多轮对话沿用 Region 时要显式保留来源，避免上下文漂移；
- C4+ 查询即使 SQL 本身只读，也必须在安全屋完成；
- 查询结果的展示、缓存、日志和埋点同样不能离开允许范围。

#### 可观测性与隐私风险

O16 要求执行前后调用埋点脚本，并在开始事件中携带用户原始 Prompt，在结束事件中携带执行摘要、步骤数和失败步骤。这有助于统计 Skill 使用、成功率和失败环节，也可能解释 O10 的部分 Trace 数据来源。

但这里存在必须核对的隐私边界：如果原始 Prompt 含 SQL、表名、业务数据、个人信息或 C4+ 内容，是否会被原样写入日志？在确认脱敏、权限、保存周期和安全屋适配前，不能默认这种埋点对所有数据等级都安全。

#### 仍需加固的执行控制

1. 路径 B 的 SQL 修复循环没有在主文档中写最大次数，应设置重试预算并保留每次差异。
2. 自然语言请求可以直接走到 SQL 执行；对高成本、超大范围和敏感查询，应有额外确认或阻断规则。
3. 模板创建和更新属于外部状态变更，应与只读查询分开授权和审计。
4. 默认 Region 不能替代业务线和数据域确认。
5. 自动安装 Node.js / CLI 会改变用户环境，不应因阅读文档或普通查询失败就无条件执行。
6. 工具预检之外仍需结果级校验：时间范围、分区、行数、空值、单位、比率重算和业务口径。

#### 与 `mtdata bi` 的关系待确认

O14B 记录 `mtdata bi` 可以提交魔数 SQL；O16 则通过 Talos CLI 实现魔数查询。两者可能是：

- 不同版本的官方查询入口；
- 不同运行环境的封装；
- `mtdata bi` 在底层再次调用 Talos；
- 两个并行工具，场景险只使用其中之一。

在明确实际调用链前，不能把两种入口都写成项目依赖，也不能将它们的成功率或错误混在一起统计。

#### 两类 Shapley 不应混用

O17A 与 O17B 实际记录了两种不同问题：

| 方法 | 公式对象 | 要回答的问题 |
| --- | --- | --- |

### 第十八批：小D统一平台整体架构与三层记忆

O18 是统一 BI Agent 平台的架构说明，不是场景险业务 Skill 的个人交付清单。它最有价值的是解释了场景险项目运行所依赖的平台边界：

1. **Channel 与统一消息协议**：将 Web、Bot、定时任务和 Agent 协作入口与 Runtime 解耦。
2. **Runtime 与 Control Plane 分离**：在线推理 / 会话 / Agent Loop 与知识、Skill、评测、可观测管理分离。
3. **共享文件与数据库一致性**：以共享文件系统承载知识、Skill、工作区，以数据库作为运行状态的唯一事实源，减少多 worker 状态漂移。
4. **脑手分离与沙箱**：推理由 Harness 负责，高安全 CLI 在 per-user 沙箱执行；统一执行工具和无感认证降低业务 Skill 直接处理凭证的需要。
5. **模型路由**：按任务阶段和复杂度选择不同层级模型，试图在质量与成本间权衡。
6. **Self-Evolution 候选闭环**：从 Trace 诊断中提炼候选记忆，再进入分层审核与发布。

三层记忆把影响面与写入门槛绑定：L3 用户私有可高度自动化，L2 业务域按置信度进入候选或确认区，L1 平台通用必须人工审核；记忆内容再分为分析模式、强制约定、踩坑记录和高频问答。这为“知识是人工维护的共识、记忆是从运行中提炼的经验”提供了清晰边界。

材料同时明确了真实断点：历史消息摘要未完成、通用沙箱命令范围有限、沙箱尚不能挂载共享文件系统。尤其第三点意味着“沙箱产出文件 → Runtime / 多实例共享”仍不闭合，因此“脑手完全分离”和“统一文件视图”目前只能称为目标架构。

还需注意：POSIX 兼容或每条记忆独立成文件，不自动保证业务层并发一致性；“观察次数达到阈值即自动确认”也可能把重复错误 Trace 放大。生产治理仍需要来源去重、冲突检测、版本 / 有效期、回滚、删除和审核责任。

### 第十九批：指标与数据集知识库混合检索评审方案

O19 将“数据治理”和“Agent 检索”分成两层：起源平台负责权威资产治理，知识库只做 Agent 友好的只读同步与检索加速。这个区分很重要——检索得快不代表指标本身正确，重复、过时或描述不清的资产仍会被更快地检索出来。

方案主链路是：离线同步元数据 → BM25 精确召回 + 向量语义召回 → RRF 融合 → 可选 Rerank → 统一搜索接口。其关键设计价值包括：

- BM25 和向量使用不同索引文本，分别服务术语命中与自然语言语义；
- 自定义业务词典保护指标缩写和业务术语；
- 默认使用对分数量纲不敏感的 RRF，等评测证明召回足够但排序不足时再增加重排；
- 用 Recall、Precision、MRR、NDCG 和多类真实问法做检索级评测；
- 数据量较小时先采用内存索引，再按规模与更新频率迁移到分布式检索设施。

这是**评审方案**而不是已上线证明。文中的效果数字是经验预估，阶段周期是计划；尚缺真实评测集、人工相关性标签、A/B 结果、线上延迟、同步新鲜度和主链路接入记录。

### 第二十批：起源指标资产现状

O20 的核心价值不是资产数量本身，而是量化了“权威平台中仍存在治理债务”：约四成半指标同时满足较久未更新且近 30 天无查询，另有少量指标没有关联数据集、应用或模型；各业务线的冷指标与数据集关联率差异很大。

这直接支持两项项目判断：

1. O19 的检索层必须把废弃状态、更新时间、热度、关联关系和审核状态纳入过滤 / 排序，不能只按文本相关性返回候选。
2. Data Agent 的准确性上限不仅受模型和检索影响，还取决于指标去重、口径补全、权威标记、关联修复和废弃治理。

“真冷”仍只是治理候选，不等于可以直接删除：30 天窗口可能漏掉季度、年度、监管或应急指标，正式废弃前仍需业务 Owner 确认、下游血缘检查、历史使用核对和可回滚下线流程。

O19 与 O20 对指标、数据集和模型总量的统计不同，说明它们可能来自不同日期、业务范围或关联口径。未核清前不能把两组数字拼成同一现状结论。

## Codex 反馈

以下仅是对第一批 10 条记录的初步归类，属于 AI 提炼，尚未由用户确认：

| 观察维度 | 第一批材料中的表现 | 对应案例 |
| --- | --- | --- |
| 数据路由与口径 | 走底表后出现口径错误；关键过滤条件未进入稳定语义层 | Q02、Q03 |
| 数据集覆盖 | 指标存在但维度不足，导致任务只能部分完成或需要补维度 | Q02、Q03、Q04、Q08 |
| 多轮上下文 | 追问依赖上一轮分析对象和数据域；只理解当前句会选错数据 | Q06 |
| 业务同义词 | “下沉”与数据字段值“代理”的映射未被 Agent 掌握 | Q08 |
| Skill 命中 | 已有分析 Skill 能直接支持渠道归因类问题 | Q05 |
| 降级与可用性 | 数据集服务停止后，可降级为 sandbox SQL 直查 Hive | Q09、Q10 |
| 性能 | 简单查数可在 1–2 分钟返回；复杂 SQL 和长周期任务可达 28–38 分钟，极端案例超过 2 小时 | Q01、Q02、Q04、Q07、Q08 |

对记录口径的暂时统计：10 条问答中，问题理解被标为准确 9 条、不准确 1 条；回答结果可暂分为准确 5 条、部分准确但未完整完成 1 条、不准确或不太准确 4 条。这只是对该批样本的转录统计，不能直接代表系统整体准确率。

第二批材料进一步说明，评测不能只做“答案字符串或数值是否一致”的二元判定。当前至少有四类需要单独裁定的问题：

1. **非标准指标名与业务默认值**：用户省略“餐饮”时，是澄清、按业务惯例默认，还是判为指标不标准。
2. **上下文联动口径**：同名“外卖餐饮订单量”是否应继承前文保险指标的特定分母口径。
3. **比较方向**：区间 A 与区间 B 的变化必须结构化表达基期、对比期和计算方向，否则正负号可能整体反转。
4. **时间粒度与同比 / 环比语义**：某日、某周、上周同日、去年同周是四种不同的时间对象，不能只靠“周同比”三个字路由。

因此，原表 5 个错误标记更适合作为“待人工裁定的问题样本”，不应未经复核直接用于计算模型准确率。

第三、四批合在一起补出了“评测发现问题—分析方法补充”的链路，但目前只能确认两份材料都存在，不能确认 O04 已经作为 O03 的 P1 改进项正式写入 v4、上线或完成回归。尤其需要避免把以下三种状态混在一起：

- O03 已观察到的首跑 / 重跑结果；
- O03 报告提出的 P0～P3 改进建议；
- O04 已写出的保费归因方法文档。

文档写出来不等于 Skill 已加载，Skill 已加载也不等于评测已经改善。

第五批进一步提供了 O01 成功案例背后的渠道归因方法，但也让 O03 的问题边界更清晰：知识文档、Skill 命中、数据集路由、SQL 执行和最终分析结论是不同的可靠性环节，应在评测中分开判分。

第六批补充了组织与平台边界：场景险 Agent 不是在真空中独立实现，数据证据、记忆、文件、共享 Session、Builder 和 Benchmark 等能力可能来自统一平台。项目复盘必须明确“平台提供什么、保险业务线建设什么、用户本人实现什么”。

第七批进一步证明需要把“组织目标—平台路线图—业务线计划—具体项目交付—个人贡献”分成五层。65%→85%、四层准确率、XBR / 实验覆盖率和 6～10 月能力项目前只能作为上位背景或目标；没有验收证据前，不能吸收到个人项目结果中。

第八批把“准确 / 不准确”的事后标签推进成查询级证据体系，这是对现有评测记录的重要补充。但当前更准确的产品命名应是“数据可信证据与风险分级”，而不是声称系统已经知道答案正确的概率。调研结论、方案设计、平台现状和项目实际接入仍需分别保存。

第九批补充了平台级评测集的规模化生产方案，但“题多”与“评得准”是两件事。自动生成 L1 直查题适合扩大基础取数覆盖，真实长尾和高阶分析仍需要人工策划、可靠 Ground Truth、盲测隔离与题库版本治理。

第十批把离线评测之外的线上真实质量补了进来。更合适的评测闭环应是：标准题验证能力与回归，生产 Trace 发现真实分布和未知失败，再将高价值失败转化为脱敏回归题。当前报告本身仍需要统一标签口径和补齐全量成功率，不能把 28 条目的性样本直接外推。

第十一批提供了项目全景的“上位叙事”，适合用来搭项目骨架，但不能直接替代底层事实核对。尤其要把产品愿景、平台团队能力、业务线资源、系统自述和用户个人贡献分别落证，避免把一个完整的平台故事误写成个人从零实现。

第十二批显著提高了场景险项目的工程可解释性：它不只是“Agent生成报告”，而是一个受控的 BI 取数、字段规范化、规格化绘图、文档填充和验证流水线。最需要补的已经不是更多功能介绍，而是提交归属、生产运行记录、验证规则和人工节省效果。

第十三批把项目从“功能和评测结果”进一步推进到“版本化架构、具体故障、告警实现资产和数据发现输入”。同时，它也暴露了新的证据风险：文档时间线不完整、人工测试与系统评测表述冲突、调研路线与实际配置不同，以及附件中含明文凭证。后续必须先完成版本和安全核对，再提炼对外项目结论。

第十四批显著收窄了个人成果的合理边界：学城写入、数据资产搜索、血缘、起源、BI / Hive 查询、XT 上线和 DQC 都有官方工具底座。真正有区分度的个人工作，应集中在场景险业务建模、受控编排、确定性脚本、评测和真实失败治理，而不是把公共 CLI 能力写成自研平台。

第十五批补出了知识层的业务内容框架，但也证明“有文档”与“Agent 有业务理解力”之间还有结构化、版本、有效期、审核、检索和评测六道门槛。后续项目描述需要使用真实入库量和 Trace 证明跨过了哪些门槛。

第十六批进一步细化了平台执行边界：官方 Skill 已经负责环境检查、表结构检索、SQL 生成 / 预检和查询执行；场景险项目的关键价值仍在正确选资产、理解指标口径、控制业务路由和验证结果。执行成功不等于分析正确。

第十七批第一次把早期人工功能验证与一个可读的业务 Skill 包连了起来：可以更具体地说明“人工查数 / 计算 → 数据集接口 → 确定性脚本”的演进。但这个结论目前是候选时间线，必须先解决 V13 / v4 / V16 / v3.0 的命名冲突，并处理认证密钥和敏感等级问题，才能用于稳定的项目陈述。

第十八至二十批把“业务 Skill 为什么能运行”和“为什么仍会选错资产”补得更完整：统一平台提供渠道、运行时、沙箱、模型路由与记忆治理；业务检索层用混合检索找到候选；权威资产平台仍需要持续治理。三层必须分别评测，不能用检索 Recall 代表数据准确，也不能用平台架构代表个人交付。

## 发散联想

这批材料以后可以沉淀为一套比“准确 / 不准确”更可诊断的真实问题评测结构：

1. 问题理解：业务对象、指标、时间、维度、过滤条件、上下文指代是否完整。
2. 能力与路由：走指标数据集、分析 Skill、底表 SQL 还是安全拒答 / 澄清。
3. 数据可信：表、字段、关联、过滤、指标口径和业务同义词是否正确。
4. 任务完成度：数值正确之外，是否覆盖要求的全部指标、维度和交付动作。
5. 执行效率：总耗时、SQL 耗时、重试次数、降级路径和是否命中缓存。
6. 闭环动作：数据集扩维、知识库补充、Skill 修复、评测回归及其真实上线状态。

这些维度目前只是候选分析框架，不能自动视为项目已经采用的正式评测体系。
