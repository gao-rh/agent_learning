# 2026-08-28 E2：意图识别与指标澄清设计

## 原始问题

用户希望在最小 Tool Calling Loop 之后增加一个更复杂的交互：先识别并确认用户意图，意图分为
查数据、问数据知识、做数据分析；再补齐具体任务，并将用户口语中的指标指称映射为完整标准指标名，
由用户确认后才执行。例如，用户询问某产品今天的保费情况时，系统应展示候选标准指标并询问是否确认。

## 用户理解

- 用户已能复述最小链路：System/Human 输入与 Tool 定义交给 Kimi，Kimi 返回 Tool Calling，应用执行 Tool 并回传结果，Kimi 再生成最终回答。
- 当前假设：拥有完整 messages 可以知道历史过程；严格来说，这不足以保证崩溃后可靠续跑。
- 用户确认：口语“B准”在本模拟案例中指“准时保”；标准指标名为“准时保保费收入”。
- 用户确认：“今天”是独立查询日期，不属于标准指标名；执行前需要确认指标、查询维度和日期。
- 用户纠正：不应把三个待确认字段机械拆成三轮，第一轮应一次性列出所有问题；后续只追问仍未确认项，不能重复已确认问题。完整回答时一轮即可，通常一至三轮完成。
- 用户进一步纠正：澄清提示应像正常对话一样先给出一套完整理解；用户回复“确认”或“1”表示全部确认，
  回复“App渠道，明天”只修改提到的条件，不应要求用户逐字段作答；界面应显示“今天/明天”，而不是内部 ISO 日期。
- 用户确认：澄清不是固定环节。首次请求中的标准指标、渠道和日期都明确且可唯一解析时，应直接查询，
  `clarification_rounds` 为 0。

## Codex 反馈

下一实验应成为第一个真正的 LangGraph Human-in-the-loop 工作流：

```text
输入
→ 意图识别
→ 必填信息检查
→ 指标候选检索
→ interrupt 等待用户确认
→ Command(resume=...) 恢复
→ 按意图路由
→ Tool 执行
→ 结果校验
→ 最终回答
```

标准指标身份与时间条件分开：标准指标名为“准时保保费收入”，`today/date_range` 作为查询条件。

最终采用批量澄清策略：

```text
一次性列出当前所有未确认项
→ 用户一次性回答
→ 只计算仍缺失或含糊的字段
→ 若还有缺口，仅追问剩余项
```

更严格地说，图先执行“充分性检查”：完整且无歧义时绕过 `interrupt`；只有存在缺失或歧义时才生成
确认提案。首次提案展示完整理解，后续只展示尚未解决的字段。内部仍以标准指标 ID、维度 ID 和 ISO 日期
执行，用户界面则使用业务名称和相对日期表达。

代码记录 `asked_question_keys`、`slot_attempts` 和 `clarification_history`，避免原样重复问题；默认设置
5 轮安全上限，但不要求固定走满两轮或三轮。

可靠恢复还需要 Checkpoint；若 Tool 有外部写入副作用，还需要幂等键或执行账本，完整 messages 本身不能
阻止恢复时重复执行。

## 发散联想

- 意图分类可使用 LLM 结构化输出，但指标标准化必须受模拟指标目录约束，不能让模型凭空创造标准名。
- `interrupt()` 所在节点恢复时会从节点开头重新执行，因此中断前不放置非幂等副作用。
- 澄清轮数必须有限，超过上限后应安全失败或要求用户重新描述。
- `tool_call_id` 关联一次 ToolCall 与 ToolMessage；`thread_id` 关联可暂停恢复的整段会话，二者不能混用。
- 一次性澄清减少交互成本，但问题过多时会增加用户漏答概率；因此恢复后必须按字段检查，而不能把整段回答简单视为全部确认。
