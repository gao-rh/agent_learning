# 智能经分评估方案 v0.1

> 状态：AI 草案，等待用户逐块确认；用于快速形成可讨论版本，不代表全部历史细节已经核验。
>
> 参考讨论记录：`记录/2026-08-30-智能经分评估体系设计.md`

## 1. 评估目标

评估智能经分 Agent 是否能够正确理解用户任务、获得可信数据、完成业务咨询或分析，并稳定交付最终结果；同时能够在失败时定位问题发生在哪个能力或工具环节。

## 2. 指标结构

### 2.1 顶层结果指标

1. **数据准确率**：取数任务最终返回正确数据结果的比例。
2. **端到端任务成功率**：各种真实任务最终解决用户问题的比例。

统一使用整题 Pass / Fail：

```text
某类任务准确率或成功率
= 该类通过任务数 / 该类有效运行任务总数
```

有唯一标准答案时称“准确率”；允许多条合理路径、按 Rubric 判断时称“任务成功率”。不使用没有明确业务含义的连续总分。

### 2.2 能力级结果与诊断

| 能力 | 结果指标 | 定位 |
| --- | --- | --- |
| 意图识别 | 不作为重点指标 | 保留边界回归和失败标签 |
| 取数澄清 | 澄清成功率 | 开发初期隔离测试 |
| 业务知识与指标口径咨询 | 咨询回答准确率 | 开发初期隔离测试 |
| 可信取数 | 数据准确率 | 顶层重点指标 |
| 数据分析 | 分析任务成功率 | 固定分析 / 开放分析分组 |
| 报告与可视化 | 并入分析或端到端任务成功率 | 错误作为失败原因 |
| 跨会话连续性与记忆 | 跨会话连续成功率 | 约 10 道线上记忆续接题 |
| 定时任务与主动交付 | 定时交付成功率 | 每日报告文档与群聊摘要交付 |

串并行和专业 Agent 内部的轻度编排不单列指标。若违反必要依赖、遗漏复合目标、重复调用失控或无证据生成结论，在对应任务中判 Fail 并记录原因。

## 3. 通用评测流程

每项能力至少明确：

1. 被测能力及单题 Pass / Fail 条件；
2. 测试任务来源、类型和参考答案；
3. 环境、工具、数据 / 知识版本和运行终点；
4. 验证器读取的最终结果或 Trace 证据；
5. 分子、分母、无效运行和分组报告方式。

历史项目主要使用 LLM-as-a-Judge：Judge 将 Agent 最终结果与人工参考答案比较，输出 Pass / Fail；失败后再查看 Case 和 Trace 做归因。正式复现时应固定题集、Agent 版本、Judge 模型、Judge Prompt、数据 / 知识版本和运行配置。

## 4. 各能力评测卡

### 4.1 可信取数

#### 测试任务

- 200 条人工确认标准结果的题目；
- 冻结查询日期和版本；
- 覆盖简单取数、当期 / 基期比较、复杂维度、比率型指标、公式型复杂指标和主要业务数据类别；
- 分为信息完整的单轮取数，以及由便宜模型扮演用户的澄清后取数。

复杂任务可能包含：时间语义解析、当期 / 基期日期范围、原子指标查询、分子分母汇总、派生指标计算和同比 / 环比计算。

#### 执行

```text
固定题目与查询日期 / 版本
-> 直接运行，或由用户模拟器完成澄清
-> 取数 Agent 查询数据并完成必要计算
-> 输出指标名称、期间、维度和最终数值
```

#### 验证

LLM Judge 比较最终结果与人工标准答案。题内所有目标指标和数值全部正确才 Pass；任一关键结果错误则整题 Fail。

#### 计算

```text
数据准确率
= 数据结果全部正确的任务数 / 有效取数任务总数
```

失败后按日期范围、指标匹配、工具参数、原子取数、聚合、公式或结果表达归因，不分别建立 KPI。

#### 待核实

Judge 模型 / Prompt / 版本、各题型实际分布、无效运行规则，以及复杂题是否保存了中间标准。

### 4.2 取数澄清

#### 测试任务

- 开发初期人工整理约 50 题，精确数量待核实；
- 覆盖单指标和多指标澄清；
- 每题保存首轮不完整问题和隐藏目标；
- 用户模拟器知道目标指标的业务含义，但不知道标准指标名称，避免答案泄露。

#### 执行

```text
首轮不完整问题
-> 被测 Agent 发起澄清
-> 便宜模型按隐藏目标回答
-> 被测 Agent 继续澄清或调用任务提交工具
-> 工具提交成功，或超过最大轮次后终止
```

测试终点是向数据 Agent 提交澄清后的任务，不继续执行实际取数。

#### 验证

1. 工具验证提交格式和接口参数是否合法；
2. LLM Judge 判断最终交给数据 Agent 的任务是否与隐藏目标一致。

工具接口成功但提交了错误指标，仍应判 Fail。多指标题必须全部目标正确且无遗漏、无错误增加才 Pass。

#### 计算

```text
澄清成功率
= 在轮次上限内正确提交任务的案例数
  / 有效澄清案例总数
```

#### 待核实

精确题量、最大轮次、提交工具和字段、Judge 模型 / Prompt、历史成功率。

### 4.3 业务知识与指标口径咨询

#### 测试任务

- 开发初期由人工整理问题和参考答案；
- 业务知识与指标口径题合计约 20～50 题；
- 业务知识来源为业务人员梳理的知识文档；
- 指标口径与元数据通过接口查询。

#### 执行

```text
人工问题
-> Agent 查询业务知识文档或指标接口
-> Agent 生成最终回答
```

#### 验证

LLM Judge 只比较最终回答与人工参考答案。回答错误后，再查看是否已正确召回知识或指标内容，用于区分召回问题、工具问题与生成使用问题。

#### 计算

```text
咨询回答准确率
= 最终回答正确的咨询任务数 / 有效咨询任务总数
```

用户回忆历史准确率接近 100%，当前未取得原始结果核验。

#### 待核实

精确题量、题集和知识文档版本、指标接口版本、Judge 模型 / Prompt、历史运行报告。

### 4.4 数据分析

#### 任务分类与通过条件

**固定分析任务**：

- 使用正确的指定分析方法；
- 查询数据和必要计算正确；
- 必要图表中的数据、时间、指标、维度和图例正确；
- 文字结论不与证据冲突。

**开放分析任务**：

- 查询数据和必要计算正确；
- 必要图表正确；
- 不评分析路径是否最优，也不要求命中唯一参考洞察；
- 事实结论有证据支持，未验证方向标为假设，不将编造原因写成事实。

#### 指标

```text
分析任务成功率
= 通过的固定 / 开放分析任务数 / 有效分析任务总数
```

报告固定分析、开放分析两个子集结果。方法、数据、图表和结论错误只作为整题失败条件与原因，不分别建立 KPI。

#### 历史测试执行与验证

- 离线分析题量较少，每一种分析大约 5 题；具体类型数与总题量待核实；
- 固定分析有人工参考答案，Judge 将最终报告与参考答案比较；
- 开放分析没有参考答案，Judge 对最终报告做无参考判断；
- Agent 一直运行到生成最终报告，报告中包含数据和图表；
- Judge 只查看最终报告，不读取数据 Trace；
- 历史分析任务成功率约 70%；数据准确率评测结果在 90% 以上；
- 后期改进主要来自线上问题，逐个排查失败 Case。

历史高层流程为：

```text
少量人工分析题
-> 运行到含数据和图表的最终报告
-> 固定分析按参考答案 Judge
-> 开放分析无参考 Judge
-> 输出 Pass / Fail
-> 统计分析任务成功率
```

验证边界：开放分析没有参考答案且 Judge 只看最终报告，可以检查自洽性、明显图文冲突和无依据结论，但不能独立证明报告中的数据查询真实正确。90% 以上的数据准确率来自独立取数评测，不自动证明每一道开放分析报告的数据正确。

#### 待核实或改进

- 具体分析类型、总题量和固定 / 开放分布；
- Judge 模型 / Prompt；
- 70% 与 90% 对应的题集版本和运行报告；
- 未来是否将结构化数据结果或 Trace 一并交给开放分析 Judge，以验证报告与证据一致性。

### 4.5 跨会话连续性与记忆

跨会话记忆已经实现。历史测试主要验证已有记忆能否在后续会话被正确使用：

```text
选择线上已有会话及已写入记忆
-> 根据原会话内容设计后续问题
-> 在后续会话向 Agent 提问
-> Agent 检索并使用记忆续接任务
-> 判断回答是否正确延续上下文
```

- 题量约 10 题；
- 题目主要根据线上真实会话和已有记忆人工设计；
- 用户回忆连续成功程度在 90% 以上，待原始结果核验。

```text
跨会话连续成功率
= 正确使用已有记忆完成续接的任务数
  / 有效跨会话测试任务数
```

验证边界：该测试证明已有记忆的读取与使用，不自动证明记忆写入、冲突更新、错误纠正、应遗忘信息处理或跨用户隔离。历史验证者和精确 Pass / Fail Rubric 待核实。

### 4.6 定时任务与主动交付

定时任务已经完整实现：每日定时触发，执行数据与分析任务，生成报告文档，同时生成摘要并发送到群聊。

```text
每日定时触发
-> 生成报告文档
-> 生成摘要
-> 向群聊发送消息
-> 检查任务和交付状态
```

```text
定时交付成功率
= 按要求完成报告与群消息交付的计划任务数
  / 应执行的计划任务总数
```

用户口述历史测试和运行结果为 100% 成功；统计周期、运行次数、重试口径，以及 100% 是否包含内容正确性仍待核实。

报告内数据和分析正确性复用数据准确率与分析任务成功率。报告或告警“是否对业务有用”没有固定离线指标，主要根据实时业务反馈持续调整，例如取消无价值告警、调整阈值，或将每天约 10 个告警减少到约 5 个。

## 5. 开发阶段与后期回归

历史评测策略分为两个阶段：

```text
开发初期：人工小题集 -> 能力隔离测试 -> 快速定位与调试
系统成型后：端到端基准 -> 整题 Pass / Fail -> 失败 Case / Trace 回溯
```

后期以端到端测试为主，不再持续关注澄清、知识咨询和口径查询的单项指标。隔离测试仍可保留少量稳定回归题，但是否作为现行方案的一部分待确认。

## 6. 横向质量

以下内容不与业务准确率混成一个总分：

| 维度 | 候选验证方式 | 当前状态 |
| --- | --- | --- |
| 工具异常恢复 / 降级 / 人工介入 | 在取数、分析和定时任务中注入超时、空结果、限流或不可用 | 待确认故障类型和通过边界 |
| 权限与安全 | 越权、敏感数据、跨用户泄露和危险操作测试；严重违规作为硬失败 | 待确认范围 |
| 稳定性 | 重复运行成功率、系统错误率、回归结果波动 | 待确认次数与门槛 |
| 延迟 | 按任务类型统计 P50 / P95 | 待确认计时边界 |
| 成本 | 统计模型、Token、工具与基础设施的单任务均值 / P95 | 待确认成本边界和预算 |
| 可观测性 | 检查 Trace、工具输入输出、版本、耗时、成本和失败字段是否完整 | 待确认必填字段 |
