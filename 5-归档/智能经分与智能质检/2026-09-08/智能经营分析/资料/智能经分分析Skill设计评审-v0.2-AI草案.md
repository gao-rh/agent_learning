# 智能经分分析 Skill 设计评审 v0.2

> 状态：基于用户最新校正形成的 AI 草案。两类请求与路由原则已经用户确认；目录、字段和工程实现仍为设计建议。
>
> **版本状态更新：** 用户进一步确认分析是按指标所属业务专题路由，不存在覆盖所有指标的通用指标异动分析 Skill。本版的“两类核心 Skill”模型已经不再准确，请以 [v0.3](../../../../../2-进行中/面试准备/项目准备/智能经营分析/资料/智能经分分析Skill设计评审-v0.3-AI草案.md) 为准。

## 一、对 v0.1 的核心校正

v0.1 将趋势、贡献和漏斗等能力设计成由 Agent 按需连续组合，容易产生一种错误理解：普通用户提出一个局部异动问题后，Agent 会自动从当前节点持续向下分析多层。

用户确认的实际设计不是这样。系统首先根据用户需要的分析范围进行路由：

```text
完整专题报告 → 长专题分析 Skill → 从头到尾执行完整分析链路

局部指标变化问题 → 指标异动分析 Skill → 只完成当前节点的一层分析
```

## 二、推荐的两类核心 Skill

### 2.1 完整专题分析 Skill

#### 触发条件

用户明确要求完整专题、完整报告或固定经营分析产物，例如：

> 生成今天的渠道分析报告。

#### 执行范围

- 从专题规定的起点开始；
- 按该专题的完整方法依次分析；
- 可以包含趋势确认、层级归因、漏斗、source 定位和运营建议；
- 最终生成结构化的完整专题报告。

#### 设计特点

- 路径较长；
- 业务专属性强；
- 输入和输出相对固定；
- 可以在关键节点使用程序校验和停止条件；
- 适合沉淀为完整的渠道专题 Skill，而不是由用户逐步追问拼出报告。

当前本地材料能够明确支撑渠道专题的完整五步链路：全渠道确认、一级渠道贡献、二级渠道贡献、漏斗定位和 source 级定位。

### 2.2 指标异动分析 Skill

#### 触发条件

用户已经给出具体分析对象，询问某个维度、维度值或局部范围内某项指标为什么变化，例如：

> 为什么钱包渠道的加入商户数下降了？

#### 执行范围

- 继承用户已经提供的指标、维度、维度值和时间；
- 先确认当前节点的变化；
- 只分析当前节点的一层直接原因；
- 输出本层主要贡献因素、数据依据和下一步建议；
- 不自动从全局重新开始；
- 不默认继续进入多层维度、漏斗和 source。

#### 一层的含义

“只做一层”指从用户当前指定节点向下分析一个直接层级。例如：

| 用户当前节点 | 本次分析的一层范围 |
| --- | --- |
| 全渠道加入商户数 | 一级渠道 |
| 某一级渠道加入商户数 | 该一级渠道下的二级渠道 |
| 某二级渠道加入商户数 | 该二级渠道的漏斗环节 |
| 某漏斗环节异常 | 该环节下的 source 或直接驱动因素 |
| 保费变化 | 单均保费、订单渗透率、订单基数 |
| 渗透率变化 | 分子、分母或直接二级指标 |

分析完成后可以提示最值得继续追查的方向，但只有用户继续追问或明确同意继续时，才进入下一层。

## 三、正确的路由维度

路由不能只依赖“分析”“异动”“报告”等关键词，需要同时判断：

| 路由字段 | 完整专题分析 | 指标异动分析 |
| --- | --- | --- |
| 用户目标 | 获得完整专题报告 | 解释一个具体变化 |
| 当前分析位置 | 通常未指定，要求从专题起点开始 | 已指定指标、维度或局部节点 |
| 分析深度 | 完整多层链路 | 当前节点向下一层 |
| 输出 | 完整报告 | 局部原因和数据依据 |
| 是否自动继续下钻 | 按专题流程继续 | 默认不继续 |

如果用户只说“帮我分析一下渠道”，信息不足以直接判断，应一次性澄清他需要完整渠道报告，还是只分析某个具体指标或渠道节点。

## 四、分析方法怎样复用

趋势、公式拆解、维度贡献、漏斗和目标 Gap 仍然有价值，但它们应当是专题 Skill 和指标异动 Skill 内部复用的方法，不应决定用户层的主路由。

```text
完整渠道专题 Skill
  ├─ 趋势确认
  ├─ 一级渠道贡献
  ├─ 二级渠道贡献
  ├─ 漏斗分析
  └─ source 定位与报告

指标异动分析 Skill
  ├─ 读取当前节点
  ├─ 选择该节点适用的一层方法
  │   ├─ 公式因子
  │   ├─ 子维度贡献
  │   └─ 下一层漏斗
  └─ 输出本层结论并停止
```

如果运行平台不适合 Skill 之间互相引用，可以将共用方法维护成同一份 reference 或确定性脚本，由两个 Skill 各自调用；不要复制两套公式和计算实现。

## 五、指标异动分析 Skill 的建议输入输出

### 输入

- 业务专题；
- 当前指标的标准身份；
- 当前维度和维度值；
- 当期、基期与比较方式；
- 当前分析节点；
- 允许分析的下一层类型；
- 用户要求的输出形式。

### 输出

- 当前变化是否成立；
- 本层用于分析的实际指标和数据范围；
- 下一层各因素的贡献或变化；
- 本层主因和次要因素；
- 数据来源与质量说明；
- 建议继续分析的下一层，但不自动执行；
- 无法解释时明确缺失的数据或知识。

### 停止条件

完成一层分析后默认停止。以下情况也必须停止：

- 指标标准身份未确定；
- 当前业务事件与指标的适用关系不明确；
- 下一层维度、公式或漏斗定义缺失；
- 取数不完整或计算无法闭合；
- 当前层没有足够数据支持归因。

## 六、专题 Skill 的建议边界

专题 Skill 需要显式声明：

1. 从哪个指标或节点开始；
2. 一共包含哪些层级；
3. 每层使用什么方法和数据；
4. 进入下一层的筛选条件；
5. Top N 和停止条件；
6. 哪些步骤可以并行；
7. 最终报告结构；
8. 数据不足时怎样降级，而不是自由补全。

渠道专题已有完整方法；其他专题是否也存在对应的长 Skill，需要根据本地材料或用户后续确认分别判断，不能由“有四个业务方向”直接推导出“四个长 Skill”。

## 七、推荐架构

```text
经营分析请求
  ↓
范围识别与一次性澄清
  ├─ 完整专题/完整报告
  │    └─ 对应长专题 Skill
  │         └─ 多层执行 → 完整报告
  └─ 具体指标/具体维度为什么变化
       └─ 指标异动分析 Skill
            └─ 当前节点 → 下一层 → 输出并停止

两条路径共同使用
  ├─ 共享取数 Agent
  ├─ 标准指标、维度和时间规则
  ├─ 贡献与漏斗计算脚本
  ├─ 数据完整性和闭合校验
  └─ 标准指标身份与数据来源保护
```

## 八、为什么这个设计更合理

1. **符合用户真实意图**：要完整报告和只问一个原因是两种不同任务，不应使用相同深度。
2. **减少无效查询**：局部问题不重新扫描全局，也不自动下钻多层。
3. **降低延迟和成本**：普通问题只执行一层数据请求和分析。
4. **提高可控性**：每轮只推进一层，更容易校验、解释和停止。
5. **保留完整能力**：需要全景报告时，长专题 Skill 仍能从头到尾执行。
6. **支持自然追问**：用户可以基于上一层结论继续追问下一层，形成可控制的渐进分析。

## 九、需要评测的重点

- “生成渠道报告”是否稳定命中完整专题 Skill；
- “为什么某渠道某指标下降”是否稳定命中指标异动分析；
- 模糊问题是否先澄清分析范围；
- 局部异动分析是否严格在一层后停止；
- 用户继续追问时是否正确继承上一层节点、指标和时间；
- 完整专题 Skill 是否按层推进并避免遗漏；
- 两条路径是否使用相同的标准指标和数据计算逻辑；
- 最终输出是否保留实际指标身份、来源和分析边界。

## 十、当前确认与未知项

### 用户已确认

- 完整渠道分析报告调用完整长专题 Skill；
- 普通局部指标变化问题调用指标异动分析 Skill；
- 指标异动分析只做一层，不默认多层下钻。

### 仍需以后补充

- “一层”的正式字段表示和不同专题的下一层映射；
- 除渠道之外，还有哪些完整长专题 Skill 已经实际存在；
- 用户留存归因的完整方法；
- 局部分析后，自动推荐下一层与用户显式确认之间的具体交互形式。
