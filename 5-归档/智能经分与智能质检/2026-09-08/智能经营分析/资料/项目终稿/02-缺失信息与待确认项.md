# 智能经营分析项目缺失信息与待确认项

> 版本：v1.2（与完整介绍草案同步）
>
> 原则：只记录会影响项目理解、技术追问或事实边界的缺口。历史准确率精确数字不在本清单中，终稿统一写“约 90%”；后续复现和简历数字由用户自行处理。

## 一、总体判断

现有材料已经足够完整介绍项目，不存在阻塞主文档的结构性缺口。剩余问题主要影响三个层面：

1. 某些能力是否已经形成强运行时约束；
2. 若被深入追问，能否说清精确实现与版本；
3. 若要做量化证明，是否有统一统计和原始报告。

## 二、P0：会影响核心事实或可靠性结论

### 2.1 业务事件与指标适用性

- 已确认现状：分析方法知识会给出推荐指标，用于缓解非专家选错指标。
- 尚缺：是否后来建立了事件—指标的强适用性规则、阻断逻辑或人工确认门禁。
- 影响：不能把“推荐指标”写成“所有业务事件都完成强校验”。

### 2.2 报告标准指标身份保护

- 已确认现状：查询和分析链路保留标准指标身份；历史事故发生在报告生成模型把标准名改写成用户口语。
- 尚缺：是否已经上线不可改写字段、引用绑定和生成后一致性校验。
- 影响：当前只能把它写成已定位问题和最终架构要求，不能宣称生产中已经完全杜绝。

### 2.3 用户留存归因的完整方法

- 已确认现状：它是四类常规经营分析之一。
- 尚缺：核心指标、输入、下钻维度、分析步骤、停止条件、报告模板和代表性案例。
- 影响：主文档只能介绍方向，不能像保费、渗透率和渠道归因一样展开机制。

### 2.4 开放分析的证据校验

- 已确认现状：开放分析已有 Agent + Skill + 数据取数与报告链路。
- 尚缺：Judge 或报告校验是否稳定读取结构化 `DataEvidence`、图表底层数据和必要 Trace。
- 影响：只看最终报告能够发现自相矛盾和明显编造，但不能独立证明底层查询真实正确。

### 2.5 高影响报告的人工审核边界

- 已确认现状：结果会进入周报、会议追问和管理讨论。
- 尚缺：哪些报告必须审核、谁审核、怎样发布、驳回后怎样修改，以及主动推送是否存在门禁。
- 影响：不能把“可选人工审核”描述成已经覆盖所有重要报告的固定流程。

## 三、P1：会影响技术深度和可复现性

### 3.1 任务契约的生产字段

- `QuerySpec`、`AnalysisTask`、`DataEvidence` 和 `AnalysisResult` 已形成完整架构语义。
- 尚缺它们在真实生产中的字段名、Schema 版本、必填规则和错误返回结构。

### 3.2 强制工具调用机制

- 已确认 Agent 会查询指标库、维度库和日期脚本。
- 尚缺：如果模型跳过调用，运行时是否能够硬阻断，还是主要依赖 Skill / Prompt 约束。

### 3.3 指标与维度覆盖统计

- 当前口述为 100 多个原子指标、100 多个维度池、单指标通常约 10 个可用维度。
- 尚缺统一统计口径、版本日期和去重规则。

### 3.4 SQL 降级链路

- 尚缺一条完整脱敏 Trace，说明标准数据路径失败后怎样选择表、生成 SQL、预检、执行、验证和向用户提示较低可信边界。
- `mtdata bi`、Talos 或其他 SQL 入口的实际生产关系尚未统一。

### 3.5 缓存细节

- 已确认历史数据缓存和当日首次查询更新。
- 尚缺缓存键、粒度、文件格式、刷新与失效、并发首查、数据回刷、失败恢复和错误缓存治理。

### 3.6 记忆数据结构与存储分工

- 已确认数据库和 Wiki 两类存储、两条写入链路及五项已实现能力。
- 尚缺数据库 / Wiki 各自承载对象、权威事实源、同步关系、召回排序、有效期、更新删除和跨用户隔离机制。

### 3.7 业务知识层当前落地范围

- 已识别基础知识、WBR / MBR、OP 和 PRD 四类知识源。
- 尚缺当前已结构化、已审核、已入库和生产可检索的数量，以及有效期、冲突和失效流程。

### 3.8 多轮上下文继承

- 真实问题曾出现追问没有正确继承上一轮分析对象和数据来源。
- 尚缺稳定修复方案及跨会话、同会话、群聊三种上下文的差异说明。

### 3.9 定时任务和周报链路

- 尚缺触发器、固定模板、是否携带周报上下文、缓存 / 重查策略、人工审核、补跑和失败恢复的统一说明。
- WBR 自动化材料记录了确定性流水线和部分图表自动化，但真实发布版本、作者、运行频率与稳定性仍需核对。

### 3.10 版本时间线

- v3.0、v4、V13、V16、“16 次迭代”和 2026-03-19 人工测试尚未形成统一版本表。
- 影响：主文档目前使用阶段时间线，不引用这些版本之间的精确演进关系。

## 四、P2：不会阻塞项目介绍，但影响量化证明

### 4.1 使用数据

当前没有统一统计或不要求补齐的内容：

- DAU / WAU；
- 高频用户精确人数；
- 日 / 周请求量；
- 周报真实运行次数；
- 报告和答案采纳率；
- 主动提醒的真告警、误报和业务处置数量。

没有数据时，终稿明确写“未统计”，不反推或估算。

### 4.2 性能和稳定性

- 缺统一的 P50 / P95 端到端延迟；
- 缺缓存命中率和优化前后同一查询对比；
- 缺 Agent、工具和平台错误率；
- 缺定时任务按时、迟到、重复和补跑统计。

### 4.3 Token 和成本

- 曾有每日约 8,000 万 Token 的口述量级；
- 尚缺统计窗口、模型范围、输入 / 输出、人工 / 定时任务和各能力拆分；
- 因此主文档不将 Token 量级写成业务成果或成本优化证明。

### 4.4 评测复现信息

- 题集版本、题型分布、环境版本、Judge 模型与 Prompt、有效 / Invalid / Fail 口径和完整运行报告尚未统一归档；
- 这些会影响不同版本之间的小幅比较，但不再影响终稿使用“约 90%”的历史量级表达。

## 五、结构口径：本版已做的临时选择

为了让主文档层次清楚，v1.2 暂时采用：

1. 报告与可视化属于分析输出层，不单列为一级业务能力；
2. 记忆属于横向共享能力，不与取数、分析并列；
3. 定时任务属于非会话入口和主动交付方式，不单列为分析类型。

这三项只影响文档分组，不改变项目实际能力。用户后续如果给出新的一级分类，直接调整目录结构即可。

## 六、不再追踪的事项

- 不再核对不同时期 70%、80%+、87%、90%+ 等历史数字之间的对应关系；
- 不再把“原项目已实现 / 统一平台提供 / 理想补充”作为架构逐节点必填分类；
- 不再要求补齐 DAU / WAU 等并不存在的统计后才能完成终稿；
- 不再把后续准确率复现和简历数字更新列为 Codex 任务。
