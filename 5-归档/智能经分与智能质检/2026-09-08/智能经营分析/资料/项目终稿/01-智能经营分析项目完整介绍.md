## 一、项目总览：让运营和业务无需专业数据知识，也能自助、自由取数并完成经营分析

智能经营分析项目是面向美团金融场景险运营和业务人员的一站式取数与经营分析 Agent。它的核心不是把数据转换成结论，而是把原本需要数据开发和商分参与的专业工作内化到系统中：用户不需要掌握 SQL、指标平台、数据表、专业指标口径或分析方法，就可以用自然语言自助、自由地取得准确数据，并继续完成经营分析。

这里的“自助”是指运营和业务能够独立发起并完成常规取数与分析，不必先向数据开发提需求、再等待商分加工；“自由”是指用户既能查询不同指标和维度，也能从自己的真实业务问题出发做固定或开放分析，而不是只能使用预设看板和固定报表。“自由”不等于模型不受约束，底层数据、计算和权限仍然由受控工具保证。

项目建立在既有指标平台、数据集和数仓能力之上，当前覆盖约 20–30 名场景险产运、商分及相关业务用户。

它不是一个简单的自然语言转 SQL 工具，也不是让大模型自由生成分析报告。项目的核心方法是：

> **把确定性规则交给代码和受控工具，把成熟业务经验沉淀为 Skill，把无法预先穷举的长尾问题交给 Agent 在受控边界内自主分析，并让关键结论能够回到标准指标和数据证据。**

为了实现这种业务自助能力，项目形成了五个层次：

1. **自助入口**：让用户直接用自然语言表达取数或分析诉求，无需先转换成专业数据需求。
2. **可信取数**：通过澄清、标准化、执行和验证，让非数据专业用户也能取得准确数据。
3. **自由分析**：把保费、渗透率、渠道归因和用户留存归因等成熟方法沉淀为 Skill，同时支持从真实业务问题出发的开放分析。
4. **交付闭环**：生成图表、报告、周报和异常提醒，并支持用户在会议或业务讨论中继续追问。
5. **专业能力底座**：把指标、维度、时间、查询、计算、知识、记忆和评估等专业能力放到系统内部，对用户隐藏复杂度。

## 二、为什么要做：让运营和业务从“依赖专业人员”转向“自己完成”

### 2.1 业务背景

场景险经营分析涉及多个险种、多套核心指标、多层渠道、商户类型、用户类型和时间口径。过去一项需求通常需要经过“业务描述问题 → 数据开发理解并取数 → 业务确认口径 → 商分分析 → 再次解释和修改”的多轮协作，成本不仅是等待时间，也包括跨角色的信息损耗和反复沟通。

按照用户真实目的，需求先分成取数与分析两大类；分析类再分为经营分析（开放式）、异动分析和常规经营分析：

| 一级类型 | 具体形态 | 用户真正想做什么 | 常见交付 |
| --- | --- | --- | --- |
| 取数 | 探数、取数、看数 | 查看某个数值、了解某组数据，或为了判断一件事先取得必要数据 | 指标结果、明细或汇总表 |
| 分析 | 经营分析（开放式） | 围绕一个临时业务问题探索趋势、结构、差异和可能原因 | 图表、分析结论和报告 |
| 分析 | 异动分析 | 已知某项指标发生异常，希望定位异常来自哪里、为什么发生 | 下钻归因、原因候选和排查建议 |
| 分析 | 常规经营分析 | 对稳定、重复出现的经营问题按成熟方法持续分析 | 常规分析报告、周报或定时任务 |

2025 年项目先完成核心指标线上化和接口化，使指标能够被标准化查询，并在此基础上搭建过多个 Workflow。这个阶段解决了“数据可以被系统访问”的基础问题，但没有完全解决以下现实矛盾：

- 业务用户仍需要知道应该查哪个指标、选哪些维度、如何理解同比环比；
- 复杂查询仍依赖数据或商分人员，传统看数至少要等待半天；
- 一份常规分析报告通常需要商分投入 2–3 天；
- 商分的分析方法掌握在少数人手里，难以被普通运营直接复用；
- 固定看板能够回答已知问题，但难以覆盖管理者临时追问和长尾分析；
- 大模型可以快速生成完整报告，但如果指标、口径或证据错了，文本越完整，误导风险反而越大。

### 2.2 项目目标

项目最初的愿景是“让每一个运营都有自己的商分”。这里的核心不是把数据转换成一份结论，而是消除运营和业务完成常规取数与经营分析时对专业角色的前置依赖：

> **运营和业务不需要依赖数据开发，不需要依赖商分，也不需要掌握专业数据知识，就可以自己取得准确的数据，并根据真实业务问题继续完成经营分析。**

这不等于组织中不再需要数据开发和商分，而是常规任务不再必须经过他们才能完成：数据开发和商分负责建设、治理和沉淀底层专业能力，运营和业务通过 Agent 直接使用这些能力。

这意味着项目必须同时满足五个目标：

1. **自助**：用户能够独立完成任务，不必先向数据开发或商分提需求。
2. **自由**：既支持常规查数和常规经营分析，也支持从局部异常或临时问题开始分析。
3. **准确**：数据、口径、时间、维度和计算正确，不编造。
4. **低门槛**：用户不需要理解 SQL、数据表、复杂指标公式和专业分析流程。
5. **有边界**：不确定、能力未覆盖或证据不足时能够澄清、降级、停止或请求人工复核。

### 2.3 系统边界

项目负责提供取数、分析、解释、图表、报告和提醒，不直接代替业务负责人做高风险经营决策，也不自动执行保险策略、营销配置或其他产生业务后果的动作。用于重要汇报或主动推送的高影响结论，应保留证据展示和人工审核边界。

## 三、项目的核心技术难点：要做到自助、自由且准确，难在哪里

业务核心问题已经在上一节明确：运营和业务完成取数与经营分析时依赖数据开发和商分，专业门槛和协作成本都高。本节不再重复业务问题，而是说明这个项目在技术上难在哪里。下面四组矛盾，是实现“无需专业数据知识也能自助、自由且准确地完成任务”时必须解决的核心技术难点。

### 3.1 自然语言的模糊性与数据规则确定性之间的矛盾

用户会使用简称、近义词、业务黑话和不完整时间表达。例如“看上周新商餐饮渗透率”至少需要确定：

- “渗透率”对应哪个标准指标；
- “新商”和“餐饮”分别属于哪个标准维度及标准维度值；
- “上周”的起止日期；
- 该指标是否支持这些维度；
- 应从哪个数据集、指标平台或 SQL 路径查询；
- 比率指标应该怎样聚合和重算。

如果这些确定性问题交给模型自由推理，最终数字可能形式合理但口径错误。项目因此将“澄清—实施—验证”确立为可信取数主线。

### 3.2 专家完整分析路径与用户局部问题之间的矛盾

商分的标准方法通常从全局开始：总体变化 → 维度下钻 → 局部原因 → 漏斗定位。但运营常常已经发现了某个局部异常，只想知道“我负责的这个渠道为什么下降”。如果 Agent 仍从总体开始跑完整流程，会出现三个问题：

- 重新查询大量无关数据；
- 回答偏离用户当前关注点；
- 查询和分析时间明显增加。

项目因此不再把完整专题写成只能从头执行的大 Workflow，而是把分析方法拆成下拆、漏斗、趋势、贡献等基础能力，由 Agent 根据用户当前节点组合执行。

### 3.3 开放性与可信度之间的矛盾

固定 Skill 能保证成熟场景稳定，但不可能预先覆盖所有临时问题；开放分析能够提高覆盖率，却会放大模型自由生成、错误路由和证据缺失的风险。

真实的新员工错误汇报案例说明：系统即使正确理解了用户口语，也可能查询一个合法、可计算、但不适用于目标业务事件的指标；如果最终报告又把标准指标名改写成用户口语，复核者甚至看不到真正使用了什么指标。

因此项目的关键可靠性问题不是单纯提高意图分类准确率，而是建立：

```text
业务目标
→ 推荐/适用指标
→ 标准指标身份
→ 查询证据
→ 分析结论
→ 最终报告
```

之间的完整一致性链路。

### 3.4 大数据量、长耗时与模型上下文之间的矛盾

长周期查询可能需要十几分钟到半小时，复杂任务甚至更久；全量结果如果直接进入模型上下文，会产生 Token 压力和上下文污染。项目同时从两个方向解决：

1. 稳定历史数据缓存复用，当日数据按需增量更新；
2. 全量结果落文件，模型只读取少量预览和结构化汇总，聚合统计由代码直接读取全量文件完成。

## 四、能力版图：从口径咨询一直到主动交付

为了便于理解，本终稿把项目能力组织为四个面向用户的能力组和三个横向支撑层。报告与可视化作为分析输出，记忆作为横向能力，定时任务作为非会话入口和交付方式。

### 4.1 数据与口径咨询

- 查询标准指标名、定义、公式、单位、支持维度、更新时间和数据来源；
- 查询业务术语、险种规则、业务流程和指标差异；
- 当指标或术语有歧义时，展示标准候选和定义并要求用户确认；
- 将咨询结果作为后续取数或分析的证据，而不是只输出自然语言解释。

### 4.2 可信取数

- 从自然语言中拆出指标、维度 / 维度值、时间、粒度、筛选和对比方式；
- 通过指标库、维度库和日期脚本完成标准化；
- 根据指标元数据获得支持维度、数据集和查询方式；
- 优先走受控指标平台或标准数据集，超出覆盖范围时进入 SQL 降级路径；
- 对比率、复合指标、同比环比等使用确定性脚本；
- 输出带标准指标身份、时间、来源、质量信息和异常说明的数据证据；
- 指标—维度组合不支持时明确返回边界，并给出可行替代方案。

现有口述范围为 100 多个原子指标、100 多个维度池，单个指标通常支持约 10 个维度；这些数字用于说明能力规模，统计口径仍未做最终审计。

### 4.3 经营分析

经营分析分为常规经营分析和开放式经营分析。

常规经营分析使用已沉淀的方法、步骤、停止条件和报告模板。当前正式名称统一为：

1. **保费**：围绕保费规模、单均保费、订单渗透率和订单基数拆解变化及目标 Gap。
2. **渗透率**：分析商户或订单渗透率的趋势、分子分母变化、结构差异和背离。
3. **渠道归因**：从全渠道到一级渠道、二级渠道、漏斗环节和 source 逐层定位主因。
4. **用户留存归因**：围绕用户或商户的新增、留存、退出及其结构变化进行归因；当前材料尚缺完整的执行步骤说明。

开放分析不要求唯一分析路径。主 Agent 明确目标和边界后，将完整任务交给分析 Agent；分析 Agent 可以参考已有 Skill，自主拆解取数任务、选择下钻顺序、解释证据、调整计划并形成报告，但所有关键数据仍需经过共享取数链路。

### 4.4 输出、交互与主动交付

- 生成与数据证据一致的图表和结构化报告；
- 支持用户对既有结果进行多轮追问和进一步下钻；
- 自动生成周报及初步分析，支持管理者提出问题后由运营实时追问；
- 通过定时任务分析流量和资源位，识别异常并向业务推送简易报告；
- 对高影响报告保留人工审核和发布确认入口。

### 4.5 横向支撑

| 支撑层 | 作用 |
| --- | --- |
| 知识 | 指标口径、业务术语、业务事件、专家分析方法、报告模板 |
| 记忆 | 用户信息、用户偏好、会话摘要与详情、跨会话任务状态、历史分析经验和冲突记忆选择 |
| 治理 | 权限、脱敏、结构化字段与格式、超时、重试、预算、Trace、审计、校验和停止条件 |

## 五、整体技术架构：受控编排与有界自主结合

### 5.1 架构总原则

项目不把所有步骤写死成传统 Workflow，也不把所有权力交给模型。核心设计是：

> **平台代码定义边界、状态、契约和停止条件；Agent 在边界内理解问题、澄清、规划、选择工具并处理可恢复错误。**

### 5.2 五层架构

```text
用户 / Web / 大象 / 定时任务 / Agent 协作
  ↓
主 Agent：对话、意图、通用澄清、高层计划、上下文组装、最终回复
  ↓
受控意图路由
  ├─ 口径咨询：主 Agent + 只读元数据工具
  ├─ 取数查数：结构化取数任务 → 取数 Agent → 带来源的取数结果
  ├─ 经营分析：结构化分析任务 → 分析 Agent → 分析结果
  └─ 通用兜底：能力探索、继续澄清、重新路由或明确拒答
  ↓
Tool Gateway：日期、指标、维度、复合计算、数据集、BI / SQL、文件与缓存
  ↓
公司数据能力：指标平台、标准数据集、数仓服务和共享文件

全链路共享：业务知识、用户记忆、历史分析经验、Skill、模板、权限、
Schema 校验、预算、超时、重试上限、Trace、审计和 checkpoint
```

### 5.3 四个核心 Agent 角色

| 角色 | 核心职责 | 明确不负责 |
| --- | --- | --- |
| 主 Agent | 对话、意图、澄清、高层计划、上下文组装和最终回复 | 不亲自执行详细数据分析 |
| 取数 Agent | 在授权工具范围内选择查询方式、处理可恢复错误并形成数据证据 | 不生成脱离查询证据的业务结论 |
| 分析 Agent | 详细计划、取数拆分、证据解释、迭代下钻、图表和报告 | 不绕过取数 Agent 直接访问底层数据 |
| 通用兜底 Agent | 探索系统能力、补充澄清和重新路由 | 不拥有全部底层工具，不把未知问题强行回答 |

口径咨询不单独创建 Agent，由主 Agent 调用只读元数据工具完成。保费、渗透率、渠道和留存也不各自创建 Agent，而是同一个分析 Agent 加载不同 Skill 和模板。

### 5.4 四类结构化任务与结果对象

这一层不是一个额外的独立功能，而是在说明 Agent 之间怎样传递信息：不能只传递一段容易被改写的自然语言，而要用固定字段说明“查什么、怎样查、实际查到了什么、结论依据是什么”。下列中文名称只用于解释架构关系，不代表生产系统一定使用这些类名。

| 结构化对象 | 主要内容 | 价值 |
| --- | --- | --- |
| 取数任务 | 标准指标、维度、筛选、时间、粒度、对比方式和查询约束 | 把自然语言需求变成可以检查和执行的取数参数 |
| 分析任务 | 分析目标、范围、指标、业务上下文、约束、Skill 和交付要求 | 防止主 Agent 只传一句模糊问题给分析 Agent |
| 带来源的取数结果 | 实际标准指标、查询结果、数据来源、时间、质量、异常和运行记录 | 让后续分析知道数字究竟从哪里来、实际查的是什么 |
| 分析结果 | 结论、依据、图表、报告、不确定性和未解决项 | 保证最终回复不丢失数据依据和分析边界 |

### 5.5 平台控制与 Agent 自主的边界

| 平台确定性控制 | Agent 边界内自主判断 |
| --- | --- |
| 可进入哪些路径 | 当前信息是否足够 |
| 契约和 Schema 是否合法 | 需要向用户追问什么 |
| 可使用哪些 Tool 和数据 | 在授权工具中如何选择 |
| 权限、预算、超时、循环和重试上限 | 如何分类错误并选择恢复方式 |
| checkpoint、Trace、日志和审计 | 分析的详细下钻计划 |
| 高影响操作的人工门禁 | 继续、调整计划还是停止 |

## 六、核心执行链路：项目是怎样把问题变成可信结果的

### 6.1 口径咨询链路

```text
识别咨询对象
→ 判断是否存在歧义
→ 必要时向用户澄清
→ 调用只读指标 / 业务元数据工具
→ 返回标准名称、定义、公式、维度、来源和质量信息
→ 主 Agent 形成带证据的解释
```

### 6.2 可信取数链路

```text
用户自然语言
→ 拆分指标、维度 / 维度值、时间、粒度和筛选
→ 指标库 / 维度库检索与候选澄清
→ 日期脚本生成确定时间窗口
→ 组装结构化取数任务
→ 取数 Agent 选择标准指标平台、数据集或 SQL 路径
→ 确定性计算与结果校验
→ 形成带标准指标和来源的取数结果
→ 主 Agent 返回数值、口径和证据边界
```

这条链路中的关键不是“模型一次猜对”，而是即使首次理解不完整，也能通过候选确认、工具返回的能力边界和二次澄清完成任务。

### 6.3 常规经营分析链路

```text
明确分析目标和当前异常节点
→ 命中对应常规经营分析 Skill
→ 加载所需指标、分析步骤和停止条件
→ 从用户当前节点开始下拆或进入漏斗
→ 通过共享取数 Agent 获取带来源的取数结果
→ 计算贡献、解释变化并继续下钻
→ 生成图表和报告
→ 校验数据、指标名、图表和结论一致性
```

### 6.4 开放分析链路

开放分析采用“主 Agent 高层规划 + 分析 Agent 详细执行”的方式：

1. 主 Agent明确用户真正要解决的问题、范围、交付形式和风险边界；
2. 将完整上下文组装成结构化分析任务；
3. 分析 Agent 根据已有 Skill 和通用分析原则生成详细计划；
4. 将计划拆为一个或多个结构化取数任务，统一调用取数 Agent；
5. 根据带标准指标和来源的取数结果决定继续下钻、调整计划、补充澄清或停止；
6. 证据足够后生成图表与报告；
7. 报告必须区分数据事实、业务解释、假设和未解决项。

### 6.5 通用兜底链路

当问题无法匹配咨询、取数或分析路径时，兜底 Agent 先查询能力目录并继续澄清。能够转化时重新进入专业路径；不能转化时明确说明无法完成的原因。兜底不是“万能 Agent”，更不能绕过专业数据能力自由查数。

## 七、关键工程机制：真正决定项目效果的不是 Prompt，而是约束和数据链路

### 7.1 指标、维度和时间分别标准化

项目不会把整个问题压缩成一个模糊“意图”。它把需求拆为三类对象：

```text
MetricSpec：标准指标、支持维度、数据集和查询方式
FilterSpec：标准维度、标准维度值
TimeSpec：确定的开始日期、结束日期和对比周期
```

指标优先使用用户原话检索：完全匹配时确定标准身份；不完全匹配时展示标准候选和定义，由用户确认；原话没有合适结果时，模型才根据理解改写检索词。相对时间全部交给脚本计算，不由模型心算。

### 7.2 确定性计算下沉到脚本

项目将以下高风险计算从自然语言推理中移出：

- 自然周、月累计、同比、环比等日期范围；
- 比率型指标的分子 / 分母汇总后重算；
- 复合指标和派生指标公式；
- 保费等乘积模型的贡献拆解；
- 数据聚合、过滤、分组和排序。

模型负责选择正确的计算方法和解释结果，不负责逐行心算或自由创造公式。

### 7.3 平台优先、SQL 降级

指标库同时提供查询路由。能走标准指标平台或数据集时优先使用受控路径；覆盖不到的长尾需求才进入 SQL。SQL 路径需要表结构、过滤、关联、时间和业务口径的额外校验，不能因为 SQL 能执行成功就认为数据正确。

### 7.4 大结果集采用“文件为主、上下文为辅”

平台查询固定调用全量导出 / 下载接口，不让模型决定是否只取第一页。全量结果保存在文件中：

- 模型只读取前 200 行预览，用来检查结构、格式和明显异常；
- 全量聚合和统计由代码直接读取文件；
- 模型只接收字段、总量、汇总、异常和必要样例；
- 最后再检查聚合结果是否合理。

这同时解决了静默分页不完整和全量明细污染上下文两个问题。

### 7.5 分析方法从“大流程”解构为可组合能力

早期 Workflow 和大 Skill 能运行，但建设维护较重，而且默认从全局开始。项目后来把方法拆成可组合的基础能力，例如：

- 趋势确认；
- 指标分子分母拆解；
- 维度逐层下拆；
- 漏斗环节定位；
- 结构贡献分析；
- 目标 Gap 拆解；
- 证据解释和停止判断。

Skill 保存的是分析方法和边界，Agent 根据用户当前问题决定从哪里进入、怎样组合，而不是机械执行所有步骤。

### 7.6 历史缓存与当日更新

对两三年以上的长周期分析，历史数据不会每次重新查询。项目将稳定历史结果缓存到统一文件，由每天首次查询补充当日数据，后续请求复用已经缓存的历史部分。这是一种“稳定历史数据复用 + 当日数据惰性刷新”的机制。

### 7.7 知识与记忆分开治理

知识用于保存组织共识和权威业务信息，包括指标口径、业务规则、分析方法、业务事件和报告模板；记忆用于保存与用户和任务相关的个性化上下文。

当前已确认的记忆对象包括：

- 用户长期信息和偏好；
- 会话摘要和会话详情；
- 按 Task / 专题组织的跨会话进度；
- 用户历史分析经验；
- 冲突记忆的选择。

写入分为会话内主动写入和闲时批量整理两条路径。正式业务规则不能因为一次用户纠错被个人记忆覆盖；个人经验如果要升级为团队方法，应经过抽象和审核后进入知识或 Skill。

### 7.8 有限重试、可恢复错误与明确停止

取数 Agent 可以在受控上限内修正参数、切换授权方法或重试，但不会无限循环。权限拒绝、参数不合法和能力不支持等不可恢复问题应直接澄清或停止；只对瞬时、幂等、可能恢复的错误重试。涉及文档写入或消息推送时，还需要避免重复交付。

## 八、四类常规经营分析怎样工作

### 8.1 保费分析

保费分析可使用统一业务链路：

```text
保费 P = 单均保费 A × 订单渗透率 R × 订单基数 Q
```

分析先判断整体保费变化，再分别检查订单基数、渗透率和单均保费；需要定量归因时，对三个因子的变化做贡献拆解，并检查贡献之和能否闭合到总变化。目标分析则把目标值作为基准，拆解实际与目标之间的 Gap。

### 8.2 渗透率分析

渗透率分析不会只看一个百分比，而是：

1. 明确指标的分子、分母和聚合方式；
2. 确认趋势拐点和时间粒度；
3. 分别比较分子、分母的变化速度；
4. 按商户、渠道、用户类型等维度检查结构差异；
5. 区分“分子增长”“分母缩水”“分母膨胀”和结构迁移等机制；
6. 将直接数据证据与进一步业务解释分开。

### 8.3 渠道归因

渠道归因使用逐层收敛的方法：

```text
全渠道异常确认
→ 一级渠道定位主因
→ 二级渠道继续下钻
→ 漏斗环节定位
→ source / 资源位定位
→ 结合业务事件形成排查建议
```

周期率值必须用周期分子之和除以周期分母之和，不能对每日比率直接求平均。渠道贡献、漏斗变化和因果结论也必须区分：变化幅度或贡献度只能说明“哪里发生变化”，业务事件只能先作为原因候选，不能未经验证直接写成因果。

### 8.4 用户留存归因

该方向已确认属于四类常规经营分析之一，主要面向新增、留存、流失 / 退出及其结构变化。现有材料能够证明周报和分析中存在留存、退出相关主题，但尚未形成与保费、渠道同等完整的指标链路、分层顺序和归因公式；正文因此不继续补造执行细节。

## 九、代表性案例：商户渗透率上升，订单渗透率却下降

一个典型问题是：准时宝商户渗透率持续上升，但商家付费订单渗透率在 7 月中旬见顶后回落，为什么两个指标发生背离？

### 9.1 先校正时间口径

月度数据中，7 月相对 6 月的两个指标都上升；订单渗透率是在 7 月中旬见顶后按周回落，并在 8 月月度数据中表现为下降。因此更准确的表述是：

> **背离从 7 月下旬的周度趋势开始，在 8 月月度数据中明确体现。**

### 9.2 再拆分子分母

商户渗透率为“活跃在保商户 ÷ 外卖活跃商户”。在保商户也略有下降，但外卖活跃商户大盘下降更快，分母收缩速度高于分子，因此商户渗透率被动上升。

商家付费订单渗透率为“商家付费投保订单量 ÷ 餐饮订单总量”。进入 8 月后，餐饮订单总量增长速度高于商家付费投保量，分母增长更快，因此订单渗透率下降。

### 9.3 最终解释

> 商户渗透率上升属于“分母缩水型”被动上升；订单渗透率下降属于“分母增长更快型”稀释。两个指标分别受商户存量和订单流量影响，分子分母的相对变化速度不同，形成背离。

这个案例体现了项目不是只给出一条趋势，而是完成“时间口径校正 → 指标公式确认 → 分子分母拆解 → 证据与业务解释分离”的完整分析过程。

## 十、项目演进：逐步放开模型自由度，同时补上可靠性边界

| 阶段 | 主要目标 | 关键建设 | 形成的认识 |
| --- | --- | --- | --- |
| 2025 年 | 指标线上化与便捷取数 | 核心指标接口化，在数据底座上搭建多个 Workflow | 数据可访问是 Agent 的前提，但 Workflow 建设维护较重 |
| 2026 年 3–4 月 | 可信取数 | 澄清、脚本化、指标支持范围工具、日期与复合计算工具、结果验证 | 高确定性问题不应交给模型自由推理 |
| 2026 年 4–6 月 | 专家分析方法产品化 | 商分、运营和技术共同沉淀 Skill；常规经营分析 | 专家方法可以复用，但完整大流程不适合所有用户入口 |
| 2026 年 4–6 月后 | 分析能力解构 | 将大分析拆成下拆、漏斗等基础能力 | Agent 应从用户当前异常节点开始，而不是机械从全局扫描 |
| 2026 年 8 月前后 | 开放分析、性能和可信度 | 长周期缓存、统一引擎迁移、开放分析和证据链治理 | 能力覆盖不再是唯一问题，安全失败和报告可信更重要 |

这条时间线体现了项目的核心演进逻辑：

> **先把取数做准，再把专家方法做成可复用能力，最后开放自主分析；模型自由度越高，证据、校验、停止和人工审核的要求也越高。**

## 十一、评估体系：既看最终结果，也能定位失败发生在哪里

### 11.1 三层评估框架

```text
第一层：顶层结果
├─ 数据准确率——只统计数据任务
└─ 端到端任务成功率——覆盖所有任务，区分首跑成功与最终成功

第二层：主体流程诊断
├─ 意图识别
├─ 澄清、拆解与任务组装
├─ 取数 Agent
└─ 分析 Agent：数据请求、图表和报告

第三层：横向质量
├─ 跨会话连续性与记忆
├─ 成本
├─ 延迟、稳定性与回归
└─ 权限、安全拒答与不编造
```

顶层只保留用户能理解的结果指标，过程能力用于诊断和回归，不把每个内部节点都包装成 KPI。

### 11.2 顶层指标

| 指标 | 单题成功条件 | 计算 |
| --- | --- | --- |
| 数据准确率 | 关键指标、时间、维度和数值全部正确 | 数据正确任务数 ÷ 有效取数任务数 |
| 端到端任务成功率 | 必要任务完成，数据硬门槛满足，分析和报告不与证据冲突，无越权和编造 | 成功任务数 ÷ 有效端到端任务数 |

存在唯一标准答案时使用准确率；存在多条合理分析路径时使用 Rubric 判定任务成功率。单题采用整题 Pass / Fail，不用若干局部分数拼成难以解释的总分。

### 11.3 验证器分层

- **确定性验证**：任务 Schema、指标身份、结构化数值、日期、维度集合、公式、触发和交付状态；
- **LLM Judge**：业务问答、开放分析、报告表达和不确定性处理；
- **人工复核**：高价值失败、边界题、Judge 争议题和高影响报告。

能由程序断言的内容不交给 Judge 猜。开放分析的 Judge 不应只看最终文字，还需要读取结构化数据证据和必要图表数据。

### 11.4 题集与回归闭环

评测题来源包括人工业务题、历史真实任务、线上失败 Case 和参数化扩展题。早期使用能力隔离测试快速定位澄清、口径、取数和分析问题；系统成型后以端到端基准为主，失败后回看完整 Trace，标记第一个使任务偏离的错误。

典型失败标签包括：

```text
澄清失败
→ 指标 / 知识未召回
→ 工具或参数错误
→ 日期、维度或指标解析错误
→ 原子数据或公式错误
→ 常规经营分析方法错误
→ 图表 / 报告错误
→ 开放分析无依据结论
→ 记忆未读取或误用
→ 定时触发 / 交付失败
→ 工具重试耗尽
```

每次回归应冻结题集、Agent、模型、Prompt、Skill、Judge、工具和数据 / 知识版本；线上高价值失败经过归因后进入固定回归集。

### 11.5 历史结果口径

项目在不同时期、不同题集和不同重试口径下产生过多个结果。当前统一只使用：

> **历史整体表现约 90%。**

这个数字只表达历史表现量级，不代替数据准确率、分析任务成功率和端到端任务成功率各自的定义，也不宣称是一次新复现得到的精确结果。

## 十二、真实使用方式与落地成果

### 12.1 用户与使用分布

- 覆盖约 20–30 名场景险产运和商分用户；
- 高频用户主要是商分和少数资深业务；
- 普通业务用户更多用于查数，深度开放分析相对较少；
- 老员工能够结合业务经验判断结果，新员工更依赖系统，因此对证据和安全失败要求更高。

### 12.2 典型使用场景

1. **即时查数**：查询指定日期、指标、区域、商户或渠道结果。
2. **临时分析**：针对某个局部异常直接下钻原因。
3. **常规经营分析**：保费、渗透率、渠道归因和用户留存归因。
4. **周报与会议追问**：Agent 生成周报和初步分析；管理者提出问题后，运营继续向 Agent 查数并将结果用于讨论。
5. **主动异常提醒**：每日定时监控流量和资源位，发现异常后推送问题、可能原因和简易报告。

### 12.3 效率与质量成果

| 成果 | 当前可用表达 | 边界 |
| --- | --- | --- |
| 工作方式 | 运营和业务可独立完成常规取数与分析，不再以数据开发和商分介入作为前置条件 | 复杂策略判断和高影响结论仍可能需要专业复核 |
| 协作成本 | 减少需求翻译、口径反复确认、跨团队排期、结果解释和多轮修改 | 当前没有统一金额或人时统计，不量化夸大 |
| 看数效率 | 从传统至少等待半天，转为用户可自助完成 | 没有统一秒级响应统计 |
| 常规分析效率 | 从 2–3 天缩短到约 1–2 小时 | 只指常规专题，不代表所有开放分析 |
| 历史质量 | 整体表现约 90% | 不写成新复现的精确数字 |
| 数据覆盖 | 覆盖核心经营指标及其常用维度 | 长尾口径、别名和 SQL 仍需治理 |
| 业务交付 | 支持图表、报告、周报、实时追问和主动提醒 | 实际频次、采纳率和完整稳定性未统一统计 |

项目的首要价值是改变工作关系：运营和业务不必先把问题翻译成数据需求、交给数据开发取数、再等待商分分析，而是可以在同一个对话中自己完成澄清、查询、分析和追问。效率提升是这种自助模式带来的结果，而不是项目定位本身。

## 十三、项目亮点

项目的第一亮点是把指标口径、数据查询和商分方法这些专业门槛内化到 Agent 中，让不具备专业数据知识的运营和业务也能自由表达问题、自助取得准确数据并完成分析。下面的工程机制都服务于这一核心定位。

### 13.1 从“Prompt 约束”升级为“工程约束”

项目没有停留在写一份规范让模型遵守，而是逐步把指标支持范围、日期语义、比率重算、查询协议和结果聚合下沉为工具与脚本。高频错误被转化为显式执行顺序和可校验状态。

### 13.2 不是让模型算，而是让模型做选择和计划

模型擅长理解、澄清、候选选择和分析规划；代码负责时间、公式、聚合和执行。这个分工既保留 Agent 的灵活性，也降低确定性任务中的幻觉。

### 13.3 共享取数 Agent 统一数据可信边界

直接查数和分析内部取数都走同一个取数 Agent，分析 Agent 不能绕过它直接访问底层数据。这样可以复用指标、权限、完整性和质量校验，并让所有结论都能回到实际查询的标准指标、数据来源和取数结果。

### 13.4 把专家经验拆成可组合的原子分析能力

项目没有把商分方法复制成一条僵硬长流程，而是根据真实运营入口，将完整分析拆成下拆、漏斗、趋势、贡献等能力。Agent 可以从用户当前异常节点开始，减少无效查询并提高适配性。

### 13.5 用文件资产隔离大结果集与模型上下文

完整数据留在文件和代码执行层，模型只读取预览、Schema、汇总和证据引用。这不仅节省 Token，也避免大量相似明细淹没任务目标和指标口径。

### 13.6 评估不只看最终答案，还看首错和可恢复性

项目区分首跑成功与最终成功；同一题重试后通过不等于首跑稳定。失败后定位第一个错误阶段，并将真实线上 Case 回流为回归题，使评估能够直接服务迭代。

### 13.7 真实业务闭环而非演示型问答

结果会进入周报、会议追问和管理讨论，因此项目从一开始就必须同时关注口径、证据、速度、交付和信任，而不只是“能不能回答”。

## 十四、当前仍然存在的边界

项目已经具备完整能力主干，但仍有几类问题不能被“约 90%”掩盖：

1. **事件—指标适用性仍以软引导为主**：分析方法知识库会推荐指标，但还不能证明所有业务事件都经过强适用性校验。
2. **报告事实字段保护需要继续确认**：历史事故中标准指标身份在报告生成层被用户口语替换，是否已经上线强保护和生成后一致性校验尚未完全确认。
3. **开放式经营分析的证据验证弱于常规经营分析**：没有唯一答案时，必须让 Judge 或复核者同时看到数据依据，而不能只看最终文字是否自洽。
4. **SQL 长尾仍有业务口径风险**：SQL 语法正确不等于选表、过滤、关联和指标定义正确。
5. **知识长尾和时效治理仍在建设**：基础知识、WBR / MBR、OP 和 PRD 的结构化、有效期、冲突和引用机制尚未全部闭环。
6. **性能统计不完整**：缓存能显著提速，但缺少统一 P50 / P95、缓存命中率和稳定性数据。
7. **使用与价值统计不完整**：DAU / WAU、请求量、报告采纳率和主动任务实际运行次数没有统一统计时，应如实写“未统计”。
8. **权限与安全依赖平台门禁**：项目需要做端到端验收，但不把平台安全能力改写成业务项目个人成果。

更细的缺失信息集中记录在[《02-缺失信息与待确认项》](02-缺失信息与待确认项.md)。这些缺口不妨碍理解项目主体，但会影响部分技术追问、精确结果或“是否已经完全闭环”的表述。

## 十五、个人职责与协作方式

用户在项目中承担 Agent 技术框架主负责人角色，负责将业务问题转化为 Agent 架构、取数链路、分析 Skill、可靠性机制和评估迭代方案；同时联合业务、产品、商分和数据团队共同完成需求、指标口径、分析方法和数据能力建设。

协作关系可以概括为：

- 业务与运营提供真实问题、使用反馈和业务边界；
- 商分沉淀和审校分析方法；
- 数据团队提供指标、数据集、数仓和口径能力；
- 平台提供运行时、权限、工具接入和公共 Agent 能力；
- 用户负责把这些能力组织成面向场景险经营分析的完整 Agent 方案并推动落地。

这个项目是跨团队共建，不表述为个人独立完成全部底层平台、数据资产和业务规则。

## 十六、最终总结

智能经营分析项目的核心价值，不是把数据转换成结论，也不只是把自然语言翻译成 SQL，而是让运营和业务摆脱完成常规数据工作时对数据开发、商分和专业数据知识的前置依赖：他们可以直接向 Agent 表达问题，自己取得准确数据，并继续完成经营分析。

它形成了一套清晰的方法论：

1. 先以指标线上化和标准数据能力建立可信底座；
2. 用澄清、脚本和验证把取数做准；
3. 将专家分析经验沉淀为可组合 Skill；
4. 用主 Agent、取数 Agent 和分析 Agent 分工支持开放问题；
5. 用文件、缓存、知识和记忆解决大结果集、长周期和连续性问题；
6. 用数据证据、报告校验、评估和失败 Case 回流控制开放分析风险；
7. 最终把工作方式从“等数据开发查数、等商分分析”推进到“运营和业务自助、自由取数并独立完成经营分析”。

项目最核心的定位是：

> **把专业数据知识和分析方法变成 Agent 的内部能力，让非数据专业用户也能自己取得准确数据、理解数据并完成经营分析。**

支撑这一定位的工程判断是：

> **Data Agent 的能力上限不只取决于模型，而取决于数据和知识是否对 AI 友好；它的可信度也不只取决于最终数字是否正确，而取决于从业务目标、标准指标、查询证据到最终报告是否始终保持一致。**
