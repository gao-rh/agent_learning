# 智能经分评估体系：完整审校版 v0.3

> 状态：AI 草案，基于用户口述历史事实、现有讨论记录和外部评估方法复核形成。
>
> 本文同时保存四类内容：**历史真实做法、当前确认口径、可行性审校、待核验证据**。带“约、接近、以上、可能、待核实”的数据不得直接用于正式对外证明。

## 1. 结论摘要

### 1.1 总体判断

当前评估体系的主干合理：

```text
开发初期：能力隔离测试 -> 快速定位与调试
系统成型后：端到端基准 -> 整题 Pass / Fail -> 失败 Case / Trace 归因
```

顶层保留“数据准确率”和“端到端任务成功率”，局部能力只保留必要的准确率 / 成功率和失败标签，避免把每个内部节点都包装成 KPI。这个方向符合 Agent 评估中“先定义成功、再明确任务、环境、验证器和决策方式”的基本结构。[《AI Agents in Depth》第7章](https://bojieli.github.io/ai-agent-book/book/chapter7/)

当前最大缺口不是指标太少，而是：

1. 多数历史结果只有口述比例，没有分子、分母和运行报告；
2. 精确数值题使用 LLM Judge，能运行但稳定性和可复现性弱于确定性比较；
3. 开放分析没有参考答案，Judge 又只看最终报告，无法独立证明数据真实正确；
4. 记忆测试只覆盖已有记忆的读取与使用；
5. 定时任务 100% 缺少统计周期、应执行次数和成功口径；
6. 没有延迟、稳定性和成本治理数据；
7. 工具重试按 3 / 10 次限制，但未按错误是否可重试、幂等性和退避策略设计。

### 1.2 可行性总表

| 模块 | 当前可行性 | 合理性结论 | 主要缺口 |
| --- | --- | --- | --- |
| 顶层指标 | 可行 | 数据准确率 + 端到端任务成功率足够，过程只作归因 | 有效运行和端到端成功的精确定义待统一 |
| 取数澄清 | 基本可行 | 隐藏目标、用户模拟器、工具终点和轮次上限构成了可重复装置 | 精确题量、轮次、工具 Schema、Judge 版本缺失 |
| 业务知识 / 口径咨询 | 基本可行 | 人工题与答案、固定知识来源、最终回答 Judge 适合早期回归 | 20～50 题偏少且可能偏简单，知识 / 接口版本未冻结 |
| 可信取数 | 高层可行 | 200 题、人工标准、冻结日期和版本、复杂题型覆盖较完整 | LLM Judge 不适合承担全部精确数值校验；题型分布未知 |
| 固定分析 | 基本可行 | 有指定方法和参考答案，可以二元判定 | 每种约 5 题，只适合烟测和初期回归 |
| 开放分析 | 部分可行 | 可检查自洽、明显图文冲突和瞎编 | 无参考答案且只看报告，无法独立验证数据和证据 |
| 跨会话记忆 | 部分可行 | 约 10 道真实会话续接题可作烟测 | 只测读取 / 使用，不测写入、更新、遗忘和隔离 |
| 定时任务 | 运行链路可行 | 触发、报告、摘要、群消息形成完整交付链 | 100% 缺少统计窗口；内容正确和业务有用需分开 |
| 成本 / 延迟 / 稳定性 | 未形成评测 | 如实记录“未治理 / 未统计”是合理边界 | 80M Token / 日没有拆分；没有延迟和稳定性数据 |
| 权限与安全 | 平台负责 | 责任边界合理，但不能写成项目已验证成果 | 缺少 Agent 到平台权限边界的集成验证证据 |
| 工具恢复 | 有控制、无评测 | 设置上限优于无限重试 | 3 / 10 次规则未区分错误类型、幂等性和退避 |

## 2. 评估对象与指标结构

### 2.1 顶层结果指标

| 指标 | 定义 | 单题成功条件 | 汇总公式 |
| --- | --- | --- | --- |
| 数据准确率 | 取数任务最终返回正确数据结果的比例 | 题内所有关键指标名称、期间、维度和数值正确 | `数据正确任务数 / 有效取数任务数` |
| 端到端任务成功率 | 各类真实任务最终解决用户问题的比例 | 数据硬门槛满足，必要任务完成，分析 / 报告不与证据冲突，无越权和编造 | `成功任务数 / 有效端到端任务数` |

有唯一标准答案时称准确率；存在多条合理路径、按 Rubric 判断时称任务成功率。统一采用整题 Pass / Fail，不把若干局部得分加权成一个缺乏业务解释的总分。

### 2.2 能力级指标与处理方式

| 能力 | 指标或处理方式 | 是否独立报告 |
| --- | --- | --- |
| 意图识别 | 不作为重点指标，仅保留边界回归和失败标签 | 否 |
| 取数澄清 | 澄清成功率 | 开发 / 回归期可报告 |
| 业务知识与指标口径咨询 | 咨询回答准确率，题型标签分开 | 开发 / 回归期可报告 |
| 可信取数 | 数据准确率 | 是，顶层重点指标 |
| 固定 / 开放分析 | 分析任务成功率，按类型切片 | 是 |
| 报告与可视化 | 并入分析或端到端成功率 | 否，仅作失败标签 |
| 跨会话记忆 | 跨会话连续成功率 | 可报告，但当前只代表读取 / 使用 |
| 定时任务 | 定时交付成功率 | 是，代表触发和交付链路 |
| 串并行与轻度编排 | 不单列指标 | 否；违反依赖或调用失控时判对应任务失败 |

### 2.3 明确不单列指标的内容

| 内容 | 已确认边界 | 为什么不单列 |
| --- | --- | --- |
| 意图识别 | 四类主意图为取数、业务知识咨询、分析、指标口径查询；历史几乎无明显错误 | 粗粒度分类不是主要故障点，保留少量边界题即可 |
| 复合任务的主目标与支撑能力 | 例如“分析 A 为什么下降”的主目标是分析，口径和取数属于分析 Agent 完成任务所需的支撑能力 | 支撑工具调用不等于出现多个一级意图 |
| 主 Agent 详细编排 | 澄清后只需把任务交给取数或分析 Agent；专业 Agent 负责内部步骤 | 项目架构中不存在统一的主 Agent 详细执行链规划模块 |
| 并行 / 串行 | 允许多条合理路径，只要求满足依赖并完成显式目标 | 很难标注唯一正确轨迹；效率由延迟、成本和调用次数观察 |
| 业务知识与指标口径的独立 KPI | 用户侧统一看咨询回答是否正确，数据集保留两类标签 | 底层知识文档与指标接口用于失败归因，不必重复造结果指标 |
| 报告与可视化独立 KPI | 图表和报告作为分析 / 端到端任务的输出 | 关键图表或报告错误直接使整题 Fail，美观只在有明确产品要求时人工验收 |

## 3. 通用评测规范

### 3.1 一条评测任务的最小内容

| 字段 | 作用 | 必要性 |
| --- | --- | --- |
| `task_id` | 唯一标识和回归追踪 | 必须 |
| `capability` / `task_type` | 区分取数、澄清、咨询、固定分析等 | 必须 |
| `initial_input` | 提供给 Agent 的首轮问题 | 必须 |
| `hidden_goal` | 多轮任务的真实目标；不直接泄露给 Agent | 澄清 / 记忆任务必须 |
| `reference_answer` 或 `rubric` | 定义整题成功 | 必须二选一 |
| `environment_version` | 数据、知识、指标接口、工具和时钟版本 | 必须 |
| `termination_rule` | 提交工具成功、最终回答、报告生成、超轮次等 | 必须 |
| `source` | 人工设计、真实线上 Case 或参数化生成 | 建议 |

用户模拟器需要明确“知道什么、不知道什么、不得主动泄露什么”。这与参考章节中将用户已知信息、行为规范、初始状态和验收条件分别建模的做法一致；否则模拟用户容易顺着 Agent 的暗示把任务判成成功。[评估环境与用户模拟器设计](https://bojieli.github.io/ai-agent-book/book/chapter7/)

### 3.2 每次运行必须记录

| 运行信息 | 用途 |
| --- | --- |
| Agent / Harness 版本 | 区分模型能力和系统实现变化 |
| 模型精确 ID | 避免“Claude / GPT”这类泛称无法复现 |
| System Prompt / Skill 版本 | 判断提示词或能力配置变化 |
| 工具、数据、知识、指标接口版本 | 防止 Ground Truth 漂移 |
| Judge 模型与 Prompt 版本 | 保证不同回归轮次可比较 |
| 最终输出与 Trace 引用 | 支持复核和失败归因 |
| Pass / Fail、失败阶段、理由、证据 | 汇总和定位首个错误 |
| Token、延迟、重试次数 | 支持后续成本和稳定性治理 |

### 3.3 有效运行口径

建议统一为：

- Agent、工具或被测依赖发生错误，属于用户真实会遇到的失败，计为 **Fail**；
- 只有评测装置自身损坏，例如测试数据缺失、Judge 服务不可用、模拟器违反隐藏任务约束，才记为 **Invalid** 并重跑；
- 不允许通过大量排除系统错误来抬高成功率。

### 3.4 验证器分层

| 层级 | 适用内容 | 当前历史做法 | 审校建议 |
| --- | --- | --- | --- |
| 确定性验证 | 工具 Schema、任务交接字段、结构化数值、触发 / 交付状态 | 澄清工具有接口校验；其余多依赖 Judge | 能程序断言的继续使用程序断言 |
| LLM Judge | 语义问答、开放分析、报告表达 | 主要验证器 | 固定模型、Prompt 和 Rubric，输出二元结果与证据 |
| 人工复核 | 边界题、Judge 争议、线上高价值失败 | 线上逐 Case 排查 | 复核全部重要失败，并抽检部分通过题 |

参考章节明确建议：凡是能写成程序断言的检查仍使用确定性验证，LLM Judge 用于确实无法机械判定的开放维度；因为 Judge 会有偏见和波动。[LLM-as-a-Judge 与验证器](https://bojieli.github.io/ai-agent-book/book/chapter7/)

Snowflake 的 Agent 评估也把答案正确性、工具选择和工具执行分开，并允许工具顺序存在多条合理路径，说明过程证据适合用于诊断，而不必强制唯一轨迹。[Snowflake Cortex Agent Evaluations](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-evaluations)

### 3.5 失败归因

端到端失败应定位第一个使任务偏离的错误，而不是只记录最终报错：

```text
澄清失败
-> 知识 / 指标未召回
-> 工具选择或参数错误
-> 日期与指标解析错误
-> 原子数据或公式错误
-> 固定分析方法错误
-> 图表 / 报告错误
-> 开放分析无依据结论
-> 记忆未读取或误用
-> 定时触发 / 交付失败
-> 工具重试耗尽
```

生产问题回流为回归题的做法合理。参考章节也建议将用户纠正、负面反馈和规则 / Judge 发现的问题轨迹，经过首错归因后沉淀为回归用例。[失败归因与生产轨迹回流](https://bojieli.github.io/ai-agent-book/book/chapter7/)

### 3.6 端到端任务成功率评测卡

| 项目 | 当前确认内容 | 审校结论 |
| --- | --- | --- |
| 被测目标 | 不限于取数，覆盖咨询、分析和复合任务是否最终解决 | 合理，能够检验完整 Agent / Harness，而不是单一模型或工具 |
| 任务来源 | 人工业务题、历史真实任务和线上失败 Case | 合理；具体题量与构成待核实 |
| 参考标准 | 每题提供人工参考答案；固定分析包含方法要求，开放分析不要求唯一思路 | 合理；开放任务需要 Rubric 而不是唯一答案 |
| 执行 | 从用户首问开始，运行主 Agent、专业 Agent、工具、图表和报告链路，直至最终回答、主动停止或达到轮次 / 资源上限 | 需要在正式回归中固定终止条件 |
| 验证 | LLM Judge 比较最终结果与参考答案 / Rubric，输出 Pass / Fail；失败后检查完整 Trace | 与历史做法一致；数据、工具和触发状态能断言时应增加确定性校验 |
| 单题 Pass | 数据型结果正确；用户要求的必要部分完成；固定方法正确执行；开放分析不瞎编；结论有证据；无越权与编造 | 合理，硬门槛应写进 Judge Rubric |
| 计算 | `通过端到端任务数 / 有效端到端任务数` | 可执行；有效 / Invalid / Fail 需按 3.3 节统一 |
| 历史结果 | 用户另口述整体成功率 90% 以上 | 指标对象和分母不明确，暂不能直接视为端到端任务成功率 |

端到端测试不能替代能力隔离测试：前者回答用户任务是否解决，后者帮助快速复现和定位澄清、取数、分析等具体问题。历史后期以端到端为主、错题再查 Case 的方式合理。

### 3.7 评估结果如何用于决策

历史已确认的使用方式是：不关注连续分数，重点查看 Pass / Fail；失败后逐 Case 改进。当前没有证据表明曾设置正式上线阈值或统计显著性门槛。

本方案建议的最小决策规则：

1. 仅比较同一冻结题集和同一 Judge / 数据 / 工具版本下的结果；
2. 数据错误、权限越界和无依据编造属于硬失败，不被其他优点抵消；
3. 总体成功率上升但某个关键业务类型明显下降时，不直接判定版本更好；
4. 每次版本变更检查新增失败 Case，并将高价值线上失败回流为固定回归题；
5. 在没有足够样本时，不用 1～2 个百分点的小幅变化宣称能力提升。

| 开放分析 | 每种约 5 题；无参考答案 | 同上 | 最终报告 | LLM Judge 无参考判断 | 数据 / 图表无明显错误；不瞎编；不要求唯一思路 | 分析任务成功率 | 与固定分析合计约 70% |
| 跨会话记忆 | 约 10 道线上会话续接题 | 已有记忆 + 后续会话 | 新会话回答 / 续接完成 | 历史验证者待核实 | 正确利用已有记忆续接，不与历史冲突 | 跨会话连续成功率 | 90% 以上 |
| 定时任务 | 每日固定任务 | 定时器、数据 / 分析链、文档和群聊 | 报告文档和摘要消息交付 | 状态检查；内容复用取数 / 分析判定 | 按期触发、文档生成、消息交付，无遗漏 / 重复 | 定时交付成功率 | 100% |

### 4.2 取数澄清

**历史流程**

```text
人工隐藏目标
-> 不完整首问
-> 便宜模型按指标语义回答澄清
-> 被测 Agent 继续询问
-> 调用任务提交工具
-> 工具成功或达到轮次上限
-> Judge 检查交给数据 Agent 的任务
```

**计算**

```text
澄清成功率
= 在轮次上限内正确提交任务的案例数
  / 有效澄清测试案例数
```

**合理性与可行性审校**

| 检查点 | 结论 |
| --- | --- |
| 测试终点 | 合理。停在数据 Agent 交接工具，可隔离澄清能力，不混入真实取数错误 |
| 防答案泄漏 | 合理。模拟器知道指标含义但不知道标准指标名 |
| 多指标判定 | 合理。必须全对且无额外目标，整题才 Pass |
| 工具成功的含义 | 只能证明接口合法，不能证明语义正确；继续使用 Judge 是必要的 |
| 便宜用户模型 | 可行，但需固定模型和行为规范，防止过度合作、主动泄露或虚构信息 |
| 约 50 题 | 适合初期开发和小回归，不能单独证明线上所有澄清场景稳定 |

**最小补漏**：核实最大轮次、提交工具字段、模拟器 Prompt、Judge 版本和精确题量；将线上新的零匹配、多候选和多指标失败补入回归集。

### 4.3 业务知识与指标口径咨询

**历史流程**

```text
人工问题与参考答案
-> 查询业务知识文档或指标接口
-> 生成最终回答
-> Judge 只看最终回答
-> 错题再查召回和工具 Trace
```

**计算**

```text
咨询回答准确率
= 正确回答的咨询任务数 / 有效咨询任务总数
```

**合理性与可行性审校**

| 检查点 | 结论 |
| --- | --- |
| 两类任务合并一个指标 | 合理。用户侧都在判断最终咨询回答是否正确；题型标签保留即可 |
| 底层来源分开 | 必须保留。业务文档和指标接口的失败原因不同 |
| Judge 只看最终回答 | 可用于结果正确性；回答错后再查 Trace 可以区分召回与生成问题 |
| 20～50 题且接近 100% | 适合作为早期开发结果；也可能说明题目偏少、偏明确，不能据此证明真实长尾接近 100% |
| 动态指标接口 | 若接口 / 元数据变化，参考答案会漂移；每次运行必须记录接口和元数据版本 |

**最小补漏**：保留业务知识 / 指标口径两个子标签；加入无答案、多候选、过期口径和不同问法。Databricks 的 Genie 评估建议同一业务问题准备 2～4 种问法，可作为未来扩题方式，不是历史事实。[Databricks Genie Benchmark](https://docs.databricks.com/aws/en/genie-agents/monitor)

### 4.4 可信取数

**任务覆盖**

| 类型 | 关键验证点 |
| --- | --- |
| 简单取数 | 指标、日期、维度、过滤和数值 |
| 当期 / 基期比较 | 当前期与比较期日期范围正确 |
| 复杂维度 | 行列 / 分组不缺失、不多加、不串维度 |
| 比率型指标 | 先分别汇总分子和分母，再相除 |
| 公式型指标 | 原子指标、公式、单位和精度正确 |
| 多指标 | 所有指标全部正确才 Pass |

**复杂计算标准**

假设基准日为 2026-08-15：

```text
当期 MTD：2026-08-01 ～ 2026-08-15
MTD 同比基期：2025-08-01 ～ 2025-08-15
MTD 环比基期：2026-07-01 ～ 2026-07-15

当期比率 Rc = Σ当期分子 / Σ当期分母
基期比率 Rb = Σ基期分子 / Σ基期分母

同比 / 环比增长率 = (当期值 - 基期值) / 基期值
相对变化率 = (Rc - Rb) / Rb
百分点变化 = Rc - Rb
```

月底天数、当天数据完整性、自然日 / 业务日、除零、空值、单位和舍入规则必须由冻结业务规则决定，不能由模型临时猜测。

**历史流程与计算**

```text
200 条人工标准题 + 冻结日期 / 版本
-> 单轮直接取数，或便宜模型完成澄清后取数
-> Agent 查询并计算
-> Judge 比较最终结果与标准答案
-> 题内全部结果正确才 Pass
```

```text
数据准确率
= 数据结果全部正确的任务数 / 有效取数任务数
```

**合理性与可行性审校**

| 检查点 | 结论 |
| --- | --- |
| 200 条人工标准 | 对第一版回归集合理，明显强于只有少量烟测；仍需查看题型和业务类别分布 |
| 冻结查询日期和版本 | 必要且合理；若底层数据会修订，还需冻结数据快照或可回放结果 |
| 整题全对才 Pass | 与用户获得的数据结果一致，适合端到端数据准确率 |
| LLM Judge 校验数值 | 历史上可运行，但精确数值、单位、维度集合更适合确定性比较；Judge 应保留给语义表达 |
| 90% 以上 | 可作为口述历史结果，缺少分子、分母和运行报告时不能精确引用 |

**最小补漏**：保留历史“LLM Judge”事实；若新建评测，增加结构化结果的程序比较，规则至少覆盖单位、精度、容差、缺失项、额外项和维度键。该建议与“能断言的继续断言”的验证原则一致，不改写历史方案。

### 4.5 固定分析、开放分析与报告

**固定分析单题 Pass**

1. 使用指定或预设分析方法；
2. 数据查询和必要计算正确；
3. 图表数据、指标、时间、维度和图例正确；
4. 结论不与数据 / 图表冲突。

**开放分析单题 Pass**

1. 不要求唯一思路或最优路径；
2. 报告中的数据和图表无可识别错误；
3. 事实结论由数据、图表或已获得业务知识支持；
4. 未验证方向标为假设；编造原因或与证据冲突则 Fail。

**历史流程与计算**

```text
每种分析约 5 题
-> 运行到含数据和图表的最终报告
-> 固定分析：Judge 对照参考答案
-> 开放分析：Judge 无参考答案检查最终报告
-> 输出 Pass / Fail
```

```text
分析任务成功率
= 通过的分析任务数 / 有效分析任务总数
```

**合理性与可行性审校**

| 检查点 | 结论 |
| --- | --- |
| 固定 / 开放分类 | 合理。两类任务的“正确”定义不同，必须分组报告 |
| 每种约 5 题 | 能发现明显退化，但样本太少，不适合比较小幅版本变化 |
| 固定分析参考答案 | 合理，参考答案应包含必要方法、数据事实和硬错误 |
| 开放分析不评思路优劣 | 与项目目标一致，避免把一条参考路径当作唯一答案 |
| 开放分析只看最终报告 | 只能判断自洽和明显瞎编，不能确认查询参数、底层数据和图表映射真实正确 |
| 图表验证 | 只看报告截图可能漏错；底层图表数据 / 配置适合确定性核对，视觉表达再由多模态 Judge 或人工检查 |
| 约 70% vs 数据准确率 90%+ | 两者题集不同，只能说明完整分析链更难，不能直接把差值归因于分析模块 |

**最小补漏**：固定分析继续使用参考答案；开放分析 Judge 至少读取最终报告、结构化数据证据和必要图表数据。报告与可视化不单列 KPI，但作为整题硬门槛和失败类别。

### 4.6 跨会话连续性与记忆

**历史流程**

```text
选择线上已有会话及已写入记忆
-> 根据历史内容设计后续问题
-> 在新会话提问
-> Agent 使用记忆续接
-> 判断是否正确延续上下文
```

```text
跨会话连续成功率
= 正确使用已有记忆完成续接的案例数
  / 有效跨会话测试案例数
```

**合理性与可行性审校**

| 检查点 | 结论 |
| --- | --- |
| 线上真实记忆来源 | 合理，分布更接近用户实际使用；需脱敏和版本化 |
| 约 10 题 | 只适合烟测，90% 以上大致意味着最多约 0～1 题失败，统计结论很弱 |
| 续接型测试 | 可以证明已有记忆的读取和使用 |
| 能力边界 | 不能证明写入是否正确、冲突更新、错误纠正、应遗忘处理或跨用户隔离 |
| 历史验证器 | 当前未明确，不应假定一定是 LLM Judge |

**最小补漏**：保留“已有记忆续接”作为历史能力边界；若建设新回归集，再增加应更新、当前指令覆盖旧记忆、不应读取和跨用户隔离题。参考章节的记忆评估也将事实正确、完整和幻觉分开，并强调获得信息与正确使用信息不是同一能力。[记忆评估与轨迹边界](https://bojieli.github.io/ai-agent-book/book/chapter7/)

### 4.7 定时任务与主动交付

**历史流程**

```text
每日定时触发
-> 执行数据与分析任务
-> 生成报告文档
-> 生成摘要
-> 向群聊发送消息
-> 业务反馈调整告警
```

```text
定时交付成功率
= 按要求完成报告和群消息交付的计划任务数
  / 应执行的计划任务总数
```

**合理性与可行性审校**

| 检查点 | 结论 |
| --- | --- |
| 每日触发到群交付 | 构成完整的用户可见链路，适合用成功率 |
| 内容正确性 | 复用数据准确率和分析任务成功率，避免重复造指标 |
| 告警是否有用 | 没有唯一离线答案，使用业务反馈调阈值和数量是合理的产品迭代方式 |
| 100% 成功 | 没有统计周期、应运行次数、迟到容忍和重试口径，当前只能作口述结果 |
| 重复交付 | 必须纳入失败；仅“最后发出来了”不能掩盖重复消息 |

**最小补漏**：定义计划运行数、允许延迟窗口、报告和群消息均成功、恰好一次交付，以及补跑 / 重试是否计入。业务反馈可以保留“告警无价值、阈值不合适、数量过多”等标签，不必强行转成历史上不存在的准确率。

## 5. 横向运行与治理审校

### 5.1 模型与 Token

| 项目 | 历史事实 | 审校结论 |
| --- | --- | --- |
| 模型测试 | 没有正式模型对比 | 模型从早期版本切到 GPT-5.6 后，若没有在同一冻结题集重跑，不能把前后结果直接解释为模型提升 |
| 早期模型名 | 用户口述“Cloud OPS” | 可能指 Claude Opus，但未确认前不得改写成正式模型名 |
| Token 治理 | 没有 | 如实表述，不包装成成本优化 |
| Token 量级 | 约 8,000 万 / 日 | 只能说明消耗量级；没有输入 / 输出、模型和任务拆分，无法计算可核实成本 |

最低可行的后续记录是：按任务类型保存模型 ID、输入 / 输出 Token、工具调用次数和总 Token。成本不是当前方案完成的历史成果。

### 5.2 延迟与稳定性

历史没有 P50 / P95 延迟、系统错误率、可用性或重复运行稳定性数据。合理表述是“未统计”，不能从整体成功率反推稳定性。

若后续补测：延迟应从用户提交到最终可见结果；定时任务则从计划触发时刻到群消息成功。稳定性至少区分 Agent Fail、工具 Fail、平台 Fail 和评测装置 Invalid。

### 5.3 权限与数据安全

权限和数据安全由上层平台负责，项目团队没有单独实现或评测。责任边界合理，但“平台负责”不等于项目已验证。

最低可行验收是：在端到端环境中验证无权限请求确实被拒绝、跨用户数据不可见、敏感字段按平台策略处理。验证平台行为不等于把平台能力算作项目团队的实现成果。

### 5.4 工具失败、重试与降级

**历史规则**

```text
没有明确报错原因：最多重试 3 次
存在明确报错原因：最多重试 10 次
```

**审校结论**

| 检查点 | 结论 |
| --- | --- |
| 有次数上限 | 合理，避免无限循环 |
| 以“是否有明确原因”决定 3 / 10 次 | 不够合理。明确原因可能是参数非法、权限拒绝等不可重试错误；无原因也可能是短暂网络故障 |
| 最多 10 次 | 若无退避，会显著放大延迟、Token 和下游压力；对有副作用工具还有重复执行风险 |
| 当前成功率 | 没有独立恢复成功率，整体 90% 以上不能代替 |

更合理的规则应基于：错误是否瞬时可恢复、操作是否幂等、是否修改参数、是否需要退避和抖动。AWS 的可靠性指南也建议限制重试、使用指数退避和 jitter，并在重试前确认操作幂等。[AWS 重试最佳实践](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html)

本项目若主要是只读取数，可继续使用有限重试；若工具会发送消息、写数据或重复生成文件，必须有幂等键或“恰好一次”保护。

## 7. 查缺补漏清单

### 7.1 正式复现前必须补齐

| 优先级 | 缺口 | 为什么重要 | 最小补法 |
| --- | --- | --- | --- |
| P0 | 各准确率 / 成功率的分子、分母、题集版本 | 决定历史数字能否引用 | 找原始运行报告或保留“口述待核验” |
| P0 | Judge 模型、Prompt 和版本 | 不同 Judge 结果不可直接比较 | 固定并保存版本 |
| P0 | 数据、知识、指标接口和工具版本 | 防止参考答案漂移 | 每轮记录版本或快照 |
| P0 | 开放分析的证据输入 | 只看报告不能验证数据真实性 | Judge 同时读取结构化数据 / 必要 Trace |
| P0 | 有效 / Invalid / Fail 口径 | 防止排除系统失败抬高成功率 | 只将评测装置故障记 Invalid |

### 7.2 提升可靠性时优先补齐

| 优先级 | 缺口 | 最小补法 |
| --- | --- | --- |
| P1 | 数值题完全依赖 LLM Judge | 对结构化数据增加确定性比较；Judge 保留语义检查 |
| P1 | 记忆只测读取 | 增加更新、冲突、不得读取和隔离题 |
| P1 | 定时任务 100% 无窗口 | 保存计划运行数、按时交付数、重复数和失败数 |
| P1 | 3 / 10 次重试规则 | 按可重试错误、幂等性、退避和总预算重构 |
| P1 | 80M Token / 日无拆分 | 按模型和任务记录输入 / 输出 Token |
| P1 | 无延迟 / 稳定性 | 从现有 Trace 增加耗时、错误来源和重试字段 |

### 7.3 扩展覆盖时再做

| 优先级 | 缺口 | 最小补法 |
| --- | --- | --- |
| P2 | 咨询题表达单一 | 同一语义增加 2～4 种问法 |
| P2 | 固定 / 开放分析每类约 5 题 | 优先将线上高价值失败沉淀为回归题 |
| P2 | 无专门安全评测 | 由平台团队或联合环境补越权、跨用户和敏感字段用例 |
| P2 | 告警效用只有零散反馈 | 保存“无价值 / 阈值不当 / 数量过多”等反馈标签和改动记录 |

## 8. 最终可执行版本

### 8.1 每轮回归运行

```text
冻结题集、数据 / 知识 / 工具、Agent 与 Judge 版本
-> 运行各能力隔离题和端到端题
-> 确定性验证可断言结果
-> LLM Judge 判断语义与开放任务
-> 输出整题 Pass / Fail
-> 统计总体和任务类型切片
-> 对失败轨迹标注首错、证据和责任模块
-> 高价值线上失败回流题库
```

### 8.2 最终报告表

| 报告项 | 必须展示 |
| --- | --- |
| 数据集 | 版本、总题量、各任务类型题量、来源 |
| 系统 | Agent、模型、Prompt、工具、数据 / 知识版本 |
| Judge | 模型、Prompt、Rubric、人工抽检说明 |
| 顶层结果 | 数据准确率、端到端任务成功率 |
| 能力切片 | 澄清、咨询、固定 / 开放分析、记忆、定时任务 |
| 运行质量 | Invalid、Agent / 工具 / 平台错误、重试和耗时 |
| 失败分析 | 首错阶段、失败原因、证据和新增回归 Case |
| 证据边界 | 口述结果、缺失材料和不可比较项 |

## 9. 最终审校结论

1. **整体方案可行且分层合理**：两个顶层指标足够，能力级指标用于回归和诊断，失败 Case 回流符合生产 Agent 的实际迭代方式。
2. **历史能力隔离测试具有真实价值**：澄清、咨询和口径小题集适合开发初期，但接近 100% 只说明这些小题集上的表现，不代表线上长尾。
3. **可信取数是目前证据最完整的模块**：200 条、人工标准、冻结条件和复杂题型均合理；主要短板是精确结果仍全部交给 LLM Judge。
4. **开放分析是当前验证最弱的一环**：无参考答案并不可怕，问题在于 Judge 只看最终报告。补充结构化数据证据后才可同时判断“不瞎编”和“数据确实对”。
5. **记忆与定时任务已有可运行验证，但结论边界较窄**：记忆只证明读取 / 使用；定时任务 100% 只证明未明确窗口内的交付结果，不能替代稳定性或业务价值。
6. **横向治理不能补写成已完成**：成本、延迟、稳定性没有治理或统计；权限安全属于平台；工具重试有控制但尚未形成可靠性评测。
7. **正式对外前的首要工作是补证据而不是继续造指标**：核实题集、版本、Judge、分子分母和运行报告，比新增更多准确率更重要。
