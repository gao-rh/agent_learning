# 智能经分分析 Skill 设计评审 v0.1

> 状态：AI 调研与设计草案，尚未由用户确认，不代表原项目生产实现或最终架构。
>
> 研究问题：现有“业务专题 + 五类基础分析能力”的拆法是否合理；这些内容应怎样组织成可触发、可组合、可靠且易维护的 Skill。
>
> **版本状态更新：** 用户随后明确校正了实际路由：完整专题报告才调用长专题 Skill；普通“某维度下某指标为什么变化”调用指标异动分析 Skill，并且只做一层分析。本版关于“普通问题动态组合多种方法持续下钻”的建议已被推翻，请以 [v0.2](智能经分分析Skill设计评审-v0.2-AI草案.md) 为准。

## 一、结论

当前方向是正确的，但不能把上一轮归纳出的五类基础能力直接等同于五个独立 Skill。

最适合当前项目的形态是：

> **一个场景险经营分析入口 Skill，内部通过渐进加载组织四类业务方法和三类通用分析方法；确定性计算全部脚本化；可信取数继续走共享取数能力；WBR 作为独立交付 Skill。**

其中：

- 四类业务方法：保费、渗透率、渠道归因、用户留存归因；
- 三类通用分析方法：趋势与异动确认、贡献归因、漏斗分析；
- 贡献归因内部包含公式因子、维度贡献和目标 Gap 三种模式；
- 用户留存如果最终包含 Cohort、生命周期或生存分析等独立方法，再新增“留存 / Cohort 分析”方法模块；当前本地材料不足以确定。

因此，上一轮的五类能力仍可用于解释分析版图，但从 Skill 工程角度应收敛为三类核心方法，而不是机械创建五个 Skill。

## 二、判断依据

### 2.1 官方 Skill 设计原则

Agent Skills 官方规范采用三级渐进加载：启动时只加载名称和描述，触发后加载 `SKILL.md`，详细 references、scripts 和 assets 再按需加载；主文件建议控制在 500 行和 5,000 Token 以内，并避免深层引用链。[Agent Skills Specification](https://agentskills.io/specification)

官方最佳实践要求 Skill 是一个边界清楚、能够与其他能力组合的完整工作单元。拆得过细会迫使一次任务加载多个 Skill，增加开销和指令冲突；拆得过宽又会导致触发不准确、内容冗余和注意力分散。[Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)

官方同时建议：任务越脆弱、越要求一致，指令和执行顺序越应明确；存在多种合理路径时，应为 Agent 保留判断空间。反复出现的计算、解析和校验应固化为经过测试的脚本，而不是让模型每次重新实现。[Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)

在 Agent 架构层面，固定、可清晰拆分的步骤适合工作流和程序门禁；开放且无法预先确定全部步骤的问题适合 Agent 自主规划。无论使用哪一种，都应保持简单、提供清晰工具接口，并依据环境返回获得真实反馈。[Anthropic: Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents)

### 2.2 本地材料给出的直接证据

现有 V13 / V16 场景险智能经分 Skill 已经采用了正确的基本结构：

- `SKILL.md` 负责入口、澄清、路由和全局规则；
- `references/` 分别保存查口径、查数、异动分析和方法论；
- `scripts/` 保存日期、比率聚合、认证和环境检查等确定性逻辑。

这一设计与官方的渐进加载原则一致。本地开发分享还记录了第一版把全部内容堆在一个文件中后出现的注意力混乱，以及将路径和脚本分层后的改善。

但本地也记录了一个现实限制：多个 Skill 互相引用时，Agent 曾错误解析第二个 Skill 的 reference / script 路径。说明在当前运行环境下，过早拆成多个相互调用的 Skill 可能不如“一个业务 Skill + 内部模块”稳定。

## 三、对上一轮五类能力的重新判断

| 上一轮能力 | 是否适合独立 Skill | 更合适的归属 |
| --- | --- | --- |
| 趋势与异动确认 | 可作为独立方法模块，但未必需要独立 Skill 包 | 通用方法 reference + 异动检测脚本 |
| 公式链路拆解 | 不建议单独成 Skill | 贡献归因的 `formula` 模式 |
| 维度下拆与贡献归因 | 不建议与公式拆解完全割裂 | 贡献归因的 `dimension` 模式 |
| 漏斗分析 | 适合独立方法模块 | 漏斗分析 reference + 漏斗计算脚本 |
| 目标 Gap 拆解 | 不建议独立成 Skill | 贡献归因的 `target-baseline` 模式 |

收敛后的三类通用方法是：

1. **趋势与异动确认**：确认变化是否存在、方向、幅度、周期与异常等级；
2. **贡献归因**：统一承载公式因子归因、维度贡献归因和目标 Gap 归因；
3. **漏斗分析**：沿业务转化链定位损失环节并继续下钻。

这个拆法更符合“每个模块拥有独特输入、算法和停止条件”的原则。

## 四、推荐的整体结构

```text
主 Agent
  └─ 判断：数据咨询 / 取数 / 经营分析
       └─ 分析 Agent
            └─ scene-insurance-analysis Skill
                 ├─ SKILL.md：适用范围、一次性澄清、方法选择、全局门禁
                 ├─ 业务方法：保费 / 渗透率 / 渠道 / 留存
                 ├─ 通用方法：趋势异动 / 贡献归因 / 漏斗
                 ├─ 确定性脚本：日期、比率、贡献、漏斗、结果校验
                 └─ 固定输入输出字段与停止条件

分析需要数据
  └─ 统一请求共享取数 Agent
       └─ 返回实际标准指标、时间、维度、来源、文件与质量信息

需要固定交付
  └─ wbr-report Skill：取数结果 → 图表 → 报告 → 文档校验与发布
```

### 为什么保留一个入口 Skill

1. 场景险的指标口径、业务别名、险种差异和查询边界高度相关；
2. 当前平台曾出现跨 Skill 路径解析不稳定；
3. 四类业务专题经常组合多种通用分析方法，过度拆分会增加重复加载和路由歧义；
4. 通过 references 按需加载，同样能够避免把全部内容一次塞入上下文。

### 为什么 WBR 单独成 Skill

WBR 拥有独立、明确的触发语句、固定输入、固定报告结构、绘图和文档写入步骤，也存在幂等、校验和发布要求。它是一项完整交付工作，与开放经营分析的停止条件明显不同，因此适合单独维护。

### 为什么取数不放进分析 Skill

直接取数和分析内部取数应共用同一套可信数据能力。分析 Skill 只描述需要什么数据、要求哪些口径和校验，不应该重新复制认证、选表、SQL、分页和比率聚合逻辑。

若当前平台暂时无法从分析 Skill 调用共享取数 Agent，可以保留一个薄的 `data-access.md` 适配层，但仍应让实际指标、维度、时间和查询规则只有一个权威实现。

## 六、`SKILL.md` 应该只保存什么

主文件只保留每次触发都必须知道的内容：

1. 什么时候使用、什么时候不使用；
2. 先识别业务专题、分析目标和用户当前所处节点；
3. 一次性澄清缺失的指标、时间、维度、比较基准和交付要求；
4. 如何选择业务 playbook 和通用分析方法；
5. 所有数据必须来自共享取数能力，不得自行编数；
6. 证据不足、查询失败或指标不适用时怎样停止、澄清或降级；
7. 最终输出必须包含哪些事实、解释、不确定性和来源信息。

以下内容不应塞进 `SKILL.md`：

- 四个业务专题的全部指标和方法；
- 详细 Shapley 公式；
- 所有维度枚举和业务别名；
- 数据平台命令和认证细节；
- 大量示例报告；
- 每个历史失败 Case 的补丁规则。

它们应进入 references、scripts、结构化元数据或评测集。

## 七、业务方法与通用方法怎样组合

### 第一步：选择业务方法

| 用户问题 | 加载的业务方法 |
| --- | --- |
| 保费为什么下降、目标为什么未达成 | `premium-playbook.md` |
| 渗透率为什么变化、两个渗透率为什么背离 | `penetration-playbook.md` |
| 哪个渠道导致加入商户数下降 | `channel-playbook.md` |
| 留存下降、不同 Cohort 表现如何 | `retention-playbook.md` |

### 第二步：选择分析方法

| 问题目标 | 方法模块 | 典型组合 |
| --- | --- | --- |
| 先确认是否真的变化 | 趋势与异动确认 | 所有专题的起点 |
| 判断哪个公式因子导致变化 | 贡献归因：公式模式 | 保费、渗透率 |
| 判断哪个维度值贡献最大 | 贡献归因：维度模式 | 渗透率、渠道、留存 |
| 判断为什么没有达标 | 贡献归因：目标基线模式 | 保费、经营目标 |
| 判断转化链哪里损失 | 漏斗分析 | 渠道、渗透率、留存 |

一个问题可以顺序组合多个方法，但不要求从全局重跑。例如用户已经说明某个二级渠道下降，可以直接从趋势确认或漏斗分析开始，不必重新扫描全部一级渠道。

## 八、每个方法模块的最小定义

每个方法 reference 应至少回答：

| 字段 | 内容 |
| --- | --- |
| 适用问题 | 什么问题应该调用该方法 |
| 不适用问题 | 哪些近似问题不能误触发 |
| 必要输入 | 指标、基期、当期、维度、公式或漏斗定义 |
| 数据请求 | 需要向取数 Agent 请求哪些粒度和字段 |
| 执行步骤 | Agent 决策步骤与必须执行的脚本 |
| 硬校验 | 日期、公式、闭合性、分子分母、维度覆盖等 |
| 继续条件 | 什么结果需要继续下钻 |
| 停止条件 | 什么时候已足够回答，什么时候必须澄清或拒答 |
| 输出结构 | 事实、主要贡献、次要因素、解释、未知项和来源 |

## 九、关键运行规则

### 9.1 先澄清任务，再触发高成本操作

在认证、查询、写文档和推送之前，一次性补齐必要信息。用户已经提供的指标、时间或分析节点不得重复追问。

### 9.2 模型决定“选什么”，脚本负责“怎么算”

- 模型：理解诉求、选择业务方法、选择分析方法、决定下钻与停止、解释结果；
- 脚本：日期、同比环比、比率聚合、Shapley、贡献闭合、漏斗率和数据校验。

### 9.3 数据不足时安全失败

以下情况不得继续生成完整归因结论：

- 未确定标准指标身份；
- 指标虽然可查，但无法证明适用于当前业务问题；
- 关键分子、分母或公式因子缺失；
- 数据查询失败或只取得不完整分页；
- 贡献计算不能闭合；
- 漏斗定义或环节口径不一致。

### 9.4 最终报告保留真实指标身份

报告可以用用户熟悉的业务表达解释，但必须同时保留实际查询的标准指标名称或 ID、时间范围和数据来源，不能让生成模型用用户口语覆盖真实查询身份。

## 十、评测设计

官方建议使用真实用户 Prompt，分别评估 Skill 触发、输出质量、执行 Trace、Token 与耗时，并与无 Skill 或旧版本进行对比。[Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills)

### 10.1 触发评测

每个业务专题和分析方法都应包含：

- 应触发样例；
- 不应触发样例；
- 与邻近能力高度相似的反例；
- 模糊简称、口语、错别字和信息不全的真实表达。

Skill 的 description 应描述用户想完成什么，而不是内部实现，并用正反例测试是否漏触发或误触发。[Optimizing skill descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)

### 10.2 方法级确定性校验

| 方法 | 关键断言 |
| --- | --- |
| 趋势与异动 | 日期范围、比较基准、变化率 / pp、周期处理正确 |
| 公式贡献 | 各因子贡献之和等于总变化；公式因子与业务专题匹配 |
| 维度贡献 | 各维度贡献闭合；Top N 排序和正负方向正确 |
| 目标 Gap | 各因子贡献百分点之和等于总 Gap |
| 漏斗分析 | 分子分母重算正确；环节顺序和同向筛选正确 |

### 10.3 端到端评测

端到端题目检查：

```text
用户问题
→ 是否加载正确业务方法
→ 是否选择正确分析方法
→ 是否形成完整数据请求
→ 是否使用真实完整数据
→ 是否正确计算并决定下钻/停止
→ 最终报告是否与数据一致
```

不能只看最终文字，也要查看第一次导致任务偏离的步骤和完整执行 Trace。

## 十一、是否需要真正拆成多个 Skill 包

当前建议是先采用“模块化单 Skill”。只有同时满足以下条件，再将通用方法拆成独立 Skill 包：

1. 同一方法已经被多个业务线复用；
2. 平台能够稳定支持 Skill 组合、路径解析和版本依赖；
3. 方法拥有独立触发范围、输入输出和评测集；
4. 拆分后在触发准确率、Token、耗时或维护成本上有可测量改善；
5. 不会导致同一任务加载多个相互冲突的全局规则。

如果这些条件尚不满足，内部 reference 模块化比物理拆成多个 Skill 更稳妥。

## 十二、最终判断

### 已确认事实

- 当前原项目确实经历了从大 Workflow / 大 Skill 向下拆和漏斗等基础能力解构的过程；
- V13 / V16 已使用主入口、references 和 scripts 分层；
- 本地保费、渗透率和渠道资料能够支持趋势、公式归因、维度归因、漏斗和目标 Gap 等分析方法；
- 当前运行环境曾出现跨 Skill 引用路径不稳定。

### 合理设计判断

- 四个业务方向不应各自复制完整技术流程；
- 五类能力不应机械对应五个独立 Skill；
- 最佳粒度是一个场景险分析入口、三类通用方法、四类业务 playbook，以及脚本和共享取数能力；
- WBR 应继续独立维护为报告交付 Skill；
- 异动检测是触发 / 算法能力，异动归因才属于经营分析过程。

### 仍未解决

- 用户留存归因究竟是否使用 Cohort、生命周期、漏斗或其他独立方法；
- 当前实际平台是否已经能够稳定地组合多个 Skill；
- 原公司内最终拆分出的 Skill 名称、数量和版本关系无法仅凭本地材料完全恢复。
