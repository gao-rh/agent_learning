## 2. 核心认识：先把几个「语义」分开

以下是教学归纳，不是 DataWorks 官方分类或内部架构。

| 概念 | 主要回答什么 | 例子 |
| --- | --- | --- |
| 数据公共层 | 底层数据如何统一建模、加工与复用？ | 订单明细、退款事实、统一门店维度 |
| 业务语义层 | 数据代表什么、如何正确计算和使用？ | 净实付金额的公式、退款口径、时间字段、粒度与允许连接 |
| 语义资产生成服务 | 上述含义从哪里来，如何生成并验证？ | 从 SQL 和文档抽取候选口径，绑定证据、识别冲突并请求确认 |
| Agent 数据访问与查询 | Agent 怎样找到并使用正确的资产？ | 选择指标、维度和过滤条件，形成受约束的查询并执行 |
| LLM 语义算子 | 哪些计算需要模型理解内容？ | 投诉分类、模糊实体匹配、文本总结 |
| 持久化语义上下文 | 多次任务如何共享并维护数据环境知识？ | 保存字段约定、连接路径与证据，处理失效、检索和版本一致性 |

最重要的区分：**定义「净收入怎么算」，不等于让 LLM 给评论分类；生成语义资产，也不等于消费已有语义资产。**

一条适合当前学习的概念链路：

```text
SQL / 元数据 / 血缘 / 文档 / 数据画像
                    ↓
证据抽取 → 候选语义 → 验证与澄清 → 版本化发布
                    ↓
            检索与受约束的数据访问
                    ↓
           Agent 查询、分析与解释
                    ↓
     失败分类、人工修订、源变更与回归评测
```

这条链路是学习框架，不是已核实的目标团队实现。

## 3. DataWorks：已知做到哪里，未知是什么

现有调研根据 2026-09-05 阅读的官方资料，辨认出三类产品能力：

1. **知识生产与检索：**Context Graph 使用工作空间资产与业务资料组织知识，有生成、发布、索引和更新流程。
2. **语义模型生成与维护：**语义分析任务结合加工逻辑、表元数据和参考资料，输出结构化语义；文档展示 YAML、运行日志、图谱和编辑等入口。
3. **消费接入：**Data Agent / ChatBI 使用语义知识；DataWorks Semantic 扩展涉及制品拉取、快照和回滚，不能把它直接等同于后端生成算法。

关键产物包括业务上下文、指标、派生公式、数据集与物理映射。应区分「生成完成」「消费者同步完成」「这次问题正确召回并使用」三个状态。

**判断：已能看到产品化流程，但公开材料不足以判断语义生成的真实准确率、核心算法、独立评测或本岗位具体分工。** 未登录云账号实测，也没有运行内部服务。UModel、Sema-SQL 等相关论文不能直接当作 DataWorks 已部署的组件。

### 4.2 新增的四篇：2026 年非阿里研究

以下首次公开时间、作者机构及发表状态来自本会话上一轮核查。四篇尚无本地全文译文，也未复现实验；此处补存核心摘要。不是已核实的引用量或热度排名，较新的预印本不能称为公认经典。

#### A. 全局入口：Data Agents: Levels, State of the Art, and Open Problems

- **首次公开：2026-02-04。**港科大（广州）、清华大学、中国人民大学。
- **定位：SIGMOD 2026 综述式教程。**是可靠的全局入口，但不是专门针对语义层生成的系统综述。
- **内容：**从数据管理、准备、分析的生命周期梳理 Data Agent，提出 L0–L5 自主性框架；分级是作者框架，不是行业标准。
- **验证性质：**综述与研究分类，不是一个新语义生成算法的效果实验。
- **重点学习：**查询助手与完整数据工作流的差别，语义知识在整体系统中的位置。
- [论文正文](https://arxiv.org/html/2602.04261v1) · [官方教程列表](https://2026.sigmod.org/sigmod_tutorials.shtml)

#### B. 最贴生成服务：TYTAN

完整题名：*Tytan: Interactive Neurosymbolic Construction of Analytic Semantic Schemas from Relational Data*。

- **首次公开：2026-08-06。**美国西北大学；预印本，上一轮未核实正式录用。
- **问题：**分析语义模型依赖人工编写，难以规模化。
- **方法：**数据库结构与数据画像提供证据，LLM 推断实体、分析角色和名称，程序验证键与访问关系，歧义通过定向问题澄清。物理数字类型不自动等于可聚合度量。
- **验证：**8 个数据库，分别评估覆盖率、数据访问正确性和语义角色准确性；没有直接证明所有下游业务分析正确。
- **重点学习：**如何从数据证据生产语义模型，而不只是给字段生成中文描述。
- [论文正文](https://arxiv.org/html/2608.06331v1)

#### C. 执行反馈补全语义：GATE

完整题名：*Bootstrapping Semantic Layer from Execution for Text-to-SQL*。

- **首次公开：2026-06-04。**首尔大学；预印本，上一轮未核实正式录用。
- **问题与方法：**语义映射不完整时保留候选解释，通过查询执行取得证据，再记录得到支持的映射。
- **验证：**真实医疗与受控查询任务；需区分答案评分与执行准确率，考虑调用预算。
- **重要边界：**记忆复用主要发生在同一问题的候选计划之间，不能当作跨用户、跨任务的企业长期语义库已经实现。
- **重点学习：**把执行当成验证候选解释的调查手段，同时区分可由数据验证的约定与必须由业务明确的定义。
- [论文正文](https://arxiv.org/html/2606.05634v1)

#### D. 长期方向：What Happens When the Model Eats the Stack?

完整题名：*What Happens When the Model Eats the Stack? Rethinking the Research Agenda for Data Agents to Withstand the Bitter Lesson*。

- **首次公开：2026-09-02。**斯坦福大学、加州大学伯克利分校；带实验的研究议程预印本，发布很新，不是公认经典。
- **问题：**模型变强后，为弥补模型短板而设计的系统层，哪些仍有长期价值？
- **观点：**企业特有、持续变化的数据环境知识需要持久化语义上下文；值得研究跨任务积累、存储、压缩与一致性。
- **验证：**比较数据任务表现并研究上下文策略；特定设置有收益，也存在质量、成本与延迟取舍，并非上下文越多越好。
- **重点学习：**把语义当作持续维护的知识资产，而不只是某次提示词；研究观点不能直接证明具体岗位前景。
- [论文正文](https://arxiv.org/html/2609.03141v1)

## 5. 综合结论与学习建议草案

这些材料拼起来，覆盖了「语义怎么生产 → 怎么被使用 → 怎么验证 → 怎么持续维护」。其中自动构建、执行式发现、长期上下文仍是不同研究切口，不能拼成一套已经被完整验证的工业方案。

对当前岗位假设，建议先掌握四件事：

1. **定义对：**粒度、时间口径、指标公式、过滤、去重、可加性、连接基数。
2. **生成有依据：**SQL 解析与血缘、文档与代码交叉检查、候选语义、来源和冲突。
3. **消费受约束：**召回完整语义、指标与维度适用性、查询验证、失败与澄清。
4. **改进可衡量：**资产级准确性与覆盖率、下游任务效果、人工修订成本、更新一致性和成本。

推荐阅读路线（尚未确认成日程）：

**先用业务例子建立语义层直觉 → SIGMOD 教程建立全局 → TYTAN 看生成 → SMQ 看消费 → GATE 看证据发现 → 持久化上下文论文看维护。**

UModel 与 Sema-SQL 分别在学习对象关系访问、混合语义执行时再深入；不必同时精读七篇。

### 下一次学习只先解决一个问题

> 为什么只有订单表 DDL 和字段注释，还不足以让 Agent 正确计算「昨天各门店的净实付金额」？一份足够使用的语义资产究竟要多写哪些东西？

使用订单、退款、门店三张虚构表。先让用户说明自己的理解，再逐步加入时间口径、退款口径、粒度与一对多连接反例；形成一份教学用语义记录。不要一上来要求搭完整平台或同时复刻全部论文。

建议后续验收问题：

- 能不能举出「SQL 能执行，但指标仍算错」的例子？
- 能不能区分已有证据、合理推断和必须询问业务的事项？
- 能不能解释生成正确但召回错误、召回正确但使用错误的区别？
- 能不能设计固定模型和预算的对照实验，而不只看几道成功演示？
- 源 SQL 更新或人工修订后，旧知识怎样失效，哪些测试需要重跑？

这些问题状态均为「待继续」，不以文档写完代替用户理解。
