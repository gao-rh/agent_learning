## 二、语义层：最能区分这份 JD 的部分

### Q01｜你理解的面向 Agent 的数据语义层是什么？

- 可能追问：它与数据字典、元数据平台、指标平台、RAG 知识库分别有什么区别？已有数仓为什么还需要它？“可理解、可调用、可推理”分别交付什么？
- 回答检查点：讲清使用者、输入输出、业务概念与物理数据的映射，以及哪些约束由程序验证。可以把三者拆为业务定义可发现、接口可执行、实体关系和适用条件可用于受约束的分析。
- 不够充分的回答：把表结构和注释向量化后交给模型；“上知识图谱就能推理”。
- 依据：JD 描述 1；T01 仅作行业建模参考。

### Q02｜现场定义一个 Agent 可以使用的业务指标，你会保存哪些属性？

- 可能追问：不同业务都叫“成交额”，但过滤条件不同怎么办？成交时间与支付时间选哪个？金额币种、退款、取消单怎么处理？
- 回答检查点：指标唯一标识、业务域、定义、统计粒度、时间字段、单位、过滤条件、可用维度、聚合方式、数据来源、版本与负责人。权限、时效和质量状态可以由独立治理服务管理，但调用时必须能关联到。
- 原创练习：用一个你确实做过的指标，写出上述字段；再找一个同名不同义的反例。所有业务规则应来自事实，不能凭常识替公司定口径。
- 依据：JD 描述 1、要求 3—4；T01。

### Q03｜SQL 语法没错、执行也成功，结果为什么仍可能错？

- 可能追问：订单表与订单明细 Join 后金额翻倍；对日转化率直接求月平均；跨渠道 UV 能否直接相加；余额能否跨日期累加。
- 回答检查点：粒度、Join 基数、重复放大、去重口径、可加性、分子分母与时间语义。修正必须回到业务定义，不是仅让模型“重试 SQL”。
- 边界：这是原创场景题；S06 只有 SQL 口径问题的低置信线索，不证明该部门问过这些例子。
- 依据：JD 描述 1—2；T01。

### Q04｜面对上万张历史表，怎样建设语义层，不靠逐表人工维护？

- 可能追问：怎样选择第一批覆盖资产？元数据缺失怎么办？历史 SQL、血缘、查询日志、报表是否有帮助？LLM 生成的定义怎样验收？
- 回答检查点：优先高价值业务域；复用可靠元数据和已有指标定义；模型建议与权威发布分离；负责人确认、自动一致性校验、样例查询回归；维护增量变更和弃用关系。
- 容易被追问的漏洞：让模型自动识别口径，却没有人工/规则准入和可追责的版本记录。
- 依据：JD 描述 1、要求 3、6；AI 扩展。

### Q05｜Agent 应该直接写 SQL，还是调用指标查询接口？

- 可能追问：白名单指标无法覆盖临时探索怎么办？怎样限制扫描量和超时？只读 SQL 是否就安全？用户有权限，但模型输出了其他业务域的数据怎么办？
- 回答检查点：比较自由 SQL、语义查询、模板/工具接口的覆盖率与治理成本。可以先让模型提出指标、维度、过滤条件等结构化意图，再由服务校验和编译；也可保留受控 SQL 探索通道，但需说明授权和资源限制。
- 安全边界：权限必须来自服务端可信身份；检索、缓存、执行、返回结果都要考虑隔离；只读仍可能泄露敏感数据或产生昂贵查询。不要只依赖 Prompt 或正则判断。
- 依据：JD 描述 1、要求 1、3—4；S01 的工具触发追问仅作侧面参考。

### Q06｜用户用自然语言问数，怎样选对表、指标、维度和口径？

- 可能追问：同义词、多义词、不同业务域怎么消歧？检索返回相似但不适用的指标怎么办？什么时候必须反问？RAG 在这里解决什么，不能解决什么？
- 回答检查点：将“候选发现”和“可用性判断”分开；按业务域、身份、时间、版本与维度兼容性过滤；使用有标注的样例验证检索；缺少必要约束时澄清或拒答。相似度不是业务正确性的证明。
- 依据：JD 描述 1、要求 4—5；AI 扩展。

### Q07｜如何证明语义层确实让 Agent 的问数更可靠？

- 可能追问：怎么建测试集？只看 SQL 执行成功率够吗？两段 SQL 不同但答案相同怎么办？模型升级后怎样回归？
- 回答检查点：分开度量资产召回、指标与过滤条件选择、结果正确性、越权拦截、澄清/拒答、时延和成本。对比有无语义层时保持模型、数据快照、问题集与权限条件一致；覆盖歧义、时间边界、Join 放大、脏数据和权限反例。
- 不要只给一个综合 Judge 分数。应能拿出样本范围、标注口径、失败分类、复核方式以及上线前后可比较的证据。
- 依据：JD 描述 1、要求 5；S02 的 Benchmark/回归追问。

### Q08｜指标口径变了，如何防止 Agent 用旧定义查询新数据？

- 可能追问：生效时间、历史重算、兼容旧接口、缓存失效、灰度和回滚怎么处理？同一问题下次还能复现吗？
- 回答检查点：定义版本、数据快照/时间范围、查询计划和身份可追溯；变更影响分析与回归；定义变更和数据更新分开管理；不能把所有变化都简化为“刷新向量库”。
- 依据：JD 描述 1、3、要求 3；AI 扩展。

## 三、公共层与业务建模

### Q09｜怎样判断一个模型应该进入公共层，而不是继续放在业务 ADS？

- 可能追问：只是两个团队用了就值得抽公共层吗？过度抽象、宽表膨胀、重复指标怎么治理？
- 回答检查点：稳定业务过程、共享粒度、一致性维度、真实复用需求、负责人和变更成本。用重复建设减少、需求交付周期、查询/计算成本等可验证指标评价，而不是只数表的数量。
- 依据：用户补充“数据公共层建设”、JD 描述 2、要求 3—4；S05 为二手相关线索。

### Q10｜给你订单、支付、退款、商品、用户数据，如何设计公共模型？

- 可能追问：先选业务过程还是先定分层？一张表一行代表什么？支付与退款粒度不同怎么关联？需要事务事实、周期快照还是累计快照？维度历史变化如何处理？
- 回答检查点：先讲需求和粒度，再选事实/维度与分层；解释实体键、重复事件、状态流转和历史口径。不是背 ODS/DWD/DWS/ADS 的名称就结束。
- 边界：这是原创业务案例，不代表阿里实际域划分或内部表结构。
- 依据：JD 描述 2、要求 4。

### Q11｜多个业务域需要统一模型，但定义不能完全统一怎么办？

- 可能追问：不同用户 ID、商品编码和成交状态如何整合？统一模型会不会抹掉业务差异？跨团队谁负责确认口径？
- 回答检查点：共享核心与域内扩展分开；记录实体映射来源、有效期和无法映射的情况；建立数据契约、兼容边界与责任人。不能为了“统一”强行合并语义不同的指标。
- 依据：JD 描述 2、要求 3、4、6；AI 扩展。

## 四、Flink + Spark + Paimon：生产问题比列组件更重要

### Q12｜你会怎样用 Flink、Spark、Paimon 组织一条流批一体链路？

- 可能追问：每个组件负责什么？Paimon 提供什么存储/更新能力？批流共用表是否等于共用全部业务逻辑？补历史和在线写入会不会冲突？
- 回答检查点：画出来源、计算、存储、消费链路，解释实时更新与历史计算的职责；明确数据版本、更新顺序、回填隔离和结果对账。相同存储不自动保证相同业务语义。
- 方案取舍：需要哪些时延、吞吐、更新语义和引擎生态，才值得采用该组合；与现有架构比较收益与迁移成本。
- 依据：JD 描述 2；S03（2025 年）；S04 仅为待核验选型线索。

### Q13｜开启 Checkpoint 就能做到端到端不丢不重吗？

- 可能追问：故障发生在 Sink 写入后但确认前怎么办？源能否回放？事务输出和幂等输出有什么区别？业务本身重复发送的事件是否会自动消失？
- 回答检查点：分别解释源位点、算子状态与 Sink 提交；Checkpoint 主要保证状态恢复的一致性，端到端还需要相应源/输出协议。业务事件去重是另一层问题，要有稳定事件键和处理规则。
- 依据：JD 描述 2—3；T02。S03 只证明类似主题被提及，不采纳其候选人答案。

### Q14｜重复、乱序、迟到、历史补发的数据分别怎么处理？

- 可能追问：Event Time/Watermark 处理哪个问题？窗口已关闭但退款补到怎么办？旧记录后到，会不会覆盖新状态？补数与实时数据怎样合并？
- 回答检查点：区分事件时间、处理时间、业务版本/序列和主键；窗口迟到策略、幂等去重、更新顺序各有边界。Watermark 不等于去重，也不天然保证同一业务主键的最终版本正确。
- 依据：JD 描述 2—3；T04。

### Q15｜你对 Paimon 的理解能落到哪些机制和生产取舍？

- 可能追问：主键表与追加表如何选择？分区、桶、小文件、Compaction 分别影响什么？高频更新、热点键和积压怎样排查？为什么不用其他湖表格式？
- 回答检查点：结合输入更新模式、读写压力、延迟与维护成本回答；用真实测试或生产记录解释取舍。没有使用经历时明确说是研究/实验，不编造生产规模或迁移收益。
- 版本边界：团队组件版本未知，不预设所有版本都支持相同能力，不硬背 `master` 的参数默认值。
- 依据：JD 描述 2、要求 2；S03；S04 仅为索引线索；T03—T04。

### Q16｜订单金额从 100 更新到 80，下游持续聚合为什么不能直接再加 80？

- 可能追问：只有新值和完整 Changelog 有什么差别？旧值从哪里来？更新/删除对下游聚合有什么要求？产生 Changelog 会增加什么成本？
- 回答检查点：明确更新流不是只追加事实；解释撤回旧贡献、应用新贡献或保留主键状态的方案。Paimon 不同日志产生模式要按输入条件、下游需求和开销选择。
- 依据：JD 描述 2；T03。此具体数字是原创练习，不是面经原题。

### Q17｜Paimon Snapshot/Tag 能完全替代业务拉链表吗？

- 可能追问：存储快照时间和业务生效时间相同吗？延迟修正一个历史客户属性时，历史报表应该怎样变化？清理快照后还要查五年前怎么办？
- 回答检查点：区分存储版本与业务有效期；先确认历史查询语义、保留周期和回溯要求，再选择 SCD/快照方案。不要把 S03 中候选人的“替代拉链表”直接当标准答案。
- 依据：JD 描述 2、要求 3；受 S03 启发的 AI 纠偏练习。

### Q18｜Spark SQL 慢了，如何用证据定位，而不是直接加资源？

- 可能追问：怎样区分扫描过多、Join 策略错误、数据倾斜、小文件、Shuffle 和 GC？一个 SQL 的 Job/Stage/Task 怎么看？优化后正确性与成本如何验证？
- 回答检查点：先看执行计划、数据量与分布、任务耗时分布和资源指标，再选过滤下推、分区裁剪、Join 策略、倾斜处理或文件治理。给出可比较的基线和回归结果。
- 依据：JD 描述 2、要求 2；T05；S05 为二手问题参考。

## 五、质量、血缘、SLA 与治理落地

### Q19｜关键链路的 SLA 具体怎么定义和监控？

- 可能追问：任务成功但数据晚了算达标吗？数据新鲜度与查询可用性有什么不同？全链路依赖怎样分配时间预算？如何定位关键路径？
- 回答检查点：由消费者需求反推截止时间、端到端延迟、新鲜度、正确性和恢复目标；记录不同阶段的进度、耗时及错误；分清任务状态和数据交付状态。
- 依据：JD 描述 3；S02；H01 是历史自述线索而非当前已读原帖。

### Q20｜怎样设计数据质量规则，并控制误报和漏报？

- 可能追问：空值率、唯一性、枚举、主外键覆盖、源目标对账、金额合理范围、日环比各管什么？大促和新业务导致波动怎么办？
- 回答检查点：规则适用范围、基线、阈值、严重等级、负责人、误报豁免、问题关闭与回归。质量规则需要绑定模型和指标语义；异常量不等于治理成效。
- Agent 消费补问：上游数据过期或被判不可信时，是阻断、带警示输出，还是允许受控查询？这需要明确产品契约，不能由模型临场决定。
- 依据：JD 描述 3、要求 3；AI 扩展。

### Q21｜表级/字段级血缘怎么采集？怎样用于故障定位和变更影响分析？

- 可能追问：静态 SQL、动态 SQL、UDF、临时表与外部 API 各怎么覆盖？字段改名会影响哪些指标、语义对象和 Agent 工具？
- 回答检查点：区分声明血缘、静态解析与运行记录；说明盲区与补齐机制；追踪物理字段到指标、接口和消费方的关系；血缘关系需要版本和置信来源。
- 依据：JD 描述 3、要求 3；AI 扩展。

### Q22｜线上指标突然下降，同时出现 Flink 积压，你怎样处理？

- 可能追问：先判断业务波动还是技术异常？Checkpoint 变慢是原因还是结果？扩容、回滚、重跑、补数各有什么风险？如何证明恢复后数据正确？
- 回答检查点：先确认影响范围与消费者处置，再沿源、传输、状态、存储、查询逐段检查；缩小故障时间窗；恢复操作具有幂等/隔离设计；补数后对账并复核下游语义查询。
- 避免：直接增加 Checkpoint 超时或一律重启；这些操作可能掩盖瓶颈，也可能引入重复。
- 依据：JD 描述 3；T02、T06；S02。

### Q23｜“治理能力产品化、自动化”具体交付什么？

- 可能追问：新资产注册、质量规则、权限审批、变更检查能否进入开发发布流程？跨团队不愿接入怎么办？怎样证明平台好用？
- 回答检查点：可复用规则模板、注册/审批接口、发布准入、默认监控、责任人和问题工单闭环。指标可选接入覆盖、实际调用、重复需求减少、变更故障、修复时长和成本，但必须解释分母与观测区间。
- 依据：JD 要求 3、4、6；S05 二手参考。

### Q24｜讲一个你真正主导的项目：为什么这样做，哪些是你负责的？

- 可能追问：最初业务问题是什么？为什么没选另一个方案？上线范围多大？遇到什么失败？跨团队冲突如何解决？如果现在重做会改什么？
- 回答检查点：按“业务问题 → 个人职责 → 技术决策 → 难点 → 验证 → 上线边界”展开。团队能力、本人交付、生产上线、实验验证分开；没有测过的指标不填百分比。
- 适用材料：优先选你真实做过的公共模型、治理、实时链路或问数系统，不因为 JD 写了 Paimon 就把旧项目改称 Paimon 生产项目。
- 依据：JD 中“主导”“端到端交付”“跨团队推进”；S01—S03 只能提供其他团队的项目追问样例。

## 六、现场编码与 SQL：4 组原创练习

以下均为 Codex 扩展练习，不是搜到的流通中心原题。JD 明确要求 Java/Python/SQL；S01 提到 AI Coding 但未披露题干，不能把下面练习归给它。

### Q25｜更新事件去重与业务金额

输入 `order_events(order_id, version, event_id, event_time, pay_time, status, amount)`，另有商品明细表。一笔订单会多次更新、重复发送，且晚到。

- 练习：按业务版本选每个订单最新记录，再统计每天支付订单数和金额。
- 先澄清：同版本冲突如何裁决；统计当前状态还是当时状态；退款单是否排除；日期时区。
- 检查点：不能把到达顺序当更新顺序；先确定订单粒度；Join 明细后不能重复求和订单金额；为同时间、重复、空值和跨天补发设计测试。

### Q26｜连续登录与最大同时在线

- 练习 A：基于登录日志求连续登录至少 N 天的用户。明确自然日时区、同日去重与跨月连续性。
- 练习 B：基于进入/退出事件求当天最大同时在线。明确起止时间相同的先后规则、跨天会话、缺失退出及去重。
- 检查点：不只写窗口函数，还要解释边界和数据前提。
- 来源关系：S04 的索引提到连续登录；S06 的免费汇编提到并发统计。这里的表定义和边界测试为原创，二者不是当前团队原题证据。

### Q27｜实现受控指标查询的参数校验

任选熟悉的 Java 或 Python，接收如下概念性请求；这是练习接口，不是阿里内部协议：

```json
{
  "metric_id": "paid_amount",
  "dimensions": ["region"],
  "start_date": "2026-08-01",
  "end_date": "2026-08-31"
}
```

- 练习：从服务端身份取得权限；验证指标、维度兼容性、时间范围、必填约束；输出规范化查询计划或结构化错误。
- 追问：非法维度、无权限、指标弃用、日期颠倒、超范围查询、数据过期怎么测试？超时重试与缓存如何隔离用户和版本？
- 边界：如果扩展到任意 SQL 执行，必须另外设计语法解析、执行权限与资源管控，不能宣称这个小函数解决了 SQL 安全。

### Q28｜血缘图中的环检测与影响范围

- 练习：输入资产依赖边，找出某字段或表变更的所有下游消费者；检测有向环并说明时间复杂度。
- 追问：多父节点、重复边、孤立节点、深链路如何处理？删除/改名怎样追踪旧版本？
- 检查点：有向图不能直接套用链表快慢指针；要选择适合图的遍历/拓扑方法，并用小反例验证。

## 七、最值得串成完整回答的综合模拟题

**原创模拟题，不是阿里真题：**

三个业务团队已有各自数仓，“支付成交额”名称相同但规则不同。订单、支付和退款通过 CDC 持续到达，可能重复、乱序及历史修正。Flink 做实时处理、Paimon 保存数据、Spark 执行历史校验与重算。现在希望业务人员通过 Agent 问“上个月各区域支付成交额为什么下降”，同时满足业务域权限、数据新鲜度和结果可解释要求。你如何设计？

可以沿这条链路讲，具体方案应按约束选择：

```text
澄清业务口径与权限
  → 定义实体、事实粒度、公共维度与更新规则
  → 流批处理、回填隔离与结果对账
  → 发布有版本的指标/关系/维度和消费接口
  → Agent 检索候选、消歧、生成受控查询计划
  → 服务端校验、执行、质量与时效检查
  → 返回数据证据、口径和限制
  → 评测、监控、变更回归与故障恢复
```

加压追问：

1. 三个团队不接受同一口径，怎么办？
2. Agent 查到了正确指标，但 Join 后结果翻倍，哪一层应该发现？
3. 实时结果比离线少 2%，怎么拆分定位？这里的 2% 是假设条件，不是用户项目指标。
4. 语义定义刚更新、缓存还没更新，怎样保持请求内一致？
5. 上游数据已过期，模型能否继续给业务结论？
6. 你说“为什么下降”，查询数据只能支持分解和相关性时，怎样避免宣称已证明因果？
7. 哪些最小能力先交付，哪些需要更多时间？如何验收，而不是只演示几道成功问数？

## 八、哪些内容暂时不应压过主线

这是依据 JD 的相关度判断，不是说这些内容一定不考：

- **训练算法深挖**：JD 没有直接要求预训练、RLHF、分布式训练；不应把本岗自动理解为大模型训练算法岗。
- **所有 Agent 框架源码**：理解工具、上下文、权限和评测有价值；不能因阿里云其他团队考过 Harness，就把本岗准备全部移到框架源码。
- **所有语言同时精通**：JD 写“一种或多种”；应先在自己最熟悉的语言上证明工程能力，SQL 和数据语义仍需单独准备。
- **ClickHouse 专项**：截图标签有 Clickhouse，正文重点是 Flink/Spark/Paimon。可准备服务层选型与基本调优，深度应结合面试反馈，不能由标签推出整个技术架构。
- **泛泛背数仓层名**：需要把分层与具体业务过程、粒度、复用和治理收益连起来。

## 九、可以向面试官核实的问题

- 语义层的首批消费者是问数 Agent、分析 Agent，还是更广泛的业务智能体？
- 当前是已有公共模型上补语义能力，还是要同时重构公共层？
- 团队现有指标、元数据、权限和质量平台有哪些可复用能力？
- Flink、Spark、Paimon 的实际版本和职责分工是什么？
- 这个岗位前几个月最重要的交付与验收指标是什么？

这些问题用于校准准备，不代表已经知道答案。本文没有修改任何个人项目事实、简历或投递进度。
