## 最重要的判断

结合你提供的 JD，以及“面试团队做 DataWorks”的补充，我建议把岗位理解为：

> 帮企业把已经存在于 SQL、表结构、业务文档和使用经验中的知识，变成 Agent 能正确理解、检索和使用的数据语义资产，并持续改善这套服务。

这是工作定位假设，不是已确认的团队分工。它比“普通数仓开发套上 AI 名称”更贴近 JD 的第一条；但流批建模、数据质量与稳定性也没有失效，它们决定语义资产背后的数据是否可靠。

## 三篇论文和产品资料，最终合起来教你什么？

**SMQ 教你看消费契约。** 业务词如何落到指标、维度与查询结构？哪些部分应由模型选，哪些应由代码决定？

**UModel 教你看对象与访问接口。** 同一业务对象的数据可能在多个地方，怎样统一标识、关系和查询方法？

**Sema-SQL 教你看执行计划。** 普通 SQL 不够时，怎样加入模型操作，并衡量质量、调用次数、Token 与延迟？

**DataWorks 资料让你看产品闭环。** 生成不是终点，还要能查看、修订、更新和被实际使用。具体功能与出处见产品拆解，不能拿论文成绩代替产品效果。

对“语义生成服务研发”这个岗位假设而言，三篇都只是能力地图的一部分：你最需要补的是**从复杂业务证据生产可靠语义的能力**。

## 该学哪些内容？按岗位相关度排序

| 优先级 | 内容 | 为什么重要 | 建议交付一个什么练习 |
| --- | --- | --- | --- |
| P0 | 数据语义建模：粒度、指标、时间、可加性、连接基数 | 指标错往往不是 SQL 语法错 | 给三张表定义三个指标，并列出重复计算与时间口径反例 |
| P0 | SQL 解析与血缘：CTE、窗口、CASE、过滤、去重、UDF | 从“程序实际怎么算”抽取口径 | 对一段复杂 SQL 输出表达式、依赖字段、条件与无法静态判断项 |
| P0 | 语义生成流水线：证据抽取、候选生成、冲突与确认 | 最贴近“把生成服务做好” | 同一指标给出代码、注释、文档冲突，设计候选与修订流程 |
| P0 | 评测：资产质量与下游任务效果分开 | 能证明改动有效，避免只凭几道演示题 | 制作小型标注集、错误分类、固定条件的前后对照 |
| P1 | 检索与上下文组织：领域筛选、词法/向量召回、关系补全 | 语义正确但找不到，仍然无法使用 | 针对一个跨表问题说明哪些证据必须一起召回 |
| P1 | 服务工程：版本、增量、缓存、重试、成本与可观测性 | 语义服务需要持续运行，不是一次性脚本 | 演练源 SQL 更新、生成失败与人工修改并存时如何保持一致 |
| P2 | DSL／编译器、语义算子、对象图运行时 | 根据实际模块再深入 | 任选一个最小闭环，不要同时复刻三套系统 |

这里的优先级是面试准备建议。不是断言面试官不会问 Flink、Spark、Paimon，也不是建议抛弃你已有的数据开发优势。

### 学到什么程度才算“可以拿来面试”？

不要以“看完”作为完成标准。每个主题至少能完成四件事：

1. 用一个自己的业务例子解释问题。
2. 给出能落地的实现步骤和输入输出。
3. 主动举一个方案会失效的反例。
4. 说清如何发现错误、如何评估改进。

例如谈关系推断，不能只说“用向量相似度找关联”。你应能解释：字段名称相似只是候选；还要检查唯一性、覆盖率、连接基数、业务时间和已有 SQL 证据；关联后可能放大指标，所以需要数据检验。

## 用一个小练习串起来，比同时追三套大工程更值

建议做“日实付金额语义生成”小练习，先用虚构数据，不需要连接真实公司数据。

**输入：** 三张表的 DDL、两段加工 SQL、一份有冲突的业务说明、十几个预先写好的测试问题。

**输出：** 候选语义资产、证据位置、冲突记录、人工修订版、针对问题的语义召回结果。

**验收：**

- 公式、过滤条件和粒度可以追溯到输入；
- 缺失依据的定义会保留待确认，而不是生成看似完整的解释；
- 构造一个一对多连接反例，能发现总额被放大；
- 修改 SQL 后能识别受影响资产，保留不冲突的人工修订；
- 比较“原始 Schema”与“语义资产”两种输入的效果，并列出退步案例。

如果暂时不写代码，也可以先完成样例与评测表。这个练习的价值是训练思路，不是包装成已上线的项目经历。

## 面试优先练这六题

下面是根据 JD 与公开产品资料推演的题目，不是同团队真实面经。

1. 给你一个陌生工作空间，怎么从 SQL、元数据和文档生成可用语义层？
2. 同名指标口径不同、SQL 与文档冲突，怎么发现并处理？
3. 没有外键时，怎么找表关系并防止聚合放大？
4. 如何证明语义生成服务变好了，而不只是 YAML 更完整？
5. 语义模型正确，为什么 Agent 仍找错指标或写错 SQL？
6. 源代码变更、旧任务晚完成、用户刚修订模型，如何处理版本一致性？

详细回答框架与连续追问已经在[专项面试准备](AI草案-DataWorks语义生成服务-面试准备.md)中。下一步最有价值的不是再扩十篇论文，而是把其中两三题与你自己真实负责过的模块连接起来：已有证据是什么、做过什么、还没做过什么。

## 对工作价值的一点总结

你要争取的工作深度，是能对“语义资产的正确性、可用性与持续改进”承担结果，而不仅仅维护字段描述模板。前者会自然积累数据建模、语言模型应用、评测和平台工程能力。

是否真正有这个空间，可以通过询问“当前主要错误是什么、我负责哪些模块、如何衡量改进、能否参与完整上线闭环”判断。此前独立的[工作前景调研](../../../2-进行中/招聘投递记录/资料/阿里平台技术部/2026-09-05-语义层与Agent数据基础设施-职业前景调研.md)保留，不将技术研究热度直接等同于具体岗位前景。
