## 一句话结论

当前简历的主线已经比较清楚：**数据开发底座 → 面向业务问数与分析的 Data Agent → 可信执行、评测与人机协同 → 本地优先个人 Agent**。真正需要继续梳理的不是再增加 Agent 名词，而是让每一个强表述都能承受四层追问：

1. 这项能力解决了什么真实问题；
2. 本人具体做了哪一层，平台和协作者做了哪一层；
3. 为什么这样设计，失败时怎样处理；
4. 指标、代码、日志、测试或用户反馈怎样证明它有效。

## 3. 整体定位与页首信息

### 3.1 “Agent 开发工程师｜Data Agent 方向”

**当前价值**

- 与智能经营分析项目、数据开发底座和目标岗位一致，比泛化的“大模型应用工程师”更能形成主线。

**需要准备的追问**

- `PROJ-02`：为什么从数据开发转向 Agent？
- `HR-04`、`HR-06`：为什么是 Data Agent，目标岗位和未来两年是什么？
- `BE-PY-03`：你到底是 Python Agent 工程师、Java 后端，还是数据开发？

**梳理清单**

- [ ] 用一句话说明 Data Agent 的服务对象是业务用户，不是数据工程师开发工具。
- [ ] 说明数据开发经历提供的优势：指标口径、数仓、SQL、数据质量和业务场景；同时承认通用后端/Harness 的补课边界。
- [ ] 针对岗位分别准备 Data Agent 主版和通用 Agent 候选版，但不要在一版中同时宣称算法、平台、全栈、Data Agent 四条主线。

### 3.2 个人概述是否保留

v0.3 有个人概述，v0.6 将其移除。是否保留应由版面和目标 JD 决定；若保留，概述中的每个能力都会被视为项目已实现能力。

- [ ] “多 Agent 编排”能回答 `AGT-01/02/12` 与 `MA-01～05`，特别是状态、通信、终止和为何不用单 Agent。
- [ ] “记忆与知识库”能回答 `MEM-01～13`，并区分真实实现与理想设计文档。
- [ ] “自动化评测”能回答 `EVAL-01/05/06`，给出数据集构造、Judge/规则、随机误差和回归流程。
- [ ] “业务落地”能给出使用人数、任务量、上线时间、真实失败与持续运营，而非只给离线准确率。
- [ ] 无法满足以上证据时，概述应收敛为项目事实，不把所有关键词集中放大。

## 5. 智能经营分析 Agent

这是简历的核心项目，也是最可能被连续追问 15～30 分钟的部分。

### 5.1 项目简介与业务价值

当前强表述：周活 30 余人；报告从 2～3 天缩至约 2 小时；每月节省约 23 人日。

- [ ] 说明用户角色：商分、运营、产运等分别用什么功能；谁是高频用户。
- [ ] 区分“取数、固定专题、开放分析、主动告警”四类任务，不能用同一成功率覆盖所有任务。
- [ ] 解释 2～3 天的基线来自谁、2 小时包含哪些人工步骤、只适用于哪些报告。
- [ ] 还原 23 人日的估算公式：每月任务数 × 单次节省时长 ÷ 每人日工时；注明是业务估算还是系统统计。
- [ ] 给出至少一个正向案例和新人错误报告反例，说明系统能力与信任边界。

关联问题：`PROJ-01/04/07`、`RAG-NL2SQL-01/02`、`EVAL-01/03`。

### 5.2 Agent 架构与编排

当前强表述：主 Agent 动态编排澄清、取数和报告 Agent；自主开发 Tool、Skill、缓存、评测脚本和定时任务。

- [ ] 画出真实调用链：用户输入 → 澄清 → 指标检索 → 查询方式选择 → 指标平台/SQL → 校验 → 分析 → 报告 → 通知。
- [ ] 标出哪些节点是 Agent、Workflow、Tool、Skill、Python 脚本或平台接口；解释“动态编排”的实际控制逻辑。
- [ ] 说明为什么拆成多个 Agent，而不是单 Agent + 多工具；用职责、上下文、并行、失败隔离或评测证据回答。
- [ ] 说明状态保存在哪里、子 Agent 怎样共享结果、循环如何终止、单节点失败怎样重试或降级。
- [ ] 列出个人实际开发的代码/脚本/配置；指标平台、模型接口、服务器和通用工具归公司平台。
- [ ] 不把未实际使用的 LangChain/LangGraph 写入技术栈；能比较但明确只是原理理解。

关联问题：`AGT-01/02/03/12/16`、`MA-01～05`、`TOOL-01/03/05/07`、`PROJ-03`。

## 6. 理赔客服智能质检 Agent

这个项目最有价值的面试主线是：**在极低阳性率、小样本和隐私约束下，设计确定性工作流与人工闭环**。不要依靠“Agent”名称夸大自主性。

### 6.1 项目定位、量级与效果

- [ ] 确认日均通话/ASR 文本/进入关键词预筛/进入模型的各层数量，不能只写一个“1 万条”。
- [ ] 说明历史 5% 抽检的计算方式，以及“100% 覆盖”指所有文本经过机器筛查，不等于 100% 人工听取或 100% 召回。
- [ ] “释放 1 名质检员”明确是岗位完全替代、工作转移到疑似 case 复核，还是人力投入减少。
- [ ] 30% 准确率、日均 1～2 个疑似 case、周均严重问题等口径必须区分；正式版只保留可复核的同口径数据。
- [ ] 说明为什么召回率无法可靠计算：没有全量人工 Gold，而不是系统“召回高但没测”。
- [ ] 准备一个误报、一个漏报风险和一次阈值/Prompt/规则迭代。

关联问题：`PROJ-04/07`、`EVAL-01/02`、`RAG-EVAL-01`。

### 6.2 工作流、模型与人工闭环

- [ ] 画出真实链路：已有 ASR → 关键词预筛 → 角色校验 → 违规初审 → 脱敏 → 外部模型复核与分级 → 人工确认 → 样本回流。
- [ ] 明确 ASR、内部低代码平台、模型能力由公司提供；本人负责业务链路、Prompt、Python 脚本、工作流配置和迭代。
- [ ] 解释错标角色如何发现、为什么需要交换、脚本幂等与异常处理。
- [ ] 解释关键词为什么保留、内部模型和外部模型各自解决什么问题、路由成本与失败降级。
- [ ] 说明 A/B/C 分级定义、证据输出与质检员动作；没有稳定标准时不要只写字母。
- [ ] 说明人工复核结果怎样回流，样本怎样去重、标注、切分和进入回归集。
- [ ] “召回优先”是设计策略，不是已测得的高召回率；说明阈值和人力成本取舍。

## 12. 逐项梳理顺序

这不是正式求职计划，只是把简历定版所需的依赖按先后排开。

1. **先统一版本事实**：任职时间、评测题数、用户数、质检量、违规量、灰记状态和测试数。
2. **再确认 Ownership**：对两个美团项目和灰记分别列“本人实现 / 平台提供 / 协作者完成 / AI 生成后本人验收”。
3. **再补证据包**：每个强数字一张口径卡；每个项目一张调用链；每个项目一个失败案例。
4. **再做追问演练**：按对应标准化 ID 连续追问三层，发现答案需要新事实时回写项目准备，而不是临场补造。
5. **最后改简历**：只把已核验、能口述、与目标 JD 相关的内容压缩进投递版；其余留在面试长答案或学习清单。
