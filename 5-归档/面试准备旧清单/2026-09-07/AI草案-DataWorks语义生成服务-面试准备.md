# AI 草案：DataWorks 语义生成服务面试准备

日期：2026-09-05。

定位依据：用户认为面试团队负责 DataWorks，岗位大概率改善语义生成服务；结合 [JD 原文](../../../2-进行中/招聘投递记录/资料/阿里平台技术部/岗位JD-截图转写.md)与 [本轮公开资料核验](../../../2-进行中/招聘投递记录/资料/阿里平台技术部/2026-09-05-阿里DataWorks语义建设-资料与进展核验.md)推演。

**本文件不是流通中心真实面经，不提供所谓命中率。** 题目和回答框架是 Codex 原创分析，体现与岗位的相关性，不代表团队一定使用下面的实现。所有回答还需结合本人真实项目证据；没有做过的部分应说“我的设计思路是”，不能说成已上线经验。

## 1. 先把岗位讲清楚

可以这样表达自己的当前理解：

> 我理解这里的语义层建设，不只是补充表和字段的描述，而是利用加工代码、元数据和业务资料，产出 Agent 能正确使用的业务语义。生成之后还需要验证、更新和提供服务，并通过下游任务验证价值。公开资料能看到 Context Graph 和语义分析任务两个入口，我希望进一步了解本岗位主要负责的模块边界。

这是候选人口述草案。不要直接断言自己负责某模块，也不要把阿里其他团队论文的方法说成 DataWorks 当前实现。

## 2. 核心题一：给你一个工作空间，如何自动生成语义模型？

来源触发：资料 S01、S02 的功能定位；下面的流程为设计建议。

**可能问法：** 输入几千张表和大量加工 SQL，如何产出实体、指标、维度、关系和使用说明？

**连续追问：** 产物结构怎么定义？哪些先用规则或解析器，哪些用 LLM？跨表上下文怎么组织？怎么处理不确定性？

**回答骨架：**

1. 先确认消费任务与交付粒度：资产发现、指标解释、查询生成并不需要完全相同的模型。
2. 采集带版本的证据：DDL、生产 SQL、任务依赖、注释、已有指标定义、文档，必要时经授权采样。
3. 确定性解析拿到物理结构与可解析表达式；LLM 提出业务含义、同义词和候选关系，不让模型代替所有解析工作。
4. 保留候选与证据对应关系，显式暴露冲突和缺失；经过结构检查、语义测试与适当人工确认再发布。
5. 发布物有独立版本和消费接口，错误与反馈能够定位到定义及源版本。

一个候选指标至少要考虑：身份、名称、表达式、粒度、时间口径、单位、维度兼容性、来源、适用范围、状态与版本。它不是要一次做成全公司的完整本体。

**容易失分：** “把全部元数据塞进 Prompt，让模型输出 YAML。”这没有解释规模、证据、质量和维护问题。

## 3. 核心题二：怎么从复杂 ETL SQL 中抽取真实口径？

来源触发：S02；本题 SQL 为自拟，不是阿里业务代码。

```sql
SELECT merchant_id,
       SUM(CASE WHEN status = 'paid' THEN amount_cent ELSE 0 END) / 100.0 AS paid_amount
FROM dwd_order
WHERE dt = '${bizdate}'
GROUP BY merchant_id;
```

**可能问法：** 这段 SQL 能证明什么，不能证明什么？

**回答检查点：**

- 能识别分组、条件、金额转换与计算表达式，追踪输出字段的输入依赖。
- 不能仅凭名称就确定源表是一单一行；也不能认定 `dt` 就是支付日期，或者这就是公司权威 GMV。
- 需要核对源粒度、`amount_cent` 单位、状态定义、分区语义和是否存在退款/重复记录。
- AST 与作用域分析处理别名、CTE、子查询和聚合；区分值依赖、过滤依赖与连接依赖，不能只有字段名连线。
- 动态 SQL、宏和 UDF 需要展开来源或标为不可解析；不能静默跳过后仍宣称口径完整。

**继续追问：** DISTINCT、窗口、去重、迟到修正、多级聚合怎么处理？解析失败时应降级为候选描述还是拒绝发布可执行定义？

**容易失分：** 认为成功解析 SQL 就等于理解全部业务含义，或以正则匹配替代复杂 SQL 解析。

## 4. 核心题三：没有外键，如何推断表关系与业务实体？

来源触发：S01、S08；具体策略为设计建议。

**可能问法：** 表都叫 `user_id`，能自动认定它们属于同一实体并 JOIN 吗？

**回答检查点：**

- 候选来源可包括已有血缘、历史查询、列名/描述相似性、值域重叠和唯一性统计。
- 候选必须区分业务域、租户、实体角色与时间版本；下单人、付款人和收货人不一定同一角色。
- 检查关系基数、空值率、连接覆盖和聚合放大。历史上有人写过的 JOIN 也可能不正确。
- Slowly Changing Dimension 或快照表需要时点条件，不能只输出等值键。
- 没有充分证据时返回多个候选或请求确认，不强造唯一关系。

**可迁移亮点：** 能将“找关系”与“验证关系是否适用于当前指标”分开讨论。

## 5. 核心题四：SQL、注释、业务文档互相冲突，信谁？

来源触发：S01、S02、S04；问题及方案为推演。

**可能问法：** 文档说收入扣退款，生产 SQL 没扣，语义生成服务应该怎么写？

**回答骨架：** 区分“当前实现”与“期望业务定义”。记录各来源、版本、负责人和生效时间，将冲突显式呈现，确定阻断或待确认状态。业务确认后的更改需回归验证，不是让 LLM 用多数投票决出真相。

**追问：** 客户已经人工修正过定义，下次自动构建是否覆盖？

**建议：** 区分自动候选层与人工确认层；重新生成形成差异，不盲目覆盖。确认可以绑定源版本或兼容范围，源变更后标记需复核；记录谁改了什么、为何修改以及影响面。

**容易失分：** 一律“生产 SQL 最可信”或一律“业务文档最可信”。它们可能分别陈旧、错误或服务不同时间范围。

## 6. 核心题五：如何评估语义生成质量？

来源触发：S01/S02 的生成目标，以及本轮尚未取得独立生成质量基准这一证据缺口。以下评估体系为原创建议，不是团队现状。

**可能问法：** 你改了抽取策略，如何证明更好，而不是生成内容更多？

| 层次 | 指标建议与分母 | 不能混淆的事 |
| --- | --- | --- |
| 结构有效 | 可解析且满足契约的对象数 / 输出对象数 | 格式正确不代表含义正确 |
| 事实与口径精度 | 经核验正确的断言数 / 被评估的输出断言数 | 须同时报告覆盖率与拒答率，不能只展示精度 |
| 覆盖 | 正确找回的必要语义项 / 标注的必要语义项 | 只返回容易项会让精度虚高 |
| 来源可验证 | 证据足以支持的断言 / 抽检断言 | 附了一个链接不等于链接支持结论 |
| 下游任务 | 正确完成的任务 / 明确界定的任务集 | SQL 执行成功不等于业务答案正确 |
| 运营成本 | 人工修正率、单个有效对象成本、更新时间和失败率 | Token 下降但覆盖下降，不一定是改进 |

**实验设计检查点：**

- 按业务域/客户/时间留出数据，避免同一 SQL 的轻微变体同时进入调优集与测试集。
- 比较元数据基线、加代码证据、加业务文档等方案；尽量固定下游模型、检索设置和数据快照。
- 同时看端到端结果和中间产物，区分“生成错了”与“生成对了却没检索到/没用对”。
- 加入困难案例：同名异义、跨期定义、关系放大、退款、权限不足、采样偏差、知识过期。
- LLM Judge 可做辅助，需人工标注校准和分类型抽检；不能用同一个模型的自评作为唯一真值。

**追问：** 模型输出的 0.95 置信度可信吗？

**建议：** 先定义置信度预测什么事件，用已标注样本校准，再决定阈值与人工复核策略。模型自述概率不天然可靠。

## 7. 核心题六：语义定义正确了，Agent 为什么还是找错表？

来源触发：S01 的消费方式、S05 的使用方问题。以下检索方案不是已证实的 DataWorks 算法。

**可能问法：** 一个概念有十张相似表，怎么让 Agent 用对？

**回答检查点：**

- 检索对象不只包含名称，还应携带粒度、时效、业务域、适用/不适用条件和证据。
- 可组合词法匹配、向量召回、结构关系扩展与重排，但须用消融实验解释每部分价值。
- 对正确资产做召回评估，对选中资产做适用性评估，再检查最终使用；三个环节分别定位错误。
- 大型上下文采用候选摘要到细节的渐进获取，保留中间模型版本。
- 权限过滤不能只在最终 SQL 执行时才出现，检索内容本身也可能泄露敏感信息。

**容易失分：** 以 Recall@10 高证明答案准确，或认为加图数据库就自然获得正确业务关系。

## 8. 核心题七：源数据变了，如何做可靠的增量生成？

来源触发：S01；下面是实现追问，不是对其源码的描述。

**可能问法：** 改一个字段或 UDF，怎样知道哪些语义对象需要更新？两个任务并发构建，旧任务最后结束怎么办？

**建议回答：**

- 使用稳定对象 ID、源内容版本和依赖关系定位变化；元数据版本、业务规则版本与数据内容时点应分开。
- 计算受影响的派生定义与检索索引范围，处理重命名、删除、撤权，不只处理新增。
- 构建到隔离版本，校验完成后原子切换发布指针；使用任务代际或条件更新阻止过期任务发布。
- 失败重试具有幂等性；取消请求后，晚到的模型返回不能继续发布。
- 下游会话与缓存引用发布版本，能够识别过期定义并重新加载。

**深入追问：** 某表采样超时，但其余生成成功，任务应叫什么状态？

**建议：** 产品可以允许局部完成，但必须暴露未覆盖清单、对象级状态与质量边界；不能把作业成功误解成所有资产语义完整。

## 9. 核心题八：语义服务如何设计权限与安全边界？

来源触发：S01、S04。以下为防护设计讨论。

**可能问法：** 知识库可以分享，那么读到表的业务说明是否就有权执行查询？

**回答检查点：**

- 知识使用授权、源数据授权、管理权限和执行权限是不同能力，需要明确组合规则。
- 表注释、文档、采样值可能含敏感信息或提示注入；作为不可信数据处理，不能执行其中的“系统指令”。
- 权限变更要影响派生知识、搜索索引与缓存，考虑泄漏窗口和快速失效机制。
- 探查查询设置只读身份、扫描/时间/并发预算；生成 SQL 需校验，但字符串黑名单不是完整安全控制。
- 保留数据来源与操作审计，对外模型的输入范围和脱敏策略应有明确边界。

**容易失分：** “有 MCP/Skill 就有权限隔离”，或“Prompt 写禁止敏感操作就安全”。

## 10. 核心题九：YAML、图谱、DSL、语义层是什么关系？

来源触发：S02、S05、S07、S08。不要把几个名词当成同一种东西。

**建议回答：** YAML/JSON 是表示格式；语义模型规定概念、关系和计算含义；图是一种关系组织或查询方式；DSL 是可解析的操作语言。是否能执行、能做哪些检查，取决于解释器/编译器和服务契约，不取决于文件后缀。

**追问：** 为什么不是一份 Markdown？为什么不直接 NL2SQL？

**建议：** 说明文本适合背景与例外，结构字段适合验证与机器消费。受限 DSL 能收窄错误空间，但增加建模、编译和长尾表达成本。根据任务权衡，不声称所有场景都需要 DSL。

**特别注意：** 淘宝直播的自研 DSL 与 DataWorks 路径在 S05 中是区分的。SMQ 也保留 Agent 编写复杂 SQL 的部分，不能作为“最终查询都确定性正确”的例证。

## 11. 核心题十：如何控制大规模语义生成的成本？

来源触发：S01、S08；以下为建议方案。

**可能问法：** 十万张表，全部交给强模型分析太贵，怎么办？

**回答检查点：**

- 按业务域、消费价值、信息完整度划分任务，先复用已有权威定义，不反复生成已确定的结构事实。
- 按依赖子图取上下文，用解析器提取结构，避免每次重传整库信息。
- 内容寻址缓存与增量更新要纳入输入、模型、Prompt 和解析器版本，不能只按表名缓存。
- 批量和并发执行需限流、背压及租户隔离；失败重试有预算并可恢复。
- 小模型、规则与强模型分工须经评估，不把“更便宜”视为默认更合适。
- 最终看每个已验证语义对象的成本与覆盖，而不仅是总 Token。

**追问：** 是否需要微调？

**建议：** 先分清错误是缺证据、解析错误、输出不稳定、上下文问题还是稳定的领域映射难题。只有数据和评估证明存在可学习规律，再讨论 SFT；不能用训练解决源知识缺失。

## 12. 核心题十一：怎么和数据公共层、流批与治理联系起来？

来源触发：JD 的数据建模和 SLA 要求。

**可能问法：** 语义层定义同一个指标，实时和离线结果不一样，算谁的错？

**回答检查点：** 分别核对业务定义、数据粒度、去重、事件时间/处理时间、迟到处理、时区、维表时态、引擎数值差异与数据完整性。数据新鲜度与语义版本都应可见。

公共层提供什么可靠粒度和状态，决定语义层能承诺什么；语义层不能仅凭名字统一就掩盖底层不一致。必要时将实时预估值与离线结算值定义为不同状态或不同指标。

Flink/Spark/Paimon 仍可能独立考察，但本轮不继续扩成泛化大数据题库。围绕真实项目准备状态一致性、回放、幂等、变更和资源问题即可；不能断言面试一定不考基础。

## 13. 核心题十二：你能带来什么，如何证明自己负责过？

来源触发：JD 要求主导设计、工程交付与跨团队沟通。

从本人一个真实案例出发准备，而非背诵平台全景：

1. 原问题是什么，错误造成什么影响？
2. 自己负责哪块代码、模型、接口或评测？与其他同事的边界？
3. 做过哪些备选设计，为什么选最终方案？
4. 最难的失败案例是什么，如何定位与恢复？
5. 改善指标的样本、分母、时间窗口和上线范围是什么？
6. 哪些经验能迁移到语义生成，哪些是目前尚未做过的设计？

可以将业务口径治理、指标建模、可信取数、数据质量或 Agent 评测的经历映射到这里，但不能把相邻经验直接包装为做过 DataWorks 生成引擎。

## 14. 一道综合模拟题

以下规模为自拟：一个租户有 5,000 张表，40% 缺少有效注释，有多层 ETL、历史文档和少量已确认指标。需要为 Agent 生成业务语义，支持每天更新。已有版本持续被查询，构建期间允许部分采样失败，人工修正不能丢失。

请说明：输入证据、产物契约、生成流程、质量评价、任务状态、并发发布和权限。然后回答：

- 如何定义第一版可用范围，哪些内容明确不生成？
- 一条错误 JOIN 怎么从下游答案追溯到生成证据？
- 新 Prompt 让整体准确率提高，却使一个业务域下降，是否发布？
- 撤销某张源表权限后，已生成的知识如何处理？
- 新任务已发布，旧任务随后结束，如何避免覆盖？
- 如果只能做一个改进，怎样先收集证据确定瓶颈，而非凭感觉选技术？

这道题可用来串联前十二题，不要求虚构阿里的架构细节或实际流量。

## 15. 建议向面试官核实的问题

- 本岗位与 Context Graph、语义分析任务、公共层建模的具体关系是什么？
- 当前最主要的质量或规模瓶颈是哪类错误？已有怎样的评测和用户反馈？
- 模型生成、检索、查询服务与任务平台分别由谁负责，我可以负责到哪一层？
- 是否已有跨客户或跨业务的回归集，人工修改怎样反馈到下一轮生成？
- 入职半年期望交付什么模块，怎样衡量效果，有谁指导？
