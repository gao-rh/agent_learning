## 1. 先看岗位：国内公司究竟在筛什么

### 1.1 Agent 岗位至少分成三条线

| 岗位路线 | 官方 JD 中的高频任务 | 简历首先要证明什么 | 与当前材料的匹配度 |
| --- | --- | --- | --- |
| Agent / AI 应用工程 | 业务机会识别、Agent/知识库/Workflow、API 与业务流程集成、端到端自动化、持续跟踪效果 | 能把真实业务问题做成可用、稳定、可迭代的 AI 系统 | **高**。智能经营分析、活动配置、数据底座是直接证据 |
| Agent 系统 / 平台工程 | API/CLI/Skill 工具链、能力注册与治理、上下文、评测、可复用平台能力、系统抽象 | 工程深度、抽象能力、可靠性和复用规模 | **中**。有编排、校验、评测和工具衔接，但平台底座不是个人开发 |
| Agent 算法 / 模型工程 | 训练/后训练、RL、Router/Planning/Reasoning、Benchmark、模型评测与推理优化 | 算法实验闭环、强基线、训练与论文证据 | **低到中**。不应只靠项目标题或框架词包装成算法岗 |

这不是概念分类，而是当前官方岗位的实际分工：

- 百度的 [AI 应用工程师 J101300](https://talent.baidu.com/jobs/detail/SOCIAL/b286456b-922b-4ff3-9da0-0e8855443ba0) 把“业务场景理解 → Agent/知识库/工作流 → 系统与流程集成 → 使用效果迭代”写成完整职责链。
- 百度的 [大模型应用研发工程师 J103341](https://talent.baidu.com/jobs/detail/SOCIAL/a5ff8d15-b547-4a87-ba55-a128dae953cd) 更偏平台：API、CLI、Skill 的注册、生成、发布、调用、治理和效果评估，以及把复杂业务沉淀为标准化、可复用方案。
- 百度的 [AIDU Agent 应用全栈工程师 J99974](https://talent.baidu.com/jobs/detail/GRADUATE/6f9c3a86-6557-409d-8fa7-e6f4c68d6765) 明确要求 Planning—Acting—Reflection、Tool/API、Memory、RAG、Eval，并同时关注成功率、稳定性、成本、延迟和用户体验。
- 字节跳动 2027 招聘把“基础大模型”和“大模型应用、AI Coding”等方向分开，并说明 HR 会依据简历与岗位的匹配度判断流程，说明一份泛化的“Agent 简历”不够，第一屏必须明确路线。参见 [字节跳动校园招聘](https://jobs.bytedance.com/campus/page-6272Gc)。
- 阿里 [ROCK 与智能引擎 AI Infra 团队](https://alibaba.github.io/ROCK/zh-Hans/careers/) 强调从数据、训练、评测、预测到应用开发的完整工程体系，更接近 AI Infra / 模型工程，不宜和业务 Agent 应用岗混为一谈。

### 1.2 对当前简历的直接含义

当前最可信的定位不是“会很多 Agent 框架”，也不是“大模型算法工程师”，而是：

> **以数据工程和场景险业务知识为底座，负责生产环境 Agent 应用的业务抽象、任务编排、可信数据访问、评测与落地。**

最稀缺的证据也不是 LangChain/LangGraph，而是以下组合同时存在：

1. 有真实线上业务，不是课程 Demo；
2. 能说明个人负责边界，平台能力与个人工作分开；
3. 既有 Agent 自主决策，也知道何时使用固定 Workflow；
4. 有指标平台优先、SQL 降级、数据校验、人工确认等可靠性设计；
5. 有 100 题评测、真实用户 case 迭代和时间效率变化；
6. 数据开发背景能解释为什么你能做经营分析 Agent，而不是与 Agent 经历割裂的旧技能。

这六点应成为简历主线。20–30 名用户并不算大规模，不应包装成“广泛推广”；但它是一个真实、边界清楚、持续使用的垂直业务群体，可以用“覆盖完整产运/商分角色”和任务时效证明价值。

## 2. 公开简历与模板拆解

### 2.1 选择标准

“公开”不等于“优秀”。本次只把样例当成写法证据，并明确区分：

- **实际技术简历**：观察候选人如何组织事实、责任和结果；
- **内容指南/模板**：学习结构或排版，不把虚构指标当成功案例；
- **研究型 CV**：只参考第一页的技术表达，不照搬论文型篇幅。

### 2.3 从样例中反复出现的共同结构

真正有用的共同点不是某一种颜色，而是以下扫描顺序：

1. **姓名 + 明确岗位定位**；
2. **1–2 行可信概述或直接进入最强经历**；
3. **公司 / 职位 / 时间**；
4. **旗舰项目：责任范围 → 关键设计 → 可靠性/评测 → 结果**；
5. 次要项目只保留能补充新能力的内容；
6. 技能、教育、论文作为证明，不与主项目抢第一屏。

高信号简历不是把信息拆成更多视觉模块，而是把因果关系压缩到更短的阅读路径。

## 3. 语言风格：国内 Agent 简历怎样写得像真实工程工作

### 3.1 每个重点项目使用四层结构

| 层次 | 要回答的问题 | 当前材料中可用的证据 |
| --- | --- | --- |
| 项目领句 | 这是哪个业务、谁在用、你负责什么 | 场景险；产运/商分约 20–30 人；负责 Agent 技术链路 |
| 关键决策 | 为什么这样拆 Agent / Workflow / Tool | 查数与分析两类编排；固定专题用 Workflow，开放问题用 Skill 组装 |
| 可靠性与验证 | 怎样避免“能跑但不可信” | 指标平台优先、SQL 降级提示、领域数据校验、100 题集、真实 case 迭代 |
| 业务结果 | 任务最终发生了什么变化 | 看数半天等待变自助；常规报告 2–3 天缩短到约 1–2 小时 |

这比当前 v0.1 的“把所有技术链路都写出来”更重要。一个旗舰项目通常保留 3–4 个 bullet，每个 bullet 只承载一个主结论。

### 3.2 句子模式

推荐使用：

> **动作与责任边界 + 面向的对象/约束 + 关键机制 + 可解释结果。**

例如，以下只是候选写法，不是正式简历正文：

- 弱：`建设智能经营分析 Agent，支持取数、分析和知识问答。`
- 较强：`主责场景险经营分析 Agent 技术链路，面向约 20–30 名产运与商分用户，将指标查询、专题分析和事件归因统一为两类任务编排。`
- 更完整：`将高频查数优先路由至指标平台，长尾需求降级为 SQL 并显式提示可靠性边界；补充指标范围和多指标关系校验，使平台覆盖范围内核心取数准确率接近 100%。`

需要控制的词：

| 少用或禁用 | 原因 | 替换方式 |
| --- | --- | --- |
| 赋能、全面提升、业内领先、效果显著 | 没有对象、基线和证据 | 直接写任务变化、用户、时间或准确率口径 |
| 参与、负责、建设（单独出现） | 看不出做了什么判断 | 接具体模块、决策、实现和验收责任 |
| 熟悉 LangChain/LangGraph | 当前美团项目未真实使用 | 写实际的 Agent 自主判断、Tool/Skill/Workflow 机制 |
| 从 0 到 1、Owner、主导 | 容易把团队结果包装成个人结果 | 只有能解释目标、关键决策、核心实现和上线责任时使用 |
| 近 100%、80%+ 等孤立数字 | 面试官无法判断分母和范围 | 同句写明平台覆盖范围、100 题集或反馈来源 |

社区写作指南也反复强调，Agent 项目不应只写 Function Calling、ReAct、RAG，而要说明工具边界、错误恢复、模式选择和任务稳定性。可参见 [卡码笔记的 Agent 项目简历拆解](https://notes.kamacoder.com/jianli/llm/llm_7.html)。这是一份社区二手经验，只用于补充，不替代官方 JD 和真实项目证据。

## 4. PDF 格式与视觉风格

### 4.1 对现有 v0.1 PDF 的复盘

现有 PDF 的问题不是“不够精致”，而是视觉类型选错了：它像业务看板/内部汇报页，不像技术简历。

1. **卡片和指标格过多**：项目正文、指标、风险、能力被拆成多个浅色模块，读者需要横跳，因果关系反而断开。
2. **低对比度**：浅蓝、浅绿、浅灰同时出现，小字号落在浅底色上，打印和招聘系统缩略图中更弱。
3. **三页分配失衡**：第一页与第三页都有明显大面积空白，但正文又显得拥挤，说明不是内容太多，而是网格消耗了空间。
4. **指标与动作分离**：`80%+`、`接近 100%` 被放在独立格子里，无法立刻看出对应哪套评测、哪个范围和个人做了什么。
5. **视觉噪声抢过内容**：章节编号、侧栏、底部能力表、页眉页脚共同争夺注意力；第一眼记住的是版式，不是智能经营分析项目。
6. **第三页像产品说明页**：灰记被拆成架构卡片、闭环格子和验证侧栏，适合产品文档，不适合 10 秒简历扫描。

因此，下一版不是“换一个配色”就能解决，而应换成文档式排版。

### 4.2 建议的硬约束

- A4，**单栏**为主；最多只在页眉或技能区使用弱双栏。
- 正式投递版目标 **2 页**；全量素材档案继续不限长度。不要用缩小字号把三页硬塞成两页。
- 黑色/深灰正文，只保留一种低饱和强调色；不使用大面积色块。
- 标题层级靠字号、粗细和细分隔线完成；不用章节数字、进度条、仪表盘、侧栏指标卡。
- 公司、角色、时间在同一视觉行；项目名紧随其下。
- 每个 bullet 约 1–3 行；数字与它证明的动作放在同一条中。
- 第一页优先放职业定位、美团经历和智能经营分析；教育、奖项、论文下沉。
- 第二页底部允许自然留白，但不能出现“半页空白”；跨页时不把项目标题与正文拆开。
- 页眉只保留姓名、目标方向、电话、邮箱和必要链接；不放照片、年龄、性别、工作年限标签。

### 4.3 三种候选版式路线

| 路线 | 页面组织 | 优点 | 风险 | 适用条件 |
| --- | --- | --- | --- | --- |
| **A. 经典两页技术社招版** | P1：定位 + 美团 + 旗舰项目；P2：次要项目 + 灰记 + 能力/教育 | 最稳、扫描快、适合国内招聘系统；内容与版式不互相抢戏 | 视觉个性较弱，需要靠文字质量取胜 | **当前初步推荐**，适合 Agent 应用/数据智能岗位 |
| B. 证据强化两页版 | 页首增加 3 个“核心证据”短句，但仍保持单栏；项目正文更短 | 10 秒内突出真实生产 Agent、评测、业务时效 | 很容易再次做成指标看板；数字口径不硬会显营销 | 等所有数字口径确认后再考虑 |
| C. 一页主简历 + 项目档案 | 一页只放 strongest signals，另附脱敏作品集/项目说明 | 投递版极简，技术面有下钻入口 | 当前美团项目不能公开，灰记也尚未形成稳定公开作品，附件价值不足 | 灰记 MVP 和脱敏证据页成熟后再采用 |

## 5. 内容顺序的三种候选路线

### 路线 A：业务 Agent 应用工程师（初步推荐）

`定位 → 美团工作概述 → 智能经营分析 → 活动自动化配置 → 灰记 → 数据/Agent 能力 → 教育论文`

- 优点：与现有最强事实和百度等应用工程 JD 最匹配；数据背景成为壁垒。
- 风险：需要把技术深度写在可靠性、评测和编排决策里，否则会被误读为低代码业务配置。
- 触发条件：目标 JD 强调 AI 应用落地、企业自动化、数据分析 Agent、知识库或 Workflow。

### 路线 B：Agent 系统与工程化

`定位 → 编排/可靠性概述 → 智能经营分析 → 灰记 → 活动配置 → 数据能力 → 教育`

- 优点：更容易与 Agent 平台、上下文工程、评测、工具治理岗位对话。
- 风险：美团内部 Agent 平台、底层 Skill 不是个人开发，证据不足时会夸大 ownership。
- 触发条件：目标 JD 强调 Skill/Tool 生命周期、平台复用、Context、Eval、可观测和系统设计。

### 路线 C：数据智能 + Agent

`定位 → 数据工程工作 → 智能取数/经营分析 → 活动配置 → 其他提效 → 教育论文 → 灰记`

- 优点：转型叙事最稳，适合数据平台、BI Agent、Text-to-SQL、数据产品 AI 化岗位。
- 风险：Agent 身份不够鲜明，可能继续被筛为传统数据开发。
- 触发条件：JD 本身要求 SQL/数仓/指标体系与 Agent 的交叉能力。

## 6. 对各项目篇幅的调研判断

| 内容 | 正式两页版建议权重 | 原因 |
| --- | --- | --- |
| 智能经营分析 | 美团部分的 55%–65% | ownership、架构、可靠性、评测和业务结果最完整，是旗舰项目 |
| 活动自动化配置 | 20%–25% | 能证明业务意图到平台能力的衔接与 human-in-the-loop，但底层 Skill 非个人开发 |
| 理赔客服风险质检 | 0%–10% | 链路完整但准确率约 30%，召回和业务改善未知；可作为探索或面试素材，不宜与旗舰项目并列 |
| 团队提效工具 | 1 行概述 | 补充执行力，不值得拆成项目 |
| 灰记 | 全文的 15%–20% | 能证明 AI-native 产品与跨端工程，但只能写当前已验证事实；未来 MVP 目标不进入投递版 |
| 教育/奖项/论文 | 末尾紧凑保留 | 学校、论文有价值，但当前是社招，不应占第一屏 |

## 7. 本轮调研的初步判断与未知项

### 初步判断（尚未由本人确认）

1. 正式版优先采用“**路线 A：业务 Agent 应用工程师 + 经典两页技术社招版**”。
2. 第一屏只讲一个故事：数据开发背景使你能负责场景险经营分析 Agent 的可信取数、分析编排与评测落地。
3. 智能经营分析不再写成 7–8 条功能清单，而压成 4 条证据链：责任范围、编排决策、可信数据与评测、业务结果。
4. 活动配置保留为次项目；质检从主项目降级为“早期探索”或暂不投递。
5. 灰记只保留投递时已验证能力；AI 生成代码与个人产品/架构/验收责任明确分开。
6. 视觉上彻底删除卡片、指标格、章节编号和大面积浅色底，回归黑白单栏技术文档。

### 仍需本人决定的一个关键问题

下一步先选择主投路线：

- A：业务 Agent 应用工程师；
- B：Agent 系统/工程化；
- C：数据智能 + Agent。

确定路线后再写 v0.2。不同路线不是只改标题，而会改变第一屏、项目顺序、保留指标和语言重心。

## 8. 研究限制与排除项

- 公开简历的业绩和身份未逐项核验，本报告只评价写法与视觉，不把它们当作求职结果证据。
- 美团 LongCat 招聘页本轮抓取超时；腾讯 Workday 页面处于维护状态，因此未将其详细 JD 纳入核心对比。
- 招聘网站和培训机构的模板内容容易为了售卖服务制造夸张指标，本轮未把“可直接搬运”的范文当作优秀简历。
- ATS 的具体解析规则由各公司系统决定；“单栏、少图形、文本可复制”是降低解析风险的保守设计，不声称适用于所有系统。
- 本轮完成的是调研与路线选择依据，不是新简历，也不代表旧稿已修复。
