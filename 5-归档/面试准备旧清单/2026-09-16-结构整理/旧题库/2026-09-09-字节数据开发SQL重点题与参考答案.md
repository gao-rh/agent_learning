## 1. 每个直播间最大同时在线人数

### 题目

有直播观看记录表 `live_log`，一行代表某用户的一次完整观看区间。

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| room_id | STRING | 直播间 ID |
| user_id | BIGINT | 用户 ID |
| enter_time | STRING | 进入时间 |
| leave_time | STRING | 离开时间 |

求每个直播间的最大同时在线人数，输出 `room_id、max_online_users`。

约定：

- 在线区间为 **`[enter_time, leave_time)`**，进入时算在线，离开时不再算在线。
- `enter_time < leave_time`；没有重复记录，同一用户在同一直播间的观看区间不重叠。
- 本题统计输入数据覆盖的完整区间，不按天拆分；只输出有观看记录的直播间。

### 样例

| room_id | user_id | enter_time | leave_time |
| --- | --- | --- | --- |
| R1 | 1 | 2026-09-01 10:00:00 | 2026-09-01 10:10:00 |
| R1 | 2 | 2026-09-01 10:05:00 | 2026-09-01 10:15:00 |
| R1 | 3 | 2026-09-01 10:10:00 | 2026-09-01 10:20:00 |
| R1 | 4 | 2026-09-01 10:12:00 | 2026-09-01 10:18:00 |
| R2 | 5 | 2026-09-01 09:00:00 | 2026-09-01 09:05:00 |
| R2 | 6 | 2026-09-01 09:05:00 | 2026-09-01 09:10:00 |

预期结果：

| room_id | max_online_users |
| --- | --- |
| R1 | 3 |
| R2 | 1 |

### 参考答案

```sql
-- Q1：每个直播间最大同时在线人数
SELECT
    room_id,
    MAX(online_users) AS max_online_users
FROM (
    SELECT
        room_id,
        event_time,
        SUM(delta) OVER (
            PARTITION BY room_id
            ORDER BY event_time
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS online_users
    FROM (
        SELECT
            room_id,
            event_time,
            SUM(delta) AS delta
        FROM (
            SELECT
                room_id,
                enter_time AS event_time,
                1 AS delta
            FROM live_log

            UNION ALL

            SELECT
                room_id,
                leave_time AS event_time,
                -1 AS delta
            FROM live_log
        ) t1
        GROUP BY room_id, event_time
    ) t2
) t3
GROUP BY room_id
ORDER BY room_id;
```

### 怎么理解

进入产生 `+1`，离开产生 `-1`。先把同一直播间、同一时刻的变化合并，再按时间累加。

R1 的计算过程如下：

| 时间 | 净变化 | 变化后在线人数 |
| --- | --- | --- |
| 10:00 | +1 | 1 |
| 10:05 | +1 | 2 |
| 10:10 | 0（一个离开、一个进入） | 2 |
| 10:12 | +1 | 3 |
| 10:15 | -1 | 2 |
| 10:18 | -1 | 1 |
| 10:20 | -1 | 0 |

如果题目只问各时段人数，取 `t3` 中的 `room_id、event_time、online_users` 即可；一行表示从当前事件时间到下一个事件时间之前的人数，最后一行表示离场后的 0 人。

### 关键边界与大数据追问

- **为什么不能用 `UNION`？** 多个用户可能同一时刻进入，不能把相同的 `+1` 事件去重。
- **为什么先按时刻汇总？** 避免同时进出被随意排成先进入、后离开，产生不存在的瞬时峰值。
- **同一用户重叠观看怎么办？** 当前算法会数成多个连接。若要求去重用户数，必须先合并同一用户在同一房间的重叠区间。
- **按某一天统计能直接只读当天进入的记录吗？** 不能，跨天观看会漏掉。需要纳入当天开始前仍在线的区间，或补上期初在线人数，再处理当天变化。
- 大房间可能产生倾斜；先按房间和时刻聚合能缩小排序数据量。最终 `ORDER BY` 仅方便阅读，大批量落表通常不需要全局排序。

来源：候选人在 2025 年 4 月字节数据开发二面回忆了“直播间不同时段同时在线人数”的题目。本文扩展为最大同时在线人数，并补充区间规则。[牛客原帖：字节 timeline](https://www.nowcoder.com/feed/main/detail/0cc4dbbee2c843718f63b4745904a278)

## 2. 支付金额行转列，以及列转行

### 题目 A：行转列

支付表 `payment`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户 ID |
| pay_type | STRING | 支付方式，只包含 `alipay`、`wechat` |
| amount | DECIMAL(18,2) | 每笔支付金额，非空 |

每个用户输出一行，包含 `alipay_amount、wechat_amount`。同一方式有多笔支付时求和，没有该方式的支付则填 0。

样例：

| user_id | pay_type | amount |
| --- | --- | --- |
| 1 | alipay | 40.00 |
| 1 | alipay | 60.00 |
| 1 | wechat | 50.00 |
| 2 | wechat | 20.00 |

预期结果：

| user_id | alipay_amount | wechat_amount |
| --- | --- | --- |
| 1 | 100.00 | 50.00 |
| 2 | 0.00 | 20.00 |

### 参考答案 A

```sql
-- Q2A：行转列
SELECT
    user_id,
    SUM(IF(pay_type = 'alipay', amount, 0)) AS alipay_amount,
    SUM(IF(pay_type = 'wechat', amount, 0)) AS wechat_amount
FROM payment
GROUP BY user_id
ORDER BY user_id;
```

`IF` 决定本行金额属于哪一列，`SUM` 汇总同一用户的多笔支付。这里要求总金额，使用 `SUM`；换成 `MAX` 会漏掉其他支付。

如果题目要求“每个用户每天一行”，把日期字段加入 `SELECT` 和 `GROUP BY`，不用把日期写死在查询里。

### 题目 B：列转行

假设上面的结果已保存为宽表 `payment_wide(user_id, alipay_amount, wechat_amount)`。

将两种支付金额转为 `user_id、pay_type、amount` 三列。每个用户固定输出两行，金额为 0 的行也保留。

```sql
-- Q2B：列转行
SELECT
    user_id,
    'alipay' AS pay_type,
    alipay_amount AS amount
FROM payment_wide

UNION ALL

SELECT
    user_id,
    'wechat' AS pay_type,
    wechat_amount AS amount
FROM payment_wide
ORDER BY user_id, pay_type;
```

预期结果：

| user_id | pay_type | amount |
| --- | --- | --- |
| 1 | alipay | 100.00 |
| 1 | wechat | 50.00 |
| 2 | alipay | 0.00 |
| 2 | wechat | 20.00 |

**它恢复的是各方式的汇总金额，不能恢复用户 1 原来的 40、60 两笔明细。** 固定少量列用 `UNION ALL` 很直观；数组或 Map 拆行可再复习 `LATERAL VIEW EXPLODE`，本次不展开。

来源：2024 年 12 月的字节数据开发面经提到手写“行转列”，没有给出完整表结构；本文的支付场景、反向练习与答案均为补充。[牛客原帖：字节数据开发面经](https://www.nowcoder.com/discuss/701930194889609216)

## 3. 每天每个城市消费 Top10，以及占区域总消费的比例

### 题目

订单表 `orders`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户 ID |
| city_id | STRING | 消费发生的城市 |
| dt | STRING | 业务日期，格式 `yyyy-MM-dd` |
| amount | DECIMAL(18,2) | 订单金额，非空且大于 0 |

城市维表 `city_region`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| city_id | STRING | 城市 ID，每个城市恰好一行 |
| region_id | STRING | 所属区域 ID |

订单中的每个城市都能匹配维表。求每天每个城市消费金额前 10 的用户，输出：日期、城市、区域、用户、用户在该城市的消费金额、城市内名次、区域当日总消费、该用户在该城市消费占区域当日总消费的比例。

明确口径：

- 输出粒度为 **日期＋城市＋用户**；同一用户在不同城市的消费分别统计。
- 每个城市每天最多 10 行；金额相同时，用户 ID 小的排前面。
- 占比为 0～1 的小数，保留 4 位。分母是整个区域当天的总消费，包含没有进入 Top10 的用户。

### 样例

`orders`：

| user_id | city_id | dt | amount |
| --- | --- | --- | --- |
| 1 | C1 | 2026-09-01 | 40.00 |
| 1 | C1 | 2026-09-01 | 60.00 |
| 2 | C1 | 2026-09-01 | 100.00 |
| 3 | C1 | 2026-09-01 | 50.00 |
| 4 | C2 | 2026-09-01 | 150.00 |
| 5 | C2 | 2026-09-01 | 100.00 |

`city_region`：

| city_id | region_id |
| --- | --- |
| C1 | A |
| C2 | A |

预期结果：

| dt | city_id | region_id | user_id | user_amount | city_rank | region_amount | region_ratio |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-09-01 | C1 | A | 1 | 100.00 | 1 | 500.00 | 0.2000 |
| 2026-09-01 | C1 | A | 2 | 100.00 | 2 | 500.00 | 0.2000 |
| 2026-09-01 | C1 | A | 3 | 50.00 | 3 | 500.00 | 0.1000 |
| 2026-09-01 | C2 | A | 4 | 150.00 | 1 | 500.00 | 0.3000 |
| 2026-09-01 | C2 | A | 5 | 100.00 | 2 | 500.00 | 0.2000 |

样例每个城市不足 10 人，所以全部保留；超过 10 人时只保留前 10 人，但区域分母仍包括所有人。

### 参考答案

```sql
-- Q3：城市 Top10 与区域占比
SELECT
    dt,
    city_id,
    region_id,
    user_id,
    user_amount,
    city_rank,
    region_amount,
    ROUND(user_amount * 1.0 / region_amount, 4) AS region_ratio
FROM (
    SELECT
        a.dt,
        a.city_id,
        b.region_id,
        a.user_id,
        a.user_amount,
        ROW_NUMBER() OVER (
            PARTITION BY a.dt, a.city_id
            ORDER BY a.user_amount DESC, a.user_id ASC
        ) AS city_rank,
        SUM(a.user_amount) OVER (
            PARTITION BY a.dt, b.region_id
        ) AS region_amount
    FROM (
        SELECT
            dt,
            city_id,
            user_id,
            SUM(amount) AS user_amount
        FROM orders
        GROUP BY dt, city_id, user_id
    ) a
    INNER JOIN city_region b
        ON a.city_id = b.city_id
) t
WHERE city_rank <= 10
ORDER BY dt, city_id, city_rank;
```

### 怎么理解与追问

先把多笔订单合并成一行“用户当天在该城市的消费”，再关联区域。内层窗口同时算城市排名和完整的区域总额，外层才筛选 Top10。

- `ROW_NUMBER`：本题要求最多 10 行，且明确了同额时按用户 ID 决定先后。
- 如果题目要求“第 10 个位置的并列用户都保留”，可用仅按金额排序的 `RANK`；如果要求“前 10 种不同金额”，用 `DENSE_RANK`。这两种口径都可能超过 10 行。
- 维表一个城市多行会放大消费金额，不能靠最后 `DISTINCT` 修复。
- 订单先聚合再关联可以缩小关联输入。两个窗口的分组不同，可能产生额外 Shuffle；不要只根据 SQL 层数猜执行代价。
- 本题金额均为正，区域分母一定大于 0。若包含退款、允许分母为 0，应明确净消费口径，并使用 `IF(region_amount = 0, NULL, ...)`。

来源：2025 年 4 月字节大数据开发暑期实习二面提到城市消费 Top10 与区域消费占比。原帖口径简略，本文补充了并列、跨城市用户和分母的规则。[牛客原帖：字节大数据开发暑期实习（已 oc）](https://www.nowcoder.com/feed/main/detail/59774c282d224401b7b378cb7a7a33f6?toCommentId=21561059)

## 4. 按 30 分钟间隔切分用户会话

### 题目

用户行为表 `user_behavior`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| event_id | BIGINT | 唯一事件 ID |
| user_id | BIGINT | 用户 ID |
| event_time | STRING | 行为发生时间，精确到秒 |

同一用户的行为按时间排序，**相邻两次行为间隔超过 30 分钟，后一次开始新会话**；恰好 30 分钟仍是同一会话。第一条行为开始第 1 次会话，允许跨自然日。

输出 `user_id、session_id、session_start、session_end、event_count、duration_seconds`。会话时长定义为最后一次行为减去第一次行为，单次行为的会话时长为 0。

### 样例

| event_id | user_id | event_time |
| --- | --- | --- |
| 1 | 1 | 2026-09-01 09:00:00 |
| 2 | 1 | 2026-09-01 09:20:00 |
| 3 | 1 | 2026-09-01 09:50:00 |
| 4 | 1 | 2026-09-01 10:21:00 |
| 5 | 2 | 2026-09-01 23:50:00 |
| 6 | 2 | 2026-09-02 00:10:00 |

预期结果：

| user_id | session_id | session_start | session_end | event_count | duration_seconds |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 2026-09-01 09:00:00 | 2026-09-01 09:50:00 | 3 | 3000 |
| 1 | 2 | 2026-09-01 10:21:00 | 2026-09-01 10:21:00 | 1 | 0 |
| 2 | 1 | 2026-09-01 23:50:00 | 2026-09-02 00:10:00 | 2 | 1200 |

### 参考答案

```sql
-- Q4：用户会话切分
SELECT
    user_id,
    session_id,
    MIN(event_time) AS session_start,
    MAX(event_time) AS session_end,
    COUNT(*) AS event_count,
    UNIX_TIMESTAMP(MAX(event_time))
        - UNIX_TIMESTAMP(MIN(event_time)) AS duration_seconds
FROM (
    SELECT
        event_id,
        user_id,
        event_time,
        SUM(is_new_session) OVER (
            PARTITION BY user_id
            ORDER BY event_time, event_id
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS session_id
    FROM (
        SELECT
            event_id,
            user_id,
            event_time,
            IF(
                prev_time IS NULL
                OR UNIX_TIMESTAMP(event_time)
                    - UNIX_TIMESTAMP(prev_time) > 1800,
                1,
                0
            ) AS is_new_session
        FROM (
            SELECT
                event_id,
                user_id,
                event_time,
                LAG(event_time) OVER (
                    PARTITION BY user_id
                    ORDER BY event_time, event_id
                ) AS prev_time
            FROM user_behavior
        ) t1
    ) t2
) t3
GROUP BY user_id, session_id
ORDER BY user_id, session_id;
```

### 怎么理解

对用户 1：

| 时间 | 与上一次间隔 | 是否新会话 | 累加后 session_id |
| --- | --- | --- | --- |
| 09:00 | 无上一条 | 1 | 1 |
| 09:20 | 20 分钟 | 0 | 1 |
| 09:50 | 30 分钟 | 0 | 1 |
| 10:21 | 31 分钟 | 1 | 2 |

判断的是相邻行为的间隔，所以一个会话的总时长可以超过 30 分钟。

### 关键边界与大数据追问

- `DATEDIFF` 计算天数，不能拿来比较分钟；这里先换成 Unix 秒数。
- 两次窗口都按 `event_time、event_id` 排序，让同一秒的多条事件有稳定顺序。不同事件 ID 的行为都保留；脏数据重复应先按事件 ID 清洗。
- 不能按 `user_id、dt` 分区，否则跨天会话会被强制切断。
- 只读当天分区会把当天首条行为误认成新会话。判断边界至少需要前一条历史行为；若还要延续会话编号、开始时间和累计统计，应保留上一批的未结束会话状态。

## 5. 浏览 → 加购 → 支付漏斗

### 题目

用户事件表 `user_event`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| user_id | BIGINT | 用户 ID |
| event_type | STRING | `view` 浏览、`cart` 加购、`pay` 支付 |
| event_time | STRING | 事件时间，精确到秒 |

按业务自然日统计：

- `view_uv`：当天发生浏览的去重用户数。
- `cart_uv`：当天存在“浏览时间 < 加购时间”的去重用户数。
- `pay_uv`：当天存在“浏览时间 < 加购时间 < 支付时间”的去重用户数。
- `view_to_cart_rate = cart_uv / view_uv`。
- `cart_to_pay_rate = pay_uv / cart_uv`。
- `view_to_pay_rate = pay_uv / view_uv`。

所有转化率保留 4 位小数，分母为 0 时返回 `NULL`。同一天可有多次浏览、加购、支付，只要存在一条合法顺序就算转化。

本题是**用户级、同日、严格时间先后**漏斗，不要求同一商品或同一订单，也不要求三个事件在日志中相邻。同一秒发生的两个步骤不算有严格先后。日期有相关事件才输出，无事件日期不补行。

### 样例

以下均发生在 2026-09-01。为缩短表格，只展示时间部分；表内实际保存完整日期时间字符串。

| user_id | event_type | event_time 的时间部分 |
| --- | --- | --- |
| 1 | view | 09:00:00 |
| 1 | cart | 09:05:00 |
| 1 | pay | 09:10:00 |
| 2 | cart | 08:55:00 |
| 2 | view | 09:00:00 |
| 2 | pay | 09:20:00 |
| 2 | cart | 09:25:00 |
| 2 | pay | 09:30:00 |
| 3 | pay | 08:00:00 |
| 3 | view | 09:00:00 |
| 3 | cart | 09:10:00 |
| 4 | view | 09:00:00 |
| 5 | cart | 09:00:00 |
| 5 | pay | 09:10:00 |

预期结果：

| dt | view_uv | cart_uv | pay_uv | view_to_cart_rate | cart_to_pay_rate | view_to_pay_rate |
| --- | --- | --- | --- | --- | --- | --- |
| 2026-09-01 | 4 | 3 | 2 | 0.7500 | 0.6667 | 0.5000 |

用户 2 的有效链路是 `09:00 浏览 → 09:25 加购 → 09:30 支付`；用户 3 的支付早于浏览，不算支付转化；用户 5 没有浏览，不进入漏斗。

### 参考答案

```sql
-- Q5：按天统计有顺序的用户漏斗
SELECT
    dt,
    view_uv,
    cart_uv,
    pay_uv,
    IF(
        view_uv = 0,
        NULL,
        ROUND(cart_uv * 1.0 / view_uv, 4)
    ) AS view_to_cart_rate,
    IF(
        cart_uv = 0,
        NULL,
        ROUND(pay_uv * 1.0 / cart_uv, 4)
    ) AS cart_to_pay_rate,
    IF(
        view_uv = 0,
        NULL,
        ROUND(pay_uv * 1.0 / view_uv, 4)
    ) AS view_to_pay_rate
FROM (
    SELECT
        dt,
        COUNT(DISTINCT IF(
            first_view_time IS NOT NULL,
            user_id,
            NULL
        )) AS view_uv,
        COUNT(DISTINCT IF(
            first_cart_time IS NOT NULL,
            user_id,
            NULL
        )) AS cart_uv,
        COUNT(DISTINCT IF(
            event_type = 'pay' AND event_time > first_cart_time,
            user_id,
            NULL
        )) AS pay_uv
    FROM (
        SELECT
            user_id,
            dt,
            event_type,
            event_time,
            first_view_time,
            MIN(IF(
                event_type = 'cart' AND event_time > first_view_time,
                event_time,
                NULL
            )) OVER (
                PARTITION BY user_id, dt
            ) AS first_cart_time
        FROM (
            SELECT
                user_id,
                TO_DATE(event_time) AS dt,
                event_type,
                event_time,
                MIN(IF(
                    event_type = 'view',
                    event_time,
                    NULL
                )) OVER (
                    PARTITION BY user_id, TO_DATE(event_time)
                ) AS first_view_time
            FROM user_event
            WHERE event_type IN ('view', 'cart', 'pay')
        ) t1
    ) t2
    GROUP BY dt
) t3
ORDER BY dt;
```

### 怎么理解

1. `t1`：在用户当天所有事件上，附加其首次浏览时间，原始事件行仍然保留。
2. `t2`：找**首次浏览之后的最早加购**，作为有效加购时间。不是简单取全天最早加购。
3. `t3`：按日期统计去重用户；支付事件必须晚于有效加购时间。因为仍有多条事件，使用 `COUNT(DISTINCT IF(...))`。
4. 最外层用人数计算比例并处理零分母。

为什么最早的有效步骤就足够？本题只要求当天存在一条合法顺序，没有额外最大时长限制。越早完成浏览、有效加购，给后续步骤留下的时间越多，不会漏掉可成立的链路。

### 关键反例与大数据追问

- **不能分别取三种事件的全天最小时间再比较。** 用户 2 的最早加购在浏览之前，但后面仍有一次合法加购；直接取全天最小值会漏算。
- **不能只判断三种事件是否都出现过。** 用户 3 三种事件都有，但先支付后浏览，不满足顺序。
- 本题按天隔离；今天浏览、明天支付不算同日转化。若改为“浏览后 24 小时内”或必须关联同一商品、订单，需要重新定义分组和匹配条件，不能照搬答案。
- 生产运行可在原始表读取处加业务所需范围的分区条件；不要对分区字段套日期函数后才过滤。本题 `TO_DATE(event_time)` 是确定业务日，不代表自动完成分区裁剪。
- 该写法保留事件行并做去重统计，没有三次明细自连接。高频用户和 `COUNT(DISTINCT)` 仍可能是瓶颈；数据量大时，可在有效步骤识别后收敛到一行“用户＋日期”再汇总，但应根据实际执行计划选择。

来源属性：Codex 补充练习，本次未核实为字节数据开发历史原题。

## 6. 每个部门工资中位数

### 题目

员工表 `employee`：

| 字段 | Hive 类型 | 含义 |
| --- | --- | --- |
| emp_id | BIGINT | 员工 ID，唯一 |
| dept_id | STRING | 部门 ID |
| salary | DECIMAL(18,2) | 工资，允许为空 |

求每个部门工资的中位数，输出 `dept_id、median_salary`。

规则：忽略工资为 `NULL` 的员工；同工资的不同员工都要计入，不能去重。奇数人数取中间一人的工资，偶数人数取中间两人工资的平均值。只输出至少有一名非空工资员工的部门。

### 样例

| emp_id | dept_id | salary |
| --- | --- | --- |
| 1 | A | 1000.00 |
| 2 | A | 2000.00 |
| 3 | A | 9000.00 |
| 4 | B | 1000.00 |
| 5 | B | 2000.00 |
| 6 | B | 3000.00 |
| 7 | B | 10000.00 |
| 8 | C | 1000.00 |
| 9 | C | 1000.00 |
| 10 | C | 9000.00 |
| 11 | D | NULL |

预期结果：

| dept_id | median_salary |
| --- | --- |
| A | 2000.00 |
| B | 2500.00 |
| C | 1000.00 |

### 参考答案

```sql
-- Q6：各部门工资中位数
SELECT
    dept_id,
    AVG(salary) AS median_salary
FROM (
    SELECT
        dept_id,
        salary,
        ROW_NUMBER() OVER (
            PARTITION BY dept_id
            ORDER BY salary, emp_id
        ) AS rn,
        COUNT(*) OVER (
            PARTITION BY dept_id
        ) AS cnt
    FROM employee
    WHERE salary IS NOT NULL
) t
WHERE rn IN (
    FLOOR((cnt + 1) / 2.0),
    FLOOR((cnt + 2) / 2.0)
)
GROUP BY dept_id
ORDER BY dept_id;
```

### 怎么理解

| 有效人数 cnt | 第一个中间位置 | 第二个中间位置 | 实际取值 |
| --- | --- | --- | --- |
| 1 | 1 | 1 | 第 1 行 |
| 3 | 2 | 2 | 第 2 行 |
| 4 | 2 | 3 | 第 2、3 行 |
| 5 | 3 | 3 | 第 3 行 |
| 6 | 3 | 4 | 第 3、4 行 |

`IN` 中两个位置相同时，一行只保留一次。对筛出来的一行或两行求 `AVG`，统一处理奇数和偶数。

### 关键边界与大数据追问

- 必须使用逐行编号 `ROW_NUMBER`。相同工资代表不同员工，不能用 `DENSE_RANK` 把他们压成一个位置。
- `NULL` 要在计算人数和编号之前过滤，不能算完人数再排除。
- 本题使用明确的“中间两项平均”定义，答案按此定义计算。若允许近似分位数，Hive 有 `PERCENTILE_APPROX`；其结果不能直接当作这个精确定义的等价替代，应先确认精度和分位数口径。
- 精确中位数需要组内排序，大部门可能成为瓶颈。不要为了避免排序直接把重复工资去掉，那会改变结果。
