## 总体判断

这些面试不是单纯考“会不会大模型”，而是围绕两个项目持续追问：

1. 智能配置助手：RAG、GraphRAG、知识图谱、意图识别、记忆、召回、rerank、测评、业务效果。
2. 联动压单：分布式锁、强制读主、数据一致性、调度算法、消息乱序、流量承载、业务量级。

面试官最关心的是：你是否真的 own 过项目、是否能说清楚技术选型和指标、是否知道系统在规模变大或异常情况下怎么演进。

| 知识图谱 | 节点和边是什么、图谱来源、如何构建、如何更新、为什么不用规则专家系统 | 准备具体 schema、样例节点边、增量更新方案、图谱召回指标 |
| 测评体系 | 召回率、准确率、F1、自动化测评系统、LLM judge 随机误差、模块解耦测评 | 把离线测评、线上监控、人工兜底、AB 实验分开讲 |
| 记忆与上下文 | 记忆存什么、长期/短期记忆、Redis 存储结构、会话缓存 key/value、记忆过多怎么办 | 明确“会话上下文”和“生成结果缓存”的区别 |
| Agent/Workflow/MCP | Agent vs workflow、function call 原理、没有 function call 如何工具调用、MCP 优点、MCP server 在本地还是云端 | 准备概念边界和一个最小执行流程 |
| 大模型基础 | token、词表、预训练、Transformer、ChatGPT 用到哪部分、微调/SFT/LoRA/DPO/RLHF | 只需能用工程语言讲清楚，不必卷公式 |

| 分布式与一致性 | 分布式锁可靠性、RedLock、Paxos/ZAB、CAP、强制读主、MQ 乱序、幂等 | 用压单项目串起来讲，避免孤立背八股 |
| 系统设计 | 亿级流量、1k QPS RAG、2TB 文件查询、NL2SQL、监控系统、限流器 | 准备“瓶颈识别 -> 分层扩展 -> 降级兜底”套路 |
| 算法题 | 二分、前缀和、哈希、树、并发打印、限流器、生产者消费者、外部排序 | 重点刷中等题和手写并发/系统小组件 |
| HR/终面 | 离职原因、职业规划、优缺点、成长、低谷、职级薪资、base、到岗、offer | 统一动机：想做 AI/大模型更紧密的业务，同时保留工程能力优势 |

## 复习优先级

1. P0：把智能配置助手讲成“业务问题 -> 架构 -> 数据链路 -> 指标 -> 失败 case -> 下一步演进”的闭环。
2. P0：把 RAG/GraphRAG/测评体系讲熟，尤其是 top-k、阈值、BM25+embedding、rerank、F1、LLM judge 偏差、线上监控。
3. P0：把联动压单讲成“并发一致性 + 调度策略 + 流量承载 + 异常兜底”的系统设计题。
4. P1：补 Redis 分布式锁、MySQL 索引/MVCC、Java 线程池/Kafka/IO 多路复用这些后端基础。
5. P1：准备 Agent、workflow、function call、MCP、LangChain/LangGraph 的边界表。
6. P2：准备大模型训练、Transformer、token/词表、SFT/LoRA/DPO/RLHF 的工程化解释。
7. P2：集中刷二分、前缀和、树、并发手写、大文件处理、限流器这几类算法。
8. P3：统一 HR 叙事，避免“只是想逃离原业务”，而是强调“希望进入 AI/大模型结合更紧密的业务，同时保留后端系统工程优势”。

## 下一步动作

用 30-60 分钟先写两份面试口径：

1. `智能配置助手 3 分钟版`：背景、目标、架构、指标、个人贡献、可扩展点。
2. `联动压单 3 分钟版`：业务问题、并发一致性设计、调度策略、流量与异常处理、业务结果。

然后再针对 RAG 测评和分布式锁分别做两张概念卡。

## 主动回忆

合上资料后回答：

1. 为什么这些面试反复追问“召回率、准确率、F1、自动化测评”，而不是只问用了什么模型？
2. 如果面试官问“top-k 为什么是 15”，应该如何把经验选择说成可验证的工程决策？
3. 如果面试官问“为什么不用 LangChain”，如何回答才不是显得自己没用过框架？
4. 如何解释 Agent 和 workflow 的区别，并把它落到自己的项目里？
5. Redis 分布式锁在主从切换时为什么可能不可靠？项目里怎么兜底？
6. 如果 RAG 召回了冗余信息，生成端有哪些手段降低幻觉？
7. 联动压单中强制读主解决了什么一致性问题？为什么它不会无限放大数据库压力？
8. HR 问“为什么离职”时，如何把动机表达成正向选择？
