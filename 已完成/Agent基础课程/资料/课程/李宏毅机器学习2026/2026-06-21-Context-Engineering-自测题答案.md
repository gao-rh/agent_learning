# Context Engineering 自测题答案

这份答案用于对照 [[2026-06-21-Context-Engineering]] 里的 30 个自测题。

使用建议：

1. 先自己口头回答，再看答案。
2. 看答案时不要只看是否“意思差不多”，要看自己有没有说出关键机制。
3. 如果一个答案看懂了但说不出来，说明还需要再讲一遍给自己听。

## A. 基础复述

### 1. 用一句话解释 Context Engineering，不能使用“写 prompt”这几个字。

短答：Context Engineering 是为每一次模型调用选择、组织、压缩、检索和加载信息，让模型在有限窗口里看到完成当前任务所需的上下文。

展开：这里的重点不是一句指令写得漂不漂亮，而是“当前这一轮模型到底应该看到什么”。系统提示、用户任务、历史对话、工具结果、文件片段、记忆、代码、错误栈、工具 schema 都可能进入上下文。Context Engineering 关心的是这些内容如何进入、以什么粒度进入、什么时候被压缩、什么时候被外部化、什么时候被重新读回。

自查：如果你的答案只停留在“优化 prompt”，说明还没有抓住课程重点。更准确的说法应该包含“选择信息”和“管理当前输入”。

### 2. 为什么说语言模型“活在当下”？

短答：因为语言模型每次生成只依赖当前输入窗口里的内容；窗口外的历史、文件、工具结果不会自动被它知道。

展开：模型不像人一样拥有连续意识。一次模型调用结束后，模型本身不会天然保存刚才做过什么。Agent 之所以看起来能连续工作，是因为外部系统把历史消息、任务状态、工具调用结果、文件、记忆等重新组织进下一轮输入。也就是说，“连续性”不是模型内部天然存在的，而是 Agent 系统通过上下文重建出来的。

自查：你应该能解释为什么同一个模型在两个不同对话里不知道彼此发生过什么，也能解释为什么 Codex 每次需要读文件、读 memory、看 git status。

### 3. 当前回合上下文包里可能包含哪些东西？至少列 6 类。

短答：可以包含 system prompt、用户任务、历史对话、工具输出、文件片段、长期记忆、当前计划、错误信息、工具 schema、检索结果、代码上下文、权限和安全约束。

展开：当前回合上下文包不是一个单纯的“用户问题”。它更像一个临时工作台，里面放着模型完成下一步所需的信息。比如 coding agent 可能需要看当前目标、仓库规则、相关文件、测试输出、失败原因、可用工具、不能碰的文件、上一次改动。学习助理可能需要看课程主线、你的原始假设、已确认结论、待确认问题和笔记模板。

自查：如果只能列出 prompt 和历史对话，说明你还把上下文理解得太窄。Agent 场景下，工具和外部状态往往比聊天文字更关键。

### 4. 为什么上下文不能太短？为什么也不能太长？

短答：太短会丢失目标、约束和证据；太长会增加成本、延迟和噪声，还可能让模型注意力被无关内容干扰。

展开：上下文太短时，模型容易忘记任务目标、用户偏好、工具结果、失败经验和安全边界。例如 debug 时只给错误一句话，不给相关代码和复现步骤，模型就只能猜。上下文太长时，模型要处理大量无关信息，成本更高，响应更慢，也更容易把旧的、错的、无关的信息当作线索。长上下文还可能出现 lost-in-the-middle：关键信息在中间位置时更容易被忽略。

自查：扎实的回答应该同时讲“信息不足”和“信息污染”，而不是只说 token 不够。

### 5. Context Engineering 和 Prompt Engineering 的差别是什么？

短答：Prompt Engineering 偏向写好当前指令；Context Engineering 偏向管理整个输入环境，包括历史、记忆、检索、工具、文件、压缩和加载策略。

展开：Prompt Engineering 通常关心如何表达任务、角色、格式、示例和约束。Context Engineering 的范围更大，它要决定哪些资料进入 prompt、哪些不进入、哪些被摘要、哪些被索引、哪些放在文件系统里、哪些工具 schema 给模型看、什么时候读取 memory、什么时候派 subagent。可以说 prompt 是 context 的一部分，但 context 远不止 prompt。

自查：如果能说出“Prompt Engineering 是内容表达，Context Engineering 是信息供应链”，基本就抓住了差别。

## B. 机制区分

### 6. Summary、Hard clear、外部卸载三者有什么区别？

短答：Summary 是把历史压成摘要；Hard clear 是直接清掉历史；外部卸载是把大内容放到文件或存储里，在上下文中保留索引、路径或简要说明。

展开：Summary 的优点是保留主线，缺点是有损，容易漏掉细节。Hard clear 最省 token，但风险最大，因为任务状态和约束可能一起消失。外部卸载介于两者之间，它不把原文全部留在窗口里，但保留可恢复路径，例如“详见 log1.txt”，需要时再用工具读取。对于大日志、网页、长 PDF、长代码文件，外部卸载通常比直接总结更安全。

自查：如果你能举出“5 MB 日志文件写入文件，只把路径和问题索引留在上下文”这个例子，就说明理解到了工程层面。

### 7. 为什么“把历史总结一下”可能会让 Agent 变笨？

短答：因为总结是有损压缩，可能删掉未来任务需要的关键状态、失败经验、精确变量、认证信息或约束。

展开：人类觉得摘要顺畅，不代表 Agent 还能继续工作。比如一个任务里有 API token 的使用规则、某个文件不能改、某个测试失败的精确错误、某个变量名、某个用户已经否定过的方案。如果摘要只写“尝试过一些方法但失败了”，模型就失去了可执行信息。Agent 变笨不是因为摘要本身坏，而是因为摘要没有保留未来决策所需的状态。

自查：好的回答要强调“状态保真”，不是只说“摘要可能不准确”。

### 8. Subagent 为什么可以看作一种自主压缩？

短答：因为 subagent 在自己的上下文里完成子任务，主 agent 只接收回传结果，相当于把大量中间轨迹压缩成一个结果包。

展开：主 agent 如果自己做所有搜索、读取、推理和试错，主上下文会越来越长。派出 subagent 后，子 agent 可以在独立上下文里读很多文件、尝试很多路径、整理证据，最后只把结论、关键证据和建议带回来。子 agent 的内部轨迹通常不会完整进入主上下文，所以它天然起到“隔离噪声”和“压缩轨迹”的作用。

自查：你应该同时看到好处和风险。好处是主线干净；风险是子 agent 如果回传太少，主 agent 无法审查依据。

### 9. Memory 和 RAG 有什么重叠？有什么不同？

短答：二者都把外部信息检索进当前上下文；RAG 更偏知识检索，Memory 更偏跨会话经验、偏好、决策和状态延续。

展开：RAG 常用于从文档库、知识库、网页、代码库中取相关片段回答当前问题。Memory 则常用于记录用户偏好、项目约定、历史决策、过去错误、待办、长期身份信息。它们的技术栈可能重叠，比如 chunking、BM25、embedding、reranking；但语义目标不同。RAG 回答“资料里有什么”，Memory 回答“过去我们经历过什么、决定过什么、偏好什么”。

自查：如果你能解释为什么“课程 PDF 检索”更像 RAG，而“用户喜欢表格、OpenClaw 只是案例”更像 Memory，就说明区分清楚了。

### 10. 为什么工具 schema 太多会污染上下文？

短答：因为每个工具的名称、描述和参数都会占用 token，并增加模型选择工具时的干扰。

展开：工具不是免费能力。一个工具要让模型能调用，通常需要把它的用途、参数、输入格式和限制写进上下文。工具越多，上下文里就越像塞了一本工具目录。模型不仅要完成任务，还要从大量工具里判断该用哪个，这会增加错误调用、误选工具和推理成本。工具 schema 太多时，真正任务信息还可能被挤掉。

自查：你应该能说出“工具越多不一定越好”，并解释为什么按需加载工具是上下文工程问题。

### 11. MCP-Zero 解决的是“工具不会用”还是“工具太多不知道该看哪些”？请解释。

短答：主要解决“工具太多，不应该一开始全给模型看哪些”的问题。

展开：MCP-Zero 的核心思路是主动工具发现。面对很多 MCP server 和 tool，系统不把所有工具 schema 全塞进上下文，而是先让模型根据任务描述自己需要什么能力，再搜索或路由到相关工具。它不是单纯教模型怎么调用某一个工具，而是在大工具生态里减少上下文负担，让模型只看到当前任务相关的工具。

自查：如果你的答案是“让模型学会工具使用”，还不够精确。更准确的是“让模型在工具很多时发现和加载合适工具”。

### 12. 为什么 Manus 说不要随便 remove tools，而是 mask tools？

短答：因为频繁移除工具会改变上下文结构、破坏 KV cache，也可能让历史工具调用变得不可解释；mask tools 可以保留工具定义稳定，同时控制当前可用动作。

展开：在生产 Agent 中，工具定义通常位于上下文前缀。这个前缀稳定时可以复用 prompt cache / KV cache，降低成本和延迟。如果中途增删工具，前缀变化会导致缓存命中下降。更麻烦的是，历史里可能已经出现某个工具调用，如果当前工具定义被移除，模型回看历史时会困惑。mask 的思路是：工具定义仍然存在，但通过状态、约束或调用层控制哪些工具当前可用。

自查：扎实回答要讲出两个层面：缓存效率和轨迹一致性。

## C. 设计判断

### 13. 如果 Agent 正在 debug，一个 5 MB 日志文件应该怎么进入上下文？

短答：不应该全量塞入上下文；应该保存为文件，先检索或过滤相关片段，再按需读取关键行和上下文窗口。

展开：做法可以是：第一步，把日志放在文件系统里，保留路径。第二步，用关键词、错误码、时间段、请求 id、堆栈关键字过滤。第三步，只读取相关片段，比如错误前后 100 行。第四步，把“日志路径、筛选条件、关键错误、已读范围”放入当前上下文。如果后续需要更多证据，再扩大读取范围。这样既可恢复，又不会让模型被大量无关日志淹没。

自查：如果答案是“让模型总结整个日志”，风险较高。更好的关键词是：文件系统、索引、过滤、局部读取、可追溯。

### 14. 如果 Agent 要记住用户长期偏好，应该直接把所有历史聊天塞进 prompt 吗？为什么？

短答：不应该。应该把长期偏好整理成结构化记忆，当前任务需要时再检索加载。

展开：所有历史聊天里有大量噪声、过期信息、临时情绪、已废弃决定和隐私内容。直接塞进 prompt 会浪费窗口，也可能让模型引用过时偏好。更合理的做法是把偏好变成短小、带来源和更新时间的 memory，例如“用户在 agent_learning 课程整理中偏好保留假设与修正，不要被动记录”。当任务涉及课程笔记时再加载这条，而不是每次都加载全部对话。

自查：好的答案会包含“结构化、可检索、可更新、按需加载、避免过期”。

### 15. 一个长任务执行 50 轮后开始跑偏，你会用哪些上下文工程手段把它拉回来？

短答：重申目标、整理当前状态、压缩历史、保留关键失败、更新 todo、读取原始约束、过滤无关轨迹，必要时把子任务拆给 subagent。

展开：具体做法可以是：先把用户目标和验收标准重新放到近端上下文；再生成一份状态摘要，包括已完成、未完成、阻塞点、禁止事项；然后把无关工具输出卸载到文件，把关键错误和决策保留在窗口；接着更新 todo，让模型每轮围绕下一步行动；如果上下文里有很多探索噪声，可以让 subagent 专门审查“现在偏离了什么”。这不是简单清空，而是把任务主线重新变得显眼。

自查：你应该能说出“拉回来”不是靠一句“别跑偏”，而是重新组织上下文的可见性。

### 16. 什么情况下应该压缩？什么情况下不应该压缩？

短答：当历史很长、重复、低价值或已被稳定总结时可以压缩；当信息高精度、高风险、未来会直接执行或需要审计时不应只靠压缩。

展开：适合压缩的内容包括重复讨论、已完成步骤、长篇背景、已经稳定的结论和低风险探索。不能轻易压缩的内容包括 API key 规则、权限约束、用户明确要求、错误栈、测试输出、文件路径、变量名、合同条款、医学法律金融细节、尚未确认的假设。对于高风险信息，更好的做法是原文保留在文件或引用精确行号，再用摘要辅助导航。

自查：判断标准不是“长不长”，而是“未来是否需要精确恢复”。

### 17. 什么信息必须高保真保留，不能只靠摘要？

短答：身份和权限约束、用户明确要求、认证状态、精确错误、代码片段、文件路径、变量名、数值、日期、法律/财务/医学细节、未确认假设来源。

展开：这些信息一旦被摘要改写，就可能改变行为。例如“不要提交大 PDF”不能被摘要成“注意文件大小”；错误栈里的 `TypeError: undefined is not a function` 不能被摘要成“有个 JS 错误”；用户说“OpenClaw 只是教学例子”不能被摘要成“OpenClaw 很重要”。高保真信息可以以原文、引用、行号、结构化字段或文件路径形式保存。

自查：如果某个信息被改一个字就可能造成错误操作，它就需要高保真保留。

### 18. 如果工具调用失败了，错误栈应该删掉吗？为什么？

短答：不应该立刻删掉。错误栈是避免重复失败和定位问题的重要上下文，但可以压缩或外部化保存。

展开：错误栈告诉 Agent 哪条路走不通、失败发生在哪里、是不是权限问题、依赖问题、路径问题或输入格式问题。如果删掉，Agent 可能重复执行同一个失败命令。更好的做法是保留关键错误行、命令、退出码和修复尝试；完整长日志可以放到文件里，当前上下文只保留摘要和路径。等问题解决且不再需要追溯时，才可以进一步压缩。

自查：答案要平衡“不要全塞”和“不要抹掉失败经验”。

## D. 迁移到自己的学习系统

### 19. 在 `agent_learning` 里，哪些内容应该进入当前上下文，哪些应该只作为 Obsidian 文件长期保存？

短答：当前任务目标、相关课程笔记、用户假设、待确认问题、模板和仓库规则应该进入当前上下文；完整历史资料、旧讨论、大量原文、稳定概念库可以长期保存在 Obsidian，按需读取。

展开：比如正在整理 Context Engineering，就需要读取本节课件、已有第一节笔记、相关概念卡、AGENTS.md 规则和用户当前问题。不需要把整个 vault、所有项目报告、所有旧课程笔记都塞进上下文。Obsidian 是长期外部记忆，Codex 的当前上下文是临时工作区。好的学习系统不是把所有笔记一次性暴露给模型，而是让模型能检索、定位、读取相关笔记。

自查：能说出“Obsidian 是长期存储，当前上下文是临时工作台”，说明迁移理解到位。

### 20. 我们现在使用的 `00-inbox -> 10-sources -> 20-concepts` 工作流，哪里体现了 Context Engineering？

短答：它把不同成熟度的信息分层存储，避免把原始记录、课程理解和稳定概念混在一个上下文里。

展开：`00-inbox` 保存原始捕获和未确认想法，相当于外部原始记忆。`10-sources` 整理一节课或一个来源，让上下文更有结构。`20-concepts` 只沉淀稳定、可复用的概念，相当于高质量长期记忆。这个流程本身就是在做上下文工程：什么时候保留原始细节，什么时候整理成来源笔记，什么时候抽象成可复用概念，什么时候不提前升级。

自查：如果你能把这个流程解释成“学习材料的压缩、过滤、晋升和按需检索”，就说明答对了。

### 21. Codex 读仓库时为什么先 `rg` 再局部读文件，而不是直接读全仓库？

短答：因为全仓库信息太多，会浪费上下文并引入噪声；`rg` 可以先定位相关文件，再局部读取必要证据。

展开：代码仓库或笔记库里的大多数文件和当前任务无关。直接读全仓库不仅 token 成本高，还容易让模型被无关模块、旧文件、生成文件干扰。`rg` 相当于关键词过滤，`sed` 或局部读取相当于精确加载。这个过程和 RAG 很像：先召回候选，再读取证据，再决定是否继续扩大范围。

自查：你应该能把这个习惯连接到“过滤”和“按需加载”，而不是只说 `rg` 比较快。

### 22. 如果要给自己做一个“学习助理 Agent”，它需要哪些 memory？哪些 memory 不该自动保存？

短答：需要保存稳定偏好、学习目标、课程进度、已确认概念、常见误区、待复习问题和项目决策；不应自动保存临时情绪、未经确认的假设、隐私敏感内容、一次性闲聊和已过期计划。

展开：有价值的 memory 应该能减少未来重复解释。例如“用户学习时希望保留原始假设，再给严格修正”“OpenClaw 在课程里只作为案例”“概念卡不要提前创建”。不该保存的内容包括你临时说错的一句话、课堂中随口发散的想法、还没确认的结论、私人敏感信息，以及已经被后续决定推翻的旧计划。学习助理的 memory 需要有状态标签，比如待确认、已确认、过期、来源。

自查：好的答案要能区分“长期帮助我学习的偏好”和“当前对话噪声”。

### 23. 你怎么判断一个笔记应该变成稳定概念卡，而不是继续留在 source note？

短答：当它已经脱离单一来源、能用自己的话解释、未来会反复用到，并且关键边界已经确认时，可以升级成概念卡。

展开：source note 主要忠实整理某节课、论文或视频；concept note 需要表达你自己的稳定理解。如果一个内容还依赖原课件上下文、还有争议、只是一个例子，应该先留在 source note。如果它回答了一个会反复遇到的问题，例如“上下文拼接不等于模型记忆”，并且你能举例、说边界、说反例，就适合变成 `20-concepts`。

自查：不要因为一个词看起来重要就立刻做概念卡。概念卡应该是“可复用理解”，不是“课程目录摘录”。

## E. 高阶反思

### 24. “上下文越长越好”这句话错在哪里？

短答：上下文越长，信息不一定越有用；它会增加成本、延迟、噪声和注意力干扰。

展开：长上下文解决的是“装得下”，不是“用得好”。如果上下文里有大量无关文件、过期决策、重复日志和错误线索，模型反而更难判断什么重要。更大的窗口也可能让开发者懒得做检索、过滤和结构化，最终把上下文变成垃圾堆。优秀的上下文应该是“足够且相关”，不是“尽量多”。

自查：能说出“长窗口降低了溢出问题，但没有消除选择问题”，就是关键。

### 25. “模型窗口变成 100 万 token 后，Context Engineering 就不重要了”这句话错在哪里？

短答：窗口变大只缓解容量限制，不解决相关性、成本、延迟、注意力分配、记忆更新和工具选择问题。

展开：即使能放 100 万 token，也要决定放哪些、顺序如何、哪些是最新、哪些已过期、哪些可信、哪些是噪声。模型处理超长上下文仍然有成本和延迟，也可能忽略中间信息。更重要的是，Agent 需要的不只是塞资料，还要能更新状态、检索长期记忆、按需调用工具、保留失败经验、避免重复错误。这些都是 Context Engineering 的范围。

自查：如果你的答案只说“还是会贵”，不够完整。还要说“相关性和状态管理仍然存在”。

### 26. Context Engineering 和模型训练/微调是什么关系？什么时候改上下文，什么时候改模型？

短答：Context Engineering 改的是模型当前看到的信息；训练/微调改的是模型参数中的能力和倾向。能通过给对信息解决的，优先改上下文；需要稳定能力、格式、策略或领域行为时，再考虑训练。

展开：如果模型答错是因为没看到文件、没看到约束、没看到历史决策，那应该改上下文。如果模型已经看到信息但不会执行某类复杂策略，比如稳定地压缩轨迹、选择工具、遵守领域格式，才可能需要微调或 RL。Context Engineering 迭代快、成本低、可解释；训练成本高、风险大，但能改变模型习惯。

自查：关键判断是：问题来自“信息没给对”，还是“能力/行为模式不会”。

### 27. Agentic Context Engineering 的风险是什么？

短答：风险是 Agent 可能保存错误记忆、错误压缩历史、过度自我强化、污染 playbook，或者把临时经验当成稳定规则。

展开：如果让 Agent 自己决定什么值得保存、什么应该删除、什么策略要升级，它可能会把一次偶然成功的做法固化成规则，也可能把用户未确认的想法写进长期记忆。更严重的是，错误摘要会影响下一轮行为，下一轮行为又产生更多错误证据，形成反馈回路。因此 Agentic Context Engineering 必须配合评估、来源记录、版本控制、人工确认和过期机制。

自查：好的答案不是反对 Agent 自己维护上下文，而是强调“需要治理和评估”。

### 28. 如果一个 Agent 自己总结自己的历史，它最容易犯什么错误？你如何评估？

短答：它容易漏掉关键状态、夸大成功、淡化失败、混淆假设和结论、丢失精确细节。评估时要用任务继续成功率、状态保真检查和原文对照。

展开：自总结最危险的不是语言不流畅，而是“看起来合理但不能继续执行”。例如它可能把“用户暂时猜测”写成“已确认结论”，把“测试失败”写成“基本完成”，把“不要改某文件”漏掉。评估方法包括：让另一个模型或人对照原始轨迹检查摘要是否保留关键约束；让 Agent 基于摘要继续任务，看是否能成功；设置必保留字段清单，例如文件路径、错误、决策、待办、用户限制。

自查：如果能提出“摘要后的任务续跑测试”，说明你已经从阅读理解进入工程评估。

### 29. 你能设计一个小实验，比较“全量历史”“摘要历史”“文件卸载 + 按需读取”三种策略吗？

短答：可以设计一个长程 debug 或资料整理任务，让三组 Agent 使用不同上下文策略，比较成功率、token、时间、重复错误和最终答案质量。

展开：实验任务可以是：给 Agent 一个包含多个错误的大日志和代码仓库，让它定位 bug 并修复。A 组每轮保留全量历史；B 组每 10 轮把历史摘要；C 组把日志和中间资料写入文件，只在上下文保留索引、todo 和关键证据，按需读取。评估指标包括：是否修复成功、用了多少 token、耗时多久、是否重复同一失败命令、最终解释是否引用正确证据、压缩后是否丢失关键约束。

自查：实验一定要有可比较指标。只说“试试看哪个更好”不算完整设计。

### 30. 用自己的话解释：为什么 Context Engineering 是 Agent 的核心技术，而不是边角优化？

短答：因为 Agent 的能力很大一部分来自它如何把外部世界、工具结果、历史经验和任务状态组织给模型看；上下文组织错了，再强的模型也会做错下一步。

展开：单次 LLM 调用只是根据输入生成输出。Agent 要持续完成任务，需要连接文件、工具、记忆、计划、错误恢复和长期状态。这些东西都必须通过上下文进入模型的工作空间。Context Engineering 决定模型看到什么、忘掉什么、如何恢复、如何选择工具、如何避免重复错误。它不是把提示词美化一下，而是在设计 Agent 的运行环境。

自查：最终你应该能说出：Agent 的“连续工作能力”不是凭空来的，是上下文工程把外部状态变成当前可用信息。
