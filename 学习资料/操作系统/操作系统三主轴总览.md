# 操作系统三主轴总览

[返回学习资料](../README.md) · [最终总结](操作系统最终总结.md) · [核心疑问](操作系统核心疑问总结.md) · [复习检验](操作系统复习检验.md)

## 这篇文档的叙事方式

《图解系统》按照硬件、内存、进程、文件、设备和网络逐章展开。这里改用 OSTEP 的三个核心问题重新组织：

1. **虚拟化**：怎样把有限的物理资源转换成多个程序都能使用的抽象。
2. **并发**：多个执行流同时推进时，怎样保证协作过程正确。
3. **持久化**：怎样让数据在进程结束、系统重启甚至故障之后仍然存在。

它们不是三个彼此独立的模块，而是操作系统同时承担的三类职责。系统调用、权限、隔离和 I/O 贯穿三条主轴。

```text
                    应用程序
                       ↓ 系统调用
              ┌────────内核────────┐
              │                    │
       虚拟化有限资源        协调并发执行
       CPU、内存             线程、锁、IPC
              │                    │
              └──────访问 I/O──────┘
                       ↓
              持久化数据 / 对外通信
              文件系统、磁盘、网络
                       ↓
                 物理硬件与设备
```

## 共同基础：操作系统从哪里开始

计算机最初只提供 CPU、内存、磁盘、网卡和其他设备。CPU 按指令周期执行机器指令，内存保存运行中的代码和数据，设备负责输入、输出和长期存储。

如果每个程序都能直接控制这些硬件，就会出现三个问题：

- 多个程序会争抢同一资源。
- 一个程序可能破坏另一个程序或整个系统。
- 每个程序都要理解复杂且不同的硬件细节。

因此，内核运行在高权限模式，应用运行在受限的用户态。应用通过系统调用请求内核创建进程、分配内存、读写文件或使用网络；设备通过中断通知内核事件已经发生。系统调用是“应用主动进入内核”，中断和异常是“硬件或执行状态使 CPU 转入内核”。

宏内核、微内核等结构是在回答“这些系统服务放在哪里、如何组织”。Linux 和 Windows 的具体结构不同，但都必须处理资源管理、隔离、并发和 I/O。

## 第一主轴：虚拟化

虚拟化的核心不是虚拟机，而是：

> **把一个物理资源转换成更易使用的逻辑抽象，并让多个程序安全地共享它。**

### 1. CPU 虚拟化：从一个 CPU 到多个进程

物理 CPU 在某一时刻只能执行有限数量的指令流。操作系统把“正在运行的程序”抽象成进程，并快速切换不同进程，使每个进程都能持续向前推进。

```text
物理 CPU
   ↓ 调度 + 时间片 + 上下文切换
进程 A / 进程 B / 进程 C
```

进程不只是代码，还包括虚拟地址空间、寄存器状态、fd 表和内核维护的运行状态。调度器决定下一个运行谁；上下文切换保存当前状态，再恢复另一个进程的状态。

调度算法的名字不是重点。需要保留的是调度目标之间存在权衡：公平性、响应时间、吞吐量、优先级、实时性、多核负载和切换成本不可能同时达到最优。

### 2. 内存虚拟化：从物理 RAM 到独立地址空间

程序使用的是虚拟地址，不是直接使用物理内存地址。每个进程看到自己的虚拟地址空间，页表负责将虚拟页映射到物理页，TLB 缓存常用映射。

```text
进程虚拟地址
   ↓ TLB / 页表
物理内存页
```

虚拟内存同时解决：

- **隔离**：一个进程通常不能随意读写另一个进程的内存。
- **简化**：程序面对连续、统一的虚拟地址，不必关心物理位置。
- **复用**：物理页可以按需分配、共享、换出或重新映射。
- **扩展能力**：支持写时复制、共享内存和内存映射文件。

分段、分页、多级页表、TLB 和页面置换都是这套抽象的具体机制。细节可以忘记，但要知道：虚拟内存不是“凭空增加 RAM”，而是在地址映射、隔离和物理资源管理之间建立一层间接关系。

### 3. 虚拟化背后的共同方法

CPU 虚拟化和内存虚拟化使用了相似思路：

| 物理资源 | 提供的抽象 | 关键机制 | 关键策略 |
| --- | --- | --- | --- |
| CPU | 进程、线程 | 上下文切换、中断、时钟 | 调度谁、运行多久 |
| 内存 | 虚拟地址空间 | 页表、TLB、缺页异常 | 分配哪些页、何时置换 |

机制回答“怎么做”，策略回答“选择谁”。这是理解调度算法、页面置换算法和磁盘调度算法的共同抓手。

## 第二主轴：并发

并发的核心不是“运行得更快”，而是：

> **多个执行流的步骤可能交错，系统必须保证共享状态和协作过程仍然正确。**

### 1. 并发从哪里产生

- 单核 CPU 会在不同进程和线程之间切换。
- 多核 CPU 可以真正同时执行多个线程。
- 中断可能在程序执行过程中到来。
- 进程可能通过共享内存、管道、文件或网络互相影响。

线程是进程内部的执行流。它共享进程的地址空间和打开资源，但拥有自己的栈、程序计数器和寄存器状态。用户线程与内核线程的核心区别是由谁管理和调度。

### 2. 并发为什么困难

当多个执行流读写同一状态时，一条高级语言语句可能被拆成多条机器指令，其执行顺序并不固定。结果如果依赖偶然顺序，就形成竞态条件。

操作系统和线程库提供几类协调工具：

- 锁和互斥量保护临界区。
- 条件变量协调“条件尚未满足时等待”。
- 信号量同时表达资源数量和执行顺序。
- 原子指令为上层同步原语提供硬件基础。

同步解决竞态，也可能引入死锁。死锁的本质是多个执行流形成循环等待。实际设计需要控制加锁顺序、减少锁范围，并避免在持锁时执行不可控的阻塞操作。

### 3. 进程间通信

进程默认相互隔离，但真实程序必须协作，因此内核提供受控通信机制：

| 方式 | 核心理解 |
| --- | --- |
| 管道 | 内核缓冲区，两端通过 fd 读写，适合字节流通信 |
| 消息队列 | 以内核管理的消息为单位交换数据 |
| 共享内存 | 多个进程映射同一物理内存，速度快但需要额外同步 |
| 信号 | 传递轻量事件，不适合承载大量数据 |
| Socket | 内核通信端点，可用于本机或跨机器通信 |

`fork()` 后父子进程继承指向相同内核对象的 fd，因此可以使用同一管道或已打开文件。fd 是进程中的整数句柄，不是对象本体。

### 4. 高并发 I/O

阻塞 I/O 中，一个线程可能长时间等待一个 fd。如果连接很多而大部分时间没有数据，“每连接一个线程”会带来大量线程栈、调度和上下文切换成本。

I/O 多路复用允许少量线程等待多个 fd 的就绪事件。`select`、`poll`、`epoll` 的实现不同，但共同目标是：只处理真正就绪的对象。它们解决的是并发管理问题，不会自动完成业务处理，也不等同于异步 I/O。

## 第三主轴：持久化

持久化的核心是：

> **内存中的状态会随进程结束或断电消失，操作系统需要把数据可靠地组织到长期存储设备中。**

### 1. 从磁盘块到文件

磁盘只提供块读写，应用需要的是有名称、目录、权限和长度的文件。文件系统完成这层转换：

```text
路径名称 -> 目录记录 / dentry -> inode -> 数据块
```

- 目录记录把文件名关联到 inode。
- dentry 是内核用于路径查找的对象和缓存。
- inode 保存文件身份、权限、大小和数据位置等元数据。
- 数据块保存文件内容。

VFS 规定通用的文件对象和操作接口，让 ext4、APFS、网络文件系统和伪文件系统可以接入相似的系统调用。

### 2. 数据块怎样分配

连续分配、隐式链表、FAT 和索引分配都在解决“文件逻辑位置如何找到物理块”。它们权衡随机访问、连续读写、碎片、扩容和元数据成本。

现代文件系统通常采用索引树或 extent，并使用位图等结构管理空闲空间。具体计算可以忘记，但要记住：文件系统同时管理**已属于文件的块**和**仍然空闲的块**。

### 3. 写入为什么不等于持久化

为了性能，应用、标准库、内核和设备之间存在多层缓冲。普通 `write()` 成功通常只表示数据已经进入内核页缓存，不保证已经到达持久存储介质。

```text
应用缓冲 -> 内核页缓存 -> 设备缓存 -> 存储介质
```

`fflush()` 主要把用户态缓冲交给内核；`fsync()` 请求内核同步指定文件的数据和必要元数据。持久化不仅关心“有没有写”，还关心“写到哪一层”。

### 4. 故障一致性

一次文件操作可能需要修改目录、inode、位图和数据块。机器可能在修改到一半时崩溃，导致这些结构互相矛盾。

日志、写时复制和恢复检查等机制用于保证或恢复一致性。这说明持久化不只是把数据放到磁盘，还包括：命名、空间管理、缓存、写入顺序和故障恢复。

### 5. 设备与 I/O

设备控制器暴露寄存器和缓冲区，驱动程序理解具体设备，操作系统提供统一接口。数据传输可能使用 DMA，完成后通过中断通知 CPU；块设备还会经过缓存、文件系统和块层。

设备管理是持久化和外部交互的基础设施：文件系统最终依赖磁盘驱动，网络通信最终依赖网卡驱动，键盘输入也依赖中断和驱动。

## 网络系统放在哪里

网络不是 OSTEP 三主轴中的独立一轴，它横跨并发和 I/O：

- Socket 把网络连接抽象成内核通信端点，并通过 fd 暴露给进程。
- TCP/IP 协议栈把应用数据转换成网络包，网卡驱动负责真正收发。
- 大量连接需要 I/O 多路复用处理并发。
- 中断、软中断和 NAPI 协调网卡事件与 CPU 处理。
- 零拷贝减少数据在用户态、内核和设备之间的重复复制。

因此，学习计算机网络时会再次遇到进程、fd、缓冲区、中断和并发；这不是重复，而是网络建立在操作系统提供的 I/O 基础之上。

## 三条主轴怎样汇合

以一个服务器处理请求为例：

```text
进程获得虚拟 CPU 和虚拟内存                 -> 虚拟化
多个线程或连接同时到达，需要调度、同步和等待  -> 并发
程序通过 Socket fd 收发数据                  -> 并发 + I/O
读取配置、写日志、更新文件                    -> 持久化
系统调用、权限和地址空间保护贯穿全程          -> 接口与隔离
```

从这里可以看出，三主轴不是对章节重新命名，而是在回答三个不同维度的问题：

- 虚拟化回答：**资源怎样被表示和分配？**
- 并发回答：**多个执行者怎样正确地共同推进？**
- 持久化回答：**状态怎样跨越一次运行并抵抗故障？**

## 《图解系统》各部分放回三主轴

| 教材部分 | 在框架中的位置 | 应保留的结论 |
| --- | --- | --- |
| 硬件结构 | 共同基础 | CPU 执行指令，内存保存运行状态，Cache 缓解速度差，设备通过总线和中断协作 |
| 操作系统结构 | 共同基础 | 用户态通过系统调用请求内核；内核组织方式可以不同 |
| 内存管理 | 虚拟化 | 虚拟地址通过页表映射物理页，并提供隔离、复用和按需分配 |
| 进程与线程 | 虚拟化 + 并发 | 进程是资源边界，线程是执行流；IPC 让隔离的进程受控协作 |
| 调度算法 | 虚拟化策略 | CPU、内存页和磁盘请求都涉及有限资源下的选择与权衡 |
| 文件系统 | 持久化 | 文件系统把路径和字节流映射为元数据、数据块和持久存储 |
| 设备管理 | 共同基础 + 持久化 | 驱动、DMA、中断和块层连接内核抽象与真实设备 |
| 网络系统 | 并发 + I/O | Socket、fd、多路复用、中断和零拷贝支撑网络服务 |
| Linux 命令 | 观察工具 | 命令用于观察进程、内存、fd、文件、磁盘和网络的真实状态 |

## 最终只需要记住

1. 操作系统通过系统调用向程序提供服务，通过中断和驱动控制设备。
2. 虚拟化把 CPU 和内存变成进程、线程和虚拟地址空间。
3. 并发处理多个执行流的交错、同步、通信和等待。
4. 持久化把易失的运行状态转换成有名称、可恢复的长期数据。
5. fd 是进程访问文件、管道、Socket 等内核对象的统一入口。
6. 权限、隔离、缓存和性能权衡贯穿所有部分。
