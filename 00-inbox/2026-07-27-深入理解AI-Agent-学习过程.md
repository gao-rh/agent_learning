### 2026-07-28 第一章前半节复述

#### 用户原始理解

- Human / Harness 中一部分原本由人显式设计的流程，正在逐渐被模型训练所替代，但未来能替代到什么程度还不知道。
- Agent 可以理解为大语言模型 + 工具 + 上下文。
- 工具和上下文各有多种分类；当前记得上下文里有固定的工具定义、系统指令和历史信息。具体分类没有完全记住，也暂时不认为需要死记。
- 现在很多模型已经具备工具调度能力，但还没有理解：为什么训练进模型的能力会比依靠 Prompt 和 Harness 更强，以及为什么能在长程任务中保持得更久。

#### 助手反馈

- “人的部分被替代”需要收紧为：一部分原来写在 Prompt、工作流和编排代码里的决策策略，正在被模型参数内化；工具实现、权限、安全、验证和业务约束仍主要由外部 Harness 承担。
- 工具调度能力通常主要来自后训练（SFT / RL），预训练主要提供语言、知识、推理和任务分解基础。
- 上下文分类不需要死记。当前先抓住 `静态前缀（系统指令 + 工具定义）+ 动态轨迹（用户消息 + 模型回复/工具调用 + 工具结果）` 即可。
- 长程稳定性不是永久记忆，而是更高的单步决策正确率、针对长轨迹的训练、错误恢复策略，以及 Harness 持续保存和回传轨迹共同作用；任务越长，单步小差异越会被连乘放大。

#### 状态

- Agent 三要素：`已复述，方向正确`
- 上下文结构：`掌握主干，不要求记分类名称`
- 原生工具调度与长程稳定性：`已讲解待复述`

### 2026-07-28 第一章后半节复述

#### 用户原始理解

- 后半部分主要讲 Harness 的重要性，以及工作流和自主 Agent 的差别。
- 阅读后没有找到一个明显的新核心认知点。

#### 助手反馈

- 这一部分真正值得留下的不是 Harness 功能分类，而是一个工程决策原则：**模型有能力完成任务，不等于系统能够可靠、安全地完成任务；模型做不稳的部分，需要由 Harness 用约束、验证和纠正补上。**
- 工作流与自主 Agent 的差别，本质是“下一步由谁决定”：工作流把路径决定权留给程序员，自主 Agent 把部分路径决定权交给模型。
- 选择时不是追求越自主越好，而是使用完成任务所需的最小自主性：单次调用能解决就不用工作流，固定路径能解决就不用自主 Agent；现实系统常在高风险环节使用工作流，在开放探索环节使用自主 Agent。
- 当前不需要记住全部护栏类型和框架名称，先保留 `能力不等于可靠性`、`决策权分配`、`最小必要自主性` 三个判断。

#### 状态

- Harness 核心价值：`已复述确认`
- 工作流与自主 Agent：`已复述确认`

#### 用户确认后的阶段结论

- Harness 的构成 `上下文 + 工具 + 约束 + 验证 + 纠正` 是一个值得保留的方法论。这里使用“验证”而不是“评估”：验证是在一次运行中检查结果对不对，评估通常是跨任务、跨样本衡量系统整体表现。
- 能由一次模型调用解决的任务，不必增加编排。
- 执行路径固定、可预先定义时使用工作流；执行路径需要根据环境反馈动态生成时使用自主 Agent。
- 同一系统可以混合使用工作流和 Agent：开放探索交给 Agent，高风险或强合规步骤交给工作流。

### 2026-07-30 Few-shot 示例放置与 KV Cache

#### 触发材料

- 《深入理解 AI Agent》第 2 章：示例在上下文中的放置与前缀稳定性。

#### 用户标记的重要判断

> 工程上有两个决策点。第一，**示例放在哪里**：放在系统提示词中，示例成为静态前缀的一部分，对所有请求生效；也可以伪造一组 user/assistant 消息放在首轮对话位置，适合按会话类型选用不同示例集的场景。第二，**示例对 KV Cache 前缀稳定性的影响**：无论放在哪个位置，示例都处于上下文靠前的区域，一旦确定就应当保持字节级稳定——如果按请求动态检索“最相关”的示例，等于每次都改写前缀，缓存会持续失效。因此生产系统通常为每类任务准备固定的示例集，而不是逐请求挑选。

#### 当前处理

- 状态：`用户标记为重要，待结合 Prompt Cache 实验确认边界`
- 可提炼概念：`Few-shot 示例放置`、`静态前缀`、`按任务类型固定示例集`、`动态示例检索与缓存命中的取舍`
- 待验证：对比“固定示例集”与“逐请求动态替换示例”的 TTFT / Prompt Cache 命中情况，并检查任务质量收益是否值得缓存损失。

### 2026-07-30 工具定义：专用搜索接口与渐进加载

#### 用户的核心问题

- Claude Code 工具定义为什么要求“NEVER invoke `grep` or `rg` as a Bash command”？是否意味着它自己定义了一个实现 `grep` / `rg` 能力的专用工具，然后不让模型通过 CLI 执行？
- 工具定义现在是完整放入上下文，还是像 Skills 一样按需拼入？Codex 采用哪种方式？

#### 助手反馈

- 用户的第一句理解是对的：Claude Code 把内容搜索收敛为专用的 `Grep` 工具；模型需要搜索时应调用它，而不是调用通用 Bash 工具后自行拼 `grep` 或 `rg` 命令。
- `Grep` 的底层使用 ripgrep。专用接口额外提供受控的权限/访问范围，以及结构化参数和输出模式：可只返回命中文件、命中数量或匹配内容；同时支持正则、按 glob 或文件类型过滤、多行匹配。核心不是“rg 不好”，而是避免模型绕开这层可控接口。
- 工具 schema 有两种模式：基础、高频工具可在开场直接可见；大规模、外接或低频工具可先只暴露名称和简介，模型需要时通过工具搜索取得完整 schema。完整 schema 追加到轨迹末尾后保留在原位，后续轮次可以复用此前的前缀缓存。
- Codex 的当前思路可先记为：`基础工具常驻 + 外接工具按需搜索与加载`。这不是绝对按“重要程度”划分，而是工具数量、来源、使用频率和上下文成本之间的工程取舍。

#### 状态

- 专用 Grep 工具与 Bash 中执行 `rg` 的区别：`已讲解待复述`
- 工具 schema 的“全量常驻 / 渐进加载”取舍：`已讲解待复述`
- 与 KV / Prompt Cache 的连接：`已建立，待用自己的话复述`

### 2026-07-30 MCP 与“工具”到底差在哪里

#### 用户原始理解 / 核心问题

- 已理解直接工具调用：告诉模型“有这个接口”，再按参数规范调用即可。
- 困惑：MCP 虽被称为“工具使用协议”，但它到底规定了什么？它和工具本身的差别是什么？

#### 助手反馈

- **工具**是一个具体能力/动作，例如“搜索仓库”“查询日历”“创建工单”。它回答的是：`能做什么`。
- **MCP**不是那个动作，而是 AI 应用与外部能力提供方之间的一套连接协议。它回答的是：`外部服务如何被接入、声明能力、被发现、被调用，以及如何处理权限、会话和返回结果`。
- 直接集成时，Codex/Claude 团队要为每个外部系统各写一套专用适配代码；MCP 把双方约定成 Host（例如 Codex/Claude Code）— Client — Server：Server 可统一暴露 tools、resources、prompts，Host 通过 MCP 连接和发现它们。一个 MCP Server 因而能被多个兼容的 AI 应用接入。
- 所以“工具”是 MCP Server 可提供的三类能力之一；另外两类是 **resources**（可读上下文数据）和 **prompts**（可复用交互模板）。MCP 的范围比“模型调用一个函数”更大。

#### 状态

- MCP = 工具本身：`已纠正，二者不是同一层`
- Host / Client / Server 分工：`已讲解待复述`
- tools / resources / prompts 三类 MCP primitive：`已讲解待复述`

#### 追问：为什么还需要“统一”

- 用户澄清：同一个外部接口无论被 Codex 还是 Claude Code 调用，请求参数与格式本来就相同；困惑 MCP 为什么还要统一。
- 助手反馈：这点正确。MCP **不改变同一个业务 API 的格式**，也不是为了让“同一个接口被不同应用调用时格式相同”。它统一的是上层的 AI 接入契约：不同服务原本各有不同 API、鉴权、工具描述、发现方式与返回格式；不同 AI Host 也各自需要把这些能力转成模型可用工具。MCP Server 位于中间，对外使用统一的发现/调用/资源/权限会话协议，对内再翻译到日历、GitHub、数据库等原有 API。这样避免每一个 Host 与每一种外部服务各写一份专用适配。
- 待复述的关键：`业务 API 仍各不相同；MCP 统一的是 AI Host ↔ 外部能力提供方的适配层。`

#### 继续澄清：接入是否只是“给出工具定义”

- 用户追问：所谓接入过程，是否不就是把工具定义给出去？
- 助手反馈：给出工具定义只是第一步——它让模型知道“能调用什么、参数是什么”，但不能执行。完整链路还需要：Host 与 MCP Server 建立连接并协商能力；Host 获取工具 schema 后按需要交给模型；模型选择调用时，Host 将工具名和参数通过 MCP 发给 Server；Server 执行业务 API/本地代码并把结果按 MCP 返回；Host 再将结果追加到模型上下文。MCP 规范的正是这整段 Host ↔ Server 的发现、调用、结果、会话与权限边界；工具 schema 只是其中一条消息。

#### 核心澄清：为什么不让 Host 直接请求业务 API

- 用户指出真正问题：既然 MCP Server 最终仍要组装参数并请求业务 API，为什么 Host 不直接请求业务 API？直接请求并没有不好。
- 助手反馈：这个判断正确。**单一 Host + 少量已知服务**时，Host 直接集成业务 API 通常更简单，也常是更合适的生产方案；MCP 不是性能必需层。两种方案的实质差别是“适配器放在哪里、由谁维护”：
  - 直接集成：Host 内置每个服务的适配器，自己处理该 API 的鉴权、schema、错误、分页与版本变化，然后调用业务 API。
  - MCP：服务方/工具方维护 MCP Server；Host 只实现一次通用 MCP Client。Server 对 Host 提供统一协议，对内再适配自己的业务 API、凭证与策略。
- MCP 的收益是生态规模：若有 H 个 Host 和 S 个外部服务，直接集成趋向 H×S 份适配；MCP 趋向 H 个 MCP Client 加 S 个 MCP Server。它还让凭证、服务专属权限与业务逻辑留在服务侧，并让 Host 统一做用户授权、调用确认和上下文隔离。
- 代价也应保留：多一层进程/网络与协议复杂度，可能增加延迟和攻击面；不跨 Host 复用、且服务很少时，不要为了 MCP 而 MCP。
- 待复述的关键：`MCP 不是让调用更“能做”，而是把“每个 Host 都要懂每个 API”的适配责任，转为“Host 懂 MCP、服务方懂自己的 API”。`

#### 追问：适配代码具体是什么

- 用户问题：图中的“适配代码”具体指什么。
- 助手反馈：适配代码不是工单/日历 API 本身，而是二者之间的翻译与接线层。例如模型工具调用给出 `create_ticket(title, assignee)`；适配代码需处理用户授权/凭证，把 `assignee` 翻成工单系统的 `assignee_id`，构造该系统要求的 HTTP 请求，调用其 API，并将成功、分页或错误结果整理成 Host/模型能消费的工具结果。没有 MCP 时这段代码由每个 Host 各自维护；有 MCP 时它通常在服务方的 MCP Server 内维护。

#### MCP 结构与模型层是否有差别

- 用户问题：一个现实 MCP 的结构是什么？它提供的接口和直接 API 的差别，是否会在模型/Agent 视角形成实质差别？
- 助手反馈：常见链路是 `Agent/模型 → Host（Codex、Claude Code）→ MCP Client → stdio 或 HTTP → MCP Server → 原有业务 API、数据库或本地能力`。先连接和协商能力，再发现 tools/resources/prompts；模型选择工具后，Host 经 MCP 发起调用，Server 执行并返回结果，Host 再将结果放回模型上下文。
- 对模型而言，**直接工具集成与 MCP 工具通常几乎相同**：都是看到 `名称 + 描述 + 参数 schema`，输出一次结构化 tool call，再读取 tool result。模型不天然知道后面是 Host 直调 API，还是 Host → MCP Server → API。
- 会传导到模型层的差别来自接口设计，不是 MCP 的必然属性：MCP Server 可能把原始 API 包装成更语义化、更小、更安全的工具，提供 resources/prompts，或通过工具发现按需加载 schema；直接集成也完全可以做到同样的事。反过来，糟糕的 MCP Server 也会给模型暴露难用的 schema 和杂乱结果。
- 待复述的关键：`MCP 主要改变集成/执行架构；模型感受到的是工具 schema 与结果质量，而不是 MCP 这个名字。`

#### 进一步追问：能否把适配直接做进最终 API

- 用户推理：维护 MCP 也是维护接口；既然适配代码只是固定格式参数与业务 API 的映射，能否直接把这层封装维护在最终服务里？是否有 MCP 能解决、直接连接一定不能解决的场景？
- 助手反馈：推理正确。**不存在理论上 MCP 能做而“直接连接”绝对不能做的能力**；直接连接可以通过足够的定制代码实现任何 MCP Server 的效果。若最终服务直接暴露 MCP endpoint，它不是绕过 MCP，而是“最终服务本身实现了 MCP”，中间层可以薄到只是同一进程中的一个路由。
- MCP 解决的是互操作和接入成本，而非新增业务能力：对一个未修改的通用 Host（例如 Codex），它只知道标准 MCP 的发现/调用协议，并不知道某个公司自定义 API。服务方发布 MCP Server 后，用户无需等待 Host 厂商为该服务写专用适配，即可接入；若只给自定义 API，则必须改 Host、安装 Host 专属插件，或由 Host 厂商新增集成。
- 因而应区分“技术上能不能”和“在既有生态、既有 Host 不改代码的约束下能否即插即用”。MCP 的价值来自后者。小系统仍可直接 API；服务也可同时提供原生业务 API 与 MCP endpoint。
- 待复述的关键：`MCP 是可互操作的扩展点，不是直接 API 做不到的新能力；把 MCP 做进最终服务，就是服务直接说 MCP。`

#### 用户当前总结

- 业务服务原本已经有自己的 API，供既有应用使用；当 AI Host 要使用时，需要把原生 API 接成模型可调用的能力，并处理工具 schema、鉴权、参数/结果转换等。
- MCP 统一的正是这层接入/适配，不是说所有场景都必须使用 MCP。
- 助手确认与微调：方向正确。“AI 不能直接用”应收紧为：**模型不能自行理解并安全调用任意原生 API；但 Host 可以为它直接集成原生 API。** 当不需要跨 Host 复用时，直接集成完全可行；MCP 是让这层接入可以标准化复用的选择。

### 2026-07-30 提示注入：来源标记是否真的在用

#### 用户问题

- 读到提示注入防御中的“用明确标记包裹外部内容并标注来源”。追问：现实 Agent 系统是否真的使用这种策略？

#### 助手反馈

- 原文对应的是 `structured content` / 来源标记：例如将网页、邮件、文档等不可信内容放入 `external_content` 一类的边界中，并注明来源；目的不是让标记“消灭”注入，而是向模型保留“这是一段数据，不是高优先级指令”的信号。
- 现实中这类区分很常见，但不一定总以手写 XML 标签出现。更常见的实现包括标准 `system/user/assistant/tool` 消息角色、带来源元数据的 tool result/content block，以及在需要时额外用 XML/JSON/YAML 包裹抓取文本。外部文本不应被扁平拼入系统提示或伪装成 user 指令。
- 它只能降低成功率，不能构成安全边界：模型仍会读到其中的文字，攻击仍可能成功。生产系统还必须叠加最小权限、沙盒、敏感数据/外发控制、高风险写操作确认、URL/网络限制和监测。OpenAI 的当前公开安全说明同样将提示注入视为需要分层缓解的持续问题，而不是靠过滤或标记一次解决。

#### 状态

- 来源标记 / 结构化角色：`已讲解，属于常见第一层防御`
- “标记即可防注入”：`已纠正，必须分层防御`

#### 情境检查

- 用户问题：若让 Agent 阅读网页，网页中出现提示注入并要求泄露用户密码，Agent 是否会执行、如何分辨？
- 助手反馈：不会执行。网页内容属于不可信外部数据，不能覆盖用户目标或更高优先级规则；泄露密码也不是用户授权的任务。判断依据包括内容来源/消息角色、是否与用户请求相关、是否试图改变任务或诱导敏感数据外发。来源标记帮助模型识别，但不是完美判别器，因此系统还需做到即使模型误判，也没有可读取的广泛凭证、没有可静默外发的高风险权限，并在关键行动前要求确认。
- 用户追问：系统如何判断一句话来自用户，还是来自被读取的网页？
- 助手反馈：不能只靠文字内容猜测。正确实现应在进入模型前保留 provenance：用户直接输入作为 `user` 消息；网页抓取结果作为 `tool` 输出或带来源标记的外部内容块；系统指令则使用 `system/developer` 等更高优先级角色。模型据此区分。若开发者把网页原文直接拼进用户消息，来源边界就被抹掉，防御会变弱；即使用户粘贴外部内容，也应视作待处理材料而非让其中命令自动改写任务。

### 2026-07-30 Skill 的执行服从度：会不会被上下文稀释？

#### 用户问题 / 假设

- Skill 如果本质只是普通提示词或一份说明，长任务里后续对话、网页内容和工具结果不断进入上下文后，它会不会很快被“稀释”？怎样确认 Agent 真正服从了它？

#### 助手反馈（待继续展开）

- 这个担心成立。Skill 通常不是比 system/developer 指令更高优先级的“硬权限”；它更像一份在任务匹配时被加载进上下文的专门工作规程。若只靠一段自然语言，确实会受上下文长度、冲突指令、模型能力和调用时机影响。
- 所以“写了 Skill”不等于“保证执行”。可靠性来自分层：让 Skill 的触发条件明确；把关键步骤写成可检查的清单；把真正不能违反的动作交给程序/权限/Hook/工具 schema 强制；最后用测试、日志或可观察产物验证步骤是否实际发生。
- 可先记为：`提示词负责引导，代码和权限负责强制，验证负责确认。` Skill 的服从度不能只靠模型自我报告。

#### 待追问

- 在 Codex 这类系统里，Skill 的完整内容何时加载？它与 system/developer 指令、AGENTS.md、Hook、工具描述分别处于什么优先级和执行边界？
- 如何为一个具体 Skill 设计“可验证的服从度测试”？

#### 用户纠正后的核心问题：模型如何知道“这是 Skill”

- 用户澄清：重点不是后续怎么验收，而是 Skill 注入上下文后，Agent/模型凭什么把它与普通用户话、网页内容或工具结果区分开？听说 Claude 会用 `<system-reminder>` 一类标志包裹；业界现在通常采用哪种方式更好？
- 已查到的 Claude Code 当前公开行为：常规会话先常驻 Skill 的 `name + description`，用作发现/触发；调用某个 Skill 时，渲染后的完整 `SKILL.md` 作为一条单独的**用户消息**追加进对话，并在该会话后续仍保留。当前文档所说的 `<system-reminder>` 用于“文件已变化”等 Host 注入的运行时提醒，而不是当前公开文档中 Skill 的标准包装方式。
- 初步结论：Skill 并不存在一个被所有模型 API 原生理解的通用 `skill` role。它是 Host 的概念；Host 必须保留来源与结构，模型才能知道“这一段是 Host 激活的工作规程”。单个 XML 标签本身不自动提高优先级，它只是在同一消息内提供边界/语义。
- 更稳妥的业界设计是分层组合：
  1. 用真正的消息角色/可信通道区分 system/developer、用户、工具/外部内容；
  2. Host 在调用时以独立、带来源的消息或 content block 注入完整 Skill，并可加结构化标签（如 `skill_instructions`、名称、版本、作用域）以避免和自然语言混在一起；
  3. 用 Hook、权限和工具校验承载必须硬执行的约束，不能只依赖标签。
- 待确认表达：`role/provenance 负责“这是谁说的”，结构化边界负责“这段是什么”，权限/代码负责“它能不能真的约束行为”。`

### 2026-07-31 Attention 的归纳偏置：更像相似匹配，而非天然的总结推理

- 用户澄清：此处不是在谈 RAG 或外部信息检索，而是在 Agent 状态相关内容中谈注意力机制的本质特性——它更擅长相似匹配，不是天然擅长总结/推理。
- 助手反馈：这个说法的核心在于单层 Attention 的动作：当前 token 产生一个 Query；它和上下文各位置的 Key 做相似度计算；再按分数加权读取对应的 Value。也就是“根据我现在需要什么，从历史里找最相关的位置，再把信息拿回来”。这是一种可微的内容寻址/软检索机制。
- 因而 Attention 天生的归纳偏置偏向：找相似模式、复制相关内容、把远处的相关片段拉到当前位置；它本身并不是一个带显式变量、规则和不变量检查的逻辑推理器。多层 Attention、MLP、训练数据与生成循环可以共同表现出复杂推理，但不能把这种表现等同于 Attention 单步的本质。
- 对 Agent 状态的启发：不要期待模型每回合都可靠地“通读历史，再自行总结出精确状态”。更稳的做法是把关键状态外显为短小、结构化、可更新的字段/清单；需要时让模型按当前目标检索相关状态。这样是在顺着 Attention 的“按需取相关内容”的优势设计上下文。
- 待进一步联系：Transformer 的 Q/K/V、状态摘要为何会漂移、以及何时保留原始轨迹而非反复摘要。
