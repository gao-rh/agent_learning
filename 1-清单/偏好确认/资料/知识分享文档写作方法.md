# 知识分享文档写作方法

## 一句话原则

知识分享文档不是教案，也不是资料堆砌。它要让读者带着一个问题进来，顺着清晰主线读下去，最后能用自己的话说清楚这个问题。

## 调研得到的写作原则

| 来源 | 可复用原则 | 对我们的影响 |
| --- | --- | --- |
| NN/g：How Users Read on the Web | 读者通常不是逐字阅读，而是扫描页面。 | 标题要承载信息，段落要短，表格和列表要帮助扫读。 |
| NN/g：Inverted Pyramid | 先给最重要的信息，再给背景和细节。 | 开头不要解释作者怎么组织文章，先回答读者最关心的问题。 |
| Google Developer Style Guide | 技术文档优先清晰、一致，并服务具体读者。 | 不追求漂亮话，优先让目标读者理解概念边界。 |
| Microsoft Writing Style Guide | 技术表达要简洁、清楚、自然。 | 少写空泛描述，多写直接判断和具体机制。 |
| IBM AI Agents | AI Agent 文章通常会围绕目标、工具、记忆、计划、外部行动展开。 | 写 Agent 时不能只讲模型或工具，要讲完整运行系统。 |

## 个人偏好

这类文档要符合以下偏好：

| 偏好 | 写法 |
| --- | --- |
| 不是教案 | 不写“本节课要解决什么”“教学目标”。 |
| 面向读者 | 从读者已经听过的说法、困惑和误解切入。 |
| 先承接再纠偏 | 先说“大家通常怎么理解”，再说“哪里对、哪里不完整”。 |
| 直接陈述 | 不写“本文判断是”“这篇文章的讲法是”。 |
| 少过程，多结论 | 不把整理过程、待确认、笔记核对放进正文。 |
| 详细但不散 | 细节要服务主线，不把专题细节强塞进主文。 |
| 图表克制 | 平行概念、模块、误区、流程可以用表格或图；开头和主叙事不要被表格打断。 |
| 遵循个人语言风格 | 具体语气、句式和表达禁区参考 [个人语言风格](个人语言风格.md)。 |

## 推荐结构

一篇知识分享文档可以按这个顺序组织：

1. **大家通常怎么说**
   先承接读者熟悉的说法。比如“很多人说 Agent 是会自己做事的 AI”。

2. **这些说法哪里对、哪里不完整**
   不要直接否定读者。先承认它抓住了什么，再指出它漏掉什么。

3. **实际应该怎么理解**
   用一句清楚的话给出核心理解。这里要直接陈述，不要写成“本文认为”。

4. **用一条主线讲清楚**
   找一条能贯穿全文的线索。比如“语言模型缺什么，Agent 补什么”。

5. **拆机制，但不堆模块**
   每一节都回答一个自然问题，例如“它怎么行动”“它怎么记忆”。

6. **回到一句话定义**
   读者读完细节后，要能重新得到一个更准确的一句话理解。

7. **留下自检问题和专题链接**
   自检问题帮助复习；专题链接承接被压缩的细节。

## 开头写法

好的开头应该做到三件事：

| 目标 | 写法 |
| --- | --- |
| 让读者确认自己来对地方了 | 直接写出读者已经听过的常见说法。 |
| 让读者发现原理解不够 | 指出这些说法各自漏掉的关键层。 |
| 给出继续阅读的理由 | 告诉读者接下来会顺着哪条主线把问题讲清楚。 |

推荐句式：

```text
现在很多人会说：Agent 是会自己做事的 AI。
这个说法有用，但不够。
它抓住了 Agent 的行动感，却没有说明行动是怎么发生的。
更准确地说，Agent 是包在语言模型外面的一套运行系统。
```

避免句式：

```text
本文的核心问题是……
本文的判断是……
本文的讲法是……
本节课要解决……
```

## 正文检查清单

写完后检查：

- 第一屏有没有直接回答读者最想知道的问题。
- 标题是否能单独扫读出文章主线。
- 每一节是否只回答一个主要问题。
- 表格是否真的帮助比较，而不是为了好看。
- 是否有过多“作者整理过程”的痕迹。
- 是否把案例当成主角，压过了概念本身。
- 是否把专题细节塞进主文，导致主线变散。
- 最后的一句话定义是否比开头更准确。

## 用在《Agent 到底是什么》上的规则

这篇文章采用“知识分享长文”形态。

主线固定为：

```text
大家通常怎么理解 Agent
-> 这些说法为什么不完整
-> 语言模型本身是什么、缺什么
-> Agent 如何补齐身份、工具、知识、记忆、触发、长期执行、安全
-> 回到 Agent 的定义
```

OpenClaw 的角色：

- 是贯穿案例。
- 不是产品介绍。
- 不单独抢主标题。
- 每次出现都要服务“Agent 是什么”这个问题。
