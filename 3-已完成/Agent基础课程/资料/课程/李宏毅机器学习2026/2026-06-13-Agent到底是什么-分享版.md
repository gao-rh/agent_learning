# Agent 到底是什么

> 很多看起来像“模型变聪明了”的能力，其实来自模型外面的 Agent 设计。

## 很多能力，不只是模型聪明

当一个 AI 产品表现得很强时，我们很容易把功劳归给底层模型。

Claude Code 能读仓库、改代码、跑命令，我们会说 Claude 模型很强；Codex 能处理软件工程任务，我们会说 GPT 很厉害；ChatGPT 好像记得你之前说过什么，我们也会觉得是模型本身越来越聪明。

这个说法只对了一半。

模型当然重要。没有足够强的模型，后面的系统设计很难发挥作用。但很多让你觉得“它真的会做事”的能力，并不是模型参数本身直接提供的，而是来自模型外面那层工程系统：它怎么拼上下文，怎么开放工具，怎么保存和检索记忆，怎么定时触发任务，怎么控制权限，怎么把工具执行结果带回下一轮。

这套把模型接进真实工作流的系统，就是 Agent。

换句话说，Agent 的核心不是让模型“变得更聪明”。模型本身已经有语言理解、推理、生成、写代码、选择下一步的能力。Agent 真正做的事，是让这些智能不再停留在“说话”层面，而是能进入真实任务，调用真实工具，读写真实资料，持续推进真实问题。

这也是理解 Agent 最关键的地方：

> 大模型本身更像一个强大的语言引擎。Agent 让这个语言引擎进入现实环境，让它的智能真正发挥作用。

## 语言模型本身能做什么，又缺什么

先把语言模型讲清楚。

语言模型最底层的能力，可以粗略理解成“文字接龙”：给它一段上下文，它根据已有文字继续生成下一段文字。

一次模型调用可以简化成：

```text
给它一段上下文
-> 模型根据上下文继续生成
-> 返回这次生成结果
```

这个能力非常强。因为当模型足够大、训练足够充分、对指令足够敏感以后，“继续生成文字”不再只是补一句话。它可以表现为解释问题、写代码、拆任务、比较方案、生成工具参数、总结资料、判断下一步该做什么。

但它仍然有几个天然边界。

第一，模型本身不是持续存在的主体。它不是一直开着、一直看着世界、一直知道你现在在做什么。每次调用模型时，都要重新给它上下文。

第二，模型本身不能直接操作现实环境。它可以生成“我应该读取这个文件”“我应该调用这个 API”“我应该执行这个命令”这样的文字，但它不能自己伸手去读文件、点按钮、跑命令。

第三，模型本身不会因为一次对话就自动形成长期记忆。更严格地说，它的参数不会因为你今天告诉它一件事就立刻改变。你感觉它记得，通常是因为对话历史、摘要或外部记忆又被塞回了上下文。

第四，模型本身不会自己醒来。没有外部触发，它不会在明天早上主动想起“我要给用户发日报”。

所以，纯粹的语言模型再强，也主要停留在“生成语言”的层面。它可以说得很好，推理得很好，写得很好，但要真正解决问题，还需要一层系统把它接到工具、资料、记忆、任务和环境里。

这层系统，就是 Agent。

![Agent 位于人和模型之间](../../图示/concepts/agent-what-is/agent-mediator.png)

## Agent 让语言智能真正进入任务

Agent 可以先用一句话理解：

> Agent 是围绕语言模型搭起来的软件系统。它接收人的目标，组织上下文，调用模型，执行工具，获取知识，保存和检索记忆，并在多轮循环中推进任务。

这个定义里最重要的不是“模型”，而是“系统”。

如果没有 Agent，模型只是在一次调用里生成文本；有了 Agent，模型的输出可以变成下一步行动。模型说“需要读这个文件”，Agent 就去读；模型说“需要搜索资料”，Agent 就去搜；模型说“需要修改代码”，Agent 就在权限允许的范围内改；模型看到工具结果以后，再继续判断下一步。

这时，语言模型的“接着文字往下生成”能力，开始被放到真实任务里使用。

它不只是回答“我建议你这么做”，而是可以在系统协调下真的去做一部分事情。

```text
人的目标
-> Agent 拼上下文
-> 模型理解和判断
-> Agent 执行工具
-> 结果回到上下文
-> 模型继续判断
-> 任务继续推进
```

很多时候，大家会直接把这个整体叫 **Agent**。`Agent Runtime` 是更工程化的说法，通常指 Agent 里面负责运行循环、工具执行、状态管理和权限控制的那一层。面向普通读者，先理解 Agent 这个整体就够了；只有在需要拆架构时，才需要单独说 runtime。

## 为什么现在才开始认真讨论 Agent

Agent 这个词并不是 2023 年以后才出现的。早期 AI 和强化学习里也有 agent：一个系统在环境里观察、行动、收到反馈，再调整策略。

但今天大家讨论的 Agent，重点发生了变化。因为大语言模型让自然语言第一次变成了非常通用的任务接口。

过去很多 AI 系统是任务型的：做分类、预测、推荐、识别、排序。它们很有用，但通常不是一个可以直接对话、直接接收开放任务的系统。

大语言模型出现以后，人可以直接用自然语言描述目标，模型可以理解任务、生成计划、写代码、总结资料、选择工具参数。于是一个新的可能性出现了：

```text
模型不只回答问题
还可以成为任务循环里的判断核心
```

AutoGPT 的历史意义就在这里。它不一定好用，但它让很多人第一次直观看到：LLM 可以进入一个循环，自己拆任务、搜索、读写文件、调用工具。

后来 Claude Code、Codex、Gemini CLI 这类 coding agent 把这个方向推进到真实开发工作流里：读仓库、改文件、跑测试、根据错误继续迭代。

OpenClaw 则适合用来观察另一类 Agent：长期在线、多渠道、有记忆、有自动触发机制的个人 Agent。

这些系统不是同一种产品，但都在回答同一个问题：

> 怎么把语言模型接进真实环境，让它不只是回答，而是能持续推进任务？

![AI 历史时间线](../../图示/concepts/agent-what-is/ai-history-timeline.png)

## 一个完整 Agent 包含什么

如果只说“Agent = LLM + tools”，这个说法太粗。

工具确实很重要，但成熟 Agent 还需要上下文、知识、记忆、状态、触发、安全边界和人类监督。否则它可能能调用几个 API，但很难稳定完成复杂任务。

一个完整 Agent 大致包含这些部分：

![完整 Agent 架构图](../../图示/concepts/agent-what-is/agent-components.png)

| 模块 | 作用 | 例子 |
| --- | --- | --- |
| 渠道 / Channel | 用户从哪里和 Agent 交互。 | QQ、Telegram、Discord、Web UI、CLI、Codex App |
| 运行层 | 组织 Agent 的执行流程。 | 接收消息、拼上下文、调模型、执行工具、保存状态 |
| 模型 | 提供理解、推理、生成和决策能力。 | GPT、Claude、Gemini |
| 上下文系统 | 拼装模型当前输入。 | system prompt、历史摘要、文件、工具结果、环境信息 |
| 工具系统 | 让 Agent 对外行动。 | file、shell、web、computer、MCP、message |
| 知识系统 | 让 Agent 获取任务相关资料。 | Skill、知识库、文档、网页、数据库、RAG |
| 记忆系统 | 保存和检索长期连续性。 | MEMORY.md、daily notes、FTS/BM25、vector search |
| 权限系统 | 控制风险。 | sandbox、approval、tool policy、隔离账号 |
| 会话与任务状态 | 管理长任务和多轮协作。 | session、task state、summary、compaction |
| 触发机制 | 让 Agent 不只靠用户消息运行。 | Heartbeat、Cron、Hooks、Webhooks |

这里的“运行层”就是前面提到的 runtime。正文不必一直说 Agent Runtime，因为读者通常关心的是 Agent 这个整体。但在理解架构时，它确实很重要：它负责把模型、工具、记忆、权限和状态串起来。

## Agent 如何知道自己是谁

一个很容易被忽略的问题是：模型本身并不知道“我是谁”。

它不会天然知道：

- 我是一个 coding agent，还是一个个人助理？
- 我现在服务谁？
- 我应该遵守哪些规则？
- 我可以使用哪些工具？
- 我现在在哪个项目里？
- 我之前承诺过什么？

这些信息不是凭空出现在模型脑子里的，而是 Agent 在每次调用模型之前拼进上下文。

![当前回合上下文包](../../图示/concepts/agent-what-is/context-package.png)

一个当前回合上下文包可能包含：

| 内容 | 作用 |
| --- | --- |
| System prompt | 告诉模型身份、边界、行为方式。 |
| 身份文件 | 例如 `SOUL.md`、`IDENTITY.md`、`USER.md`。 |
| 项目规则 | 例如 `AGENTS.md`、仓库规范、课程整理规则。 |
| 用户输入 | 当前任务、问题或补充信息。 |
| 对话历史 / 摘要 | 保持当前任务连续。 |
| 记忆检索结果 | 把长期记忆中相关片段带回本轮。 |
| 文件和网页内容 | 当前任务需要看的资料。 |
| 工具定义 | 告诉模型有哪些工具、参数怎么写。 |
| 工具执行结果 | 上一轮工具调用后的结果。 |
| 当前环境 | 时间、工作目录、权限、任务状态。 |

所以，Agent 的“自我”不是模型权重里的灵魂，而是每次调用前被拼进上下文的身份、规则、目标和记忆。

这也是为什么同一个模型，放进不同 Agent 里，会表现得很不一样。

Claude 模型本身是一回事，Claude Code 作为 coding agent 又是另一回事。GPT 模型本身是一回事，Codex 作为软件工程 Agent 又是另一回事。用户最终感受到的能力，往往是“模型能力 + Agent 设计 + 工具环境 + 工作流约束”的结果。

## Agent 如何使用工具

Agent 能做事，核心靠工具。

但要注意，模型不是直接操作电脑。模型负责判断下一步需要什么工具，Agent 负责把这个判断变成真实动作。

![Agent 执行循环](../../图示/concepts/agent-execution-loop-white.png)

一次工具调用大致是这样发生的：

```text
Agent 把工具定义放进上下文
-> 模型判断是否需要调用工具
-> 模型输出 tool call
-> Agent 校验工具名、参数、权限、沙箱和审批
-> Agent 执行工具
-> 工具结果回写给模型
-> 模型继续判断或给出最终回答
```

常见工具包括：

| 工具类型 | 做什么 | 例子 |
| --- | --- | --- |
| 文件工具 | 读写本地文件。 | Read、Write、Edit |
| Shell 工具 | 执行命令。 | 跑测试、调用 CLI、执行脚本 |
| Web 工具 | 搜索和打开网页。 | 搜索资料、抓取页面 |
| Computer 工具 | 操作图形界面。 | 截图、点击、输入、滚动 |
| Message 工具 | 给人或渠道发消息。 | QQ、Telegram、Discord |
| MCP / API 工具 | 调外部服务。 | GitHub、Google Drive、数据库 |
| Media 工具 | 处理音频、图片、视频。 | TTS、ASR、FFmpeg、图片生成 |
| Sub-agent 工具 | 派生专门执行单元。 | 并行读资料、分工调查、局部验证 |

工具调用通常有两种识别方式。

一种是结构化 tool call，API 返回 `function_call`、`tool_use` 或 `tool_call` 这样的结构化对象。这种方式更稳定，也更方便做参数校验和权限控制。

另一种是文本标记解析，例如模型输出 `Action: read_file`，Agent 再从文本里解析动作。这种方式简单通用，但更容易格式错，也更容易误触发。

工具很强，也很危险。比如 OpenClaw 这类系统可以执行 shell command，这意味着它可以做很多真实事情，也意味着它有可能破坏文件、泄露信息或误操作外部系统。

所以 Agent 必须有权限系统：

- 哪些工具可以用。
- 哪些路径可以读写。
- 哪些命令需要审批。
- 外部账号和密钥如何隔离。
- 高风险动作是否需要人确认。
- 失败后是否允许自动重试。

AI 做事和 AI 搞事只有一线之隔。成熟 Agent 一定不是“模型想干什么就干什么”，而是让模型在受控边界内行动。

## Agent 如何获取知识

Agent 要解决真实问题，不能只依赖模型训练时学到的通用知识。

现实任务经常需要当前资料：项目文件、业务文档、网页、PDF、数据库、历史记录、代码仓库、会议纪要。Agent 必须能把这些资料带到模型面前。

可以把 Agent 的知识来源分成三类。

| 知识类型 | 形式 | 解决的问题 |
| --- | --- | --- |
| 模型内知识 | 模型训练时学到的通用知识。 | 常识、语言能力、一般推理。 |
| 流程知识 | Skill / SOP / 工作流说明。 | 这类任务应该按什么步骤做。 |
| 外部资料知识 | 文档、网页、知识库、数据库、项目文件。 | 当前任务需要的事实、上下文和证据。 |

### Skill：流程性知识

Skill 可以理解成 Agent 的 SOP，也可以理解成“程序化经验”。

它不是单个工具，而是一套完成任务的方法说明、脚本、模板、参考资料和资源。

比如一个视频制作 Skill，可能会告诉 Agent：

```text
读取 video/SKILL.md
-> 写 narration.json
-> 做 HTML 投影片
-> 投影片截图
-> TTS 配音
-> ASR 验证
-> FFmpeg 合成视频
```

Skill 的价值不是简单“给模型更多文字”，而是告诉 Agent：

- 什么时候应该使用这套能力。
- 先读什么资料。
- 按什么顺序做。
- 调用哪些工具。
- 产出什么格式。
- 失败时怎么处理。

Skill 通常按需读取，不需要一开始全部塞进上下文。这也是一种 Context Engineering：先把索引和触发条件给模型，必要时再读取详细流程、脚本和参考资料。

### 知识库：事实性知识

知识库提供的是事实、证据、文档和领域知识。

它可以是 Markdown 文件夹、PDF、Word、网页、代码仓库、数据库，也可以是全文索引、向量库或 RAG 系统。

Agent 通常不会把整个知识库塞给模型，而是：

```text
用户问题
-> 检索相关资料
-> 筛选和排序片段
-> 注入当前上下文
-> 模型基于这些片段回答或继续调用工具
```

Skill、知识库和记忆容易混在一起，但它们回答的问题不一样：

| 机制 | 更像什么 | 回答的问题 |
| --- | --- | --- |
| Skill | 方法和流程 | 我该怎么做？ |
| 知识库 | 事实和证据 | 我需要知道什么？ |
| 记忆 | Agent 自己的连续性 | 我之前经历过什么、承诺过什么、学到什么？ |

RAG 后面可以作为专题展开。这里先记住一件事：知识不是自然出现在模型脑子里，而是 Agent 在运行时按需检索、筛选并注入上下文。

## Agent 如何记忆

“模型有没有记忆”是最容易误解的地方。

如果说得严格一点：语言模型不会因为一次对话，就自动把这次对话写进长期记忆。它可以在当前上下文里利用你刚说的话，但这不等于它以后天然还记得。

Agent 的记忆通常是外部文件、数据库、索引和摘要系统。

![记忆进入上下文](../../图示/concepts/agent-what-is/memory-to-context.png)

常见记忆形式有几种：

| 记忆类型 | 形式 | 作用 |
| --- | --- | --- |
| 短期记忆 | 当前对话历史、当前任务状态、未压缩上下文。 | 保持本轮任务连续。 |
| 长期记忆 | `MEMORY.md`、长期偏好、重要事实、稳定决策。 | 跨 session 保持连续。 |
| 每日日志 | `memory/YYYY-MM-DD.md`、daily notes、事件流水。 | 记录发生过什么，方便后续回顾和提取长期记忆。 |
| 摘要记忆 | session summary、compaction summary。 | 上下文变长后保留关键信息。 |

一个很直观的判断是：

```text
说记住了
不等于写入记忆

写入记忆
也不等于本轮一定能用

只有被检索并注入当前上下文
模型才真正能使用
```

所以，Agent 记忆不是神秘能力，而是一条工程链路：

```text
发生事件
-> 写入外部记忆
-> 建关键词索引和语义索引
-> 查询时检索相关片段
-> 候选合并、去重、加权
-> 取 Top N 片段
-> 注入当前上下文
-> 模型基于这些记忆回答或行动
```

![记忆搜索总览](../../图示/concepts/memory-search-overview.png)

关键词搜索、语义搜索和加权的区别也很重要：

| 机制 | 擅长 | 不擅长 |
| --- | --- | --- |
| 关键词搜索 | 路径、名字、日期、术语、报错、精确字符串。 | 换一种说法可能搜不到。 |
| 语义搜索 | 意思相近、表达不同、自然语言问题。 | 精确版本号、路径、错误码可能不稳。 |
| 加权融合 | 综合字面相关、语义相关、时间、重要性、来源可信度。 | 需要调参和评估，不能保证每次都完美。 |

这里可以看出，Agent 记忆本质上很像一个小型 RAG 系统：保存、索引、检索、筛选、注入。

## Agent 什么时候会被触发

用户发消息不是 Agent 唯一的触发方式。

如果 Agent 只能在用户发消息时回应，它更像一个增强聊天助手。要长期运行，它还需要定时、事件和外部系统触发。

![Agent 触发机制](../../图示/concepts/agent-what-is/agent-triggers.png)

| 触发方式 | 含义 | 适合场景 |
| --- | --- | --- |
| 用户消息 | 人主动发起任务。 | 对话、问答、写代码、整理笔记。 |
| Heartbeat | 周期性唤醒 Agent 检查是否有事。 | 长期陪伴、follow-up、轻量巡检。 |
| Cron | 按固定时间执行任务。 | 日报、周报、定时同步、提醒。 |
| Hooks | 系统内部事件触发。 | `/new`、`/reset`、compaction、工具前后、gateway startup。 |
| Webhooks | 外部系统通过 HTTP 触发。 | GitHub、飞书、QQ、业务系统通知。 |

Heartbeat 在 Agent 语境里不是普通网络心跳，也不是让模型一直思考。

它更像：

```text
定时器到点
-> Agent 唤醒主 session
-> 检查任务规则、通知、承诺和 standing orders
-> 无事：静默
-> 有事：通知用户或继续执行
```

Cron 更适合精确定时任务，比如每天凌晨同步 GitHub、生成日报、发送提醒。

Hooks 是内部事件机制，比如 session reset、compaction 前后、工具执行前后。Webhooks 则是外部 HTTP 入口，比如 GitHub、飞书、QQ 或业务系统发来通知。

这些机制让 Agent 不只是“等人来问”，而是可以在合适的时间被唤醒，继续处理任务。

## Agent 如何长时间执行

长期任务会遇到一个现实问题：上下文窗口有限。

对话越来越长，工具结果越来越多，文件和网页越来越多，模型上下文总有放不下的时候。即使模型支持很长上下文，输入越长也越贵、越慢、越容易混乱。

这时就需要 Context Compression / Compaction。

可以这样理解：

```text
长对话 / 长任务
-> 上下文逐渐变长
-> 触发 compaction
-> 把旧历史压缩成 summary
-> 新一轮继续带 summary 工作
```

Compaction 解决的是“任务如何继续”，但它也有风险：

- 摘要可能丢细节。
- 摘要可能把错误判断写成事实。
- 后续模型只能看到 summary，看不到完整原始过程。
- 重要证据需要保留文件、日志或引用，不能只靠摘要。

所以，一个长期运行的 Agent 不只是“会记忆”就够了。它还需要会保存证据、压缩历史、恢复任务状态、管理待办，并在高风险动作前让人确认。

这也是为什么成熟 Agent 往往比 demo 复杂很多。真正难的不是让模型说出下一步，而是让系统在很多轮之后仍然知道任务进行到哪里、哪些信息可靠、哪些动作允许执行。

## 当前有哪些 Agent，它们差在哪里

现在常见 Agent 系统可以分成几类。

![当前 Agent 类型对照](../../图示/concepts/agent-what-is/agent-types.png)

| Agent / 系统 | 定位 | 特点 |
| --- | --- | --- |
| AutoGPT | 早期 autonomous agent | 展示 agent loop，但容易跑偏、卡住、成本高。 |
| Claude Code | coding agent | 读代码、改文件、跑命令，进入终端/IDE 工作流。 |
| Codex | 软件工程 agent | 面向仓库、任务、测试、PR、云端/本地工程闭环。 |
| Gemini CLI | terminal agent | 把 Gemini 接入终端，面向开发者工作流。 |
| OpenClaw | gateway-first personal agent runtime | 多渠道、长期在线、记忆、Heartbeat、Hooks、Cron。 |
| Hermes | self-hosted agent runtime | profile、skills、memory、gateway/cron，更偏长期个人化运行。 |

AutoGPT 的价值主要是历史性的。它证明了 LLM 可以进入任务循环，但也暴露了早期 autonomous agent 的问题：容易跑偏、卡住、幻觉、烧成本，也缺少稳定的权限、上下文管理和人类监督方式。

Claude Code、Codex、Gemini CLI 代表的是 coding agent 方向。它们的重点不是“陪你聊天”，而是把模型接进真实代码仓库和工程流程：读文件、改代码、跑测试、处理错误、生成 PR 或任务结果。

OpenClaw、Hermes 更像长期个人 Agent runtime。它们关注的不只是一次任务，而是多渠道入口、长期在线、记忆、自动触发和个人化运行。

这里再次回到开头那个误归因：当 Codex 很好用时，不只是 GPT 模型强；当 Claude Code 很好用时，也不只是 Claude 模型强。模型是核心智能，但真正让它进入开发工作流的，是外层 Agent 系统。

## OpenClaw 在这里是什么角色

这篇文章不是为了介绍 OpenClaw。

OpenClaw 更适合作为一个观察窗口，因为它把很多 Agent 机制展示得比较清楚：渠道、身份、Skill、工具、记忆、Heartbeat、Hooks、Cron、长期运行和安全边界。

如果用一句话概括：

> OpenClaw 不是模型本身，而是把模型能力工程化、产品化、日常化的中介层。

这个理解可以推广到 Codex、Claude Code 这类系统。它们都不是“一个模型”本身，而是围绕模型建立的软件系统。模型负责理解、推理和生成；Agent 负责把这些能力放进真实工作流。

## 常见误区

**误区一：Agent 就是大模型。**  
不对。大模型是智能核心，Agent 还包含上下文、工具、知识、记忆、触发、状态和权限。

**误区二：模型真的记住了过去。**  
多数情况下不是。连续性来自历史、摘要或外部记忆被重新注入上下文，而不是模型参数因为一次对话发生改变。

**误区三：模型说“我记住了”就真的记住。**  
如果没有写入外部记忆或未来可检索的存储，那就是“记了个寂寞”。

**误区四：接了工具就是 Agent。**  
工具只是行动能力的一部分。成熟 Agent 还需要上下文、状态、记忆、安全和任务循环。

**误区五：模型直接操作电脑。**  
模型输出工具调用意图，真正执行的是 Agent 的工具层。

**误区六：Skill、知识库、记忆是一回事。**  
不是。Skill 提供流程，知识库提供事实，记忆提供这个 Agent 自己的连续性。

**误区七：Heartbeat 就是普通网络心跳。**  
Agent 里的 Heartbeat 更像周期性唤醒主 session，用来检查是否有任务、通知或承诺需要处理。

**误区八：AutoGPT 失败说明 Agent 不行。**  
AutoGPT 证明了方向，但生产可用还需要工具稳定性、权限系统、上下文管理、监督机制和真实工作流接入。

## 最后回到定义

Agent 到底是什么？

它不是一个更神秘的大模型，也不是简单的 “LLM + tools”。

更准确地说：

> Agent 是围绕语言模型建立的软件系统。它把模型的语言智能接入上下文、工具、知识、记忆、触发和安全边界，让模型能在真实场景中持续解决问题和执行任务。

如果只记住三件事，可以记这三句：

第一，语言模型本身主要是在当前上下文里生成下一段内容，它不是天然持续存在、天然记住一切、天然能操作电脑的主体。

第二，Agent 的价值不是让模型参数更聪明，而是让模型已有的语言智能真正进入任务现场：能看上下文、用工具、查资料、记住重要信息、被事件触发、长期推进工作。

第三，一个成熟 Agent 的难点不在“让模型说下一步”，而在“让系统安全、稳定、可追踪地把下一步做出来”。
