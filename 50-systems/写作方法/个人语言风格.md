# 个人语言风格

## 一句话原则

表达要像一个认真理解过问题的人，在直接、自然地把事情讲清楚。

少写内部整理过程，多写读者真正需要的判断、解释、例子和图表。

## 整体语气

| 偏好 | 具体写法 |
| --- | --- |
| 直接 | 先说结论，再解释原因。不要绕很久才进入主题。 |
| 自然 | 像给一个聪明但不熟悉这个主题的人解释，不要像模板化公文。 |
| 有判断 | 可以直接判断“它是什么”“它不是什么”，但判断后要给理由。 |
| 不装严谨 | 不需要反复写“本文认为”“阶段性判断”。该陈述就陈述。 |
| 不营销 | 不用“颠覆”“最强”“重新定义”这类夸张词。 |
| 有感性抓手 | 可以保留直观想法，例如“模型不是记住了，是 Agent 帮它拼了上下文”。 |
| 能回到严格表达 | 直觉说法后面要补一层更准确的技术解释。 |
| 表格克制 | 表格只在需要比较、归纳、查阅时使用；开头两屏和主叙事不要被表格打断。 |
| 完整长文 | 分享版不是摘要版；重要信息要尽量保留，只是用更易读的结构和主线重新组织。 |

## 喜欢的展开方式

| 场景 | 推荐写法 |
| --- | --- |
| 开头 | 先接住读者已经听过的说法，再指出它哪里不完整。 |
| 纠偏 | 不要直接否定，先说“这个说法抓住了什么”，再说“漏掉了什么”。 |
| 解释概念 | 先讲这个东西解决了什么问题，再讲它由哪些部分组成。 |
| 讲复杂系统 | 用一条主线串起来，例如“模型缺什么，Agent 补什么”。 |
| 讲并列概念 | 可以用表格，但先确认它真的能帮助比较，不要为了显得结构化而硬塞表格。 |
| 讲流程 | 优先用图或步骤，把输入、处理、输出讲清楚。 |
| 讲案例 | 案例服务概念，不让产品介绍抢走主题。 |

## 不喜欢的表达

这些表达容易让文章像整理日志、教案或模板文档，应该避免：

```text
本文的判断是……
这篇文章的讲法是……
本节课要解决……
教学目标是……
下面我们将从几个方面展开……
经过整理，我发现……
主教案……
当前草稿……
待确认……
笔记核对……
```

更自然的替代表达：

| 不推荐 | 推荐 |
| --- | --- |
| 本文的判断是，Agent 是一套运行系统。 | Agent 更准确地说，是包在语言模型外面的一套运行系统。 |
| 这篇文章的讲法是从误区开始。 | 先从大家最常见的说法开始。 |
| 本节课要解决 Agent 是什么。 | 很多人听过 Agent，但并不清楚它和大模型到底差在哪里。 |
| 教学目标是理解 Agent 的组成。 | 要理解 Agent，先看它由哪些部分组成。 |
| 当前草稿的问题是结构混乱。 | 现在的问题是：读者读完以后，可能仍然分不清模型、工具和 Agent 的边界。 |

## 开头偏好

好的开头应该快速完成三件事：

1. 让读者觉得“这就是我困惑的问题”。
2. 让读者意识到自己原来的理解有一部分对，但不完整。
3. 给出一个更清楚的主线，让读者愿意继续读下去。

推荐开头结构：

```text
现在很多人会说：Agent 是会自己做事的 AI。
这个说法有用，但不够。
它抓住了 Agent 的行动感，却没有说明行动是怎么发生的。
更准确地说，Agent 是包在语言模型外面的一套运行系统。
```

## 概念解释偏好

解释概念时，不要只给定义。更好的顺序是：

1. 读者通常怎么理解。
2. 这个理解为什么有用。
3. 它漏掉了什么。
4. 更准确的说法是什么。
5. 一个能记住的例子。
6. 一张图或一张表。

例如解释 Agent 的记忆：

```text
很多人会以为 Agent 有记忆，是因为大模型真的记住了过去发生的事。
更准确地说，大多数情况下，模型本身没有因为一次对话而改变参数。
所谓记忆，是 Agent 把外部保存的信息检索出来，再塞回当前上下文。
模型看起来像记得，其实是这次回答前又被提醒了一遍。
```

## 分享文档的检查清单

写完重要分享文档后，检查这些问题：

- 第一屏有没有直接进入读者关心的问题。
- 有没有把内部整理过程写进正文。
- 有没有过多使用“本文”“本节课”“教案”这类词。
- 有没有只堆概念，没有讲清楚读者为什么需要知道它。
- 有没有把直觉说法和严格说法都保留下来。
- 有没有让案例服务概念，而不是让案例变成文章主角。
- 有没有只在真正需要比较、流程和查阅时使用表格和图。
- 开头两屏是不是只讲了最重要的点，没有急着堆结构。
- 分享长文有没有保留足够信息量，而不是变成几段摘要。
- 最后一段能不能让读者用一句话复述核心概念。
